AWS Data Engineer — Kumpulan Tips (tips1)

Soal 1 Domain 1: Data Ingestion and Transformation
💡 Tips

Jika kirim data (clickstream/log) ke Kinesis dari aplikasi Java butuh batching + retry + async maka pakai Kinesis Producer Library (KPL) karena KPL sudah menyediakan batching, agregasi, async, dan retry otomatis.Ingat produsen Kinesis: KPL = buffering/retry otomatis (latensi lebih tinggi); SDK PutRecord = kontrol penuh, latensi rendah; KCL = sisi consumer.

Soal 2 Domain 2: Data Store Management
💡 Tips

Jika satu data lake di S3 ingin dipakai banyak tool (Hive, Athena, Redshift, QuickSight) hemat biaya & effort maka pakai AWS Glue Data Catalog karena satu katalog metadata dipakai bersama tanpa menyalin data.Ingat: Glue Data Catalog = metastore pusat (kompatibel Hive Metastore) untuk Athena, Redshift Spectrum, EMR, Glue ETL.

Soal 3 Domain 2: Data Store Management
💡 Tips

Jika ingin hapus data lama DynamoDB otomatis tanpa ganggu read/write & minim maintenance maka pakai DynamoDB TTL karena item kedaluwarsa dihapus otomatis gratis tanpa konsumsi throughput.Ingat: TTL = atribut timestamp epoch (detik); penghapusan dalam hitungan hari, tidak instan.

Soal 4 Domain 2: Data Store Management
💡 Tips

Jika data S3 panas 30 hari lalu jarang diakses dan >1 tahun untuk compliance maka S3 Standard-IA setelah 30 hari lalu Glacier Deep Archive setelah 1 tahun karena lifecycle policy memindahkan ke kelas lebih murah sesuai pola akses.Ingat urutan termurah ke dingin: Standard → Standard-IA (min 30 hari) → Glacier Instant/Flexible → Deep Archive (retrieval berjam-jam, termurah).

Soal 5 Domain 1: Data Ingestion and Transformation
💡 Tips

Jika butuh enkripsi end-to-end PII di Kinesis dengan key milik sendiri (in-house KMS) maka pakai client-side encryption sebelum data masuk Kinesis karena hanya client-side yang menjamin kendali penuh atas kunci (bukan SSE yang dikelola AWS).Ingat: "in-house/own keys + end-to-end" → client-side encryption; SSE-KMS hanya at-rest.

Soal 6 Domain 1: Data Ingestion and Transformation
💡 Tips

Jika perlu pivot baris jadi kolom (sales per kuartal) di SQL portabel maka pakai SUM(CASE WHEN ... THEN ... END) (conditional aggregation) karena teknik ini standar SQL, tidak butuh ekstensi PIVOT/crosstab.Ingat: pivot universal = CASE di dalam agregat; crosstab butuh ekstensi tablefunc di PostgreSQL.

Soal 7 Domain 1: Data Ingestion and Transformation
💡 Tips

Jika Glue ETL tidak boleh memproses ulang data S3 yang sudah diproses maka aktifkan Glue Job Bookmarks karena bookmark melacak data yang sudah diproses dan hanya memproses data baru.Ingat kata sinyal: "jangan proses ulang / incremental" di Glue → Job Bookmarks.

Soal 8 Domain 1: Data Ingestion and Transformation
💡 Tips

Jika perlu standarkan format nomor telepon (hapus -, (), spasi) di Glue DataBrew maka pakai transformasi Find and replace karena cukup ganti karakter non-numerik jadi kosong, paling sederhana.Ingat: DataBrew = persiapan data visual tanpa koding (250+ transformasi siap pakai).

Soal 9 Domain 2: Data Store Management
💡 Tips

Jika perlu analisis waktu eksekusi query (start/end, durasi) di Redshift maka query view STL_QUERY karena STL_QUERY menyimpan riwayat eksekusi query termasuk waktu mulai & selesai.Ingat prefix tabel sistem Redshift: STL = log historis; STV = snapshot real-time; SVL/SVV = view gabungan.

Soal 10 Domain 2: Data Store Management
💡 Tips

Jika DynamoDB kena Provisioned Throughput Exception saat lonjakan traffic mendadak/besar maka pindah ke On-Demand capacity mode karena On-Demand menskala instan tanpa provisioning; Auto Scaling terlalu lambat untuk spike mendadak.Ingat: trafik tak terduga/spike → On-Demand; trafik stabil/prediktif → Provisioned (lebih murah).

Soal 11 Domain 2: Data Store Management
💡 Tips

Jika workload DynamoDB tumbuh cepat & sulit diprediksi (write/read tinggi) maka pakai On-Demand capacity karena throughput menyesuaikan otomatis tanpa hitung kapasitas manual.Ingat kapasitas: 1 WCU = 1 tulis 1KB/dtk; 1 RCU = 1 strong read 4KB/dtk (eventually consistent = 2 read 4KB/dtk).

Soal 12 Domain 1: Data Ingestion and Transformation
💡 Tips

Jika butuh pipeline Kafka (MSK) yang highly available & scalable maka deploy ≥3 broker di multi-AZ + auto-scaling, sink ke S3 via Kafka Connect karena multi-AZ memberi fault tolerance.Ingat: HA di AWS = sebar minimal 3 AZ; MSK cocok untuk payload besar/ekosistem Kafka yang sudah ada.

Soal 13 Domain 2: Data Store Management
💡 Tips

Jika ingin query SQL langsung ke data lake S3 dengan admin paling minim maka pakai Amazon Athena karena serverless, tanpa kelola server, bayar per data yang dipindai.Ingat: "SQL ke S3 + serverless/least admin" → Athena (berbasis Presto/Trino).

Soal 14 Domain 2: Data Store Management
💡 Tips

Jika load ratusan GB dari S3 ke Redshift lambat karena satu file besar maka pecah jadi banyak file kecil + COPY karena COPY memuat paralel per slice sehingga jauh lebih cepat.Ingat: jumlah file sebaiknya kelipatan jumlah slice; ukuran ideal 1 MB–1 GB terkompresi per file.

Soal 15 Domain 2: Data Store Management
💡 Tips

Jika butuh replika/HA Redshift RA3 lintas AZ maka aktifkan Redshift Multi-AZ (RA3) karena RA3 mendukung deployment Multi-AZ untuk ketahanan antar-AZ.Ingat: RA3 = compute & storage terpisah (managed storage/RMS) + dukung Multi-AZ.

Soal 16 Domain 1: Data Ingestion and Transformation
💡 Tips

Jika ada data loss di jalur Kinesis → Lambda → DynamoDB padahal kapasitas cukup maka kecilkan batch size trigger & naikkan memori Lambda karena penyebabnya Lambda timeout/lambat, bukan kapasitas.Ingat: di Lambda, menaikkan memori otomatis menaikkan CPU; timeout maks 15 menit.

Soal 17 Domain 4: Data Security and Governance
💡 Tips

Jika API butuh auth aman + kontrol akses + residensi data (GDPR) maka API Gateway + OAuth2 via Cognito user pools + usage plan/API key karena Cognito menangani autentikasi, usage plan mengontrol & melacak akses.Ingat: Cognito User Pool = autentikasi (siapa); Identity Pool = kredensial AWS sementara (akses).

Soal 18 Domain 2: Data Store Management
💡 Tips

Jika butuh Row Level Security + login akun Amazon.com maka pakai RDS PostgreSQL (native RLS) atau Redshift (RLS) + Cognito karena keduanya mendukung RLS native dan Cognito mengurus federasi login.Ingat: RLS = filter baris per user; didukung PostgreSQL & Redshift.

Soal 19 Domain 2: Data Store Management
💡 Tips

Jika perubahan DynamoDB harus mengalir near real-time ke OpenSearch maka pakai DynamoDB Streams + Lambda karena Streams menangkap perubahan dan Lambda mengirimnya ke OpenSearch.Ingat CDC DynamoDB: DynamoDB Streams/Kinesis Data Streams + Lambda untuk propagasi perubahan.

Soal 20 Domain 4: Data Security and Governance
💡 Tips

Soal 21 Domain 3: Data Operations and Support

Jika EMR butuh tahan outage AZ & biaya minim maka simpan data di S3 (via EMRFS), bukan HDFS karena S3 tahan lama lintas AZ dan cluster bisa dibuat ulang tanpa kehilangan data.Ingat: EMR tahan lama = pisahkan storage (S3/EMRFS) dari compute; HDFS hanya penyimpanan sementara.
