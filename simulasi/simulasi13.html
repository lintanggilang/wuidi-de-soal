The company needs to ensure that when a customer's analyst runs queries, they can ONLY see their own tenant's data — without relying on application-level WHERE clause filtering. Which Redshift feature provides this server-enforced row-level security?
  • A. Use Redshift Spectrum with S3 bucket-per-tenant partitioning and enable for the analyst role, satisfying strict compliance and audit requirements and enforcing encryption and fine-grained access control and meeting the latency and throughput goals of the design
  • B. Implement Row-Level Security (RLS) policies in Redshift — CREATE RLS POLICY tenant_isolation USING (tenant_id = current_setting('app.tenant_id')); ATTACH RLS POLICY to tables and enable for the analyst role. The policy automatically filters rows based on the session variable
  • C. Create separate schemas for each tenant and grant access to only their schema, satisfying strict compliance and audit requirements and integrating natively with the rest of the pipeline and handling the described workload reliably at scale
  • D. Add WHERE tenant_id = ? to all views accessed by customers, integrating natively with the rest of the pipeline and protecting the data both in transit and at rest and satisfying strict compliance and audit requirements
Jawaban Benar: B
Redshift Row-Level Security (RLS) policies transparently filter rows at query execution time: (1) CREATE RLS POLICY tenant_isolation WITH (tenant_id int) USING (tenant_id = current_setting('app.tenant_id')::int); (2) ATTACH RLS POLICY tenant_isolation ON sales TO ROLE tenant_analyst; (3) ALTER TABLE sales ROW LEVEL SECURITY ON; Saat tenant analyst menjalankan SELECT * FROM sales, Redshift automatically appends WHERE tenant_id = {their_tenant_id}. Advantages: Database-enforced (cannot bypass), transparent to queries (no application changes needed), works with any SQL client, auditable, cannot be accidentally removed by developers. Session variable (SET app.tenant_id) di-set saat connection establishment.

Opsi A: SALAH. Expensive — 200 buckets — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: BENAR.
Opsi C: SALAH. Works tapi 200 schemas = management nightmare, schema DDL changes harus di-replicate 200x.
Opsi D: SALAH. Can be bypassed jika user gains direct table access.

Jawaban Benar: A
Cross-account copy with different KMS keys requires dual key permissions: Process during S3 CopyObject: (1) S3 reads source object → needs kms:Decrypt on SOURCE key (Account A's CMK). (2) S3 prepares to write to destination → needs kms:GenerateDataKey on DESTINATION key (Account B's CMK). Key point: Objects encrypted with SSE-S3 (AWS managed) CAN be copied cross-account without KMS permissions. ONLY SSE-KMS encrypted objects require explicit KMS cross-account permissions.

Opsi A: BENAR.
Opsi B: SALAH. Keys are completely independent; re-encryption handles transition — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. "automatic" only for SSE-S3, NOT for SSE-KMS with CMK.
Opsi D: SALAH. No intermediate plaintext storage needed; happens in-process.
