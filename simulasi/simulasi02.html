Skill 4.3.2
A data engineer is confused about how S3 encrypts a 5GB file using SSE-KMS. They ask: "Does S3 send the entire 5GB file to KMS for encryption?" Explain the encryption mechanism that S3 actually uses with KMS.
  • A. KMS maintains a persistent connection to S3 and streams decryption in real-time, satisfying strict compliance and audit requirements and enforcing encryption and fine-grained access control and satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline and protecting the data both in transit and at rest
  • B. S3 uses envelope encryption: it calls KMS GenerateDataKey to get a unique plaintext data key AND its encrypted (ciphertext) copy. S3 encrypts the 5GB object locally using the plaintext data key (AES-256), then discards the plaintext key and stores the encrypted data key alongside the encrypted object. For decryption, S3 sends only the small encrypted data key to KMS for decryption, then uses the returned plaintext key to decrypt the object locally
  • C. Yes, S3 sends all data to KMS for direct encryption using the CMK and its encrypted (ciphertext) copy, protecting the data both in transit and at rest and handling the described workload reliably at scale and satisfying strict compliance and audit requirements and enforcing encryption and fine-grained access control and satisfying all of the stated requirements with minimal effort
  • D. S3 downloads the CMK from KMS and uses it directly to encrypt each file, handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline and enforcing encryption and fine-grained access control and meeting the latency and throughput goals of the design
Jawaban Benar: B
Envelope encryption adalah fundamental concept di AWS KMS: Encryption flow (PutObject with SSE-KMS): (1) S3 calls kms:GenerateDataKey(KeyId=cmk-123). (2) KMS returns: {Plaintext: "random-256-bit-key", CiphertextBlob: "encrypted-version-of-key"}. (3) S3 uses Plaintext key to AES-256 encrypt the 5GB object LOCALLY (never leaves S3). (4) S3 DISCARDS the plaintext key from memory. (5) S3 stores: [Encrypted 5GB Object] + [CiphertextBlob metadata]. Decryption flow (GetObject): (1) S3 retrieves CiphertextBlob (encrypted data key) — tiny, ~200 bytes. (2) S3 calls kms:Decrypt(CiphertextBlob). (3) KMS returns Plaintext data key. (4) S3 decrypts object locally using plaintext key. (5) S3 discards plaintext key after use. Why envelope encryption: Performance: KMS has 5,500-30,000 requests/second limit. Sending 5GB through KMS would be impossibly slow. Data never leaves S3 in plaintext. Each object gets unique data key — compromising one key doesn't expose other objects. KMS only processes tiny data keys (~256 bits), not gigabytes.

Opsi A: SALAH. No persistent connection; stateless API calls.
Opsi B: BENAR.
Opsi C: SALAH. Salah — KMS has 4KB payload limit for direct encryption — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: SALAH. CMK NEVER leaves KMS hardware (HSM).

Why is this important for data sovereignty, and what happens if the KMS key is in a different region?

  • B.   • D. KMS keys are regional. If data is in sa-east-1 but encrypted with a key in us-east-1, decryption requests must reach us-east-1, creating a technical dependency on a foreign jurisdiction and potentially violating sovereignty requirements if the foreign region becomes inaccessible

KMS keys bersifat REGIONAL — key yang dibuat di us-east-1 hanya bisa digunakan di us-east-1. Opsi C: SALAH. Salah — KMS keys tidak global — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
