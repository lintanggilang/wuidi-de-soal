An analytics engineering team is migrating two existing ingestion workflows to AWS. The first workflow is an Apache Spark application written in Scala that will run on Amazon EMR and must read data from a PostgreSQL database. The second workflow is a legacy Windows-based data integration tool that can connect to databases only through an ODBC data source name (DSN). The team wants to keep changes to each workflow minimal by using the most appropriate connectivity method for each. Which TWO statements are correct? (Select TWO.)

Jawaban benar

The Spark application on Amazon EMR should connect to PostgreSQL by using a JDBC driver, because JDBC is commonly used by Java/Scala applications and is platform-independent.

The Windows-based integration tool should use an ODBC driver and DSN to connect to PostgreSQL, because ODBC is generally language-independent but requires platform-specific drivers.

Karena

This scenario is testing your ability to choose the correct database connectivity interface when ingesting from relational sources. A JVM-based workload (like a Scala Spark job running on Amazon EMR) naturally aligns with JDBC. JDBC is the common interface used by Java and JVM languages to connect to relational databases, and it is designed to be platform-independent as long as the appropriate database-specific JDBC driver is available. A legacy Windows tool that explicitly requires an ODBC DSN must use ODBC. ODBC is commonly used by a wide variety of tools regardless of programming language, but it depends on operating system-specific driver installations (for example, installing an ODBC driver on Windows and configuring a DSN). The incorrect options either swap the properties of JDBC and ODBC, claim that drivers are unnecessary, or propose routing both workflows through a service that is not a direct, minimal-change database connectivity method for the stated requirements. Karena

S3 Lifecycle policies are the purpose-built mechanism to expire (delete) data after it reaches a specific age. Therefore, meeting a retention goal in a versioned bucket commonly requires two lifecycle behaviors: one rule action that expires the current objects after a set number of days, and another rule action that removes the noncurrent versions after they have been noncurrent for the required duration. This approach is fully managed by S3 and avoids building and operating custom deletion workflows. Karena

To call a Lambda function from Kinesis Data Streams with minimal operational effort, the most direct pattern is to configure Lambda as a stream consumer by using an event source mapping. Firehose can transform records with Lambda but cannot deliver directly to DynamoDB, and EventBridge rules are not a substitute for consuming record payloads from Kinesis Data Streams. Karena

This approach avoids long-term access keys entirely, keeps permissions centralized in IAM, and requires minimal ongoing operations because AWS handles credential vending and rotation automatically when the service assumes the role. Jawaban benar

Create and attach a customer-managed IAM policy to the Lambda execution role that allows only the required S3 actions on only the required bucket locations, such as: { "Version": "2012-10-17", "Statement": [ { "Sid": "ListOnlyHrIngestPrefix", "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::corp-data-lake", "Condition": { "StringLike": { "s3:prefix": "hr/ingest/*" } } }, { "Sid": "ReadOnlyHrIngestObjects", "Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::corp-data-lake/hr/ingest/*" }, { "Sid": "WriteOnlyHrCuratedObjects", "Effect": "Allow", "Action": "s3:PutObject", "Resource": "arn:aws:s3:::corp-data-lake/hr/curated/*" } ] }

Karena

This scenario requires permissions that are both specific to a narrow set of S3 operations and limited to specific key prefixes within a single bucket. AWS managed policies are intentionally generalized for broad use cases, so they often grant access that is wider than what a tightly controlled data pipeline should have. The least-privilege approach is to author a customer-managed IAM policy that matches exactly what the Lambda function does: • Use s3:ListBucket on the bucket ARN (not an object ARN) and restrict the list operation to only the required prefix by using a condition on s3:prefix. This aligns with how S3 evaluates List operations: the action applies to the bucket resource, while the filter is expressed as a condition. • Use s3:GetObject only on the object ARNs under the input prefix. Object-level actions must reference the object ARN pattern (bucket ARN plus the key path and wildcard). • Use s3:PutObject only on the object ARNs under the output prefix. This permits writing results without granting read access to other bucket locations. By granting only these scoped actions, the execution role will not have permissions to read from finance/raw/ (or any other unrelated prefix), which satisfies the requirement to protect sensitive data while still enabling the ETL workflow to function correctly. A retail data platform team uses Amazon Managed Workflows for Apache Airflow (Amazon MWAA) to orchestrate a nightly pipeline. One task connects to an Amazon Redshift cluster in the same VPC by using a JDBC connection over TCP port 5439 to run SQL statements. After a security hardening change, the Airflow task begins to fail with a connection timeout to the Redshift cluster endpoint. The team confirms that the Redshift cluster is healthy and that an Amazon EC2 instance in the same VPC can still connect to the cluster endpoint successfully. Which action will most likely restore the Amazon MWAA workflow with the LEAST operational overhead?

Jawaban benar

Modify the Amazon Redshift security group inbound rules to allow TCP port 5439 from the security group that is associated with the Amazon MWAA environment.

Karena

Amazon MWAA is a managed Apache Airflow service, but the tasks it runs still execute inside your VPC. In practice, that means Airflow workers are subject to the same networking controls as other workloads: VPC routing, network ACLs, and—most commonly—security groups. A JDBC connection from an Airflow task to an Amazon Redshift cluster is a direct TCP connection to the cluster endpoint (typically port 5439). If that task starts timing out immediately after a “security hardening change,” the most likely root cause is that the Redshift security group’s inbound rules no longer allow traffic from the source of the connection. The fact that an EC2 instance in the same VPC can still connect strongly suggests the cluster is reachable and healthy, and that the issue is specific to what is (and is not) allowed as a source in the Redshift security group. Updating the Redshift security group to allow inbound TCP 5439 from the security group attached to the MWAA environment is the fastest and lowest-effort remediation. It fixes the network path for the existing workflow without requiring changes to DAG code, adding new components such as NAT gateways, or introducing alternate access methods. NAT gateways address internet egress for private subnets and do not help with private, intra-VPC database connectivity. Similarly, adding IAM permissions might fix an access denied error when fetching credentials, but it cannot resolve a TCP connection timeout because IAM does not control network reachability. A healthcare analytics team is building a serverless ingestion pipeline. An AWS Lambda function runs inside private subnets in a VPC and must mount an Amazon Elastic File System (Amazon EFS) file system (through an EFS access point) to share intermediate files across concurrent function invocations. After deployment, the Lambda function logs show repeated timeouts while attempting to mount the EFS file system. The team wants to fix the issue by making the MINIMUM required network-permission change. Which change should the team make?

Jawaban benar

Add an inbound rule to the EFS mount targets’ security group that allows TCP port 2049 from the Lambda function’s security group.

Karena

When a Lambda function is configured to run in a VPC and mount Amazon EFS, the Lambda function acts as an NFS client and must be able to establish a network connection to the EFS mount targets. Amazon EFS uses the NFSv4.1 protocol, which relies on TCP port 2049. Security groups act as stateful firewalls at the network interface level. For this connectivity pattern, the mount targets must allow inbound traffic from the client. Therefore, the correct fix is to update the security group that is attached to the EFS mount targets to allow inbound TCP 2049 from the Lambda function’s security group. This approach is also the most restrictive (least privilege) because it grants access only to the Lambda function’s resources that use that specific security group, rather than opening NFS access to broad IP ranges. Changes like opening TCP 2049 to the world can make the system reachable by unintended sources, and changing unrelated ports (such as 443) does not match the protocol required to mount EFS. Similarly, adding inbound rules to the Lambda function’s security group does not solve the core requirement: EFS must accept inbound NFS connections from the Lambda function. Other options do not satisfy the requirements: enhanced fan-out addresses consumer-side read throughput only; Firehose removes replay capability because it does not store data for reprocessing; and a custom shard-scaling mechanism using UpdateShardCount increases operational overhead and is constrained by resharding limitations.
