As an e-commerce retailer, you plan to integrate clickstream data from your web servers' Java applications into Amazon Kinesis. You aim to establish a system with robust retry mechanisms, efficient batching capabilities, and asynchronous operation. Additionally, you intend to gather server logs under the same operational constraints.

Which of the following approaches would you recommend?

Jawaban benar

Utilize the Amazon Kinesis Producer Library (KPL) for Java applications to ensure efficient batching, asynchronous data transmission, and built-in retry mechanisms for both clickstream data and server logs.

Karena

Pendekatan yang direkomendasikan adalah memanfaatkan Amazon Kinesis Producer Library (KPL) untuk aplikasi Java. KPL dirancang khusus untuk menyederhanakan dan mengoptimalkan proses pengiriman data ke Amazon Kinesis Data Streams. KPL menyediakan kemampuan bawaan untuk data batching yang efisien, operasi asynchronous untuk meningkatkan throughput data, serta mekanisme retry otomatis guna menangani kegagalan pengiriman. Hal ini menjadikannya pilihan ideal untuk melakukan streaming baik clickstream data maupun server logs dari aplikasi Java Anda, sehingga data dikumpulkan dan diproses secara andal dan efisien dengan upaya pengembangan dan overhead operasional yang minimal.

💡 Tips

Jika kirim data (clickstream/log) ke Kinesis dari aplikasi Java butuh batching + retry + async maka pakai Kinesis Producer Library (KPL) karena KPL sudah menyediakan batching, agregasi, async, dan retry otomatis.Ingat produsen Kinesis: KPL = buffering/retry otomatis (latensi lebih tinggi); SDK PutRecord = kontrol penuh, latensi rendah; KCL = sisi consumer.

A financial services company maintains a vast and secure data lake on Amazon S3. They aim to analyze this data using a diverse set of tools, namely Apache Hive, Amazon Athena, Amazon Redshift, and Amazon QuickSight.

What is the most efficient method to integrate their data with these analysis tools, with an emphasis on minimizing both costs and development efforts?

Jawaban benar

Use AWS Glue to catalog the data and make it accessible to all the analysis tools.

Karena

AWS Glue adalah layanan extract, transform, and load (ETL) yang terkelola penuh sehingga memudahkan pelanggan menyiapkan dan memuat data mereka untuk analitik. Dengan membuat katalog terpusat atas data menggunakan AWS Glue, perusahaan dapat membuat data lake yang tersimpan di S3 dapat ditemukan oleh alat analisis yang ingin mereka gunakan (Apache Hive, Amazon Athena, Amazon Redshift, dan Amazon QuickSight) tanpa perlu menduplikasi data atau melakukan konfigurasi dan integrasi yang ekstensif untuk setiap alat. Pendekatan ini tidak hanya meminimalkan upaya pengembangan yang diperlukan untuk menghubungkan data dengan alat analisis, tetapi juga menekan biaya karena menghindari kebutuhan menyimpan banyak salinan data atau mengelola sumber daya komputasi tambahan. Mengunggah salinan data ke setiap alat, menghubungkan setiap alat langsung ke S3 dengan konfigurasi individual, atau mengekspor data ke instance EC2 untuk dianalisis akan menimbulkan kompleksitas lebih besar, biaya lebih tinggi, dan pekerjaan pengembangan yang lebih banyak dibandingkan integrasi yang ringkas dan hemat biaya yang disediakan AWS Glue.

💡 Tips

Jika satu data lake di S3 ingin dipakai banyak tool (Hive, Athena, Redshift, QuickSight) hemat biaya & effort maka pakai AWS Glue Data Catalog karena satu katalog metadata dipakai bersama tanpa menyalin data.Ingat: Glue Data Catalog = metastore pusat (kompatibel Hive Metastore) untuk Athena, Redshift Spectrum, EMR, Glue ETL.

As part of an initiative to manage costs and control the size of your DynamoDB table, your AWS account manager proposes implementing a solution to automatically delete old data after one month without disrupting current read and write operations.

Which approach would allow you to achieve this goal with minimal maintenance and without impacting existing read and write operations?

Jawaban benar

Utilize DynamoDB Time-to-Live (TTL) feature to automatically delete items based on a specified expiry timestamp, ensuring old data is removed after one month.

Karena

Jawaban yang benar adalah memanfaatkan fitur DynamoDB Time-to-Live (TTL) untuk menghapus item secara otomatis berdasarkan timestamp kedaluwarsa yang ditentukan. Fitur ini memungkinkan Anda mendefinisikan atribut TTL pada tabel DynamoDB untuk menetapkan waktu kedaluwarsa setiap item. DynamoDB secara otomatis menghapus item yang telah melewati TTL-nya, sehingga data lama terhapus tanpa perlu intervensi manual atau infrastruktur tambahan. Menerapkan TTL hanya membutuhkan pemeliharaan minimal dan tidak memengaruhi operasi read dan write yang berjalan, menjadikannya solusi paling efisien dan hemat biaya untuk mengelola retensi data di DynamoDB.

💡 Tips

Jika ingin hapus data lama DynamoDB otomatis tanpa ganggu read/write & minim maintenance maka pakai DynamoDB TTL karena item kedaluwarsa dihapus otomatis gratis tanpa konsumsi throughput.Ingat: TTL = atribut timestamp epoch (detik); penghapusan dalam hitungan hari, tidak instan.

You are a data engineer managing a data lake on Amazon S3. Your organization has a large volume of data ingested daily, and most of the data is only actively accessed within the first 30 days. After that, it is infrequently accessed for analysis and auditing purposes, and any data older than one year is rarely accessed but must be retained for compliance reasons. To optimize storage costs, you want to implement a lifecycle policy for these data objects.

Jawaban benar

Move objects to S3 Standard-IA (Infrequent Access) storage class after 30 days

Transition objects to S3 Glacier Deep Archive after one year

Karena

Memindahkan objek ke S3 Standard-IA setelah 30 hari membantu menekan biaya untuk data yang jarang diakses, sementara S3 Glacier Deep Archive menyediakan storage class yang hemat biaya untuk data jangka panjang yang sangat jarang diakses namun perlu disimpan demi kepatuhan.

💡 Tips

Jika data S3 panas 30 hari lalu jarang diakses dan >1 tahun untuk compliance maka S3 Standard-IA setelah 30 hari lalu Glacier Deep Archive setelah 1 tahun karena lifecycle policy memindahkan ke kelas lebih murah sesuai pola akses.Ingat urutan termurah ke dingin: Standard → Standard-IA (min 30 hari) → Glacier Instant/Flexible → Deep Archive (retrieval berjam-jam, termurah).

Your organization processes datasets containing personally identifiable information (PII) and is considering the implementation of Amazon Kinesis Data Streams for a publish-subscribe (pub-sub) system. Due to regulatory obligations, it's required that the data be encrypted end-to-end, utilizing an in-house key management system.

Which TWO of the following strategies would effectively comply with the encryption and key management stipulations?

Jawaban benar

Incorporate client-side encryption for data prior to its publication to Amazon Kinesis Data Streams, employing keys from your internal key management system, and configure Kinesis Data Streams to utilize these keys for encryption at rest.

Implement client-side encryption for the data before sending it to Amazon Kinesis Data Streams, utilizing your proprietary key management system for both in-transit and at-rest encryption.

Karena

Strategi yang benar adalah:

Menerapkan client-side encryption pada data sebelum dikirim ke Amazon Kinesis Data Streams, dengan memanfaatkan sistem manajemen kunci milik Anda sendiri untuk enkripsi baik saat in-transit maupun at-rest.

Menerapkan client-side encryption pada data sebelum dipublikasikan ke Amazon Kinesis Data Streams, menggunakan kunci dari sistem manajemen kunci internal Anda, dan mengonfigurasi Kinesis Data Streams untuk menggunakan kunci tersebut bagi enkripsi at-rest.

Opsi-opsi ini memastikan organisasi memenuhi persyaratan regulasi untuk enkripsi end-to-end menggunakan sistem manajemen kunci internal. Dengan mengenkripsi data secara client-side sebelum masuk ke Kinesis Data Streams dan menggunakan kunci yang dikelola secara internal, organisasi mempertahankan kendali penuh atas proses enkripsi dan pengelolaan kunci, selaras dengan mandat untuk memanfaatkan sistem manajemen kunci internal saat menangani dataset PII.

💡 Tips

Jika butuh enkripsi end-to-end PII di Kinesis dengan key milik sendiri (in-house KMS) maka pakai client-side encryption sebelum data masuk Kinesis karena hanya client-side yang menjamin kendali penuh atas kunci (bukan SSE yang dikelola AWS).Ingat: "in-house/own keys + end-to-end" → client-side encryption; SSE-KMS hanya at-rest.

A database analyst needs to transform rows into columns in a PostgreSQL database to summarize sales data by quarter for each product. The sales data is stored in a table named sales_data with columns product_id, quarter, and sales_amount. The analyst wants to create a report that displays each product_id with columns for each quarter (Q1, Q2, Q3, Q4) showing the sales amount for each quarter. Which SQL query will correctly pivot the data to meet the analyst's requirements?

Jawaban benar

SELECT

Karena

Query SQL yang tepat untuk mengubah baris menjadi kolom (pivot) di database PostgreSQL guna merangkum data penjualan per kuartal untuk setiap produk adalah dengan menggunakan agregasi bersyarat berupa statement CASE di dalam fungsi SUM. Teknik ini tidak bergantung pada ekstensi khusus PostgreSQL dan berlaku luas untuk melakukan pivot data di SQL. Dengan mengagregasi jumlah penjualan secara bersyarat berdasarkan kuartal, query menghasilkan kolom terpisah untuk setiap kuartal (Q1, Q2, Q3, Q4), dengan setiap kolom menampilkan jumlah penjualan kuartal tersebut untuk tiap produk. Pendekatan ini sederhana dan tidak mengasumsikan penggunaan fitur SQL non-standar atau memerlukan pemasangan modul tambahan, sehingga menjadi solusi yang paling universal. Metode lain, seperti menggunakan fungsi PIVOT atau fungsi crosstab, mungkin tidak langsung didukung di PostgreSQL atau membutuhkan pengetahuan maupun ekstensi tertentu yang belum tentu tersedia atau dikenal semua pengguna. Selain itu, mengagregasi jumlah penjualan ke dalam sebuah array tidak memenuhi kebutuhan akan kolom terpisah untuk tiap kuartal, sehingga metode agregasi bersyarat paling sesuai untuk skenario yang dijelaskan.

💡 Tips

Jika perlu pivot baris jadi kolom (sales per kuartal) di SQL portabel maka pakai SUM(CASE WHEN ... THEN ... END) (conditional aggregation) karena teknik ini standar SQL, tidak butuh ekstensi PIVOT/crosstab.Ingat: pivot universal = CASE di dalam agregat; crosstab butuh ekstensi tablefunc di PostgreSQL.

Dengan job bookmarks diaktifkan, AWS Glue melacak progres job ETL dan memastikan hanya data baru yang diproses pada eksekusi job berikutnya. Pendekatan ini menghilangkan kebutuhan logika kustom atau infrastruktur tambahan untuk mengelola file yang sudah diproses, menjadikannya solusi paling sederhana dan efisien untuk memastikan data tidak diproses ulang. Oleh karena itu, mengaktifkan fitur AWS Glue job bookmarks adalah pilihan terbaik untuk menjaga kesinambungan pemrosesan data sekaligus meminimalkan kompleksitas dan usaha.

💡 Tips

Jika Glue ETL tidak boleh memproses ulang data S3 yang sudah diproses maka aktifkan Glue Job Bookmarks karena bookmark melacak data yang sudah diproses dan hanya memproses data baru.Ingat kata sinyal: "jangan proses ulang / incremental" di Glue → Job Bookmarks.

A data engineering team is using AWS Glue DataBrew to clean a dataset containing customer feedback. The dataset includes a column with mixed formatting for phone numbers (e.g., "123-456-7890", "(123) 456-7890", "1234567890"). The team needs to standardize the phone numbers into a single format ("1234567890") before analysis. Which AWS Glue DataBrew transformation should the team use to accomplish this task in the most straightforward manner?

Jawaban benar

Use the "Find and replace" transformation to remove dashes, spaces, and parentheses.

Karena

Transformasi yang paling langsung dan efektif untuk menstandarkan nomor telepon menjadi satu format numerik dengan menghapus tanda hubung, tanda kurung, dan spasi adalah transformasi "Find and replace". Transformasi ini memungkinkan tim menentukan karakter yang akan dicari (misalnya tanda hubung "-", tanda kurung "()", dan spasi " ") lalu menggantinya dengan string kosong, sehingga karakter-karakter tersebut terhapus dari nomor telepon. Dengan menerapkan transformasi ini secara berulang untuk tiap jenis karakter yang ingin dihapus, tim dapat menstandarkan format nomor telepon di seluruh dataset secara efisien.

Opsi yang menyarankan penggunaan transformasi "Format phone number" mungkin tampak masuk akal, tetapi AWS Glue DataBrew tidak menyediakan transformasi khusus bernama "Format phone number" yang secara otomatis menstandarkan nomor telepon ke format tertentu. Kebutuhan ini menyangkut penghapusan karakter non-numerik, yang lebih tepat dicapai dengan fungsi find and replace.

Transformasi "Extract pattern" berguna untuk menarik pola tertentu dari teks menggunakan regex, tetapi dalam kasus ini akan membutuhkan pola kompleks untuk mengecualikan berbagai karakter non-numerik sambil memastikan seluruh bagian nomor telepon tertangkap dengan akurat. Pendekatan ini lebih rumit dibandingkan langsung menghapus karakter yang tidak diinginkan.

Transformasi "Split column" dapat memisahkan data pada sebuah kolom menjadi beberapa kolom berdasarkan pembatas. Meskipun bisa dipakai sebagai bagian dari proses menghapus karakter non-numerik dengan memisah lalu menggabungkan bagian numeriknya, metode ini lebih merepotkan dan kurang langsung dibandingkan sekadar mengganti karakter yang tidak diperlukan.

Oleh karena itu, transformasi "Find and replace" adalah metode paling sederhana dan efektif untuk membersihkan nomor telepon pada dataset, menjadikannya pilihan terbaik untuk skenario yang dijelaskan.

💡 Tips

Jika perlu standarkan format nomor telepon (hapus -, (), spasi) di Glue DataBrew maka pakai transformasi Find and replace karena cukup ganti karakter non-numerik jadi kosong, paling sederhana.Ingat: DataBrew = persiapan data visual tanpa koding (250+ transformasi siap pakai).

A data engineer needs to optimize query performance on an Amazon Redshift cluster. They want to analyze query execution times to identify long-running queries and assess the impact of different optimization strategies. Which Amazon Redshift system table or view should the data engineer query to obtain detailed information about query execution, including start and end times, to facilitate this analysis?

Jawaban benar

STL_QUERY

Karena

Untuk menganalisis waktu eksekusi query dan mengidentifikasi query yang berjalan lama pada cluster Amazon Redshift, system view yang paling tepat untuk ditanyakan adalah STL_QUERY. View STL_QUERY menyediakan informasi rinci tentang eksekusi query, termasuk teks query, waktu mulai, waktu selesai, dan durasi eksekusi. System view ini dirancang khusus untuk memantau dan menganalisis performa query, sehingga menjadi sumber daya berharga bagi data engineer yang ingin mengoptimalkan waktu eksekusi query dan mengevaluasi efektivitas berbagai strategi optimasi.

STV_BLOCKLIST adalah system table yang menyediakan informasi tentang blok yang saat ini ditandai untuk dihapus pada cluster. View ini berguna untuk memahami operasi vacuum, tetapi bukan untuk menganalisis performa query.

STV_TBL_PERM menampilkan data snapshot mengenai kondisi terkini tabel permanen, termasuk informasi penggunaan ruang disk. Meskipun dapat membantu menilai pemanfaatan penyimpanan, view ini tidak memberikan wawasan tentang waktu eksekusi query.

STL_WLM_QUERY: berisi informasi tentang query yang ditangani oleh sistem workload management (WLM), tetapi tidak sekomprehensif itu untuk analisis waktu eksekusi yang rinci.

Oleh karena itu, untuk tujuan khusus menganalisis waktu eksekusi query guna mengidentifikasi dan mengoptimalkan query yang berjalan lama, menanyakan system view STL_QUERY menawarkan pendekatan paling langsung dan rinci untuk memperoleh informasi yang diperlukan.

💡 Tips

Jika perlu analisis waktu eksekusi query (start/end, durasi) di Redshift maka query view STL_QUERY karena STL_QUERY menyimpan riwayat eksekusi query termasuk waktu mulai & selesai.Ingat prefix tabel sistem Redshift: STL = log historis; STV = snapshot real-time; SVL/SVV = view gabungan.

As an online retailer with a website featuring millions of products, you recently experienced Provisioned Throughput Exceptions from DynamoDB during a significant sale on a particular electronic item. Anticipating an upcoming sale that will be three times larger, you seek recommendations to ensure your website can handle the increased load without encountering similar issues.

What would be your course of action to prepare for the surge in traffic?

Jawaban benar

Transition to a DynamoDB On-Demand capacity mode, allowing your database to scale automatically to accommodate the load without manual intervention or provisioning.

Karena

Pendekatan yang direkomendasikan adalah beralih ke mode kapasitas DynamoDB On-Demand. Opsi ini memungkinkan database Anda otomatis menyesuaikan skala untuk mendukung beban kerja menjelang penjualan tanpa intervensi manual apa pun. Kapasitas On-Demand ideal untuk beban kerja yang tidak dapat diprediksi, seperti lonjakan trafik mendadak saat event penjualan, karena menyesuaikan kapasitas secara real-time guna menjaga performa dan menghindari Provisioned Throughput Exceptions. Metode ini memberikan pengalaman yang mulus dengan menghilangkan kebutuhan memperkirakan dan menyediakan throughput di muka, memastikan situs web Anda dapat menangani lonjakan permintaan yang diperkirakan terjadi selama penjualan.

Auto Scaling tidak dianggap sebagai jawaban terbaik dalam skenario ini terutama karena tantangan khusus berupa event penjualan yang diperkirakan tiga kali lebih besar dari sebelumnya, di mana lonjakan permintaan dan trafik terjadi mendadak dan signifikan. Meskipun DynamoDB Auto Scaling efektif untuk menyesuaikan kapasitas secara bertahap sesuai pola akses yang berubah, ia tidak selalu dapat menaikkan skala cukup cepat untuk mengakomodasi lonjakan trafik yang mendadak dan masif, seperti yang diperkirakan selama event penjualan besar. Auto Scaling menyesuaikan unit kapasitas berdasarkan metrik dan ambang pemanfaatan yang telah ditentukan, yang dapat menimbulkan jeda antara mulainya peningkatan permintaan dan tindakan penskalaan, sehingga berpotensi menimbulkan Provisioned Throughput Exceptions pada periode peningkatan trafik yang cepat.

💡 Tips

Jika DynamoDB kena Provisioned Throughput Exception saat lonjakan traffic mendadak/besar maka pindah ke On-Demand capacity mode karena On-Demand menskala instan tanpa provisioning; Auto Scaling terlalu lambat untuk spike mendadak.Ingat: trafik tak terduga/spike → On-Demand; trafik stabil/prediktif → Provisioned (lebih murah).

Given the fast-paced nature of the game, you anticipate around 400 write operations per second to your database. Furthermore, there is a high demand for accessing this game data, with expectations of around 1800 eventually consistent reads per second.

How should you provision your DynamoDB table to meet these requirements?

Provision the table using on-demand capacity to automatically scale read and write throughput to accommodate the expected 400 writes per second and 1800 eventually consistent reads per second without manual intervention.

Model ini menawarkan solusi fleksibel dan hemat biaya untuk menangani beban kerja yang bervariasi, terutama bagi aplikasi dengan pola trafik yang tidak dapat diprediksi. Kapasitas on-demand menghilangkan kebutuhan menghitung dan menyesuaikan unit kapasitas secara manual, memastikan database dapat memenuhi kebutuhan performa aplikasi sekaligus mengelola biaya secara efektif.

A data engineering team is tasked with setting up a reliable and scalable streaming data pipeline using Amazon Managed Streaming for Apache Kafka (MSK) to process real-time data from various sources. The goal is to ensure that the data can be ingested efficiently, processed, and then stored in Amazon S3 for further analysis. Considering best practices for high availability, scalability, and cost-effectiveness, which of the following configurations should the team implement?

Jawaban benar

Deploy an MSK cluster with at least three broker nodes spread across multiple AZs and enable auto-scaling based on CPU utilization. Utilize Amazon Kinesis Data Firehose for data ingestion, Apache Kafka Connect with the S3 sink connector for moving processed data to S3, and manage stream processing using Apache Spark.

Karena

Untuk pipeline data streaming yang andal dan skalabel menggunakan Amazon MSK, penting untuk mengikuti praktik terbaik yang memastikan ketersediaan tinggi, skalabilitas, dan efisiensi biaya:

High Availability: Men-deploy cluster MSK dengan setidaknya tiga broker node yang tersebar di beberapa Availability Zone (AZ) memastikan layanan tetap tersedia meskipun salah satu AZ mengalami gangguan. Konfigurasi ini menawarkan toleransi kesalahan dan kesinambungan layanan yang lebih baik dibandingkan pengaturan pada satu AZ atau dengan node yang lebih sedikit.

Scalability: Mengaktifkan auto-scaling berdasarkan utilisasi CPU memungkinkan sistem otomatis menyesuaikan sumber daya sesuai kebutuhan beban kerja. Pendekatan ini menyeimbangkan performa dan biaya, menaikkan skala saat diperlukan untuk menangani beban puncak dan menurunkannya pada periode aktivitas rendah.

Ingesti dan Pemrosesan Data yang Efisien: Memanfaatkan Amazon Kinesis Data Firehose untuk ingesti data menyederhanakan proses memuat data streaming secara andal ke layanan AWS seperti S3. Apache Kafka Connect dengan S3 sink connector menawarkan solusi tangguh untuk memindahkan data yang telah diproses ke S3 dengan mulus. Mengelola stream processing dengan Apache Spark memungkinkan pemrosesan dan analisis data real-time yang efisien, memanfaatkan kemampuan pemrosesan cepat dan kemudahan penggunaan Spark.

Opsi lain tidak sepenuhnya memanfaatkan kemampuan layanan AWS untuk ketersediaan tinggi dan skalabilitas, atau menyarankan konfigurasi yang mungkin tidak memberikan keseimbangan terbaik antara performa, keandalan, dan efisiensi biaya. Misalnya, men-deploy pada satu AZ atau menonaktifkan auto-scaling dapat memicu potensi gangguan layanan dan meningkatkan biaya operasional.

💡 Tips

Jika butuh pipeline Kafka (MSK) yang highly available & scalable maka deploy ≥3 broker di multi-AZ + auto-scaling, sink ke S3 via Kafka Connect karena multi-AZ memberi fault tolerance.Ingat: HA di AWS = sebar minimal 3 AZ; MSK cocok untuk payload besar/ekosistem Kafka yang sudah ada.

You are tasked with loading several hundred gigabytes of data daily from Amazon S3 into Amazon Redshift. The data is currently stored in a single file, and the loading process is proving to be prohibitively slow.

Which approach would most effectively optimize the data loading process?

Jawaban benar

Split the large file into multiple smaller files and use the Redshift COPY command to load them concurrently.

Karena

Pendekatan paling efektif untuk mengoptimalkan proses pemuatan data adalah memecah file besar menjadi beberapa file yang lebih kecil dan menggunakan perintah COPY Redshift untuk memuatnya secara bersamaan. A media company is processing video metadata through a data engineering pipeline on AWS. The pipeline uses AWS Lambda functions triggered by messages in an Amazon Simple Queue Service (SQS) queue. Each message contains information for a Lambda function to process video metadata. Occasionally, some messages fail to be processed due to temporary issues such as throttling or transient errors in the Lambda function. To ensure that failed messages are not lost and can be analyzed and reprocessed later, what should the company implement in their SQS and Lambda setup?

Jawaban benar

Enable an SQS dead-letter queue to capture messages that fail to be processed after a specified number of attempts.

Karena

Menerapkan SQS dead-letter queue (DLQ) adalah solusi optimal untuk menangkap pesan yang gagal diproses setelah sejumlah upaya tertentu. Dead-letter queue menyediakan cara untuk menyisihkan dan mengisolasi pesan yang tidak dapat diproses dengan sukses, sehingga dapat disimpan dengan aman untuk analisis atau pemrosesan ulang di kemudian hari. Dengan mengonfigurasi dead-letter queue untuk antrian SQS asli, perusahaan memastikan setiap pesan yang tidak dapat diproses oleh fungsi Lambda, akibat throttling, kesalahan sementara, atau masalah lain, tidak hilang. Pendekatan ini memungkinkan penanganan kesalahan dan pemecahan masalah yang lebih baik dengan menjaga pesan yang gagal diproses, memfasilitasi pemeriksaannya untuk memahami penyebab kegagalan dan menentukan tindakan korektif yang tepat.

Mengonfigurasi Amazon CloudWatch Alarms berguna untuk pemantauan dan pemberitahuan, tetapi tidak menangani penanganan atau penyimpanan pesan yang gagal. Alarm dapat memberi tahu administrator tentang masalah tetapi tidak menyediakan mekanisme untuk menyimpan dan memproses ulang pesan yang gagal.

Menambah timeout dan alokasi memori fungsi Lambda mungkin mengurangi jumlah kegagalan akibat keterbatasan sumber daya tetapi tidak menawarkan solusi menyeluruh untuk menangani pesan yang gagal karena alasan lain. Cara ini juga tidak menyediakan mekanisme untuk menangani pesan yang tidak dapat diproses setelah beberapa kali percobaan.

Menggunakan Amazon Kinesis Data Streams alih-alih SQS memperkenalkan arsitektur berbeda untuk menangani data streaming. Meskipun Kinesis memiliki keunggulan untuk kasus penggunaan tertentu, ia tidak secara langsung menyelesaikan masalah pengelolaan dan pemrosesan ulang pesan yang gagal diproses. Kebutuhan khusus menangani pesan gagal dalam pengaturan berbasis antrian lebih langsung dipenuhi dengan menerapkan dead-letter queue di SQS.

Oleh karena itu, mengaktifkan SQS dead-letter queue adalah metode paling langsung dan efektif untuk memastikan pesan yang gagal diproses oleh AWS Lambda tidak hilang dan dapat ditangani dengan tepat, selaras dengan praktik terbaik untuk pipeline pemrosesan data yang tangguh dan resilien.

💡 Tips

Jika pesan SQS yang gagal diproses Lambda tak boleh hilang maka pakai Dead-Letter Queue (DLQ) karena DLQ menampung pesan yang gagal setelah sejumlah percobaan untuk dianalisis/diproses ulang.Ingat: DLQ menangkap pesan gagal setelah maxReceiveCount tercapai.

A regional hospital network's analytics team stores daily compliance audit exports in an Amazon S3 bucket under the prefix audit/. The objects are frequently accessed for the first month, are rarely accessed after 60 days, and must remain available for long-term retention. The team needs to reduce storage costs automatically without affecting objects in other prefixes.

Which solution will meet these requirements with the LEAST operational overhead?

Jawaban benar

Create an S3 Lifecycle rule for the audit/ prefix to transition objects to S3 Standard-IA after 60 days and to a Glacier storage class after 6 months.

Karena

Amazon S3 Lifecycle adalah fitur terkelola untuk menerapkan tindakan berbasis waktu terhadap objek dalam sebuah bucket. Sebuah lifecycle rule dapat menyertakan filter, seperti prefix atau object tags, dan dapat menggunakan Transition action untuk memindahkan objek yang cocok ke storage class berbiaya lebih rendah seiring bertambahnya usia objek. Hal ini cocok untuk beban kerja dengan pola akses yang dapat diprediksi, seperti audit export yang ditanyakan sesaat setelah dibuat lalu kebanyakan disimpan untuk kepatuhan atau pencarian historis.

Transition action berbeda dari expiration action. Transition mengubah storage class suatu objek, sedangkan expiration menghapus objek, versi lama, atau multipart upload yang tidak lengkap. Storage Lens berguna untuk visibilitas dan analisis biaya di seluruh organisasi, tetapi bersifat observasional alih-alih mekanisme otomatisasi untuk tiering. Fungsi Lambda terjadwal merupakan anti-pattern umum untuk kasus penggunaan ini karena membutuhkan kode kustom, pemantauan, retry, dan pengelolaan izin padahal S3 sudah menyediakan otomatisasi lifecycle. Untuk informasi lebih lanjut, lihat Overview of S3 Lifecycle management dan Elements of an S3 Lifecycle configuration.

💡 Tips

Jika perlu turunkan biaya hanya untuk prefix tertentu (audit/) otomatis maka buat S3 Lifecycle rule bertarget prefix (Standard-IA 60 hari → Glacier 6 bulan) karena lifecycle bisa dibatasi per prefix tanpa pengaruhi objek lain.Ingat: Lifecycle rule bisa difilter per prefix/tag — transisi & expiration berdasar umur objek.
