By scoping the rule to a prefix such as staging/, the lifecycle policy applies only to the temporary datasets that require cleanup. Your answer is correct
Create and attach a customer-managed IAM policy to the Lambda execution role that allows only the required S3 actions on only the required bucket locations, such as: { "Version": "2012-10-17", "Statement": [ { "Sid": "ListOnlyHrIngestPrefix", "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::corp-data-lake", "Condition": { "StringLike": { "s3:prefix": "hr/ingest/*" } } }, { "Sid": "ReadOnlyHrIngestObjects", "Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::corp-data-lake/hr/ingest/*" }, { "Sid": "WriteOnlyHrCuratedObjects", "Effect": "Allow", "Action": "s3:PutObject", "Resource": "arn:aws:s3:::corp-data-lake/hr/curated/*" } ] }

Correct. This policy scopes listing to the hr/ingest/ prefix by using an s3:prefix condition on s3:ListBucket, allows reads only for objects in hr/ingest/, and allows writes only for objects in hr/curated/. Because there are no permissions that grant access to finance/raw/, the Lambda role cannot read that sensitive prefix.

Explanation
Incorrect. Although S3 access points can help manage access at scale, attaching AmazonS3FullAccess still violates the least-privilege requirement because the role remains broadly authorized at the identity-policy level. Overall explanation
This scenario requires permissions that are both specific to a narrow set of S3 operations and limited to specific key prefixes within a single bucket. The least-privilege approach is to author a customer-managed IAM policy that matches exactly what the Lambda function does: • Use s3:ListBucket on the bucket ARN (not an object ARN) and restrict the list operation to only the required prefix by using a condition on s3:prefix. Object-level actions must reference the object ARN pattern (bucket ARN plus the key path and wildcard). • Use s3:PutObject only on the object ARNs under the output prefix. By granting only these scoped actions, the execution role will not have permissions to read from finance/raw/ (or any other unrelated prefix), which satisfies the requirement to protect sensitive data while still enabling the ETL workflow to function correctly. Explanation
Correct. Amazon MWAA runs inside a VPC and uses security groups to control network traffic for its schedulers and workers. Explanation
Incorrect. VPC endpoints are used to privately access AWS service APIs (control plane) and supported service endpoints. Creating a VPC endpoint does not replace the need for network connectivity and allowed inbound rules to the cluster endpoint for database connections.
Your answer is incorrect
Create a NAT gateway in a public subnet and update the route tables for the Amazon MWAA private subnets to route 0.0.0.0/0 traffic through the NAT gateway.
Explanation
Incorrect. A NAT gateway provides outbound internet access for resources in private subnets. Overall explanation
Amazon MWAA is a managed Apache Airflow service, but the tasks it runs still execute inside your VPC. If that task starts timing out immediately after a “security hardening change,” the most likely root cause is that the Redshift security group’s inbound rules no longer allow traffic from the source of the connection. NAT gateways address internet egress for private subnets and do not help with private, intra-VPC database connectivity. Similarly, adding IAM permissions might fix an access denied error when fetching credentials, but it cannot resolve a TCP connection timeout because IAM does not control network reachability.
