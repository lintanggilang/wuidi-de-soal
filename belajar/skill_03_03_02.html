Skill 3.3.2: Logging and monitoring solutions

Ringkasan

Skill ini termasuk dalam Domain 3: Operations & Support (Task 3.3: Maintain and monitor data pipelines), dengan fokus pada logging and monitoring solutions. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon CloudWatch
Monitoring metrik, alarm, dan dashboard untuk sumber daya & aplikasi AWS.

Poin-Poin Kunci

  • AWS Glue continuous logging delivers real-time logs to CloudWatch Logs with minimal latency. Setting retention to 730 days (2 years) ensures compliance without manual management. CloudWatch Logs Insights provides serverless SQL-like querying for audit investigations. Option B: Custom S3 logging requires additional code and doesn't capture Glue's native driver/executor logs. Option C: OpenSearch adds significant cost and operational overhead for infrequent audit queries. Option D: Nightly exports create operational complexity and potential data loss if exports fail.
  • CloudWatch cross-account observability is the AWS-native solution for centralized multi-account monitoring with minimal operational effort. It allows a monitoring account to view and query logs, metrics, and traces from linked source accounts without data movement. Option A: Subscription filters + Kinesis works but requires managing streams, delivery failures, and IAM policies across accounts. Option C: CloudWatch agent cannot directly write to cross-account log groups without complex networking setup. Option D: Nightly exports are not real-time and require managing Lambda functions in every account.
  • AWS X-Ray with active tracing provides a distributed trace ID that spans multiple services. Embedding this trace ID in structured JSON logs creates end-to-end traceability that correlates log entries across Lambda invocations and downstream services. CloudWatch Logs Insights can then query by trace_id to reconstruct the full processing path. Option B: Manual UUID passing works but requires custom implementation in every service and doesn't integrate with AWS tracing tools. Option C: Lambda request ID is unique per invocation and cannot trace across multiple invocations. Option D: CloudWatch Logs has no automatic correlation capability based on log group prefixes.
  • CloudWatch Logs data protection policies automatically detect and mask sensitive data (like credentials, credit card numbers, API keys) using managed data identifiers. Masked data appears as asterisks to unauthorized viewers while maintaining audit trails for authorized users. Option B: Lambda-based redaction is complex, adds latency, and requires maintaining custom regex patterns. Option C: IAM restrictions don't mask the sensitive data; anyone with access still sees it. Option D: Encryption protects data at rest but doesn't mask sensitive content from authorized viewers of the logs.
  • For CloudWatch Logs metric filters, a simple quoted string pattern performs a text match anywhere in the log event. "java.lang.OutOfMemoryError" will match any log line containing that exact text, which is how Glue (Spark/Java) reports OOM errors. Option A: JSON filter syntax { $.errorType } only works with structured JSON logs; Glue continuous logging outputs mixed formats. Option C: Space-delimited filter syntax doesn't support wildcards within field values in this format. Option D: JSON filter syntax with AND requires the logs to be in structured JSON format with specific field names, which Glue's native logs don't follow.
  • Configuring an EMR cluster with a log URI (S3 path) ensures that all cluster logs (YARN application logs, step logs, bootstrap action logs) are automatically pushed to S3 every 5 minutes and upon cluster termination. KMS encryption ensures log security. Option B: CloudWatch agent installation adds complexity and may not capture all EMR-specific log types (bootstrap actions). Option C: HDFS storage is ephemeral and lost when the cluster terminates. Option D: EMR Managed Scaling is for capacity management, not log preservation.
  • This CloudWatch Logs Insights query correctly uses the supported syntax: fields to select displayed columns, filter with like and regex to narrow results by ERROR level and specific job log stream, sort by timestamp descending, and limit for manageable output. Option B: SQL syntax is not supported in CloudWatch Logs Insights (it uses its own query language). Option C: stats provides aggregated counts, not individual log entries needed for investigation. Option D: The parse command syntax is incorrect and the display command doesn't exist in Logs Insights.
  • CloudWatch Logs encryption is configured at the log group level using associate-kms-key. The KMS key policy must grant the logs.{region}.amazonaws.com service principal permissions to generate data keys and decrypt. This encrypts all log data at rest in that log group. Option B: Services send logs to CloudWatch Logs in plaintext; encryption is handled by the CloudWatch Logs service, not the producing services. Option C: There is no account-level default encryption setting for CloudWatch Logs via AWS Config. Option D: Redirecting to S3 changes the storage location entirely and doesn't encrypt CloudWatch Logs in place.
  • AWS X-Ray integrates with Step Functions and Lambda to provide distributed tracing. When X-Ray tracing is enabled, trace IDs propagate through the entire execution, and the service map visualizes the complete flow including latency at each step. This provides true end-to-end traceability. Option B: Manual cross-referencing of separate log groups is time-consuming and error-prone without correlation IDs. Option C: CloudWatch ServiceLens works with X-Ray traces but doesn't automatically correlate without X-Ray being enabled first. Option D: Custom DynamoDB tracking adds code complexity and still requires custom tooling to visualize.
  • The multi_line_start_pattern parameter in the CloudWatch agent configuration defines a regex pattern that identifies the beginning of a new log event. Lines not matching this pattern are appended to the previous event. For Java logs, a common pattern is the timestamp (e.g., "^\\d{4}-\\d{2}-\\d{2}") which ensures stack traces are grouped with their originating error line. Option B: max_event_size limits event size but doesn't handle multi-line detection. Option C: Separate log groups don't solve the multi-line parsing problem. Option D: "utf-8-multi" is not a valid encoding option for the CloudWatch agent.
