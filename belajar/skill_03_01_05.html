Skill 3.1.5: Consume and maintain data APIs

APIversioningmaintenance

Summary

Skill this including in Domain 3: Operations & Support (Task 3.1: Automate data processing), with fokus on consume and maintain data apis. Materi berikut merangkum service AWS that relevan beserta concept important that needs kamu kuasai for topik this.

Key Services & Concepts

Amazon API Gateway
Manages REST/HTTP/WebSocket API: throttling, otorisasi, caching, and integration backend.

Key Points

  • Custom domain names with base path mappings enables routing path-based (/v1, /v2) to API stages that different in bawah satu domain. Ini provides URL that bersih for consumers (api.company.com/v1/data, api.company.com/v2/data) and separates deployment in a full without overhead manages dua API separate.
  • Uses HTTP headers "Deprecation" (RFC 8594) and "Sunset" provides machine-readable notice that can dideteksi by consumer applications automatically. API Gateway access logging with API keys enables tracking granular about consumer mana that still uses endpoint deprecated. Ini combines komunikasi proaktif with monitoring.
  • Adds field optional new to response body is backward-compatible change because consumer that already ada mengabaikan field that not mereka kenal (appropriate with Postel's Law / Robustness Principle).
  • API Gateway usage plans with API keys provides kontrol granular per consumer — throttle rate (requests per second) and quota (total requests per period) can is configured in a independent for each team. Ini ensures fair usage without affects consumer other.
  • CloudWatch metrics for API Gateway (4XXError, 5XXError, Latency, Count) provides real-time visibility to kesehatan API. Composite alarms combines multiple conditions (for example, error rate > 5% DAN latency > 2s) for alerting that more akurat. Detailed logging provides data for troubleshooting.
  • API Gateway supports canary deployments in a native on stage level. Traffic can is allocated to canary (for example 10%) while sisanya still in deployment saat this. By CloudWatch alarms on canary metrics, rollback automatic can is reached through API Gateway deployment rollback. Ini built-in without code kustom.
  • Separate Lambda functions for each versi enables independent deployment cycles and isolasi logika bisnis. Lambda layers sharing common code (utility functions, data access layer) reduces duplikasi. Base path mappings on custom domain provides clean URL routing.
  • Uses OpenAPI specification sebagai single source of truth ensures dokumentasi and implementation always synchronized. API Gateway supports import OpenAPI spec that mendefinisikan endpoints, request/response models, and validation. CI/CD pipeline ensures changes always dimulai from spec update.
  • Approach gradually mengkombinasikan multiple communication channels: developer portal for awareness, Sunset header (RFC 8594) for machine-readable notice, custom metrics for tracking who that still uses field deprecated, and direct contact for consumers that not yet migration. Ini maximizes awareness and minimalisir disruption.
  • Tiered usage plans enables diferensiasi service level between consumer groups. Critical consumers mendapat throttle/burst limits higher so that still can accesses API saat traffic spike. Method-level throttling melindungi endpoint that expensive in a komputasi.

Common Misconceptions & Pitfalls

  • Adds overhead manajemen dua API separate.
  • Baik for configuration but stage variables not supports routing to versi API that correct-correct different in a struktural.
  • Mencampur logika versi in satu function that difficult in-maintain.
  • Will directly memecah consumer that not siap.
  • Not provides tracking and easy terlewat.
  • Not identifies consumer individual that not yet migration.
  • Adalah breaking change because consumer that reads field old not will menemukan data mereka.
  • Can jadi problem if consumer performs strict schema validation.
  • Adalah breaking change that will menyebabkan parsing errors on consumer that mengharapkan string.
  • Membatasi all consumer in a same without diferensiasi.
  • Bekerja per IP that not suitable for internal consumers that may share IP.
  • Not enforceable because consumer can bypass or changes implementation.
  • Terlalu slow for detects problem before impact.
  • Berguna sebagai additional but only menguji from perspektif sintetis, not traffic aktual.
  • Bagus for tracing but not provides alerting or error rate monitoring directly.
  • Requires dua endpoints separate and not terintegrasi for rollback automatic.
  • Requires development kustom that significant.
  • For Lambda functions, not API Gateway stage deployments.
  • Only works if perbedaan versi minimal and superficial, not suitable for different business logic.
  • Mencampur logika kedua versi, creates testing and deployment more complex and berisiko.
  • Memaksimalkan duplikasi code.
  • Bersifat reactive — dokumentasi diupdate setelah changes, can ada gap.
  • Mengubah architecture sepenuhnya and not solution for REST API that already ada.
  • Rentan against human error and delays.
  • Will directly memecah consumers.
  • Can menyebabkan NullPointerException on consumers that uses field the said.
  • Not provides time migration.
  • Not provides prioritas and can overload backend.
  • Only effective for data that rarely changes, not suitable for real-time analytics API.
  • Mengubah API from synchronous to asynchronous that memecah consumer expectations.
