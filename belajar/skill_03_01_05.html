Skill 3.1.5: Consume and maintain data APIs

APIversioningmaintenance

Ringkasan

Skill ini termasuk dalam Domain 3: Operations & Support (Task 3.1: Automate data processing), dengan fokus pada consume and maintain data apis. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon API Gateway
Mengelola REST/HTTP/WebSocket API: throttling, otorisasi, caching, dan integrasi backend.

Poin-Poin Kunci

  • Custom domain names dengan base path mappings memungkinkan routing path-based (/v1, /v2) ke API stages yang berbeda di bawah satu domain. Ini memberikan URL yang bersih untuk consumers (api.company.com/v1/data, api.company.com/v2/data) dan memisahkan deployment secara penuh tanpa overhead mengelola dua API terpisah.
  • Menggunakan HTTP headers "Deprecation" (RFC 8594) dan "Sunset" memberikan machine-readable notice yang dapat dideteksi oleh consumer applications secara otomatis. API Gateway access logging dengan API keys memungkinkan tracking granular tentang consumer mana yang masih menggunakan endpoint deprecated. Ini menggabungkan komunikasi proaktif dengan monitoring.
  • Menambahkan field opsional baru ke response body adalah backward-compatible change karena consumer yang sudah ada mengabaikan field yang tidak mereka kenal (sesuai dengan Postel's Law / Robustness Principle).
  • API Gateway usage plans dengan API keys memberikan kontrol granular per consumer — throttle rate (requests per second) dan quota (total requests per period) dapat dikonfigurasi secara independen untuk setiap team. Ini memastikan fair usage tanpa mempengaruhi consumer lain.
  • CloudWatch metrics untuk API Gateway (4XXError, 5XXError, Latency, Count) memberikan real-time visibility ke kesehatan API. Composite alarms menggabungkan multiple conditions (misalnya, error rate > 5% DAN latency > 2s) untuk alerting yang lebih akurat. Detailed logging memberikan data untuk troubleshooting.
  • API Gateway mendukung canary deployments secara native pada stage level. Traffic dapat dialokasikan ke canary (misalnya 10%) sementara sisanya tetap di deployment saat ini. Dengan CloudWatch alarms pada canary metrics, rollback otomatis dapat dicapai melalui API Gateway deployment rollback. Ini built-in tanpa kode kustom.
  • Separate Lambda functions untuk setiap versi memungkinkan independent deployment cycles dan isolasi logika bisnis. Lambda layers sharing common code (utility functions, data access layer) mengurangi duplikasi. Base path mappings pada custom domain menyediakan clean URL routing.
  • Menggunakan OpenAPI specification sebagai single source of truth memastikan dokumentasi dan implementasi selalu synchronized. API Gateway mendukung import OpenAPI spec yang mendefinisikan endpoints, request/response models, dan validasi. CI/CD pipeline memastikan perubahan selalu dimulai dari spec update.
  • Pendekatan bertahap mengkombinasikan multiple communication channels: developer portal untuk awareness, Sunset header (RFC 8594) untuk machine-readable notice, custom metrics untuk tracking siapa yang masih menggunakan field deprecated, dan direct contact untuk consumers yang belum migrasi. Ini memaksimalkan awareness dan minimalisir disruption.
  • Tiered usage plans memungkinkan diferensiasi service level antar consumer groups. Critical consumers mendapat throttle/burst limits lebih tinggi sehingga tetap bisa mengakses API saat traffic spike. Method-level throttling melindungi endpoint yang mahal secara komputasi.

Miskonsepsi & Jebakan Umum

  • Menambah overhead manajemen dua API terpisah.
  • Baik untuk konfigurasi tetapi stage variables tidak mendukung routing ke versi API yang benar-benar berbeda secara struktural.
  • Mencampur logika versi dalam satu fungsi yang sulit di-maintain.
  • Akan langsung memecah consumer yang tidak siap.
  • Tidak memberikan tracking dan mudah terlewat.
  • Tidak mengidentifikasi consumer individual yang belum migrasi.
  • Adalah breaking change karena consumer yang membaca field lama tidak akan menemukan data mereka.
  • Bisa jadi masalah jika consumer melakukan strict schema validation.
  • Adalah breaking change yang akan menyebabkan parsing errors pada consumer yang mengharapkan string.
  • Membatasi semua consumer secara sama tanpa diferensiasi.
  • Bekerja per IP yang tidak cocok untuk internal consumers yang mungkin share IP.
  • Tidak enforceable karena consumer bisa bypass atau mengubah implementasi.
  • Terlalu lambat untuk mendeteksi masalah sebelum impact.
  • Berguna sebagai tambahan tetapi hanya menguji dari perspektif sintetis, bukan traffic aktual.
  • Bagus untuk tracing tetapi tidak menyediakan alerting atau error rate monitoring secara langsung.
  • Memerlukan dua endpoints terpisah dan tidak terintegrasi untuk rollback otomatis.
  • Memerlukan development kustom yang signifikan.
  • Untuk Lambda functions, bukan API Gateway stage deployments.
  • Hanya bekerja jika perbedaan versi minimal dan superficial, tidak cocok untuk different business logic.
  • Mencampur logika kedua versi, membuat testing dan deployment lebih kompleks dan berisiko.
  • Memaksimalkan duplikasi kode.
  • Bersifat reactive — dokumentasi diupdate setelah perubahan, bisa ada gap.
  • Mengubah arsitektur sepenuhnya dan bukan solusi untuk REST API yang sudah ada.
  • Rentan terhadap human error dan delays.
  • Akan langsung memecah consumers.
  • Bisa menyebabkan NullPointerException pada consumers yang menggunakan field tersebut.
  • Tidak memberikan waktu migrasi.
  • Tidak memberikan prioritas dan bisa overload backend.
  • Hanya efektif untuk data yang jarang berubah, tidak cocok untuk real-time analytics API.
  • Mengubah API dari synchronous ke asynchronous yang memecah consumer expectations.
