Skill 1.1.6: Set up event triggers

S3EventNotificationsEventBridge

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.1: Perform data ingestion), dengan fokus pada set up event triggers. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon S3
Object storage tahan lama; dasar data lake, mendukung event notification, versioning, dan lifecycle.
Amazon EventBridge
Event bus serverless untuk routing event antar layanan; mendukung schedule rule.
Amazon SNS
Pub/sub notifikasi untuk fan-out pesan ke banyak subscriber (SQS, Lambda, HTTP).

Poin-Poin Kunci

  • Amazon EventBridge integration dengan S3 adalah cara paling reliable untuk event-driven triggers. EventBridge menangkap semua S3 events dengan at-least-once delivery dan mendukung filtering berdasarkan prefix. Ini juga bisa langsung menargetkan Glue API.
  • EventBridge rules mendukung content-based filtering pada event payload termasuk S3 object key. Tiga rules terpisah dengan suffix filter (.csv, .json, .parquet) memberikan routing paling bersih tanpa kode tambahan. Setiap rule menargetkan pipeline yang berbeda.
  • DLQ menangkap messages yang gagal diproses setelah max retries, mencegah infinite reprocessing. Idempotent processing dengan DynamoDB tracking memastikan bahwa jika message diproses ulang, hasilnya sama (tidak ada duplikasi data).
  • Marker file (sentinel file) pattern adalah solusi paling sederhana dan reliable. Source system mengupload "_COMPLETE" file setelah semua data files selesai diupload. S3 event notification hanya memicu pipeline ketika marker file muncul, menjamin semua data sudah tersedia.
  • SQS queue sebagai buffer antara S3 events dan Lambda mencegah event loss. SQS menyimpan messages hingga Lambda siap memprosesnya (retention up to 14 days). Lambda SQS event source mapping juga mengatur batch size dan concurrency secara otomatis.
  • Enabling EventBridge on an S3 bucket works alongside existing S3 Event Notifications tanpa konflik. EventBridge menerima semua S3 events secara independen dan Anda bisa membuat rules dengan multiple targets. Existing notification ke SNS tetap berfungsi.
  • EventBridge menangkap Glue Job State Change events natively. Dengan rule filtering pada state "FAILED" dan input transformation, event detail (jobName, error message) bisa diteruskan ke Step Functions sebagai input. Ini adalah pola event-driven yang paling direct.
  • EventBridge mendukung content-based filtering termasuk numeric matching pada field seperti object size. Rule bisa memfilter events dimana detail.object.size > 104857600 (100 MB). Ini menghindari invokasi yang tidak perlu.
  • EventBridge S3 events include detail.reason field yang menunjukkan bagaimana object dibuat (PutObject, CompleteMultipartUpload, CopyObject, dll). Memfilter pada field ini di EventBridge rule memastikan Lambda hanya dipanggil untuk multipart uploads.
  • Cross-account EventBridge event forwarding adalah pola paling secure dan native untuk cross-account event triggers. Account A mengizinkan Account B's event bus sebagai target melalui resource-based policy. Ini menggunakan IAM untuk security dan tidak memerlukan shared credentials.

Miskonsepsi & Jebakan Umum

  • Tidak real-time dan bisa miss files di antara interval polling.
  • Arsitektur-nya salah karena EventBridge tidak "poll" SQS.
  • Bisa kehilangan events jika Lambda throttled.
  • Memaksa reorganisasi data berdasarkan format.
  • Untuk transformasi read access, bukan event routing.
  • Menambah Lambda sebagai router yang meningkatkan kompleksitas.
  • Menyebabkan data loss jika processing gagal.
  • Membatasi throughput ke 300 msg/s dan S3 events tidak guarantee deduplication ID.
  • Menunda retry terlalu lama tanpa menyelesaikan masalah root cause.
  • Tidak bisa menghitung events sebelum trigger.
  • Bisa bekerja tapi lebih kompleks dan rentan race condition.
  • Tidak event-driven dan memiliki latency.
  • Membantu tapi masih bisa hit account-level limits.
  • Bukan event-driven dan untuk operasi massal yang dijadwalkan.
  • S3 Event Notifications tidak memiliki configurable retry policy.
  • Membutuhkan migrasi aplikasi existing.
  • Bisa bekerja tapi menambah overhead Lambda invocation.
  • Memerlukan Glue memiliki SNS subscription endpoint yang tidak langsung supported.
  • Tidak membawa detail error message.
  • Glue tidak memiliki "notification trigger" built-in yang memanggil API langsung.
  • Menambah layer SNS dan Lambda yang tidak diperlukan.
  • S3 Event Notifications tidak mendukung filtering berdasarkan ukuran file.
  • Untuk storage class management, bukan event filtering.
  • Bekerja tapi memicu Lambda untuk setiap file yang tidak efisien.
  • Membuang invocation cost untuk events yang tidak diproses.
  • Mengubah arsitektur storage secara tidak perlu.
  • Bisa bekerja tapi S3 Event Notifications kurang fleksibel dibanding EventBridge.
  • Tidak supported — S3 Event Notifications tidak bisa langsung target cross-account Lambda.
  • Tidak event-driven, lambat, dan membutuhkan cross-account S3 access.
  • Bekerja tapi membutuhkan subscription confirmation.
