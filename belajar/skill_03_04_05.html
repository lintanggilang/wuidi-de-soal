Skill 3.4.5: Data skew mechanisms

skewsaltingAQE

Summary

Skill this including in Domain 3: Operations & Support (Task 3.4: Ensure data quality), with fokus on data skew mechanisms. Materi berikut merangkum service AWS that relevan beserta concept important that needs kamu kuasai for topik this.

Key Services & Concepts

Apache Spark
Engine komputasi terdistribusi in-memory; inti Glue ETL and EMR.

Key Points

  • Gejala that ditunjukkan — partly large task complete fast but several task memakan time very old (long-tail tasks) with memory spill — is indikator klasik data skew on join key. Salting technique adds suffix acak on key that skewed, distributes data in a merata to more partition.
  • Because device_metadata only 50 MB, broadcast join is solution most effective and requires minimal code changes. Broadcast join sends table small to all executors, avoids shuffle sepenuhnya so that data skew not menjadi problem.
  • For mengaktifkan AQE skew join optimization, dua configuration is required: spark.sql.adaptive.enabled=true (mengaktifkan AQE in a keseluruhan) and spark.sql.adaptive.skewJoin.enabled=true (mengaktifkan feature handling skew in a specific). AQE will detects partition that jauh larger from median and memecahnya menjadi sub-partition.
  • Write sharding with adds random suffix on partition key distributes writes in a merata to several physical partitions. For "pending" status, key menjadi "pending_0", "pending_1", ..., "pending_9", divides load to 10 partition. Reads is performed with scatter-gather query on all suffix.
  • Masalah main is partition key that not terdistribusi merata (user_country). Kinesis uses MD5 hash on partition key for determines shard assignment. If only ada ~200 negara and 2 negara dominan, hash-nya will always mengarah to shard that same. Uses user_id or composite key (country + random suffix) menciptakan distribusi hash that more merata.
  • Salting technique that correct: (1) Tambahkan kolom salt acak (0 until N-1) to table kiri (that large/skewed). (2) Explode/replicate table kanan N kali, each with salt value different. (3) Join on kombinasi key asli DAN salt column. Ini distributes rows from key that skewed to N partition different.
  • Indikator most jelas from data skew in Spark UI is disparitas large between median and maximum on Shuffle Read Size/Records per task. If median 50 MB but max 8 GB, this menunjukkan distribusi data that very not merata between partition.
  • Two-phase aggregation (also disebut partial aggregation with salting) is teknik standar for resolves skew on operasi aggregation. Fase 1: tambahkan salt column, lakukan partial aggregation per (store_id, salt) — this distributes data flagship stores to several partition. Fase 2: hapus salt column and lakukan final aggregation per store_id.
  • Spark AQE uses dua parameter for determines whether sebuah partition dianggap skewed: (1) skewedPartitionFactor (default 5) — partition dianggap skewed if ukurannya larger from median × factor this. (2) skewedPartitionThresholdInBytes (default 256 MB) — size minimum so that partition dipertimbangkan for split. Keduanya must terpenuhi.
  • Uses ExplicitHashKey enables producer mengontrol distribusi records directly to shard certain, bypass MD5 hash from partition key. By calculates hash that distributes records in a merata (for example round-robin or random hash), hot shard problem can is resolved sambil still mempertahankan session_id sebagai partition key for consumer ordering.
