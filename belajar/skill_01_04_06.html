Key Services & Concepts

AWS SAM
Framework for membangun & men-deploy application serverless.

Key Points

  • SAM requires the Transform: AWS::Serverless-2016-10-31 header to enable SAM resource types. AWS::Serverless::Function with an S3 Events property automatically creates the S3 bucket notification, Lambda permission, and event mapping — reducing boilerplate significantly. AWS::Serverless::SimpleTable creates a DynamoDB table with minimal configuration.
  • The correct SAM workflow is: sam build resolves dependencies (installs packages from requirements.txt), compiles code, and places everything in .aws-sam/build directory. sam deploy --guided (first time) or sam deploy (subsequent) uploads the built artifact to S3 and creates/updates the CloudFormation stack. The --guided flag prompts for stack name, region, and other parameters, saving them to samconfig.toml for future deployments.
  • sam local invoke executes the Lambda function locally in a Docker container that mimics the Lambda runtime environment. The --event flag passes a JSON file simulating the Kinesis event payload. You can generate sample events with sam local generate-event kinesis get-records and customize them. This provides fast local iteration without deploying to AWS.
  • AWS::Serverless::StateMachine with DefinitionUri separates the state machine definition from the SAM template, keeping both files focused and readable. DefinitionSubstitutions enables variable replacement — replacing placeholder strings in the ASL file with actual Lambda ARNs at deployment time (e.g., "${ExtractFunctionArn}" → actual ARN). This maintains IaC benefits while managing complexity.
  • Lambda Layers separate dependencies from function code. The combined total (function code + all layers) can be up to 250MB unzipped, but layers are shared across functions and managed independently. AWS::Serverless::LayerVersion in SAM handles the layer packaging and versioning. Additionally, if still too large, container images support up to 10GB. Layers also enable reuse across multiple Lambda functions without duplicating dependencies.
  • SAM Parameters with --parameter-overrides enable a single template to serve all environments. The Globals section sets defaults shared across all functions. Parameter overrides at deploy time inject environment-specific values. Combined with samconfig.toml (which stores deployment profiles per environment), this provides clean multi-environment management from one codebase.
  • SAM policy templates (like DynamoDBCrudPolicy, S3ReadPolicy, KinesisStreamReadPolicy) are shorthand that generates least-privilege IAM policies. If the Policies property doesn't include DynamoDB access, the Lambda execution role won't have DynamoDB permissions. Fix: add "- DynamoDBCrudPolicy: {TableName: !Ref MyTable}" to the Policies list. SAM resolves this to a proper IAM policy with read/write permissions scoped to that specific table.
  • SAM's implicit API feature creates an API Gateway REST API automatically when a function has an Api event type. Just specifying Path and Method in the event properties generates all necessary resources: RestApi, Resource, Method, Lambda Permission, and Deployment. This reduces a typical 50+ lines of CloudFormation to 3-4 lines of SAM configuration.
  • Lambda's KmsKeyArn property specifies the CMK used to encrypt environment variables at rest. When set, Lambda uses this key instead of the default AWS-managed key. The function's execution role must have kms:Decrypt permission for the key. SAM handles the association between function and KMS key during deployment. This satisfies the security requirement with minimal code changes.
  • Lambda Layers are specifically designed for sharing code across functions. AWS::Serverless::LayerVersion packages the shared utility code as a layer. Listing it in Globals.Function.Layers applies it to ALL functions in the template without per-function configuration. Bug fixes in the shared code only require updating the layer once. SAM builds and deploys the layer alongside the functions.

Common Misconceptions & Pitfalls

  • Using the CloudFormation transform instead of SAM transform means SAM resources won't be recognized.
  • Manually creating bucket notifications defeats the purpose of SAM's simplified event source definitions.
  • SAM supports multiple event types (S3, SQS, Kinesis, Schedule, etc), not just API Gateway.
  • Sam package is an older workflow; sam deploy now handles packaging internally The order is wrong.
  • Sam init scaffolds new projects; sam publish publishes to Serverless Application Repository, not deploy to your account.
  • Sam deploy requires sam build first to resolve dependencies; it doesn't auto-build.
  • Sam local start-api is for testing API Gateway-triggered functions via HTTP, not Kinesis events.
  • Testing in production is risky and slow; local testing provides faster feedback.
  • Sam local generate-event works for multiple services including Kinesis, not just API Gateway.
  • 200+ inline lines make the template unreadable and difficult to maintain or diff in version control.
  • Splitting one workflow into three loses the orchestration logic that Step Functions provides.
  • Manual console creation loses IaC benefits (repeatability, version control).
  • The 250MB limit is a hard limit that cannot be increased via quota requests for zip deployments.
  • Bypassing SAM loses build automation, dependency management, and cross-platform compilation.
  • Rewriting without pandas may not be feasible for complex data transformations.
  • Separate templates diverge over time, requiring changes in multiple files for every modification.
  • Manual changes defeat IaC principles and risk deploying wrong values.
  • Sam sync is for development iteration speed, not multi-environment configuration management.
  • SAM automatically creates and assigns the execution role; no STS AssumeRole is needed.
  • Lambda accesses DynamoDB via public endpoints by default; VPC endpoints are only needed if Lambda is in a VPC with no internet access.
  • API Gateway doesn't mediate Lambda-to-DynamoDB calls; they're separate service interactions.
  • Manual deployment loses IaC benefits and creates resources outside the template's management.
  • While HttpApi works, the question asks for LEAST code; the implicit API from a function event is even more minimal.
  • This is raw CloudFormation approach requiring extensive boilerplate that SAM eliminates.
  • Manual pre-encryption is complex, doesn't integrate with Lambda's decryption at invocation, and values in the template are still visible.
  • While valid for secrets, the requirement is about encrypting env vars with CMK, not eliminating them entirely; also adds latency for every invocation.
  • A key policy without reference from the function doesn't enable encryption of that function's env vars.
  • Combining functions violates single-responsibility principle and increases blast radius of failures.
  • Publishing to PyPI adds external dependency management complexity and requires public/private registry setup.
  • Symlinks are not reliably handled by sam build and can cause deployment issues across different operating systems.
