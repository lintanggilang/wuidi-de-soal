Skill 3.2.5: Provisioned vs serverless tradeoffs

provisionedserverlesstradeoffs

Ringkasan

Skill ini termasuk dalam Domain 3: Operations & Support (Task 3.2: Analyze data by using AWS services), dengan fokus pada provisioned vs serverless tradeoffs. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Lihat poin-poin kunci di bawah.

Poin-Poin Kunci

  • Untuk workload yang predictable, consistent, dan berjalan setiap hari sepanjang tahun, Reserved Instances memberikan diskon hingga 72% dibanding On-Demand pricing. EMR on EC2 dengan RI ideal untuk sustained utilization pattern. EMR Serverless mengenakan premium untuk convenience dan lebih cost-effective untuk sporadic/unpredictable workloads.
  • Redshift Serverless secara otomatis scales compute resources berdasarkan workload demand. Pada hari tanpa query, biaya mendekati nol (hanya storage). Pada hari sibuk, resources scale up sesuai kebutuhan. RPU base capacity memungkinkan warm state untuk response cepat.
  • Untuk spikes yang diketahui sebelumnya (game launches dijadwalkan), scheduled scaling pada provisioned capacity adalah pilihan paling cost-effective. Table di-scale up sebelum launch dan scale down setelah traffic kembali normal.
  • Keuntungan utama serverless (Glue) adalah eliminasi operational overhead. Tim tidak perlu mengelola cluster lifecycle (start/stop/resize), OS patching, security updates, atau capacity planning. Untuk tim dengan limited DevOps, ini sangat signifikan.
  • Amazon EMR on EC2 dengan long-running Spark Structured Streaming application selalu aktif dan ready to process data tanpa cold start. Application terus polling sumber data dan memproses dalam micro-batches (bisa serendah 100ms trigger interval). Zero cold start karena cluster selalu running.
  • Arsitektur hybrid memberikan optimasi terbaik: Redshift Serverless handles complex analytical queries dengan performa tinggi dan auto-scales berdasarkan demand (hemat saat volume rendah). Athena handles simple ad-hoc queries dengan biaya per-scan yang minimal. Ini memberikan cost-effectiveness karena kedua service hanya charge saat digunakan.
  • Amazon EMR on EC2 menyediakan fleksibilitas maksimum: mendukung semua framework Hadoop ecosystem (Spark, Hive, Presto, HBase), memungkinkan custom AMIs, bootstrap actions untuk konfigurasi spesifik, dan kontrol penuh atas versi framework. Ini paling mirip dengan on-premises Hadoop.
  • AWS serverless data services (Glue, Athena, Redshift Serverless, EMR Serverless) semuanya mendukung VPC deployment, KMS customer-managed keys, dan CloudTrail logging. Keamanan bukan lagi differentiator utama antara provisioned dan serverless.
  • EMR Serverless pre-initialized capacity (pre-warmed workers) menjaga pool of initialized workers yang ready to execute, menghilangkan cold start time. Workers tetap warm dan bisa langsung mulai processing. Biaya pre-initialized workers lebih rendah dari running cluster tapi menghilangkan 4-5 menit cold start.
  • TCO comparison antara provisioned (RI) dan serverless bergantung pada average utilization. Provisioned RI memberikan fixed cost regardless of usage, sehingga semakin tinggi utilization semakin cost-effective. Weighted average utilization: (8h × 80% + 4h × 40% + 12h × 5%) / 24h ≈ 37%. Dengan RI discounts (hingga 72% off on-demand), provisioned menjadi lebih murah di titik ini dibanding serverless yang charges per-RPU-hour consumed.

Miskonsepsi & Jebakan Umum

  • Berisiko interruption yang bisa menggagalkan 3-hour job.
  • Berlaku tapi cost advantage tidak berlaku untuk steady predictable workload.
  • Benar tapi per-compute-hour rate lebih mahal dari RI.
  • Sangat wasteful untuk workload unpredictable.
  • Memerlukan prediksi kapan query akan dijalankan, tidak cocok untuk truly unpredictable patterns.
  • Adalah solusi berbeda yang mungkin tidak memenuhi kebutuhan performa sub-second untuk complex queries.
  • Sangat wasteful untuk 1,000 WCU normal usage.
  • Lebih mahal per request dan memiliki throttling pada initial spike jika previous peak belum mencapai level tersebut.
  • Memiliki lag time yang bisa menyebabkan throttling saat traffic naik 100x secara tiba-tiba (auto-scaling reacts, doesn't predict).
  • Salah karena EMR mendukung lebih banyak framework/format.
  • Salah karena EMR bisa lebih cepat dengan konfigurasi optimal.
  • Salah karena EMR juga terintegrasi dengan Glue Data Catalog secara native.
  • Memiliki cold start dan tidak mendukung complex Spark transformations.
  • Memiliki cold start 1-2 menit bahkan dengan pre-initialized workers.
  • Juga always-on tapi memiliki higher startup time jika job perlu di-restart.
  • Kurang optimal untuk complex multi-join queries yang berjalan 30 menit.
  • Memerlukan cluster management dan tidak cost-optimal untuk variable workloads.
  • Wasteful pada hari dengan 5 queries.
  • Memecah ke multiple services yang memerlukan rewrite signifikan.
  • Berbeda paradigma dan tidak mendukung HBase/Spark workloads.
  • Hanya mendukung Spark dan Hive, bukan Presto atau HBase.
  • Partially true tapi granular network controls juga tersedia di serverless melalui VPC configurations dan security groups.
  • Salah karena Glue mendukung VPC connections, EMR Serverless mendukung VPC, dll.
  • Oversimplifies (patching bukan satu-satunya aspek security).
  • Salah karena Glue juga memiliki startup time.
  • Menambah latency untuk individual datasets.
  • Berfungsi tapi lebih kompleks secara operasional dengan dua systems berbeda.
  • Salah karena utilization pattern (bukan hanya query count) menentukan cost.
