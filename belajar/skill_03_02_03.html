Skill 3.2.3: SQL in Redshift and Athena

SQLRedshiftAthenaviews

Ringkasan

Skill ini termasuk dalam Domain 3: Operations & Support (Task 3.2: Analyze data by using AWS services), dengan fokus pada sql in redshift and athena. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon Redshift
Data warehouse berskala petabyte; mendukung COPY/UNLOAD, materialized view, dan streaming ingestion.
Redshift Streaming Ingestion
Konsumsi langsung dari Kinesis/MSK ke materialized view Redshift, latensi detik, tanpa staging S3.
Amazon Athena
Query SQL serverless terhadap data di S3 (Presto/Trino); bayar per data yang dipindai.

Poin-Poin Kunci

  • Materialized views di Redshift menyimpan hasil query secara fisik, sehingga query berikutnya membaca dari pre-computed results (sub-second). AUTO REFRESH akan otomatis memperbarui materialized view ketika data underlying berubah (setelah nightly load). Ini ideal untuk query berat yang data-nya jarang berubah.
  • Partition projection memungkinkan Athena menghitung partisi secara in-memory berdasarkan pola yang didefinisikan (misalnya date range), tanpa perlu melakukan GetPartitions call ke Glue Data Catalog. Ini secara drastis mengurangi query planning time untuk tabel dengan banyak partisi.
  • CTAS di Athena memungkinkan pembuatan tabel baru dari hasil query SELECT. Anda bisa menentukan format output (Parquet), lokasi S3 tujuan, dan strategi partitioning. Data secara fisik ditulis ke S3 dalam format yang ditentukan. Ini ideal untuk membuat layer data yang ditransformasi.
  • Late-binding views (WITH NO SCHEMA BINDING) di Redshift tidak memverifikasi schema underlying table saat view dibuat. Schema divalidasi hanya saat query time. Ini sangat berguna untuk external/Spectrum tables yang schema-nya bisa berubah. Regular views memvalidasi schema saat CREATE dan akan error jika kolom berubah.
  • Window functions dengan PARTITION BY month membatasi kalkulasi dalam setiap bulan. SUM() OVER dengan ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW memberikan running total yang benar dalam bulan. RANK() OVER dengan ORDER BY daily_sales DESC memberikan ranking berdasarkan nilai sales dalam bulan.
  • Redshift mendukung PartiQL syntax untuk querying SUPER type columns. PartiQL memungkinkan unnesting arrays menjadi baris individual menggunakan syntax FROM table t, t.reviews r dimana setiap element array menjadi row terpisah. Ini native dan efisien untuk semi-structured data.
  • SVV_TABLE_INFO menampilkan metadata tabel termasuk sort key configuration. Jika tabel tidak memiliki sort key pada kolom date, Redshift tidak bisa melakukan zone map filtering (range-restricted scan) dan harus melakukan full sequential scan. Sort key memungkinkan Redshift melewati blocks yang tidak relevan berdasarkan min/max metadata.
  • Athena views menyimpan definisi query tanpa mematerialisasi data. Analysts bisa SELECT dari view dengan tambahan WHERE clauses untuk filtering. Views memberikan abstraction layer yang reusable dan maintainable.
  • Recursive CTEs (WITH RECURSIVE) memungkinkan traversal hierarki dengan kedalaman yang tidak diketahui atau variabel. CTE terdiri dari anchor member (root level) dan recursive member (UNION ALL) yang meng-join kembali ke CTE untuk level berikutnya. Redshift mendukung recursive CTEs.
  • AWS Glue Data Catalog berfungsi sebagai metastore terpusat yang bisa diakses oleh KEDUA Athena dan Redshift Spectrum. Tabel yang didefinisikan di Glue Data Catalog dengan Parquet SerDe dan partition information akan otomatis queryable dari Athena (native integration) dan Redshift Spectrum (via external schema yang mereferensikan Glue catalog). Satu definisi tabel, dua query engine.

Miskonsepsi & Jebakan Umum

  • Berfungsi tapi memerlukan scheduling terpisah dan tabel manual.
  • Hanya menyimpan definisi query, tetap execute setiap kali dipanggil (45 detik).
  • Memerlukan manual refresh dan temp table hilang setelah session.
  • Tetap memerlukan partition lookup.
  • Menghilangkan granularitas partitioning harian yang berguna untuk filter 7 hari terakhir.
  • Tidak berlaku untuk Athena standar yang serverless (tidak ada DPU configuration untuk query planning).
  • Menambah kompleksitas yang tidak perlu dengan Glue ETL job terpisah.
  • Memerlukan tabel target yang sudah ada.
  • Hanya menyimpan definisi query tanpa materialisasi data.
  • Pada regular view tetap memiliki schema binding dan bisa break.
  • Juga memiliki schema binding dan gagal saat refresh jika schema berubah.
  • Akan break saat schema berubah.
  • Sangat tidak efisien untuk masalah yang bisa diselesaikan dengan window functions.
  • Tidak efisien dan lebih kompleks.
  • Kehilangan PARTITION BY month sehingga running total lintas bulan dan rank tidak per-bulan.
  • Memerlukan redesign tabel dan ETL pipeline.
  • Sangat fragile dan tidak mendukung nested structures.
  • Mengekstrak scalar value, tidak bisa unnest arrays menjadi multiple rows.
  • Berguna untuk alerts tapi bukan untuk diagnosa sort key.
  • Menunjukkan detail scan tapi bukan root cause.
  • Relevan jika sort key ada tapi data unsorted, namun SVL_QUERY_SUMMARY bukan tempat untuk memeriksa ini.
  • Hanya bookmark, tidak bisa di-query dengan filter tambahan di atasnya.
  • Untuk parameterized execution bukan untuk reusable query abstraction yang bisa difilter oleh analysts.
  • Mematerialisasi data ke S3 yang bertentangan dengan requirement.
  • Adalah Oracle syntax, tidak didukung di Redshift.
  • Untuk kalkulasi dalam partisi, bukan traversal hierarki.
  • Memerlukan jumlah join yang diketahui sebelumnya dan sangat tidak efisien.
  • Tidak bisa diakses dari Athena.
  • Memiliki integrasi terbatas lintas kedua services dalam mode ini.
