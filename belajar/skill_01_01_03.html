Skill 1.1.3: Configuration for batch ingestion

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.1: Perform data ingestion), dengan fokus pada configuration for batch ingestion. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS Config
Merekam & mengevaluasi konfigurasi sumber daya untuk kepatuhan dari waktu ke waktu.

Poin-Poin Kunci

  • Auto Scaling memungkinkan Glue menyesuaikan worker secara dinamis. Meningkatkan spark.sql.shuffle.partitions mendistribusikan data skew ke lebih banyak partisi. groupFiles menggabungkan file-file kecil menjadi group yang lebih efisien sehingga mengurangi memory overhead.
  • Splitting files agar jumlahnya kelipatan dari jumlah slices memaksimalkan paralelisme COPY. Setiap slice membaca satu file secara independen. COMPUPDATE OFF melewati analisis kompresi otomatis yang memakan waktu, dan STATUPDATE OFF melewati update statistics otomatis. Keduanya bisa ditambahkan setelah initial load.
  • Push-down predicates memungkinkan Glue memfilter partisi di level Data Catalog sebelum membaca data. Dengan menentukan filter (misalnya partition_date = yesterday), Glue hanya merencanakan dan membaca partisi yang diperlukan, mengurangi planning time drastis.
  • Karena CPU dan network utilization rendah, replication instance memiliki kapasitas tersisa. MaxFullLoadSubTasks mengontrol berapa banyak tabel yang dimuat secara paralel (default 8). Meningkatkan nilai ini akan memanfaatkan kapasitas yang tersisa untuk memuat lebih banyak tabel secara bersamaan.
  • groupFiles = "inPartition" menginstruksikan Glue untuk menggabungkan file-file kecil dalam satu partisi menjadi groups yang lebih besar sebelum memproses. groupSize menentukan ukuran target (bytes) per group. Ini mengurangi jumlah tasks yang perlu dijadwalkan secara dramatis.
  • Glue job bookmarks melacak data yang telah diproses sebelumnya. Dengan mengaktifkan bookmark (job-bookmark-enable), setiap run hanya memproses file baru sejak run terakhir. Ini adalah solusi native Glue untuk incremental processing.
  • Parquet adalah columnar format yang optimal untuk analytical queries di Athena. Snappy compression memberikan keseimbangan baik antara rasio kompresi dan kecepatan dekompresi. Partitioning by region dan date sesuai dengan pola query yang menggunakan filter pada kolom tersebut. Coalesce mengontrol ukuran file output.
  • Untuk CPU-intensive transformations, compute-optimized (c5) instances memberikan performa terbaik per dollar. Menggunakan Spot Instances untuk core/task nodes mengurangi biaya hingga 90%. Master node harus On-Demand untuk stability.
  • MAXERROR menentukan jumlah error yang bisa ditoleransi sebelum COPY gagal. Dengan nilai tinggi, job akan berhasil bahkan jika ada banyak record bermasalah. STL_LOAD_ERRORS menyimpan detail setiap record yang gagal dimuat untuk investigasi.
  • hashfield atau hashexpression menentukan kolom/ekspresi yang digunakan untuk mempartisi data secara paralel. hashpartitions menentukan jumlah partisi (koneksi paralel). Glue akan membuat N koneksi paralel ke database, masing-masing membaca subset data berdasarkan hash.

Miskonsepsi & Jebakan Umum

  • Tidak langsung mengatasi OOM.
  • Hanya menambah resources tapi tidak mengatasi data skew.
  • Tidak cocok untuk 2 TB data karena single-node processing.
  • Kurang kompresi dibanding gzip tapi splitting lebih penting.
  • Tidak mempengaruhi kecepatan loading.
  • Tidak menyelesaikan masalah partition pruning tanpa konfigurasi tambahan.
  • Tidak mempercepat planning phase.
  • Menghapus metadata yang mungkin masih diperlukan.
  • Tidak diperlukan karena resources belum penuh.
  • Hanya untuk membaca subdirectory.
  • Tidak mengatasi masalah file kecil.
  • Adalah Spark native config yang kurang efektif dibanding Glue native groupFiles.
  • Digunakan untuk konteks multi-instance bukan incremental.
  • Mengubah model dari scheduled ke event-driven.
  • Bergantung pada naming convention yang mungkin tidak selalu ada, dan tidak melacak file yang sudah diproses.
  • Tanpa partitioning menyebabkan full scan setiap query.
  • Tidak efisien untuk analytical queries.
  • Tidak cocok untuk daily batch job yang bisa menggunakan transient cluster.
  • Untuk storage-heavy workloads, bukan CPU-intensive.
  • Lebih mahal tanpa keuntungan compute.
  • Hanya menangani format header dan null.
  • Memaksakan loading tapi mengubah data (truncate columns) yang bisa menyebabkan data loss tanpa logging yang jelas.
  • Hanya validasi tanpa loading aktual.
  • Membutuhkan manajemen manual multiple jobs.
  • Menambah compute tapi tidak mengubah cara baca JDBC.
  • Mempercepat satu koneksi tapi tetap single-threaded.
