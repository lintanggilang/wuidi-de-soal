Domain 2: Data Store Management — Task 2.3: Manage the lifecycle of data

Skill 2.3.2: S3 Lifecycle policies (storage tier)

LifecycleGlacierIntelligent-Tiering

Ringkasan

Skill ini termasuk dalam Domain 2: Data Store Management (Task 2.3: Manage the lifecycle of data), dengan fokus pada s3 lifecycle policies (storage tier). Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon S3
Object storage tahan lama; dasar data lake, mendukung event notification, versioning, dan lifecycle.
S3 Lifecycle
Aturan transisi antar storage class dan expiration objek berdasarkan umur/tag/prefix.
S3 Intelligent-Tiering
Memindahkan objek antar tier akses otomatis berdasarkan pola akses tanpa biaya retrieval.
Amazon S3 Glacier
Storage arsip berbiaya sangat rendah untuk data jarang diakses dengan waktu retrieval lebih lama.

Poin-Poin Kunci

  • This lifecycle policy matches each storage tier to the stated access pattern and constraints: (1) S3 Standard for days 0-30: heavy access in first 7 days, occasional access through day 30; (2) S3 Standard-IA after 30 days: lower cost for infrequent access, millisecond retrieval. The 30-day minimum storage charge for Standard-IA means earlier transition wastes money; (3) Glacier Instant Retrieval after 90 days: lowest cost for data accessed ~once per quarter with millisecond retrieval — satisfies the "instant retrieval for legal compliance" requirement; (4) Glacier Flexible Retrieval after 365 days: when "several hours" retrieval is acceptable, this provides significantly lower cost. Option B — One Zone-IA has no cross-AZ redundancy, risking data loss for compliance-required videos. Glacier Deep Archive has 12-48 hour retrieval — the question states "several hours" is acceptable only AFTER 365 days, not after 90 days. Option C — Intelligent-Tiering works well for unpredictable access patterns but charges a monitoring fee per object. For predictable patterns (heavy → occasional → rare → archive), lifecycle rules are more cost-effective because there's no per-object monitoring overhead. Also, Intelligent-Tiering's archive tiers must be explicitly enabled and configured. Option D — transitioning to Standard-IA after 7 days incurs the 30-day minimum storage charge (you pay for 30 days even though the object was in Standard-IA for only 23 days before the next transition). Also, Glacier Flexible Retrieval after 60 days doesn't satisfy "instant retrieval for compliance" between days 60-365.
  • The 128 KB minimum object size charge makes Standard-IA cost-prohibitive for small files: (1) each 50 KB file in Standard-IA is billed as 128 KB — you pay for 2.56x the actual storage; (2) S3 Standard storage cost: 50 KB × $0.023/GB = very small; (3) S3 Standard-IA equivalent: 128 KB × $0.0125/GB — while the per-GB rate is lower, the billed volume is 2.5x larger; (4) effective per-actual-KB cost in Standard-IA exceeds Standard for files below 128 KB; (5) with millions of such files, the aggregate cost increase is significant. The 30-day minimum storage duration adds further cost if files are deleted or overwritten before 30 days. The solution: keep small files in Standard or aggregate them into larger objects before transitioning. Option B — lifecycle transitions do incur request charges (COPY to new storage class), but for a one-time transition, this is a small one-time cost, not an ongoing increase. The question describes sustained cost increase, pointing to the per-object minimum size charge. Option C — retrieval charges for Standard-IA exist but are relatively small ($0.01/GB retrieved). The cost INCREASE is from storage billing (ongoing), not occasional retrieval. Access patterns may contribute but aren't the primary driver of increased cost. Option D — there is no "penalty" for transitioning before 30 days. The 30-day minimum is a billing construct: if you DELETE the object before 30 days in IA, you're charged for the remaining days. But the transition at 15 days itself doesn't trigger penalties; it's the minimum size charge that drives cost up.
  • S3 Lifecycle transitions follow a defined waterfall hierarchy where not all transitions between classes are permitted: (1) the valid transition paths are ordered: Standard → Standard-IA → Intelligent-Tiering → One Zone-IA → Glacier Instant Retrieval → Glacier Flexible Retrieval → Glacier Deep Archive, BUT not every adjacent jump is allowed; (2) specifically, Glacier Instant Retrieval cannot transition directly to Glacier Flexible Retrieval in lifecycle rules; (3) this is an AWS-imposed constraint in the lifecycle rule validation; (4) the restructure options are: skip Glacier Instant Retrieval (Standard-IA → Glacier Flexible directly), or go from Glacier Instant Retrieval to Glacier Deep Archive (skipping Flexible). Choose based on retrieval requirements. Option B — while the constraint is real, the explanation is imprecise. They're separate storage classes, not the "same family." The constraint is about lifecycle rule transition paths, which have specific allowed sequences defined by AWS. Option C — minimum storage duration charges don't cause lifecycle rule creation errors. They're billing constructs: if you transition OUT of a class before its minimum duration, you still pay for the full minimum. The error is about an invalid transition PATH, not timing. Option D — using separate rules doesn't bypass the constraint. S3 evaluates the combined effect of all rules. An object in Glacier Instant Retrieval cannot be transitioned to Glacier Flexible Retrieval regardless of whether it's one rule or two.
  • Multiple lifecycle rules with different filters handle diverse requirements elegantly: (1) each rule has its own filter (prefix, tag, or combination) and actions (transitions, expirations); (2) Rule 1 (prefix filter "logs/") applies only to objects under logs/ — transitioning to Glacier after 30 days; (3) Rule 2 (prefix "analytics/") ensures analytics output moves to Standard-IA for cost optimization while remaining instantly accessible; (4) Rule 3 uses an AND filter combining prefix "raw/" with tag "archive=true" — only objects matching BOTH conditions transition to Deep Archive; (5) objects in raw/ WITHOUT the "archive=true" tag match no rule and stay in Standard. A single bucket can have up to 1,000 lifecycle rules, supporting complex policies. Option B — lifecycle rules don't support conditional logic (if/elif). Each rule has one filter and one set of actions. You need separate rules for different behaviors, not conditional branching within a single rule. Option C — one rule per bucket is unnecessarily restrictive. S3 supports multiple rules per bucket with different prefix/tag filters. Splitting data into multiple buckets adds complexity (separate bucket policies, cross-bucket references, etc.) without benefit. Option D — Intelligent-Tiering moves objects between tiers based on access frequency, not business rules (prefix, tags). It can't enforce "logs go to Glacier after 30 days regardless of access" — frequently accessed logs would remain in the frequent tier. Business-driven policies require lifecycle rules, not access-pattern-based automation.
  • File compaction reduces the total object count, directly reducing per-object monitoring fees: (1) Intelligent-Tiering charges monitoring per object ($0.0025/1000 objects/month) regardless of object size; (2) 500 million objects × $0.0025/1000 = $1,250/month in monitoring alone; (3) compacting small files into larger objects (e.g., combining 1000 small files into 1 file) reduces object count from 500M to 500K, cutting monitoring to $1.25/month; (4) compaction also improves read performance (fewer GET requests) and reduces request costs. Note: AWS does exempt objects smaller than 128 KB from the monitoring fee, storing them in the Frequent Access tier only — but the question states the charges ARE significant, suggesting many objects exceed 128 KB or the cost calculation reflects the actual billable objects. Compaction addresses the root cause: too many objects. Option A — objects <128 KB are already exempt from monitoring charges. If the $1,250 charge is occurring, it's from objects ≥128 KB. This option doesn't reduce costs for the billable objects. Option B — the monitoring/automation charge applies regardless of whether archive tiers are configured. Enabling/disabling archive tiers doesn't change the base monitoring fee. Option D — switching to lifecycle rules works for predictable patterns but the scenario states "unpredictable access patterns" — lifecycle rules may transition frequently-accessed objects to IA (incurring retrieval charges) or miss optimization opportunities for truly inactive data.
  • Standard-IA is the direct multi-AZ equivalent of One Zone-IA: (1) same access pattern optimization (infrequent access, instant retrieval); (2) multi-AZ redundancy — data survives AZ-level failures; (3) cost premium over One Zone-IA is ~25% ($0.0125 vs $0.01/GB) — a small premium for AZ resilience; (4) 99.9% availability SLA vs 99.5% for One Zone-IA; (5) for critical reporting data that cannot tolerate AZ outages, the 25% storage premium is justified by availability guarantees. The lifecycle rule simply changes the transition target from One Zone-IA to Standard-IA. Option B — Glacier Instant Retrieval has lower storage cost ($0.004/GB) and millisecond retrieval, but it has higher retrieval costs and a 90-day minimum storage duration. If objects are accessed within 90 days of transition or accessed more than once per quarter, Glacier Instant Retrieval can be more expensive than Standard-IA. It's not a direct replacement for the same use case. Option C — Intelligent-Tiering's IA tier does provide cross-AZ redundancy, but it requires the monitoring fee per object and doesn't give direct control over WHEN objects transition. It's a different management model, not a direct tier substitution in lifecycle rules. Option D — CRR creates copies in a DIFFERENT region (not another AZ in the same region), doubling storage costs and adding replication latency. It's over-engineered for AZ-level resilience — Standard-IA provides cross-AZ within the same region natively.
  • Standard-IA has per-GB retrieval charges that compound with Athena's scan costs: (1) Standard-IA storage is cheaper but charges $0.01/GB for every byte retrieved; (2) when Athena scans 100 GB of data in Standard-IA, the cost is: Athena scan ($5/TB × 0.1 TB = $0.50) + S3 retrieval ($0.01/GB × 100 GB = $1.00) + GET requests; (3) for frequently queried data, the retrieval charges can exceed the storage savings from using Standard-IA; (4) optimization strategies: Parquet/ORC format (Athena reads only required columns, reducing bytes retrieved); partitioning (Athena skips irrelevant partitions); keeping frequently-queried date ranges in Standard. The lifecycle rule should be calibrated to the ACTUAL access pattern, not just age. Option B — Standard-IA does NOT require restore operations. Data is instantly accessible (millisecond latency). Only Glacier classes (Flexible/Deep Archive) require explicit restore before access. Standard-IA data is directly readable. Option C — Athena CAN directly query Standard-IA objects — no storage class change occurs. S3 serves the data from Standard-IA without transitioning it. The object remains in Standard-IA after being read. Option D — accessing an object in Standard-IA does NOT reset its minimum storage duration timer. The 30-day minimum applies from the creation/transition date regardless of subsequent access.
  • Lifecycle rules for noncurrent versions provide targeted, automated version management: (1) "NoncurrentVersionTransition" moves old versions to cheaper storage (Deep Archive at $0.00099/GB vs Standard $0.023/GB = 95% savings); (2) "NoncurrentVersionExpiration" permanently deletes versions older than N days; (3) "NewerNoncurrentVersions" parameter (count-based retention) keeps the N most recent noncurrent versions regardless of age — providing rollback capability; (4) these actions ONLY affect noncurrent versions — current (latest) versions are never touched; (5) ongoing automation prevents future accumulation. Result: keep 3 recent versions for rollback, transition everything else cheaply, and delete very old versions automatically. Option B — disabling versioning on a bucket is NOT possible. You can only SUSPEND versioning. Suspending versioning does NOT delete existing noncurrent versions — they remain and continue incurring storage costs. It only prevents NEW versions from being created. Option C — lifecycle rules based on object age use CREATION date. A current version of a file updated yesterday is 1 day old — it wouldn't expire. But this rule doesn't distinguish between current and noncurrent versions. It could expire current versions of files that haven't been updated in 90 days, causing data loss. Option D — S3 Batch Operations for one-time cleanup is valid but doesn't prevent future accumulation. Suspending versioning prevents new versions but loses the ability to recover from accidental overwrites — the reason versioning was enabled. Lifecycle rules maintain versioning protection while controlling costs.
  • Objects in Glacier Flexible Retrieval require explicit restore before they can be read by any service: (1) initiate restore via S3 API (restore-object), console, or S3 Batch Operations (for many objects); (2) choose retrieval speed: Expedited (1-5 min, highest cost), Standard (3-5 hours), or Bulk (5-12 hours, lowest cost); (3) specify retention period (days to keep the restored copy available); (4) once restored, a temporary copy exists in the S3 Standard access tier — readable by Athena, S3 GET, etc.; (5) the archive copy remains in Glacier (you're not charged to re-archive); (6) after the retention period, the temporary copy is automatically removed. For a one-time query, use S3 Batch Operations to restore all objects in the relevant partitions, wait for restoration, run the query, then let copies expire. Option B — lifecycle rules only transition FORWARD (Standard → IA → Glacier). They cannot transition objects BACK to a higher-access tier. Modifying the rule prevents future transitions but doesn't restore already-archived objects. Option C — Athena has no GLACIER_RETRIEVAL hint. It cannot automatically restore archived objects during query execution. Query engines read from S3 using standard GET operations which fail on Glacier objects. Option D — the storage class is a property of the S3 OBJECT, not the Glue table metadata. Creating a new table doesn't change the objects' storage class. The same GET request failure occurs regardless of which metadata entry points to the Glacier object.
  • Tag-based lifecycle filtering enables different strategies for different data categories within the same bucket: (1) tags identify business-meaningful categories (quarterly-reporting vs. unused); (2) separate lifecycle rules with tag filters apply appropriate transitions to each category; (3) Glacier Instant Retrieval is perfect for quarterly access — extremely low storage cost ($0.004/GB) with millisecond retrieval, no restore needed; (4) Deep Archive remains for truly unused data where 12-48 hour retrieval is acceptable; (5) this is the recommended pattern for heterogeneous access patterns in a single bucket. Option B — S3 Intelligent-Tiering with Deep Archive tier could work if the quarterly access is sufficient to prevent archive (objects accessed within 180 consecutive days stay in frequent/infrequent tiers). However, quarterly access (every 90 days) may still allow the 90-day inactivity window for the Archive Instant Access tier, and 180 days for Deep Archive. The behavior isn't deterministic for exact quarterly patterns. Also, monitoring fees per object add up. Option C — moving objects between buckets adds complexity (different bucket policies, access configurations, naming conventions). Tag-based filtering within one bucket is simpler and maintains a single access point. Option D — extending to 365 days keeps ALL data in Standard/IA for a full year regardless of access patterns, losing Deep Archive savings on the truly unused majority of data. It doesn't differentiate — it just delays archiving for everything.
