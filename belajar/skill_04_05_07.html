Skill 4.5.7: Governance framework and data sharing

governanceframeworkmesh

Summary

Skill this including in Domain 4: Security & Governance (Task 4.5: Understand data privacy and governance), with fokus on governance framework and data sharing. Materi berikut merangkum service AWS that relevan beserta concept important that needs kamu kuasai for topik this.

Key Services & Concepts

Amazon DataZone
Katalog bisnis & portal self-service for discovery, subscription, and governed access (kini SageMaker Catalog).

Key Points

  • Domain ownership is prinsip data mesh that directly resolves bottleneck central team. Alih-alih 5 engineers melayani 20 domains, each domain has engineers itself that bertanggung jawab atas data mereka — from ingestion up to publishing data products. On AWS: each domain mendapat AWS account (or set of accounts), manages Glue ETL, S3 storage, and publishes through DataZone projects. Central team changes role menjadi platform team that provides tools/templates.
  • AWS Clean Rooms designed for privacy-preserving data collaboration. Key features: (1) Collaboration — both parties bring their data without sharing raw records, (2) Analysis rules — restrict what queries can be run (only aggregations, minimum group sizes to prevent re-identification), (3) Output restrictions — results must meet minimum aggregation thresholds (e.g., COUNT must be ≥100 before showing result), preventing exposure of individuals, (4) No data movement — each party's data stays in their account.
  • Amazon DataZone with custom metadata forms provides governance enforcement that terintegrasi with data discovery: (1) Metadata forms — template fields required diisi (Data Owner, Data Steward, Classification Level) before asset can in-publish to catalog. Ini enforces completeness. (2) Business glossary — standardisasi terminology (Confidential, Internal, Public) so that classification consistent. (3) Catalog sebagai single source of truth — all governance metadata terpusat and discoverable. (4) Tied to access workflows — classification can drive approval policies.
  • AWS Data Exchange designed for third-party data sharing and monetization: (1) Publisher creates data products — datasets, APIs, or Lake Formation-based access, (2) Products listed in AWS Marketplace — discoverable by potential subscribers, (3) Pricing — free, subscription, or per-use pricing models, (4) Subscriber eligibility — publisher can enable "subscription verification" that requires approval before access granted (important for controlled distribution to research institutions), (5) Automatic fulfillment — once approved, subscribers get access without manual setup per institution.
  • Data classification framework that effective applies controls proportional to sensitivity level. Progressive security controls: Public — minimal controls because data can diakses who saja. Internal — basic encryption (SSE-S3 managed) and authentication required. Confidential — stronger encryption (customer-managed CMK provides key rotation control and access audit), role-based access (least privilege), and audit logging required. Restricted — maximum controls: CMK with CloudHSM key store (FIPS 140-2 Level 3), MFA required for decrypt operations, real-time monitoring (GuardDuty, Macie), DLP scanning, and dynamic data masking.
  • Federated computational governance berarti: policies defined centrally, enforced AUTOMATICALLY (computational — not manual review), and applied across federation of domains. AWS implementation: (1) SCPs — preventive guardrails that automatically prevent policy violations (region restrictions, service restrictions), (2) Config conformance packs — detective controls deployed to all domain accounts via Organizations, automatically evaluating compliance, (3) Lake Formation tag-based policies — centrally defined data access patterns inherited by all domains. Domain teams operates freely WITHIN guardrails without needing manually implement governance.
  • AWS Clean Rooms with cryptographic computing is solution ideal for privacy-preserving matching: (1) Clean Rooms collaboration — kedua parties bring data without sharing raw records, (2) Cryptographic computing (optional enhancement) — data still encrypted during processing so that even AWS cannot see individual records, (3) Analysis rules — restrict output to aggregate-only (conversion rate, total purchases) with minimum thresholds (e.g., results only shown if at least 100 matched customers), (4) No individual-level results — matching happens internally but only aggregate outputs returned.
  • Data governance maturity models typically have 5 levels: Level 1 (Initial) — no formal governance. Level 2 (Managed) — basic controls exist (encryption, IAM) but reactive. Level 3 (Defined) — formal processes, cataloging, quality monitoring, lineage. Level 4 (Quantitatively Managed) — metrics-driven, automated governance. Level 5 (Optimizing) — continuous improvement, AI-driven governance. Perusahaan this has encryption and access controls but lacks cataloging, quality, lineage — typical Level 2. Next steps to Level 3: (1) DataZone for cataloging and discovery, (2) Glue Data Quality for quality rules, (3) Lineage tracking, (4) Formal policies and roles.
  • In governance framework that proper: Data Owner — accountable for business decisions about data (including sharing), has final business authority TAPI must comply with governance policies. Data Steward — guardian of data quality and compliance, provides requirements that Owner must meet (PII handling, consent, regulatory compliance). Data Custodian — responsible for technical implementation (encryption, access controls, storage). Resolution: Owner decides to share but Steward and Custodian requirements must dipenuhi first. If deadlock, Data Governance Council/Committee arbitrates.
  • Federated governance is model that correct when: (1) Multiple domains with regulatory requirements different — HIPAA, SOX, CCPA has controls that different and specific domain expertise is required, (2) Scale — 15 domains too many for satu central team manages all detail, (3) Speed — domain teams can bergerak fast without bottleneck central approval for domain-specific decisions. Structure: Central team sets BASELINE (minimum encryption standards, access patterns, audit requirements, tooling choices) and domains ADD domain-specific controls in atas baseline.

Common Misconceptions & Pitfalls

  • Federated computational governance about automating governance policies, not distributing pipeline ownership.
  • Self-serve platform membantu but if still central team that deploy, bottleneck still ada.
  • Data as product about treating datasets sebagai products (quality, documentation, SLAs), not format standardization.
  • Database endpoint with RLS still exposes individual rows that pass the filter.
  • Sharing raw data via S3 exposes individual records regardless of encryption.
  • Data Exchange shares the actual dataset; once downloaded, partner has full access to all records.
  • Config rules only detect missing tags, not enforce rich governance metadata.
  • DynamoDB table separate from data catalog, easy menjadi stale.
  • Resource tags useful but not provides discovery experience or not connected to data access workflows.
  • 50 replication rules not scalable, not support monetization, and requires knowing each institution's account.
  • Redshift data sharing requires each consumer to have Redshift; research institutions may not.
  • DataZone for internal/organizational governance, not external marketplace.
  • Encryption alone not sufficient; access control, monitoring, and other controls must also progressive.
  • Classification without corresponding controls not meaningful.
  • Uniform controls wastes resources for low-sensitivity data or under-protects high-sensitivity.
  • Independent policies not "federated" — leads to inconsistency.
  • Manual PR review is not computational and creates central bottleneck (opposite of data mesh goal).
  • Wiki reference is manual, not computational.
  • Redshift data sharing exposes queryable data; column masking helps but individual rows still visible.
  • Shared bucket exposes raw data from kedua parties.
  • Data Exchange creates full dataset available to partner, violating privacy.
  • Encryption/access alone not highest maturity.
  • Security ≠ governance; governance encompasses quality, cataloging, lineage, stewardship.
  • Level 1 would mean NO controls; they have basic ones. Also "all simultaneously" is impractical.
  • Steward advises and sets requirements but doesn't make business decisions.
  • Custodian implements solutions, doesn't have blocking authority over business decisions.
  • Owner cannot override compliance requirements.
  • Uniform policies not address domain-specific regulations; central team unlikely has HIPAA + SOX + CCPA expertise.
  • No governance leads to inconsistency and compliance failures.
  • HIPAA controls not automatically cover SOX (financial audit trails) or CCPA (consumer rights); over-engineering non-healthcare domains adds cost without benefit.
