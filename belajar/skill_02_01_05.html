Key Points

  • Redshift federated queries enable querying external databases (Aurora PostgreSQL/MySQL, RDS) directly from Redshift SQL without data movement. The query pushes predicates to Aurora for efficient filtering, retrieves only matching rows, and joins them with local Redshift tables. Since inventory changes every few minutes, federated queries always read current Aurora values — no replication lag. The external schema is configured once, then analysts use standard SQL JOINs.
  • Materialized views with AUTO REFRESH are the ideal solution: (1) the complex aggregation is computed once and stored physically; (2) AUTO REFRESH detects when base tables change (after hourly ETL) and incrementally updates the materialized view — only recomputing affected portions, not the entire 5 TB aggregation; (3) dashboard queries read from the pre-computed materialized view in milliseconds; (4) Redshift automatically rewrites compatible queries to use the materialized view transparently.
  • Redshift Spectrum is purpose-built for this scenario: (1) it queries S3 data directly without loading it into Redshift (saving storage costs for 100 TB); (2) independent Spectrum compute layer scales automatically to scan S3 in parallel, separate from the main cluster's resources; (3) the same Redshift SQL session can JOIN local tables (business metrics) with external Spectrum tables (S3 logs) transparently; (4) partition pruning on date eliminates scanning irrelevant partitions; (5) Parquet column pruning and predicate pushdown minimize data read.
  • Redshift data sharing is the native, purpose-built solution for cross-cluster data access: (1) zero-copy sharing — no ETL, no data duplication, no storage costs on the consumer; (2) live access — the consumer sees the producer's data as it is now, including daily updates immediately after commit; (3) cross-region data sharing is supported; (4) the consumer queries shared data with standard SQL as if it were local; (5) the producer controls what's shared (specific schemas/tables) and can revoke access.
  • This optimization attacks Spectrum's cost model (charged per byte scanned): (1) adding event_type as a partition enables partition pruning — queries filtering on event_type skip entire directory trees, potentially eliminating 90%+ of scanned data; (2) Parquet columnar format means only referenced columns are read (vs. reading entire rows in CSV/JSON); (3) Snappy compression reduces physical bytes by 60-80%. Combined, a $250 query might drop to $10-25. Spectrum scales its compute automatically — the bottleneck is data volume scanned, not compute capacity.
  • Federated queries provide true real-time access: (1) queries hit the live RDS database, seeing the absolute latest data with zero lag; (2) predicate pushdown ensures only relevant rows transfer from RDS to Redshift (not the entire orders table); (3) standard SQL JOIN syntax combines RDS real-time data with Redshift analytics seamlessly; (4) no additional infrastructure or ETL jobs to manage. For status lookups that filter to a small subset of orders, the cross-database overhead is minimal.
  • Cross-account data sharing is the native Redshift solution for this scenario: (1) the producer explicitly controls which tables are shared and which accounts can access them; (2) consumers get read-only access by design — they cannot modify producer data; (3) no data copying means consumers always see current production reference data (updated currency rates, new product categories); (4) cross-account sharing uses AWS RAM (Resource Access Manager) for secure account-level grants; (5) zero storage cost on consumer side.
  • Materializing critical Spectrum query results locally eliminates the variable Spectrum performance entirely: (1) critical dashboard queries read from local Redshift storage with consistent sub-second performance; (2) AUTO REFRESH keeps results current without manual intervention; (3) no dependency on shared Spectrum compute pool means no contention-related variability; (4) only critical/predictable queries are materialized — ad-hoc queries still use Spectrum. This trades some storage cost for guaranteed performance on known workloads.
  • Redshift's architecture natively supports multi-source queries through complementary features: (1) Spectrum external schemas define S3 data lake tables (Parquet/CSV/JSON) queryable via SQL; (2) federated query external schemas define live connections to Aurora/RDS databases; (3) local schemas contain Redshift-native tables. A single SQL statement can JOIN across all three: SELECT * FROM local.sales s JOIN spectrum.clickstream c ON s.user_id = c.user_id JOIN aurora_ext.inventory i ON s.product_id = i.product_id. Each source is optimized independently (Spectrum parallelizes S3 scans, federated queries push predicates to RDS).
  • WLM queue isolation addresses the root cause: while Spectrum's S3 scanning runs on separate infrastructure, the results must flow back to the Redshift cluster for final JOIN, aggregation, and sort operations — this is what consumes local resources. WLM queues limit how much cluster memory and concurrency Spectrum-heavy queries can consume, reserving guaranteed capacity for local queries. Query routing (by user group or query group) automatically directs queries to the appropriate queue.

Common Misconceptions & Pitfalls

  • ETL every 5 minutes introduces 5-minute staleness, adds Glue job costs, and creates operational complexity for what should be a simple query pattern.
  • Athena federated queries could work but add latency from the Athena query engine layer, and Redshift's native federated queries provide better performance for Redshift-centric workloads with direct integration.
  • Loading 3 years of sales data (potentially terabytes) into Aurora is impractical and expensive; Aurora isn't optimized for analytical queries on historical data.
  • Manual summary tables work but require custom scheduling, don't incrementally refresh, and must recompute the full aggregation each hour (wasteful if only small portions changed).
  • Spectrum queries data in S3, not local Redshift tables; moving the 5 TB fact table to S3 for Spectrum access would be slower than local queries, not faster.
  • Result caching serves identical query text from cache, but after hourly ETL updates the underlying data, the cache is invalidated and the 8-minute query must re-execute; dashboards won't benefit immediately after ETL.
  • Athena querying S3 and exporting to Redshift is a multi-step manual process; Spectrum provides the same capability in a single SQL statement.
  • Loading portions of 100 TB for ad-hoc queries requires predicting which data is needed, consumes cluster storage, and the COPY operation itself takes significant time for large datasets.
  • Redshift federated queries connect to RDS/Aurora databases, not directly to S3 files; Spectrum is the S3 access mechanism.
  • Daily Glue ETL creates a 24-hour stale copy, costs compute for the ETL job, and doubles storage costs (200 GB × 2 regions).
  • Redshift federated queries connect to RDS/Aurora PostgreSQL, not to other Redshift clusters; data sharing is the Redshift-to-Redshift mechanism.
  • UNLOAD → S3 replication → COPY is a complex multi-step pipeline with hours of latency and operational overhead.
  • Intelligent-Tiering affects storage cost tiers, not query performance or Spectrum scanning costs.
  • Materialized views on Spectrum external tables have limitations (not all aggregations supported) and require storage in Redshift for the materialized results; better for known patterns, not ad-hoc queries.
  • Spectrum compute nodes scale independently from the Redshift cluster slices; you cannot manually increase Spectrum nodes, and more compute doesn't reduce data scanned (the cost driver).
  • DMS with CDC provides near real-time (seconds of lag) but requires a DMS replication instance (ongoing cost), duplicates the orders table in Redshift (storage cost), and still has some replication lag that may matter for order status queries.
  • Athena federated queries add an extra layer (Athena → RDS → export → Redshift) with more latency and complexity than Redshift's native federated query capability.
  • 5-minute export cycles create staleness; order status that changed 4 minutes ago wouldn't appear until next export, making "currently shipped" queries inaccurate.
  • Redshift federated queries connect to RDS/Aurora databases, not to other Redshift clusters; this approach isn't technically possible for Redshift-to-Redshift access.
  • Redshift does not support read replicas across accounts (or at all in the traditional sense); this feature doesn't exist.
  • UNLOAD/COPY creates point-in-time copies that immediately become stale; requires recurring ETL, doubles storage, and operational overhead for maintaining sync.
  • Adding Redshift nodes doesn't increase Spectrum compute allocation; Spectrum is a separate shared resource pool that scales independently.
  • Scheduling during off-peak doesn't guarantee performance (other clusters' schedules may conflict) and limits when critical queries can run.
  • Concurrency scaling adds capacity for queries running on the main cluster, not for Spectrum queries which execute on the separate Spectrum layer.
  • DataBrew is a data preparation/transformation tool, not a query federation engine; it doesn't create queryable unified views.
  • Lake Formation provides governance and catalog management but doesn't have its own query engine; queries still execute through Athena, Redshift, or EMR.
  • Replacing Redshift with Athena loses Redshift's performance for local data (materialized views, result caching, columnar storage on managed SSD); the question asks about Redshift as the hub.
  • A separate cluster is a valid but expensive solution (doubling infrastructure costs); WLM provides isolation within a single cluster at zero additional cost.
  • Increasing cluster size adds resources for both workloads but doesn't guarantee isolation; without WLM, a burst of Spectrum aggregations can still consume all available resources regardless of cluster size.
  • Moving to Athena would work for pure Spectrum queries but loses the ability to JOIN S3 data with local Redshift tables in a single query, which is often required.
