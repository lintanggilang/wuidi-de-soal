Key Services & Concepts

Amazon Data Firehose
Pengiriman streaming ter-manage to S3/Redshift/OpenSearch with buffering; near real-time, minim code.
Amazon EMR
Cluster big data managed (Spark, Hive, Presto); supports Spot Instances for hemat cost.

Key Points

  • Amazon Data Firehose (previously Kinesis Data Firehose) is solution most correct for high-volume log ingestion to S3. Firehose supports direct integration from many AWS services (VPC Flow Logs, WAF, CloudTrail), auto-scaling without management, built-in buffering for batch writes that efficient to S3, dynamic partitioning for organisasi data, and format conversion (JSON to Parquet).
  • Amazon EMR with Spark provides kontrol full above cluster sizing, memory configuration, and processing optimization that is required for 10 TB data with complex joins and business rules in limit time 4 hours. Memory-optimized instances (r5/r6g) optimal for large-scale data joining. EMR also supports custom libraries for business rules.
  • OCSF (Open Cybersecurity Schema Framework) is standard industri for normalisasi security log data. Uses AWS Glue ETL for mentransformasi each source to format OCSF provides: (1) schema that consistent and well-documented, (2) Parquet format for query efficiency, (3) maintainability because OCSF is standard that evolving with community support. AWS Security Lake also uses OCSF.
  • AWS Security Lake automatically collects log from berbagai AWS sources (CloudTrail, VPC Flow Logs, Route 53, Security Hub findings, dll), menormalisasi to OCSF schema, and stores in S3. Security Lake supports rollup regions for reduces cross-region transfer, subscriber-based access control that enables business units only melihat data mereka, and delegated administrator for security team.
  • Kinesis Data Streams → Managed Flink provides latency terendah for real-time processing: Kinesis provides sub-second delivery, and Flink processes events via streaming with stateful enrichment (lookup to threat intelligence database uses async I/O). Output to Firehose → S3 for historical analysis and OpenSearch for real-time dashboards.
  • For one-time processing 2 PB data, EMR with Spot instances provides cost terendah. Spot instances can 60-90% cheaper from On-Demand. EMR Spark provides full kontrol over cluster sizing and processing parallelism for memenuhi 48-hour deadline. For one-time jobs, Spot interruption can is handled with checkpointing.
  • Glue ETL jobs that scheduled bulanan provides solution most automatic and repeatable: scheduled triggers ensures jobs runs without intervensi manual, jobs can processes multiple log sources (CloudTrail + VPC Flow Logs + S3 access logs), produces summary tables that terstruktur in Data Catalog, and QuickSight dashboards automatic refresh from summary tables.
  • S3 Glacier Instant Retrieval optimal for data that diakses rarely (at all per kuartal) but requires millisecond retrieval when diakses — suitable for 30-365 days in mana access rarely but must segera available. Deep Archive (365+ days) provides cost terendah ($0.00099/GB/month) for data that almost not pernah diakses except legal hold (retrieval in 12 hours still acceptable).
  • Konversi to Parquet provides improvement terbesar for Athena: columnar format enables Athena only reads column that is required (reduces data scanned significant), Snappy compression reduces size file more lanjut, and buffer 128 MB produces file berukuran optimal for Athena (ideal 128 MB-512 MB). Kombinasi Parquet + larger files can reduces query cost and time up to 90%.
  • Apache Flink (via Managed Service) is one-satunya opsi that supports windowed joins — capabilities for combines events from multiple streams in time window certain (5 minutes). Flink processes events in a stateful, stores state per IP address, and detects when GuardDuty finding and unusual VPC traffic from IP that same occurs in window 5 minutes. This provides true real-time correlation.

Common Misconceptions & Pitfalls

  • Adds hop through CloudWatch Logs that adds cost ingestion and latency — does not need for route to S3.
  • Has concurrency limits and timeout that membuatnya not ideal for 5 TB/day.
  • Has gap 1 hours and Glue not ideal for continuous ingestion.
  • Not supports complex business rules, custom UDFs limited, and has query timeout limits.
  • Has auto-scaling but less control over cluster configuration and can less predictable for strict 4-hour SLA on 10 TB.
  • Not can performs joins cross-file and has 15-minute timeout per invocation.
  • Berfungsi but custom schema without standard can becomes maintenance burden.
  • Not mentransformasi data fisik and views can becomes complex and slow.
  • Mendeteksi schema but not menormalkan — each source still has schema different.
  • Menggandakan storage and requires custom access management.
  • Maximizes cross-region transfer costs.
  • Very expensive for 200 accounts and requires cluster management that significant.
  • Only detect based on pattern count, not enrichment-based threat detection, and alarm evaluation adds latency.
  • Has buffering delay Firehose (minimum 60 seconds) that exceeds requirement 30 seconds.
  • Has micro-batch latency higher from Flink and EMR cluster startup time becomes problem.
  • Charges $5/TB scanned = $10,000 for 2 PB, without Spot pricing benefit, and has concurrent query limits.
  • Has per-DPU-hour pricing that usually more expensive from EMR Spot for workloads scale large.
  • Requires loading 2 PB that itself consumes time significant and very expensive for one-time use.
  • Only menampilkan metrics, not detailed log analysis that is required for unique principals and IP range checking.
  • Has limit query scope and cannot join between log sources that different.
  • Not automatic — requires human intervention each months.
  • Adds monitoring fee per object that significant for 500 GB/day × 7 years = millions of objects.
  • Not has multi-AZ durability that less correct for compliance logs.
  • More expensive from Glacier Instant Retrieval for access that very rarely.
  • Reduces storage but Athena still must decompress and scan entire file because row-format.
  • Membantu filter but without columnar format, improvement limited.
  • Still JSON row-format that forces full file scan.
  • Only performs single-event pattern matching — not supports temporal correlation between events different.
  • Has latency 5+ minutes and not streaming.
  • Melakukan top-N analysis, not multi-source temporal correlation.
