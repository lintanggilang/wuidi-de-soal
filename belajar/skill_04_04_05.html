Skill 4.4.5: Integrate services for logging

EMRFirehoselogging

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.4: Prepare logs for audit), dengan fokus pada integrate services for logging. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon Data Firehose
Pengiriman streaming ter-manage ke S3/Redshift/OpenSearch dengan buffering; near real-time, minim kode.
Amazon EMR
Cluster big data terkelola (Spark, Hive, Presto); mendukung Spot Instances untuk hemat biaya.

Poin-Poin Kunci

  • Amazon Data Firehose (sebelumnya Kinesis Data Firehose) adalah solusi paling tepat untuk high-volume log ingestion ke S3. Firehose mendukung direct integration dari banyak AWS services (VPC Flow Logs, WAF, CloudTrail), auto-scaling tanpa management, built-in buffering untuk batch writes yang efisien ke S3, dynamic partitioning untuk organisasi data, dan format conversion (JSON ke Parquet).
  • Amazon EMR dengan Spark memberikan kontrol penuh atas cluster sizing, memory configuration, dan processing optimization yang diperlukan untuk 10 TB data dengan complex joins dan business rules dalam batas waktu 4 jam. Memory-optimized instances (r5/r6g) optimal untuk large-scale data joining. EMR juga mendukung custom libraries untuk business rules.
  • OCSF (Open Cybersecurity Schema Framework) adalah standar industri untuk normalisasi security log data. Menggunakan AWS Glue ETL untuk mentransformasi setiap sumber ke format OCSF memberikan: (1) schema yang konsisten dan well-documented, (2) Parquet format untuk query efficiency, (3) maintainability karena OCSF adalah standard yang evolving dengan community support. AWS Security Lake juga menggunakan OCSF.
  • AWS Security Lake secara otomatis mengumpulkan log dari berbagai AWS sources (CloudTrail, VPC Flow Logs, Route 53, Security Hub findings, dll), menormalisasi ke OCSF schema, dan menyimpan di S3. Security Lake mendukung rollup regions untuk mengurangi cross-region transfer, subscriber-based access control yang memungkinkan business units hanya melihat data mereka, dan delegated administrator untuk security team.
  • Kinesis Data Streams → Managed Flink memberikan latency terendah untuk real-time processing: Kinesis memberikan sub-second delivery, dan Flink memproses events secara streaming dengan stateful enrichment (lookup ke threat intelligence database menggunakan async I/O). Output ke Firehose → S3 untuk historical analysis dan OpenSearch untuk real-time dashboards.
  • Untuk one-time processing 2 PB data, EMR dengan Spot instances memberikan biaya terendah. Spot instances bisa 60-90% lebih murah dari On-Demand. EMR Spark memberikan full kontrol over cluster sizing dan processing parallelism untuk memenuhi 48-hour deadline. Untuk one-time jobs, Spot interruption bisa ditangani dengan checkpointing.
  • Glue ETL jobs yang dijadwalkan bulanan memberikan solusi paling otomatis dan repeatable: scheduled triggers memastikan jobs berjalan tanpa intervensi manual, jobs dapat memproses multiple log sources (CloudTrail + VPC Flow Logs + S3 access logs), menghasilkan summary tables yang terstruktur di Data Catalog, dan QuickSight dashboards otomatis refresh dari summary tables.
  • S3 Glacier Instant Retrieval optimal untuk data yang diakses jarang (sekali per kuartal) tapi memerlukan millisecond retrieval ketika diakses — cocok untuk 30-365 hari di mana akses jarang tapi harus segera available. Deep Archive (365+ hari) memberikan biaya terendah ($0.00099/GB/month) untuk data yang hampir tidak pernah diakses kecuali legal hold (retrieval dalam 12 jam masih acceptable).
  • Konversi ke Parquet memberikan improvement terbesar untuk Athena: columnar format memungkinkan Athena hanya membaca kolom yang diperlukan (mengurangi data scanned signifikan), Snappy compression mengurangi ukuran file lebih lanjut, dan buffer 128 MB menghasilkan file berukuran optimal untuk Athena (ideal 128 MB-512 MB). Kombinasi Parquet + larger files bisa mengurangi query cost dan waktu hingga 90%.
  • Apache Flink (via Managed Service) adalah satu-satunya opsi yang mendukung windowed joins — kemampuan untuk menggabungkan events dari multiple streams dalam time window tertentu (5 menit). Flink memproses events secara stateful, menyimpan state per IP address, dan mendeteksi ketika GuardDuty finding dan unusual VPC traffic dari IP yang sama terjadi dalam window 5 menit. Ini memberikan true real-time correlation.

Miskonsepsi & Jebakan Umum

  • Menambahkan hop melalui CloudWatch Logs yang menambah biaya ingestion dan latency — tidak perlu untuk route ke S3.
  • Memiliki concurrency limits dan timeout yang membuatnya tidak ideal untuk 5 TB/day.
  • Memiliki gap 1 jam dan Glue tidak ideal untuk continuous ingestion.
  • Tidak mendukung complex business rules, custom UDFs terbatas, dan memiliki query timeout limits.
  • Memiliki auto-scaling tapi less control over cluster configuration dan bisa kurang predictable untuk strict 4-hour SLA pada 10 TB.
  • Tidak bisa melakukan joins cross-file dan memiliki 15-minute timeout per invocation.
  • Berfungsi tapi custom schema tanpa standard bisa menjadi maintenance burden.
  • Tidak mentransformasi data fisik dan views bisa menjadi complex dan lambat.
  • Mendeteksi schema tapi tidak menormalkan — setiap sumber tetap memiliki schema berbeda.
  • Menggandakan storage dan memerlukan custom access management.
  • Maximizes cross-region transfer costs.
  • Sangat mahal untuk 200 accounts dan memerlukan cluster management yang signifikan.
  • Hanya detect berdasarkan pattern count, bukan enrichment-based threat detection, dan alarm evaluation adds latency.
  • Memiliki buffering delay Firehose (minimum 60 seconds) yang melebihi requirement 30 detik.
  • Memiliki micro-batch latency lebih tinggi dari Flink dan EMR cluster startup time menjadi masalah.
  • Charges $5/TB scanned = $10,000 untuk 2 PB, tanpa Spot pricing benefit, dan memiliki concurrent query limits.
  • Memiliki per-DPU-hour pricing yang biasanya lebih mahal dari EMR Spot untuk workloads berskala besar.
  • Memerlukan loading 2 PB yang sendiri memakan waktu signifikan dan sangat mahal untuk one-time use.
  • Hanya menampilkan metrics, bukan detailed log analysis yang diperlukan untuk unique principals dan IP range checking.
  • Memiliki batas query scope dan tidak bisa join antar log sources yang berbeda.
  • Tidak otomatis — memerlukan human intervention setiap bulan.
  • Menambah monitoring fee per object yang signifikan untuk 500 GB/day × 7 years = jutaan objects.
  • Tidak memiliki multi-AZ durability yang kurang tepat untuk compliance logs.
  • Lebih mahal dari Glacier Instant Retrieval untuk akses yang sangat jarang.
  • Mengurangi storage tapi Athena masih harus decompress dan scan seluruh file karena row-format.
  • Membantu filter tapi tanpa columnar format, improvement terbatas.
  • Masih JSON row-format yang memaksa full file scan.
  • Hanya melakukan single-event pattern matching — tidak mendukung temporal correlation antar events berbeda.
  • Memiliki latency 5+ menit dan bukan streaming.
  • Melakukan top-N analysis, bukan multi-source temporal correlation.
