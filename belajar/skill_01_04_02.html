Key Services & Concepts

AWS Lambda
Komputasi serverless event-driven; limit timeout 15 minutes and memory up to 10 GB.

Key Points

  • Lambda CPU allocation is proportional to memory. At 512 MB, Lambda gets ~1/3 vCPU. At 1769 MB, it gets 1 full vCPU. Increasing memory reduces duration (more CPU + more memory headroom) and reduces memory pressure (95% → ~50%). This often makes functions faster AND cheaper because shorter duration offsets per-ms cost increase.
  • Concurrency = (messages per second) × (processing time per message). 50,000/60 = 833 messages/second. If each takes 0.2s, needed concurrency = 833 × 0.2 = ~167. With batch size = 10 and batch processing: 833/10 = 83 invocations/second × 0.2s = ~17 concurrent (even less). The formula depends on whether processing is per-message or per-batch. For single message processing: ~167.
  • Two complementary strategies: (1) Reserved concurrency limits Lambda to 80 concurrent executions, ensuring max 80 connections. (2) RDS Proxy pools and multiplexes connections — even if 80 Lambdas run, Proxy manages connection reuse efficiently. Together they prevent connection exhaustion.
  • With ParallelizationFactor=1, each shard has exactly 1 concurrent Lambda invocation. Since each takes 10 seconds, each shard processes 1 batch every 10 seconds = 0.1 batches/sec/shard. With 10 shards processing concurrently: 10 × 0.1 = 1 batch/second total. To increase throughput: (1) increase ParallelizationFactor (up to 10), or (2) reduce processing time, or (3) add shards.
  • Provisioned Concurrency guarantees pre-initialized execution environments. Model is loaded during provisioning (not at invocation time). Every invocation hits a warm environment with zero cold start. Cost: you pay for provisioned environment 24/7 regardless of usage.
  • Lambda supports configurable ephemeral storage from 512 MB to 10,240 MB (10 GB). For a 5 GB file, allocating 10 GB /tmp provides sufficient space. Download from S3 to /tmp, process, upload result to S3. Ensure memory is sufficient for processing (up to 10 GB).
  • Reserved concurrency serves two purposes: (1) For Function A — guarantees 200 execution slots always available, even if other functions consume the remaining 800. (2) For batch functions — caps each at 200, preventing any single function from consuming all account concurrency. Total: 200 (A) + 200×4 (B-E) = 1000 = full account allocation, properly divided.
  • Lambda execution model: code outside the handler (module/global scope) executes once during cold start (INIT phase). The execution environment persists between invocations. Connection pools and config loaded at INIT are reused in subsequent warm invocations — 2-second initialization only happens once per environment lifecycle.
  • Without ReportBatchItemFailures, any exception from the Lambda handler causes the ENTIRE batch to return to the queue — 9 successful messages are reprocessed unnecessarily. With FunctionResponseTypes: ["ReportBatchItemFailures"], the function returns a response specifying which messageIds failed. Only those messages return to the queue. Processed messages are deleted. This prevents duplicate processing.
  • Since 2019, Lambda VPC networking uses Hyperplane ENIs with negligible cold start impact (~1 second vs. previous 10+ seconds). If cold starts are still 8-10 seconds, the cause is likely large deployment packages, heavy initialization code, or both. However, for irregular invocations (10-30 min gaps) where cold starts ARE the problem, Provisioned Concurrency is the definitive solution — it eliminates cold starts entirely.

Common Misconceptions & Pitfalls

  • Eliminates cold starts but doesn't fix resource constraints.
  • Has longer cold starts and unclear performance benefit.
  • Over-provisioned but the math shows ~167 is minimum.
  • Makes problem worse — connections held longer.
  • May impact RDS performance and memory.
  • Lambda still needs VPC to reach RDS in private subnet.
  • Would be correct if each batch took 1 second.
  • /D incorrect — Kinesis-Lambda doesn't auto-scale beyond configured parallelism per shard.
  • Makes EVERY invocation load the model — worse than cold start.
  • Unreliable — Lambda may still recycle, and doesn't guarantee preventing cold starts.
  • Speeds up cold start but doesn't eliminate it.
  • Max 250 MB unzipped — can't include 5 GB file.
  • Works but adds VPC requirement and latency — /tmp is simpler for this use case.
  • Doesn't prevent batch from starving real-time.
  • Prevents cold starts but doesn't guarantee concurrent execution slots.
  • Pays 2-second init EVERY invocation — terrible performance.
  • Still need to be read; connection pool still needed.
  • Messages aren't discarded by default.
  • Batch splitting is for Kinesis (BisectBatchOnError), not SQS.
  • Correctly identifies that VPC shouldn't cause 8-10s delay, but doesn't solve the cold start problem for the user.
  • Helps but doesn't eliminate cold starts.
