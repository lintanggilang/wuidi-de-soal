Skill 1.3.1: Orchestration services for ETL

StepFunctionsMWAAAirflowGlueworkflows

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.3: Orchestrate data pipelines), dengan fokus pada orchestration services for etl. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS Glue
ETL serverless berbasis Spark + Data Catalog; ideal untuk transformasi dan katalogisasi data.
Amazon MWAA
Managed Workflows for Apache Airflow; orkestrasi pipeline berbasis DAG.
AWS Step Functions
Orkestrasi alur kerja serverless (state machine) dengan retry, paralel, dan error handling.

Poin-Poin Kunci

  • Step Functions mendukung semua requirements: complex workflows (up to 25,000 events), Choice states for conditional branching, Parallel states for concurrent execution, built-in retry with exponential backoff, dan ASL definition yang bisa di-define di CloudFormation/CDK.
  • Parallel state runs all branches concurrently dan waits for ALL branches to complete before proceeding (fan-out/fan-in). Each branch handles one database (extract → transform). After Parallel completes, the next states (join → load) execute knowing all data is ready. This is exactly the fan-in pattern needed.
  • Deferrable operators (introduced in Airflow 2.2+) release the worker slot while waiting for external jobs. The task is deferred to a triggerer that uses asyncio — no worker blocked. When Glue job completes, triggerer resumes the task. This is essential for long-running external jobs to avoid worker starvation.
  • Glue Workflow adalah solusi paling sederhana untuk orchestrating Glue-native resources (crawlers + ETL jobs). Zero additional infrastructure — fully integrated dalam Glue console. Scheduled trigger → crawler → conditional trigger (on success) → ETL job. Minimal operational overhead.
  • Map state (Distributed mode) iterates over an array (file list) dan executes the same steps for each item. Distributed Map supports up to 10,000 concurrent executions and can process millions of items. MaxConcurrency controls parallelism. Perfect for processing independent items with same logic.
  • ExternalTaskSensor waits (polls/defers) until a task in another DAG reaches a successful state for the same execution_date. TriggerDagRunOperator explicitly triggers another DAG, creating a clear dependency chain. Both are Airflow-native patterns for inter-DAG dependencies.
  • Step Functions .sync integration pattern (Run a Job) memanggil service API dan secara otomatis menunggu job completion sebelum transition ke state berikutnya. Untuk Glue, ini berarti StartJobRun.sync akan wait sampai Glue job finishes (success/failure). Tidak perlu custom polling logic.
  • Wrapping states in a Parallel state (single branch) creates a "try-catch" block equivalent. Any failure in any enclosed state bubbles up to the Parallel's Catch block. The shared error state handles notification and logging once, eliminating duplication. Alternative: use EventBridge integration to capture state machine failure events.
  • EcsRunTaskOperator is the recommended replacement for KubernetesPodOperator in MWAA. It runs containers as ECS tasks (Fargate = serverless). Container images stay the same, just the orchestration layer changes. ECS Fargate requires no cluster management.
  • Standard Workflows support long-running executions (up to 1 year). The .sync pattern waits for Glue completion. Wait state with Seconds or Timestamp combined with Choice state can implement "send alert after 1 hour if not done, continue waiting." Standard supports exactly-once execution semantics.

Miskonsepsi & Jebakan Umum

  • Batas 15 menit dan anti-pattern untuk complex workflows.
  • Tidak memiliki native branching atau parallel state management.
  • Lebih limited dalam conditional logic dan hanya untuk Glue jobs/crawlers.
  • Membutuhkan external coordination for fan-in.
  • Valid alternative tapi Parallel lebih explicit untuk fixed known branches.
  • Blocks a worker for 45 minutes.
  • Same blocking issue and wastes resources.
  • Requires custom code for polling crawler status.
  • Requires managing Airflow environment — overkill untuk 3 steps.
  • Valid tapi requires defining ASL and Lambda functions.
  • Parallel state has limit of ~50 branches and is for fixed, different branches.
  • Sequential processing, very slow.
  • For conditional routing, not iteration.
  • Race-condition prone and not reliable for dependency management.
  • Fragile — if DAG A runs longer than estimated, DAG B starts with incomplete data.
  • Creates unmaintainable mega-DAGs.
  • Returns immediately without waiting — workflow proceeds before job finishes.
  • Reinvents what .sync does natively.
  • Hardcoded wait tidak account for variable run times.
  • Don't have automatic error handling — they have different execution model.
  • Loses context about which step failed.
  • Adds operational complexity — valid but more overhead than ECS.
  • MWAA workers don't have Docker daemon access.
  • Requires significant code refactoring and loses container isolation benefits.
  • Has 5-minute maximum duration — far too short for 3-hour workflow.
  • Cannot exceed 5 minutes regardless of configuration.
