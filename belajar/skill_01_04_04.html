Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.4: Apply programming concepts), dengan fokus pada software engineering best practices. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS CodePipeline
Orkestrasi CI/CD untuk membangun, menguji, dan men-deploy secara otomatis.

Poin-Poin Kunci

  • Trunk-based development with short-lived feature branches minimizes merge conflicts because branches diverge briefly. Pull request reviews catch errors before production. Automated CI running unit tests on PRs ensures broken code never reaches main. This balances velocity with safety.
  • Local SparkSession with pytest allows testing transformation logic in isolation — no AWS resources needed, fast feedback loop (seconds vs minutes). Pattern: create DataFrame with known input → apply transform function → assert output matches expected DataFrame. This tests business logic independently of infrastructure.
  • Integration tests validate the interaction between components (RDS → Glue → Redshift) which unit tests cannot cover. Issues like connection timeouts, schema drift in source, Redshift COPY command failures, and data type mismatches only surface during end-to-end execution. A dedicated test environment with seed data provides repeatable, automated validation.
  • Structured logging (JSON) enables CloudWatch Logs Insights queries for fast troubleshooting. Correlation IDs link related log entries across distributed workers. Checkpoint logging (records_read=1M, records_filtered=50K, records_written=950K) quickly identifies where data loss occurs. Dead-letter capture preserves failed records for investigation. Log levels allow filtering noise.
  • Custom CloudWatch metrics provide quantitative pipeline health data. Alarms trigger proactively BEFORE SLA breaches (e.g., alarm if processing_duration exceeds 80% of SLA window). SNS notifications ensure immediate human response. Dashboards give at-a-glance health across all 25 pipelines. This covers failures (error_count), performance degradation (duration trending up), and data completeness (records_processed below expected).
  • All four concerns impact long-term reliability: Hardcoded paths break when environments change (dev→prod). No input validation causes cryptic failures on bad data. Duplicated logic means bugs must be fixed in multiple places. Unformatted SQL is error-prone to modify. Externalizing config enables environment promotion. Input validation provides clear failure messages. DRY functions reduce bug surface area. Separated SQL files enable syntax checking.
  • Tiered error handling distinguishes between error types: Transient errors (network, throttling) are retryable — exponential backoff prevents thundering herd. Malformed records shouldn't stop the pipeline — dead-letter queue preserves them without blocking good records. Checkpointing prevents reprocessing already-completed work after recovery. Non-retryable errors (disk full) need immediate human intervention. This pattern maximizes data throughput while maintaining data integrity.
  • CodePipeline provides automated, repeatable deployments. Environment-specific parameter files separate configuration from code — same CloudFormation template deploys to dev/staging/prod with different parameters. CodeBuild runs tests before deployment (fail-fast). Pipeline stages can include manual approval gates before production. This eliminates human error and ensures consistency across environments.
  • Secrets Manager handles sensitive credentials with automatic rotation capability and audit logging. Parameter Store with hierarchical paths (/app/{env}/glue/{param}) organizes non-sensitive config by environment and service. Runtime retrieval based on environment parameter ensures jobs automatically get correct config without code changes. IAM policies control which environment's secrets each role can access.
  • A runbook is the most operationally valuable documentation for pipeline maintenance. Architecture diagrams show dependencies and data flow. SLA requirements define when issues are urgent. Common failure scenarios with remediation steps enable quick resolution without deep code knowledge. Escalation procedures prevent single points of failure. Data dictionaries help understand what each component does.

Miskonsepsi & Jebakan Umum

  • Separate repos make collaboration impossible and code synchronization a nightmare.
  • Direct commits with no reviews leads to broken production pipelines.
  • Long-lived branches accumulate massive merge conflicts and integration issues (the exact problem they're facing).
  • Development endpoints are expensive, slow, and don't provide automated regression testing.
  • Integration tests against production are slow, expensive, and not unit tests.
  • Testing after production is too late — bugs already affect downstream consumers.
  • Running the same tests repeatedly doesn't increase coverage.
  • More unit tests don't catch integration-level issues (connectivity, permissions, schema mismatches).
  • Manual checks are unreliable and not scalable.
  • Writing all records to debug bucket is expensive and doesn't identify the failure point.
  • Glue metrics show job-level info but not record-level failures.
  • Print statements are unstructured, unsearchable, and provide no context.
  • Manual checking is reactive and doesn't scale.
  • Job failure notifications don't catch SLA breaches or quality issues.
  • Learning from consumers means SLAs are already broken.
  • Working code with technical debt accumulates maintenance cost.
  • Partial fixes leave other risks.
  • Full rewrite is excessive when targeted improvements suffice.
  • Ignoring errors silently loses data.
  • Arbitrary sleeps don't prevent errors and add latency.
  • Retrying from beginning is wasteful and may hit the same non-transient error.
  • Testing in production risks data corruption and outages.
  • Manual deployment is the problem being solved; error-prone and unauditable.
  • Environment logic in code is fragile and makes testing difficult.
  • Credentials in Git repos are a critical security vulnerability and are hard to rotate.
  • Spreadsheets have no access control, versioning, or audit trail.
  • Hardcoded env vars require job updates for config changes and don't support rotation.
  • Line-by-line comments are excessive, become stale, and don't help with operational issues.
  • A single README lacks the operational detail needed for incident response.
  • Video walkthroughs become outdated as UI changes and are not searchable during incidents.
