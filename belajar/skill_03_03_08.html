Key Points

  • Athena is ideal for one-time, ad-hoc analysis of S3-stored logs. It's serverless (no infrastructure to provision), charges only per data scanned ($5/TB), and with Parquet format + partition pruning, the actual data scanned will be far less than 2 TB. For a one-time investigation, this is the most cost-effective approach. Option B: OpenSearch requires provisioning and maintaining a cluster, with significant cost for a one-time analysis; ingesting 2 TB would take hours and the cluster would be idle afterward. Option C: EMR would work but requires cluster provisioning, configuration, and management; Athena provides the same capability without operational overhead. Option D: Re-ingesting S3 logs into CloudWatch Logs would incur $0.50/GB ingestion costs ($1,000 for 2 TB) and is impractical for historical data.
  • This tiered architecture optimizes for both requirements: OpenSearch provides sub-second search and interactive dashboards for the hot 7-day window, while S3 + Athena provides cost-effective long-term retention for occasional compliance queries. Index lifecycle management automates the transition. Option B: CloudWatch Logs Insights at 500 GB/day would cost $250/day in ingestion alone ($91,000/year) and doesn't provide sub-second search latency for complex fraud pattern queries. Option C: Redshift is optimized for structured analytical queries, not full-text log search; loading 500 GB daily would require a very large (expensive) cluster. Option D: Storing 365 days in OpenSearch (even with UltraWarm) for 500 GB/day would be extremely expensive (~180 TB total storage).
  • CloudTrail Lake provides a managed, serverless query capability specifically designed for CloudTrail events. It requires no table creation, no SerDe configuration, and no partition management. You can immediately query events using SQL syntax optimized for CloudTrail's schema. This provides the fastest time-to-insight with zero setup for CloudTrail-specific analysis. Option A: Athena with CloudTrail SerDe works well but requires table creation, partition management setup, and understanding the nested JSON schema structure. Option C: EMR requires cluster provisioning and Spark programming knowledge—significantly more setup time. Option D: OpenSearch requires data ingestion (time-consuming for 30 days of logs) and cluster management for a one-time query.
  • The CloudWatch agent supports multi_line_start_pattern configuration, which uses a regex pattern (matching the timestamp format) to identify the beginning of a new log event. All subsequent lines until the next match are grouped into a single CloudWatch log event. This solves the problem at ingestion time, making all downstream queries work correctly. Option A: Logs Insights' parse command works on individual log events; it cannot join separate events back together after they've been ingested as separate entries. Option B: While structured JSON logging is a best practice, it requires application code changes which may not be feasible for all components. Option D: This adds cost and complexity with Lambda processing and duplicate log storage.
  • ALB access logs use a space-delimited format (not JSON or CSV) with quoted fields that can contain spaces. The Regex SerDe is the correct approach for parsing this format in Athena, using a regular expression that handles the mixed quoting. The query correctly calculates error rates using conditional aggregation on HTTP 5xx status codes. Option B: ALB logs are NOT in JSON format; they use a custom space-delimited format with quoted fields. Option C: OPENCSV with comma delimiter doesn't match ALB's space-delimited format with quoted strings containing spaces. Option D: SPLIT on raw text is unreliable for ALB logs because some fields (like the request URL) contain spaces within quotes.
  • Amazon EMR with Spark is optimal for large-scale (50 TB), complex log processing requiring custom parsing logic across multiple formats, UDF-based enrichment (geolocation lookups), and timezone normalization. Spark provides full programmatic control, efficient distributed processing, and native Parquet writing with partitioning. Option B: Athena CTAS is limited to 100 partitions per query and has a 30-minute query timeout; processing 50 TB with complex transformations would require many fragmented queries. Option C: CloudWatch Logs Insights cannot read S3-stored logs directly and doesn't output Parquet; it's designed for CloudWatch log groups only. Option D: A single Glue job for 10+ formats and 50 TB would be difficult to manage, debug, and would likely exceed Glue's timeout limits; EMR offers more control at this scale.
  • High JVM memory pressure in OpenSearch is primarily caused by too many shards (each shard consumes heap memory for metadata). With daily indices over 6 months, the cluster has ~180 indices with potentially thousands of shards. ISM policies automate lifecycle management: moving old indices to UltraWarm (which doesn't consume data node JVM heap) and deleting very old data. Right-sizing shards reduces the total count. Option B: Adding nodes distributes shards but doesn't reduce the total shard count that causes JVM pressure; it's also more expensive. Option C: EBS size doesn't affect JVM memory pressure—the issue is shard metadata in heap, not disk space. Option D: Weekly indices reduce index count by 7x but don't address the fundamental lifecycle management problem; after enough weeks, the same issue recurs.
  • CloudWatch Logs Insights supports querying up to 50 log groups simultaneously in a single query. When multiple log groups are selected, the query runs across all of them and results include the @logStream field to identify which service produced each event. This native capability makes cross-service correlation straightforward. Option B: Manual correlation across separate queries is time-consuming, error-prone, and doesn't scale. Option C: Consolidating logs via subscription filters adds cost, latency, and creates duplicate storage; it's unnecessary since Logs Insights can query multiple groups directly. Option D: CloudWatch ServiceLens is designed for X-Ray trace correlation, not arbitrary log field correlation; it requires X-Ray instrumentation in all services.
  • OpenSearch is purpose-built for full-text search with sub-second latency, supporting free-text queries across all fields via inverted indices, faceted filtering, and interactive dashboards. For a 100 GB hot dataset requiring interactive search, OpenSearch provides the best user experience with features like auto-complete, highlighting, and aggregation facets. Option B: Athena's LIKE operator requires full table scans and cannot achieve under-5-second latency on 100 GB for arbitrary text searches; it's not designed for interactive full-text search. Option C: Importing 100 GB daily into CloudWatch Logs costs $50/day in ingestion and Logs Insights queries on 100 GB would not consistently meet 5-second latency for complex free-text searches. Option D: Redshift Spectrum doesn't support full-text search with inverted indices; it would need to scan all JSON data for text matching.
  • CloudWatch Logs charges $0.50/GB for ingestion—the primary cost driver. At 200 GB/day, that's $100/day ($3,000/month) just for ingestion, before any query or storage costs. This makes it significantly more expensive than Athena (which queries S3 data at $5/TB scanned, with S3 storage at ~$0.023/GB) or OpenSearch (which has infrastructure costs but no per-GB ingestion fee of that magnitude). Option B: Athena's cost depends heavily on data format and query patterns; scanning 200 GB × 50 queries/day in unoptimized format can be expensive, but it's still typically cheaper than CloudWatch ingestion. The statement "always cheapest" is an oversimplification. Option C: UltraWarm storage is approximately $0.024/GB-month, comparable to S3, but OpenSearch requires hot node infrastructure costs. Option D: AWS services have very different pricing models.
