Skill 1.2.3: Integrate data from multiple sources

integratemultiplesources

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.2: Transform and process data), dengan fokus pada integrate data from multiple sources. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Lihat poin-poin kunci di bawah.

Poin-Poin Kunci

  • AWS Glue ETL job bisa membaca dari multiple heterogeneous sources (JDBC untuk RDS, DynamoDB connector, S3 untuk files) dalam satu job. DynamicFrames/DataFrames memungkinkan joins dan transformasi sebelum menulis hasil akhir ke Redshift. Ini paling efisien karena satu job menangani semua.
  • Glue Streaming ETL mendukung stream-to-batch joins. Streaming source (Kinesis) di-join dengan static/slowly changing data dari S3 menggunakan broadcast join atau lookup. Glue menangani micro-batching dan writes ke data lake secara otomatis.
  • Glue crawlers mendeteksi schema berbagai database. Data Catalog menjadi metadata registry pusat. Glue ETL jobs dengan schema mapping (ApplyMapping transform) menstandarkan heterogeneous schemas ke format canonical yang konsisten. Ini paling maintainable karena schema changes terdeteksi otomatis.
  • Setiap source membutuhkan connector yang berbeda: AppFlow memiliki native Salesforce connector, Lambda bisa consume REST APIs, dan Glue JDBC menghubungkan ke data warehouse on-premises. Landing data ke S3 sebagai common layer, kemudian satu consolidation job mengintegrasikan semuanya.
  • Lake Formation cross-account sharing memungkinkan sharing Data Catalog tables dan underlying S3 data tanpa copying. Central account bisa query semua data melalui Athena dengan unified view. Lake Formation mengelola fine-grained permissions.
  • Broadcast join sangat efisien ketika satu tabel kecil (fits in memory per worker). Dimension table 10,000 rows di-broadcast ke semua executors, sehingga join dilakukan locally tanpa expensive data shuffling. Ini menghindari shuffle dari 2 billion row fact table.
  • Medallion architecture memisahkan ingestion (bronze) dari integration (silver). Setiap source di-ingest pada jadwalnya masing-masing. Integration job membaca "latest available" partition dari setiap source, sehingga view selalu ter-update meskipun data arrives asynchronously.
  • Standardisasi data sebelum join adalah best practice. Menggunakan lower() function pada kolom email di kedua sources sebelum join memastikan matching yang akurat. Ini simpel, efisien, dan deterministic.
  • Redshift menyediakan unified SQL interface: Streaming Ingestion untuk real-time data dari Kinesis, internal tables untuk historical data, dan Redshift Spectrum external tables untuk S3 files. Semua bisa di-join dalam single SQL query.
  • Apache Iceberg (dan Delta Lake, Hudi) mendukung MERGE INTO (upsert) yang menangani insert, update, dan delete dalam satu operasi atomic. Iceberg melakukan row-level operations pada Parquet files tanpa rewriting entire partitions. Ini paling efisien untuk CDC (Change Data Capture) integration.

Miskonsepsi & Jebakan Umum

  • Sulit untuk large datasets dan complex joins.
  • AppFlow tidak mendukung DynamoDB dan RDS sebagai sources.
  • Membuang Redshift resources untuk raw data staging.
  • Valid tapi lebih complex untuk setup.
  • Memiliki payload limits dan timeout constraints.
  • Sangat inefficient — S3 read per record adalah N+1 problem.
  • AppFlow tidak support RDBMS/MongoDB directly.
  • Memindahkan masalah schema heterogeneity.
  • Sulit di-maintain untuk 5 sources.
  • DMS tidak support Salesforce dan REST APIs.
  • Glue tidak bisa native connect ke Salesforce atau REST APIs dalam satu job.
  • Kinesis untuk streaming bukan batch integration.
  • Tidak scalable dan security concern.
  • Mahal karena menduplikasi semua data.
  • Hanya untuk billing, tidak memberikan data access.
  • Membutuhkan shuffle besar untuk fact table yang sangat mahal.
  • Menambah service dan biaya loading 2B rows.
  • Adalah N+1 problem — 2 billion DynamoDB calls.
  • Menyebabkan excessive runs saat hourly logs tiba.
  • Memblokir processing dan wastes compute waiting.
  • Overkill untuk masalah casing sederhana dan memakan resources.
  • Glue/Spark joins case-sensitive secara default tanpa auto case-insensitive mode.
  • Menambah complexity yang tidak diperlukan.
  • Bukan untuk complex analytical queries.
  • Tidak scalable dan tidak support real-time streaming ingestion.
  • Tidak bisa query Redshift internal tables tanpa federated connector tambahan.
  • Membuang resources untuk seluruh dataset.
  • Menambah query complexity dan storage costs.
  • Tracking saja, tidak menangani merging logic.
