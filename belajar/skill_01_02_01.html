Skill 1.2.1: Optimize container usage (EKS, ECS)

Summary

Skill this including in Domain 1: Ingestion & Transformation (Task 1.2: Transform and process data), with fokus on optimize container usage (eks, ecs). Materi berikut merangkum service AWS that relevan beserta concept important that needs kamu kuasai for topik this.

Key Services & Concepts

Amazon ECS
Orkestrasi container managed; can runs in EC2 or Fargate.
Amazon EKS
Kubernetes managed for runs workload container.
AWS Fargate
Compute serverless for container without manages server.

Key Points

  • VPA menganalisis historical resource usage and automatically adjusts memory requests/limits for pods. In "Auto" mode, VPA will evict pods and restart mereka with right-sized resources. This is ideal for workloads with variable memory patterns.
  • Fargate Spot menawarkan diskon up to 70% dibanding On-Demand for workloads that toleran against interruption. Batch ETL tasks that has retry logic can memanfaatkan this. Tasks that time-critical still gunakan On-Demand.
  • Pod affinity rules ensures pods in-schedule on node that same or dekat in a fisik (same AZ, placement group). Ini reduces network latency for inter-pod communication that heavy (such as Flink data shuffling).
  • ECS capacity providers with managed scaling enables cluster auto-scale GPU instances based on pending tasks. By scale-to-zero, GPU instances only runs saat ada tasks that requires GPU (2-3 hours/days), menghemat cost significant.
  • EBS volumes sebagai PersistentVolumes provides storage that can is configured appropriate requirements (size, IOPS). For file 10GB that needs processing local, EBS provides performa I/O that baik.
  • For workloads 24/7 that continuous, EC2 with Savings Plans or Reserved Instances provides diskon significant (up to 72%) dibanding On-Demand. By known fixed resource requirements, EC2 cheaper from Fargate on sustained usage.
  • Karpenter provisions nodes in hitungan seconds (vs minutes for Cluster Autoscaler) and automatically memilih instance types optimal based on pending pod requirements. Karpenter also support mixed instance types and consolidation.
  • KCL distributes shard leases among workers. By 10 shards, 10 tasks (workers) ensures each task processes correct 1 shard — beban terdistribusi merata. If satu task fails, KCL will redistribusi shard to remaining workers.
  • Multi-stage build reduces image size with separates build stage (compile dependencies) from runtime stage (only binary/packages that is required). python:3.11-slim jauh smaller from full image. Deletes pip cache and unnecessary files reduces size more lanjut. Smaller image = faster pull = faster task startup.
  • Private subnets without NAT Gateway ensures there is no internet access. VPC endpoints (Gateway endpoint for S3/DynamoDB) enables access to AWS services without internet. EKS private endpoint enables kubelet/pods communicates with control plane in a private.

Common Misconceptions & Pitfalls

  • Adds pods but each pod still can OOM.
  • Not secure and can menyebabkan node-level OOM.
  • Mencegah bursting but memaksa over-provisioning.
  • Adds operational overhead and not suitable for variable workloads.
  • Membuang resources and cost.
  • Very slow and not memanfaatkan parallelism.
  • Justru menyebarkan pods more jauh, increases latency.
  • Adds overhead networking layer that increases latency.
  • Fargate not supports GPU instances.
  • Membuang cost 21-22 hours per days.
  • Also membuang cost if nodes always on.
  • Not always feasible for transformation that requires random access to entire file.
  • Has latency higher from EBS and expensive for temporary processing storage.
  • Over-provisioning compute for problem storage.
  • Can terinterrupsi — not suitable for continuous processing.
  • Still more expensive from EC2 RI for 24/7.
  • Scale pods not nodes — pods still pending if node resources habis.
  • More slow because must scale node groups that already didefinisikan.
  • Single point of failure, if task dies all processing stops.
  • 10 tasks will idle because only ada 10 shards, membuang resources.
  • Not tahu about shard count.
  • Adds complexity without benefit significant.
  • Memperlambat each task start.
  • Mempengaruhi entire VPC including resources that butuh internet.
  • Bergantung on CNI plugin and can in-bypass.
  • Memblokir all including VPC endpoints.
