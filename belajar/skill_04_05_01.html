Skill 4.5.1: Permissions for data sharing

Redshiftdatasharing

Summary

Skill this including in Domain 4: Security & Governance (Task 4.5: Understand data privacy and governance), with fokus on permissions for data sharing. Materi berikut merangkum service AWS that relevan along with concept important that needs kamu kuasai for topik this.

Key Services & Concepts

Amazon Redshift
Data warehouse scale petabyte; supports COPY/UNLOAD, materialized view, and streaming ingestion.
Redshift Streaming Ingestion
Konsumsi directly from Kinesis/MSK to materialized view Redshift, latensi seconds, without staging S3.

Key Points

  • Creates datashares separate per region with views that already difilter (WHERE region = 'NA') provides granular access control in level producer. Consumer only can melihat data that there is in datashare mereka — there is no way for bypass filter because view definition there is in producer cluster. Each datashare in-authorize only to one consumer account.
  • For cross-account data sharing, step-langkahnya is: (1) Producer creates datashare and adds objects (schemas, tables, views), (2) Producer performs AUTHORIZE for provides access to consumer AWS account, (3) Di consumer side, admin performs ASSOCIATE datashare with consumer cluster namespace, (4) Consumer creates database from datashare, (5) Consumer grants access to users/groups.
  • Lake Formation supports cross-account grants with column-level permissions. Administrator can GRANT SELECT on column certain (excluding PII columns) to external AWS account. AWS RAM (Resource Access Manager) is used for shares Lake Formation resources (databases, tables) cross-account. Setelah in-share, account penerima can melihat and query only column that in-grant.
  • S3 Access Points provides way most scalable for manages multi-tenant access. Each access point has DNS name itself and policy that independent, limits access to prefix certain (for example s3://bucket/tenant-123/*). Applications is provided access to access point specific through IAM. This avoids bucket policy that makin kompleks (limit 20 KB).
  • When schema is added to datashare, ALL object in schema said (tables, views, UDFs) becomes accessible by consumer. For limits to object certain, step that correct is: (1) ALTER DATASHARE REMOVE SCHEMA for deletes schema-level sharing, (2) ALTER DATASHARE ADD SCHEMA (only for namespace reference), (3) ALTER DATASHARE ADD TABLE for each table specific and ADD VIEW for views specific.
  • Redshift provides system views khusus for monitoring data sharing: SVV_DATASHARE_CONSUMERS menampilkan informasi consumer that authorized, and system views such as SVL_DATASHARE_USAGE_PRODUCER (as well as table SVL and SYS related) provides detail about query activity from consumers including table that diakses, volume data, and frekuensi. Producer has visibility full without requires kerjasama from consumer.
  • For cross-account datashares, uses ALTER DATASHARE datashare_name SET ACCOUNT 'consumer_account' REMOVE (or syntax REVOKE authorization) segera mencabut access consumer account. Query that sedang runs will fails and there is no query new that can is run. This is way tercepat without affects consumer other that may uses datashare that same.
  • Redshift Serverless can bertindak as consumer for datashares without requires provisioned cluster that runs terus-menerus. Consumer team can creates Redshift Serverless endpoint, create database from datashare, and data always mencerminkan state terbaru from producer (live, not copy). Although consuming team primarily uses Athena, Serverless endpoint can is used when they need the shared data.
  • Lake Formation Tag-Based Access Control (LF-TBAC) is solution most efficient and scalable. By menandai column PII with tag (classification=pii) and column non-PII with (classification=non-pii), administrator quite creates one grant: external account mendapat SELECT on resource that tagged classification=non-pii. This automatically excludes all column PII in all 50 table without needing per-table configuration.
  • This is question that menguji pemahaman architecture Redshift data sharing. In Redshift data sharing, consumer queries is run uses compute resources MILIK CONSUMER, not producer. Producer only shares access to data storage (on RA3 managed storage) — compute processing sepenuhnya on consumer cluster/serverless. By because that, consumer queries TIDAK affects producer performance. If producer mengalami degradation, penyebabnya not from data sharing consumers.

Common Misconceptions & Pitfalls

  • Creates copy data that adds storage cost and latency.
  • Provides access to all data first lalu depends on RLS in consumer — this less secure because consumer admin can memodifikasi RLS.
  • Not uses Redshift data sharing and requires data in S3.
  • Uses ALTER DATASHARE SET ACCOUNT that not syntax valid.
  • AWS RAM not is used for Redshift data sharing (RAM is used for Lake Formation).
  • Melewatkan step AUTHORIZE and ASSOCIATE that is required for cross-account (GRANT USAGE only for same-account/namespace).
  • Not supports column-level restrictions — policies applies in level table or database.
  • Not supports column-level permissions for Glue/Lake Formation in a native.
  • Works in file level, not column level — all column there is in file that same.
  • Digunakan for transforming data on retrieval, not access control — overkill and adds latency.
  • Not scalable — managing ratusan buckets adds overhead.
  • Can works but bucket policy has size limit and becomes difficult is managed with many tenants.
  • Datashares not supports column-level restrictions directly.
  • Requires data movement or view creation that adds maintenance.
  • Not works because datashare access not based on GRANT/REVOKE tradisional — if schema in-share, all objects accessible.
  • Mencatat API calls but not query-level detail such as table that diakses in datashare.
  • Provides aggregate metrics but less granular dibanding system views.
  • Requires kerjasama consumer and not practical.
  • Also affects all consumers.
  • Mempengaruhi ALL consumers, not only that compromised.
  • Syntax-nya not correct — REVOKE USAGE applies for same-cluster namespaces, and SET AUTHORIZATION not for denying account access.
  • Creates copy that stale and requires maintenance.
  • Athena cannot becomes target federated query from Redshift; federated query creates Redshift query external sources, not sebaliknya.
  • Adds complexity and better suited for public/commercial data sharing.
  • IAM in consumer account cannot limits column access for Lake Formation/Athena queries.
  • Berfungsi but requires 20 filter separate — less efficient.
  • Requires restructuring databases that adds maintenance.
  • Not needs because the problem not on data sharing.
  • Not applicable because consumer queries not enters to producer's WLM queues.
