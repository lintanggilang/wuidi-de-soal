Key Points

  • An AnalysisException for column resolution strongly indicates a schema drift issue — the upstream data no longer contains the expected column. This is the most common cause of sudden column-not-found errors in production pipelines: an upstream team deploys changes without coordinating with downstream consumers. Investigation should compare actual file schemas (using Glue crawler or manual inspection) with the expected schema. Option B: DPU exhaustion causes OutOfMemoryError or task failures, not schema resolution errors. Option C: Permission issues would cause AccessDenied errors, not column resolution errors. Option D: While possible, this would also affect the Glue crawler and would be evident in the catalog's modification history.
  • Bootstrap scripts that install packages from PyPI without pinned versions are vulnerable to upstream package releases that introduce breaking changes or incompatible dependency versions. Since it worked yesterday, a new package release is the most likely cause. Pinning versions (package==x.y.z) and hosting in a private repository eliminates external dependency risks. Option B: IAM permission changes would produce a different error about accessing the bootstrap script, not a non-zero return code from script execution. Option C: EMR AMIs don't auto-update on running clusters; you specify the release label at launch. Option D: Network issues would produce timeout errors in the bootstrap logs, not a non-zero return code from package installation specifically.
  • A Step Functions workflow provides robust orchestration: it can check the crawler state (GetCrawler API), wait if running, and retry with backoff. This ensures the new crawl starts only when the previous one completes, preventing the "already running" error while guaranteeing catalog updates. Option A: Running more frequently doesn't solve the overlap problem and may increase costs. Option C: Two crawlers on the same source would have the same overlap problem and could cause catalog update conflicts. Option D: While event-driven triggering is good practice, it doesn't address the concurrent run issue if data writes overlap with ongoing crawls.
  • Steadily growing memory usage in a streaming application is the hallmark of a memory leak or unbounded state accumulation. In Spark Streaming/Structured Streaming, stateful operations (aggregations, joins with watermarks) can accumulate state indefinitely if TTL or watermarks aren't properly configured. The solution is to implement state cleanup mechanisms. Option B: Simply increasing memory postpones the problem; if there's a leak, it will eventually exceed any allocation. Option C: Increasing YARN limits also postpones the issue without addressing the root cause. Option D: Disk space issues would manifest as "No space left on device" errors, not memory limit violations.
  • Glue job bookmarks can be reset using the ResetJobBookmark API or from the console. This clears the bookmark state, causing the next run to reprocess all data as if running for the first time. After the full reprocessing run completes, the bookmark is re-established at the new state and subsequent runs resume incremental processing. Option B: Disabling bookmarks permanently is excessive for a one-time reprocessing need and adds ongoing maintenance overhead. Option C: Renaming files is operationally risky and doesn't address the fundamental issue. Option D: Creating a duplicate job adds unnecessary complexity; bookmark reset solves this directly.
  • When executor failures are concentrated on specific nodes (rather than random), it strongly suggests node-level issues: disk space exhaustion (/mnt or /tmp full), unhealthy local disks (HDFS or YARN marks disks as bad), or hardware issues. YARN marks nodes as unhealthy when local disk usage exceeds thresholds. Investigating node health is the correct first step before tuning configurations. Option B: Increasing max attempts masks the root cause and delays the eventual failure. Option C: Corrupted JARs would cause class loading errors uniformly across all nodes, not node-specific failures. Option D: Adding capacity doesn't fix underlying node health issues.
  • "Connection reset by peer" after a specific duration (45 minutes) is a classic symptom of network timeout issues. NAT Gateways have a 350-second idle timeout, and if the JDBC connection has idle periods during large batch writes, the connection is silently dropped. Adding TCP keepalive parameters (tcpKeepAlive=true) in the JDBC URL prevents this. Option B: WLM statement timeouts would produce a Redshift-specific error message ("statement timeout"), not a TCP connection reset. Option C: Glue job role credentials are managed internally and refresh transparently; they don't cause connection resets. Option D: Disk space issues would produce a Redshift error about disk full, not a TCP connection reset.
  • Glue jobs support a MaxRetries parameter (0-10) that automatically retries the entire job upon failure. Within a Glue workflow, this is configured in the trigger settings. This is the simplest and most appropriate approach for transient failures because Glue handles the retry lifecycle, including waiting between attempts. Option B: While application-level retries are good for individual API calls, S3 throttling that fails the entire job suggests widespread throttling that requires job-level retry rather than call-level retry. Option C: S3 Event Notifications don't capture 503 error responses. Option D: EventBridge-based restart works but adds unnecessary complexity when Glue's built-in retry mechanism handles this natively.
  • A Hive metastore with 500,000 partitions experiencing growing query latency is a classic database maintenance issue. Stale partitions from deleted/archived data still occupy metastore space, and outdated statistics cause suboptimal query plans. Cleaning up unnecessary partitions, updating statistics, and potentially scaling the RDS instance directly addresses the root cause. Option B: Restarting the cluster refreshes caches temporarily but doesn't fix the underlying metastore database growth. Option C: Connection pool size isn't the issue; the individual queries themselves are slow due to table scan operations on large partition tables. Option D: Migrating to Aurora may help but doesn't address the data volume issue; the same partition bloat would eventually cause problems on Aurora too.
  • AWS Glue uses warm pools to speed up job startup. Workers in warm pools may have previously downloaded libraries cached locally. When the same S3 path is used for an updated library, some workers use the cached old version while others (cold-started) download the new one. The solution is to change the filename/path with versioning so all workers are forced to download the new file. Option B: S3 provides strong read-after-write consistency since December 2020; eventual consistency is no longer an issue for overwrites. Option C: While Glue version differences exist, import errors from a shared library update suggest a caching/version problem rather than Python version incompatibility. Option D: Permission issues would affect all runs of those jobs consistently, not intermittently.
