Skill 1.1.10: Fan-in and fan-out streaming

fan-infan-outstreamingSNSSQS

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.1: Perform data ingestion), dengan fokus pada fan-in and fan-out streaming. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Redshift Streaming Ingestion
Konsumsi langsung dari Kinesis/MSK ke materialized view Redshift, latensi detik, tanpa staging S3.
Amazon SNS
Pub/sub notifikasi untuk fan-out pesan ke banyak subscriber (SQS, Lambda, HTTP).
Amazon SQS
Antrian pesan terkelola; FIFO menjaga urutan namun dibatasi throughput per message group.
Enhanced Fan-Out
Konsumen Kinesis dengan throughput dedikasi 2 MB/s per shard via HTTP/2 push, latensi rendah.

Poin-Poin Kunci

  • Tanpa Enhanced Fan-Out, semua consumers berbagi 2 MB/s read throughput per shard menggunakan GetRecords API (polling). Dengan 3 consumers, masing-masing secara efektif mendapat ~666 KB/s. Selain itu, GetRecords dibatasi 5 calls/second per shard yang juga dibagi. Ini meningkatkan read latency.
  • SNS + SQS fan-out pattern adalah yang paling scalable. SNS dapat handle millions of messages/second dan delivers ke semua subscribers (SQS queues) secara independen. Setiap SQS queue buffers messages untuk consumer masing-masing, memberikan decoupling sempurna.
  • Kinesis dengan gateway ID sebagai partition key menjamin ordering per gateway (semua records dari gateway yang sama masuk ke shard yang sama). Dengan 50 MB/s, dibutuhkan minimal 50 shards (1 MB/s per shard). 500 gateways akan terdistribusi di antara 50 shards (~10 gateways per shard). Ini scalable dan real-time.
  • Amazon EventBridge Pipes mendukung source (Kinesis), filtering (content-based), optional enrichment, dan target (another Kinesis stream). Dengan multiple pipes dari source yang sama dengan different filters, records bisa di-route ke target streams berbeda. Ini serverless dan minimal code.
  • Amazon MSK (Kafka) consumer groups memungkinkan setiap group membaca semua messages dari topic secara independen. Kafka dirancang untuk high-throughput (100K+ events/sec) dengan multiple consumer groups tanpa performance degradation karena messages disimpan di log.
  • EventBridge Pipes dapat consume dari Kinesis source, apply transformation (including schema normalization via enrichment or input transformer), dan write ke target Kinesis stream. Three pipes (one per source) fan-in ke satu target stream. Ini serverless, no-code, dan maintainable.
  • Enhanced Fan-Out memberikan dedicated 2MB/s dan ~70ms latency via HTTP/2 push — ideal untuk pricing engine yang butuh sub-second. Standard shared consumer (GetRecords) cukup untuk data lake writer yang toleran latency. Kinesis Analytics (Flink) melakukan preprocessing untuk ML. Ini mengoptimalkan cost sesuai requirement masing-masing.
  • Kinesis resource policy (sejak 2023) memungkinkan cross-account access secara langsung. Producer accounts menggunakan IAM roles (AssumeRole) untuk mendapat temporary credentials dan menulis ke stream di central account. Ini mengikuti least privilege dan tidak memerlukan static credentials.
  • Kafka Streams KStream.branch() (atau split() di newer versions) memungkinkan routing messages ke multiple output topics berdasarkan predicates (conditions). Ini berjalan sebagai stream processing application yang membaca dari source topic dan menulis ke destination topics. Ini MSK-native dan scalable.
  • ReadProvisionedThroughputExceeded menunjukkan bahwa consumers melebihi read capacity (2 MB/s shared atau 5 GetRecords calls/s per shard). Dengan 5 consumers berbagi, setiap consumer hanya bisa GetRecords 1x/second per shard. Enhanced Fan-Out memberikan dedicated 2 MB/s per consumer per shard via HTTP/2 push, menghilangkan sharing.

Miskonsepsi & Jebakan Umum

  • Salah — multiple consumers bisa polling bersamaan.
  • Hanya berlaku dengan Enhanced Fan-Out.
  • Kinesis tidak auto-shard berdasarkan consumer count.
  • Menjadi bottleneck dan single point of failure.
  • Baik untuk streaming tapi Enhanced Fan-Out max 20 consumers dan memiliki biaya per-consumer per-shard.
  • Valid tapi lebih operational overhead.
  • Tidak cocok untuk high-throughput streaming.
  • Overkill untuk simple routing.
  • Mendukung dynamic partitioning tapi target-nya S3/Redshift/dll, bukan Kinesis stream lain.
  • Bekerja tapi membutuhkan code maintenance.
  • Hanya mendukung max 20 consumers tapi dengan 100K events/sec membutuhkan banyak shards yang mahal.
  • Memiliki message size limit 256KB dan bisa costly di volume ini.
  • Memiliki throughput limits yang mungkin tidak cukup.
  • Bukan streaming fan-in ke Kinesis.
  • Bisa multiple sources tapi memiliki biaya DPU dan startup time.
  • Bekerja tapi membutuhkan code untuk setiap stream.
  • Minimum buffer 60 detik, tidak cocok untuk sub-second pricing engine.
  • Membutuhkan producing ke 3 streams yang mahal.
  • Menambah complexity dan tidak diperlukan karena Kinesis adalah regional service.
  • Overkill dan menambah latency.
  • Biasanya untuk transformasi, bukan multi-topic routing.
  • Kafka brokers tidak memiliki routing rules built-in.
  • Setiap group membaca ALL messages dan membuang yang tidak dibutuhkan (inefficient).
  • Adalah symptom, bukan confirmation metric untuk fan-out bottleneck.
  • Terkait ingestion bukan consumption.
  • Terkait producers bukan consumers.
