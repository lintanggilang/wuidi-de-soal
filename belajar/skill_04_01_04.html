Domain 4: Security & Governance — Task 4.1: Apply authentication mechanisms

Skill 4.1.4: Set up IAM roles for access

IAMrolesLambdaAPIGateway

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.1: Apply authentication mechanisms), dengan fokus pada set up iam roles for access. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS Lambda
Komputasi serverless event-driven; batas timeout 15 menit dan memori hingga 10 GB.
Amazon API Gateway
Mengelola REST/HTTP/WebSocket API: throttling, otorisasi, caching, dan integrasi backend.
AWS IAM
Identity and Access Management: user, group, role, dan policy untuk akses least-privilege.

Poin-Poin Kunci

  • Least privilege berarti memberikan hanya permissions yang benar-benar diperlukan pada resource yang spesifik. Custom policy dengan: (1) Kinesis read permissions (GetRecords, GetShardIterator, DescribeStream, ListShards) — hanya actions untuk consume data. (2) DynamoDB write permissions (PutItem, BatchWriteItem) — hanya actions untuk menulis. (3) SNS publish permission — hanya action untuk mengirim notifikasi. Semua terbatas pada ARN spesifik.
  • CloudFormation service role is a best practice yang memisahkan "who can create stacks" dari "what resources stacks can create." Tanpa service role, CloudFormation menggunakan permissions dari calling user — jika user tidak memiliki glue:CreateJob, stack creation gagal. Solusinya: buat IAM role yang dipercaya oleh cloudformation.amazonaws.com dengan permissions untuk semua resources yang akan dibuat, lalu assign role tersebut ke stack.
  • Untuk third-party cross-account access, best practice adalah: (1) Trust policy dengan Principal: {"AWS": "arn:aws:iam::SAAS_ACCOUNT_ID:root"}. (2) Condition: {"StringEquals": {"sts:ExternalId": "provided-external-id"}}. External ID melindungi dari "confused deputy" attacks — tanpa External ID yang benar, bahkan jika seseorang mengetahui role ARN, mereka tidak bisa assume role. (3) Permission policy hanya memberikan s3:PutObject pada bucket spesifik.
  • AWS_IAM authorization pada API Gateway mengharuskan semua request di-sign menggunakan Signature Version 4 (SigV4) dengan credentials IAM entity (user atau role). API Gateway memverifikasi signature dan memeriksa apakah caller memiliki execute-api:Invoke permission pada API resource ARN. Ini adalah mekanisme native dan paling secure untuk IAM-based authentication.
  • AWS CLI named profiles dengan role_arn dan source_profile adalah best practice untuk multi-account access. Konfigurasi: [profile dev] role_arn = arn:aws:iam::DEV_ACCOUNT:role/DataEngineerRole, source_profile = default. CLI secara otomatis memanggil sts:AssumeRole dan menggunakan temporary credentials (expire setelah 1 jam). Ini aman karena menggunakan temporary credentials, audit-friendly (AssumeRole events tercatat di CloudTrail), dan tidak menyimpan long-term credentials per account.
  • iam:PassRole adalah permission yang mengontrol siapa yang boleh meng-assign (pass) IAM role ke AWS service. Ini adalah security control yang mencegah privilege escalation — tanpa batasan ini, user bisa membuat service dengan admin role dan mendapat permissions lebih dari yang mereka miliki. Engineer memerlukan policy: {"Effect": "Allow", "Action": "iam:PassRole", "Resource": "arn:aws:iam::ACCOUNT:role/GlueETLRole", "Condition": {"StringEquals": {"iam:PassedToService": "glue.amazonaws.com"}}}.
  • EMR EC2 instances mendapatkan permissions melalui instance profile. Instance profile berisi IAM role yang mendefinisikan permissions untuk aplikasi yang berjalan di cluster (Spark, Hive, etc.). Role ini memerlukan: s3:GetObject/PutObject untuk data access, glue:GetDatabase/GetTable untuk Catalog access, dan cloudwatch:PutMetricData untuk metrics. Secara default, AWS membuat EMR_EC2_DefaultRole untuk ini, tetapi custom instance profile lebih baik untuk least privilege.
  • Untuk berhasil memanggil sts:AssumeRole, calling principal (dalam hal ini GlueServiceRole) membutuhkan permission sts:AssumeRole pada target role ARN di IAM policy-nya. Ini sering terlewat — engineer menambahkan trust policy di Account B tapi lupa menambahkan permission di Account A. Diperlukan: {"Effect": "Allow", "Action": "sts:AssumeRole", "Resource": "arn:aws:iam::ACCOUNT_B:role/CrossAccountRole"} pada GlueServiceRole.
  • Lambda execution role hanya perlu trust policy untuk lambda.amazonaws.com. Trust policy menentukan SIAPA yang boleh assume role — dalam hal ini, Lambda service yang akan assume role saat menjalankan function. API Gateway tidak perlu ada di trust policy karena API Gateway memiliki role terpisah (API Gateway execution role) atau menggunakan Lambda proxy integration yang cukup dengan Lambda resource-based policy. DynamoDB dan Lambda invocation ditangani oleh permission policy, bukan trust policy.
  • CloudFormation service role memerlukan iam:PassRole permission ketika template meng-assign role ke service (misalnya assigning LambdaExecRole ke Lambda function). Permission yang diperlukan: {"Effect": "Allow", "Action": "iam:PassRole", "Resource": "arn:aws:iam::123456789012:role/LambdaExecRole", "Condition": {"StringEquals": {"iam:PassedToService": "lambda.amazonaws.com"}}}. Condition memastikan role hanya bisa di-pass ke Lambda service.

Miskonsepsi & Jebakan Umum

  • Memberikan hampir semua permissions.
  • Memberikan permissions berlebihan (termasuk Delete, Create).
  • Bisa bekerja tapi bukan best practice — memberikan user permission langsung ke semua services kurang secure.
  • Salah — syntax error menghasilkan error berbeda.
  • Salah — CloudFormation bisa dipanggil dari CLI, SDK, dan Console.
  • Memungkinkan siapa saja mencoba assume role.
  • Long-term credentials tidak aman untuk third-party.
  • Menambahkan complexity yang tidak perlu jika IAM auth sudah cukup.
  • Dimaksudkan untuk end-user authentication, bukan IAM-based service-to-service.
  • Tidak aman — WAF tidak bisa memvalidasi IAM identity.
  • Menggunakan long-term credentials.
  • Rawan error dan security risk.
  • Salah — full admin berlebihan.
  • Salah — role tidak perlu permission untuk di-pass.
  • Salah — trust policy mengontrol siapa yang boleh assume role, bukan siapa yang boleh pass role.
  • Kurang secure, credentials bisa bocor.
  • EMR service role untuk cluster management, bukan untuk EC2 instances.
  • IAM groups hanya untuk IAM users, bukan services.
  • AWS Organizations tidak diperlukan untuk cross-account role assumption.
  • Jika trust policy sudah allows Account A root, semua principals di Account A yang memiliki sts:AssumeRole permission bisa assume.
  • STS memiliki regional endpoints yang accessible secara default.
  • Salah — API Gateway tidak perlu assume Lambda's role.
  • Salah — DynamoDB tidak assume role.
  • CloudFormation tidak perlu assume LambdaExecRole.
  • Error bukan tentang membuat role, tapi meng-assign role ke Lambda.
  • Melanggar least privilege dan merupakan security risk.
