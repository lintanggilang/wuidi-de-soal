Skill 4.1.4: Set up IAM roles for access

IAMrolesLambdaAPIGateway

Summary

Skill this including in Domain 4: Security & Governance (Task 4.1: Apply authentication mechanisms), with fokus on set up iam roles for access. Materi berikut merangkum service AWS that relevan beserta concept important that needs kamu kuasai for topik this.

Key Services & Concepts

AWS Lambda
Komputasi serverless event-driven; limit timeout 15 minutes and memory up to 10 GB.
Amazon API Gateway
Manages REST/HTTP/WebSocket API: throttling, otorisasi, caching, and integration backend.
AWS IAM
Identity and Access Management: user, group, role, and policy for access least-privilege.

Key Points

  • Least privilege berarti provides only permissions that correct-correct is required on resource that specific. Custom policy with: (1) Kinesis read permissions (GetRecords, GetShardIterator, DescribeStream, ListShards) — only actions for consume data. (2) DynamoDB write permissions (PutItem, BatchWriteItem) — only actions for writes. (3) SNS publish permission — only action for sends notifikasi. All limited on ARN specific.
  • CloudFormation service role is a best practice that separates "who can create stacks" from "what resources stacks can create." Without service role, CloudFormation uses permissions from calling user — if user not has glue:CreateJob, stack creation fails. Solusinya: buat IAM role that dipercaya by cloudformation.amazonaws.com with permissions for all resources that will is created, lalu assign role the said to stack.
  • For third-party cross-account access, best practice is: (1) Trust policy with Principal: {"AWS": "arn:aws:iam::SAAS_ACCOUNT_ID:root"}. (2) Condition: {"StringEquals": {"sts:ExternalId": "provided-external-id"}}. External ID melindungi from "confused deputy" attacks — without External ID that correct, even if seseorang mengetahui role ARN, mereka cannot assume role. (3) Permission policy only provides s3:PutObject on bucket specific.
  • AWS_IAM authorization on API Gateway requires all request in-sign uses Signature Version 4 (SigV4) with credentials IAM entity (user or role). API Gateway memverifikasi signature and memeriksa whether caller has execute-api:Invoke permission on API resource ARN. Ini is mekanisme native and most secure for IAM-based authentication.
  • AWS CLI named profiles with role_arn and source_profile is best practice for multi-account access. Konfigurasi: [profile dev] role_arn = arn:aws:iam::DEV_ACCOUNT:role/DataEngineerRole, source_profile = default. CLI automatically calls sts:AssumeRole and uses temporary credentials (expire setelah 1 hours). Ini secure because uses temporary credentials, audit-friendly (AssumeRole events tercatat in CloudTrail), and not stores long-term credentials per account.
  • iam:PassRole is permission that mengontrol who that boleh meng-assign (pass) IAM role to AWS service. Ini is security control that prevents privilege escalation — without batasan this, user can creates service with admin role and mendapat permissions more from that mereka miliki. Engineer requires policy: {"Effect": "Allow", "Action": "iam:PassRole", "Resource": "arn:aws:iam::ACCOUNT:role/GlueETLRole", "Condition": {"StringEquals": {"iam:PassedToService": "glue.amazonaws.com"}}}.
  • EMR EC2 instances gets permissions through instance profile. Instance profile contains IAM role that mendefinisikan permissions for application that runs in cluster (Spark, Hive, etc.). Role this requires: s3:GetObject/PutObject for data access, glue:GetDatabase/GetTable for Catalog access, and cloudwatch:PutMetricData for metrics. In a default, AWS creates EMR_EC2_DefaultRole for this, but custom instance profile better for least privilege.
  • For succeeds calls sts:AssumeRole, calling principal (in this case GlueServiceRole) requires permission sts:AssumeRole on target role ARN in IAM policy-nya. Ini often terlewat — engineer adds trust policy in Account B but lupa adds permission in Account A. Diperlukan: {"Effect": "Allow", "Action": "sts:AssumeRole", "Resource": "arn:aws:iam::ACCOUNT_B:role/CrossAccountRole"} on GlueServiceRole.
  • Lambda execution role only needs trust policy for lambda.amazonaws.com. Trust policy determines SIAPA that boleh assume role — in this case, Lambda service that will assume role saat runs function. API Gateway does not need ada in trust policy because API Gateway has role separate (API Gateway execution role) or uses Lambda proxy integration that quite with Lambda resource-based policy. DynamoDB and Lambda invocation is handled by permission policy, not trust policy.
  • CloudFormation service role requires iam:PassRole permission when template meng-assign role to service (for example assigning LambdaExecRole to Lambda function). Permission that is required: {"Effect": "Allow", "Action": "iam:PassRole", "Resource": "arn:aws:iam::123456789012:role/LambdaExecRole", "Condition": {"StringEquals": {"iam:PassedToService": "lambda.amazonaws.com"}}}. Condition ensures role only can in-pass to Lambda service.

  • Provides permissions berlebihan (including Delete, Create).
  • Can works but not best practice — provides user permission directly to all services less secure.
  • Salah — syntax error produces error different.
  • Salah — CloudFormation can is called from CLI, SDK, and Console.
  • Enables who saja mencoba assume role.
  • Long-term credentials not secure for third-party.
  • Adds complexity that does not need if IAM auth already quite.
  • Dimaksudkan for end-user authentication, not IAM-based service-to-service.
  • Not secure — WAF cannot validates IAM identity.
  • Uses long-term credentials.
  • Rawan error and security risk.
  • Salah — full admin berlebihan.
  • Salah — role does not need permission for in-pass.
  • Salah — trust policy mengontrol who that boleh assume role, not who that boleh pass role.
  • Kurang secure, credentials can bocor.
  • EMR service role for cluster management, not for EC2 instances.
  • IAM groups only for IAM users, not services.
  • AWS Organizations not is required for cross-account role assumption.
  • If trust policy already allows Account A root, all principals in Account A that has sts:AssumeRole permission can assume.
  • STS has regional endpoints that accessible in a default.
  • Salah — API Gateway does not need assume Lambda's role.
  • Salah — DynamoDB not assume role.
  • CloudFormation does not need assume LambdaExecRole.
  • Error not about creates role, but meng-assign role to Lambda.
  • Melanggar least privilege and merupakan security risk.
