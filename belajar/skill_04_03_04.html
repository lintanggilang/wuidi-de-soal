Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.3: Ensure data encryption and masking), dengan fokus pada encryption in transit. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS KMS
Manajemen kunci enkripsi; dasar SSE-KMS untuk enkripsi at-rest dan kebijakan key.

Poin-Poin Kunci

  • S3 bucket policy dengan aws:SecureTransport condition enforces TLS: Policy: {"Effect": "Deny", "Principal": "*", "Action": "s3:*", "Resource": ["arn:aws:s3:::my-bucket", "arn:aws:s3:::my-bucket/*"], "Condition": {"Bool": {"aws:SecureTransport": "false"}}}. How it works: aws:SecureTransport = "true" → request made over HTTPS (TLS). aws:SecureTransport = "false" → request made over HTTP (plaintext). Deny when "false" → ONLY HTTPS requests succeed. Scope: Applies to ALL principals (Principal: "*"). Applies to ALL S3 actions (s3:*). Both bucket-level (arn:aws:s3:::my-bucket) and object-level (arn:aws:s3:::my-bucket/*). Important nuances: AWS SDK default: Most SDKs use HTTPS by default (but can be overridden). AWS CLI: Uses HTTPS by default. Legacy applications: May have hardcoded HTTP endpoints — will break (by design). VPC Endpoints: Traffic to S3 via VPC endpoint is ALWAYS HTTPS (gateway endpoints). This policy additionally ensures public access is also HTTPS-only.
  • Enforcing TLS on Glue JDBC connections requires multi-layer configuration: Server side (RDS): Set parameter group: rds.force_ssl = 1 (PostgreSQL) or require_secure_transport = ON (MySQL). This REJECTS any non-SSL connection attempt. Download RDS CA certificate bundle (rds-combined-ca-bundle.pem). Client side (Glue Connection): JDBC URL: jdbc:postgresql://mydb.xyz.rds.amazonaws.com:5432/mydb?ssl=true&sslmode=verify-full. SSL modes: disable — no SSL (insecure). allow — try SSL, fallback to no-SSL. prefer — try SSL, fallback (DEFAULT for many drivers). require — SSL required but no server cert verification. verify-ca — SSL + verify server cert is signed by trusted CA. verify-full — SSL + verify cert + verify hostname (MOST secure). Glue Connection property: "Require SSL connection" = checked. Upload CA cert as Glue job resource (via S3 path). Why verify-full: Prevents man-in-the-middle attacks. Verifies you're connecting to the REAL RDS endpoint (not a DNS-spoofed server). Validates certificate chain to trusted Amazon CA.
  • Direct Connect encryption options: Option 1 — VPN over Direct Connect: Create VPN tunnels that ride over the Direct Connect link. Data path: On-prem → [IPsec encrypted] → Direct Connect → AWS VPN Gateway → VPC. Configuration: Use public VIF for VPN endpoint connectivity, OR use Transit Gateway with Direct Connect + VPN attachment. Encryption: IPsec (AES-256). Throughput: Up to 1.25 Gbps per VPN tunnel (multi-tunnel for more). Best for: Existing Direct Connect without MACsec support. Option 2 — MACsec (IEEE 802.1AE): Layer 2 encryption on the physical Direct Connect connection. Wire-speed encryption (10 Gbps, 100 Gbps — no throughput loss). Configuration: Direct Connect connection must support MACsec. Exchange MACsec keys (CKN/CAK) with AWS. Enable on connection. Best for: New dedicated connections, high-throughput requirements. Option 3 — Application-level TLS: S3 API calls use HTTPS regardless of transport. Glue, Athena, Redshift connections use TLS. Provides encryption even without VPN/MACsec. But: other protocols (NFS, custom TCP) remain unencrypted. Why encryption needed: Direct Connect is a PRIVATE connection but NOT encrypted. Traffic could theoretically be intercepted at co-location facility. Compliance standards (PCI-DSS, HIPAA) often require transit encryption.
  • MSK TLS configuration has multiple layers: Cluster-level configuration (at creation): Encryption in transit setting: TLS — ONLY encrypted connections accepted. TLS_PLAINTEXT — both TLS and plaintext accepted (migration mode). PLAINTEXT — no encryption (not recommended). Inter-broker encryption: separatement configurable. Between-broker replication can be encrypted independently. Client configuration (producers/consumers): Bootstrap servers: Use TLS endpoints (port 9094) not plaintext (9092). Producer config: security.protocol=SSL, ssl.truststore.location=/path/to/kafka.client.truststore.jks. Consumer config: Same SSL properties. Truststore contains Amazon root CA certificates. MSK-managed certificates: MSK automatically provisions TLS certificates for brokers via ACM. No manual certificate management on broker instances. Certificate rotation handled by AWS. Mutual TLS (mTLS) optional: Clients can authenticate with their own certificates. MSK supports ACM Private CA for client cert issuance. Provides both encryption AND authentication. Key ports: 9092 — plaintext. 9094 — TLS. 9096 — SASL/SCRAM with TLS. 9098 — IAM authentication with TLS.
  • EMR Security Configuration for comprehensive in-transit encryption: Configuration structure: {"EncryptionConfiguration": {"EnableInTransitEncryption": true, "InTransitEncryptionConfiguration": {"TLSCertificateConfiguration": {"CertificateProviderType": "PEM", "S3Object": "s3://my-bucket/certs/my-certs.zip"}}}}. What gets encrypted: (1) HDFS data transfer: DataNode-to-DataNode replication encrypted. Client-to-DataNode reads/writes encrypted. NameNode RPC communication encrypted. (2) MapReduce: Shuffle data between map and reduce tasks encrypted. (3) Spark: Executor-to-executor shuffle encrypted (spark.authenticate + spark.network.crypto.enabled). Driver-to-executor communication encrypted. (4) Tez: Shuffle encryption enabled. (5) EMRFS → S3: Already HTTPS by default (TLS 1.2+). Security Configuration ensures this can't be downgraded. Certificate options: PEM from S3: Upload zip with private key + certificate + CA chain. ACM: EMR requests certificates from ACM Private CA. Custom Java class: Programmatic certificate provision (e.g., HashiCorp Vault integration). Performance impact: ~5-15% overhead for encryption/decryption. CPU utilization increases for TLS handshakes and data encryption. Plan for larger instance types or more nodes.
  • Redshift TLS enforcement via parameter group: Configuration steps: (1) Modify parameter group: Parameter: require_SSL = true → ALL connections MUST use SSL/TLS (no plaintext). Parameter: ssl_min_protocol_version = "TLSv1.2" → reject TLS 1.0, TLS 1.1. (2) Apply parameter group to cluster (may require reboot for static parameters). (3) Client configuration: JDBC URL: jdbc:redshift://cluster.xxx.redshift.amazonaws.com:5439/mydb?ssl=true&sslMode=verify-full. ODBC: sslmode=verify-full, min_tls=1.2. (4) Legacy application remediation: Identify apps using TLS 1.0/1.1 (CloudWatch connection logs). Upgrade JDBC/ODBC drivers to versions supporting TLS 1.2. Update application SSL configuration. Additional Redshift SSL features: Supports ACM-issued certificates for custom domains. Certificate rotation managed by AWS. FIPS 140-2 compliant encryption modules available. Cipher suite configuration for specific algorithm requirements. Monitoring: CloudWatch metric: SSLConnections vs NonSSLConnections. System table: svl_connection_log shows SSL version per connection. Alert on any TLS 1.0/1.1 attempts after enforcement.
  • AWS service-to-service encryption in transit analysis: Hop 1 — On-premises Producer → Kinesis: AWS SDK/KPL: HTTPS by default (TLS 1.2). Risk: Custom producers might use HTTP if misconfigured. Mitigation: Cannot force HTTPS at Kinesis level (no aws:SecureTransport equivalent for Kinesis). Must enforce at producer application configuration. Hop 2 — Kinesis → Lambda: AWS internal invocation: encrypted channel managed by AWS. Lambda event source mapping pulls from Kinesis over internal encrypted links. No user configuration needed or possible. Hop 3 — Lambda → DynamoDB: AWS SDK in Lambda: HTTPS by default. boto3/SDK calls always use TLS to DynamoDB endpoint. VPC endpoint (if configured): still HTTPS. Hop 4 — Within Kinesis (shard-to-shard): Kinesis manages data within the service boundary. Server-side encryption (at rest) protects stored stream data. Inter-AZ replication uses AWS-internal encrypted links. Key risks and mitigations: On-prem producers: Enforce HTTPS in application config. SDK customization: Developers might set verify=False or use_ssl=False — code review required. Older SDK versions: May negotiate TLS 1.0 — upgrade SDKs. VPC endpoints: Ensure DNS resolution points to VPC endpoint (not public endpoint).
  • Client-Side Encryption (CSE) = encrypt BEFORE data leaves your control: Two approaches: CSE-KMS (AWS KMS managed): Application calls KMS GenerateDataKey → gets plaintext + encrypted data key. Encrypts data locally with plaintext data key. Uploads: encrypted data + encrypted data key as S3 object metadata. S3 stores ciphertext (S3 never sees plaintext). Recipient: downloads encrypted object, calls KMS Decrypt on data key, decrypts locally. CSE-C (Client-managed key): Application uses its own master key (not in KMS). Generates data key locally, encrypts data. Uploads encrypted data + wrapped data key. Complete independence from AWS for key management. Defense-in-depth layers: Layer 1: Client-side encryption (data encrypted before leaving app). Layer 2: TLS (HTTPS) encrypts the already-encrypted data in transit. Layer 3: S3 SSE (can ALSO enable) encrypts the already-encrypted object at rest. Result: Triple encryption — even if one layer compromised, data remains protected. AWS Encryption SDK: Multi-language SDK (Java, Python, JavaScript, C). Handles envelope encryption, key caching, algorithm selection. Supports data key caching for performance. Message format includes authentication (prevents tampering).
  • ACM capabilities untuk data pipeline TLS management: Use Case 1 — ALB (Public Certificate): ACM issues free public TLS cert for api.company.com. Auto-renews 60 days before expiration. Attach to ALB listener → HTTPS termination. No manual certificate management. Supports wildcard (*.company.com) and SAN certificates. Use Case 2 — Internal mTLS (Private CA): ACM Private Certificate Authority: Create private CA within your organization. Issue certificates for internal services (not publicly trusted). mTLS flow: Service A presents cert → Service B validates against private CA. Service B presents cert → Service A validates against private CA. Both sides verified → encrypted + authenticated channel. Use case: Glue → internal API, Lambda → internal microservices. Use Case 3 — Redshift Custom Domain: Redshift custom domain names support ACM certificates. Alternatively, import third-party certificates for services without native ACM integration. Lifecycle management: Public certs: auto-renewed by ACM (domain validation via DNS CNAME). Private certs: configurable expiration, programmatic issuance/revocation. Imported certs: manual renewal (ACM alerts 45 days before expiration). Cost: Public ACM certs: free. Private CA: $400/month per CA + per-certificate fee.
  • IoT + streaming + mandatory TLS requires architectural optimization: Challenge: TLS handshake = 1-2 round trips. High-latency networks: handshake may timeout. Many devices = many concurrent handshakes. Direct to Kinesis: HTTPS PutRecord per message = new connection per request (unless HTTP keep-alive). Solution Architecture: [IoT Devices] → [TLS/MQTT] → [IoT Core] → [Rules Engine] → [Kinesis]. Benefits of IoT Core approach: MQTT protocol: Persistent connection — ONE TLS handshake, then thousands of messages over same connection. Much less overhead than per-request HTTPS. Optimized for low-bandwidth devices. TLS session resumption: IoT Core supports session tickets — subsequent connections skip full handshake. Reduces latency for reconnections. Greengrass edge gateway: Local devices connect to Greengrass (low latency, local network). Greengrass maintains SINGLE persistent TLS connection to cloud. Aggregates hundreds of device messages into batched uploads. Reduces cloud-facing TLS connections from N devices to 1. Connection management: IoT Core handles millions of persistent connections. Built-in retry logic and connection draining. QoS levels for delivery guarantees.

Miskonsepsi & Jebakan Umum

  • VPC endpoints use HTTPS but don't prevent HTTP access through public endpoint.
  • S3 doesn't have configurable listener ports; both HTTP/HTTPS always available at service level.
  • SSE encrypts data at rest, doesn't affect transport protocol.
  • TLS is NOT default; many JDBC drivers default to sslmode=prefer (may fallback).
  • IAM auth uses TLS but must still be explicitly configured in the connection string.
  • VPC traffic is NOT automatically encrypted; eavesdropping possible within VPC.
  • Factually wrong; DX is unencrypted by default.
  • Transfer Acceleration unrelated to DX.
  • Producers/consumers MUST be configured to use TLS endpoints.
  • MSK is managed; no direct broker EC2 access for cert installation.
  • Security groups control network access, NOT encryption.
  • Ranger is for authorization, not encryption.
  • Simplified but requires Security Configuration (not just a checkbox).
  • VPC does NOT encrypt inter-instance traffic.
  • NLB in front of Redshift is not a standard architecture.
  • Security groups filter by port/IP, not TLS version.
  • Redshift historically supported TLS 1.0; must explicitly set minimum version.
  • All hops are encrypted by default with AWS SDK.
  • Kinesis internal operations are protected by AWS infrastructure.
  • Most AWS SDKs use TLS by default.
  • VPN to S3 is not standard architecture.
  • Transfer Acceleration is performance optimization, not security.
  • SSE happens at S3 (server-side) AFTER data arrives.
  • Public certs auto-renew, not manual.
  • ACM integrates with many services.
  • Different certificate types serve different purposes.
  • Violates security requirement.
  • TLS 1.0 is deprecated, not faster in meaningful ways, and less secure.
  • Kinesis doesn't have TLS timeout settings for producers.
