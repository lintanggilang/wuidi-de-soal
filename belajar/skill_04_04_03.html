Domain 4: Security & Governance — Task 4.4: Prepare logs for audit

Skill 4.4.3: CloudTrail Lake queries

CloudTrailLakeSQL

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.4: Prepare logs for audit), dengan fokus pada cloudtrail lake queries. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS CloudTrail
Audit trail panggilan API akun AWS; CloudTrail Lake untuk query SQL atas event.

Poin-Poin Kunci

  • CloudTrail Lake mendukung import of existing CloudTrail logs dari S3 ke event data store. Setelah import selesai, tim bisa langsung menjalankan SQL queries pada data historis tersebut. Ini memberikan fastest time-to-investigation karena tidak perlu menunggu events baru terkumpul dan tidak perlu setup infrastructure.
  • Memisahkan management events dan data events ke event data stores yang berbeda adalah best practice karena: (1) data events biasanya menghasilkan volume jauh lebih tinggi dengan biaya yang signifikan, (2) retention requirements mungkin berbeda, (3) seven-year extendable pricing lebih cost-effective untuk retention 2555 hari dibanding one-year extendable pricing. Organization event data store secara otomatis mengumpulkan events dari semua member accounts.
  • CloudTrail Lake menggunakan SQL syntax di mana event data store direferensikan oleh ID-nya. Field userIdentity.arn mengakses nested field menggunakan dot notation. Fungsi date_add dan now() digunakan untuk time-based filtering. NOT LIKE digunakan untuk filtering IP ranges.
  • Untuk low query frequency (5/day), Athena lebih cost-effective karena biaya hanya berdasarkan data yang di-scan per query ($5/TB scanned). CloudTrail Lake memiliki biaya ingestion ($2.50 per 100K events ingested) dan retention storage charges yang berlaku terus-menerus terlepas dari apakah data di-query atau tidak. Untuk 3 tahun retention dengan volume tinggi events, biaya CloudTrail Lake bisa sangat signifikan. Athena + S3 dengan lifecycle rules ke Glacier memberikan storage costs yang jauh lebih rendah.
  • CloudTrail Lake mendukung dashboards yang dibuat dari saved queries dan dapat menampilkan widgets berupa bar charts, line charts, dan tables. Item 1 (top denied calls) bisa dicapai dengan query filtering errorCode = 'AccessDenied' dan GROUP BY userIdentity. Item 2 (hourly trend) bisa dicapai dengan time-series grouping. Namun item 3 tidak achievable karena CloudTrail events menyimpan sourceIPAddress tapi TIDAK menyimpan informasi negara/geografi — konversi IP ke negara memerlukan GeoIP database eksternal yang tidak tersedia di CloudTrail Lake SQL.
  • Best practice adalah membuat event data stores terpisah untuk management events dan data events karena mereka memiliki volume, cost profiles, dan potentially different retention periods. Event data store configuration (event types) tidak bisa diubah setelah creation untuk beberapa settings. Membuat event data store terpisah juga memungkinkan query yang lebih targeted dan cost management yang lebih baik.
  • Query yang benar menggunakan eventName = 'DeleteTable' (nama API DynamoDB yang tepat), eventSource = 'dynamodb.amazonaws.com', dan mengambil userIdentity fields yang mengidentifikasi principal. sourceIPAddress membantu investigasi asal request. requestParameters berisi nama tabel yang dihapus.
  • CloudTrail Lake pricing memiliki dua komponen utama: ingestion (per event) dan retention (per GB stored per month). Dengan 2 billion data events per bulan yang diakumulasi selama 7 tahun, total stored data akan sangat besar dan biaya retention menjadi primary cost driver. Ini bisa mencapai puluhan ribu dollar per bulan.
  • CloudTrail Lake menyediakan StartQuery API yang bisa dipanggil secara programmatic. Menggunakan EventBridge Scheduler untuk memicu Lambda yang menjalankan StartQuery, kemudian GetQueryResults untuk mengecek hasilnya, dan SNS untuk notifikasi jika ditemukan anomali, adalah pendekatan yang paling terintegrasi dan flexible.
  • CloudTrail Lake mendukung integrations yang memungkinkan ingestion events dari sumber di luar AWS melalui channels. Aplikasi kustom dapat mengirim events menggunakan PutAuditEvents API ke channel yang terkait dengan event data store. Events ini kemudian queryable menggunakan SQL sama seperti CloudTrail events native.

Miskonsepsi & Jebakan Umum

  • Memerlukan setup: membuat tabel, konfigurasi partition projection, dan memahami format log — lebih banyak operational setup.
  • Memerlukan provisioning cluster, konfigurasi ingestion, dan waktu indexing — paling banyak setup.
  • Hanya akan menangkap events baru setelah pembuatan, bukan data historis 6 bulan.
  • Menggabungkan semuanya yang kurang optimal dari segi biaya dan management.
  • Tidak scalable untuk 100 accounts dan tidak bisa cross-account query.
  • Memiliki retention terlalu pendek untuk data events jika compliance memerlukan 7 tahun.
  • Menggunakan element_at yang merupakan fungsi Athena/Presto, bukan CloudTrail Lake SQL, dan memiliki hardcoded date bukan relative time.
  • Menggunakan $EDS_ID yang bukan syntax valid — CloudTrail Lake menggunakan event data store ID langsung.
  • Tidak memfilter IP addresses sesuai requirement dan INTERVAL syntax tidak didukung di CloudTrail Lake.
  • Salah karena pricing models sangat berbeda.
  • Benar tentang Athena federated queries tapi bukan faktor utama untuk use case ini.
  • Salah karena CloudTrail Lake tidak charge per query — biaya utamanya adalah ingestion dan retention.
  • Salah karena geographic data tidak tersedia.
  • Salah karena time-series didukung.
  • Salah karena CloudTrail Lake memiliki native dashboards.
  • Beberapa konfigurasi event data store bisa diupdate tapi memisahkan tetap best practice.
  • Salah karena trail dan event data store adalah entities terpisah — menambahkan data events ke trail tidak otomatis memasukkannya ke existing event data store.
  • Menghapus 30 hari data yang sudah ada.
  • Menggunakan 'DropTable' yang bukan nama API DynamoDB yang benar (itu SQL terminology).
  • Menggunakan field eventCategory = 'Delete' yang bukan field valid di CloudTrail events — eventCategory hanya berisi 'Management' atau 'Data'.
  • Menggunakan resources.type yang bukan standard filtering approach dan time range terlalu spesifik jika tanggal persis tidak diketahui.
  • Salah karena "first copy free" berlaku untuk CloudTrail trail delivery ke S3, bukan untuk CloudTrail Lake ingestion — Lake memiliki pricing terpisah.
  • Salah karena tidak ada flat fee — pricing sepenuhnya usage-based.
  • Salah karena CloudTrail Lake tidak charge per query — queries included tanpa biaya tambahan.
  • Salah karena CloudTrail Lake tidak memiliki built-in scheduled query feature dengan email notifications pada saat ini.
  • Hanya mendeteksi anomali volume API calls, bukan pattern matching kustom seperti privilege escalation patterns yang memerlukan query spesifik.
  • Menambah kompleksitas dan biaya yang tidak perlu.
  • Salah karena menulis ke S3 bucket CloudTrail tidak membuat events muncul di CloudTrail Lake — Lake memiliki storage terpisah dari S3 trail delivery.
  • Salah karena EventBridge tidak memiliki routing otomatis ke CloudTrail Lake.
  • Salah karena tidak ada subscription filter dari CloudWatch Logs ke CloudTrail Lake.
