Skill 4.4.3: CloudTrail Lake queries

CloudTrailLakeSQL

Summary

Skill this including in Domain 4: Security & Governance (Task 4.4: Prepare logs for audit), with fokus on cloudtrail lake queries. Materi berikut merangkum service AWS that relevan beserta concept important that needs kamu kuasai for topik this.

Key Services & Concepts

AWS CloudTrail
Audit trail panggilan API akun AWS; CloudTrail Lake for query SQL atas event.

Key Points

  • CloudTrail Lake supports import of existing CloudTrail logs from S3 to event data store. Setelah import complete, team can directly runs SQL queries on data historis the said. Ini provides fastest time-to-investigation because does not need waits events new terkumpul and does not need setup infrastructure.
  • Memisahkan management events and data events to event data stores that different is best practice because: (1) data events usually produces volume jauh higher with cost that significant, (2) retention requirements may different, (3) seven-year extendable pricing more cost-effective for retention 2555 days dibanding one-year extendable pricing. Organization event data store automatically mengumpulkan events from all member accounts.
  • CloudTrail Lake uses SQL syntax in mana event data store direferensikan by ID-nya. Field userIdentity.arn accesses nested field uses dot notation. Fungsi date_add and now() is used for time-based filtering. NOT LIKE is used for filtering IP ranges.
  • For low query frequency (5/day), Athena more cost-effective because cost only based on data that in-scan per query ($5/TB scanned). CloudTrail Lake has cost ingestion ($2.50 per 100K events ingested) and retention storage charges that applies terus-menerus terlepas from whether data in-query or not. For 3 years retention with volume high events, cost CloudTrail Lake can very significant. Athena + S3 with lifecycle rules to Glacier provides storage costs that jauh lower.
  • CloudTrail Lake supports dashboards that is created from saved queries and can menampilkan widgets berupa bar charts, line charts, and tables. Item 1 (top denied calls) can is reached with query filtering errorCode = 'AccessDenied' and GROUP BY userIdentity. Item 2 (hourly trend) can is reached with time-series grouping. Namun item 3 not achievable because CloudTrail events stores sourceIPAddress but TIDAK stores informasi negara/geografi — konversi IP to negara requires GeoIP database external that not available in CloudTrail Lake SQL.
  • Best practice is creates event data stores separate for management events and data events because mereka has volume, cost profiles, and potentially different retention periods. Event data store configuration (event types) cannot is changed setelah creation for several settings. Creates event data store separate also enables query that more targeted and cost management that better.
  • Query that correct uses eventName = 'DeleteTable' (nama API DynamoDB that correct), eventSource = 'dynamodb.amazonaws.com', and retrieves userIdentity fields that identifies principal. sourceIPAddress membantu investigasi asal request. requestParameters contains nama table that is deleted.
  • CloudTrail Lake pricing has dua komponen main: ingestion (per event) and retention (per GB stored per month). By 2 billion data events per months that diakumulasi during 7 years, total stored data will very large and cost retention menjadi primary cost driver. Ini can reaches puluhan ribu dollar per months.
  • CloudTrail Lake provides StartQuery API that can is called in a programmatic. Uses EventBridge Scheduler for triggers Lambda that runs StartQuery, then GetQueryResults for checks hasilnya, and SNS for notifikasi if ditemukan anomali, is approach that most terintegrasi and flexible.
  • CloudTrail Lake supports integrations that enables ingestion events from source in luar AWS through channels. Aplikasi kustom can sends events uses PutAuditEvents API to channel that related with event data store. Events this then queryable uses SQL same such as CloudTrail events native.

Common Misconceptions & Pitfalls

  • Requires setup: creates table, configuration partition projection, and memahami format log — more operational setup.
  • Requires provisioning cluster, configuration ingestion, and time indexing — most many setup.
  • Only will captures events new setelah creation, not data historis 6 months.
  • Menggabungkan semuanya that less optimal from segi cost and management.
  • Not scalable for 100 accounts and cannot cross-account query.
  • Has retention too pendek for data events if compliance requires 7 years.
  • Uses element_at that merupakan function Athena/Presto, not CloudTrail Lake SQL, and has hardcoded date not relative time.
  • Uses $EDS_ID that not syntax valid — CloudTrail Lake uses event data store ID directly.
  • Not memfilter IP addresses appropriate requirement and INTERVAL syntax not is supported in CloudTrail Lake.
  • Salah because pricing models very different.
  • Benar about Athena federated queries but not faktor main for use case this.
  • Salah because CloudTrail Lake not charge per query — cost utamanya is ingestion and retention.
  • Salah because geographic data not available.
  • Salah because time-series is supported.
  • Salah because CloudTrail Lake has native dashboards.
  • Several configuration event data store can diupdate but separates still best practice.
  • Salah because trail and event data store is entities separate — adds data events to trail not automatic memasukkannya to existing event data store.
  • Deletes 30 days data that already ada.
  • Uses 'DropTable' that not nama API DynamoDB that correct (that SQL terminology).
  • Uses field eventCategory = 'Delete' that not field valid in CloudTrail events — eventCategory only contains 'Management' or 'Data'.
  • Uses resources.type that not standard filtering approach and time range too specific if tanggal persis not diketahui.

  • Salah because there is no flat fee — pricing sepenuhnya usage-based.
  • Salah because CloudTrail Lake not charge per query — queries included without cost additional.
  • Salah because CloudTrail Lake not has built-in scheduled query feature with email notifications on saat this.
  • Only detects anomali volume API calls, not pattern matching kustom such as privilege escalation patterns that requires query specific.
  • Adds complexity and cost that does not need.
  • Salah because writes to S3 bucket CloudTrail not creates events muncul in CloudTrail Lake — Lake has storage separate from S3 trail delivery.
  • Salah because EventBridge not has routing automatic to CloudTrail Lake.
