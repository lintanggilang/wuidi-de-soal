Skill 4.2.3: Database users, groups, roles

databaseusersRedshiftGRANT

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.2: Apply authorization mechanisms), dengan fokus pada database users, groups, roles. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon Redshift
Data warehouse berskala petabyte; mendukung COPY/UNLOAD, materialized view, dan streaming ingestion.
Redshift Streaming Ingestion
Konsumsi langsung dari Kinesis/MSK ke materialized view Redshift, latensi detik, tanpa staging S3.

Poin-Poin Kunci

  • Redshift roles (introduced as native feature) memungkinkan centralized permission management: CREATE ROLE analysts_readonly; GRANT SELECT ON ALL TABLES IN SCHEMA sales TO ROLE analysts_readonly; GRANT ROLE analysts_readonly TO user1, user2, ..., user50; Benefit: (1) Permissions didefinisikan SEKALI di role, (2) New users hanya perlu GRANT role — no need to repeat permission statements, (3) Permission changes (e.g., add new table) hanya perlu update role — automatically applies to all members, (4) Audit simplified — check role membership vs 50 individual grants. Redshift role hierarchy juga memungkinkan roles inherit dari roles lain.
  • Column-level access control di Redshift memungkinkan GRANT/REVOKE pada specific columns: GRANT SELECT (patient_id, name, appointment_date) ON TABLE patients TO ROLE customer_service; Behavior: Jika user mencoba SELECT * FROM patients — query fails dengan "permission denied for column diagnosis_code". User HARUS explicitly list only permitted columns. Ini enforce security di database engine level — tidak bisa di-bypass melalui application layer.
  • Redshift Row-Level Security (RLS) policies transparently filter rows at query execution time: (1) CREATE RLS POLICY tenant_isolation WITH (tenant_id int) USING (tenant_id = current_setting('app.tenant_id')::int); (2) ATTACH RLS POLICY tenant_isolation ON sales TO ROLE tenant_analyst; (3) ALTER TABLE sales ROW LEVEL SECURITY ON; Saat tenant analyst menjalankan SELECT * FROM sales, Redshift automatically appends WHERE tenant_id = {their_tenant_id}. Advantages: Database-enforced (cannot bypass), transparent to queries (no application changes needed), works with any SQL client, auditable, cannot be accidentally removed by developers. Session variable (SET app.tenant_id) di-set saat connection establishment.
  • Redshift provides system tables/views untuk permission auditing: pg_catalog.pg_user: Lists all database users (usename, usesysid, usesuper). pg_catalog.pg_group: Shows group names and member user IDs (groname, grolist). SVV_RELATION_PRIVILEGES: Shows effective permissions on tables/views — includes: identity_name (user/role), identity_type, relation_name, privilege_type. Additional useful views: SVV_ROLE_GRANTS: Shows role hierarchy dan membership, HAS_TABLE_PRIVILEGE(): Function to check specific user's access, pg_catalog.pg_namespace: Schema information. Example audit query: SELECT u.usename, g.groname, rp.relation_name, rp.privilege_type FROM pg_user u LEFT JOIN pg_group g ON u.usesysid = ANY(g.grolist) JOIN svv_relation_privileges rp ON rp.identity_name = u.usename WHERE rp.namespace_name = 'finance'.
  • RDS IAM Database Authentication memerlukan konfigurasi di multiple layers: Step 1 — RDS Instance: Modify DB instance → Enable IAM DB Authentication. Step 2 — Database level: CREATE USER lambda_app WITH LOGIN; GRANT rds_iam TO lambda_app; (rds_iam role indicates user authenticates via IAM). Step 3 — IAM Policy: Allow rds-db:connect pada resource "arn:aws:rds-db:region:account:dbuser:dbi-resource-id/lambda_app". Step 4 — Application code: token = rds_client.generate_db_auth_token(DBHostname, Port, DBUser); Connect menggunakan token sebagai password (valid 15 minutes). Benefits: No persistent passwords, token auto-expires, leverages IAM for centralized access control, integrates with CloudTrail.
  • Redshift permission evaluation: Permissions dari groups dan individual users dievaluasi secara ADDITIVE (union). REVOKE pada user level hanya menghapus permissions yang directly granted ke user tersebut — TIDAK menghapus permissions yang inherited dari group membership. Dalam kasus ini: john's effective permissions = (permissions dari group "analytics") UNION (direct user permissions) - (direct user revocations). Karena SELECT didapat dari GROUP (bukan direct grant), REVOKE dari user tidak mempengaruhi. Untuk benar-benar block john dari revenue_table: (1) Remove john dari group "analytics", ATAU (2) REVOKE SELECT pada table dari GROUP "analytics" dan buat group baru tanpa table tersebut, ATAU (3) Gunakan RLS policy untuk deny access. Ini berbeda dari IAM dimana explicit Deny SELALU wins.
  • Dua GRANT statements diperlukan untuk cover existing + future objects: (1) GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO ROLE bi_readonly — Memberikan SELECT pada semua tables yang SUDAH ADA saat statement dijalankan. (2) ALTER DEFAULT PRIVILEGES IN SCHEMA analytics GRANT SELECT ON TABLES TO ROLE bi_readonly — Mendefinisikan bahwa setiap table BARU yang dibuat di schema "analytics" akan otomatis mendapat GRANT SELECT ke bi_readonly role. Tanpa ALTER DEFAULT PRIVILEGES, setiap table baru memerlukan manual GRANT. Juga diperlukan: GRANT USAGE ON SCHEMA analytics TO ROLE bi_readonly (agar bisa "see" schema).
  • Redshift supports IAM-federated access melalui GetClusterCredentials API: Flow: (1) User authenticates via SAML/SSO → assumes IAM role, (2) Application calls redshift:GetClusterCredentials with parameters: DbUser (database username), DbGroups (Redshift groups to join), AutoCreate (auto-create user if not exists), (3) API returns temporary database credentials, (4) User connects to Redshift — automatically member of specified DbGroups. IAM Policy controls: IAM policy pada role determines WHICH DbUsers dan DbGroups the federated user can request (via conditions). Redshift database permissions: Groups in Redshift have pre-configured GRANT permissions. Mapping: IAM Role "analysts-role" → allowed DbGroups: ["analytics_readonly"] → Redshift group "analytics_readonly" has SELECT on analytics schema.
  • Complete remediation approach: Immediate: ALTER USER contractor_user DISABLE; — prevents any new connections. Existing active sessions: SELECT pg_terminate_backend(pid) untuk kill active sessions. Also: REVOKE ALL ON ALL TABLES IN SCHEMA ... FROM contractor_user; untuk remove all permissions. Audit: STL_CONNECTION_LOG — shows all connections: login time, source IP, success/failure. STL_QUERY — shows all SQL executed by the user (full query text, timestamps, tables accessed). STL_QUERYTEXT — untuk queries yang terlalu panjang. SVL_STATEMENTTEXT — comprehensive statement log. Prevention: Migrate to IAM-based authentication via GetClusterCredentials. When contractor's IAM access is revoked (role assumption removed), they cannot generate DB credentials. Temporary credentials expire automatically (default 15 min - 3600 sec configurable).
  • Schema-level isolation menggunakan precise GRANT statements: ETL Role: GRANT USAGE ON SCHEMA raw, staging TO ROLE etl_role; GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA raw TO ROLE etl_role; GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA staging TO ROLE etl_role; (NO grants on presentation schema — implicit deny). Transformation Role: GRANT USAGE ON SCHEMA raw, staging, presentation TO ROLE transform_role; GRANT SELECT ON ALL TABLES IN SCHEMA raw TO ROLE transform_role; GRANT ALL ON ALL TABLES IN SCHEMA staging, presentation TO ROLE transform_role; BI Role: GRANT USAGE ON SCHEMA presentation TO ROLE bi_role; GRANT SELECT ON ALL TABLES IN SCHEMA presentation TO ROLE bi_role; (Only USAGE + SELECT on presentation — cannot see raw/staging schemas). Key: USAGE permission on schema is required first — without it, user cannot even list objects.

Miskonsepsi & Jebakan Umum

  • Expensive dan data duplication needed.
  • Massive security risk, no audit trail per-user, violates least privilege.
  • Query engine feature bukan access control mechanism.
  • Requires application changes dan JOIN complexity.
  • Shows NULL tapi user TAHU kolom exists — mungkin tidak compliant dengan regulations yang memerlukan "no access".
  • Bekerja sebagai alternative approach — CREATE VIEW patient_safe AS SELECT patient_id, name, appointment_date FROM patients — tapi pengguna masih perlu dicegah akses ke base table langsung. Views + column-level grants bisa dikombinasikan untuk defense-in-depth.
  • Works tapi 200 schemas = management nightmare, schema DDL changes harus di-replicate 200x.
  • Can be bypassed jika user gains direct table access.
  • Evaluates cluster-level configuration, bukan database-internal permissions.
  • Shows query history bukan permissions.
  • Shows API calls ke Redshift service tapi TIDAK in-database SQL permissions.
  • AmazonRDSFullAccess grants RDS API permissions (CreateDB, etc.), NOT database-level connectivity.
  • RDS Proxy supports IAM auth tapi database-level GRANT rds_iam still needed.
  • Correct conclusion tapi wrong reasoning.
  • Salah — Redshift bukan IAM (no explicit deny concept di database permissions).
  • No error, just evaluated as described.
  • Memberikan CREATE, DROP, dll — violates read-only requirement.
  • Mengizinkan melihat schema tapi tidak SELECT dari tables.
  • Hanya cover existing tables — future tables won't be accessible.
  • Doesn't scale for federation.
  • Salah — federated users get permissions based on DbGroups, not superuser.
  • S3 policies irrelevant for Redshift database access.
  • Passwords may not have expiry set.
  • Disabling password doesn't revoke permissions on existing sessions.
  • Is good defense-in-depth addition but doesn't fully address schema isolation requirements.
