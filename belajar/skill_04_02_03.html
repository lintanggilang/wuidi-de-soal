Key Points

  • Redshift roles (introduced as native feature) enables centralized permission management: CREATE ROLE analysts_readonly; GRANT SELECT ON ALL TABLES IN SCHEMA sales TO ROLE analysts_readonly; GRANT ROLE analysts_readonly TO user1, user2, ..., user50; Benefit: (1) Permissions didefinisikan SEKALI in role, (2) New users only needs GRANT role — no need to repeat permission statements, (3) Permission changes (e.g., add new table) only needs update role — automatically applies to all members, (4) Audit simplified — check role membership vs 50 individual grants. Redshift role hierarchy also enables roles inherit from roles other.
  • Column-level access control in Redshift enables GRANT/REVOKE on specific columns: GRANT SELECT (patient_id, name, appointment_date) ON TABLE patients TO ROLE customer_service; Behavior: If user mencoba SELECT * FROM patients — query fails with "permission denied for column diagnosis_code". User MUST explicitly list only permitted columns. This enforce security in database engine level — cannot in-bypass through application layer.
  • Redshift Row-Level Security (RLS) policies transparently filter rows at query execution time: (1) CREATE RLS POLICY tenant_isolation WITH (tenant_id int) USING (tenant_id = current_setting('app.tenant_id')::int); (2) ATTACH RLS POLICY tenant_isolation ON sales TO ROLE tenant_analyst; (3) ALTER TABLE sales ROW LEVEL SECURITY ON; When tenant analyst runs SELECT * FROM sales, Redshift automatically appends WHERE tenant_id = {their_tenant_id}. Advantages: Database-enforced (cannot bypass), transparent to queries (no application changes needed), works with any SQL client, auditable, cannot be accidentally removed by developers. Session variable (SET app.tenant_id) in-set when connection establishment.
  • Redshift provides system tables/views for permission auditing: pg_catalog.pg_user: Lists all database users (usename, usesysid, usesuper). pg_catalog.pg_group: Shows group names and member user IDs (groname, grolist). SVV_RELATION_PRIVILEGES: Shows effective permissions on tables/views — includes: identity_name (user/role), identity_type, relation_name, privilege_type. Additional useful views: SVV_ROLE_GRANTS: Shows role hierarchy and membership, HAS_TABLE_PRIVILEGE(): Function to check specific user's access, pg_catalog.pg_namespace: Schema information. Example audit query: SELECT u.usename, g.groname, rp.relation_name, rp.privilege_type FROM pg_user u LEFT JOIN pg_group g ON u.usesysid = ANY(g.grolist) JOIN svv_relation_privileges rp ON rp.identity_name = u.usename WHERE rp.namespace_name = 'finance'.
  • RDS IAM Database Authentication requires configuration in multiple layers: Step 1 — RDS Instance: Modify DB instance → Enable IAM DB Authentication. Step 2 — Database level: CREATE USER lambda_app WITH LOGIN; GRANT rds_iam TO lambda_app; (rds_iam role indicates user authenticates via IAM). Step 3 — IAM Policy: Allow rds-db:connect on resource "arn:aws:rds-db:region:account:dbuser:dbi-resource-id/lambda_app". Step 4 — Application code: token = rds_client.generate_db_auth_token(DBHostname, Port, DBUser); Connect uses token as password (valid 15 minutes). Benefits: No persistent passwords, token auto-expires, leverages IAM for centralized access control, integrates with CloudTrail.
  • Redshift permission evaluation: Permissions from groups and individual users dievaluasi in a ADDITIVE (union). REVOKE on user level only deletes permissions that directly granted to user said — TIDAK deletes permissions that inherited from group membership. In case this: john's effective permissions = (permissions from group "analytics") UNION (direct user permissions) - (direct user revocations). Because SELECT didapat from GROUP (not direct grant), REVOKE from user not affects. For correct-correct block john from revenue_table: (1) Remove john from group "analytics", ATAU (2) REVOKE SELECT on table from GROUP "analytics" and buat group new without table said, ATAU (3) Gunakan RLS policy for deny access. This different from IAM where explicit Deny SELALU wins.
  • Dua GRANT statements is required for cover existing + future objects: (1) GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO ROLE bi_readonly — Provides SELECT on all tables that ALREADY EXIST when statement is run. (2) ALTER DEFAULT PRIVILEGES IN SCHEMA analytics GRANT SELECT ON TABLES TO ROLE bi_readonly — Mendefinisikan that each table NEW that is created in schema "analytics" will automatic mendapat GRANT SELECT to bi_readonly role. Without ALTER DEFAULT PRIVILEGES, each table new requires manual GRANT. Also is required: GRANT USAGE ON SCHEMA analytics TO ROLE bi_readonly (so that can "see" schema).
  • Redshift supports IAM-federated access through GetClusterCredentials API: Flow: (1) User authenticates via SAML/SSO → assumes IAM role, (2) Application calls redshift:GetClusterCredentials with parameters: DbUser (database username), DbGroups (Redshift groups to join), AutoCreate (auto-create user if not exists), (3) API returns temporary database credentials, (4) User connects to Redshift — automatically member of specified DbGroups. IAM Policy controls: IAM policy on role determines WHICH DbUsers and DbGroups the federated user can request (via conditions). Redshift database permissions: Groups in Redshift have pre-configured GRANT permissions. Mapping: IAM Role "analysts-role" → allowed DbGroups: ["analytics_readonly"] → Redshift group "analytics_readonly" has SELECT on analytics schema.
  • Complete remediation approach: Immediate: ALTER USER contractor_user DISABLE; — prevents any new connections. Existing active sessions: SELECT pg_terminate_backend(pid) for kill active sessions. Also: REVOKE ALL ON ALL TABLES IN SCHEMA ... FROM contractor_user; for remove all permissions. Audit: STL_CONNECTION_LOG — shows all connections: login time, source IP, success/failure. STL_QUERY — shows all SQL executed by the user (full query text, timestamps, tables accessed). STL_QUERYTEXT — for queries that too panjang. SVL_STATEMENTTEXT — comprehensive statement log. Prevention: Migrate to IAM-based authentication via GetClusterCredentials. When contractor's IAM access is revoked (role assumption removed), they cannot generate DB credentials. Temporary credentials expire automatically (default 15 min - 3600 sec configurable).
  • Schema-level isolation uses precise GRANT statements: ETL Role: GRANT USAGE ON SCHEMA raw, staging TO ROLE etl_role; GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA raw TO ROLE etl_role; GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA staging TO ROLE etl_role; (NO grants on presentation schema — implicit deny). Transformation Role: GRANT USAGE ON SCHEMA raw, staging, presentation TO ROLE transform_role; GRANT SELECT ON ALL TABLES IN SCHEMA raw TO ROLE transform_role; GRANT ALL ON ALL TABLES IN SCHEMA staging, presentation TO ROLE transform_role; BI Role: GRANT USAGE ON SCHEMA presentation TO ROLE bi_role; GRANT SELECT ON ALL TABLES IN SCHEMA presentation TO ROLE bi_role; (Only USAGE + SELECT on presentation — cannot see raw/staging schemas). Key: USAGE permission on schema is required first — without it, user cannot even list objects.

Common Misconceptions & Pitfalls

  • Expensive and data duplication needed.
  • Massive security risk, no audit trail per-user, violates least privilege.
  • Query engine feature not access control mechanism.
  • Requires application changes and JOIN complexity.
  • Shows NULL but user TAHU column exists — may not compliant with regulations that requires "no access".
  • Works as alternative approach — CREATE VIEW patient_safe AS SELECT patient_id, name, appointment_date FROM patients — but user still needs is prevented access to base table directly. Views + column-level grants can dikombinasikan for defense-in-depth.
  • Works but 200 schemas = management nightmare, schema DDL changes must in-replicate 200x.
  • Can be bypassed if user gains direct table access.
  • Evaluates cluster-level configuration, not database-internal permissions.
  • Shows query history not permissions.
  • Shows API calls to Redshift service but TIDAK in-database SQL permissions.
  • AmazonRDSFullAccess grants RDS API permissions (CreateDB, etc.), NOT database-level connectivity.
  • RDS Proxy supports IAM auth but database-level GRANT rds_iam still needed.
  • Correct conclusion but wrong reasoning.
  • Incorrect — Redshift not IAM (no explicit deny concept in database permissions).
  • No error, just evaluated as described.
  • Provides CREATE, DROP, dll — violates read-only requirement.
  • Mengizinkan melihat schema but not SELECT from tables.
  • Only cover existing tables — future tables won't be accessible.
  • Doesn't scale for federation.
  • Incorrect — federated users get permissions based on DbGroups, not superuser.
  • S3 policies irrelevant for Redshift database access.
  • Passwords may not have expiry set.

  • Is good defense-in-depth addition but doesn't fully address schema isolation requirements.
