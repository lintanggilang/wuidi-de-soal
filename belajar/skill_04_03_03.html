Key Points

  • Cross-account encrypted S3 access requires THREE aligned policies: Policy 1 — Account A KMS Key Policy: {"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::AccountB:role/GlueJobRole"}, "Action": ["kms:Decrypt", "kms:DescribeKey"], "Resource": "*"}. Note: Resource "*" in key policy means "this key" (key policies are self-referential). Policy 2 — Account A S3 Bucket Policy: {"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::AccountB:role/GlueJobRole"}, "Action": ["s3:GetObject"], "Resource": "arn:aws:s3:::bucket-name/*"}. Policy 3 — Account B IAM Policy (on Glue role): {"Effect": "Allow", "Action": ["s3:GetObject"], "Resource": "arn:aws:s3:::bucket-name/*"}, {"Effect": "Allow", "Action": ["kms:Decrypt", "kms:DescribeKey"], "Resource": "arn:aws:kms:region:AccountA:key/key-id"}. Why all three needed: Cross-account S3: requires BOTH bucket policy (resource-based) AND IAM policy (identity-based). Cross-account KMS: requires BOTH key policy (resource-based) AND IAM policy (identity-based). Missing KMS key policy → Decrypt fails even with IAM Allow. Missing IAM kms:Decrypt → can't call KMS even if key policy allows.
  • Organization-based KMS key policy for scalable cross-account access: Key Policy: {"Effect": "Allow", "Principal": {"AWS": "*"}, "Action": ["kms:Decrypt", "kms:DescribeKey", "kms:GenerateDataKey"], "Resource": "*", "Condition": {"StringEquals": {"aws:PrincipalOrgID": "o-abc123def4"}}}. How it works: Principal "*" = any AWS principal. Condition limits to ONLY principals within Organization o-abc123def4. Any account added to the Organization automatically gets access. Any account removed from the Organization automatically loses access. Scale: ONE policy statement covers ALL 50 accounts (and future accounts). No key policy size concerns. No individual ARN management. Additional control layers: Consumer accounts still need IAM policies granting kms:Decrypt (defense in depth). Can combine with aws:PrincipalOrgPaths condition to restrict to specific OUs. SCP can further restrict which accounts/roles can call kms:Decrypt.
  • Cross-account copy with different KMS keys requires dual key permissions: Process during S3 CopyObject: (1) S3 reads source object → needs kms:Decrypt on SOURCE key (Account A's CMK). (2) S3 prepares to write to destination → needs kms:GenerateDataKey on DESTINATION key (Account B's CMK). (3) In memory: source decrypted → immediately re-encrypted with new data key from destination CMK. (4) Re-encrypted object written to destination bucket. Required permissions on the copying principal: {"Effect": "Allow", "Action": "kms:Decrypt", "Resource": "arn:aws:kms:region:AccountA:key/source-key-id"}, {"Effect": "Allow", "Action": "kms:GenerateDataKey", "Resource": "arn:aws:kms:region:AccountB:key/dest-key-id"}, {"Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::source-bucket/*"}, {"Effect": "Allow", "Action": "s3:PutObject", "Resource": "arn:aws:s3:::dest-bucket/*"}. Key point: Objects encrypted with SSE-S3 (AWS managed) CAN be copied cross-account without KMS permissions. ONLY SSE-KMS encrypted objects require explicit KMS cross-account permissions.
  • Redshift data sharing encryption behavior: How it works: Producer creates datashare: CREATE DATASHARE my_share; ALTER DATASHARE my_share ADD SCHEMA public; ALTER DATASHARE my_share ADD ALL TABLES IN SCHEMA public; GRANT USAGE ON DATASHARE my_share TO ACCOUNT 'AccountB-id'; Consumer creates database from share: CREATE DATABASE shared_db FROM DATASHARE my_share OF ACCOUNT 'AccountA-id' NAMESPACE 'producer-namespace'; Encryption handling: Producer's data encrypted with Producer's KMS key — unchanged. Consumer queries shared data through Redshift's internal protocol. Redshift service handles decryption transparently. Consumer does NOT need kms:Decrypt on producer's key. Consumer's local queries on shared data are processed by producer cluster. Key distinction from S3 cross-account: Unlike S3 cross-account access where the consumer needs direct KMS key access, Redshift data sharing abstracts the encryption layer entirely. This is because: Data stays on producer cluster storage. Consumer sends queries that execute on producer's compute (for shared data). Results returned to consumer already decrypted by producer's infrastructure. Requirements: Both clusters must be encrypted (can be different keys). Both must be in same region (or use cross-region data sharing which has additional requirements).
  • S3 CRR with KMS encryption requires destination-region key configuration: Option 1 — Multi-Region Keys (MRK): Create MRK in us-east-1 (primary key). Replicate to eu-west-1 (replica key). Same key ID prefix (mrk-xxx) in both regions. CRR can use the replica key transparently. Advantage: Same logical key, simplified management. Option 2 — Different Keys (most common): CRR replication rule specifies destination encryption: "Destination": {"Bucket": "arn:aws:s3:::dr-bucket", "EncryptionConfiguration": {"ReplicaKmsKeyID": "arn:aws:kms:eu-west-1:account:key/dest-key-id"}}. Replication Role Permissions: kms:Decrypt on source key (us-east-1): decrypt source objects. kms:Encrypt on destination key (eu-west-1): re-encrypt for destination. s3:GetObject on source bucket. s3:ReplicateObject on destination bucket. Process: CRR reads object → decrypts with source key → transmits → re-encrypts with destination key → stores in destination bucket. Key constraint: KMS keys are REGIONAL — a us-east-1 key cannot be used directly in eu-west-1. Must use multi-region key OR specify a different destination key.
  • Lake Formation cross-account sharing with encrypted data: Architecture: Account A (Data Owner): S3 bucket encrypted with CMK-A. Lake Formation registered location with DataAccessRole-A. DataAccessRole-A has: s3:GetObject + kms:Decrypt on CMK-A. Lake Formation GRANT to Account B. Account B (Consumer): Creates resource link to shared database. User queries via Athena. Query Flow (with credential vending): (1) Account B user runs Athena query on resource link. (2) Athena contacts Lake Formation for data access. (3) Lake Formation (Account A) verifies Account B has GRANT. (4) Lake Formation vends TEMPORARY credentials from DataAccessRole-A. (5) Athena uses vended credentials to: Read S3 objects (s3:GetObject — via DataAccessRole-A). Decrypt data (kms:Decrypt on CMK-A — via DataAccessRole-A). (6) Results returned to Account B user. Key insight: Account B NEVER needs direct KMS key access. Lake Formation's credential vending abstracts encryption completely. Account A maintains full control over who accesses data AND keys. This is fundamentally different from direct S3 cross-account access (where consumer needs both S3 + KMS permissions).
  • Organization-wide centralized encryption enforcement: Component 1 — Central KMS Key (Security Account): Key policy allows Organization-wide access: {"Principal": {"AWS": "*"}, "Action": ["kms:Decrypt", "kms:GenerateDataKey", "kms:DescribeKey"], "Condition": {"StringEquals": {"aws:PrincipalOrgID": "o-orgid"}}}. Central team controls key policy, rotation, enable/disable. Component 2 — SCP (Enforcement): {"Effect": "Deny", "Action": "s3:PutObject", "Resource": "*", "Condition": {"StringNotEqualsIfExists": {"s3:x-amz-server-side-encryption-aws-kms-key-id": "arn:aws:kms:region:security-account:key/central-key-id"}}}. No member account can upload to ANY S3 bucket without using the central key. Account admins CANNOT override SCPs. Component 3 — AWS Config (Detection): Organization-wide config rule: s3-bucket-default-encryption-kms check. Auto-remediation: update bucket default encryption to central key. Dashboard showing compliance status across all accounts. Component 4 — Bucket Default Encryption: Set via CloudFormation StackSets across all accounts: default encryption = central KMS key. Even if user doesn't specify encryption header, default kicks in.
  • Common cross-account troubleshooting: misleading error from KMS denial: The confusing part: Error says "AccessDenied on GetObject" — but the ACTUAL cause is KMS Decrypt failure. S3 doesn't differentiate between "you can't access the bucket" vs "you can't decrypt the object" in its error message. Both show as AccessDenied. Debugging approach: (1) Check CloudTrail in Account A for kms:Decrypt events → look for denied calls. (2) Verify KMS key policy includes Account B's role. (3) Verify Account B's IAM policy includes kms:Decrypt on Account A's key ARN. Fix: Account A KMS key policy ADD: {"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::AccountB:role/user-role"}, "Action": "kms:Decrypt", "Resource": "*"}. Account B IAM policy ADD: {"Effect": "Allow", "Action": "kms:Decrypt", "Resource": "arn:aws:kms:region:AccountA:key/key-id"}. Important note: If bucket uses SSE-S3 (not SSE-KMS): No KMS policy needed — S3 handles decryption internally. Cross-account access only needs S3 bucket policy + IAM policy. The SSE-KMS vs SSE-S3 distinction is critical for cross-account scenarios.
  • Cross-account, cross-region re-encryption workflow: Scenario complexity: Different account (A → B) + different region (us-east-1 → eu-west-1) + different key. Solution 1 — S3 CRR (automated): Configure CRR on Account A's source bucket: Destination: Account B's bucket in eu-west-1. ReplicaKmsKeyID: Account B's eu-west-1 key ARN. Replication role needs: kms:Decrypt on Account A key (us-east-1) + kms:Encrypt on Account B key (eu-west-1). Solution 2 — Glue/Lambda job: Read from Account A bucket → decrypt with Account A key. Write to Account B bucket → encrypt with Account B key. Job's IAM role needs cross-account, cross-region KMS permissions. Solution 3 — KMS ReEncrypt API (.
  • KMS Grants vs Key Policies for cross-account access: KMS Grants characteristics: Temporary: Created programmatically, retired when no longer needed. Scoped: Specific operations (Decrypt, GenerateDataKey, CreateGrant, etc.). Constrained: Can require specific encryption context. Delegatable: Grantee can create sub-grants (with CreateGrant permission). Not subject to key policy 32KB limit. Eventually consistent (slight delay after creation). Create Grant example: aws kms create-grant --key-id key-arn --grantee-principal arn:aws:iam::AccountB:role/PipelineRole --operations Decrypt DescribeKey --constraints EncryptionContextSubset={project=data-lake}. When to use Grants vs Key Policy: Use GRANTS when: Access is temporary (project-based, time-limited). Programmatic management needed (automation creates/retires). Many consumers (avoids key policy size limit). Service integration (AWS services use grants automatically). Use KEY POLICY when: Permanent, stable access (organizational access). Small number of principals. Want immediate consistency (grants are eventually consistent). Need to see all permissions in one document.

Common Misconceptions & Pitfalls

  • KMS access NEVER inherited from S3 permissions.
  • VPC peering irrelevant for S3/KMS API calls.
  • KMS keys cannot be copied/replicated between accounts.
  • KMS keys don't have "credentials" to share, conceptually wrong.
  • Removes security for convenience, unacceptable.
  • 50 keys = 50× management overhead, cost, rotation complexity.
  • Keys are completely independent; re-encryption handles transition.
  • "automatic" only for SSE-S3, NOT for SSE-KMS with CMK.
  • No intermediate plaintext storage needed; happens in-process.
  • Works with encrypted clusters.
  • CRR fully supports encrypted destinations.
  • Manual key material export/import is complex and creates independent keys (not replicas).
  • Single-region keys are region-specific, won't work cross-region.
  • Not needed due to credential vending model.
  • Fully supported with registered locations.
  • SSE-S3 ≠ customer managed key, no central control.
  • Cross-account KMS sharing is fully supported.
  • Independent keys aren't centrally managed.
  • Aws s3 cp works cross-account with proper permissions.
  • Transfer Acceleration unrelated to permissions.
  • S3 fully supports cross-account.
  • ): Note: ReEncrypt API EXISTS but works only within SAME region and requires both keys accessible to the caller. Does NOT work cross-region. Data MUST pass through KMS (4KB limit) — not suitable for large objects (only for envelope encrypted data keys). For S3 objects: decrypt-then-encrypt is the correct pattern (envelope encryption means you're actually re-encrypting the data key, not the full object through KMS).
  • KMS keys cannot be "transferred" between regions.
  • Double encryption is not a standard pattern and adds complexity without benefit.
  • Grants work cross-account (specify cross-account principal ARN).
  • Grants CAN be retired/revoked (RevkeGrant or RetireGrant).
  • Grants allow cryptographic operations.
