Key Points

  • The EvaluateDataQuality transform in Glue supports inline quality evaluation during ETL processing. It can be configured with row-level outcomes that route failing rows to a quarantine path while allowing passing rows to continue processing. This implements a "dead letter" pattern for data quality without stopping the pipeline. Option B: A simple Filter removes bad rows but doesn't capture them for investigation or provide structured quality metrics; it's a basic approach without proper quality governance. Option C: Running quality checks separately (before ETL) means the actual data being processed might differ from what was checked, and it doesn't handle the quarantine pattern. Option D: Glue crawlers discover schemas; they don't enforce data quality rules or filter records.
  • For streaming ETL with strict latency requirements, implementing validation as native DataFrame/DynamicFrame operations (null checks, type validations, range checks) adds minimal overhead because these operations are executed within the existing Spark DAG without additional shuffles or I/O. They leverage Spark's in-memory processing and don't require external service calls. Option B: EvaluateDataQuality with statistical rules (like distribution analysis) on every micro-batch adds significant computation overhead that could exceed the 5% latency budget. Option C: Lambda invocation per record introduces network latency, serialization overhead, and Lambda concurrency limits at 10M records/hour. Option D: Sampling misses quality issues in the unsampled 90%, which is unacceptable when the requirement is to ensure no bad records reach the destination.
  • EvaluateDataQuality supports configurable actions on rule failure, including stopping the job (rejecting the batch). The publishResults parameter sends quality metrics to CloudWatch, providing the documented quality assessment required by regulations. Combined with CloudWatch Alarms and SNS, this creates a complete quality gate with alerting. Option B: Custom code works but lacks the structured quality reporting, metadata capture, and integration with Glue's quality framework needed for regulatory documentation. Option C: Processing first then validating violates the "check during processing" principle and risks downstream consumers seeing bad data before deletion. Option D: Glue Data Quality recommendations suggest rules based on data profiling but don't enforce hard regulatory thresholds; ML-based anomaly detection may not meet the precise 0.1% requirement.
  • For complex type validation with quarantine routing at the record level, a custom Map.apply() function provides the most precise control. The try-except pattern attempts conversion and catches failures per-record, allowing you to tag or route individual failing records. This handles edge cases like "N/A", empty strings, and malformed numbers that need record-level decisions. Option A: ResolveChoice with "cast" converts incompatible values to null, but doesn't distinguish between legitimately null source values and failed conversions—you lose the ability to differentiate original nulls from conversion failures. Option B: ColumnDataType in DQDL checks the column's declared type in the schema, not the actual parsability of string values. Option C: Relationalize flattens nested structures; it doesn't perform intelligent type conversion or quarantine non-convertible values.
  • EvaluateDataQuality natively supports publishing quality evaluation results to CloudWatch metrics when configured with the appropriate output options. Using custom dimensions (job name, source system, rule name) enables slicing metrics across all 50 sources in a unified CloudWatch dashboard. This approach requires no custom code, scales automatically, and integrates with CloudWatch alarming for automated alerting. Option B: DynamoDB storage works but requires custom code in every job to write structured metrics, plus additional configuration for QuickSight connectivity. Option C: S3-based metrics require custom code, manual schema management, and introduce query latency for dashboard refresh. Option D: Glue's console-based quality view shows results per job but doesn't provide a consolidated dashboard view across 50 sources with custom visualizations and alerting.
  • EvaluateDataQuality supports row-level outcomes when configured with the appropriate output mode. Each record is tagged with the results of all evaluated rules, indicating which rules passed and which failed for that specific record. This provides the per-record, per-rule granularity needed without multiple evaluation passes. Option B: Sequential filters mean a record rejected by the first rule never gets evaluated by subsequent rules, losing information about additional violations. Option C: A single SQL CASE WHEN can work but doesn't integrate with Glue's quality framework for metric publishing, doesn't handle the cross-field calculation rule elegantly, and produces custom output rather than standardized quality results. Option D: Running quality evaluation four times quadruples processing time and requires deduplication logic to merge results.
  • MERGE INTO (upsert) on an Iceberg table provides exactly-once semantics by matching on the primary key: new records are inserted, and duplicates of existing records trigger an update (or are skipped with WHEN MATCHED THEN UPDATE). This handles both within-batch and cross-batch duplicates atomically. Option B: dropDuplicates() only removes duplicates within the current batch; if a duplicate arrives in a later batch that matches an existing record in the table, it will create a duplicate. Option C: Apache Iceberg does not support unique constraints; it's an open table format without database-style constraint enforcement. Option D: Failing the job on duplicates doesn't solve the problem—it prevents processing entirely and requires manual cleanup.
  • A left anti-join is the correct distributed approach for referential integrity validation at scale. Spark/Glue efficiently handles the join between 5M orders and 10M customers using distributed hash joins or sort-merge joins, identifying orders with no matching customer. The anti-join result contains only the violating records for flagging. Option B: Per-record DynamoDB lookups for 5 million records would be extremely slow, expensive (5M read capacity units), and create a bottleneck. Option C: While Glue Data Quality supports ReferentialIntegrity rules in DQDL, it evaluates at the dataset level and may not efficiently handle the specific flagging-without-blocking requirement with custom exception routing. Option D: Loading 10 million customer IDs into a Python set (~400 MB) may exceed driver memory limits and doesn't leverage distributed processing.
  • Sequential EvaluateDataQuality transforms within a single Glue job provide the progressive gate behavior. Each transform evaluates its ruleset and the StopJobOnFailedRules action halts execution if the threshold isn't met, preventing downstream stages from running. This keeps all logic in a single job for simplicity, shared DynamicFrame context, and no inter-job data transfer overhead. Option B: Three separate jobs add orchestration complexity, require data serialization/deserialization between jobs, and increase total execution time due to job startup overhead. Option C: Combining all rules with averaged thresholds loses the progressive gate behavior—a critical schema failure might be masked by high pass rates in other categories. Option D: Glue workflow conditional triggers can check job status but not granular quality metric thresholds without custom Lambda integration.
  • Statistical checks (standard deviation, mean, distribution analysis) require full dataset scans and aggregation operations—they're computationally expensive. Lightweight checks (null validation, type checks) execute as simple per-row operations within the existing processing DAG with minimal overhead. Separating expensive checks to post-processing maintains quality coverage while reducing inline overhead to near-zero for simple validations. Option B: More DPUs help with data parallelism but statistical aggregations require shuffles regardless of parallelism level; the overhead ratio remains similar. Option C: Removing all inline checks means bad data reaches the target before being detected, violating the "check during processing" requirement. Option D: Caching 500 GB in memory would require enormous memory allocation and may cause OOM errors; the quality check overhead comes from computation, not I/O.
