Skill 2.4.5: Indexing, partitioning, compression

indexingpartitioningcompression

Ringkasan

Skill ini termasuk dalam Domain 2: Data Store Management (Task 2.4: Design data models and schema evolution), dengan fokus pada indexing, partitioning, compression. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Partition projection
Fitur Athena yang menghitung partisi dari pola tanpa memanggil metastore, mempercepat query.

Poin-Poin Kunci

  • Partitioning berdasarkan year/month/day/region adalah strategi optimal karena sesuai dengan pola query yang menggunakan filter transaction_date dan region. Hierarki date-first memungkinkan partition pruning yang efektif karena date range queries sangat umum.
  • Compound sort key (order_date, customer_id) adalah pilihan terbaik karena order_date sebagai kolom pertama akan sangat efektif untuk zone map filtering pada range queries yang paling sering digunakan. customer_id sebagai kolom kedua membantu merge joins dengan dimension table.
  • GSI dengan sensor_type sebagai partition key dan timestamp sebagai sort key memungkinkan query efisien berdasarkan sensor_type dengan time range filter tanpa scan seluruh tabel. GSI memberikan access pattern yang berbeda dari base table.
  • ZSTD (Zstandard) memberikan keseimbangan terbaik antara compression ratio yang tinggi (mendekati Gzip) dan kecepatan decompression yang cepat (mendekati Snappy). Untuk analytical workload dimana data dibaca berulang kali, ZSTD mengurangi storage cost sekaligus mempertahankan query performance.
  • Small file problem adalah masalah umum di data lakes. Setiap file memerlukan overhead untuk opening, reading metadata, dan closing. Menggabungkan file kecil menjadi file 128-512 MB mengurangi jumlah file operations secara drastis dan memungkinkan parallel processing yang lebih efisien.
  • VACUUM FULL melakukan dua operasi penting: (1) menghapus deleted rows (reclaim space dari tombstones) dan (2) mengurutkan ulang rows berdasarkan sort key. ANALYZE kemudian memperbarui statistics yang digunakan query optimizer. Kedua operasi ini mengembalikan performa zone maps dan query planning.
  • Z-ordering menggunakan space-filling curves untuk memetakan data multi-dimensi ke satu dimensi sambil mempertahankan locality. Ini memungkinkan data yang dekat dalam multiple dimensions (lat, long, timestamp) juga dekat secara fisik di storage, sehingga file pruning efektif untuk semua kombinasi filter.
  • Row group size 128 MB (default Parquet) memberikan keseimbangan optimal. Untuk wide tables (200 kolom) dimana hanya 5-10 kolom dibaca, row group yang cukup besar memastikan column chunks memiliki cukup data untuk sequential I/O yang efisien.
  • Ketika data baru di-load ke Redshift (via COPY atau INSERT), rows baru ditambahkan sebagai unsorted region. Zone maps pada unsorted region memiliki min/max ranges yang sangat wide, membuat data skipping tidak efektif. VACUUM SORT mengurutkan ulang data sehingga zone maps memiliki ranges yang tight dan bisa melakukan effective pruning.
  • Untuk high-cardinality columns, ORC min/max statistics (row index) tidak efektif karena setiap stripe likely memiliki wide range of user_ids. Bloom filters di ORC memberikan probabilistic test yang dapat menentukan apakah suatu stripe definitely doesn't contain a specific user_id, enabling effective data skipping untuk equality predicates.

Miskonsepsi & Jebakan Umum

  • Menghasilkan terlalu banyak partisi kecil (high cardinality) yang justru menurunkan performa.
  • Menempatkan region di level pertama, yang kurang optimal jika date queries lebih sering.
  • Tanpa partitioning akan selalu melakukan full scan.
  • Memberikan equal weight ke semua kolom, tapi memerlukan VACUUM REINDEX yang mahal dan kurang efisien ketika satu kolom (order_date) dominan di-filter.
  • Tidak optimal untuk workload yang diketahui pola query-nya.
  • Mengabaikan order_date yang merupakan filter utama.
  • Mengubah base table akan merusak access pattern existing.
  • Menggunakan timestamp sebagai partition key yang akan menghasilkan hot partitions.
  • Tidak bisa digunakan karena LSI harus memiliki partition key yang sama dengan base table (device_id), sehingga tetap perlu query per device.
  • Sudah less common dan tidak optimal dibandingkan ZSTD.
  • Tercepat untuk decompress tapi compression ratio lebih rendah, meningkatkan scan volume dan cost.
  • Memiliki compression ratio tertinggi tapi decompression yang lambat, meningkatkan query latency.
  • Akan memperburuk masalah dengan lebih banyak directory listings.
  • Justru lebih buruk karena kehilangan columnar benefits.
  • Meningkatkan biaya tanpa menyelesaikan root cause — overhead per-file tetap ada.
  • Bisa berhasil tapi lebih disruptive dan memerlukan downtime lebih lama.
  • Tidak mengatasi unsorted rows dan tombstones.
  • Meningkatkan biaya tanpa menyelesaikan root cause data organization.
  • Membantu tapi tanpa Z-ordering, data mungkin tersebar acak sehingga min/max ranges overlap.
  • Menyebabkan partition explosion karena kombinasi ranges yang banyak.
  • Hanya membantu spatial queries tapi tidak mengoptimalkan temporal dimension secara bersamaan.
  • Terlalu besar, memerlukan memory berlebihan dan membuat predicate pushdown kurang granular.
  • Terlalu kecil — column chunks hanya ~40 KB per kolom, menghasilkan banyak random I/O.
  • Sangat kecil, setiap column chunk hanya ~160 bytes yang tidak efisien untuk I/O.
  • Salah — compound sort keys bekerja sangat baik dengan zone maps, terutama untuk kolom pertama.
  • Salah — LIKE dengan prefix bisa leverage zone maps.
  • Salah — zone maps bekerja dengan VARCHAR.
  • Salah — kedua format mendukung predicate pushdown, tapi ORC memiliki Bloom filter built-in.
