Key Points

  • HNSW is the optimal choice for this workload profile: (1) consistently low query latency — HNSW provides O(log N) search complexity through its hierarchical graph structure, easily achieving sub-100ms for 10M vectors; (2) high recall — with properly tuned ef_search parameters, HNSW typically achieves 95-99% recall, well within the 5% tolerance; (3) read-heavy optimization — HNSW's pre-built graph structure makes queries extremely fast, and since catalog updates are weekly, the higher index build time is acceptable; (4) pgvector supports HNSW natively with CREATE INDEX ... USING hnsw.
  • IVF is the preferred choice for high-ingestion, memory-constrained environments: (1) ingestion speed — inserting a vector into IVF requires computing distance to centroids only (not updating neighbor connections like HNSW), making insertions O(k) where k = number of clusters, not O(M × log N) like HNSW graph updates; (2) memory efficiency — IVF stores a centroid table + inverted lists (vector assignments), consuming significantly less memory per vector than HNSW's multi-layer neighbor adjacency lists (which store M connections per vector per layer); (3) for 500M vectors at 256 GB RAM, IVF with quantization (IVF-PQ) can compress vectors while IVF structure provides search partitioning; (4) OpenSearch k-NN supports IVF natively via the Faiss engine.
  • HNSW with tuned parameters provides the optimal balance of high recall and acceptable latency: (1) ef_construction=512 builds a denser graph — each node maintains connections to more neighbors, creating more paths to find relevant results; (2) ef_search=200 means the query explores 200 candidates during traversal (vs. default 40), dramatically increasing the probability of finding all 99% of true nearest neighbors; (3) at 5 million vectors and 500ms budget, HNSW with these parameters typically achieves 99%+ recall while staying within latency bounds; (4) the trade-off is ~4× slower index build and ~3× slower queries compared to defaults — but both remain acceptable (build once for static corpus, 500ms query budget is generous).
  • Reducing M and applying quantization are the two primary levers for HNSW memory reduction: (1) HNSW graph memory is proportional to M (connections per layer) — reducing M from 16 to 8 cuts graph adjacency list memory by ~50%; the trade-off is slightly lower recall, compensated by increasing ef_search at query time; (2) Product Quantization compresses each 768/1536-dimensional float32 vector from thousands of bytes to 64-128 bytes of quantized codes — a 75-90% reduction in vector storage; (3) combined effect on 180 GB: graph reduction (90 GB) + vector quantization (potentially 120 GB → 30 GB) achieves the 60% target. OpenSearch k-NN supports both M parameter tuning and PQ encoding via the Faiss engine.
  • Dimensionality reduction directly attacks the root cause — expensive high-dimensional distance computations: (1) distance computation is O(d) where d = dimensions; reducing from 2,048 to 256 makes each distance computation 8× faster; (2) PCA is the standard preprocessing step that identifies dimensions contributing most to variance — for learned embeddings like ResNet, the top 256 principal components typically capture 90-95% of the discriminative information; (3) index build time, memory consumption, and query latency all improve proportionally to the dimension reduction; (4) the reduced vectors are indexed normally with HNSW, benefiting from both faster distance computation AND smaller graph structure.
  • OpenSearch provides the complete feature set for multi-modal search: (1) k-NN plugin supports both HNSW and IVF indexes for vector similarity on text AND image embeddings; (2) native Lucene-based full-text search with BM25 scoring for keyword matching; (3) efficient metadata filtering using OpenSearch's inverted indexes (brand, category as keyword fields, price as numeric range); (4) hybrid queries combine all three signal types in a single request using script_score or neural search plugin; (5) the rescore API and normalization processors allow tuning the blend of vector similarity + text relevance + filter scores; (6) managed service handles scaling to 20M vectors.
  • The sqrt(N) heuristic for nlist is a well-established starting point for IVF configuration: (1) nlist = sqrt(200M) ≈ 14,142 creates clusters of manageable size (~14,000 vectors); too few clusters means each cluster is too large (slow exhaustive search within cluster); too many means cluster centroids poorly represent their members (low recall); (2) nprobe directly controls the recall-latency trade-off: searching more clusters finds more true neighbors but takes proportionally longer; (3) with distinct domains (electronics, clothing, etc.), embeddings from the same domain cluster tightly together, meaning the correct cluster is usually found with moderate nprobe values; (4) practical tuning: start with nprobe=sqrt(nlist)≈120, then adjust based on measured recall.
  • HNSW with pgvector is the optimal configuration for this RAG use case: (1) 2M vectors with HNSW provides consistent sub-50ms latency for top-20 retrieval — HNSW's graph traversal is highly efficient at this scale; (2) pgvector integrates with standard PostgreSQL WHERE clauses, enabling filtered vector search (e.g., ORDER BY embedding query_vector WHERE category = 'legal' AND date > '2024-01-01'); (3) partial indexes (CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops) WHERE access_level = 'public') create separate HNSW graphs for high-value filter categories, providing filtered search without post-filtering recall loss; (4) daily batch updates are well-suited to HNSW which handles periodic bulk insertions efficiently.
  • For operational data engineering, the write/update pattern is typically the most impactful architectural decision: (1) 100,000 daily insertions into HNSW requires 100,000 graph update operations — each insertion traverses the graph to find connection points and updates neighbor lists at potentially multiple layers; this can degrade index quality over time if not periodically rebuilt; (2) IVF insertion is trivially cheap — compute distance to cluster centroids, assign to nearest cluster, append to inverted list; (3) HNSW's query advantage (2% recall, 3ms latency) may not justify the operational complexity of maintaining a graph-based index under continuous writes; (4) IVF cluster centroids remain stable across insertions (periodic re-clustering needed only when data distribution shifts significantly). The choice is fundamentally about operational sustainability, not peak performance.
  • REINDEX CONCURRENTLY is the correct maintenance pattern for HNSW indexes under update workloads: (1) HNSW graph quality degrades when nodes are updated (deleted + re-inserted) because the new node's connections may be suboptimal — it connects to current neighbors that may not be the globally best connections; (2) REINDEX rebuilds the entire graph from scratch, re-establishing optimal connectivity across all nodes; (3) CONCURRENTLY ensures the rebuild happens in the background without blocking the recommendation API's read queries; (4) weekly scheduling aligns with the embedding pipeline cadence — rebuild after new vectors are loaded. The pattern: upsert 1M vectors → REINDEX CONCURRENTLY → latency returns to 10ms baseline.

Common Misconceptions & Pitfalls

  • Brute-force search on 10 million 768-dimensional vectors would take 500ms-2s per query, far exceeding the 100ms requirement, and cannot sustain 1,000 QPS.
  • B-tree indexes don't support similarity/distance operations; they can only do exact value matches, which is meaningless for embedding vector similarity search.
  • IVF is viable but provides less consistent latency than HNSW; IVF's recall depends heavily on the nprobe parameter (number of clusters searched), and achieving 95% recall at 1,000 QPS may require probing many clusters, increasing latency. IVF is better suited for scenarios where memory is constrained or rapid index builds are needed.
  • Flat indexes don't use specialized data structures and require loading all vectors for search; S3-backed storage would make 200ms queries impossible due to I/O latency.
  • HNSW provides excellent query latency but requires ~4× more memory per vector (storing neighbor lists) and has slower insertions (graph updates require connecting to M neighbors); at 500M vectors with 256 GB limit, HNSW likely exceeds memory.
  • PQ alone compresses vectors but doesn't provide a search structure; without IVF partitioning, the system must still compare against all 500M compressed vectors (too slow at 200ms target).
  • IVF with nprobe=1 searches only the single nearest cluster, providing ~50-70% recall at best; achieving 99% recall with IVF requires nprobe≈50-100 which may exceed the latency budget for 5M vectors at 1,536 dimensions.
  • Default HNSW parameters (ef_search=40) achieve approximately 90-95% recall; a re-ranking model can only re-rank the candidates already retrieved — it cannot find documents that HNSW missed entirely.
  • Brute-force on 5M vectors at 1,536 dimensions requires computing 5M distance calculations of 1,536-dimensional vectors per query; this takes 2-5 seconds on typical Aurora instances, exceeding the 500ms budget.
  • While OpenSearch supports disk-based approximate nearest neighbor search (for IVF-based indexes), HNSW is fundamentally designed as an in-memory structure; disk-based HNSW would have dramatically higher latency due to random graph traversal patterns causing many disk seeks.
  • Increasing ef_construction increases build time and memory (larger candidate lists during construction) without reducing the final graph size.
  • The distance metric doesn't affect memory consumption; it's purely a computation choice that doesn't change storage requirements.
  • Splitting vectors into sub-vectors and maintaining separate indexes creates complex query coordination, result merging challenges, and doesn't reduce total computation (same total dimensions compared across sub-indexes).
  • Flat index on 100M vectors requires computing distance against ALL vectors (even with SIMD); this would be far slower than HNSW's graph-based approach that only computes distance against ~200-400 candidates.
  • More shards distribute vectors but each shard still computes 2,048-dimensional distances; latency is bounded by the per-vector computation cost, not parallelism (at 100M vectors with HNSW, the graph traversal itself isn't the bottleneck — distance computation is).
  • Pgvector provides vector search and SQL filtering, but PostgreSQL's text search (ts_vector/ts_query) is significantly less capable than OpenSearch's BM25 for full-text relevance ranking, and hybrid scoring requires complex manual query construction; it also lacks the native score blending capabilities.
  • Lambda with brute-force search on 20M vectors would take seconds per query and cannot sustain production query volumes; this is not a viable architecture for similarity search at scale.
  • Neptune is a graph database for relationship traversal; it doesn't support vector similarity search natively and isn't designed for embedding-based search workloads.
  • 1M clusters with 200M vectors gives only ~200 vectors per cluster; clusters are so small that cluster centroids become unreliable representatives, and nprobe=1 gives very low recall because similar vectors may span many tiny clusters.
  • Nprobe=nlist means searching ALL clusters = brute-force search = no speed benefit from having an index at all.
  • Only 4 clusters for 200M vectors means each cluster contains 50M vectors; searching within a 50M-vector cluster is essentially brute-force and provides no speed benefit over a flat index.
  • IVF with pre-filtering can be effective but pgvector's IVF implementation has limitations with filtered search; applying a WHERE filter before IVF search may eliminate entire clusters, reducing effective recall significantly for selective filters.
  • Creating indexes for every combination of category × access_level leads to index explosion (potentially hundreds of indexes), excessive storage consumption, and maintenance complexity during daily updates.
  • Brute-force on 2M vectors at 1,536 dimensions requires 2M × 1,536 × 4 bytes = 12 GB of distance computations per query; on Aurora's instance types, this takes 200-500ms, exceeding the 50ms requirement.
  • Build time matters for disaster recovery but indexes are typically rebuilt rarely; daily operations dominate architectural decisions.
  • RAM is important for cost but can be addressed with instance sizing; it's a linear cost factor, not an architectural constraint.
  • 2% recall difference is relevant but can often be recovered by increasing ef_search for HNSW or nprobe for IVF without changing the fundamental architecture.
  • Autovacuum handles dead tuple cleanup (standard PostgreSQL maintenance) but does not rebuild or optimize HNSW graph connectivity; maintenance_work_mem doesn't affect index quality.
  • Switching to IVF is unnecessary; IVF does avoid graph fragmentation but has lower recall characteristics; the proper solution is maintaining HNSW quality through periodic rebuilds.
  • Increasing ef_search partially compensates (explores more candidates to find correct neighbors despite poor graph connectivity) but doesn't fix the root cause; latency will continue to degrade each week, requiring ever-higher ef_search values — an unsustainable approach.
