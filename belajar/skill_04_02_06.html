IAM Access Analyzer
Mengidentifikasi access berlebih/external and membantu menyusun policy least-privilege.

Key Points

  • Least privilege for Glue ETL requires granularitas in multiple levels: Action-level granularity: s3:GetObject (read only) — NOT s3:Get* (which includes s3:GetBucketPolicy, s3:GetEncryptionConfiguration). s3:PutObject (write) — only on output path. s3:DeleteObject — only if job overwrites/replaces output files. s3:ListBucket — needed for Spark to list partition paths, but restricted via Condition. Resource-level granularity: PREFIX restriction: arn:aws:s3:::raw-data/transactions/* — NOT arn:aws:s3:::raw-data/* (which exposes other data). ListBucket condition: {"StringLike": {"s3:prefix": ["transactions/*"]}} — prevents listing other prefixes. Supporting permissions: glue:GetTable, glue:GetDatabase — for catalog metadata reads needed by Spark. Why not others:.
  • IAM Access Analyzer policy generation workflow: Step 1 — Prerequisites: CloudTrail trail enabled with management AND data events (for S3 object-level tracking). Trail must cover sufficient time period (ideally 90+ days for full coverage of periodic jobs). Step 2 — Generate Policy: Console: IAM → Roles → Select role → "Generate policy". Specify: CloudTrail trail ARN, time period (e.g., last 90 days), region(s). Step 3 — Analysis: Access Analyzer scans CloudTrail for all API calls made by that role. Identifies: exact actions used, specific resource ARNs accessed, conditions (source IPs, request parameters). Step 4 — Output: Generated policy with ONLY used actions/resources. Example: If role only called s3:GetObject on 3 specific prefixes in 90 days, generated policy reflects exactly that. Step 5 — Human review: Generated policy is a STARTING POINT. May need additions for: infrequent operations (quarterly reports), disaster recovery actions, future growth. Critical: Don't blindly apply — review for missing edge cases.
  • Least privilege for Redshift access requires two-layer approach: Layer 1 — IAM Policy (AWS API level): {"Effect": "Allow", "Action": ["redshift-serverless:GetCredentials"], "Resource": "arn:aws:redshift-serverless:region:account:workgroup/specific-workgroup"}, {"Effect": "Allow", "Action": ["redshift-data:ExecuteStatement", "redshift-data:GetStatementResult", "redshift-data:DescribeStatement"], "Resource": "*", "Condition": {"StringEquals": {"redshift-data:workgroup-name": "specific-workgroup"}}}. NOT included: redshift-serverless:CreateWorkgroup, redshift-serverless:DeleteWorkgroup, redshift-serverless:UpdateWorkgroup (no admin actions). Layer 2 — Redshift Database Permissions: CREATE USER reporting_tool PASSWORD DISABLE; GRANT USAGE ON SCHEMA reporting TO reporting_tool; GRANT SELECT ON ALL TABLES IN SCHEMA reporting TO reporting_tool; No INSERT, UPDATE, DELETE, CREATE, DROP privileges. Combined: Even if someone modifies IAM policy, database permissions still restrict actions. Even if database permissions are broadened, IAM policy limits which AWS APIs can be called.
  • Resource-level restrictions in IAM policies for Glue catalog: Policy structure: {"Effect": "Allow", "Action": ["glue:GetDatabase", "glue:GetDatabases"], "Resource": "arn:aws:glue:us-east-1:123456789012:database/analytics_database"}, {"Effect": "Allow", "Action": ["glue:GetTable", "glue:GetTables", "glue:GetPartitions", "glue:GetPartition", "glue:BatchGetPartition"], "Resource": ["arn:aws:glue:us-east-1:123456789012:table/analytics_database/*", "arn:aws:glue:us-east-1:123456789012:catalog"]}, Catalog resource: Required for glue:GetTable calls (Glue needs catalog-level access to resolve database/table hierarchy). Database resource: Specific database ARN — cannot access marketing_database, finance_database, etc. Table resource: Wildcard within specific database — analytics_database/* allows all tables IN that database only. Key: Even if Glue job code attempts client.get_table(DatabaseName='finance_database', Name='sensitive_table') → AccessDenied at IAM level.
  • Permission Boundaries enable delegated administration with guardrails: Concept: Permission Boundary = ceiling on what a role CAN be granted. Effective permissions = Intersection of (identity policy) AND (permission boundary). Even if role has "s3:*" on "Resource":"*" in its identity policy, boundary limits actual permissions. Implementation: (1) Security team creates boundary policy: "analytics-team-boundary" → Allows: s3:GetObject/PutObject on arn:aws:s3:::analytics-*, glue:* on analytics databases, logs:CreateLogGroup/PutLogEvents. Denies: iam:*, sts:AssumeRole to other accounts, s3 access outside analytics-* prefix. (2) Team's role creation policy: {"Effect": "Allow", "Action": "iam:CreateRole", "Resource": "*", "Condition": {"StringEquals": {"iam:PermissionsBoundary": "arn:aws:iam::account:policy/analytics-team-boundary"}}}. (3) Result: Teams can create roles freely BUT every role they create is capped by the boundary. Self-service WITH guardrails.
  • Multi-dimensional least privilege policy: Service-specific actions: S3: s3:GetObject ONLY (not PutObject, DeleteObject). Comprehend: comprehend:DetectPiiEntities ONLY (not comprehend:* which includes model training). DynamoDB: dynamodb:PutItem ONLY (not GetItem, Scan, DeleteItem). Resource restrictions: S3: "arn:aws:s3:::intake-bucket/uploads/*" — only uploads prefix. Comprehend: "*" — stateless APIs don't have specific resource ARNs. DynamoDB: "arn:aws:dynamodb:region:account:table/pii-scan-results" — specific table only. Time-based condition: {"Condition": {"DateGreaterThan": {"aws:CurrentTime": "2024-01-01T08:00:00Z"}, "DateLessThan": {"aws:CurrentTime": "2024-01-01T18:00:00Z"}}}. Note: aws:CurrentTime is evaluated per-request. Better approach for Lambda: use EventBridge schedule to only trigger during business hours, and add time condition as defense-in-depth.
  • Service Control Policies (SCPs) provide organization-level guardrails: SCP Characteristics: Applied at Organization Root, OU, or Account level. CANNOT be overridden by ANY policy within member accounts. Even account root user is bound by SCPs. Acts as permission ceiling — narrows what's possible. SCP Example: {"Effect": "Deny", "Action": "s3:PutObject", "Resource": "*", "Condition": {"StringNotEquals": {"s3:x-amz-server-side-encryption": "aws:kms"}}}. Add second statement for missing header: {"Effect": "Deny", "Action": "s3:PutObject", "Resource": "*", "Condition": {"Null": {"s3:x-amz-server-side-encryption": "true"}}}. Result: ANY s3:PutObject call WITHOUT KMS encryption → DENIED. Applies to all accounts under the OU/Organization. Account admins CANNOT override (they can't modify SCPs). Why not others:.
  • Principle of least privilege = grant ONLY what is needed NOW, not what might be needed later: Crawler actual requirements: glue:CreateTable — creates new tables when new data sources found. glue:UpdateTable — updates schema when source structure changes. glue:GetTable, glue:GetDatabase — reads existing metadata. glue:CreatePartition, glue:BatchCreatePartition — adds new partition metadata. glue:UpdatePartition, glue:BatchUpdatePartition — updates existing partitions. s3:GetObject, s3:ListBucket — reads actual data files. logs:CreateLogGroup, logs:PutLogEvents — writes CloudWatch logs. NOT needed: glue:DeleteTable — crawler doesn't delete tables (even when source removed, table metadata remains). glue:CreateDatabase — database should be pre-created by admin; crawler discovers tables WITHIN existing database. glue:DeleteDatabase — destructive, never needed for crawling. Refinement principle: Start with what's needed → add ONLY when use case demands. "Future use" = over-provisioning = security risk.
  • Access Analyzer generated policies are a starting point, not a final product: Known limitation: Access Analyzer only sees what WAS done — not what SHOULD be done. 30-day window may miss: quarterly reports, annual compliance jobs, disaster recovery procedures, seasonal data processing. Recommended workflow: (1) Generate baseline policy from CloudTrail (best starting point). (2) Review operational documentation: quarterly ETL runs, year-end processing, periodic data migrations. (3) Add missing permissions for known-but-infrequent operations. (4) Deploy policy with monitoring: CloudWatch Alarm on CloudTrail "errorCode=AccessDenied" for the role. SNS notification when access denied occurs. Rapid response process to add missing permissions. (5) Iterate: After a full annual cycle, re-generate to capture everything. Avoid: Waiting 365 days (C) — too long with overly permissive policy in place. Adding wildcards (D) — defeats the purpose of least privilege. Discarding (A) — wastes valuable baseline data. Key: Least privilege is ITERATIVE, not one-time.
  • Cross-account least privilege requires policies on BOTH sides: Account A — Glue Job Role (Identity Policy): {"Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::account-b-bucket/shared-prefix/*"} — specific prefix, not entire bucket. {"Effect": "Allow", "Action": ["redshift-data:ExecuteStatement", "redshift-data:GetStatementResult"], "Resource": "arn:aws:redshift:region:account-a:cluster:my-cluster"} — specific cluster. Account B — S3 Bucket Policy (Resource Policy): {"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::account-a:role/GlueJobRole"}, "Action": "s3:GetObject", "Resource": "arn:aws:s3:::account-b-bucket/shared-prefix/*", "Condition": {"StringEquals": {"aws:PrincipalOrgID": "o-orgid123"}}} — restricts to: specific role (not account root), specific prefix, within organization. Why both needed: Cross-account S3 access requires BOTH identity policy AND resource policy to Allow. If either Denies → access denied. This is different from same-account where identity policy alone suffices.

Common Misconceptions & Pitfalls

  • S3:* includes s3:DeleteBucket, s3:PutBucketPolicy — extremely dangerous.
  • S3:Get* includes admin actions, no prefix restriction.
  • Bucket-level wildcard too broad (exposes all data in bucket).
  • Needs actual usage data from CloudTrail.
  • AdministratorAccess is the opposite of least privilege.
  • Superuser access defeats least privilege.
  • Redshift:* allows cluster management.
  • Resource:* provides no restriction.
  • VPC endpoint policies have limited Glue catalog condition support.
  • IAM should ALSO enforce restrictions (defense in depth).
  • Detective control only, damage already done.
  • Doesn't scale, creates bottleneck.
  • Timeout ≠ access control, function could still be invoked.
  • Wildcard actions/resources violate least privilege.
  • Lambda doesn't have a source IP (runs in AWS network).
  • Account admins can remove/modify IAM policies.
  • Default encryption doesn't ENFORCE (clients can specify different encryption or none with explicit header).
  • Detective only, doesn't prevent.
  • Managed policies are often overly broad.
  • Explicit Deny + Allow CreateDatabase still over-provisions.
  • VPC peering doesn't provide S3 authorization.
  • Account root principal too broad.
  • Hardcoded credentials = massive security risk.
