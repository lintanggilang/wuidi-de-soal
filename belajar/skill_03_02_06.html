Skill 3.2.6: Aggregation, rolling average, pivoting

Ringkasan

Skill ini termasuk dalam Domain 3: Operations & Support (Task 3.2: Analyze data by using AWS services), dengan fokus pada aggregation, rolling average, pivoting. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Lihat poin-poin kunci di bawah.

Poin-Poin Kunci

  • AVG() dengan ROWS BETWEEN 6 PRECEDING AND CURRENT ROW menghitung rata-rata dari maximum 7 rows (6 sebelumnya + current). AVG() secara otomatis membagi dengan jumlah rows yang ada dalam window, jadi untuk 6 hari pertama akan menggunakan jumlah data yang tersedia.
  • GROUPING SETS memberikan kontrol eksplisit atas level agregasi yang diinginkan. (quarter, category) memberikan detail per quarter per category, (quarter) memberikan subtotal per quarter, dan () memberikan grand total. Ini persis memenuhi requirement.
  • Conditional aggregation dengan CASE WHEN adalah teknik pivot yang paling reliable dan widely supported di Amazon Redshift. Setiap kolom output didefinisikan sebagai aggregate dengan CASE yang memfilter region tertentu.
  • APPROXIMATE COUNT(DISTINCT) di Redshift menggunakan HyperLogLog algorithm yang memberikan estimasi cardinality dengan error rate sekitar 2% sambil jauh lebih cepat dari exact count distinct. Ini ideal untuk dashboard real-time dimana speed lebih penting dari exact precision.
  • Window function dengan rangeBetween(-3600, 0) pada kolom timestamp (dalam detik) menghitung rolling average 1 jam untuk setiap row, looking back 3600 seconds dari current row. partitionBy("sensor_id") memastikan kalkulasi per sensor. Ini memberikan true rolling average bukan tumbling window.
  • Mengkonversi timestamp ke unix time (seconds), membagi dengan 900 (15 menit × 60 detik), floor untuk rounding down, lalu kali kembali 900 dan konversi ke timestamp. Ini memberikan 15-minute aligned buckets yang akurat. Digunakan dengan GROUP BY untuk aggregation.
  • COALESCE(SUM(quantity), 0) menangani kasus dimana SUM() mengembalikan NULL (ketika semua values dalam group adalah NULL). SUM() di SQL mengabaikan NULLs, dan jika SEMUA values adalah NULL, hasilnya NULL. COALESCE mengkonversi NULL final menjadi 0.
  • Conditional aggregation (MAX/MIN with CASE WHEN) adalah teknik standar untuk pivoting di Athena (Trino/Presto). Setiap metric_name menjadi satu CASE expression. Tantangannya adalah 50 kolom membuat query panjang tapi tetap efisien karena single table scan. MAX digunakan karena setiap sensor_id + metric_name combination hanya memiliki satu value.
  • LAG(revenue, 12) OVER (ORDER BY month_date) efisien karena mengakses row 12 posisi sebelumnya (12 bulan = 1 tahun) dalam single pass. Kemudian (revenue - LAG(revenue,12)) / LAG(revenue,12) * 100 memberikan growth percentage. Window functions di Redshift sangat optimized.
  • PySpark groupBy().agg() dengan multiple aggregate functions menghitung semua metrik dalam single shuffle operation. sum(), avg(), countDistinct(), dan max() semua dikomputasi dalam satu pass setelah groupBy. datediff dengan max(purchase_date) memberikan days since last purchase. Ini paling efisien karena hanya satu shuffle.

Miskonsepsi & Jebakan Umum

  • Selalu membagi dengan 7 meskipun kurang dari 7 data points tersedia, menghasilkan rata-rata yang salah untuk hari-hari pertama.
  • Menggunakan RANGE yang di Redshift memiliki behavior berbeda dengan ROWS untuk date types.
  • Akan menghasilkan subtotals hierarchical dari kanan: (quarter, category), (quarter), () yang sebenarnya juga benar dalam kasus ini - namun GROUPING SETS lebih eksplisit.
  • Menghasilkan semua kemungkinan kombinasi termasuk (category) alone yang tidak diminta.
  • Memerlukan multiple passes dan UNION yang kurang efisien.
  • Melakukan kebalikan dari yang diminta.
  • Tersedia di beberapa database (SQL Server, Oracle) dan Redshift baru saja menambahkan dukungannya, namun conditional aggregation tetap menjadi pendekatan paling portable dan well-understood.
  • Memerlukan refresh time dan storage, serta still slow to compute initially.
  • Memberikan estimasi yang tidak akurat dan tidak representative.
  • Bukan teknik statistik yang valid.
  • Hanya memberikan overall average, bukan rolling.
  • Menggunakan tumbling window (fixed 1-hour windows) bukan rolling window.
  • Mengubah shape data, bukan menghitung rolling average.
  • Menghasilkan string bukan timestamp, kehilangan temporal ordering.
  • Hanya truncate ke menit, memerlukan logic tambahan yang rumit.
  • Secara konseptual benar tapi syntax integer division di Athena (Presto) memerlukan CAST yang membuat kurang clean.
  • Equivalent dengan COALESCE di Redshift dan juga benar - namun COALESCE lebih standar SQL.
  • Akan menampilkan NULL untuk all-NULL categories.
  • Mengubah setiap NULL menjadi 0 sebelum SUM - ini menghasilkan 0 juga tapi mengubah semantics karena NULLs yang seharusnya diabaikan malah dihitung sebagai 0.
  • Sangat tidak efisien dan menghasilkan narrow format, bukan wide.
  • Salah karena Athena (Trino) tidak memiliki PIVOT clause native dengan dynamic columns.
  • Melakukan kebalikan - wide ke narrow.
  • Lebih verbose dan kurang efisien dibanding single window function pass.
  • Memerlukan full table scan dua kali.
  • Sangat tidak efisien untuk large tables.
  • Menghasilkan 4 shuffle operations dan 3 joins tambahan.
  • Tidak mengagregasi rows, hanya menambah kolom ke setiap row.
  • Akan gagal pada large datasets karena memory constraints.
