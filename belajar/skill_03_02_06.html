Key Points

  • AVG() with ROWS BETWEEN 6 PRECEDING AND CURRENT ROW calculates rata-rata from maximum 7 rows (6 previously + current). AVG() automatically divides with number rows that there is in window, jadi for 6 days first will uses number data that available.
  • GROUPING SETS provides kontrol eksplisit above level agregasi that diinginkan. (quarter, category) provides detail per quarter per category, (quarter) provides subtotal per quarter, and () provides grand total. This persis memenuhi requirement.
  • Conditional aggregation with CASE WHEN is technique pivot that most reliable and widely supported in Amazon Redshift. Each column output didefinisikan as aggregate with CASE that filters region certain.
  • APPROXIMATE COUNT(DISTINCT) in Redshift uses HyperLogLog algorithm that provides estimasi cardinality with error rate sekitar 2% sambil jauh faster from exact count distinct. This is ideal for dashboard real-time where speed more important from exact precision.
  • Window function with rangeBetween(-3600, 0) on column timestamp (in seconds) calculates rolling average 1 hours for each row, looking back 3600 seconds from current row. partitionBy("sensor_id") ensures kalkulasi per sensor. This provides true rolling average not tumbling window.
  • Mengkonversi timestamp to unix time (seconds), divides with 900 (15 minutes × 60 seconds), floor for rounding down, lalu kali returns 900 and konversi to timestamp. This provides 15-minute aligned buckets that akurat. Digunakan with GROUP BY for aggregation.
  • COALESCE(SUM(quantity), 0) handles case where SUM() returns NULL (when all values in group is NULL). SUM() in SQL mengabaikan NULLs, and if ALL values is NULL, hasilnya NULL. COALESCE mengkonversi NULL final becomes 0.
  • Conditional aggregation (MAX/MIN with CASE WHEN) is technique standard for pivoting in Athena (Trino/Presto). Each metric_name becomes one CASE expression. Tantangannya is 50 column creates query panjang but still efficient because single table scan. MAX is used because each sensor_id + metric_name combination only has one value.
  • LAG(revenue, 12) OVER (ORDER BY month_date) efficient because accesses row 12 posisi previously (12 months = 1 years) in single pass. Then (revenue - LAG(revenue,12)) / LAG(revenue,12) * 100 provides growth percentage. Window functions in Redshift very optimized.
  • PySpark groupBy().agg() with multiple aggregate functions calculates all metrik in single shuffle operation. sum(), avg(), countDistinct(), and max() all dikomputasi in one pass after groupBy. datediff with max(purchase_date) provides days since last purchase. This most efficient because only one shuffle.

Common Misconceptions & Pitfalls

  • Uses RANGE that in Redshift has behavior different with ROWS for date types.
  • Will produces subtotals hierarchical from kanan: (quarter, category), (quarter), () that sebenarnya also correct in case this - however GROUPING SETS more eksplisit.
  • Produces all possibility kombinasi including (category) alone that not requested.
  • Requires multiple passes and UNION that less efficient.
  • Melakukan kebalikan from that requested.
  • Available in several database (SQL Server, Oracle) and Redshift new only adds dukungannya, however conditional aggregation still becomes approach most portable and well-understood.
  • Requires refresh time and storage, as well as still slow to compute initially.
  • Provides estimasi that not akurat and not representative.
  • Not technique statistics that valid.
  • Only provides overall average, not rolling.
  • Uses tumbling window (fixed 1-hour windows) not rolling window.
  • Changes shape data, not calculates rolling average.
  • Produces string not timestamp, kehilangan temporal ordering.
  • Only truncate to minutes, requires logic additional that rumit.
  • In a konseptual correct but syntax integer division in Athena (Presto) requires CAST that creates less clean.
  • Equivalent with COALESCE in Redshift and also correct - however COALESCE more standard SQL.
  • Will menampilkan NULL for all-NULL categories.
  • Changes each NULL becomes 0 before SUM - this produces 0 also but changes semantics because NULLs that should diabaikan malah is calculated as 0.
  • Very not efficient and produces narrow format, not wide.
  • Incorrect because Athena (Trino) not has PIVOT clause native with dynamic columns.
  • Melakukan kebalikan - wide to narrow.
  • More verbose and less efficient dibanding single window function pass.
  • Requires full table scan two kali.
  • Very not efficient for large tables.
