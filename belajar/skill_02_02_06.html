Key Points

  • Amazon DataZone (rebranded as Amazon SageMaker Catalog) is purpose-built for enterprise data marketplace scenarios: (1) a domain spans multiple AWS accounts, providing a unified governance boundary; (2) projects represent organizational units (business units) that own and manage data assets; (3) the data catalog provides business-friendly discovery with metadata, descriptions, glossary terms, and data quality indicators; (4) the subscription workflow enables self-service: analysts request access, owners approve/deny, and access is automatically provisioned; (5) it integrates with Lake Formation, Redshift, and S3 for underlying access control without exposing IAM complexity to business users. Option B — Lake Formation cross-account sharing provides the technical access mechanism but lacks the business catalog, discovery interface, subscription workflow, and approval process. It's infrastructure, not a business-level experience. Option C — RAM + custom Step Functions could replicate parts of this functionality but requires significant custom development for the catalog UI, approval workflow, asset metadata management, and subscription tracking. DataZone provides all of this out of the box. Option D — QuickSight is a BI visualization tool, not a data governance/sharing platform. It provides dataset access within QuickSight but doesn't enable analysts to discover and access raw data in data lakes or warehouses for their own analysis tools.
  • DataZone's Business Glossary is the dedicated feature for standardized business vocabulary: (1) glossary terms are first-class objects in DataZone with rich metadata (definition, owner, status, related terms); (2) they can be hierarchical (parent-child relationships) and linked to each other; (3) when publishing data assets, producers associate glossary terms at both the dataset level and individual column level; (4) consumers search the catalog using business terms rather than technical database/table/column names; (5) this bridges the gap between technical data catalogs (Glue) and business understanding. For example, a column named "cust_ltv_score" in a technical catalog becomes discoverable as "Customer Lifetime Value" in the business glossary. Option B — Glue Data Catalog tags are key-value pairs for resource organization, not rich business vocabulary definitions. They lack descriptions, ownership, relationships, and the search/discovery experience. DataZone doesn't automatically import Glue tags as glossary terms. Option C — DataZone doesn't support uploading JSON schema files as vocabulary definitions. The glossary is a structured, interactive feature with its own management UI and API, not a file upload. Option D — Lake Formation tags are for access control (tag-based permissions), not business vocabulary. While they can be named after business concepts, they lack definitions, relationships, and the discovery experience that a proper glossary provides.
  • DataZone supports configurable approval workflows for data subscriptions: (1) subscription requests require approval before access is provisioned; (2) approval policies can be configured at the project or environment level to specify who must approve; (3) metadata forms attached to data assets can define required approvers, compliance requirements, and justification fields; (4) multiple approvers can be designated for sensitive data assets; (5) notifications route to all required approvers, and access is only granted when all approvals are obtained. This enables governance policies like "customer data requires compliance sign-off" without custom workflow development. Option B — DataZone does support configurable approval flows beyond single-level. While the exact mechanisms have evolved, the service is designed for enterprise governance where multi-level approval is a common requirement. Building custom Step Functions workflows adds unnecessary complexity. Option C — making the compliance team project co-owners gives them full project management access (publish, modify, delete assets), not just approval authority. This violates the principle of least privilege. Option D — separate domains create isolation, not collaboration. Domains are organizational boundaries — splitting governance across domains prevents the unified catalog and discovery experience that's the core value proposition.
  • DataZone's data portal provides enterprise-grade search and discovery: (1) full-text search across all metadata — asset names, descriptions, column names, column descriptions, glossary terms, and custom metadata forms; (2) results are ranked by relevance and enriched with business context (who owns it, when it was last updated, data quality indicators); (3) faceted filtering allows narrowing results by project, domain, glossary term, freshness, or format; (4) asset detail pages show business descriptions, technical schemas, sample data, lineage, and usage statistics; (5) the subscription action is integrated directly in the discovery interface — one click to request access. This is the "data marketplace" experience that differentiates DataZone from technical catalogs. Option B — manual browsing defeats the purpose of a data catalog. With 200 assets across 8 projects, this is impractical and doesn't surface cross-project assets the analyst might not know exist. Option C — querying Glue Data Catalog directly exposes technical complexity (API knowledge, column name patterns) and misses the business context (descriptions, glossary terms) that make assets discoverable by non-technical users. Option D — requiring manager intervention for data discovery is the legacy pattern that DataZone eliminates. Self-service is the core value proposition — analysts should discover data independently.
  • DataZone's environment-aware access provisioning handles cross-environment data access: (1) environment profiles define the compute capabilities available to a project (Redshift, Athena, SageMaker, etc.); (2) when a subscription is approved, DataZone's managed access provisioning determines the appropriate mechanism based on source and consumer environments; (3) for Redshift-to-Redshift sharing, it uses Redshift data sharing; (4) for enabling non-Redshift environments to access Redshift data, it can provision Redshift Spectrum tables or configure federated query access; (5) the data producer publishes once, and DataZone handles the complexity of making data accessible across different compute engines. This abstraction is what makes the "data marketplace" work across heterogeneous environments. Option B — automatic data copying would create data duplication, staleness issues, storage costs, and governance complexity (multiple copies of sensitive data). DataZone prefers access provisioning over data copying. Option C — requiring consumers to match producer environments defeats the purpose of a data marketplace. The whole point is decoupling data discovery/access from physical storage implementation. Option D — materialized views in a consumer's cluster require the consumer to have a Redshift cluster. The data scientist uses SageMaker, not Redshift. Also, cross-cluster materialized views aren't how DataZone provisions access.
  • DataZone supports governance policies that control both visibility (who can discover assets) and access (who can subscribe): (1) domain-level governance rules can restrict which projects see which assets based on classification; (2) metadata forms allow tagging assets with sensitivity classifications (PHI, PII, Confidential); (3) project attributes/tags identify compliance certifications (HIPAA-certified, SOC2-certified); (4) policies match asset classifications against project certifications to determine visibility; (5) this ensures PHI datasets are invisible to uncertified projects — they cannot discover what they cannot access, implementing the principle of "need to know" at the catalog level. Option B — separate domains provide isolation but prevent legitimate cross-domain discovery. A HIPAA-certified project might also need non-PHI data from the main domain. Splitting domains fragments the catalog and reduces the value of unified discovery. Option C — security through obscurity is never appropriate for compliance. Making assets unsearchable doesn't prevent deliberate browsing, API access, or accidental exposure. Proper policy enforcement is required for HIPAA. Option D — IAM-level API restrictions are too coarse-grained and don't integrate with DataZone's governance model. Managing per-asset visibility through IAM policies for hundreds of users/assets is impractical and doesn't provide the audit trail DataZone's native policies offer.
  • Asset versioning in DataZone handles breaking changes through controlled evolution: (1) publishing a new version preserves the existing version for current subscribers; (2) subscribers receive notifications about the new version availability; (3) the version history documents what changed (schema diff) so subscribers can assess impact; (4) subscribers migrate at their own pace — no forced breaking change; (5) the producer can set deprecation timelines ("version 1 will be retired on date X") providing clear migration windows. This pattern mirrors API versioning best practices applied to data products. Option B — directly modifying a published asset's schema would break all subscribers immediately. DataZone doesn't automatically propagate renames because downstream systems reference the original column name in queries, dashboards, and ML features. Option C — unpublishing and republishing disrupts all subscribers. Existing subscriptions may not automatically reconnect (requiring re-approval), and there's a period where the data is completely unavailable. Option D — creating a completely separate asset with a different name fragments the catalog, loses the relationship between versions, and requires manual subscriber management. DataZone's versioning maintains a single logical asset with multiple versions, preserving lineage and subscription relationships.
  • Custom metadata forms with required fields enforce metadata standards at publish time: (1) metadata forms are templates that define what information must be provided for published assets (business description, owner, classification, freshness SLA, etc.); (2) required fields must be populated before the publish action succeeds — this is a blocking validation, not an after-the-fact check; (3) forms can be defined at domain level (applying to all projects) or project level (project-specific requirements); (4) standardized forms ensure consistent metadata quality across the entire catalog; (5) this shifts metadata quality from "best effort" to "enforced requirement," improving discovery and governance quality. Option B — post-publish Lambda enforcement creates a poor user experience (asset appears then disappears) and doesn't prevent bad metadata from entering the catalog temporarily. Proactive validation at publish time is superior. Option C — Glue Data Quality evaluates DATA quality (completeness, uniqueness, freshness of actual data values), not METADATA quality (description completeness, glossary associations). These are different dimensions. Option D — weekly reports are reactive and rely on manual compliance. With 200+ assets and multiple publishers, manual follow-up doesn't scale and allows low-quality metadata to persist for days/weeks.
  • DataZone is designed to layer business metadata on top of technical catalogs, not replace them: (1) DataZone connects to Glue Data Catalog as a metadata source, importing technical schemas automatically; (2) data producers curate which assets to publish — selecting the 100 relevant business datasets from the 500 technical tables; (3) business enrichment (descriptions, glossary terms, ownership, quality metrics) is added during the publish process; (4) the Glue Data Catalog continues serving its technical purpose (ETL jobs, crawlers, Athena queries) while DataZone serves business discovery and governance; (5) schema changes in Glue propagate to DataZone, maintaining consistency. This is the "two-layer catalog" architecture: technical + business. Option B — automatically publishing all 500 tables overwhelms business users with irrelevant technical assets (staging tables, temp tables, raw landing zones). Curation is essential for a useful business catalog. Option C — manual synchronization doesn't scale and inevitably leads to drift. DataZone's integration with Glue eliminates manual schema maintenance. Option D — Glue Data Catalog serves a different purpose (technical metadata for ETL, crawlers, query engines) and cannot be replaced by DataZone. Athena, Glue ETL, EMR, and Redshift Spectrum all depend on the Glue Data Catalog's technical metadata. DataZone adds a business layer on top, not a replacement.
  • DataZone supports global discovery with regional access enforcement: (1) projects and environments are regional — an EU environment provisions compute and access only in eu-west-1; (2) the catalog provides unified search — analysts discover relevant data regardless of region; (3) access provisioning is environment-bound: subscribing to EU data from an eu-west-1 environment grants access within that region only; (4) governance policies can prevent creating environments that would access data across regulatory boundaries; (5) metadata (descriptions, schemas, glossary terms) is centrally searchable, but actual data access stays within the mandated region. This separates "discoverability" (global) from "accessibility" (regional). Option B — completely separate domains prevent cross-region discovery, which defeats the purpose of a unified catalog. Business analysts should be able to find what data exists globally, even if access is restricted regionally. Discovery doesn't violate GDPR — accessing/processing the data does. Option C — replicating EU data to us-east-1 violates GDPR data residency requirements, even if "only for catalog purposes." DataZone catalog metadata doesn't require data replication — it references data in its original location. Option D — SCPs provide coarse-grained preventive controls but don't provide the positive user experience of "discover globally, access locally." They also can't differentiate between legitimate single-region access and prohibited cross-region access at the DataZone level.
