Skill 1.2.6: Transform data between formats

CSVParquetORCAvroJSON

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.2: Transform and process data), dengan fokus pada transform data between formats. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Lihat poin-poin kunci di bawah.

Poin-Poin Kunci

  • Parquet adalah columnar format — Athena hanya membaca kolom yang diquery (column pruning), secara drastis mengurangi data yang di-scan dan biaya. Snappy compression memberikan good compression ratio dengan decompression speed yang sangat cepat. Kombinasi ini optimal untuk analytical queries.
  • Amazon Data Firehose memiliki built-in format conversion yang mengkonversi JSON/CSV input ke Apache Parquet atau Apache ORC. Fitur ini menggunakan schema dari Glue Data Catalog untuk mapping fields. Tidak perlu Lambda atau service tambahan.
  • INT96 timestamp adalah legacy Parquet format yang tidak semua systems support correctly. Mengkonversi ke TIMESTAMP_MICROS (INT64) menggunakan spark.sql.parquet.outputTimestampType memastikan compatibility dengan Redshift Spectrum dan services lainnya. Ini fix masalah di source.
  • File count = number of Spark partitions. Dengan repartition(N), Anda bisa mengontrol berapa banyak output files. Jika 500 GB CSV menjadi ~100 GB Parquet (compression), dan target 128-256 MB per file, maka N = 100GB/200MB ≈ 500 partitions. coalesce() juga bisa mengurangi partisi tanpa shuffle.
  • Glue membaca Avro files dengan embedded schemas otomatis. Dengan schema evolution handling (misalnya mergeSchema option saat write Parquet), new fields ditambahkan ke output schema tanpa breaking existing data. Existing records mendapat NULL untuk new fields.
  • Untuk latency-sensitive queries (dashboards), decompression speed lebih penting dari compression ratio. Snappy decompresses ~2-3x faster dari GZIP. Dalam Parquet, compression diterapkan per column chunk sehingga splittability bukan issue. Trade-off: file ~30% larger tapi query 2-3x faster decompression.
  • Glue DynamicFrame Relationalize transform secara otomatis flatten nested structures (arrays dan structs) menjadi separate flat DynamicFrames linked by auto-generated keys. Ini menangani multiple levels of nesting secara rekursif. Sangat powerful untuk complex nested JSON.
  • Redshift UNLOAD command mendukung FORMAT AS PARQUET secara native. Data ditulis langsung ke S3 dalam Parquet format dengan columnar storage dan compression. Ini paling efisien karena Redshift melakukan conversion internally tanpa data transfer overhead.
  • Athena dan Redshift Spectrum keduanya mendukung ORC secara native. Migration ke Parquet tidak wajib untuk fungsionalitas. Namun, Parquet memiliki broader ecosystem support (Spark, pandas, Arrow, ML frameworks), lebih baik untuk nested data, dan umumnya direkomendasikan AWS untuk new workloads.
  • Glue DynamicFrames mendeteksi mixed types dan membuat ChoiceType. ResolveChoice transform menyediakan strategies: cast (convert semua ke satu type), make_cols (buat kolom terpisah per type), make_struct (nested structure), atau project (keep specific type). Ini menyelesaikan type ambiguity sebelum write ke Parquet.

Miskonsepsi & Jebakan Umum

  • Avro row-oriented, lebih cocok untuk serialization bukan analytics.
  • JSON sangat verbose dan row-oriented.
  • Row format berarti semua kolom dibaca meskipun hanya query 2 kolom.
  • Lambda transformation bisa modify content tapi Firehose native format conversion lebih efisien untuk format change.
  • Partitioning berbeda dari format conversion.
  • S3 tidak melakukan format conversion.
  • Tidak mengubah physical file format.
  • Tidak bisa correctly interpret INT96 di Spectrum.
  • Adalah Spark option yang valid tapi kurang presisi untuk size control.
  • Glue tidak otomatis optimize file sizes ke target tertentu.
  • Tidak mengontrol logical file size.
  • Tidak scalable saat schema berubah sering.
  • Menambah unnecessary step dan kehilangan type information.
  • Smaller files tapi slower decompression menambah query latency.
  • Di Parquet semua compression splittable per row group.
  • File terlalu besar — more I/O time dari S3.
  • Valid tapi Relationalize lebih direct di ETL pipeline.
  • Glue tidak auto-flatten, Parquet mendukung nested types.
  • Bekerja tapi membutuhkan code per nested level — tedious untuk 5 levels.
  • Redshift Spectrum external tables are read-only, tidak bisa INSERT INTO.
  • Sangat lambat untuk large datasets dan bottleneck di single connection.
  • Menambah step dan biaya Glue job.
  • Over-generalization — keduanya memiliki trade-offs.
  • Salah — mereka berbeda (ORC dari Hive ecosystem, Parquet dari Hadoop/Spark).
  • Parquet standard tidak memiliki variant type (beberapa extensions ada tapi non-standard).
  • Mengorbankan query performance.
