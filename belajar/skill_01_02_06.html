Key Points

  • Parquet is columnar format — Athena only reads kolom that diquery (column pruning), in a drastis reduces data that in-scan and cost. Snappy compression provides good compression ratio with decompression speed that very fast. Kombinasi this optimal for analytical queries.
  • Amazon Data Firehose has built-in format conversion that mengkonversi JSON/CSV input to Apache Parquet or Apache ORC. Fitur this uses schema from Glue Data Catalog for mapping fields. Not needs Lambda or service additional.
  • INT96 timestamp is legacy Parquet format that not all systems support correctly. Mengkonversi to TIMESTAMP_MICROS (INT64) uses spark.sql.parquet.outputTimestampType ensures compatibility with Redshift Spectrum and services others. Ini fix problem in source.
  • File count = number of Spark partitions. By repartition(N), Anda can mengontrol berapa many output files. If 500 GB CSV menjadi ~100 GB Parquet (compression), and target 128-256 MB per file, maka N = 100GB/200MB ≈ 500 partitions. coalesce() also can reduces partition without shuffle.
  • Glue reads Avro files with embedded schemas automatic. By schema evolution handling (for example mergeSchema option saat write Parquet), new fields is added to output schema without breaking existing data. Existing records mendapat NULL for new fields.
  • For latency-sensitive queries (dashboards), decompression speed more important from compression ratio. Snappy decompresses ~2-3x faster from GZIP. In Parquet, compression is applied per column chunk so that splittability not issue. Trade-off: file ~30% larger but query 2-3x faster decompression.
  • Glue DynamicFrame Relationalize transform automatically flatten nested structures (arrays and structs) menjadi separate flat DynamicFrames linked by auto-generated keys. Ini handles multiple levels of nesting in a rekursif. Very powerful for complex nested JSON.
  • Redshift UNLOAD command supports FORMAT AS PARQUET in a native. Data is written directly to S3 in Parquet format with columnar storage and compression. Ini most efficient because Redshift performs conversion internally without data transfer overhead.
  • Athena and Redshift Spectrum keduanya supports ORC in a native. Migration to Parquet not required for fungsionalitas. Namun, Parquet has broader ecosystem support (Spark, pandas, Arrow, ML frameworks), better for nested data, and generally direkomendasikan AWS for new workloads.
  • Glue DynamicFrames detects mixed types and creates ChoiceType. ResolveChoice transform provides strategies: cast (convert all to satu type), make_cols (buat kolom separate per type), make_struct (nested structure), or project (keep specific type). Ini solves type ambiguity before write to Parquet.

Common Misconceptions & Pitfalls

  • Avro row-oriented, better suited for serialization not analytics.
  • JSON very verbose and row-oriented.
  • Row format berarti all kolom is read although only query 2 kolom.
  • Lambda transformation can modify content but Firehose native format conversion more efficient for format change.
  • Partitioning different from format conversion.
  • S3 not performs format conversion.
  • Not changes physical file format.
  • Not can correctly interpret INT96 in Spectrum.
  • Adalah Spark option that valid but less presisi for size control.
  • Glue not automatic optimize file sizes to target certain.
  • Not mengontrol logical file size.
  • Not scalable saat schema changes often.
  • Adds unnecessary step and kehilangan type information.
  • Smaller files but slower decompression adds query latency.
  • Di Parquet all compression splittable per row group.
  • File too large — more I/O time from S3.
  • Valid but Relationalize more direct in ETL pipeline.
  • Glue not auto-flatten, Parquet supports nested types.
  • Bekerja but requires code per nested level — tedious for 5 levels.
  • Redshift Spectrum external tables are read-only, cannot INSERT INTO.
  • Very slow for large datasets and bottleneck in single connection.
  • Adds step and cost Glue job.
  • Over-generalization — keduanya has trade-offs.
  • Salah — mereka different (ORC from Hive ecosystem, Parquet from Hadoop/Spark).
  • Parquet standard not has variant type (several extensions ada but non-standard).
  • Mengorbankan query performance.
