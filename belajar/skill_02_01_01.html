Skill 2.1.1: Storage for cost and performance

RedshiftEMRLakeFormationRDSDynamoDB

Ringkasan

Skill ini termasuk dalam Domain 2: Data Store Management (Task 2.1: Choose a data store), dengan fokus pada storage for cost and performance. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon EMR
Cluster big data terkelola (Spark, Hive, Presto); mendukung Spot Instances untuk hemat biaya.
Amazon Redshift
Data warehouse berskala petabyte; mendukung COPY/UNLOAD, materialized view, dan streaming ingestion.
Redshift Streaming Ingestion
Konsumsi langsung dari Kinesis/MSK ke materialized view Redshift, latensi detik, tanpa staging S3.
Amazon DynamoDB
Database NoSQL key-value latensi rendah; skala horizontal, mendukung TTL dan Streams.
Amazon RDS
Relational database terkelola (PostgreSQL, MySQL, dll) untuk beban OLTP.
AWS Lake Formation
Tata kelola data lake: izin berbasis tabel/kolom/baris dan LF-Tags di atas Glue Catalog.

Poin-Poin Kunci

  • Redshift Serverless is ideal for this workload because it automatically scales to handle complex JOINs across 50 TB (meeting the 30-second requirement) and scales to zero during the 16 hours/day and weekends when the cluster is idle — eliminating cost for ~76% of the time. With predictable 8-hour weekday usage, the pay-per-use model significantly reduces costs compared to always-on provisioned clusters.
  • DynamoDB On-Demand mode is purpose-built for unpredictable workloads with 10x traffic variance. It instantly accommodates traffic spikes (5K to 50K RPS) without pre-provisioning, and you pay only for actual requests — dramatically reducing costs during the extended off-peak periods. The single-item read/write by primary key (user_id) pattern is DynamoDB's optimal use case, providing consistent single-digit millisecond latency.
  • Amazon MSK is optimal for this scenario: (1) at 2 TB/hour throughput, Kafka's partitioned log architecture handles this volume efficiently; (2) consumer groups allow multiple independent consumers (real-time dashboard + batch S3 loader) to read the same stream at different rates without interference; (3) 7-day retention enables full event replay; (4) Kafka's publish-subscribe model inherently supports both real-time and batch consumption patterns. MSK also provides built-in integration with AWS services and supports exactly-once semantics.
  • Athena's pay-per-query model ($5/TB scanned) is ideal for infrequent, ad-hoc analytics. At 200 GB/query × 15 queries/day = 3 TB/day scanned = $15/day. With Parquet format (columnar), actual data scanned is often 10-30% of raw size due to column pruning, potentially reducing costs further. No infrastructure management, no idle costs, and acceptable query times for exploratory analysis.
  • Aurora PostgreSQL addresses all requirements: (1) ACID transactions are native to relational databases; (2) complex SQL with JOINs, window functions, CTEs for regulatory reporting; (3) read-after-write consistency guaranteed; (4) 500 GB highly normalized data is a classic OLTP relational use case; (5) stored procedures enforced at the database level; (6) Aurora handles 5,000 TPS with auto-scaling read replicas. Multi-AZ provides durability for financial data.
  • EMR provides maximum flexibility for this scenario: (1) Spark supports custom Python UDFs, graph analysis (GraphX), and ML feature engineering (MLlib) — all required capabilities; (2) transient clusters (terminate after use) eliminate idle costs; (3) Spot Instances reduce compute costs by up to 90% for fault-tolerant batch processing; (4) 100 TB processing is well-suited to Spark's distributed computing model; (5) the 2-week temporary nature makes a transient cluster ideal — no long-term commitment.
  • Lake Formation is designed specifically for centralized data lake governance: (1) column-level security controls which columns each team can see; (2) row-level security (data filters) restricts rows by department; (3) LF-Tags allow policy-based access (tag columns as "PII" and grant access to tagged resources); (4) cross-account sharing via RAM or direct grants; (5) single permission model enforced across Athena, Glue, Redshift Spectrum — eliminating per-service configuration.
  • RA3 nodes decouple compute from storage. Hot data (3 TB) is automatically cached on high-performance local SSDs for fast access, while the full 20 TB is stored on S3-backed Managed Storage at S3 pricing ($0.024/GB/month). You size RA3 nodes for compute needs (query concurrency/complexity), not storage volume. As data grows further, storage costs increase minimally while compute stays constant. This addresses the DC2 limitation where adding storage requires adding expensive compute nodes.
  • This combination uses each service for its optimal use case: (1) DynamoDB excels at high-throughput point reads/writes by primary key (player_id) with single-digit ms latency at 20M DAU scale; (2) Redis Sorted Sets are purpose-built for leaderboards — ZRANGEBYSCORE returns top-N players in O(log n + m) time with sub-millisecond latency, automatically maintaining sort order on every score update.
  • The lakehouse architecture combines data lake flexibility (S3 stores any format at low cost — structured, semi-structured, unstructured) with data warehouse performance (Redshift for curated, optimized sub-second queries). This addresses both requirements: analysts explore raw JSON/text in the lake using Athena's schema-on-read, while dashboards query pre-aggregated data in Redshift with sub-second latency. Cost is optimized by storing the bulk (750 GB/day) cheaply in S3 while loading only curated summaries into expensive Redshift storage.

Miskonsepsi & Jebakan Umum

  • Athena is cost-effective for ad-hoc queries but complex multi-table JOINs across 50 TB consistently within 30 seconds is unreliable without dedicated compute resources and result caching.
  • RA3 reserved instances run 24/7 (168 hours/week) but the workload only needs 40 hours/week, wasting 76% of provisioned capacity costs.
  • EMR with Spark SQL requires cluster management overhead and Spot instance interruptions may fail time-sensitive analytics queries.
  • RDS has connection limits, requires vertical scaling for peak capacity, and session data (key-value pattern) doesn't benefit from relational features.
  • Provisioned at 50K RCU/WCU costs for peak capacity even during 5K RPS periods; auto-scaling takes minutes to react and may not handle sudden flash sale spikes.
  • ElastiCache Redis provides excellent latency but requires provisioned nodes running 24/7 and manual cluster scaling; it also lacks DynamoDB's durability guarantees.
  • Kinesis Data Streams can handle this but has shard-level throughput limits (1 MB/s or 1000 records/s per shard); 2 TB/hour would require ~570 shards, making it more expensive and complex to manage than MSK at this scale.
  • SQS is a queue (each message consumed once), not a stream; it doesn't support multiple consumers reading the same messages or replay.
  • S3 writes don't provide sub-5-second latency for real-time dashboards due to eventual consistency and event notification delays.
  • Redshift dc2.large 2-node On-Demand costs ~$480/month running 24/7, regardless of whether queries are running; far more expensive for 15 queries/day.
  • EMR requires managing cluster lifecycle, and even with auto-termination, minimum cluster spin-up costs exceed Athena's per-query pricing for low-frequency usage.
  • Redshift Serverless at 32 RPU base has minimum charges and is designed for more sustained workloads; costs significantly more than Athena for 15 queries/day.
  • DynamoDB transactions support ACID but limited to 100 items per transaction; it doesn't support complex SQL JOINs or stored procedures needed for regulatory reporting.
  • Redshift is OLAP (analytical), not OLTP; it's optimized for large sequential scans, not high-frequency transactional writes at 5,000 TPS.
  • S3 + Athena is a data lake pattern without ACID transactions, stored procedures, or consistent read-after-write guarantees.
  • Glue ETL has a 48-hour maximum job timeout and limited support for custom graph analysis or ML feature engineering compared to native Spark on EMR.
  • Athena is SQL-only; it cannot perform graph analysis, custom Python UDFs, or ML feature engineering.
  • Redshift is a permanent data warehouse; provisioning for 100 TB, using it for 2 weeks, then decommissioning is expensive and Redshift doesn't support custom Python UDFs or graph analysis natively.
  • Redshift native permissions only apply within Redshift, not across S3/Glue/Athena, and don't provide centralized governance.
  • SCPs control service-level access (which services accounts can use), not data-level access (which rows/columns users can see).
  • Per-service IAM policies create a fragmented, hard-to-maintain permission landscape with no column/row-level granularity in S3.
  • Adding DC2 nodes couples compute scaling with storage, paying for expensive SSD+compute even for rarely-accessed historical data; cost-ineffective for 17 TB of cold data.
  • Athena cannot match Redshift's performance for complex multi-table JOINs on hot data that requires sub-second response times.
  • This manual approach requires data lifecycle management and separate query logic for hot vs. cold data; RA3 automates this transparently.
  • Aurora can handle this but connection pooling at 20M DAU with frequent writes and 5ms read requirement is challenging; it also requires managing read replicas and won't match DynamoDB's effortless scaling.
  • S3 has 50-200ms first-byte latency, far exceeding the 5ms read requirement.
  • DynamoDB GSI on score requires scanning all items to find top 100 globally, which is inefficient; GSI doesn't support efficient "top N across all partitions" queries because results are distributed across partitions.
  • Athena cannot provide sub-second dashboard response times for concurrent users without result caching limitations.
  • RDS isn't designed for analytics at this scale, and having no integration prevents cross-source analysis.
  • Loading JSON and text into Redshift requires expensive transformation, wastes Redshift storage on data that may only be queried occasionally, and Redshift isn't optimized for semi-structured exploration.
