Skill 4.3.2: Encryption keys (KMS)

KMSencryptionkeysSSE

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.3: Ensure data encryption and masking), dengan fokus pada encryption keys (kms). Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS KMS
Manajemen kunci enkripsi; dasar SSE-KMS untuk enkripsi at-rest dan kebijakan key.

Poin-Poin Kunci

  • SSE-KMS with Customer Managed Key (CMK) memenuhi semua requirements: Requirement 1 — Key rotation control: Automatic rotation: Enable yearly rotation (key material rotated, key ID unchanged). Manual rotation: Create new key, re-encrypt data, update key alias. On-demand rotation for compliance. Requirement 2 — Emergency key disable: aws kms disable-key --key-id key-123. IMMEDIATE effect: all subsequent Encrypt/Decrypt calls FAIL. No one can read encrypted data — even with S3 access. Re-enable when emergency resolved. Requirement 3 — Audit trail: Every kms:Decrypt logged in CloudTrail: who (principal), what (key ARN), when (timestamp), from where (source IP). kms:GenerateDataKey logged for write operations. Integration with CloudWatch for alerting on anomalous patterns. Why NOT SSE-S3: No key disable capability. No per-request CloudTrail entries. No custom rotation control. AWS manages everything — limited visibility. Why NOT SSE-C: YOU must store/manage keys outside AWS. No CloudTrail logging of KMS operations (keys never touch KMS). Key loss = permanent data loss. Complex operational burden.
  • Envelope encryption adalah fundamental concept di AWS KMS: Encryption flow (PutObject with SSE-KMS): (1) S3 calls kms:GenerateDataKey(KeyId=cmk-123). (2) KMS returns: {Plaintext: "random-256-bit-key", CiphertextBlob: "encrypted-version-of-key"}. (3) S3 uses Plaintext key to AES-256 encrypt the 5GB object LOCALLY (never leaves S3). (4) S3 DISCARDS the plaintext key from memory. (5) S3 stores: [Encrypted 5GB Object] + [CiphertextBlob metadata]. Decryption flow (GetObject): (1) S3 retrieves CiphertextBlob (encrypted data key) — tiny, ~200 bytes. (2) S3 calls kms:Decrypt(CiphertextBlob). (3) KMS returns Plaintext data key. (4) S3 decrypts object locally using plaintext key. (5) S3 discards plaintext key after use. Why envelope encryption: Performance: KMS has 5,500-30,000 requests/second limit. Sending 5GB through KMS would be impossibly slow. Data never leaves S3 in plaintext. Each object gets unique data key — compromising one key doesn't expose other objects. KMS only processes tiny data keys (~256 bits), not gigabytes.
  • S3 Bucket Keys dramatically reduces KMS API calls: Problem analysis: 10M files/day = ~115 files/second average. Peak could be 10-100x during batch processing = 1,000-10,000+ KMS calls/second. Each GetObject on SSE-KMS object = 1 kms:Decrypt call. Each PutObject = 1 kms:GenerateDataKey call. S3 Bucket Keys solution: Without Bucket Keys: [Object 1 → KMS call] [Object 2 → KMS call] [Object 3 → KMS call] ... (1 call per object). With Bucket Keys: [KMS generates bucket-level key] → S3 derives per-object keys LOCALLY from bucket key. KMS called once per time window → S3 handles millions of objects using derived keys. Result: 99% reduction in KMS API calls. Cost reduction: KMS charges $0.03 per 10,000 requests → significant savings at 10M files/day. Enable: aws s3api put-bucket-encryption --bucket my-bucket --server-side-encryption-configuration '{"Rules": [{"BucketKeyEnabled": true, ...}]}'. Additional: Request quota increase as buffer for peaks.
  • Redshift cluster encryption migration process: Steps: (1) Modify cluster: aws redshift modify-cluster --cluster-identifier my-cluster --encrypted --kms-key-id key-arn. (2) Redshift initiates migration: Creates new encrypted storage. Copies data blocks with encryption applied. Maintains cluster availability during migration. (3) Timeline: 50TB cluster → several hours to complete. Performance degradation during migration (I/O intensive). (4) Completion: Cluster endpoint remains the same. All data now encrypted at rest with specified KMS key. Snapshots from this point forward are encrypted. Important considerations: Plan migration during low-usage window. Monitor cluster performance during migration. Automated snapshots may take longer during process. Once encrypted, cannot revert to unencrypted. Cross-region copies of encrypted snapshots require target region KMS key. KMS key selection: AWS managed key (aws/redshift): simple, no management. Customer managed key: full control, rotation, audit, cross-account sharing.
  • KMS key policy least privilege = different actions for different roles: Glue ETL Role (data read/write): kms:GenerateDataKey — needed for S3 PutObject (SSE-KMS). kms:Decrypt — needed for S3 GetObject. kms:DescribeKey — needed to verify key availability. NOT needed: kms:Encrypt (S3 uses GenerateDataKey, not Encrypt directly). NOT needed: kms:CreateKey, kms:DisableKey, kms:ScheduleKeyDeletion. Redshift Role (data read-only): kms:Decrypt — needed to read encrypted data from S3/Redshift storage. kms:DescribeKey — verify key status. NOT needed: kms:GenerateDataKey (not writing new encrypted data via KMS). Admin Role (key management): kms:CreateKey, kms:PutKeyPolicy, kms:EnableKey, kms:DisableKey. kms:ScheduleKeyDeletion, kms:CancelKeyDeletion. kms:EnableKeyRotation, kms:GetKeyPolicy, kms:ListKeys. NOT needed: kms:Decrypt, kms:GenerateDataKey (admin manages keys, doesn't access data). Separation of duties: Data engineers can't disable keys. Admins can't decrypt data. Read-only consumers can't write encrypted data.
  • DynamoDB encryption options have significant cost implications at scale: Option 1 — AWS Owned Key (DEFAULT): Cost: FREE (no KMS charges). Audit: No CloudTrail entries for encryption operations. Control: None — can't disable, rotate, or share. Best for: Non-regulated workloads, cost-sensitive applications. Option 2 — AWS Managed Key (aws/dynamodb): Cost: Key itself free, BUT each DynamoDB operation generates CloudTrail event. At 50K reads/sec = 4.3B events/day. CloudTrail costs for management events can be significant. Control: Limited — can view key policy, see usage, but can't rotate or share. Option 3 — Customer Managed Key (CMK): Cost: $1/month for key + $0.03 per 10,000 API requests. 50K reads/sec × 3600 × 24 = 4.32B requests/day. BUT: DynamoDB caches data keys, so NOT every read = KMS call. Actual KMS calls much lower than DynamoDB operations. Control: Full — custom rotation, disable/enable, cross-account, key policy. Audit: Full CloudTrail for key operations. Recommendation for 50K reads/sec: AWS owned key if audit not required (cheapest). CMK if compliance requires audit trail (DynamoDB's caching reduces actual KMS costs).
  • KMS automatic rotation behavior: What happens during rotation: Key ID/ARN: UNCHANGED — still same arn:aws:kms:region:account:key/uuid. Key material: NEW cryptographic material generated. Old key material: RETAINED (never deleted during rotation). Metadata: KMS tracks which version encrypted each ciphertext. Behavior after rotation: Encrypt/GenerateDataKey: Uses NEW key material. Decrypt: Automatically identifies which key material version was used (from ciphertext metadata) → uses CORRECT version. Result: No disruption, no re-encryption needed. Key policy: Unchanged — same principals have same access. Why NO re-encryption needed: Each encrypted object's ciphertext contains metadata identifying the key material version. KMS Decrypt call reads this metadata → selects correct version transparently. All versions remain active under the same Key ID. When you SHOULD manually re-encrypt: Compliance requires data encrypted with material no older than X days. Want to decommission old key material (manual rotation with new key ID). Migrating between encryption types. Manual rotation (different key ID): Requires re-encryption of old data. Old key must be kept until all data re-encrypted. More complex but allows complete material decommission.
  • Client-side field-level encryption provides granular column protection: Implementation in Glue PySpark: (1) Generate data key: response = kms.generate_data_key(KeyId='key-arn', KeySpec='AES_256'). plaintext_key = response['Plaintext']. encrypted_key = response['CiphertextBlob']. (2) Encrypt sensitive fields: from cryptography.fernet import Fernet (or AES-GCM). encrypted_ssn = encrypt(plaintext_key, row['ssn']). encrypted_cc = encrypt(plaintext_key, row['credit_card']). (3) Write to S3: DataFrame with: region (plaintext), amount (plaintext), ssn (encrypted blob), credit_card (encrypted blob), _encryption_key (encrypted data key). (4) Downstream decryption: Read encrypted_key → call kms:Decrypt → get plaintext key. Use plaintext key to decrypt field values locally. Why client-side: S3 SSE encrypts ENTIRE object — can't selectively encrypt columns. Analytics queries on region, amount still work without decryption. Only services with KMS access can read SSN, credit_card. Defense in depth: even if S3 access compromised, field-level encryption adds protection.
  • Preventing KMS key deletion requires multiple layers: Layer 1 — Key Policy Deny: {"Effect": "Deny", "Principal": {"AWS": "*"}, "Action": "kms:ScheduleKeyDeletion", "Resource": "*"}. This denies ALL principals from scheduling deletion. Note: Even root account is bound by explicit Deny in key policy. Layer 2 — SCP (Organization level): {"Effect": "Deny", "Action": "kms:ScheduleKeyDeletion", "Resource": "arn:aws:kms:region:account:key/specific-key-id"}. Prevents any principal in any account in the OU from scheduling deletion. Even account administrators cannot override SCPs. Layer 3 — Additional safeguards: aws kms disable-key-deletion (if available via custom configuration). CloudWatch Alarm on kms:ScheduleKeyDeletion API calls. AWS Config rule detecting keys with deletion scheduled. Important: KMS ScheduleKeyDeletion has mandatory 7-30 day waiting period — provides time to cancel even if somehow scheduled. CancelKeyDeletion can rescue a key during waiting period.
  • End-to-end encryption memerlukan explicit configuration di setiap stage: Stage 1 — Kinesis Data Streams: Server-side encryption: aws kinesis start-stream-encryption --stream-name my-stream --encryption-type KMS --key-id key-arn. Data encrypted immediately upon ingestion. Producer → Kinesis: TLS in transit (HTTPS endpoint). Consumer reads: KMS Decrypt called transparently. Stage 2 — Glue ETL: In-memory: data decrypted for processing (necessary for transformation). Security Configuration: Encrypts job bookmarks with KMS. Encrypts CloudWatch logs. S3 output encryption settings (SSE-KMS, key ARN). Temporary disk spill: Glue encrypts temp files on local disk. Glue ↔ S3/Kinesis: TLS in transit. Stage 3 — S3 Output: SSE-KMS on bucket: all objects encrypted at rest. Bucket policy enforcing encryption: Deny PutObject without encryption header. TLS enforced: Deny non-HTTPS requests. Continuous protection: At rest: encrypted in Kinesis, encrypted in S3, encrypted temp files in Glue. In transit: TLS between all services (default for AWS API calls). In processing: data necessarily decrypted in memory (encrypt output immediately).

Miskonsepsi & Jebakan Umum

  • No persistent connection; stateless API calls.
  • Salah — KMS has 4KB payload limit for direct encryption.
  • CMK NEVER leaves KMS hardware (HSM).
  • Removes security, violates compliance.
  • SSE-S3 loses audit trail, key control, disable capability.
  • Limits business functionality to work around technical issue.
  • Incorrect, migration IS supported.
  • Unnecessary downtime, complex process.
  • Not instant, requires data migration.
  • Key policy required; IAM alone insufficient for KMS access (key policy is always evaluated).
  • Doesn't separate management from data operations.
  • Kms:* gives everyone ability to delete keys, change policies.
  • SSE-KMS is object-level, not field-level.
  • Redshift encryption doesn't apply to S3 Parquet files.
  • Splits data, complicates joins, loses atomicity.
  • Rotation and deletion are independent settings.
  • Keys CAN be deleted (after waiting period).
  • KMS doesn't have a "deletion protection" toggle like RDS (must be done via policy).
  • Single key doesn't automatically configure encryption (each service needs explicit setup).
  • VPC doesn't provide encryption (provides network isolation).
  • Data unprotected in Kinesis and during processing.
