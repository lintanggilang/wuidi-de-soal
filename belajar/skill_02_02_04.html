Skill 2.2.4: Synchronize partitions

Ringkasan

Skill ini termasuk dalam Domain 2: Data Store Management (Task 2.2: Understand data cataloging systems), dengan fokus pada synchronize partitions. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Partition projection
Fitur Athena yang menghitung partisi dari pola tanpa memanggil metastore, mempercepat query.

Poin-Poin Kunci

  • MSCK REPAIR TABLE is the fastest single-command solution for synchronizing Hive-style partitions: (1) it scans the table's S3 location for subdirectories matching the key=value partition pattern; (2) it compares discovered partitions against the catalog and adds missing ones; (3) it requires no configuration — just execute the SQL statement in Athena; (4) for Hive-style naming (year=XXXX/month=XX/...), it automatically extracts partition values from directory names. This is ideal when multiple partitions accumulate between crawler runs. Option B — running the crawler on-demand works but takes significantly longer (minutes to start, then crawl time) compared to MSCK REPAIR (seconds to minutes for the SQL command). Option C — ALTER TABLE ADD PARTITION is precise but requires knowing exact partition values and S3 paths for each new partition; for 24 hourly partitions added daily, this is impractical without automation. Option D — deleting and recreating the table is destructive and unnecessary; it risks losing table properties, permissions, and configuration that were set post-creation.
  • Partition projection eliminates BOTH problems simultaneously: (1) NO partition synchronization needed — Athena doesn't store or read partition entries from the catalog; it computes partition locations using the projection configuration (type, range, format); (2) NO query planning latency from catalog lookups — instead of fetching 500K partition entries from Glue API (which is throttled), Athena calculates which partitions match the WHERE clause mathematically; (3) for device_id as "enum" type, Athena knows all valid values; for date as "date" type with format "yyyy-MM-dd", it generates all dates in the specified range; (4) the S3 path template (e.g., s3://bucket/device_id=${device_id}/date=${date}/) tells Athena where to find data without catalog queries. Option B — incremental crawling reduces sync time but doesn't address query planning latency with 500K+ partitions; the Glue API still throttles when Athena fetches partition metadata. Option C — changing partition granularity requires rewriting all existing data and may not meet query requirements (device-level filtering). Option D — event-driven registration solves sync latency but not query planning latency; 500K partitions in the catalog still cause slow GetPartitions API calls during query planning.
  • BatchDeletePartition (API) or ALTER TABLE DROP PARTITION (SQL) directly removes specific orphaned catalog entries: (1) these are the only methods that explicitly DELETE partition metadata from the catalog; (2) they're surgical — only the specified partitions are removed; (3) no S3 data is affected (only metadata); (4) ALTER TABLE DROP PARTITION in Athena is the SQL equivalent accessible without code. Option B — MSCK REPAIR TABLE only ADDS missing partitions; it does NOT remove partitions whose S3 paths are empty or deleted. This is a critical distinction: MSCK REPAIR is additive-only. The orphaned entries remain after MSCK REPAIR runs. Option C — Glue crawlers with "Update all" policy update schema and add new partitions, but the default crawler behavior does NOT remove partitions for deleted S3 paths. The crawler's "Delete objects from the catalog that are no longer in the data store" deletion policy must be explicitly enabled — and even then, it requires careful configuration to avoid accidentally removing valid partitions during transient S3 issues. Option D — deleting and recreating the table is unnecessarily destructive, losing table properties, permissions, column comments, and requiring downstream query updates if table properties change.
  • S3 event-driven Lambda with CreatePartition API provides the lowest latency for partition registration: (1) S3 Event Notifications fire within seconds of object creation; (2) Lambda extracts partition values from the S3 key (parsing year=, month=, day=, hour=, minute= from the path); (3) CreatePartition API call registers the partition instantly; (4) using BatchCreatePartition and deduplication logic (check if partition already exists before creating) handles multiple files per partition; (5) total latency from file landing to queryability is typically under 10 seconds. Option B — MSCK REPAIR every minute is wasteful: each execution performs a full S3 LIST of all directories (expensive at scale), consumes Athena query execution resources, and has a minimum overhead of 5-15 seconds per run even when no new partitions exist. Option C — partition projection is excellent but requires predictable, regular partition paths. It works here technically, but if any partition has no data (a 5-minute window with no events), queries targeting that partition would attempt to read non-existent S3 paths, resulting in potential errors or empty results that are harder to distinguish from "no data received." For streaming with consistent arrival, it's viable but doesn't provide the explicit registration guarantee. Option D — Glue crawlers have a minimum startup latency of 30-60 seconds and cannot achieve sub-minute registration; they're designed for batch discovery, not real-time.
  • Partition projection with a custom storage.location.template is the optimal long-term solution for non-Hive-style paths: (1) the template s3://sales/${year}/${month}/${day}/ tells Athena exactly how to construct S3 paths from partition values; (2) no partition entries need to be stored in the catalog — Athena computes paths mathematically; (3) new partitions (new days) are automatically queryable without ANY registration step; (4) it handles the non-standard directory naming perfectly because the template is fully customizable; (5) no ongoing maintenance — no crawlers, no MSCK REPAIR, no Lambda functions needed. Option A — ALTER TABLE ADD PARTITION works correctly for one-time or scripted registration, but requires ongoing execution for each new partition. It solves the immediate problem but creates operational burden. It IS the correct answer if partition projection isn't feasible (e.g., unpredictable partition values). Option B — renaming S3 directories means rewriting all S3 keys (S3 doesn't support rename — it's copy + delete), which for large datasets is extremely time-consuming and expensive; it also breaks any existing references to these paths. Option D — Glue crawlers can handle numeric paths (they recognize pattern-based partitions), but this requires crawler scheduling and maintenance; partition projection eliminates the need for any external sync mechanism.
  • BatchUpdatePartition is designed exactly for this use case — surgically updating specific partition metadata: (1) it updates the StorageDescriptor (including Location) for specified partitions without touching others; (2) it processes up to 100 partitions per call, making 200 partitions achievable in 2 API calls; (3) it preserves all other partition metadata (schema, parameters, creation time); (4) the remaining 9,800 partitions at the old location are unaffected (only 200 were migrated). Option B — deleting the table loses all metadata, permissions, and downstream references; recreating it is unnecessary when only 2% of partitions need updating. Option C — ALTER TABLE SET LOCATION changes the TABLE-level location (used as the base for MSCK REPAIR discovery), but individual partitions have their own Location stored independently. Changing the table location doesn't update existing partition locations. Also, only 200 of 10,000 partitions moved — the other 9,800 are still at the old location, so changing the table-level location would be incorrect. Option D — running the crawler against both buckets doesn't update existing partition locations because crawlers add NEW partitions but don't modify locations of existing partitions that point elsewhere (unless the partition is deleted first).
  • For date-type partition projection, the interval and interval.unit properties are REQUIRED: (1) projection.date.interval defines the step between consecutive partition values (e.g., 1); (2) projection.date.interval.unit defines the time unit (DAYS, HOURS, MINUTES, etc.); (3) without these, Athena cannot generate the series of valid date values within the specified range; (4) the correct configuration requires: projection.date.interval=1 and projection.date.interval.unit=DAYS for daily partitions. Without these properties, Athena cannot determine which date values are valid within the 2020-01-01 to NOW range, so it cannot construct paths to read. Option A — storage.location.template is optional when the table's base Location combined with Hive-style partition naming (date=${date}/) matches the actual S3 structure. If the table Location is 's3://events/' and paths follow Hive-style naming, Athena constructs paths correctly without an explicit template. Option B — "NOW" resolves correctly and 2025-01-15 is within the range 2020-01-01 to NOW (assuming current date is after 2025-01-15); timezone issues might cause 1-day edge cases but wouldn't cause a failure for a date well within range. Option D — partition columns in Athena for partition projection work as string type by default; the projection.date.format handles string-to-date conversion internally regardless of the declared column type.
  • Glue ETL's enableUpdateCatalog option provides native, built-in partition registration during data writes: (1) when writing via getSink() or write_dynamic_frame() with catalog connection options, setting enableUpdateCatalog=true instructs the job to update the catalog with any new partitions; (2) partitionKeys specifies which columns define the partition scheme; (3) the registration happens atomically with the data write — no gap between data availability and partition discoverability; (4) this is a built-in Glue feature requiring only configuration, not custom code; (5) it handles the 50 new partitions per run automatically. Option B — custom boto3 code works but requires the developer to track which partitions were newly created, handle deduplication (avoid errors for already-existing partitions), and manage error handling. It's more complex and error-prone than the native option. Option C — a workflow with MSCK REPAIR adds a separate job step, consumes additional Athena resources, and still introduces latency (the Python shell job startup + MSCK execution time). Option D — writing to a "catalog target" in Glue does auto-register partitions but may have different performance characteristics and doesn't allow custom S3 path structures; using getSink with enableUpdateCatalog gives the best of both worlds (custom S3 paths + auto-registration).
  • This is expected behavior, not a problem to fix: (1) Parquet is a self-describing format — each file carries its own schema in its footer; (2) the Glue Catalog table schema represents the superset (union) of all columns across all partitions; (3) individual partition schemas in the catalog reflect what actually exists in that partition's files; (4) when Athena reads old partitions, it maps columns by name — columns in the table schema but missing from the file return NULL; (5) this IS schema evolution working correctly. Re-crawling won't change anything because the crawler honestly reports what it finds in each partition's files. Option B — crawlers do NOT propagate table-level schemas to partition schemas; they independently inspect each partition's data and record what they find. The table schema is the MERGED result of all partitions, not a template imposed on them. Option C — updating partition schemas via BatchUpdatePartition to add customer_segment would make the catalog claim the column exists in old partitions, but Athena reads Parquet columns by name from the actual files regardless of catalog claims — the behavioral outcome (NULL for old partitions) remains the same. Misaligning catalog schemas from actual data can cause confusion. Option D — backfilling old files is technically possible but extremely expensive (rewriting 2.5 years of data) for no behavioral change — Athena already returns NULL for the missing column, which is semantically equivalent to an explicit NULL column.
  • Enum-type partition projection requires explicit enumeration of all valid values: (1) the projection.region.values property defines the complete set of valid region values; (2) Athena ONLY generates paths for values listed in this property; (3) "ap-southeast-1" is not in the current list, so Athena never constructs paths for it, hence zero results; (4) updating via ALTER TABLE SET TBLPROPERTIES ('projection.region.values'='us-east-1,us-west-2,eu-west-1,ap-southeast-1') immediately includes the new region; (5) this is a metadata-only change — no data movement or crawler run needed. This is the trade-off of enum-type projection: you get fast, deterministic partition resolution but must manually maintain the values list. Option B — when partition projection is enabled, Athena ignores catalog-based partitions entirely; MSCK REPAIR TABLE has no effect on projected tables because the catalog partitions aren't consulted. Option C — partition projection never scans S3 to discover values; it uses only the defined configuration. Disabling/re-enabling doesn't add auto-discovery. Option D — "injected" type requires the query to always include the partition column in the WHERE clause with specific values, and those values are passed directly to the path template. It doesn't auto-discover values from S3 either, and it removes the ability to query across all regions without explicitly listing them in WHERE.
