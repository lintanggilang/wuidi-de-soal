LakeFormationLF-Tags

Key Services & Concepts

AWS Lake Formation
Tata kelola data lake: permission based on table/column/rows and LF-Tags in above Glue Catalog.

Key Points

  • Transisi to Lake Formation melibatkan changes permission model: Before Lake Formation: Access dikontrol by IAM policies (glue:GetTable, s3:GetObject) + S3 bucket policies. Group "IAMAllowedPrincipals" in Lake Formation in a default provides "Super" permission to all databases — effectively bypassing Lake Formation permissions. Setelah migration (removing IAMAllowedPrincipals): Lake Formation becomes authoritative — principals MUST has BOTH: (1) IAM policy that allows Lake Formation/Glue/S3 API calls, DAN (2) Lake Formation GRANT on specific database/table/column. Without Lake Formation GRANT, although IAM policy allows glue:GetTable and s3:GetObject, access DENIED. Migration steps: (1) Identify all principals needing access, (2) Create Lake Formation GRANTs for each, (3) THEN remove IAMAllowedPrincipals.
  • Lake Formation Data Filters (also dikenal as Data Cell Filtering) enables fine-grained access control: Row-Level Filter: Ekspresi that mendefinisikan rows mana that visible. Contoh: "region = 'US'" — only rows with region US that returned to querier. Column-Level Control: Specify included columns (whitelist) or excluded columns (blacklist). Contoh: exclude "ssn" column. Cell-Level Security: Kombinasi row + column filtering. Specific cells (intersection of filtered rows and columns) that accessible. Implementation: (1) CREATE DATA FILTER us_team_filter ON TABLE transactions WITH ROW FILTER EXPRESSION "region = 'US'" AND COLUMN EXCLUSION ["ssn"]; (2) GRANT SELECT ON TABLE transactions WITH DATA FILTER us_team_filter TO PRINCIPAL us_team_role; When US team queries: SELECT * FROM transactions → automatic only melihat US rows, without SSN column.
  • LF-Tags (Lake Formation Tag-Based Access Control) is ABAC pattern for data lakes: Step 1 — Define LF-Tag keys: "classification" (values: public, internal, confidential), "domain" (values: finance, marketing, engineering). Step 2 — Assign tags to resources: Table "revenue" → classification=confidential, domain=finance. Table "web_analytics" → classification=internal, domain=marketing. Step 3 — Grant permissions based on tags: GRANT SELECT TO analytics_role ON TAG (classification=internal OR classification=public) AND (domain=marketing); Result: analytics_role automatically gets access to ALL current and future tables that match tag expression. Scale benefit: 500 tables × 200 roles = 100,000 potential individual grants. By LF-Tags: ~10-20 tag-based grant expressions cover all scenarios. New tables automatically get permissions when tagged.
  • Lake Formation cross-account sharing workflow: Account A (Data Owner): (1) Register S3 locations with Lake Formation, (2) GRANT SELECT on databases/tables to Account B (AWS account ID, IAM role ARN, or Organization ID), (3) Optionally choose sharing method: Named Resource method or LF-Tag method. Account B (Data Consumer): (1) Accept the resource share (via AWS RAM if applicable), (2) Create Resource Link in local Glue catalog: This is a pointer to Account A's shared database/table. Resource link appears as local catalog entry. (3) GRANT Lake Formation permissions on resource link to local IAM principals (e.g., Athena users/roles). (4) Local users query through resource link — transparently queries Account A's data. Key: Data stays in Account A's S3 — no copying. Lake Formation handles cross-account S3 access transparently.
  • Lake Formation permission model has nuance regarding S3 access: When S3 location is REGISTERED with Lake Formation: LF service role (AWSServiceRoleForLakeFormation) reads S3 on behalf of users. The USER'S S3 permissions are NOT evaluated — LF service role's permissions are used. In this case, S3 bucket policy denying the USER's role wouldn't block access because the service role is the one actually reading S3. When S3 location is NOT registered (or using hybrid mode): User's credentials are used for S3 access — bucket policy WOULD apply. Critical distinction: If S3 bucket policy denies the LAKE FORMATION SERVICE ROLE, then access blocked regardless. Best practice: Register all data lake S3 locations with Lake Formation so that permission management centralized. Remove broad IAMAllowedPrincipals access and let LF service role handle S3 reads.
  • Registering S3 locations with Lake Formation requires proper IAM role configuration: Registration: REGISTER RESOURCE s3://company-data-lake/ WITH IAM ROLE arn:aws:iam::account:role/LakeFormationDataAccessRole. The specified role needs: S3 Permissions: s3:GetObject, s3:PutObject, s3:DeleteObject on s3://company-data-lake/*, s3:ListBucket on the bucket. KMS Permissions (critical for encrypted data): kms:Decrypt — to read encrypted objects, kms:GenerateDataKey — to write encrypted objects, kms:DescribeKey — to verify key status. Additionally, KMS Key Policy must include: {"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::account:role/LakeFormationDataAccessRole"}, "Action": ["kms:Decrypt", "kms:GenerateDataKey", "kms:DescribeKey"], "Resource": "*"}. Without KMS permissions, Lake Formation reads will fail with AccessDenied even if S3 permissions are correct.
  • Hybrid Access Mode allows per-database/table opt-in to Lake Formation: Databases NOT opted-in (legacy mode): IAMAllowedPrincipals group retains "Super" permission. Any IAM principal with glue:GetTable, s3:GetObject permissions can access data. Lake Formation grants are ignored. This is the DEFAULT state for existing databases. Databases OPTED-IN to Lake Formation: IAMAllowedPrincipals is removed (or restricted). Access requires: (1) IAM policy allowing Glue/Athena/LF API calls (e.g., lakeformation:GetDataAccess, glue:GetTable), AND (2) Explicit Lake Formation GRANT to the principal. Migration strategy: Opt-in databases one at a time — add LF grants to all principals, then remove IAMAllowedPrincipals. If something breaks, can revert by re-adding IAMAllowedPrincipals.
  • WITH GRANT OPTION in Lake Formation mendelegasikan granting authority: Without GRANT OPTION: Principal can use the permission (SELECT) but CANNOT share it with others. By GRANT OPTION: Principal can both USE the permission AND GRANT it to other principals. Constraints: (1) Can only grant permissions they themselves hold — analyst has SELECT, so can only grant SELECT (not INSERT, ALTER, DROP, etc.). (2) Can grant to other roles/users but not beyond their own permission scope. (3) If the original grant is REVOKED, all downstream grants (cascading) can also be revoked. Use case: Data stewardship model — domain owners receive permissions WITH GRANT OPTION and manage access for their team without involving Lake Formation admin for every request. Decentralized governance.
  • EMR + Lake Formation integration requires specific configuration: Standard EMR (without LF integration): EMR uses instance profile to access S3 directly. Lake Formation permissions are NOT enforced — only IAM + S3 policies apply. Anyone on the cluster with instance profile access can read ALL data. EMR with Lake Formation integration: (1) Configure EMR Security Configuration with Lake Formation enabled. (2) EMR uses "credential vending" — instead of using instance profile for S3, it calls Lake Formation's GetDataAccess API. (3) Lake Formation returns temporary, scoped credentials that only allow access to data the requesting principal is granted. (4) Per-user/per-job enforcement — different users on same cluster get different credentials. (5) Supports SAML-based user identity for fine-grained access. Requirements: EMR runtime roles support, Lake Formation grants to the runtime role or user identity, EMR cluster configured with proper security configuration.
  • Permission evaluation precedence (highest to lowest): (1) Explicit Deny (any layer) — ALWAYS wins. IAM explicit Deny overrides everything. (2) Service Control Policies (SCPs) — organization-level ceiling. (3) Permission Boundaries — identity-level ceiling. (4) IAM Allow + Lake Formation Grant — BOTH required for access. (5) S3/Resource policies — additional layer. In this scenario: Athena query process: Step 1: Athena calls Glue:GetTable to read table metadata → IAM evaluates → EXPLICIT DENY found → request FAILS immediately. Query never reaches Step 2 (actual data read from S3). Lake Formation permissions work ALONGSIDE IAM, not above it. For successful access, principal needs: (1) NO explicit IAM Deny on relevant actions, (2) IAM Allow for service APIs (glue:GetTable, lakeformation:GetDataAccess, athena:StartQueryExecution), (3) Lake Formation GRANT on the table.

Common Misconceptions & Pitfalls

  • Incorrect — Athena natively integrates with LF.
  • Incorrect — LF handles KMS encrypted data.
  • Re-crawl not required for permission changes.
  • Not enforced server-side, bypassable.
  • Data duplication, ETL complexity.
  • S3 not aware of column-level content.
  • Custom code maintenance burden, eventual consistency issues.
  • SCPs are for API-level controls, not data-level.
  • Would require S3 cross-account access AND creates duplicate metadata.
  • Data duplication, latency, cost.
  • Requires complex bucket policy management and doesn't leverage LF governance.
  • Either full results or access denied, not empty.
  • Incorrect — bucket policies remain intact.
  • Oversimplifies — LF doesn't "override" bucket policies, it uses different access path.
  • Incorrect — Lake Formation fully supports KMS.
  • Incorrect — KMS permissions require explicit configuration.
  • Nothing random, behavior is deterministic per-database.
  • Incorrect — LF is active for opted-in DBs.
  • Incorrect — hybrid is per-database.
  • Incorrect — non-admins with GRANT OPTION can grant.
  • Incorrect — GRANT OPTION is about delegation not expiry.
  • Incorrect — scope limited to what they themselves have.
  • Incorrect — EMR does support LF integration.
  • Defeats purpose of LF (bypasses fine-grained control).
  • No scheduled evaluation window concept in LF.
  • No loop, evaluation is deterministic.
  • Incorrect — LF does not override IAM.
