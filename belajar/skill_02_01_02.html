Key Points

  • This design optimally serves the primary access pattern: Query operation on partition key device_id with sort key condition (timestamp BETWEEN start AND end) retrieves all readings for a device in a time range in a single efficient operation — no scan required. With 2 million unique devices, writes distribute evenly across partitions (avoiding hot partitions). The GSI on sensor_type enables the secondary pattern without compromising the base table design.
  • ALL distribution replicates the small products table (50 MB) on every node, so JOIN operations between orders and products are always local — zero network traffic for the JOIN. The 50 MB dimension table has negligible storage overhead when replicated across 4 nodes (200 MB total). The compound sort key on the orders table with order_date first enables zone map-based block skipping for date range filters, dramatically reducing I/O.
  • Read replicas offload read-heavy reporting queries from the primary instance, eliminating contention. Routing enterprise reporting to replicas during business hours handles the 80% read load separately while the primary serves writes and standard tenant queries without contention. RDS supports up to 5 read replicas per instance, providing scalable read capacity. This targets the specific access pattern (read-heavy enterprise reporting) without over-engineering.
  • This multi-pronged optimization addresses Athena's cost model ($5/TB scanned): (1) secondary partition on event_type allows quarterly queries that filter by specific events to skip entire partitions, potentially reducing scanned data by 80%+; (2) Parquet columnar format means Athena only reads required columns (vs. all columns in CSV/JSON); (3) compression reduces physical bytes scanned; (4) partition projection eliminates catalog lookup latency for the deeply nested partition structure. Together, a $250 quarterly query might drop to $30-50.
  • Three separate GSIs, each optimized for its specific access pattern, provides the best performance and cost efficiency: (1) email GSI handles 10K RPS login lookups as O(1) point reads; (2) city GSI groups users by city for efficient listing; (3) registration_month GSI enables time-range queries. Projecting only needed attributes (KEYS_ONLY or INCLUDE specific attributes) minimizes GSI storage and write costs. Each GSI can have independent provisioned capacity matching its traffic pattern.
  • Materialized views pre-compute and physically store query results, serving subsequent queries from the stored result set in milliseconds. AUTO REFRESH keeps the materialized view synchronized with base table changes, ensuring dashboard data freshness. Since the 20 queries are predictable and repeated, materialized views eliminate the 45-second full scan on every refresh. Redshift can also automatically rewrite incoming queries to use materialized views transparently.
  • WLM provides performance isolation by allocating resources to query queues — large tenants get dedicated resources that can't starve smaller tenants, even when running resource-intensive queries. Queue concurrency limits prevent large tenants from monopolizing all query slots. Row-Level Security (RLS) enforces data isolation at the database level — users see only their tenant's rows regardless of the SQL they execute, preventing accidental or malicious cross-tenant data access. Together, these address both requirements.
  • This design leverages DynamoDB's native capabilities optimally: (1) GSI with customer_id as partition key groups all orders for a customer together; (2) order_date as sort key physically stores items in chronological order within the partition; (3) ScanIndexForward=false reverses the sort for "most recent first"; (4) Limit=20 returns exactly one page; (5) LastEvaluatedKey/ExclusiveStartKey provides server-side cursor-based pagination that's efficient regardless of dataset size. Each page request reads only 20 items — O(1) cost per page.
  • WLM queue configuration with SQA directly solves the mixed-workload problem: (1) separate queues ensure analytical queries cannot consume resources allocated to API queries; (2) high concurrency for API queue means many short queries can execute simultaneously; (3) SQA detects short-running queries and routes them to a special fast lane, bypassing queued long queries; (4) query timeouts prevent runaway queries from holding resources indefinitely. This guarantees API queries get dedicated resources regardless of analytical workload.
  • Lake Formation column-level permissions are purpose-built for this scenario: permissions are granted on specific columns to specific principals, and enforcement happens transparently at query time — if Finance queries SELECT * FROM employees, Lake Formation automatically excludes SSN from results. This works across Athena, Redshift Spectrum, and Glue jobs without application changes. Single source of truth, centralized management, auditable access.

Common Misconceptions & Pitfalls

  • Timestamp as partition key creates a "hot partition" problem where all current writes go to the same hourly partition, causing throttling.
  • Composite string as sole key prevents range queries; DynamoDB cannot do "BETWEEN" on partition keys, requiring expensive full table Scans.
  • Sensor_type as partition key concentrates all writes for a sensor type (eg., "temperature" from millions of devices) into a single partition — extreme hot partition.
  • Distributing the 2 TB orders table with ALL would replicate it on every node (8 TB total storage), which is impractical and wastes storage.
  • KEY distribution on both tables co-locates matching keys but the small products table would be sparse on each node (12.5 MB/node), and JOIN performance is identical to ALL distribution while adding complexity.
  • EVEN distribution requires redistributing data at JOIN time (full network shuffle), which is the current performance problem.
  • Vertical scaling has limits (max instance size) and doesn't solve read contention — more CPU/RAM on a single instance still means shared I/O.
  • Multi-AZ standby is for failover only; it does NOT serve read traffic (it's a synchronous replica that handles only failover scenarios).
  • Splitting tenants into separate instances adds operational complexity, cross-instance queries, and doesn't leverage RDS's built-in read replica capability.
  • S3 Select works with individual objects and doesn't integrate well with Athena's partition pruning or columnar format optimizations.
  • File size optimization helps with listing overhead but doesn't reduce data scanned (the main cost driver).
  • Glacier has minimum 1-12 hour restore times, making quarterly reports impractical without advance planning; restore costs are also significant.
  • LSIs require a composite primary key (partition + sort) on the base table and share throughput with the base table; they can't be created on a table that already exists with a simple key.
  • GSI overloading with a single index means all three access patterns compete for the same partition key space and provisioned capacity; the 10K RPS email pattern would dominate capacity, and the different access pattern frequencies make independent scaling impossible.
  • Scan operations read every item in the table and apply filters after reading, consuming full table RCUs regardless of result set size — prohibitively expensive at scale.
  • Regular views are just stored query text; they execute the full query every time they're accessed, providing no performance benefit over querying tables directly.
  • Result caching works for identical queries (same SQL text and parameters), but dashboard queries with different time-range parameters produce different SQL each time, bypassing the cache.
  • Adding nodes provides linear speedup (45s → maybe 15-20s with double nodes) but cannot achieve the sub-5-second requirement without addressing the fundamental access pattern.
  • 1,000 separate clusters is operationally impractical and prohibitively expensive (~$1M+/year at minimum cluster costs).
  • IAM controls who can connect to the cluster but cannot restrict which rows within shared tables a user can see.
  • Application-level filtering is error-prone (one missed WHERE clause exposes all data) and provides no performance isolation between tenants.
  • Scan reads the entire table (all customers' orders), consuming massive RCUs and taking minutes; offset-based pagination requires re-reading all previous pages.
  • DynamoDB items have a 400 KB limit; thousands of orders would exceed this, and list operations don't support efficient pagination.
  • Without a sort key, Query returns items in arbitrary order within the partition; application-side sorting requires fetching ALL items first, defeating pagination efficiency.
  • More resources reduce contention probability but don't guarantee isolation; a sufficiently complex analytical query can still monopolize shared resources.
  • Scheduling restricts analytical work to limited hours, reducing productivity without addressing the fundamental resource contention when both must run.
  • Concurrency scaling adds capacity when queues are full but doesn't prioritize short queries over long ones; API queries may still wait behind analytical queries in the queue.
  • Named queries are suggestions, not enforcement; users can write their own SQL selecting any columns, providing no actual security.
  • Data duplication creates sync issues (updates must propagate to all copies), triples storage costs, and doesn't prevent someone from accessing the wrong copy.
  • IAM cannot provide column-level access control within Parquet files; S3 permissions are at the object (file) level, not column level.
