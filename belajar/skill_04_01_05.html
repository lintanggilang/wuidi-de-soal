Domain 4: Security & Governance — Task 4.1: Apply authentication mechanisms

Skill 4.1.5: IAM policies (Access Points, PrivateLink)

IAMpoliciesAccessPointsPrivateLink

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.1: Apply authentication mechanisms), dengan fokus pada iam policies (access points, privatelink). Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS IAM
Identity and Access Management: user, group, role, dan policy untuk akses least-privilege.
AWS PrivateLink
Akses privat ke layanan via interface endpoint tanpa melewati internet publik.
S3 Access Points
Endpoint bernama dengan policy sendiri untuk menyederhanakan akses ke bucket besar bersama.

Poin-Poin Kunci

  • S3 Access Points dirancang khusus untuk menyederhanakan access management pada shared buckets. Setiap Access Point memiliki hostname unik dan access point policy tersendiri yang bisa membatasi akses ke prefix tertentu. Tim Analytics mengakses melalui access-point-analytics, ML melalui access-point-ml, dll. Ini menggantikan satu bucket policy yang kompleks dengan multiple simple policies.
  • VPC endpoint policies control API calls yang diperbolehkan melalui endpoint tersebut. Dengan membatasi resource ke ARN dua bucket spesifik (arn:aws:s3:::data-lake-bucket dan arn:aws:s3:::data-lake-bucket/*), semua request S3 melalui endpoint ini hanya bisa mengakses kedua bucket tersebut. Ini memberikan defense-in-depth tambahan.
  • Bucket policy dengan explicit Deny menggunakan condition "aws:SourceVpc" memastikan bahwa SEMUA requests yang tidak berasal dari VPC yang ditentukan akan ditolak, terlepas dari IAM permissions yang ada. Statement: {"Effect": "Deny", "Principal": "*", "Action": "s3:*", "Resource": ["bucket-arn", "bucket-arn/*"], "Condition": {"StringNotEquals": {"aws:SourceVpc": "vpc-12345"}}}. Explicit Deny selalu override Allow.
  • AWS PrivateLink menggunakan Interface Endpoints (powered by ENIs) di consumer VPC yang terhubung ke provider's VPC Endpoint Service (backed by NLB). Engineer perlu: (1) Create Interface Endpoint di VPC-A dengan service name yang diberikan provider (com.amazonaws.vpce.region.vpce-svc-xxxxx). (2) Accept the connection (provider mungkin perlu approve). (3) Configure security group pada endpoint ENI untuk allow traffic dari data processing service. Data mengalir melalui AWS private network.
  • aws:PrincipalOrgID adalah global condition key yang memeriksa apakah calling principal berasal dari AWS Organization tertentu. Dengan menambahkan Allow statement bersyarat pada aws:PrincipalOrgID, hanya principals dari accounts yang merupakan member organization o-abc123def yang mendapat akses. Ini sangat berguna untuk shared resources — saat account baru ditambahkan ke organization, mereka otomatis mendapat akses tanpa perlu mengupdate bucket policy.
  • VPC endpoint policies berfungsi sebagai additional access control layer (filter). Request harus diizinkan oleh SEMUA policies yang relevan: IAM policy, resource policy (bucket policy), DAN VPC endpoint policy. Jika VPC endpoint policy tidak mengizinkan akses ke bucket tersebut, request akan ditolak meskipun IAM dan bucket policy mengizinkan. VPC endpoint policy bersifat intersectional — request hanya berhasil jika diizinkan oleh semua layer.
  • Untuk memberikan cross-account access ke specific role, gunakan role ARN sebagai Principal. Ini memberikan akses hanya ke DataProcessorRole di Account B, bukan semua entities di account tersebut. Ini adalah pendekatan paling restrictive dan mengikuti least privilege.
  • S3 Block Public Access di account level adalah preventive control paling kuat. Saat diaktifkan, ini secara otomatis memblokir semua konfigurasi public access pada SEMUA buckets di account — termasuk public bucket policies, public ACLs, dan new public bucket/access point policies. Bahkan jika developer menambahkan bucket policy dengan Principal "*", Block Public Access akan override dan tetap memblokir public access.
  • S3 Access Points tidak override bucket policies. Access dikontrol oleh INTERSECTION dari Access Point policy dan bucket policy (plus IAM policy). Explicit Deny di bucket policy selalu menang — ini adalah prinsip fundamental IAM policy evaluation. Access Points dimaksudkan untuk menyederhanakan policy management, bukan untuk bypass existing restrictions. Jika bucket policy explicitly deny akses dari role tertentu, Access Point tidak bisa memberikan akses tersebut.
  • Defense-in-depth memerlukan multiple layers of control: (1) IAM policy — controls what the Lambda role can do (only specific buckets). (2) VPC endpoint policy — controls what can be accessed through the endpoint (only same specific buckets). Bahkan jika attacker mendapat credentials berbeda, endpoint hanya mengizinkan traffic ke designated buckets. (3) S3 bucket policy with aws:SourceVpce — ensures bucket hanya accessible dari VPC endpoint tertentu, mencegah akses dari lokasi lain. Ketiga layer bersama-sama membuat exfiltration sangat sulit.

Miskonsepsi & Jebakan Umum

  • Menambah biaya storage dan complexity sinkronisasi shared data.
  • Tidak memungkinkan resource-based control dan sulit mengelola untuk banyak tim.
  • Hanya mengontrol dari sisi identity, tidak memberikan resource-level simplification yang sama.
  • Bisa jadi defense-in-depth tambahan tapi tidak membatasi endpoint itu sendiri — resources di VPC masih bisa mencoba akses bucket lain.
  • Salah — Gateway endpoints tidak memiliki security groups (hanya Interface endpoints yang punya).
  • Salah — S3 Gateway endpoint menggunakan prefix list di route table, bukan per-bucket IP routing.
  • Tidak scalable dan tidak mencegah policies ditambahkan kembali.
  • Bukan konsep yang valid — S3 bukan "target" endpoint.
  • Hanya memblokir public access via ACLs/policies, bukan access dari other VPCs atau AWS accounts.
  • Berlebihan untuk single service connection.
  • Menggunakan internet dan lebih lambat.
  • Memerlukan kooperasi provider dan membuka akses lebih luas.
  • Menggunakan format ARN yang salah untuk org condition.
  • Hanya memeriksa satu account, bukan seluruh organization.
  • Salah — aws:SourceAccount hanya tersedia untuk service-to-service calls, bukan langsung applicable untuk org ID.
  • Salah — endpoint policy juga harus allow.
  • Salah — endpoint policies bersifat enforcing, bukan advisory.
  • Salah — jika traffic diroute melalui endpoint (via route table), tidak ada fallback ke internet path; request akan fail.
  • Mengizinkan ALL Lambda functions dari semua accounts — sangat tidak aman.
  • Memberikan akses ke SEMUA principals di Account B yang memiliki IAM permission — kurang restrictive.
  • Dengan SourceAccount condition masih terlalu broad — mengizinkan semua principals di Account B, dan aws:SourceAccount condition tidak selalu tersedia untuk direct API calls.
  • Adalah detective control (deteksi + remediate) — ada window dimana bucket sudah public sebelum remediation.
  • Memerlukan penerapan di setiap bucket dan bisa dihapus oleh developer.
  • Hanya detection dan alerting, bukan prevention.
  • Salah — Access Points tidak override.
  • Salah — Access Point tetap valid, hanya permissions yang terbatas.
  • Salah jika Deny diterapkan pada semua S3 actions (tergantung apa yang di-deny di bucket policy).
  • Kurang IAM restriction dan NACLs tidak bisa distinguish antar S3 buckets.
  • Single layer, jika credentials compromised, bisa digunakan dari mana saja.
  • Lambda private IPs bersifat dynamic dan berubah setiap invocation.
