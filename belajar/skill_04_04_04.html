Skill 4.4.4: Log analysis with AWS services

AthenaOpenSearchLogsInsights

Summary

Skill this including in Domain 4: Security & Governance (Task 4.4: Prepare logs for audit), with fokus on log analysis with aws services. Materi berikut merangkum service AWS that relevan along with concept important that needs kamu kuasai for topik this.

Key Services & Concepts

Amazon Athena
Query SQL serverless against data in S3 (Presto/Trino); bayar per data that is scanned.
Amazon OpenSearch
Pencarian & analitik log near real-time; suitable for observability and full-text search.
CloudWatch Logs
Pengumpulan & storage log; CloudWatch Logs Insights for query log.

Key Points

  • Partition projection eliminates requirements for runs MSCK REPAIR TABLE or adds partition manually, that very important for data that terus bertambah each days. By date-type projection matching path pattern (s3://bucket/AWSLogs/account/CloudTrail/region/yyyy/mm/dd/), Athena automatically calculates partition without metadata calls to Glue catalog. Query with WHERE date = '2024-03-15' only scan data days that (~27 GB vs 50 TB), very reduces cost.
  • CloudWatch Logs Insights can query up to 50 log groups in a simultaneously and provides result in hitungan seconds for data recent. Query: `filter @message like /ERROR/ | stats count(*) as errorCount by @logGroup | sort errorCount desc | limit 10` will provides top 10 functions with error terbanyak. Supports wildcard pattern for log group selection.
  • Amazon OpenSearch Service memenuhi all requirements: sub-second search latency through inverted indexing, full-text search across all fields, real-time dashboards via OpenSearch Dashboards (Kibana successor), and built-in alerting plugin for notifications. By 2 TB/day, OpenSearch can handles volume this with cluster that appropriately sized.
  • API Gateway access logs, if in format custom or CLF, stores status code as part from messages log. CloudWatch Logs Insights requires `parse` command for mengekstrak fields from log messages that not in format JSON that automatic in-discover. Contoh: `parse @message "* * * *" as ip, method, path, status | filter status >= 500`. For JSON logs, fields automatic available but must direferensikan with prefix that correct.
  • Solution optimal memilih tool based on volume, frekuensi query, and latency requirement: (1) VPC Flow Logs 500 GB/day that in-query weekly suitable for Athena + S3 Parquet — cost storage low and bayar per query, partition reduces scan. (2) Application logs 50 GB/day with interactive queries multiple times/day suitable for OpenSearch that provides sub-second latency and rich dashboards. (3) CloudTrail 10 GB/day that rarely in-query suitable for Athena — cost very low because rarely query.
  • Uses CloudTrail SerDe that didesain khusus for format CloudTrail JSON, mendefinisikan struct types for nested fields (userIdentity STRUCT ), and partition projection for date provides kombinasi best. Struct types enables dot notation queries (userIdentity.arn) and partition projection mengeliminasi overhead metadata management.
  • OpenSearch Service provides three tiers: Hot (instance store/EBS, fastest), UltraWarm (S3-backed, cost-effective for data that rarely diakses but still searchable), and Cold storage (most cheap, data must in-attach returns to warm before can in-search). Konfigurasi B memenuhi all requirements: hot for dashboards real-time (0-30d), UltraWarm for searchable with latency higher (30-90d), cold for compliance archival (90d+).
  • CloudWatch Contributor Insights designed khusus for top-N analysis in real-time. Rules can is configured for filters log events (for example status >= 500) and mengelompokkan based on field keys (endpoint, sourceIP, userAgent). Dashboard automatically menampilkan top contributors that changes in real-time.
  • Infrastructure logs (7 TB) that only in-query monthly merupakan 70% from active data but rarely diakses. Memindahkannya to S3 (cost ~$0.023/GB/month) and query with Athena ($5/TB scanned) monthly jauh cheaper from stores in OpenSearch hot nodes. Mengecilkan OpenSearch cluster from 10 TB to 3 TB provides penghematan significant on instance costs.
  • In CloudWatch Logs Insights, function `percentile(field, percent)` calculates persentil that is determined. Syntax `stats percentile(latency_ms, 99) as p99 by endpoint` mengelompokkan based on endpoint and calculates p99 latency. `sort p99 desc` mengurutkan from tertinggi.
