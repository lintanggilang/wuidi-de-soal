Skill 4.4.4: Log analysis with AWS services

AthenaOpenSearchLogsInsights

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.4: Prepare logs for audit), dengan fokus pada log analysis with aws services. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon Athena
Query SQL serverless terhadap data di S3 (Presto/Trino); bayar per data yang dipindai.
Amazon OpenSearch
Pencarian & analitik log near real-time; cocok untuk observability dan full-text search.
CloudWatch Logs
Pengumpulan & penyimpanan log; CloudWatch Logs Insights untuk query log.

Poin-Poin Kunci

  • Partition projection menghilangkan kebutuhan untuk menjalankan MSCK REPAIR TABLE atau menambah partisi secara manual, yang sangat penting untuk data yang terus bertambah setiap hari. Dengan date-type projection matching path pattern (s3://bucket/AWSLogs/account/CloudTrail/region/yyyy/mm/dd/), Athena secara otomatis menghitung partisi tanpa metadata calls ke Glue catalog. Query dengan WHERE date = '2024-03-15' hanya scan data hari itu (~27 GB vs 50 TB), sangat mengurangi biaya.
  • CloudWatch Logs Insights dapat query hingga 50 log groups secara bersamaan dan memberikan hasil dalam hitungan detik untuk data recent. Query: `filter @message like /ERROR/ | stats count(*) as errorCount by @logGroup | sort errorCount desc | limit 10` akan memberikan top 10 functions dengan error terbanyak. Mendukung wildcard pattern untuk log group selection.
  • Amazon OpenSearch Service memenuhi semua requirements: sub-second search latency melalui inverted indexing, full-text search across all fields, real-time dashboards via OpenSearch Dashboards (Kibana successor), dan built-in alerting plugin untuk notifications. Dengan 2 TB/day, OpenSearch dapat menangani volume ini dengan cluster yang appropriately sized.
  • API Gateway access logs, jika dalam format custom atau CLF, menyimpan status code sebagai bagian dari pesan log. CloudWatch Logs Insights memerlukan `parse` command untuk mengekstrak fields dari log messages yang tidak dalam format JSON yang otomatis di-discover. Contoh: `parse @message "* * * *" as ip, method, path, status | filter status >= 500`. Untuk JSON logs, fields otomatis tersedia tapi harus direferensikan dengan prefix yang benar.
  • Solusi optimal memilih tool berdasarkan volume, frekuensi query, dan latency requirement: (1) VPC Flow Logs 500 GB/day yang di-query weekly cocok untuk Athena + S3 Parquet — biaya storage rendah dan bayar per query, partisi mengurangi scan. (2) Application logs 50 GB/day dengan interactive queries multiple times/day cocok untuk OpenSearch yang memberikan sub-second latency dan rich dashboards. (3) CloudTrail 10 GB/day yang jarang di-query cocok untuk Athena — biaya sangat rendah karena jarang query.
  • Menggunakan CloudTrail SerDe yang didesain khusus untuk format CloudTrail JSON, mendefinisikan struct types untuk nested fields (userIdentity STRUCT ), dan partition projection untuk tanggal memberikan kombinasi terbaik. Struct types memungkinkan dot notation queries (userIdentity.arn) dan partition projection mengeliminasi overhead metadata management.
  • OpenSearch Service menyediakan tiga tiers: Hot (instance store/EBS, fastest), UltraWarm (S3-backed, cost-effective untuk data yang jarang diakses tapi masih searchable), dan Cold storage (paling murah, data harus di-attach kembali ke warm sebelum bisa di-search). Konfigurasi B memenuhi semua requirements: hot untuk dashboards real-time (0-30d), UltraWarm untuk searchable dengan latency lebih tinggi (30-90d), cold untuk compliance archival (90d+).
  • CloudWatch Contributor Insights dirancang khusus untuk top-N analysis secara real-time. Rules dapat dikonfigurasi untuk memfilter log events (misalnya status >= 500) dan mengelompokkan berdasarkan field keys (endpoint, sourceIP, userAgent). Dashboard secara otomatis menampilkan top contributors yang berubah secara real-time.
  • Infrastructure logs (7 TB) yang hanya di-query monthly merupakan 70% dari active data tapi jarang diakses. Memindahkannya ke S3 (biaya ~$0.023/GB/month) dan query dengan Athena ($5/TB scanned) monthly jauh lebih murah dari menyimpan di OpenSearch hot nodes. Mengecilkan OpenSearch cluster dari 10 TB ke 3 TB memberikan penghematan signifikan pada instance costs.
  • Dalam CloudWatch Logs Insights, fungsi `percentile(field, percent)` menghitung persentil yang ditentukan. Syntax `stats percentile(latency_ms, 99) as p99 by endpoint` mengelompokkan berdasarkan endpoint dan menghitung p99 latency. `sort p99 desc` mengurutkan dari tertinggi.

Miskonsepsi & Jebakan Umum

  • Berfungsi tapi memerlukan maintenance partisi manual.
  • Memerlukan scan full data terlebih dahulu dan menambah biaya storage.
  • Tanpa partisi akan scan seluruh 50 TB (sangat mahal).
  • Memerlukan export ke S3 terlebih dahulu dan tidak memberikan hasil real-time.
  • Menunjukkan error count per function tapi tidak memberikan ranking top-N dalam satu query dan memerlukan navigasi manual.
  • Memerlukan setup dan ingestion pipeline yang sudah berjalan — bukan solusi "quick".
  • Memiliki query latency beberapa detik dan tidak mendukung full-text search dengan sub-second response pada 2 TB daily data.
  • Tidak dioptimasi untuk full-text search dan materialized view refresh setiap menit bukan real-time.
  • Bersifat batch dan tidak memberikan sub-second latency untuk interactive search.
  • Salah — filter sebelum stats adalah urutan yang benar dan valid.
  • Salah — `bin(5m)` adalah syntax valid yang menggunakan @timestamp secara implisit.
  • Salah — >= operator bekerja setelah field di-parse dengan benar.
  • CloudWatch Logs Insights memiliki biaya ingestion tinggi untuk 500 GB/day.
  • Bisa bekerja tapi CloudWatch Logs Insights kurang ideal untuk 50 GB/day interactive analysis dan CloudTrail Lake mahal untuk occasional queries.
  • Sangat mahal untuk 500 GB/day VPC logs yang jarang diquery.
  • Memberikan performance terbaik per-query tapi memerlukan proses konversi ongoing dan double storage costs.
  • Kehilangan kemampuan query nested fields secara langsung — harus menggunakan JSON functions yang lebih lambat.
  • Tanpa partition projection memerlukan manual partition management.
  • Kehilangan kemampuan search di OpenSearch setelah 30 hari.
  • Menghapus data setelah 90 hari padahal compliance masih memerlukan retention.
  • Sangat mahal karena hot tier untuk semua data.
  • Bukan real-time — setiap query adalah point-in-time dan harus dijalankan ulang secara manual.
  • Memerlukan pre-aggregation dan tidak memberikan dynamic top-N ranking.
  • Mendeteksi deviasi dari baseline tapi tidak dirancang untuk ranking top contributors.
  • Terlalu agresif dan membuat interactive queries lambat untuk security investigation.
  • Kehilangan kemampuan full log analysis — metrics bukan pengganti log search.
  • Akan sangat mahal untuk 10 TB data ingestion.
  • Menggunakan `avg()` yang menghitung rata-rata, bukan persentil ke-99.
  • Menggunakan `p99()` yang bukan syntax function yang valid — harus menggunakan percentile(field, 99).
  • Menggunakan `pct()` yang bukan fungsi valid di CloudWatch Logs Insights — fungsi yang benar adalah `percentile()`.
