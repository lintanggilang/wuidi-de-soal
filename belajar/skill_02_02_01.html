Domain 2: Data Store Management — Task 2.2: Understand data cataloging systems

Skill 2.2.1: Use data catalogs to consume data

GlueDataCatalogdiscovery

Ringkasan

Skill ini termasuk dalam Domain 2: Data Store Management (Task 2.2: Understand data cataloging systems), dengan fokus pada use data catalogs to consume data. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS Glue
ETL serverless berbasis Spark + Data Catalog; ideal untuk transformasi dan katalogisasi data.
Glue Data Catalog
Metastore terpusat (Hive-compatible) berisi definisi tabel/partisi yang dipakai Athena, EMR, Redshift Spectrum.
CloudWatch Logs
Pengumpulan & penyimpanan log; CloudWatch Logs Insights untuk query log.

Poin-Poin Kunci

  • Lake Formation's cross-account catalog sharing provides centralized data discovery without data movement: (1) each business unit's Glue Data Catalog is shared with the central governance account via Lake Formation grants (database/table-level sharing); (2) analysts in the central account see a unified view of all shared databases and tables across all 15 accounts; (3) schema information, partition details, and table properties are visible without executing queries; (4) Lake Formation permissions control who can discover (see metadata) vs. who can access (query data), providing layered security; (5) no data duplication — analysts still query data in its source location, but discovery is centralized.
  • The Glue Data Catalog functions as a searchable metadata repository: (1) the catalog search API and console allow text search across table names, column names, descriptions, and custom properties; (2) searching "purchase" surfaces tables with purchase-related columns even if the table name is non-obvious (e.g., a table named "fact_transactions" with a column "purchase_amount"); (3) business metadata tags (added by data stewards) like "domain:sales" or "contains:purchase-data" enhance discoverability; (4) the catalog shows full schema details, data location, partition structure, and last-updated timestamps without requiring query execution. This is the primary use case for a data catalog — enabling discovery without pre-existing knowledge of data organization.
  • Lake Formation provides fine-grained catalog-based access control: (1) column-level permissions let administrators grant SELECT on specific columns to specific principals — GRANT SELECT (patient_id, diagnosis_code) ON TABLE patient_records TO ROLE clinical_researchers; (2) when services query through the catalog, Lake Formation intercepts and filters columns the principal isn't authorized to see; (3) cell-level filtering (row-level) can further restrict access based on data values; (4) a single physical dataset serves all teams — no data duplication; (5) the catalog becomes the "data access API" where discovery and authorization are unified. This is the recommended architecture for regulated data in AWS.
  • Amazon DataZone transforms the technical catalog into a self-service data marketplace: (1) data producers publish curated "data products" with business descriptions, quality metrics, and usage documentation; (2) consumers browse and subscribe to data products through a user-friendly portal — no need to memorize database/table names; (3) subscriptions automatically provision the correct Athena access to the catalog tables; (4) schema changes, deprecations, and new datasets are visible immediately in the portal; (5) usage analytics show which datasets are most popular, helping analysts discover relevant data through community signals. This creates a "catalog-first" culture where discovery precedes consumption.
  • Redshift Spectrum's native Glue Data Catalog integration works through external schemas: (1) CREATE EXTERNAL SCHEMA spectrum_schema FROM DATA CATALOG DATABASE 'my_glue_db' IAM_ROLE 'arn:aws:iam::...' creates the link; (2) Redshift immediately sees all tables defined in that Glue database — no manual table creation needed; (3) as tables are added/modified in the Glue catalog (by crawlers, ETL jobs, or manual updates), Spectrum automatically picks up changes on next query; (4) partition information from the catalog is used for pruning (WHERE dt='2024-03-01' only scans that partition's S3 prefix); (5) analysts query with SELECT * FROM spectrum_schema.table_name using standard SQL. The catalog is the single source of truth for metadata.
  • LF-TBAC with resource links implements the data mesh pattern on AWS: (1) Tag-Based Access Control allows producers to tag tables with business metadata (LF-Tags like "domain=sales", "product=customer-360", "sensitivity=pii") and grant access based on tag expressions rather than individual table ARNs; (2) resource links create local catalog entries in the consumer's database that point to the producer's shared table — consumers query their own schema (SELECT * FROM my_catalog.customer_360) while data remains in the producer's account; (3) new data products are automatically discoverable by consumers who have matching tag-based grants; (4) this separates logical (tag-based discovery) from physical (actual database/table locations).
  • EMR's native Glue Data Catalog integration replaces the traditional Hive metastore: (1) setting the metastore factory class to AWS Glue's implementation makes ALL Spark SQL table references resolve against the Glue catalog transparently; (2) Spark jobs use standard SQL table references without knowledge of underlying storage (spark.table("sales_db.transactions") works whether the data is on S3, registered via a crawler, or defined manually); (3) catalog table properties store format, location, SerDe, schema, and connection details; (4) this is configured once at the EMR cluster level — all Spark jobs on the cluster automatically use catalog-based resolution; (5) changes to catalog metadata (new partitions, schema updates) are picked up by subsequent Spark queries without code changes.
  • Catalog enrichment with classification metadata provides discoverable data governance: (1) tiering (gold/silver/bronze) communicates data quality and authoritativeness at the catalog level — analysts searching for customer data see the gold-tier table first and understand it's the authoritative source; (2) business metadata (owner, refresh frequency, data quality score) helps analysts evaluate which dataset meets their needs; (3) "deprecated" status with migration guidance provides a transition path — existing queries referencing deprecated tables can be identified and migrated; (4) Lake Formation tags enable tag-based search (find all gold-tier tables in the sales domain); (5) this approach preserves historical tables for backward compatibility while clearly guiding new consumption.
  • Lake Formation cross-account sharing meets all four requirements: (1) named resource grants specify exact tables — the partner sees ONLY granted tables in their resource links, not the institution's full catalog; (2) data remains in the institution's S3 bucket — resource links point to the original location, no data copying occurs; (3) REVOKE permission immediately removes access — the partner's next query fails instantly without waiting for data deletion or bucket policy propagation; (4) CloudTrail records all cross-account Glue API calls (GetTable, GetPartitions) and Lake Formation access events provide query-level audit trails. The partner's experience: they see shared tables as local catalog entries and query normally through their own Athena.
  • Standardized catalog definitions ensure consistent consumption across all engines: (1) Hive-compatible SerDe classes (like OpenCSVSerDe, LazySimpleSerDe, ParquetHiveSerDe) are understood by Athena, Spark, Spectrum, and Glue because they all implement the Hive metastore interface; (2) columnar formats (Parquet/ORC) include schema information within the data files, making them self-describing — engine differences in type handling are minimized because the file itself declares its types; (3) explicit table properties in the catalog (serialization.format, field.delim, timestamp.formats) provide consistent hints to all engines; (4) using standard Hive data types (string, bigint, timestamp) avoids ambiguity that causes cross-engine differences. Prevention is better than engine-specific workarounds.

Miskonsepsi & Jebakan Umum

  • Building a custom search application on exported metadata creates operational overhead (crawlers, exports, custom code), introduces staleness (metadata becomes outdated between exports), and doesn't integrate with Lake Formation's permission model.
  • Requiring analysts to log into 15 separate DataZone portals defeats the purpose of centralized discovery; they'd need to know which account has which data to begin searching.
  • RAM sharing of S3 buckets gives direct access to underlying data without metadata context (schema, descriptions, classifications); analysts see raw files, not discoverable datasets.
  • Manual outreach to owners is inefficient at scale (20+ databases, potentially different owners) and defeats the purpose of a catalog.
  • Running queries against 500+ tables wastes compute cost, takes hours, and may access sensitive data the analyst shouldn't see; discovery should happen at the metadata level, not the data level.
  • INFORMATION_SCHEMA in Athena is limited to the currently-selected database; cross-database schema search requires switching databases individually and doesn't search descriptions or tags.
  • Physical copies multiply storage costs (especially for PHI data), create data synchronization challenges, and increase the compliance surface area (more copies of sensitive data to track).
  • IAM policies cannot enforce column-level access within Parquet/ORC files; IAM operates on S3 objects (entire files), not on columnar data within files.
  • S3 Access Points operate at the object (file) level, not the column level; you cannot restrict access to specific columns within a Parquet file using S3 policies.
  • A ticketing system adds friction without improving discovery; analysts still need to know what to request, and the process slows down self-service analytics.
  • Auto-complete helps with typing accuracy but doesn't solve discovery (analysts need to already know approximately what table to type); it also doesn't provide context about what each table contains.
  • Wiki pages become outdated as tables are added/modified/deprecated; maintaining documentation separate from the actual catalog metadata creates drift and inaccuracies.
  • DMS replicates data between databases, not catalog metadata; pg_catalog is PostgreSQL's internal system catalog that tracks Redshift's own objects, not external data sources.
  • Manually exporting and executing DDL creates a maintenance burden; any catalog change requires re-exporting and re-running DDL, creating metadata drift.
  • There is no JDBC interface to the Glue Data Catalog; Spectrum uses AWS API calls (Glue GetTable/GetPartitions) internally, not JDBC connections.
  • A single shared database violates data mesh ownership principles; all domains become dependent on a shared namespace, creating governance bottlenecks and naming conflicts.
  • Configuration files become stale, don't integrate with query engines natively, and require manual updates when producers reorganize their catalogs.
  • AWS Service Catalog provisions infrastructure resources, not data catalog metadata; it's designed for CloudFormation templates, not data product discovery.
  • Secrets Manager stores credentials securely but doesn't provide schema metadata, table locations, or partition information — it solves authentication but not catalog-based data discovery/access.
  • Exporting to JSON creates a point-in-time snapshot that becomes stale; real-time catalog resolution ensures Spark always reads current metadata.
  • Programmatic Glue API calls work but require custom code in every Spark job, don't integrate with Spark SQL's native catalog resolution, and duplicate functionality that the native integration provides automatically.
  • IAM deny policies prevent access but don't explain WHY or WHERE to find the correct alternative; analysts get cryptic access-denied errors without guidance.
  • Deleting tables breaks existing queries, dashboards, and ETL jobs that reference them; this causes immediate production issues without a transition period.
  • Renaming tables breaks existing references (same problem as deletion) and is a crude mechanism that doesn't convey quality level, ownership, or alternatives.
  • Daily CSV exports create data staleness, duplicate data (compliance risk for financial data), and require managing the export pipeline — this is data movement, not data sharing.
  • S3 bucket policies grant raw file access without table/column-level control; the partner could read ALL files in that prefix (potentially including other tables), and revoking requires identifying and removing specific policy statements (error-prone).
  • VPN + direct Athena access would require sharing IAM credentials or creating cross-account roles for the partner to use the institution's Athena; this complicates security and doesn't use catalog-based discovery.
  • Lambda-based metadata transformation adds latency, complexity, and a failure point to every query; it patches symptoms rather than fixing root cause (non-standard catalog definitions).
  • Maintaining multiple table definitions per dataset creates N× catalog complexity, synchronization challenges, and defeats the purpose of a single catalog as source of truth.
  • Mandating a single engine is impractical — different workloads benefit from different engines (Athena for ad-hoc, EMR for heavy processing, Spectrum for Redshift-integrated queries).
