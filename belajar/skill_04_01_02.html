Domain 4: Security & Governance — Task 4.1: Apply authentication mechanisms

Skill 4.1.2: IAM groups, roles, endpoints

IAMgroupsrolesendpoints

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.1: Apply authentication mechanisms), dengan fokus pada iam groups, roles, endpoints. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS IAM
Identity and Access Management: user, group, role, dan policy untuk akses least-privilege.
Amazon VPC
Jaringan terisolasi; security group & endpoint mengontrol konektivitas sumber daya.

Poin-Poin Kunci

  • AWS best practice adalah menggunakan IAM Groups untuk mengelola permissions berdasarkan job function. Group "DataEngineers" berisi common policies (S3 read prod, S3 write dev, Glue job run) yang berlaku untuk semua 15 engineer. Group "SeniorDataEngineers" menambahkan EMR management policies. Senior engineers menjadi member di kedua groups dan mewarisi semua permissions.
  • Cross-account S3 access memerlukan konfigurasi di kedua akun: (1) Account A: IAM role untuk Glue dengan trust policy yang mengizinkan glue.amazonaws.com sebagai principal, plus IAM policy dengan permission s3:GetObject pada ARN bucket Account B. (2) Account B: Bucket policy yang mengizinkan Account A's Glue role ARN untuk mengakses bucket. Kedua sisi harus explicitly mengizinkan.
  • Trust policy menentukan SIAPA yang boleh assume role (Principal), sedangkan permission policy menentukan APA yang boleh dilakukan setelah assuming role. Redshift yang akan assume role, jadi trust policy harus memiliki Principal: redshift.amazonaws.com. Permission policy kemudian memberikan akses ke S3 dan izin lambda:InvokeFunction.
  • EMR menggunakan dua IAM roles: (1) EMR Service Role — trusted oleh elasticmapreduce.amazonaws.com — untuk provisioning dan managing cluster resources. (2) EC2 Instance Profile Role — trusted oleh ec2.amazonaws.com — digunakan oleh EC2 instances dalam cluster untuk mengakses AWS services seperti S3, DynamoDB, dll. Hive/Spark jobs running pada EC2 instances menggunakan instance profile role, jadi DynamoDB permissions harus ada di role tersebut.
  • Gateway Endpoints hanya tersedia untuk S3 dan DynamoDB, gratis, dan bekerja melalui route table entries — traffic diarahkan melalui gateway tanpa ENI. Interface Endpoints (powered by AWS PrivateLink) mendukung sebagian besar AWS services (termasuk SageMaker, Glue, Athena), menggunakan ENI dengan private IP di subnet, dan memiliki biaya per jam plus data processing. Interface Endpoints juga memerlukan security group pada ENI untuk access control.
  • Role chaining di AWS memiliki limitasi penting: session duration maximum dibatasi 1 jam (3600 detik) terlepas dari MaxSessionDuration yang dikonfigurasi pada role individual. Jika Glue job berjalan lebih dari 1 jam, temporary credentials dari role chain akan expire dan menyebabkan AccessDenied. Ini adalah limitasi yang sering tidak diketahui.
  • Cross-account IAM role dengan: (1) Trust policy yang mengizinkan Account 222222222222 sebagai Principal untuk AssumeRole. (2) Permission policy dengan s3:GetObject pada resource ARN spesifik (arn:aws:s3:::bucket/prefix/*). (3) Condition menggunakan "aws:CurrentTime" dengan StringGreaterThanEquals dan StringLessThanEquals untuk membatasi waktu akses. Ini memenuhi semua requirement secara native IAM.
  • IAM policy evaluation logic mengikuti aturan: Explicit Deny selalu menang. Urutan evaluasi: (1) Jika ada explicit Deny di policy manapun → DENY. (2) Jika ada explicit Allow → ALLOW. (3) Jika tidak ada explicit Allow → implicit DENY. Karena ada explicit Deny di bucket policy, akses akan ditolak meskipun IAM group policy mengizinkan. Ini berlaku terlepas dari jenis policy (identity-based, resource-based, SCP, permission boundary).
  • Service-linked roles adalah pre-defined oleh AWS dan tidak bisa dimodifikasi — Anda tidak bisa menambah atau mengubah permission policies-nya. Untuk KMS customer-managed keys, solusinya adalah menambahkan ARN service-linked role ke KMS key policy sebagai authorized principal untuk kms:Decrypt dan kms:GenerateDataKey. KMS key policy memberikan akses dari sisi resource.
  • Untuk cross-account S3 access, diperlukan permission di kedua sisi: (1) Identity-based policy di source account (IAM role permission) — Account A Glue role perlu s3:PutObject, Account C EMR role perlu s3:GetObject. (2) Resource-based policy di destination account (S3 bucket policy) — explicitly allow Account A's Glue role ARN untuk PutObject dan Account C's EMR role ARN untuk GetObject. Ini mengikuti principle of least privilege.

Miskonsepsi & Jebakan Umum

  • Memberikan semua orang permissions yang sama termasuk EMR — melanggar least privilege.
  • Tidak scalable dan sulit di-maintain.
  • Terlalu permissive dan SCP tidak dimaksudkan untuk granular user permissions.
  • Melanggar best practice — gunakan roles, bukan long-term credentials.
  • Tidak memberikan cross-account access — VPC endpoint hanya route traffic, tidak memberikan permission.
  • Terlalu permissive dan tidak mengikuti service-specific trust.
  • Salah karena Lambda tidak perlu assume role ini — Redshift yang memanggil Lambda menggunakan role Redshift sendiri.
  • Salah karena S3 tidak assume role.
  • Salah — DynamoDB tidak assume role.
  • Salah — DynamoDB tidak memerlukan service-linked role untuk access.
  • Salah — VPC endpoint tidak diperlukan untuk permission (meskipun membantu routing).
  • Salah — Gateway Endpoints tidak memerlukan security group, dan Interface Endpoints yang memerlukan security group.
  • Membalikkan definisi keduanya.
  • Salah — keduanya berbeda secara fundamental dalam arsitektur.
  • Salah — AWS mengizinkan chaining lebih dari 2 roles.
  • Salah — Glue dapat melakukan role chaining melalui boto3 STS calls dalam job script.
  • Bisa jadi masalah tapi soal menyebutkan "all policies appear correct" — limitasi 1 jam session duration adalah penyebab paling umum yang terlewat.
  • Tidak scalable dan sulit di-audit.
  • Melanggar best practice — selalu gunakan roles untuk cross-account access.
  • Bagus untuk access management tapi tidak memiliki native time-based condition.
  • Salah — ini hanya berlaku untuk cross-account access dimana kedua sisi harus Allow.
  • Salah — waktu pembuatan tidak mempengaruhi evaluasi.
  • Salah — tidak ada hirarki prioritas antara identity dan resource-based policies untuk Deny.
  • Salah — service-linked roles tidak bisa di-custom saat creation.
  • Bisa bekerja tetapi bukan solusi yang tepat jika Anda sudah menggunakan service-linked role dan hanya perlu akses KMS — lebih baik update KMS key policy.
  • Salah — service-linked roles tidak bisa dimodifikasi.
  • Sangat tidak aman dan melanggar least privilege.
  • Kurang secure — kedua account mendapat permissions yang sama.
  • Menambah biaya dan complexity.
