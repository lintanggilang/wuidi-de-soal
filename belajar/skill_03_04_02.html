Key Points

  • This DQDL ruleset uses the correct syntax: Completeness checks the percentage of non-null values (0.98 = 98%), ColumnValues with "in" validates against an allowed set of values, and ColumnValues with a comparison operator validates that dates don't exceed the current timestamp using now(). Option B: "IsComplete" is not a valid DQDL rule type (it's "Completeness"), percentage notation isn't used (decimals are), and "DateColumnValues" isn't a separate rule type. Option C: "NullCheck", "Enum", and "RangeCheck" are not valid DQDL rule type names. Option D: Completeness = 1.0 means 100% (not 98%), UniqueValues counts distinct values which doesn't enforce specific allowed values, and Freshness checks data age relative to now, not whether dates are in the future.
  • Glue Data Quality's rule recommendation feature analyzes the statistical profile of your data and automatically generates appropriate DQDL rules with realistic thresholds. This uses the actual data distribution to propose rules, which can then be reviewed and adjusted based on business requirements. This is the most efficient approach that combines data-driven thresholds with business oversight. Option A: Manually setting thresholds slightly below profiled values is reasonable but labor-intensive and doesn't account for whether the profiled values represent acceptable quality or existing problems. Option C: Setting 100% thresholds is unrealistic for this data and would cause constant false-positive failures. Option D: Defining quality rules for imperfect data is valid—rules detect degradation from the current baseline even if the baseline isn't perfect.
  • DQDL supports the "where" clause (also called row-level filtering) that applies a rule only to rows matching a condition. By creating two rules with different "where" conditions, you effectively implement conditional validation logic. Each rule evaluates only against the subset of rows matching its condition. Option B: IF-THEN-ELSE is not valid DQDL syntax; DQDL uses declarative rule definitions, not procedural logic. Option C: DQDL does support conditional evaluation through the "where" clause, making custom code unnecessary for this case. Option D: "CompositeRule" is not a valid DQDL rule type; DQDL rules are individual declarations that can be combined in a ruleset.
  • Storing DQDL rulesets in version control and deploying via IaC (CloudFormation/CDK) provides full governance: version history, code review for changes, environment promotion workflows, rollback capability, and audit trails. This follows infrastructure-as-code best practices applied to data quality rules. Option B: Console-based management doesn't provide cross-environment promotion, code review, or proper audit trails; changes are manual and error-prone across 200 jobs. Option C: A shared DynamoDB table creates a single point of failure and prevents environment isolation—a bad rule change affects all environments simultaneously. Option D: Hard-coded rules in scripts tightly couple quality definitions to ETL logic, making it difficult to update rules without modifying and redeploying the ETL code.
  • The correct DQDL syntax uses "DataFreshness" for checking that a timestamp column's most recent value is within a specified time window (using human-readable time units like "hours"), and "RowCount" with "between" for validating record count ranges. DQDL supports natural time units (hours, minutes, days) for freshness rules. Option B: "Freshness" is not the correct rule type name (it's "DataFreshness"), and using minutes instead of the supported "hours" unit may not parse correctly. Option C: This uses ColumnValues with a computed expression which isn't valid DQDL syntax; DataFreshness is the purpose-built rule for this. Option D: "DataFreshness" without a time unit (just "4") is ambiguous and invalid; "DatasetRowCount" is not the correct rule name (it's "RowCount").
  • Using a CustomSql rule that validates against a reference table is the most maintainable approach for large value sets. The reference table can be updated independently (adding new legitimate categories) without modifying the DQDL ruleset itself. This separates the rule logic from the reference data, following the principle of configuration over code. Option A: Listing 47 values explicitly in the DQDL rule works but requires ruleset modifications whenever a legitimate new category is added, creating a maintenance burden. Option B: DataBrew recipe filtering removes data silently without alerting—this is a transformation, not a quality rule. Option C: Counting distinct values (exactly 47) is too rigid; it would fail if a legitimate new category is added AND if an existing category disappears in a batch, conflating two different issues.
  • The "where" clause in DQDL enables cross-column dependency validation by scoping a rule's evaluation to a subset of rows. This correctly validates that card_last_four is complete AND matches the 4-digit pattern only for credit card payments, and bank_account_id is complete only for bank transfers. Option B: IF-THEN conditional syntax is not valid in DQDL; the language uses declarative rules with "where" clauses for conditional evaluation. Option C: "CrossColumnCheck" is not a valid DQDL rule type. Option D: Using overall completeness of 0.5 (50%) is a crude approximation that doesn't properly validate the conditional relationships and would pass even if the wrong records have nulls.
  • A hybrid approach is most practical: native DQDL rules for common patterns (null checks, uniqueness, ranges) provide optimized evaluation and standardized reporting, while CustomSql rules accommodate complex queries that don't map to standard rule types. This gradual migration lets the team convert simple queries first and tackle complex ones iteratively. Option B: Rewriting as custom Python loses the declarative quality management benefits (standardized metrics, built-in reporting, rule recommendations) that DQDL provides. Option C: Keeping SQL queries in Athena doesn't integrate with the Glue ETL pipeline for inline quality gates and doesn't provide the automated actions (stop job, quarantine) that DQDL supports. Option D: There's no automated SQL-to-DQDL conversion tool, and bulk deployment without testing would be risky.
  • Glue Data Quality supports standalone evaluation tasks (also called "data quality runs") that can be scheduled to evaluate rulesets against Data Catalog tables directly. This feature runs quality checks without an ETL job, reading the underlying S3 data through the catalog table definition. Results are automatically available in the Glue console and can be published to CloudWatch. Option B: While functional, creating an ETL job solely for quality evaluation adds unnecessary complexity and cost when the standalone evaluation feature exists. Option C: The Lambda approach adds custom code and doesn't leverage the native scheduling capability of Glue Data Quality evaluation tasks. Option D: Athena-based checks require custom SQL maintenance and don't integrate with Glue's quality metrics framework.
  • Adding ColumnDataType validation as a prerequisite ensures type assumptions are verified before dependent rules execute. The Analyzers section in DQDL provides metadata about the data being evaluated, helping identify type mismatches early. This defensive approach prevents cascade failures from unexpected data types. Option B: DQDL does not support try-catch syntax; it's a declarative rule language, not a procedural programming language. Option C: Running 15 separate rulesets is operationally expensive (15 separate evaluations) and loses the ability to have a single quality score for the dataset. Option D: While controlling error behavior is useful, simply marking errors as failures without addressing the root cause (type mismatch) doesn't improve the quality of the evaluation results.
