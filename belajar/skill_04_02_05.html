Key Points

  • ABAC (Attribute-Based Access Control) uses tags is solution most scalable for organisasi large: Cara kerja: (1) Tag IAM roles: aws:PrincipalTag/department = "finance", aws:PrincipalTag/team = "risk-analytics". (2) Buat SATU IAM policy template that uses conditions: {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::data-lake/${aws:PrincipalTag/department}/*", "Condition": {...}}. (3) Saat new team is created: quite tag role mereka — TIDAK needs policy new. Keuntungan ABAC: Satu policy melayani all 50 teams. New teams automatic mendapat access that correct via tags. Not ada policy sprawl. Audit more easy because policy logic terpusat.
  • LF-Tags (Lake Formation Tag-Based Access Control) is choice ideal for skenario this: Implementation: (1) Define LF-Tag key: "sensitivity" with values: "phi", "de-identified", "public". (2) Assign tags to tables: Table "patient_records" → sensitivity=phi. Table "aggregated_stats" → sensitivity=de-identified. Table "hospital_directory" → sensitivity=public. (3) Grant based on tags: GRANT SELECT ON TAG (sensitivity IN ['public', 'de-identified']) TO researcher_role; GRANT SELECT ON TAG (sensitivity IN ['public', 'de-identified', 'phi']) TO physician_role; Benefit: New tables automatically get correct permissions when tagged — no manual grant needed. 200+ tables managed with a few tag-based grant expressions. Compliance audit straightforward: "Who has access to PHI?" → query LF-Tag grants.
  • Pemilihan between RBAC vs ABAC depends on organisasi: RBAC better suited when: Job functions stabil and well-defined. Number of distinct roles manageable (3 envs × 4 BUs = ~12-24 roles). Compliance teams prefer explicit role-to-permission mappings. Changes to access patterns infrequent. Easier to answer "What can role X do?" — directly lihat policy attached to role. ABAC better suited when: Organisasi rapidly growing (new teams, new projects frequently). Hundreds of permutation possibilities. Need "automatic" permission assignment based on attributes. When you want ONE policy that scales dynamically. For retail company this: 3 × 4 = 12 possible combinations — manageable with RBAC. Stable functions = rarely needs policy changes. Compliance team can clearly see "finance-prod-analyst has: read access to finance production tables".
  • For organisasi scale large with many dimensi access control, ABAC + LF-Tags is solution optimal: Multi-dimensional ABAC design: Resource Tags: aws:ResourceTag/content-type = video|audio|text, aws:ResourceTag/region = eu|apac|na, aws:ResourceTag/sensitivity = public|internal|restricted. Principal Tags: aws:PrincipalTag/team = content-eng|platform|analytics, aws:PrincipalTag/location = eu|apac|na, aws:PrincipalTag/clearance = standard|elevated|admin. Policy example (single policy for all 500+ engineers): "Condition": {"StringEquals": {"aws:ResourceTag/region": "${aws:PrincipalTag/location}", "aws:ResourceTag/sensitivity": ["public", "internal"]}} — Engineers can only access data from their region, up to internal sensitivity. Scale benefit: 2,000+ policies → ~5-10 ABAC policies. New engineer onboarding: just tag their role → instant correct access. New data asset: just tag the resource → automatically accessible to authorized principals.
  • Redshift RBAC (native database roles) provides granular access control: Implementation: (1) CREATE ROLE finance_reader; CREATE ROLE finance_writer; CREATE ROLE marketing_reader; (2) GRANT SELECT ON ALL TABLES IN SCHEMA finance TO ROLE finance_reader; GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA finance TO ROLE finance_writer; (3) GRANT ROLE finance_reader TO user_john; GRANT ROLE finance_writer TO user_sarah; Advantages: Role hierarchy — roles can be granted to other roles (role nesting). Permission changes affect all role members instantly. Clear audit trail — "Who has finance_reader role?" Easy to answer. Separation of duties — different roles for read vs write vs admin. Supports system-defined roles: sys:operator, sys:dba, sys:superuser.
  • Session tags + ABAC enables dynamic access without policy changes: Architecture: (1) Identity Provider (IdP) stores current project assignments. (2) When engineer authenticates via SSO → IdP passes session tags: aws:PrincipalTag/project = "alpha". (3) IAM role trust policy allows transitive session tags. (4) Single IAM policy: {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::data-lake/${aws:PrincipalTag/project}/*"}. (5) Project changes in IdP → next login session automatically scopes to new project. Dynamic behavior: No IAM policy changes needed — ever. Project reassignment effective immediately on next session. 100+ engineers share ONE policy. Audit: CloudTrail shows session tags on every API call.
  • Defense-in-depth authorization requires multiple layers that each other melengkapi: Layer 1 — SCPs (Organization guardrails): "No one in this organization can delete production S3 buckets" — applies regardless of IAM policies. Prevents shadow admin scenarios. Sets hard ceiling on what ANY principal can do. Layer 2 — ABAC (Department-level): Tag-based IAM policies dynamically scope access: ${aws:PrincipalTag/department} matches resource tags. Handles 100s of departments with minimal policies. Layer 3 — Lake Formation LF-Tags (Data-level): Fine-grained: row filters, column exclusions, cell-level security. Classification-based: "sensitivity=pii" → only approved roles access. Auto-applies to new tables via tag inheritance. Layer 4 — Redshift RBAC (Database-level): Native SQL-level permissions: GRANT SELECT ON schema.table TO role. Role hierarchy for complex permission structures. Column-level and row-level security within Redshift. Why combined: Each layer addresses what it does BEST.
  • Tenant isolation in shared pipeline requires runtime-scoped authorization: Approach: (1) Glue job receives tenant-id as parameter (e.g., job argument --tenant-id=acme). (2) Glue job assumes a scoped-down role using session policy or the job's execution role uses resource tags. (3) Session policy restricts S3 access: {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::pipeline-data/acme/*"}. Alternative with ABAC: Tag the Glue job with tenant-id tag. Policy condition: "Condition": {"StringEquals": {"aws:ResourceTag/tenant-id": "${aws:PrincipalTag/tenant-id}"}}. Benefit: Single job definition, single base role, but per-execution tenant isolation. Even if job code has bug, IAM prevents cross-tenant data access.
  • Not all AWS service actions support aws:ResourceTag conditions: Key concept: ABAC with aws:ResourceTag requires: (1) The service supports tagging the resource, (2) The specific API ACTION passes tag information in the authorization context, (3) The condition key is supported for that action. Issue with Glue: Several Glue actions supports resource-level permissions and tag conditions (e.g., glue:GetTable on specific table ARN), TETAPI several actions not fully support tag-based authorization. Solution: Check AWS documentation "Actions, resources, and condition keys for AWS Glue" — verify which actions support resourceTag. Workarounds: (1) Use naming conventions (department prefix in database name) + wildcard ARN patterns. (2) Use Lake Formation LF-Tags instead — specifically designed for Glue catalog resource ABAC. (3) Combine IAM resource-level permissions with supplementary Lake Formation grants.
  • Best practice is hybrid approach that evolves with organisasi: Phase 1 (Current, 20 engineers): RBAC with 5 roles adequate. Simple, auditable, team understands it. Roles: admin, data-engineer, analyst, read-only, service-role. Phase 2 (Transition, 50-100 engineers): ABAC signals: New team → requires new policy (toil). Same role used by people needing different access scopes. IAM policy count growing linearly with team growth. Introduce ABAC for dynamic dimensions: project, team, environment. Keep RBAC for base capabilities. Phase 3 (Scale, 200+ engineers): Full ABAC for resource scoping (tags drive access boundaries). RBAC for capability levels (what CAN you do — read/write/admin). Lake Formation LF-Tags for data catalog governance. Migration strategy: (1) Start tagging all resources now (even while using RBAC). (2) Tag IAM roles with metadata. (3) Add ABAC conditions incrementally to existing policies. (4) New access patterns use ABAC; legacy RBAC remains until refactored.

Common Misconceptions & Pitfalls

  • Over-engineering, account proliferation complexity.
  • Policy sprawl, not scalable (butuh update manual each ada team new).
  • Violates least privilege, massive security risk.
  • IP-based restrictions don't map to data sensitivity or user clearance.
  • 200+ tables × multiple users = thousands of individual grants, unmanageable.
  • Separate accounts create operational complexity, data sharing challenges.
  • Salah — ABAC not always better, depends on use case.
  • S3 bucket policies alone insufficient for fine-grained access control.
  • Combining both unnecessarily adds complexity.
  • Country-level is too broad, violates least privilege.
  • Network security cannot provide data-level authorization.
  • Schema-level is too coarse, doesn't allow table/column level control.
  • Separate clusters = excessive cost, data duplication, cross-cluster query complexity.
  • Individual user grants don't scale, hard to audit.
  • No access control, violates least privilege.
  • Lambda rewriting policies creates race conditions, eventual consistency issues, IAM policy size limits.
  • Manual process, slow, error-prone, doesn't scale.
  • Custom interceptor adds latency, single point of failure, maintenance burden.
  • Lake Formation doesn't cover Redshift internal permissions or org-level guardrails.
  • IAM alone can't do row/column level, Redshift internal permissions, etc.
  • Violates tenant isolation, one tenant's job run could access all data.
  • 1000 tenants = 1000 jobs + 1000 roles = unmanageable.
  • KMS-only approach doesn't prevent listing/metadata access and is complex to manage.
  • Wrong — ABAC works with many services (EC2, RDS, S3, etc.).
  • Partially wrong — Glue DOES support some ABAC, but not uniformly.
  • Wrong — aws:PrincipalTag IS visible to policy engine.
  • Pure RBAC at 200+ people creates role explosion.
  • Network security is NOT authorization.
  • Premature optimization for 20 engineers.
