Key Points

  • HNSW is the optimal choice for this scenario: (1) it provides the best recall-latency tradeoff among approximate nearest neighbor algorithms at 10M scale; (2) the multi-layer graph structure enables O(log n) query time with 95%+ recall at sub-50ms; (3) HNSW handles incremental inserts well (daily 50K additions are added to the graph without full rebuild); (4) ef_construction=128 builds high-quality graphs, and m=16 connections per node balances memory and search quality.
  • MemoryDB is purpose-built for this scenario: (1) full Redis data structure support (sorted sets for leaderboards, lists for chat, hashes for player state); (2) sub-millisecond read latency from in-memory storage; (3) Multi-AZ durability with a distributed transaction log that persists every write before acknowledging — guaranteeing zero data loss on failover (unlike ElastiCache which may lose recent writes during failover); (4) 100K+ ops/sec throughput.
  • HNSW is superior for this fraud detection scenario: (1) at 500K vectors with 256 dimensions, HNSW easily achieves sub-5ms query time; (2) HNSW handles incremental insertions without retraining — new fraud patterns added weekly are immediately searchable; (3) HNSW provides higher recall (fewer missed similar patterns) than IVF at equivalent latency, critical when false negatives mean undetected fraud; (4) query latency is consistent regardless of query vector position in the space.
  • Aurora PostgreSQL with pgvector uniquely satisfies ALL four requirements in a single engine: (1) pgvector provides vector similarity search with HNSW indexes for semantic retrieval; (2) PostgreSQL's rich SQL supports complex metadata filtering with standard WHERE clauses and joins; (3) built-in full-text search (tsvector/tsquery with GIN indexes) provides keyword fallback; (4) PostgreSQL's native ACID transactions ensure document update consistency. This eliminates multi-service complexity and data synchronization challenges.
  • Neptune is purpose-built for graph workloads: (1) native graph storage engine optimizes for traversal operations (pointer-based adjacency vs. JOIN-based in relational); (2) Gremlin traversal language expresses "3 hops from retailer" naturally (g.V(retailer).repeat(out()).times(3)); (3) built-in shortest path algorithms execute in O(V+E) time; (4) cycle detection is native to graph query languages; (5) 50M edges with properties are Neptune's bread and butter.
  • Redis Cluster Mode is optimal for this use case: (1) sharding distributes 200M keys across multiple nodes (each node handles a subset of requests), enabling 500K+ RPS aggregate throughput; (2) consistent hashing ensures predictable key-to-node mapping; (3) read replicas per shard multiply read capacity for this read-heavy workload; (4) Redis provides sub-millisecond latency for single-key lookups, easily meeting p99 < 5ms; (5) cluster auto-scaling accommodates traffic spikes.
  • OpenSearch is a dedicated search engine with all required capabilities built-in: (1) inverted indexes with BM25/TF-IDF scoring provide relevance-ranked full-text search; (2) aggregation framework computes facet counts (brand: Apple(500), Samsung(300)) in the same query; (3) completion suggesters provide type-ahead autocomplete from partial input; (4) fuzzy queries use Levenshtein distance for misspelling tolerance; (5) horizontal scaling handles 50M documents with sub-second search latency.
  • OpenSearch with k-NN plugin is optimal: (1) HNSW algorithm handles 100M vectors efficiently with sub-100ms latency; (2) OpenSearch's filtered k-NN applies metadata predicates during the search (not post-search), ensuring results respect availability and price constraints; (3) near real-time index refresh (1-second default) makes availability changes searchable immediately; (4) OpenSearch Service is fully managed with Multi-AZ deployment for 99.9% availability.
  • DAX is purpose-built for this pattern: (1) write-through/read-through cache that's transparent to the application (same DynamoDB API, just point to DAX endpoint); (2) the hot 100K items are cached in memory, serving 90% of reads at microsecond latency without consuming DynamoDB RCUs; (3) cache misses (10% long-tail) fall through to DynamoDB normally; (4) net effect: 90% reduction in DynamoDB RCU consumption (only long-tail reads consume RCUs). DAX cost is typically far less than the RCU savings.
  • Neptune excels at this use case: (1) native graph storage with index-free adjacency enables O(1) neighbor lookups during path traversal; (2) Gremlin's shortestPath() step or weighted traversals implement Dijkstra/A* algorithms natively; (3) edge property updates (travel_time) are simple property mutations that take effect immediately; (4) ACID transactions prevent route calculations from reading partially-updated weights during a traffic update batch; (5) 10M nodes/30M edges is well within Neptune's capacity.

Common Misconceptions & Pitfalls

  • Brute-force scan of 10M × 1536-dimension vectors takes seconds, far exceeding the 100ms requirement.
  • B-tree indexes work for scalar value ordering, not high-dimensional similarity search; hashing vectors destroys distance relationships.
  • IVF requires periodic retraining when data distribution shifts (daily additions may degrade cell boundaries), and at nprobe=50/nlist=1000 it searches 5% of data which may give lower recall than HNSW for the same latency.
  • DynamoDB+DAX provides sub-ms reads but doesn't natively support Redis data structures (sorted sets, lists); application must implement leaderboards differently.
  • ElastiCache Redis provides the same data structures and latency but uses asynchronous replication; during failover, the last few seconds of writes to the primary may be lost (the replica may not have received them yet) This violates the "zero data loss" requirement.
  • Aurora's disk-based architecture cannot achieve sub-millisecond latency consistently at 100K ops/sec.
  • Brute-force scan of 500K × 256-dim vectors takes approximately 50-100ms on Aurora, exceeding the 10ms requirement when accounting for concurrent queries and database overhead.
  • IVF with nprobe=nlist is equivalent to brute-force search, defeating the purpose of an index.
  • While IVF uses less memory and builds faster, it requires retraining (rebuilding cell centroids) when data distribution changes; stale centroids after weekly updates degrade recall — unacceptable for fraud detection.
  • Neptune is for graph traversal (relationship queries), not semantic similarity search or document management; it doesn't natively support vector indexes.
  • Using two separate services (DynamoDB + external vector DB) requires synchronization, doubles operational complexity, and DynamoDB doesn't provide full-text search.
  • OpenSearch provides vector + full-text search but lacks ACID transactions (eventual consistency) and has limited metadata query capabilities compared to SQL.
  • Aurora can simulate graph queries but self-JOINs for multi-hop paths become exponentially expensive; at 50M edges and 3+ hops, query performance degrades significantly.
  • DynamoDB adjacency list requires multiple sequential reads for multi-hop traversal (one read per hop), with no native shortest path or cycle detection capabilities.
  • Redshift recursive CTEs are possible but extremely inefficient for graph traversal at 50M edges — each recursion level requires a full JOIN operation, and Redshift is optimized for analytical scans, not iterative traversal.
  • Memcached provides simple caching but lacks data persistence, replication for HA, and cluster mode's automatic resharding; a node failure loses its entire cache segment.
  • 200M users × ~1KB per record = 200+ GB exceeds per-instance memory; additionally, local caches create consistency issues across instances.
  • DAX provides sub-ms reads but is tightly coupled to DynamoDB's data model and pricing; at 500K RPS, DAX cluster costs are higher than Redis for pure cache workloads, and DAX has limited data structure support.
  • DynamoDB doesn't support full-text search, relevance ranking, fuzzy matching, or faceted navigation; these would all require application-level implementation.
  • Redshift LIKE queries don't provide relevance scoring, are slow for text search at scale, and Redshift is designed for analytical queries, not real-time search.
  • PostgreSQL full-text search works for smaller datasets but lacks native autocomplete suggesters, fuzzy matching is limited, and faceted aggregations on 50M rows are slower than OpenSearch's optimized aggregation engine.
  • Custom FAISS endpoints require managing infrastructure, scaling, and the separate DynamoDB call adds latency and complexity; also not a fully managed end-to-end solution.
  • Aurora pgvector can work but 100M vectors may exceed practical limits for a single PostgreSQL instance; filtered vector queries with WHERE clauses scan all matching vectors before applying the ANN index, which is less efficient than OpenSearch's integrated filtered search.
  • Neptune doesn't have native vector similarity search capabilities at this scale.
  • On-Demand at 50K reads/second would cost more than provisioned with caching since every request is charged at on-demand rates ($125 per million reads).
  • ElastiCache Redis works but requires application code changes (different API), cache invalidation logic, and lacks DAX's transparent DynamoDB integration and automatic item-level cache management.
  • Provisioning for peak (50K RCU) is the current expensive approach; doesn't reduce costs.
  • 10M nodes adjacency matrix would be 10M×10M entries (petabytes); even adjacency list format at 30M edges exceeds Lambda's 10 GB memory limit.
  • Making individual DynamoDB GetItem calls per graph hop introduces 2-5ms network latency per step; a route with 50+ hops would take 100-250ms just for I/O, with no native shortest path algorithm.
  • Redshift recursive CTEs over 30M edges would be extremely slow for shortest path calculations; Redshift is not designed for iterative graph algorithms.
