Key Points

  • A single crawler with appropriate grouping handles multi-vendor discovery efficiently: (1) the crawler's built-in classifiers automatically detect file formats (CSV, JSON, Parquet, XML) without configuration per vendor; (2) S3 path grouping at the vendor level creates one table per vendor directory, consolidating daily files into a single partitioned table; (3) when new vendors are onboarded, the next crawler run automatically discovers their prefix, infers schema, and creates a new catalog table — zero manual intervention; (4) partition detection recognizes the date= pattern and registers partitions automatically; (5) a single daily schedule aligns with the business process (all vendors upload daily).
  • This is the correct and designed behavior for schema evolution in columnar data lakes: (1) Parquet files are self-describing — each file's footer contains its own schema; (2) the catalog schema represents the "superset" schema (union of all columns across all files/partitions); (3) when Athena reads a specific Parquet file, it maps the file's columns to the catalog schema by column name; columns present in the catalog but absent from the file return NULL; (4) this enables forward-compatible schema evolution — new columns can be added to new data without rewriting historical data; (5) queries that don't reference loyalty_points work identically on old and new partitions; queries that reference it get actual values from new data and NULL from old data. This is analogous to Iceberg's schema evolution behavior.
  • Custom classifiers extend Glue crawlers to handle non-standard formats: (1) Grok classifiers use named regex patterns to define record structure — e.g., %{INT:sensor_id} %{NUMBER:temperature} %{TIMESTAMP_ISO8601:reading_time} maps fixed-width fields to named, typed columns; (2) custom classifiers are evaluated BEFORE built-in classifiers, giving priority to custom format detection; (3) when the Grok pattern matches the file content, the crawler extracts column names and types from the pattern's named captures; (4) Glue also supports JSON and XML custom classifiers for non-standard JSON/XML structures; (5) the classifier is created once and assigned to any crawler that might encounter these files.
  • The "Crawl new folders only" recrawl policy is purpose-built for this pattern: (1) after the initial full crawl, subsequent runs track which S3 prefixes have been processed; (2) on each run, only new prefixes (new partition directories) are crawled — the 500 daily additions instead of all 2 million objects; (3) this reduces S3 LIST API calls by 99%+ (only listing new prefix contents vs. traversing entire bucket); (4) existing table schemas are preserved — only new partitions are added to the catalog; (5) runtime drops from hours to minutes proportional to new data volume. This is the standard optimization for high-partition-count tables with append-only patterns.
  • The "table level" configuration determines where in the S3 path hierarchy the crawler identifies table boundaries vs. partition boundaries: (1) if the table level is set too deep, the crawler treats intermediate directories as separate tables; (2) setting the table-level depth correctly (at the events/ level in this case) tells the crawler: "everything at s3://data-lake/events/ is ONE table, and subdirectories below that are partitions"; (3) with correct configuration, year=2024/month=03/day=15/hour=10 are recognized as partition keys, creating one table with four partition columns; (4) this is configured in the crawler's S3 target settings or via the "Add another S3 source" with explicit grouping. The crawler then identifies the Hive-style key=value pattern and creates partition columns automatically.
  • JDBC crawler Include/Exclude paths provide precise control over what's crawled: (1) Include path format is database_name/schema_name/table_name with % as wildcard; "database/sales/%" means "all tables in the sales schema"; (2) Exclude patterns use the same format with wildcards to filter out matching patterns — "database/sales/tmp_%" excludes all tables starting with tmp_ in the sales schema; (3) the crawler issues JDBC metadata queries (equivalent to INFORMATION_SCHEMA queries) only for included paths, minimizing database load; (4) this configuration is set in the crawler's JDBC target definition and evaluated server-side during metadata retrieval.
  • "Add new columns only" provides the optimal balance of automation and stability: (1) NEW fields (appearing weekly) are automatically added to the catalog schema — consumers can start querying them immediately without manual intervention; (2) REMOVED fields (deprecated) remain in the catalog — existing queries referencing them don't break (they'll return NULL from newer files that lack the field); (3) TYPE CHANGES are NOT applied automatically — this prevents breaking changes like a field switching from string to integer which would cause casting errors in existing queries; type changes require explicit review. This is the recommended policy for production data lakes with evolving schemas.
  • Targeted S3 path + exclusion patterns is the most efficient and maintainable approach: (1) setting the target to s3://bucket/data/ immediately eliminates /logs/ and /tmp/ from the crawler's scope without needing exclusion patterns for them; (2) exclusion patterns using glob syntax filter within the target: "_metadata" excludes Spark checkpoint directories, "_SUCCESS" excludes Hadoop job completion markers, "_committed*" and "_started*" exclude Delta Lake/streaming commit files; (3) ".*" (dot-prefixed files) excludes hidden files that some systems create; (4) these patterns are evaluated during S3 listing, so excluded files are never downloaded or sampled, improving performance.
  • A Glue crawler's IAM role needs three categories of permissions: (1) S3 permissions — s3:GetObject to read data files for schema inference, s3:ListBucket/s3:GetBucketLocation to traverse directory structures; (2) Glue Catalog permissions — the crawler creates and modifies catalog entries, requiring glue:CreateTable (new tables), glue:UpdateTable (schema updates), glue:GetTable/GetDatabase (check existing definitions), glue:CreatePartition/BatchCreatePartition (new partitions), glue:UpdatePartition (partition updates); (3) CloudWatch Logs — logs:CreateLogGroup, logs:CreateLogStream, logs:PutLogEvents for crawler execution logging. The error specifically indicates missing glue:CreateTable — the crawler discovered data but couldn't write the table definition to the catalog.
  • Combining both recrawl policy and schema change policy provides maximum performance: (1) "Crawl new folders only" uses metadata tracking to identify only NEW S3 prefixes since the last run — for 7 daily partitions added per week, the crawler examines only 7 directories instead of traversing the full 100 TB data lake hierarchy; (2) "Do not update table definition" means even when the crawler examines new directories, it doesn't sample files to check for schema differences against the existing table definition — it only registers the directory as a new partition using the existing schema; (3) combined effect: the crawler's work is reduced to "find new partition-style paths and add them to the catalog" — a few seconds to minutes instead of 3 hours.

Common Misconceptions & Pitfalls

  • Excluding known prefixes means the crawler only runs on unknown directories; however, it also means existing vendor tables never get updated with new partitions or schema changes, requiring a separate mechanism for ongoing maintenance.
  • 50 separate crawlers create operational overhead (50 schedules, 50 configurations to maintain, 50 CloudWatch monitoring entries); adding new vendors requires creating new crawlers rather than automatic discovery.
  • Lambda with CreateTable provides control but requires custom code for format detection, schema inference, and type mapping — replicating what the crawler does natively. A "generic schema" that's updated later means queries fail until the schema is corrected.
  • Strict schema enforcement would make data lakes impractical; schema flexibility is a core data lake advantage over rigid warehouse schemas.
  • Crawlers NEVER modify data files — they only read and update metadata; backfilling data would violate the principle that crawlers are read-only discovery tools.
  • Creating a separate table for each schema version would break queries that need to span old and new data; the single-table approach with NULL filling is the standard data lake pattern.
  • Glue crawlers don't support custom file extension mappings to existing classifiers; classification is based on file content inspection (magic bytes, structure), not file extensions.
  • Pre-processing with Lambda works but adds operational complexity (another pipeline step, Lambda concurrency limits, error handling) and doubles storage; custom classifiers eliminate this intermediate step.
  • Manual catalog creation works for initial setup but doesn't handle schema changes if the sensor format evolves; crawlers with custom classifiers automatically detect schema updates on subsequent runs.
  • More DPUs accelerate processing but don't reduce the fundamental number of S3 LIST operations needed; listing 2 million objects is bounded by S3 API throughput (1,000 objects per LIST call = 2,000 API calls minimum), not crawler compute.
  • Parallel crawlers targeting different date ranges still collectively scan all 2 million objects; total compute and S3 API calls remain similar, and coordination between crawlers adds complexity.
  • Manually managing exclusion patterns based on dates requires updating the crawler configuration daily; it's also error-prone if new data arrives in unexpected paths.
  • If schemas were incompatible, the crawler would update the table schema to the union of columns (with NULL for missing columns) or create schemas based on compatibility settings — not create path-based table names like events_year_2024.
  • IAM permission issues cause crawler errors or empty results, not multiple table creation; the crawler wouldn't create tables for paths it can't access.
  • Hive-style naming (key=value) is actually what crawlers are DESIGNED to detect for partition discovery; it helps, not hinders, partition recognition.
  • Restricting database user permissions provides security but the crawler would still attempt to query all schemas (and fail on unauthorized ones), potentially causing errors or incomplete results; Include/Exclude patterns are cleaner and purpose-built for this use case.
  • Crawling all 200 tables then deleting unwanted ones wastes time (crawling 200 tables when only ~40 are needed), creates transient incorrect catalog state, and adds Lambda complexity.
  • Pg_hbaconf controls client authentication (IP addresses, SSL requirements), not schema visibility; it cannot hide schemas from JDBC connections.
  • "Update all properties" applies type changes and removes deprecated columns, both of which can break existing queries and dashboards without warning; inappropriate for production.
  • "Do not update" prevents any automatic discovery of new columns; the team must manually track schema changes across all vendors and update the catalog — slow and error-prone.
  • There is no native "Log schema changes" policy in Glue crawlers; while this concept (event-driven schema governance) is valid, implementing it requires custom architecture not available as a built-in crawler policy.
  • IAM/bucket policies blocking the crawler from _metadata paths is overly complex, hard to maintain as new metadata patterns emerge, and may interfere with other Glue operations (ETL jobs) that legitimately need to read these files.
  • Deleting metadata files removes information that Spark jobs might need for exactly-once semantics or checkpointing; lifecycle policies destroying _metadata can break streaming pipelines The correct approach is to exclude them from crawling, not delete them.
  • Glue crawlers don't support "include patterns" on S3 targets in the same way; the target path itself defines inclusion. Using the root bucket with complex inclusion/exclusion is less clean than scoping the target appropriately.
  • StartCrawler/StopCrawler are needed by the invoker (person or automation starting the crawler), not by the crawler's execution role; the crawler doesn't start/stop itself.
  • Iam:PassRole is needed by the PERSON/PROCESS that starts the crawler (to pass the role TO the crawler), not by the crawler role itself during execution.
  • AWSGlueServiceRole is a managed policy that provides broad Glue permissions, but the team may use custom policies for least-privilege; saying "just use the managed policy" doesn't explain what's missing. Also, AWSGlueServiceRole alone doesn't include S3 access to specific buckets.
  • Lambda + S3 events is a valid alternative architecture that provides real-time partition registration; however, the question asks about crawler optimization, and this approach requires new infrastructure (Lambda function, S3 event configuration, error handling). It IS a superior approach for real-time needs but doesn't optimize the existing crawler setup.
  • There is no "CrawlerLineageSettings" parameter that controls sample size; sample size configuration is limited, and even with fewer samples, the full S3 listing still occurs, which is the primary time consumer.
  • Reducing frequency from weekly to monthly means new daily partitions aren't discoverable for up to 30 days — analysts can't query recent data.
