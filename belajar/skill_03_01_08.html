Skill 3.1.8: Lambda for data automation

Lambdaautomationevent-driven

Ringkasan

Skill ini termasuk dalam Domain 3: Operations & Support (Task 3.1: Automate data processing), dengan fokus pada lambda for data automation. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS Lambda
Komputasi serverless event-driven; batas timeout 15 menit dan memori hingga 10 GB.
Amazon EventBridge
Event bus serverless untuk routing event antar layanan; mendukung schedule rule.

Poin-Poin Kunci

  • Event source mapping maximum concurrency (fitur yang lebih baru) langsung membatasi jumlah concurrent Lambda invocations yang dipicu oleh SQS, memberikan kontrol yang presisi. Batch size 10 memproses lebih banyak pesan per invocation, mempercepat processing.
  • Untuk Kinesis event source mappings, "bisect on function error" memecah batch menjadi dua jika terjadi error, secara progresif mengisolasi record yang bermasalah. "Maximum retry attempts" membatasi berapa kali record diretryi. "On-failure destination" mengirim failed record ke SQS DLQ setelah retry limit tercapai, memungkinkan processing melanjutkan ke record berikutnya.
  • Lambda layers memungkinkan packaging shared dependencies secara terpisah dari function code. Layers dapat di-share antar multiple functions dan di-version independently. Ketika dependency diupdate, hanya layer version baru yang di-publish dan functions menggunakan versi baru. Ini mengurangi deployment package size (function code tanpa dependencies) dan centralize management.
  • Lambda destinations (fitur async invocation) memungkinkan routing hasil invocation — baik success maupun failure — ke target destinations seperti Lambda function, SQS, SNS, atau EventBridge. On-failure destination langsung mengirim event payload beserta error details ke Lambda lain untuk analysis. Ini lebih rich dibanding DLQ karena menyertakan response payload dan metadata.
  • AWS Lambda Power Tuning adalah open-source tool (Step Functions-based) yang secara otomatis menjalankan fungsi dengan berbagai memory configurations, mengukur execution time dan cost untuk masing-masing, dan menghasilkan visualization curve yang menunjukkan sweet spot optimal. Ini data-driven dan comprehensive.
  • Parallelization factor (1-10) memungkinkan multiple Lambda invocations per shard, meningkatkan throughput processing tanpa menambah shard. DynamoDB Streams mempertahankan records selama 24 jam, jadi data tidak hilang selama throttle — hanya processing tertunda. Increasing reserved concurrency memastikan fungsi memiliki kapasitas untuk burst.
  • Lambda supports ephemeral storage (/tmp) up to 10,240 MB (10 GB), cukup untuk file 5 GB. Streaming processing (membaca dan menulis file dalam chunks) menghindari kebutuhan memuat seluruh file ke memory sekaligus, memungkinkan processing file besar dengan memory yang lebih kecil.
  • AWS Step Functions menyediakan orchestration visual dengan: parallel states untuk steps yang bisa run concurrently, Retry policies per step (configurable intervals, max attempts, backoff rate), Catch blocks untuk error handling spesifik per step, dan conditional branching (Choice state). Ini memberikan full control dan visibility atas multi-step pipeline.
  • Menempatkan SQS queue antara S3 events dan Lambda memberikan buffering — events tidak hilang karena persisted di queue. Lambda SQS event source mapping dengan maximum concurrency setting mengontrol berapa banyak concurrent invocations, mencegah throttling. SQS messages di-retry secara otomatis jika processing gagal.
  • Lambda function URLs menyediakan dedicated HTTPS endpoint langsung untuk Lambda function tanpa memerlukan API Gateway atau load balancer. Dengan auth type NONE, endpoint menjadi public. Function URLs mendukung request/response streaming, built-in HTTPS, dan CORS configuration. Ini adalah solusi paling sederhana untuk simple HTTP endpoints.

Miskonsepsi & Jebakan Umum

  • Mengurangi cold starts tetapi tidak membatasi total concurrent invocations — reserved concurrency yang membatasi.
  • Tidak mengontrol concurrency.
  • Membatasi fungsi secara global tetapi bisa menyebabkan throttling dan message kembali ke queue jika exceeded.
  • Berarti menunggu 24 jam — unacceptable delay.
  • Tidak berlaku untuk stream-based invocations (Kinesis) yang synchronous — DLQ pada fungsi hanya untuk async invocations.
  • Kehilangan visibility ke masalah data.
  • Menambah latency cold start karena mount operation dan biaya EFS yang lebih tinggi.
  • Viable tetapi lebih overhead untuk sharing dependencies.
  • Menghilangkan keuntungan microservices dan memperbesar blast radius.
  • Overhead yang berlebihan untuk use case ini.
  • Bisa bekerja tetapi hanya mengirim original event tanpa error context details dan memerlukan intermediate SQS queue.
  • Memberikan rekomendasi tetapi kurang detail dibanding Power Tuning's multi-point analysis.
  • Viable tetapi tidak se-comprehensive dan lebih time-consuming.
  • Mengabaikan cost optimization — setelah titik tertentu, more memory tidak mengurangi time secara proporsional.
  • Memerlukan redesign arsitektur yang signifikan.
  • Justru meningkatkan invocations per record, memperburuk throttling.
  • Tidak bisa disisipkan antara DynamoDB Streams dan Lambda — streams langsung trigger Lambda.
  • Viable tetapi menambah cold start latency (VPC + mount), biaya lebih tinggi, dan overhead konfigurasi.
  • Wasteful dan mahal — memory lebih mahal dari ephemeral storage.
  • Hanya mendukung subset format (CSV, JSON, Parquet) dan query sederhana, bukan transformasi kompleks.
  • Bersifat fire-and-forget tanpa orchestration state atau error handling.
  • Menghadapi Lambda timeout limit dan single point of failure.
  • Sulit di-debug, tidak memiliki built-in retry, dan tidak mendukung conditional logic.
  • Mengurangi cold starts tetapi tidak mencegah throttling jika invocations melebihi reserved concurrency.
  • Mungkin tidak cukup untuk extreme bursts dan meningkatkan biaya.
  • Mengurangi events tetapi tidak menyelesaikan concurrency issue untuk files yang match filter.
  • Bekerja tetapi requirement spesifik menyebutkan "tanpa API Gateway" — dan function URL lebih sederhana untuk use case ini.
  • Untuk content customization di edge, bukan general-purpose API.
  • Memerlukan provisioning dan biaya load balancer.
