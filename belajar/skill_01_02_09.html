Skill 1.2.9: Volume, velocity, and variety

volumevelocityvariety3V

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.2: Transform and process data), dengan fokus pada volume, velocity, and variety. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Lihat poin-poin kunci di bawah.

Poin-Poin Kunci

  • (1) 100 TB adalah high volume, tapi monthly updates berarti low velocity (batch). (2) 500K events/second adalah high velocity (real-time streaming), volume moderat per event tapi high aggregate. (3) Emails, social media, surveys = different formats dan structures = high variety (unstructured dan semi-structured data). Setiap dataset memiliki dominant "V" yang berbeda, mempengaruhi architecture choices.
  • 50 TB daily membutuhkan distributed processing framework (Spark on EMR). Batch velocity berarti tidak perlu streaming services. Low variety (structured CSV) simplifies transformation. S3 + Parquet optimal untuk large-volume analytics. Redshift Spectrum queries without loading.
  • S3 data lake adalah solusi terbaik untuk high variety karena menerima semua format tanpa schema requirements (schema-on-read). Prefix-based organization memisahkan data types. Glue Data Catalog menyediakan unified metadata layer. Tiap tipe data bisa diproses dengan service yang sesuai (Athena untuk structured, Rekognition untuk images, dll).
  • 1M events/sec dengan 100ms latency requirement membutuhkan true streaming with low latency. Kinesis + Enhanced Fan-Out provides dedicated throughput (~70ms latency). Apache Flink melakukan stateful processing dengan millisecond-level latency.
  • Untuk cross-type querying, data harus di-normalize ke format yang queriable bersama. ETL processes extract structured fields dari semi-structured (JSON parsing) dan unstructured (NLP/NER extraction) data, creating a unified schema di Redshift. SQL queries kemudian bisa join across patient records, lab results, dan extracted entities dari clinical notes.
  • 10 GB per week is low volume (by big data standards). Weekly arrival is low velocity. Single CSV format is low variety. This dataset doesn't require big data tools. AWS Glue with minimal DPUs atau bahkan Lambda (jika file < 10 GB dan processing simple) sudah cukup. Over-engineering dengan EMR atau Kinesis membuang resources.
  • Processing paradigm depends on velocity AND time-sensitivity of insights. Clickstream (100K/sec) membutuhkan streaming untuk real-time personalization. Orders (1K/sec) membutuhkan streaming untuk real-time inventory deduction dan payment processing. Reviews (100/day) sangat low velocity dan insights tidak time-critical — batch processing harian sudah memadai dan lebih cost-effective.
  • Zone-based organization (raw → curated → consumption) memisahkan data by processing stage. Sub-folders by source/format enable format-appropriate processing. Glue crawlers auto-discover schemas untuk structured and semi-structured data. Unstructured data (PDFs, images) disimpan di raw zone untuk processing oleh AI/ML services.
  • Kinesis On-Demand mode secara otomatis scales capacity berdasarkan throughput aktual. Untuk spike events yang jarang (New Year), On-Demand menghindari paying for 500 shards 24/7 ketika hanya 50 shards needed normally. Scales up dalam detik untuk spike dan scales down setelah.
  • Architecture addresses each V: Kinesis handles high velocity (100K/sec). Lambda/Firehose transformation layer normalizes 20 formats (variety) into common schema. S3 data lake stores 10 TB/day cost-effectively (volume). EMR/Athena process large volume data for analytics. This is the Lambda Architecture pattern addressing all three V's simultaneously.

Miskonsepsi & Jebakan Umum

  • Overkill untuk batch processing — Kinesis untuk streaming, DynamoDB untuk operational data bukan 50 TB analytics.
  • Kehilangan fidelity data dan impractical untuk images/videos.
  • Tidak cocok untuk binary/unstructured data at scale.
  • Batch processing cannot achieve 100ms latency.
  • Micro-batch setiap 60 detik, tidak bisa 100ms.
  • SQS polling adds latency, Lambda cold starts, not designed for 1M/sec.
  • Tidak memungkinkan cross-type joins.
  • Untuk NLP extraction bukan querying.
  • 10 GB easily fits single-node processing.
  • Single CSV format is lowest variety.
  • Weekly batch is opposite of high velocity.
  • Misses real-time requirements.
  • Menyulitkan format-specific processing.
  • PDFs dan images tidak bisa di-convert ke Parquet.
  • Bisa handle variability tapi SQS doesn't guarantee ordering needed for CDR processing.
  • Sangat mahal — membayar 10x capacity 99.9% waktu.
  • Doesn't address velocity requirement.
  • Expensive at 10 TB/day and doesn't handle variety well.
  • Cannot handle any of the three V's at this scale.
