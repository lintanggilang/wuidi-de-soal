Key Points

  • (1) 100 TB is high volume, but monthly updates berarti low velocity (batch). (2) 500K events/second is high velocity (real-time streaming), volume moderat per event but high aggregate. (3) Emails, social media, surveys = different formats and structures = high variety (unstructured and semi-structured data). Each dataset has dominant "V" that different, affects architecture choices.
  • 50 TB daily requires distributed processing framework (Spark on EMR). Batch velocity berarti does not need streaming services. Low variety (structured CSV) simplifies transformation. S3 + Parquet optimal for large-volume analytics. Redshift Spectrum queries without loading.
  • S3 data lake is solution terbaik for high variety because receives all format without schema requirements (schema-on-read). Prefix-based organization separates data types. Glue Data Catalog provides unified metadata layer. Tiap type data can is processed with service that appropriate (Athena for structured, Rekognition for images, dll).
  • 1M events/sec with 100ms latency requirement requires true streaming with low latency. Kinesis + Enhanced Fan-Out provides dedicated throughput (~70ms latency). Apache Flink performs stateful processing with millisecond-level latency.
  • For cross-type querying, data must in-normalize to format that queriable bersama. ETL processes extract structured fields from semi-structured (JSON parsing) and unstructured (NLP/NER extraction) data, creating a unified schema in Redshift. SQL queries then can join across patient records, lab results, and extracted entities from clinical notes.
  • 10 GB per week is low volume (by big data standards). Weekly arrival is low velocity. Single CSV format is low variety. This dataset doesn't require big data tools. AWS Glue with minimal DPUs or even Lambda (if file < 10 GB and processing simple) already quite. Over-engineering with EMR or Kinesis membuang resources.
  • Processing paradigm depends on velocity AND time-sensitivity of insights. Clickstream (100K/sec) requires streaming for real-time personalization. Orders (1K/sec) requires streaming for real-time inventory deduction and payment processing. Reviews (100/day) very low velocity and insights not time-critical — batch processing harian already memadai and more cost-effective.
  • Zone-based organization (raw → curated → consumption) separates data by processing stage. Sub-folders by source/format enable format-appropriate processing. Glue crawlers auto-discover schemas for structured and semi-structured data. Unstructured data (PDFs, images) is stored in raw zone for processing by AI/ML services.
  • Kinesis On-Demand mode automatically scales capacity based on throughput aktual. For spike events that rarely (New Year), On-Demand avoids paying for 500 shards 24/7 when only 50 shards needed normally. Scales up in seconds for spike and scales down setelah.
  • Architecture addresses each V: Kinesis handles high velocity (100K/sec). Lambda/Firehose transformation layer normalizes 20 formats (variety) into common schema. S3 data lake stores 10 TB/day cost-effectively (volume). EMR/Athena process large volume data for analytics. This is the Lambda Architecture pattern addressing all three V's simultaneously.

Common Misconceptions & Pitfalls

  • Overkill for batch processing — Kinesis for streaming, DynamoDB for operational data not 50 TB analytics.
  • Kehilangan fidelity data and impractical for images/videos.
  • Not suitable for binary/unstructured data at scale.
  • Batch processing cannot achieve 100ms latency.
  • Micro-batch each 60 seconds, cannot 100ms.
  • SQS polling adds latency, Lambda cold starts, not designed for 1M/sec.
  • Not enables cross-type joins.
  • For NLP extraction not querying.
  • 10 GB easily fits single-node processing.
  • Single CSV format is lowest variety.
  • Weekly batch is opposite of high velocity.
  • Misses real-time requirements.
  • Menyulitkan format-specific processing.
  • PDFs and images cannot in-convert to Parquet.
  • Can handle variability but SQS doesn't guarantee ordering needed for CDR processing.
  • Very expensive — membayar 10x capacity 99.9% time.
  • Doesn't address velocity requirement.
  • Expensive at 10 TB/day and doesn't handle variety well.
  • Cannot handle any of the three V's at this scale.
