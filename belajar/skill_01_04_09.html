Key Services & Concepts

AWS CodePipeline
Orkestrasi CI/CD for membangun, menguji, and men-deploy automatically.

Key Points

  • CodePipeline provides a fully managed CI/CD pipeline with distinct stages. Source stage automatically triggers on code commits (eliminating manual initiation). Build stage runs tests BEFORE deployment (catching bugs early). Deploy stage uses infrastructure-as-code for consistent, repeatable deployments. This reduces 2-hour manual processes to automated 10-minute deployments with built-in quality gates.
  • Multi-layer testing ensures comprehensive coverage: unit tests validate individual transformation functions quickly (seconds). Integration tests verify end-to-end flow with synthetic data that matches production schema without HIPAA violations. Data quality assertions catch schema drift, null handling issues, and data type mismatches that unit tests miss. Synthetic data eliminates regulatory risk while testing realistic scenarios.
  • Blue/green deployment runs both versions simultaneously, eliminating any processing gap. Both versions read from the same source (Kinesis stream with separate consumer groups ensures independent processing). Comparing outputs validates the new version produces correct results before cutover. If green produces errors, traffic stays on blue with no impact. This provides zero downtime AND safe rollback. For financial data, comparing transaction counts and checksums between blue and green validates accuracy.
  • S3 versioning maintains every previous script version. Rollback is simply updating the Glue job's script location to point to the previous S3 version — a single API call taking seconds. Combined with CloudFormation's UpdateRollback or CodeDeploy's automatic rollback, recovery time drops from hours to under a minute. Tagging successful versions creates clear rollback targets.
  • Sequential pipeline stages guarantee ordering: infrastructure completes before application deployment begins. Pipeline artifacts enable passing values (new role ARN, new resource names) between stages without hardcoding. Multi-source triggers ensure the pipeline runs when either infrastructure or application code changes, always deploying in the correct order. Stage transitions only proceed after the previous stage succeeds.
  • CDK Pipelines enable "self-mutating" pipelines: the pipeline itself is defined in code, and if you change the pipeline definition (add a stage, modify a build step), the pipeline updates itself on the next run. buildspec.yml stored in the repo ensures build configuration is versioned alongside application code. Pull requests provide review before pipeline changes. New projects instantiate the same CDK pipeline construct with different parameters.
  • Custom Docker images with pre-installed dependencies eliminate installation time entirely. The image is built once (manually or via a separate pipeline), pushed to ECR, and referenced in the CodeBuild project. Every build starts with all dependencies available, making 15 daily deployments feasible with 4-minute builds. This saves the team 120 minutes/day (8 min × 15 builds) compared to installing each time.
  • Post-deployment canary tests validate functional correctness in the actual production environment. Running against a known dataset with expected outcomes provides a definitive pass/fail signal. Automated rollback on failure minimizes the blast radius of bad deployments. CloudWatch metrics track deployment health over time, identifying patterns (e.g., deployments failing more on Fridays). This closes the gap between "deployed" and "working correctly.".
  • CodePipeline Manual Approval actions provide integrated, auditable gates. The approval is recorded with the approver's IAM identity, timestamp, and comments — all stored in the pipeline execution history. CloudTrail provides additional audit logging of all API calls. S3 lifecycle policies with Glacier transition ensure 7-year retention at minimal cost. The entire flow is automated except the approval decision, creating an immutable audit trail.
  • Full GitOps requires: Git as source of truth (all infra in repo), automatic deployment on commit (CodePipeline trigger), and drift remediation (detecting and correcting manual changes). The drift detection stage ensures infrastructure matches Git state before new changes. AWS Config continuously monitors for out-of-band modifications, and Systems Manager Automation automatically remediates drift without manual intervention. This creates a self-healing infrastructure system.

Common Misconceptions & Pitfalls

  • Lambda triggered by S3 upload skips testing and has no approval mechanism; it's a fragile anti-pattern.
  • Cron-based polling is unreliable, introduces delay, and EC2 maintenance adds operational burden.
  • Step Functions orchestrates workflow but isn't designed for CI/CD; it lacks source integration and build capabilities.
  • Manual QA in production is too late; bad data may already affect patients or downstream systems.
  • Copying production healthcare data violates HIPAA and data privacy regulations; synthetic data must be used.
  • Syntax checks catch formatting issues but not logical errors in transformations (eg., incorrect join conditions, wrong date parsing).
  • Buffering delays processing and creates a burst when backlog is processed, potentially overwhelming downstream systems.
  • Reducing the gap doesn't eliminate it; even 5 minutes of lost transactions is unacceptable.
  • Maintenance windows still create a gap and don't work for 24/7 financial processing.
  • Re-running the full pipeline (build + test + deploy) takes 10-30 minutes, prolonging the outage.
  • Disabling the job stops all data processing, making the outage worse, not better.
  • Manual console edits bypass version control and testing, potentially introducing new bugs while creating drift.
  • Manual triggering is error-prone and doesn't scale; developers will forget the correct order under pressure.
  • Monorepos can work but don't inherently solve deployment ordering; a pipeline still needs sequential stages.
  • Retry logic for missing IAM roles is a band-aid that masks the fundamental ordering problem and introduces non-deterministic behavior.
  • Wiki documentation can't create pipelines and becomes outdated quickly.
  • Exported templates without version control lack change history and review capability.
  • Scripts without storage aren't reproducible and lack change tracking.
  • Larger compute speeds up CPU-bound tasks but pip install is mostly network I/O (downloading packages), providing minimal improvement.
  • Skipping installation means tests can't run since PySpark/pandas won't be available.
  • S3 caching helps but still requires downloading and extracting the cache each build (2-3 minutes overhead); not as fast as pre-installed deps.
  • Waiting 24 hours for consumer reports means bad data propagates through the entire system before detection.
  • CloudFormation success means infrastructure deployed correctly, not that the application logic is correct.
  • Manual checks are slow, unreliable, and don't scale to 15 deployments/day.
  • Jira integration requires custom development and the approval record lives outside the AWS audit trail.
  • Email approvals are not machine-verifiable, easily lost, and don't integrate with deployment automation.
  • MFA verifies identity but doesn't capture explicit approval decisions or provide an audit trail of what was approved.
  • Local deployment from laptops isn't automated, auditable, or repeatable across team members.
  • Manual deployment breaks the "automatic reconciliation" principle of GitOps.
  • Lambda functions running CLI commands lack state management, dependency resolution, and rollback capabilities.
