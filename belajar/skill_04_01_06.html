Key Points

  • Amazon RDS is managed service where AWS bertanggung jawab above OS patching, hardware maintenance, and provides engine version upgrades. In shared responsibility model for RDS, AWS manages: infrastructure layer, OS patching, database engine patching (scheduled maintenance windows), and hardware reliability. Customer only bertanggung jawab for: data encryption configuration, network access (Security Groups), IAM authentication, and managing database users/permissions.
  • AWS Glue is fully managed — customer not melihat or manages underlying compute infrastructure, OS, or runtime. AWS handles all that. Customer Glue responsibilities: IAM permissions, data encryption settings, VPC connectivity, and job-level security configurations. Amazon EMR is semi-managed — AWS provides cluster provisioning and Hadoop ecosystem, but customer bertanggung jawab for: OS-level security hardening (custom AMIs), SSH key management, security group configurations on nodes, Kerberos/LDAP setup, encryption configuration in cluster level, and bootstrap action security.
  • This is example klasik perbedaan shared responsibility model between managed and unmanaged services. Amazon Redshift (managed): AWS manages underlying OS, hardware, patching, and infrastructure security. Customer bertanggung jawab for data, access control, network config (VPC/Security Groups), and encryption settings. EC2 + Spark (unmanaged/self-managed): Customer bertanggung jawab for ALL layer including OS patching, security hardening, middleware updates, and application security. AWS only bertanggung jawab for physical infrastructure (hypervisor to below).
  • Managed services such as Athena including in scope AWS compliance programs (SOC 2, PCI DSS, HIPAA eligible, dll.) — artinya AWS has been disertifikasi for manages infrastructure and service layer with standard said. Customer mewarisi sertifikasi this for part that is managed AWS. For EC2+Presto (unmanaged), AWS compliance only mencakup physical infrastructure (data center, hardware, hypervisor). All layer in above — OS, database software, application — becomes tanggung jawab customer for memenuhi standard compliance. Customer must performs: OS hardening, access logging, encryption implementation, and mendokumentasikan all controls for auditor.
  • DynamoDB (managed) provides encryption at rest in a terintegrasi — customer quite memilih between AWS owned key, AWS managed key, or customer managed CMK. AWS handles all implementation technical (no OS/filesystem level config). For MongoDB in EC2 (unmanaged), customer bertanggung jawab for multiple encryption layers: (1) EBS volume encryption — uses KMS key, (2) MongoDB WiredTiger encryption — configuration encryptionKeyFile and encryptionCipherMode, (3) Key management — rotasi, storage, access control for encryption keys, (4) TLS/SSL configuration for in-transit encryption. Operational overhead jauh higher.
  • For team small (2 engineers), operational overhead security from self-managed Kafka very berat: ZooKeeper security hardening, Kafka broker TLS certificate management and rotation, SASL/SCRAM or mTLS authentication configuration, ACL management, OS patching on all nodes, multi-AZ setup for HA, monitoring cluster security posture. Amazon Kinesis as managed service eliminates all that — AWS handles infrastructure security, provides native IAM integration for access control, built-in encryption (at rest and in-transit), and automatic multi-AZ availability. Tim only needs fokus on IAM policies and application-level security.
  • Network security responsibilities different significant between managed and unmanaged. RDS (managed): AWS manages internal networking between primary instance and replicas, Multi-AZ synchronous replication traffic, automated failover routing, and DNS endpoint management. Customer manages: VPC subnet group selection, Security Group rules (inbound/outbound), public accessibility setting, and SSL/TLS enforcement. EC2 database (unmanaged): Customer manages ALL networking: replication traffic routing and encryption, failover mechanism (custom scripts/third-party), Security Groups, NACLs, OS-level firewall (iptables/nftables), DNS management, load balancing.
  • AWS Glue DataBrew (serverless/fully managed): AWS handles all patching — OS, runtime, libraries, and framework updates occurs transparently. Customer does not need schedule maintenance windows or track CVEs for infrastructure layer. EMR (semi-managed): Although AWS provides EMR releases with updated software, customer bertanggung jawab for: (1) Memilih and updating to EMR release version terbaru, (2) Custom AMI patching if uses custom AMIs, (3) Monitoring for security vulnerabilities in Hadoop ecosystem components, (4) Updating bootstrap actions that may install software additional, (5) Cluster replacement for applies patches (in-place patching not always feasible).
  • Amazon OpenSearch Service (managed): Node-to-node encryption enabled with single checkbox/API call. AWS menangkan entire PKI infrastructure — certificate generation, distribution to all nodes, automatic rotation, and TLS configuration. Customer does not need manages certificates. Self-hosted Elasticsearch on EC2 (unmanaged): Customer must manages complete PKI: (1) Setup Certificate Authority (CA), (2) Generate certificates per node, (3) Distribute certificates in a secure, (4) Configure elasticsearch.yml with xpack.security.transport.ssl settings, (5) Implement certificate rotation before expiry, (6) Monitor certificate validity. Operational overhead very significant.
  • Redshift Serverless (fully managed): AWS bertanggung jawab full above all software layers — engine version, OS, libraries, dependencies. Customer TIDAK needs track or patch infrastructure components. Tanggung jawab customer only: SQL stored procedures, user management, access controls, and data classification. EMR (semi-managed): Although AWS provides pre-packaged EMR releases, customer bertanggung jawab for: (1) Memilih EMR release version that appropriate (and upgrading), (2) Custom software installed via bootstrap actions — tracking versions and security, (3) Additional JAR dependencies that in-upload, (4) Custom AMI components if is used, (5) Python/R packages that in-install via pip/conda. For vulnerability management, team must maintain Software Bill of Materials (SBOM) for all custom components in EMR.
