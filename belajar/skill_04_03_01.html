Poin-Poin Kunci

  • Redshift Dynamic Data Masking (DDM) adalah solusi optimal untuk skenario ini: Implementation: (1) Create masking policy: CREATE MASKING POLICY ssn_mask WITH (ssn VARCHAR) USING ('XXX-XX-' || RIGHT(ssn, 4)); CREATE MASKING POLICY full_mask WITH (val VARCHAR) USING (NULL); (2) Attach to columns for specific roles: ATTACH MASKING POLICY ssn_mask ON patient_records(ssn) TO ROLE analyst_role; ATTACH MASKING POLICY full_mask ON patient_records(patient_name) TO ROLE analyst_role; (3) Priority: physician_role → no masking policy attached → sees original data. analyst_role → masking policies active → sees masked values. Advantages: No data duplication (unlike.
  • Deterministic tokenization (pseudonymization) memenuhi kedua requirement: Consistency requirement: HMAC-SHA256(customer_id, secret_key) → selalu menghasilkan token yang SAMA untuk customer_id yang sama. Vendor dapat track: "token_abc visited page X on Monday, then purchased Y on Tuesday" — behavioral analysis intact. Irreversibility: HMAC is one-way — tanpa secret_key, vendor tidak dapat reverse token → customer_id. Brute-force infeasible untuk large ID spaces. Secret key hanya disimpan oleh data owner — never shared with vendor. Implementation in Glue ETL: from hashlib import hmac; token = hmac.new(secret_key, customer_id.encode(), 'sha256').hexdigest(). Mengapa bukan opsi lain:.
  • Crypto-shredding adalah approach yang paling practical dan reliable untuk GDPR deletion: Architecture: (1) During data ingestion: Each customer gets unique KMS key (or per-customer data key encrypted by a customer-specific CMK). PII fields encrypted with customer's key: {name: ENC(key_123, "John Doe"), email: ENC(key_123, "john@example.com"), transactions: [unencrypted aggregate data]}. (2) Normal operation: Applications decrypt PII using customer's key for display/processing. Non-PII data remains accessible without the key. (3) Deletion request (GDPR Art. 17): Schedule KMS key deletion: aws kms schedule-key-deletion --key-id key_123 --pending-window-in-days 7. After pending window: key permanently deleted. ALL encrypted PII across S3, Redshift, DynamoDB → permanently unreadable. Aggregated/anonymized data derived from customer remains usable. Advantages over physical deletion: Don't need to find every copy across distributed systems (backups, caches, logs). Instant "logical deletion" — data becomes garbage without key. Works even for data in immutable storage (S3 Glacier, backups).
  • Amazon Macie adalah purpose-built service untuk PII discovery in S3: Capabilities: ML-powered classification: identifies PII even in unstructured text, PDFs, images. Managed data identifiers: 100+ built-in PII patterns (SSN, credit cards, bank accounts, names, addresses, passport numbers, driver's licenses). Custom data identifiers: regex + keyword patterns for organization-specific sensitive data. Format support: CSV, JSON, Parquet, Avro, PDF, text, MS Office documents. Continuous monitoring: Automated sensitive data discovery — scans new/modified objects. Event-driven: integrates with S3 event notifications. Scheduled jobs: daily/weekly comprehensive scans. Scale: manages 500+ buckets across multi-account (Organizations integration). Findings: Severity classification (High, Medium, Low). Integration with Security Hub for centralized dashboard. EventBridge integration for automated remediation (e.g., quarantine, encrypt, alert). Cost optimization: sampling-based discovery mode reduces scan costs.
  • AWS Glue DataBrew provides visual data masking transforms untuk ETL pipelines: DataBrew Masking Features: Built-in transformations: MASK_CUSTOM — replace characters with specified mask (e.g., * for all but last 4). MASK_DATE — generalize dates (keep only year). MASK_RANGE — mask numerical ranges. HASH — cryptographic hash replacement. REDACT — complete removal. Credit card masking recipe: Step 1: Select credit_card_number column. Step 2: Apply MASK_CUSTOM transform: mask character = "*", keep last 4 positions. Result: "4532-1234-5678-9012" → "****-****-****-9012". Alternative approach in Glue PySpark: Use custom transformation in Glue ETL script: df = df.withColumn("credit_card", concat(lit("****-****-****-"), substring(col("credit_card"), -4, 4))). DataBrew advantage: Visual, no-code, auditable transformations. Recipe versioning for compliance documentation. Profile data before/after to verify masking completeness.
  • K-anonymity via generalization addresses re-identification risk: Problem: Direct identifiers removed, but quasi-identifiers (age, zip, diagnosis) combined can uniquely identify individuals. Example: "35-year-old male, zip 98115, diabetes Type-1" → might identify only one person in a small community. K-anonymity (k≥5 for HIPAA Safe Harbor): Generalization: Age 35 → "30-39". Zip 98115 → "981**". Rare diagnosis → broader category. Result: Every record matches at least k-1 other records — cannot pinpoint individual. HIPAA Safe Harbor method requires: Zip codes truncated to 3 digits (or 000 if population = k for all groups.
  • Format-Preserving Encryption (FPE) optimal untuk PCI-DSS compliant masking: PCI-DSS Requirement 3.4: PAN must be rendered unreadable. Acceptable methods: One-way hash, truncation, index tokens, OR strong cryptography with associated key management. FPE (AES-FF1/FF3-1) properties: Format preservation: 16-digit input → 16-digit output. Valid format: output passes Luhn check → applications don't break. Deterministic: PAN "4532-1234-5678-9012" always maps to same masked value → referential integrity maintained (foreign keys, joins between tables still work). NIST-approved: FF1 (NIST SP 800-38G) — accepted by PCI-DSS. Reversible (with key): production can decrypt if needed; non-production environments never have the key. Why for testing: FK relationships preserved: masked PAN in transactions table matches masked PAN in refunds table. Format valid: application code doesn't throw validation errors. Realistic data: testing resembles production behavior.
  • In-stream tokenization architecture untuk real-time masking: Architecture: [Producer] → [Raw Kinesis Stream (restricted)] → [Lambda/Flink Consumer] → [Clean Kinesis Stream (analytics)] → [Analytics Consumers]. Lambda/Flink transformation: Read event: {"user_email": "john@example.com", "event": "page_view", "timestamp": "..."}. Apply HMAC: token = HMAC-SHA256(secret_key, "john@example.com") → "a1b2c3d4...". Output: {"user_token": "a1b2c3d4...", "event": "page_view", "timestamp": "..."}. Consistency: Same email always produces same token → cohort analysis works. Secret management: Key from AWS Secrets Manager, rotated periodically. Latency: Lambda adds ~10-50ms processing per batch. Flink provides sub-second end-to-end. Separation of concerns: Raw stream: only authorized services (compliance, fraud detection) access. Clean stream: safe for any analytics consumer.
  • Metadata-driven masking framework untuk multi-jurisdictional compliance: Design: (1) Classification Layer (Glue Data Catalog tags): Field: email → PII_type: "contact_info", jurisdictions: ["GDPR", "CCPA", "LGPD"]. Field: IP_address → PII_type: "online_identifier", jurisdictions: ["GDPR"] (GDPR considers IP as PII, some others don't). (2) Policy Engine (DynamoDB rules table): {pii_type: "contact_info", regulation: "GDPR", context: "analytics"} → mask_technique: "pseudonymization". {pii_type: "contact_info", regulation: "CCPA", context: "sale"} → mask_technique: "opt_out_deletion". (3) Masking Execution: ETL jobs query policy engine → apply appropriate masking per field per jurisdiction. Most restrictive rule wins when data subject to multiple regulations. (4) Audit Trail: Every masking operation logged with regulation reference. Demonstrable compliance for each regulation. Why this approach: Flexible — new regulations added by updating policy table, not code. Auditable — clear mapping from regulation → masking action. Accurate — different fields masked differently based on actual regulatory requirements.
  • Plain hashing BUKAN true anonymization untuk low-entropy data seperti email: Vulnerability: Email addresses have limited entropy — predictable patterns. Attacker approach: Generate list of probable emails (firstname.lastname combinations + common domains). Hash each: SHA256("john.smith@gmail.com") → "abc123...". Match against hashed dataset. Result: millions of emails recoverable in minutes. This is a "pre-image attack via enumeration" — technically SHA-256 is one-way, but the INPUT SPACE is small enough to enumerate. Solutions (in order of preference): (1) HMAC with secret key: HMAC-SHA256(secret_key, email) — without secret_key, rainbow tables useless. Key management critical — store in KMS/Secrets Manager. (2) Salted hash: SHA256(random_salt + email) — different salt per record. Prevents matching across records but salt must be stored. (3) Differential privacy: Add calibrated noise to aggregated statistics rather than pseudonymizing individual records. For true anonymization: Consider if you need consistency (HMAC/tokenization) or irreversibility (generalization, differential privacy).

Miskonsepsi & Jebakan Umum

  • Views work but are harder to maintain at scale, don't support complex masking functions natively.
  • Physicians need PII for patient care, can't remove.
  • Data duplication, sync overhead, storage cost.
  • Vendor cannot do cross-session analysis (lose analytical value).
  • Same customer gets different IDs each session — cannot track behavior. Key distinction: Tokenization = pseudonymization (consistent replacement, reversible by key holder). Anonymization = irreversible (no one can recover original data).
  • Semua records become one "customer" — useless for behavior analysis.
  • Moving data isn't deleting it.
  • Extremely difficult across distributed systems, backup tapes, etc.
  • Soft delete ≠ actual deletion, violates GDPR.
  • Glue Data Quality checks data correctness, not PII detection.
  • Doesn't scale, relies on manual tagging accuracy.
  • Custom regex misses complex patterns, doesn't handle unstructured data well, maintenance burden.
  • S3 encryption encrypts entire objects, doesn't mask specific fields.
  • Redshift DDM operates within Redshift, not on S3 files.
  • Crawlers read metadata, don't transform data content.
  • Random noise destroys data utility for ML; diagnosis noise makes data useless.
  • Encryption ≠ anonymization under HIPAA; encrypted data is still considered PHI.
  • Insufficient, quasi-identifier linkage attacks still possible.
  • Truncation is valid for DISPLAY only; PCI-DSS allows first 6 + last 4 for display, but stored data still needs full protection in scope systems.
  • Static value breaks referential integrity, unrealistic testing.
  • Plaintext PAN violates PCI-DSS Req 34.
  • Batch introduces hours of latency, raw PII accessible during delay.
  • Kinesis encryption protects data at rest/transit, doesn't mask specific fields.
  • Deleting email removes ability to do cross-session cohort analysis.
  • GDPR isn't always the most restrictive (e.g., Brazilian LGPD has unique requirements).
  • "least restrictive" guarantees violations of stricter regulations.
  • Massive duplication, operational overhead.
  • MD5 is LESS secure than SHA-256, factually wrong.
  • 64-character hex output is standard database column size.
  • SHA-256 is NOT mathematically reversible; the issue is enumeration attack on limited input space.
