Skill 2.4.6: Vectorization concepts

vectorizationBedrockembeddings

Ringkasan

Skill ini termasuk dalam Domain 2: Data Store Management (Task 2.4: Design data models and schema evolution), dengan fokus pada vectorization concepts. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon Bedrock
Akses model fondasi (LLM) terkelola untuk embedding dan generative AI.

Poin-Poin Kunci

  • Amazon Bedrock Knowledge Bases menyediakan solusi RAG end-to-end yang otomatis: memecah dokumen menjadi chunks, membuat vector embeddings, menyimpannya di vector store, dan melakukan semantic search pada query time untuk menemukan konteks relevan yang dikirim ke foundation model.
  • Semantic chunking memecah dokumen berdasarkan batas topik yang dideteksi oleh perubahan signifikan dalam embedding similarity antar kalimat berurutan. Ini ideal untuk corpus campuran karena secara otomatis menyesuaikan ukuran chunk berdasarkan konten — FAQ pendek mungkin menjadi satu chunk, sementara manual teknis dipecah di batas topik alami.
  • Amazon Titan Text Embeddings V2 mendukung multilingual content dan memiliki fitur configurable output dimensions (256, 512, atau 1024) yang memungkinkan tradeoff antara storage efficiency dan quality. Dimensi 256 sangat cocok untuk use case dengan storage constraints sambil tetap mempertahankan kualitas yang baik untuk retrieval.
  • Amazon OpenSearch Serverless dengan vector search collection type dirancang untuk high-concurrency, low-latency vector similarity search. Serverless mode otomatis scales untuk menangani 10,000 concurrent users, dan arsitektur-nya dioptimalkan untuk approximate nearest neighbor (ANN) search pada scale besar (50M vectors).
  • Cosine similarity mengukur sudut antara dua vektor, tidak bergantung pada magnitude (panjang) vektor. Ini ideal ketika Anda ingin membandingkan "arah" atau makna semantik tanpa dipengaruhi oleh panjang deskripsi. Produk yang dideskripsikan singkat vs detail akan memiliki vectors dengan magnitude berbeda tapi arah yang sama jika kontennya serupa.
  • Amazon Bedrock Knowledge Bases mendukung data source syncing yang dapat dijadwalkan atau dipicu secara manual. Proses sync mendeteksi dokumen baru, yang diubah, dan yang dihapus, kemudian memperbarui embeddings di vector store sesuai perubahan.
  • Change data capture (CDC) pattern untuk mendeteksi dokumen yang berubah, kemudian hanya memproses perubahan melalui embedding pipeline dan melakukan upsert ke vector store, adalah pendekatan paling efisien. Ini menghindari re-processing dokumen yang tidak berubah, menghemat waktu dan biaya embedding API calls.
  • Ketika chunks terlalu besar, satu embedding mewakili multiple topics yang dicampur bersama, menghasilkan "diluted" vector yang kurang spesifik untuk topik manapun. Ini menyebabkan irrelevant results karena embedding tidak cukup terfokus pada satu topik (seperti drug interactions). Solusinya adalah menggunakan chunks yang lebih kecil dan terfokus.
  • Amazon OpenSearch Service secara native mendukung hybrid search yang mengkombinasikan k-NN vector search (semantic) dengan BM25 text scoring (keyword) dalam single query. Score normalization memungkinkan penggabungan results dari kedua metode secara seamless.
  • HNSW (Hierarchical Navigable Small World) index adalah algoritma ANN (Approximate Nearest Neighbor) yang membuat graph structure multi-layer untuk navigasi cepat menuju neighbors terdekat. Dengan HNSW index, pgvector dapat melakukan similarity search dalam sub-second pada 10M vectors dengan accuracy trade-off minimal (recall >95%).

Miskonsepsi & Jebakan Umum

  • Mahal, memerlukan waktu lama, dan tidak update otomatis saat dokumen berubah.
  • Kurang efektif untuk semantic understanding dibandingkan vector similarity search.
  • Tidak mungkin karena context window memiliki batas token yang tidak bisa menampung 10,000 dokumen.
  • Membuat embeddings terlalu general untuk dokumen panjang, kehilangan detail spesifik.
  • Akan memecah FAQ secara tidak tepat dan mungkin memotong konteks di manual.
  • Berguna tapi lebih kompleks dan belum tentu menangani variasi ukuran dokumen sebaik semantic chunking.
  • Hanya optimal untuk English, tidak multilingual.
  • Memiliki fixed 1536 dimensions yang boros storage.
  • Dirancang untuk image+text, overkill untuk text-only queries.
  • Baik untuk smaller scales tapi akan struggle dengan 50M vectors pada 10K concurrent users tanpa significant tuning.
  • Tidak memiliki native vector similarity search capabilities.
  • Tidak bisa memberikan sub-100ms latency untuk similarity search pada 50M vectors.
  • Juga magnitude-dependent dan kurang umum untuk semantic similarity.
  • Dipengaruhi oleh magnitude sehingga deskripsi panjang vs pendek akan terlihat "jauh".
  • Salah — S3 versioning saja tidak memicu re-embedding otomatis tanpa proses sync.
  • Sangat tidak efisien dan menyebabkan downtime.
  • Terlalu kompleks dan Knowledge Base sudah menyediakan built-in sync mechanism.
  • Sangat wasteful untuk large corpus yang jarang berubah seluruhnya.
  • Tidak realistis — vector databases umumnya tidak generate embeddings secara internal.
  • Menambahkan latensi signifikan ke setiap query.
  • Tidak diperlukan — Titan V2 capable untuk medical text jika chunking benar.
  • Salah — mengurangi dimensi justru kehilangan informasi.
  • Bisa membantu sedikit tapi tidak menyelesaikan root cause bahwa embeddings sendiri kurang spesifik.
  • Salah — DynamoDB tidak mendukung native vector search atau full-text search.
  • Bisa dilakukan tapi memerlukan custom logic untuk menggabungkan scores dari dua tipe query yang berbeda.
  • Menambah latency dan complexity dalam result merging.
  • Membantu sedikit tapi exact search tetap O(n) yang tidak scalable.
  • Mengurangi kualitas retrieval secara signifikan dan masih memerlukan linear scan tanpa index.
  • Membantu jika ada filter yang baik tapi tidak menyelesaikan masalah dasar exact search.
