Key Services & Concepts

AWS Lake Formation
Tata kelola data lake: permission based on table/kolom/baris and LF-Tags in atas Glue Catalog.
AWS CloudFormation
Infrastructure as Code deklaratif (template) for deployment berulang.
AWS CDK
Mendefinisikan infrastructure with bahasa pemrograman, dikompilasi to CloudFormation.

Key Points

  • Change sets preview exactly what CloudFormation will do — Add, Modify, Replace, or Delete each resource. For stateful resources like Redshift, "Replace" means the old cluster is deleted and a new one created. DeletionPolicy: Snapshot ensures a snapshot is taken before the old cluster is destroyed, enabling recovery. Verifying dependent resources prevents broken references after the new cluster gets a different endpoint.
  • CDK uses construct references to automatically infer deployment order. When you write: glue_job = GlueJob(role=my_iam_role), CDK recognizes that the Glue job depends on the IAM role and generates the DependsOn clause in CloudFormation. This ensures resources are created in the correct order. For cases where implicit dependencies aren't detected, addDependency() explicitly states "create resource A before resource B.".
  • CloudFormation cross-stack references (Outputs with Export + Fn::ImportValue) provide a managed way to share values between stacks. CloudFormation prevents the exporting stack from being deleted or modified in a way that would break importing stacks. This creates a dependency graph between stacks. The Pipeline stack automatically receives the correct S3 ARN and database name without hardcoding.
  • Custom Resources execute arbitrary logic during CloudFormation lifecycle events (Create, Update, Delete). A Lambda-backed custom resource can start a Glue Crawler, poll for completion, then create tables directly if needed. The cfn-response mechanism tells CloudFormation whether the operation succeeded, maintaining the stack's create/rollback semantics. This extends CloudFormation's capabilities beyond its native resource types.
  • CloudFormation's default behavior is all-or-nothing (atomic) deployment. If any resource fails to create, CloudFormation rolls back by deleting all resources created during that operation, returning to the previous known-good state. The stack enters ROLLBACK_COMPLETE or UPDATE_ROLLBACK_COMPLETE status. For new stacks, all resources are removed. The --no-rollback or DisableRollback option preserves resources for debugging but should only be used in development.
  • Nested stacks decompose a monolithic template into focused, maintainable modules while maintaining a single deployment unit. Each nested stack handles one concern (networking, storage, compute). The parent stack passes outputs from one nested stack as parameters to another, maintaining resource references. Updates to one nested stack don't affect others unless their outputs change. This reduces blast radius while preserving cross-resource references.
  • Conditions (e.g., IsPrimary: !Equals [!Ref "AWS::Region", "us-east-1"]) enable/disable resources per region. Mappings provide lookup tables for region-specific values without parameters. Pseudo-parameters like AWS::Region and AWS::AccountId enable unique naming without hardcoding. This single template adapts to any region at deploy time. Fn::Sub makes string interpolation readable: "arn:aws:s3:::${AWS::AccountId}-${AWS::Region}-datalake".
  • Multi-layered prevention works best: drift detection identifies existing drift before it causes deployment failures. AWS Config rules provide real-time alerting when manual changes occur. Restrictive IAM policies are the strongest control — if users can't modify resources via console, drift can't occur. Service Control Policies (SCPs) can enforce this at the organization level. Together, these ensure IaC remains the single source of truth.
  • CreationPolicy with cfn-signal provides application-level readiness verification. The EMR bootstrap action runs after the cluster starts, performs health checks (e.g., verifying YARN is accepting jobs), then sends a success signal via cfn-signal. CloudFormation won't mark the EMR resource as CREATE_COMPLETE until the signal arrives or timeout occurs. This guarantees dependent resources (Glue jobs) are only created after EMR is truly ready, not just provisioned.
  • cdk diff (equivalent to a change set preview) shows exactly what will happen — update, replace, or delete. For Glue jobs, script path changes are in-place updates: CloudFormation modifies the job definition without affecting running executions. Running jobs continue with their original configuration. New runs pick up the updated script. Best practice is to deploy during maintenance windows to avoid version confusion, and use job bookmarks to track processing state across script changes.

Common Misconceptions & Pitfalls

  • Manual changes create drift between template and reality.
  • Deleting the entire stack destroys all resources unnecessarily and causes extended downtime.
  • Replacement of data stores CAN cause data loss if DeletionPolicy isn't configured properly.
  • Repeated deployments are unreliable and don't solve the underlying dependency problem.
  • Separating into stacks adds unnecessary complexity; within a single stack, CDK handles ordering.
  • CDK code defines infrastructure declaratively; sleep() in CDK code would execute during synthesis, not deployment.
  • Hardcoded values break when resources are recreated with new ARNs/names.
  • Passing parameters manually requires the operator to know current values and is error-prone during frequent deployments.
  • Manual copying is error-prone and adds operational overhead.
  • CloudFormation creates the crawler resource but doesn't RUN it; DependsOn only ensures the crawler is created, not that it has completed a crawl.
  • While valid for known schemas, this doesn't work when table schemas must be discovered from data at deployment time.
  • Manual intervention breaks automation and may cause race conditions with dependent resources.
  • CloudFormation doesn't pause for manual decisions during creation; it's automatic.
  • CDK doesn't add retry logic; it relies on CloudFormation's native behavior.
  • Partial deployment contradicts CloudFormation's atomic design principle.
  • Comments don't reduce deployment time or blast radius.
  • Completely independent stacks with no references make it impossible to share VPC, security groups, or IAM roles between resources that need them.
  • CDK in a single stack still has the same blast radius and long deployment time; the monolith issue persists.
  • Manual fixes break IaC principles and aren't repeatable.
  • Duplicate templates diverge and double maintenance effort.
  • Unnecessarily limiting functionality reduces the solution's capabilities.
  • Accepting drift normalizes bad practices and makes deployments increasingly unreliable.
  • Documentation without enforcement doesn't prevent human error.
  • Destroying and recreating causes data loss for stateful resources and extended downtime.
  • There is no stack-level timeout setting; CloudFormation waits indefinitely for resources by default.
  • DependsOn only ensures CloudFormation creates EMR before Glue jobs, but "created" doesn't mean "healthy and ready.".
  • WaitCondition with fixed timeout is a blunt instrument that always waits the full duration regardless of when EMR becomes ready.
  • Glue job definition updates succeed regardless of running executions.
  • CloudFormation doesn't terminate running Glue job executions; it only updates the job definition.
  • Script path changes don't trigger replacement; CDK/CloudFormation updates the existing job resource.
