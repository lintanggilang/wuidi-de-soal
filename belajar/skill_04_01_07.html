Key Services & Concepts

Amazon SageMaker
Platform ML end-to-end; SageMaker Catalog/Unified Studio for governance & discovery data.
Amazon DataZone
Katalog bisnis & portal self-service for discovery, subscription, and governed access (kini SageMaker Catalog).

Key Points

  • Domain Units in DataZone/SageMaker Unified Studio designed khusus for merepresentasikan organizational boundaries in in sebuah Domain. Domain is top-level container that merepresentasikan keseluruhan perusahaan, whereas Domain Units merepresentasikan subdivisi such as business units or departments. Each Domain Unit can has: (1) Governance policies tersendiri, (2) Data steward/owner assignments, (3) Approval workflows for data access, (4) Hierarchical structure (nested domain units).
  • DataZone implements publish-subscribe governance model: (1) Data Producer (Analytics) publishes asset to catalog, (2) Data Consumer (Marketing) discovers asset, (3) Consumer submits subscription request with business justification, (4) Data Owner/Steward reviews and approves/rejects, (5) Setelah approved, DataZone automatically provisions access (creates grants) so that consumer's project environment can accesses data. Workflow this ensures: auditability (who minta access, when, kenapa), governance control (owner approval), automated provisioning (no manual IAM policy updates).
  • Environment Profiles in DataZone mendefinisikan template for compute environments that can in-provision by projects. Each Environment Profile mencakup: (1) Blueprint type (Athena, Redshift, SageMaker, dll.), (2) Configuration parameters (instance types, cluster settings), (3) IAM roles and permissions that will in-provision, (4) Network configuration (VPC, subnets). Project members can creates Environment from available Profiles. When subscription in-approve, DataZone automatically grants access through environment that appropriate.
  • DataZone allows publishers to control asset visibility and subscription scope. When publishing an asset, the data steward can restrict: (1) Discovery scope — who can see the asset in the catalog (domain unit level restriction), (2) Subscription scope — who can request access. By limits visibility to Finance domain unit only, members from Marketing/Engineering domain units not will menemukan asset this in catalog search. This implements "need-to-know" principle on data discovery level, not only access level.
  • DataZone natively supports cross-account data sharing within the same domain. The workflow: (1) Account A registers as a data source and publishes assets, (2) Account B's project discovers and requests subscription, (3) After approval, DataZone automatically provisions cross-account access — typically using AWS Lake Formation cross-account grants, RAM shares, or cross-account IAM roles depending on the data source type. Key benefit: centralized governance — all access is auditable, revocable, and managed through single governance plane regardless of AWS account boundaries.
  • DataZone projects support role-based access with different permission levels: Project Owner: Full control — manage project settings, add/remove members, configure environments, approve requests within project scope. Project Contributor: Active participant — create assets, publish data, run jobs, request subscriptions, manage environments they've created. Project Viewer/Reader: Consumption-focused — browse available data, request subscriptions, query data through provisioned environments, but cannot publish or modify assets. This enables least-privilege access in in project.
  • DataZone supports configurable approval workflows that can requires multi-level approvals. For PII datasets: (1) Assets diberi metadata/glossary terms indicating PII classification, (2) Subscription request policies is configured so that PII-classified assets requires approval from multiple approvers, (3) Data Owner approves from business relevance perspective, (4) Compliance domain unit steward approves from privacy/regulatory perspective. Only after ALL approvers menyetujui, DataZone provisions access. This ensures governance without blocking legitimate access.
  • DataZone operates at two levels: (1) Governance layer — subscription approval, catalog management; (2) Infrastructure layer — actual IAM/Lake Formation permissions provisioned to environments. If subscription approved but access denied when query: the problem possibility in provisioning layer. Common causes: Environment profile's IAM role not has Lake Formation permissions to underlying table/database, Subscription grant fulfillment fails (race condition or misconfiguration), Lake Formation resource-link not yet terbuat in consumer's Glue catalog, Environment blueprint not properly configured for handle subscription grants. Troubleshooting: check DataZone subscription grant status detail, verify Lake Formation permissions on environment's execution role.
  • DataZone's hierarchy maps perfectly to data mesh principles: Domain = Organization (federated governance plane): Provides centralized catalog, shared glossary/metadata standards, organization-wide policies. Domain Units = Autonomous Teams/Business Domains: Each team independently manages their data products, defines local governance (who can publish, approval workflows), assigns data stewards. Projects = Data Product Workspaces: Teams build pipelines, prepare data, publish data products to catalog, manage lifecycle. Key data mesh alignment: (1) Domain ownership — teams own their domain units, (2) Data as product — publishing workflow makes data discoverable, (3) Self-serve infrastructure — environment profiles provide compute, (4) Federated governance — domain-level standards inherited by all units.
  • DataZone provides catalog-level lineage tracking across organizational boundaries. The lineage chain: (1) "Customer Segments" published by Sales domain unit — tracked as source asset. (2) Subscription relationship recorded — Marketing subscribed to this asset (who, when, why). (3) Marketing's derived "Campaign Targets" can declare its upstream dependency on "Customer Segments". (4) DataZone catalog shows the data flow: Sales → subscription → Marketing → derived product. Kombinasi with AWS Glue Data Catalog lineage (that tracks transformations in ETL level) provides end-to-end visibility. This critical for: impact analysis (if source changes, who affected?), compliance auditing (data provenance), and quality management.
