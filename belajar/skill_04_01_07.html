Domain 4: Security & Governance — Task 4.1: Apply authentication mechanisms

Skill 4.1.7: SageMaker Unified Studio domains

SageMakerDataZonedomains

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.1: Apply authentication mechanisms), dengan fokus pada sagemaker unified studio domains. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon SageMaker
Platform ML end-to-end; SageMaker Catalog/Unified Studio untuk governance & discovery data.
Amazon DataZone
Katalog bisnis & portal self-service untuk discovery, subscription, dan governed access (kini SageMaker Catalog).

Poin-Poin Kunci

  • Domain Units dalam DataZone/SageMaker Unified Studio dirancang khusus untuk merepresentasikan organizational boundaries di dalam sebuah Domain. Domain adalah top-level container yang merepresentasikan keseluruhan perusahaan, sedangkan Domain Units merepresentasikan subdivisi seperti business units atau departments. Setiap Domain Unit dapat memiliki: (1) Governance policies tersendiri, (2) Data steward/owner assignments, (3) Approval workflows untuk data access, (4) Hierarchical structure (nested domain units).
  • DataZone mengimplementasikan publish-subscribe governance model: (1) Data Producer (Analytics) publishes asset ke catalog, (2) Data Consumer (Marketing) discovers asset, (3) Consumer submits subscription request dengan business justification, (4) Data Owner/Steward reviews dan approves/rejects, (5) Setelah approved, DataZone automatically provisions access (creates grants) sehingga consumer's project environment dapat mengakses data. Workflow ini ensures: auditability (siapa minta akses, kapan, kenapa), governance control (owner approval), automated provisioning (no manual IAM policy updates).
  • Environment Profiles dalam DataZone mendefinisikan template untuk compute environments yang dapat di-provision oleh projects. Setiap Environment Profile mencakup: (1) Blueprint type (Athena, Redshift, SageMaker, dll.), (2) Configuration parameters (instance types, cluster settings), (3) IAM roles dan permissions yang akan di-provision, (4) Network configuration (VPC, subnets). Project members dapat membuat Environment dari available Profiles. Saat subscription di-approve, DataZone secara otomatis grants access melalui environment yang sesuai.
  • DataZone allows publishers to control asset visibility and subscription scope. When publishing an asset, the data steward can restrict: (1) Discovery scope — who can see the asset in the catalog (domain unit level restriction), (2) Subscription scope — who can request access. Dengan membatasi visibility ke Finance domain unit only, members dari Marketing/Engineering domain units tidak akan menemukan asset ini di catalog search. Ini implements "need-to-know" principle pada data discovery level, bukan hanya access level.
  • DataZone natively supports cross-account data sharing within the same domain. The workflow: (1) Account A registers as a data source and publishes assets, (2) Account B's project discovers and requests subscription, (3) After approval, DataZone automatically provisions cross-account access — typically using AWS Lake Formation cross-account grants, RAM shares, or cross-account IAM roles depending on the data source type. Key benefit: centralized governance — all access is auditable, revocable, and managed through single governance plane regardless of AWS account boundaries.
  • DataZone projects support role-based access with different permission levels: Project Owner: Full control — manage project settings, add/remove members, configure environments, approve requests within project scope. Project Contributor: Active participant — create assets, publish data, run jobs, request subscriptions, manage environments they've created. Project Viewer/Reader: Consumption-focused — browse available data, request subscriptions, query data through provisioned environments, but cannot publish or modify assets. Ini memungkinkan least-privilege access di dalam project.
  • DataZone supports configurable approval workflows yang dapat memerlukan multi-level approvals. Untuk PII datasets: (1) Assets diberi metadata/glossary terms indicating PII classification, (2) Subscription request policies dikonfigurasi sehingga PII-classified assets memerlukan approval dari multiple approvers, (3) Data Owner approves dari business relevance perspective, (4) Compliance domain unit steward approves dari privacy/regulatory perspective. Hanya setelah SEMUA approvers menyetujui, DataZone provisions access. Ini memastikan governance tanpa blocking legitimate access.
  • DataZone operates at two levels: (1) Governance layer — subscription approval, catalog management; (2) Infrastructure layer — actual IAM/Lake Formation permissions provisioned to environments. Jika subscription approved tapi access denied saat query: masalahnya kemungkinan di provisioning layer. Common causes: Environment profile's IAM role tidak memiliki Lake Formation permissions ke underlying table/database, Subscription grant fulfillment gagal (race condition atau misconfiguration), Lake Formation resource-link belum terbuat di consumer's Glue catalog, Environment blueprint tidak properly configured untuk handle subscription grants. Troubleshooting: check DataZone subscription grant status detail, verify Lake Formation permissions pada environment's execution role.
  • DataZone's hierarchy maps perfectly ke data mesh principles: Domain = Organization (federated governance plane): Provides centralized catalog, shared glossary/metadata standards, organization-wide policies. Domain Units = Autonomous Teams/Business Domains: Each team independently manages their data products, defines local governance (who can publish, approval workflows), assigns data stewards. Projects = Data Product Workspaces: Teams build pipelines, prepare data, publish data products to catalog, manage lifecycle. Key data mesh alignment: (1) Domain ownership — teams own their domain units, (2) Data as product — publishing workflow makes data discoverable, (3) Self-serve infrastructure — environment profiles provide compute, (4) Federated governance — domain-level standards inherited by all units.
  • DataZone provides catalog-level lineage tracking across organizational boundaries. The lineage chain: (1) "Customer Segments" published by Sales domain unit — tracked as source asset. (2) Subscription relationship recorded — Marketing subscribed to this asset (who, when, why). (3) Marketing's derived "Campaign Targets" can declare its upstream dependency on "Customer Segments". (4) DataZone catalog shows the data flow: Sales → subscription → Marketing → derived product. Kombinasi dengan AWS Glue Data Catalog lineage (yang tracks transformations di ETL level) memberikan end-to-end visibility. Ini critical untuk: impact analysis (jika source berubah, siapa affected?), compliance auditing (data provenance), dan quality management.

Miskonsepsi & Jebakan Umum

  • Salah — Projects adalah collaboration environments untuk tim yang bekerja bersama, bukan governance boundaries.
  • Salah — Environment Profiles mendefinisikan compute configurations, bukan governance boundaries.
  • Tidak leverage DataZone's built-in governance capabilities.
  • Tidak mengikuti proper data sharing workflow dan bisa violate data governance policies.
  • Violates least-privilege principle.
  • Adalah mechanism setelah approval untuk memberikan akses ke data, bukan compute environment definition.
  • Mengatur governance rules bukan compute configuration.
  • Adalah organizational boundaries.
  • Terlalu vague dan Domain-level visibility terlalu broad.
  • Akan menghancurkan seluruh organizational structure.
  • Adalah access control at infrastructure layer tapi tidak mencegah discovery di catalog — users masih bisa melihat metadata.
  • Is a severe anti-pattern yang violates security best practices.
  • Creates data duplication, increases costs, dan bypasses governance.
  • Addresses network connectivity, bukan data governance.
  • Adalah over-engineering dan breaks collaboration.
  • Doesn't leverage DataZone's data governance capabilities dan fine-grained project-level control.
  • Bekerja di infrastructure level tapi tidak menyediakan business-level approval workflow.
  • Isolates data tapi removes it from governed sharing.
  • Makes cross-domain sharing unnecessarily complex.
  • Salah — Athena adalah primary DataZone environment type.
  • Manual bucket policy seharusnya tidak diperlukan; DataZone automates ini.
  • Status menunjukkan "Approved" jadi belum revoked.
  • Centralizes everything (anti-mesh).
  • Breaks cross-domain discovery.
  • Salah — AWS provides native lineage capabilities.
  • Salah — cross-domain lineage didukung.
  • Salah — lineage bisa span domain units.
