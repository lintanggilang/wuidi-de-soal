Layanan & Konsep Utama

Lihat poin-poin kunci di bawah.

Poin-Poin Kunci

  • Decoupling sources into independent tasks (bulkhead pattern) isolates failures. 9 out of 10 sources can succeed even when one fails. Failed source retries independently without impacting others. This maximizes data freshness for available sources.
  • Kinesis (99.9% SLA), Lambda (99.95%), S3 (99.99%), Glue (serverless) are all highly available by design across AZs. Provisioned Redshift cluster in a single AZ is the weakest link — if that AZ fails, the cluster is unavailable. Multi-AZ Redshift atau Redshift Serverless distributes across AZs.
  • EMR Managed Scaling automatically adjusts cluster size based on workload metrics (YARN pending containers). As data grows and more processing is needed, nodes are added automatically up to the maximum. When load decreases, nodes are removed. No manual intervention needed.
  • Layered durability: (1) Kinesis retains data for 24h+ — data survives temporary failures. (2) Lambda retries failed batches automatically. (3) BisectBatchOnError isolates bad records without losing good ones. (4) DLQ captures records that fail all retries for later processing. No data is permanently lost.
  • Checkpointing through intermediate S3 writes creates "save points." If stage 3 fails, only stage 3 reruns (using stage 2's output from S3), not stages 1-2. This reduces wasted compute from 3 hours to minutes. Orchestrator (Step Functions/MWAA) manages stage-level retries.
  • S3 CRR ensures data is replicated continuously to DR region. Glue Catalog export maintains metadata availability. IaC (CloudFormation/CDK) enables rapid deployment of pipeline infrastructure in DR region within hours (meets 4-hour RTO). This is "warm standby" approach — data ready, compute deployable.
  • Dead-letter pattern separates bad records from good ones without stopping processing. Validate → route invalid to quarantine → process valid records. Invalid records are available for investigation and manual fixing. Throughput maintained for 999,998 valid records.
  • Horizontal scaling with auto-scaling compute maintains constant processing time regardless of volume. Data is partitioned (by date, key, etc.) and processed in parallel. If data doubles, cluster doubles workers automatically — wall-clock time stays ~1 hour. This is the fundamental principle of distributed data processing.
  • Catch blocks handle errors after retries are exhausted. The Catch redirects to a "handle failure" state that logs details, then transitions to Redshift load instead of failing the entire workflow. This implements graceful degradation — pipeline continues with partial results. Job A output still gets loaded.
  • Lambda aliases with weighted routing enable canary deployments: shift small traffic to new version, monitor errors, auto-rollback if issues detected. Kinesis never stops — old version handles 90% of traffic during validation. CodeDeploy integration automates this.

Miskonsepsi & Jebakan Umum

  • Doesn't fix the dependency problem.
  • Guarantees zero data when one source has issues.
  • Wastes time re-processing successful sources.
  • Kinesis retention doesn't affect availability.
  • Lambda reserved concurrency is for throttling prevention, not availability.
  • S3 already 99.99% durable and available.
  • Reactive and may miss growth spikes.
  • Wastes money for months while data is only 100 GB.
  • Cannot process 10 TB datasets.
  • Prevents throttling but not failure handling.
  • Notify but don't prevent data loss.
  • Is about read consistency, not write durability.
  • Doesn't prevent failures or reduce restart cost.
  • For incremental source reads, not mid-job checkpointing.
  • Pipeline doesn't use EBS primarily.
  • Not all services have automatic multi-region; S3 doesn't replicate across regions by default.
  • Meets RTO but doubles cost unnecessarily.
  • Ideal but not always possible (external sources).
  • Loses data without audit trail.
  • Only delays the problem — 1 TB still takes 1 hour.
  • Doesn't wait for Job A output that Redshift might need.
  • Streaming pipelines have no natural maintenance windows.
  • All traffic immediately goes to new code without safety net.
  • Causes data backlog and potential loss.
