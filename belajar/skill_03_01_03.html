Summary

Skill this including in Domain 3: Operations & Support (Task 3.1: Automate data processing), with fokus on call sdks from code. Materi berikut merangkum service AWS that relevan beserta concept important that needs kamu kuasai for topik this.

Key Services & Concepts

Amazon API Gateway
Manages REST/HTTP/WebSocket API: throttling, otorisasi, caching, and integration backend.

Key Points

  • Boto3 paginators is way that most clean and recommended for handles paginated API responses. Paginator automatically handle continuation tokens, iterating through all halaman without manual loop. Ini also supports PageSize configuration and JMESPath filtering.
  • Boto3 adaptive retry mode uses token bucket algorithm that in a dynamic adjusts retry behavior based on throttling responses. Ini more sophisticated from standard mode — ia memperlambat request rate when detects throttling, prevents thundering herd. max_attempts: 10 provides quite retry for intermittent throttling. Konfigurasi this applies for all API calls on client the said.
  • Boto3 waiters is built-in polling mechanism that waits resource reaches state certain. Waiters has configurable Delay (polling interval) and MaxAttempts, with proper error handling for terminal failure states. For EMR, 'cluster_running' waiter polls describe_cluster in a teratur. WaiterConfig enables tuning for fit within Lambda timeout.
  • Cross-account access to AWS resources uses STS AssumeRole pattern. Pipeline in Account A calls sts.assume_role() for gets temporary credentials (AccessKeyId, SecretAccessKey, SessionToken) that has permissions from role in Account B. Credentials this is used for creates DynamoDB client new that operates in context Account B.
  • batch_write_item() can mengembalikan UnprocessedItems when throughput terlampaui. Items this TIDAK automatically in-retry by SDK — developer must explicitly handles mereka. Pattern that correct: loop that retrieves UnprocessedItems from response, apply exponential backoff, and re-submit until there is no UnprocessedItems tersisa.
  • Boto3 S3 operations raise botocore.exceptions.ClientError for service-level errors. For handles "object there is no", Anda catch ClientError and periksa error code in response dictionary. For S3 get_object, code will '404' or 'NoSuchKey'. Pattern this provides granular error handling.
  • IAM task roles on ECS is best practice because: (1) there is no credentials that needs in-manage — boto3 automatically gets temporary credentials from credential provider chain through container metadata endpoint, (2) credentials rotate automatic, (3) there is no risk credential exposure. Boto3 will automatic menemukan and uses task role credentials without configuration additional.
  • S3 delete_objects() API (multi-object delete) receives up to 1,000 keys per single API call, in a drastis reduces number HTTP requests from 10,000 menjadi 10 calls. Ini is way most efficient for bulk deletion. Pattern: batch keys menjadi groups of 1000, call delete_objects() for each batch.
  • Redshift Data API is asynchronous — execute_statement() returns immediately with Id (query ID). For gets results, Anda must poll describe_statement() until Status menjadi 'FINISHED' (or 'FAILED'/'ABORTED'), then call get_statement_result() for retrieves data. Pattern: while loop with sleep interval checking status.
  • Botocore has exception hierarchy that jelas: botocore.exceptions.ConnectionError (and subclasses EndpointConnectionError, ConnectTimeoutError, ReadTimeoutError) is transient network errors that secure for in-retry. botocore.exceptions.ClientError is service-level errors that requires pemeriksaan error code — several retryable (throttling, 500) and several not (validation errors, access denied). Membedakan kedua type this important for retry strategy that correct.

Common Misconceptions & Pitfalls

  • Can works for use case simple but resource interface provides less kontrol and can memory-intensive for 2M objects.
  • In a technical correct but manual token management more error-prone and verbose dibandingkan paginator — paginator is best practice.
  • Salah — MaxKeys is limited 1000 by S3 API, cannot diset higher.
  • Not adaptive and requires modifikasi each call.
  • Not solves throttling — only provides more time for fails.
  • Uses 'legacy' mode with only 5 attempts without adaptive behavior.
  • Adalah architecture that better for long waits but question specific about boto3 pattern.
  • Still unreliable if cluster takes longer than 15 min.
  • EMR not has "resource interface" that blocking in boto3.
  • Not ada parameter account ID in client constructor.
  • DynamoDB endpoint URL same for all accounts in region that same; endpoint not membedakan between accounts.
  • Only configures region, not provides cross-account access.
  • Very slow for 500K records and still can throttled.
  • Reduces possibility UnprocessedItems but not menghilangkannya sepenuhnya — handling still is required.
  • Salah — UnprocessedItems will HILANG if not in-handle (this penyebab data loss).
  • Terlalu broad — cannot membedakan between missing object vs permission error vs network error.
  • Has race condition — object can is deleted between check and download (TOCTOU).
  • S3 client not expose exceptions sebagai attributes on client object (different with several service such as DynamoDB).
  • Requires logic additional and still uses long-lived keys.
  • Tetap requires decryption key and access keys management.
  • Still uses long-lived credentials.
  • Increases complexity and still requires 10,000 API calls (only parallel).
  • Can works but resource interface in a internal still limits delete calls, and less control dibanding explicit batching.
  • Not immediate — can requires until 24+ hours for S3 processes lifecycle rules.
  • Not ada parameter 'synchronous' in execute_statement() API.
  • Boto3 not has built-in waiter for Redshift Data API statement completion.
  • Salah — get_statement_result() will throw error if statement not yet complete, not blocking.
  • Salah — retry on non-retryable errors (for example AccessDenied) is sia-sia.
  • Network errors not ClientError and not has HTTP status code.
