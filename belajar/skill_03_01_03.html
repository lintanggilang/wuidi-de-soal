Skill 3.1.3: Call SDKs from code

boto3SDKAPI

Ringkasan

Skill ini termasuk dalam Domain 3: Operations & Support (Task 3.1: Automate data processing), dengan fokus pada call sdks from code. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon API Gateway
Mengelola REST/HTTP/WebSocket API: throttling, otorisasi, caching, dan integrasi backend.

Poin-Poin Kunci

  • Boto3 paginators adalah cara yang paling clean dan recommended untuk menangani paginated API responses. Paginator secara otomatis handle continuation tokens, iterating melalui semua halaman tanpa manual loop. Ini juga mendukung PageSize configuration dan JMESPath filtering.
  • Boto3 adaptive retry mode menggunakan token bucket algorithm yang secara dinamis menyesuaikan retry behavior berdasarkan throttling responses. Ini lebih sophisticated dari standard mode — ia memperlambat request rate ketika mendeteksi throttling, mencegah thundering herd. max_attempts: 10 memberikan cukup retry untuk intermittent throttling. Konfigurasi ini berlaku untuk semua API calls pada client tersebut.
  • Boto3 waiters adalah built-in polling mechanism yang menunggu resource mencapai state tertentu. Waiters memiliki configurable Delay (polling interval) dan MaxAttempts, dengan proper error handling untuk terminal failure states. Untuk EMR, 'cluster_running' waiter polls describe_cluster secara teratur. WaiterConfig memungkinkan tuning untuk fit within Lambda timeout.
  • Cross-account access ke AWS resources menggunakan STS AssumeRole pattern. Pipeline di Account A memanggil sts.assume_role() untuk mendapatkan temporary credentials (AccessKeyId, SecretAccessKey, SessionToken) yang memiliki permissions dari role di Account B. Credentials ini digunakan untuk membuat DynamoDB client baru yang beroperasi dalam context Account B.
  • batch_write_item() dapat mengembalikan UnprocessedItems ketika throughput terlampaui. Items ini TIDAK secara otomatis di-retry oleh SDK — developer harus explicitly menangani mereka. Pattern yang benar: loop yang mengambil UnprocessedItems dari response, apply exponential backoff, dan re-submit sampai tidak ada UnprocessedItems tersisa.
  • Boto3 S3 operations raise botocore.exceptions.ClientError untuk service-level errors. Untuk menangani "object tidak ada", Anda catch ClientError dan periksa error code di response dictionary. Untuk S3 get_object, code akan '404' atau 'NoSuchKey'. Pattern ini memberikan granular error handling.
  • IAM task roles pada ECS adalah best practice karena: (1) tidak ada credentials yang perlu di-manage — boto3 secara otomatis mendapatkan temporary credentials dari credential provider chain melalui container metadata endpoint, (2) credentials rotate otomatis, (3) tidak ada risk credential exposure. Boto3 akan otomatis menemukan dan menggunakan task role credentials tanpa konfigurasi tambahan.
  • S3 delete_objects() API (multi-object delete) menerima hingga 1,000 keys per single API call, secara drastis mengurangi jumlah HTTP requests dari 10,000 menjadi 10 calls. Ini adalah cara paling efisien untuk bulk deletion. Pattern: batch keys menjadi groups of 1000, call delete_objects() untuk setiap batch.
  • Redshift Data API adalah asynchronous — execute_statement() returns immediately dengan Id (query ID). Untuk mendapatkan results, Anda harus poll describe_statement() sampai Status menjadi 'FINISHED' (atau 'FAILED'/'ABORTED'), kemudian call get_statement_result() untuk mengambil data. Pattern: while loop dengan sleep interval checking status.
  • Botocore memiliki exception hierarchy yang jelas: botocore.exceptions.ConnectionError (dan subclasses EndpointConnectionError, ConnectTimeoutError, ReadTimeoutError) adalah transient network errors yang aman untuk di-retry. botocore.exceptions.ClientError adalah service-level errors yang memerlukan pemeriksaan error code — beberapa retryable (throttling, 500) dan beberapa tidak (validation errors, access denied). Membedakan kedua tipe ini penting untuk retry strategy yang benar.

Miskonsepsi & Jebakan Umum

  • Bisa bekerja untuk use case sederhana tapi resource interface memberikan kurang kontrol dan bisa memory-intensive untuk 2M objects.
  • Secara teknis benar tapi manual token management lebih error-prone dan verbose dibandingkan paginator — paginator adalah best practice.
  • Salah — MaxKeys dibatasi 1000 oleh S3 API, tidak bisa diset lebih tinggi.
  • Tidak adaptive dan memerlukan modifikasi setiap call.
  • Tidak menyelesaikan throttling — hanya memberikan lebih banyak waktu untuk gagal.
  • Menggunakan 'legacy' mode dengan hanya 5 attempts tanpa adaptive behavior.
  • Adalah arsitektur yang lebih baik untuk long waits tapi pertanyaan spesifik tentang boto3 pattern.
  • Masih unreliable jika cluster takes longer than 15 min.
  • EMR tidak memiliki "resource interface" yang blocking di boto3.
  • Tidak ada parameter account ID di client constructor.
  • DynamoDB endpoint URL sama untuk semua accounts dalam region yang sama; endpoint tidak membedakan antar accounts.
  • Hanya mengatur region, tidak memberikan cross-account access.
  • Sangat lambat untuk 500K records dan tetap bisa throttled.
  • Mengurangi kemungkinan UnprocessedItems tapi tidak menghilangkannya sepenuhnya — handling tetap diperlukan.
  • Salah — UnprocessedItems akan HILANG jika tidak di-handle (ini penyebab data loss).
  • Terlalu broad — tidak bisa membedakan antara missing object vs permission error vs network error.
  • Memiliki race condition — object bisa dihapus antara check dan download (TOCTOU).
  • S3 client tidak expose exceptions sebagai attributes pada client object (berbeda dengan beberapa service seperti DynamoDB).
  • Memerlukan logic tambahan dan masih menggunakan long-lived keys.
  • Tetap memerlukan decryption key dan access keys management.
  • Masih menggunakan long-lived credentials.
  • Meningkatkan complexity dan masih memerlukan 10,000 API calls (hanya parallel).
  • Bisa bekerja tapi resource interface secara internal tetap membatasi delete calls, dan less control dibanding explicit batching.
  • Tidak immediate — bisa memerlukan sampai 24+ jam untuk S3 memproses lifecycle rules.
  • Tidak ada parameter 'synchronous' di execute_statement() API.
  • Boto3 tidak memiliki built-in waiter untuk Redshift Data API statement completion.
  • Salah — get_statement_result() akan throw error jika statement belum selesai, tidak blocking.
  • Salah — retry pada non-retryable errors (misalnya AccessDenied) adalah sia-sia.
  • Network errors bukan ClientError dan tidak memiliki HTTP status code.
