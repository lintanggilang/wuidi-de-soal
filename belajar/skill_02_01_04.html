Key Points

  • AWS Transfer Family provides a fully managed SFTP service that stores files directly in S3, eliminating the on-premises server. Partners only need a DNS change (same SFTP protocol, same client software). The S3 Event Notification → Lambda → Glue pattern creates an event-driven pipeline that automatically processes files upon arrival without polling or manual intervention. Transfer Family handles authentication, encryption, and high availability.
  • This hybrid approach addresses the math: 500 TB over 1 Gbps = ~50 weeks (far exceeding 2-week deadline). Snow Family provides offline transfer — 7 Snowball Edge devices (80 TB each = 560 TB capacity) can be loaded in parallel on-premises in a few days and shipped to AWS in ~1 week. DataSync with HDFS agent then handles the ongoing 5 TB/day incremental sync over Direct Connect (easily achievable at 1 Gbps = ~10 TB/day capacity). This combination meets both the bulk deadline and ongoing sync requirement.
  • SCT + DMS with CDC is the standard AWS migration methodology for database migrations with minimal downtime: (1) SCT handles schema complexity (converting Oracle PL/SQL to Redshift SQL, mapping data types, converting stored procedures); (2) DMS full load migrates the initial 10 TB while the source remains online; (3) CDC continuously replicates changes from Oracle redo logs to keep Redshift synchronized during migration (days/weeks); (4) final cutover within 4 hours only needs to drain last few minutes of changes. This approach minimizes downtime to the brief cutover window.
  • DMS with CDC leverages PostgreSQL's built-in logical replication (WAL-based) which adds minimal overhead (~2-3%) to the source database. DMS reads the WAL stream without adding triggers or modifying the source schema. The S3 target endpoint supports direct Parquet output with configurable partitioning (timestamp-based), eliminating the need for a separate format conversion step. CDC ensures near real-time replication (seconds to 1 minute latency).
  • DataSync is purpose-built for this exact scenario: (1) the agent maximizes network utilization with parallel streams, compression, and integrity verification — transferring 50 TB over 10 Gbps Direct Connect in approximately 12 hours; (2) built-in metadata preservation maps NFS permissions and timestamps to S3 object metadata for compliance; (3) incremental sync uses checksums to identify changed files, efficiently transferring only the 500 GB/day of new data; (4) scheduled tasks automate ongoing sync without custom scripting.
  • Transfer Family's custom identity provider + managed workflows provide the complete multi-tenant solution: (1) Lambda-backed authentication validates partner credentials and returns partner-specific home directory mapping (logical directory to S3 prefix), isolating partners from each other; (2) each partner sees only their directory (cannot access other partners' files); (3) managed workflows execute post-upload Lambda steps with access to the session context (username, uploaded file path), enabling partner-specific SNS notification routing; (4) single server handles all 200 partners efficiently.
  • The two-stage approach (DMS → S3 → Glue → DynamoDB) provides maximum transformation flexibility: (1) DMS handles the efficient extraction from MongoDB with CDC support for ongoing replication during migration; (2) S3 intermediate stage decouples extraction from transformation; (3) Glue ETL with Python allows complex logic for flattening 5-level nested documents, unwinding arrays into separate DynamoDB items, and handling polymorphic documents with conditional attribute mapping; (4) DynamoDB batch writes from Glue load the transformed data efficiently.
  • Using purpose-built tools for each data type, running in parallel, maximizes efficiency: (1) Snowball Edge for 150 TB files bypasses bandwidth limitations (3 Gbps × 6 weeks = ~18 TB maximum over network, far short of 150 TB); multiple devices per data center enable parallel loading; (2) DMS is purpose-built for database migration with CDC, handling Oracle-to-AWS replication efficiently; (3) MGN replicates VMware images at the block level with continuous sync until cutover. All three streams can run simultaneously, meeting the 6-week deadline.
  • Transfer Family managed workflows provide native post-upload processing: (1) workflows execute immediately after upload completes (no S3 event delay); (2) sequential steps ensure malware scan occurs before schema validation; (3) Lambda custom steps enable any validation logic (schema checks, data type validation, record counts); (4) conditional routing (on-success vs. on-exception) automatically moves files to appropriate locations; (5) built-in integration means no additional infrastructure between Transfer Family and the validation logic.
  • SCT assessment reports are designed specifically for migration planning: (1) they analyze every database object and categorize conversion difficulty (green=automatic, yellow=needs review, red=requires manual rewrite); (2) for stored procedures, SCT attempts T-SQL to PL/pgSQL conversion and flags incompatible constructs; (3) CLR functions and SSIS packages are identified as requiring alternative solutions (Lambda, Glue); (4) the report provides percentage of automatic conversion achievable, helping estimate timeline and effort; (5) specific recommendations for each non-convertible item guide the team's manual work.

Common Misconceptions & Pitfalls

  • EC2 + s3fs-fuse requires server management, patching, scaling, and s3fs has known performance limitations; it doesn't provide automatic pipeline triggering.
  • AppFlow doesn't support SFTP as a source connector; it's designed for SaaS application integrations (Salesforce, SAP, etc.), not generic SFTP pulls.
  • Modifying 50 partners' upload processes violates the "no partner-side changes" requirement and introduces significant coordination overhead.
  • S3 Transfer Acceleration helps with internet transfers but is still bandwidth-limited; the internet connection would need 200+ Gbps to transfer 500 TB in 2 weeks.
  • 1 Gbps maxes out at ~10 TB/week; 500 TB would take ~50 weeks, far exceeding the 2-week window.
  • DMS is designed for database migration (relational/NoSQL), not HDFS file migration; it doesn't support HDFS as a source.
  • Stopping Oracle for backup and restore to RDS would require many hours of downtime (10 TB backup + restore), and federated queries aren't a migration — they create a dependency on Oracle.
  • CSV export requires taking Oracle offline for consistent export (exceeding 4-hour window for 10 TB), manual schema recreation for 500+ objects is error-prone, and provides no incremental sync.
  • DataSync copies files, not database structures; Oracle data files are not directly readable by Redshift.
  • DataSync copies files, not database logical changes; PostgreSQL data directory files are binary (not Parquet), and copying them every minute would be massive I/O overhead.
  • Nightly pg_dump provides data that's up to 24 hours stale (not near real-time), and the dump process itself creates significant source load for a 200 GB database.
  • Triggers on every table and row add significant overhead (easily exceeding 5%) at high write volumes, and Lambda invocation per row change would be prohibitively expensive and create massive Lambda concurrency.
  • Transfer Family is designed for partner file exchange (SFTP/FTP), not bulk data migration from NFS; it doesn't support NFS as a source or provide incremental sync capabilities.
  • Aws s3 sync works but uses single-stream transfer (not maximizing 10 Gbps), doesn't preserve NFS permissions as metadata, and requires managing the sync scheduling manually.
  • Snow Family is unnecessary when 10 Gbps Direct Connect can transfer 50 TB in ~12 hours; manual rsync to EC2 adds complexity and doesn't preserve metadata for S3.
  • AppFlow doesn't support generic SFTP as a connector; it's for SaaS integrations, and pulling from partner servers reverses the data flow direction.
  • A single shared user has no isolation between partners (one partner could overwrite another's files), and file naming conventions are unreliable for identification.
  • 200 separate servers would cost ~$43,800/month in endpoint fees alone ($0.30/hour × 200 × 730 hours), which is prohibitively expensive when a single server with multiple users suffices.
  • DocumentDB is a valid alternative but the question specifically asks about migrating to DynamoDB; this changes the target architecture entirely.
  • Storing MongoDB documents as raw DynamoDB Maps preserves the nested structure but doesn't optimize for DynamoDB's access patterns (GSIs require top-level attributes; nested Maps can't be indexed).
  • Athena JSON SerDe handles simple nesting but struggles with deeply nested polymorphic structures and cannot handle array flattening into separate records well.
  • 3 Gbps combined bandwidth can transfer only ~18 TB in 6 weeks; DataSync cannot move 200 TB within the timeline.
  • DMS is for database migration only; it doesn't support NFS file sources or VM image replication.
  • Snowmobile is for extremely large migrations (50-100 PB); for 200 TB it's overkill, has long lead times, and visiting 3 data centers sequentially may not fit within 6 weeks.
  • Polling introduces latency (up to 1 minute delay), wastes compute during idle periods, and requires managing EC2 infrastructure.
  • S3 Event Notifications + Step Functions work but add architectural complexity, potential timing issues (event delay), and extra services to manage; managed workflows are the native, purpose-built solution within Transfer Family.
  • Transfer Family does not have built-in CSV schema validation; it provides file transfer, not content validation.
  • DMS pre-migration assessment only checks technical connectivity and compatibility (data types, table structures), not stored procedure conversion complexity or ETL package migration.
  • Performance Insights monitors query performance metrics but cannot assess schema conversion complexity or stored procedure compatibility.
  • Trusted Advisor provides AWS account-level best practices (cost, security, performance), not database migration assessment.
