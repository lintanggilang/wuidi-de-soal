Skill 2.3.1: Load/unload S3 and Redshift

COPYUNLOADS3Redshift

Ringkasan

Skill ini termasuk dalam Domain 2: Data Store Management (Task 2.3: Manage the lifecycle of data), dengan fokus pada load/unload s3 and redshift. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon Redshift
Data warehouse berskala petabyte; mendukung COPY/UNLOAD, materialized view, dan streaming ingestion.
Redshift Streaming Ingestion
Konsumsi langsung dari Kinesis/MSK ke materialized view Redshift, latensi detik, tanpa staging S3.
Amazon S3
Object storage tahan lama; dasar data lake, mendukung event notification, versioning, dan lifecycle.

Poin-Poin Kunci

  • Splitting files to match slice count is the single most impactful optimization for COPY performance: (1) Redshift's COPY command parallelizes loading across slices; (2) each slice can process one or more files simultaneously — this is the fundamental parallelism mechanism; (3) with a single file, only ONE slice processes the load (single-threaded), wasting 15 of 16 slices; (4) with 16 files, ALL slices work in parallel, theoretically providing 16x throughput; (5) the ideal number of files is a multiple of the slice count for even distribution; (6) files should be approximately equal in size to avoid stragglers. AWS documentation explicitly recommends this as the #1 COPY optimization. Option B — GZIP compression reduces transfer volume (important for network-bound loads) but GZIP files cannot be split across slices. A single GZIP file still means single-slice processing. For parallel GZIP, you need multiple GZIP files (combining A and B is optimal). Option C — Parquet format is efficient (columnar, compressed, typed) and works well with COPY, but a single Parquet file still limits parallelism to one slice. File splitting provides more dramatic improvement than format change alone. Option D — COMPROWS affects compression encoding analysis (how many rows are sampled to determine optimal column encoding). It doesn't impact load speed — it affects the quality of compression decisions for stored data.
  • MAXERROR is the built-in mechanism for tolerating known data quality issues during COPY: (1) default MAXERROR is 0 — any single error aborts the entire load; (2) setting MAXERROR to a threshold (e.g., 100 for production loads with known quality issues) allows the COPY to complete despite some bad records; (3) failed records are captured in STL_LOAD_ERRORS with full detail: the raw field value ('N/A'), the target column type (Integer), the line number, and the file name; (4) after load, query STL_LOAD_ERRORS to investigate and fix source data quality issues; (5) this is the recommended approach for "load what you can, investigate failures separately." Option B — ACCEPTINVCHARS handles invalid UTF-8 characters (byte sequences that aren't valid UTF-8), not type conversion errors. 'N/A' is valid text; the problem is casting it to Integer. ACCEPTINVCHARS doesn't help here. Option C — pre-processing with Glue works but adds pipeline complexity, latency, and cost for a problem COPY handles natively. For 12 of 10 million records (0.00012%), the overhead of a separate ETL step is disproportionate. Option D — changing the column to VARCHAR loses type safety, prevents numeric operations, wastes storage (VARCHAR vs INTEGER), and pushes data quality handling downstream. It's a workaround that creates more problems than it solves.
  • UNLOAD with FORMAT AS PARQUET and PARTITION BY provides native partitioned Parquet export: (1) UNLOAD supports Parquet format output directly (added in 2020); (2) PARTITION BY creates Hive-style partitioned directory structure in S3 automatically; (3) the query results are written in parallel across Redshift slices, utilizing cluster compute for the export; (4) partition columns are extracted from the SELECT and used to organize output directories; (5) a single UNLOAD command handles the entire 200 GB export with proper partitioning — no multi-step pipeline needed. The downstream Spark job can read directly from the partitioned Parquet structure. Option B — running 24 separate UNLOAD commands is functional but inefficient: each command re-executes joins and aggregations (or requires a temp table), adds coordination overhead, and doesn't leverage Redshift's built-in PARTITION BY capability. Option C — this is outdated information. UNLOAD has supported FORMAT AS PARQUET since 2020. Unloading to CSV then converting adds an unnecessary intermediate step, doubles S3 storage temporarily, and requires additional compute (Glue job) and time. Option D — CTAS for external tables (Redshift Spectrum) can write to S3, but it creates a table definition in the external schema. UNLOAD is more appropriate for one-time exports or scheduled exports that don't need to be registered as permanent external tables.
  • The "mandatory" flag in manifest entries is specifically designed to prevent silent data loss: (1) by default, manifest entries are optional — if a file doesn't exist, it's silently skipped (which caused the data loss); (2) setting "mandatory": true changes behavior: COPY fails with an error if the file cannot be found; (3) this fail-fast approach prevents partial loads from being mistaken for successful complete loads; (4) the manifest becomes a contract: "these exact files MUST all be loaded, or report failure"; (5) combine with MAXERROR 0 (default) for strict loading — any missing file OR data error causes immediate failure. Option B — prefix-based COPY loads ALL files under a prefix, which can include unexpected files (temp files, old files). Manifests provide explicit control over which files to load. Removing the manifest loses that precision and introduces different risks. Option C — post-COPY validation catches the issue after the fact but doesn't prevent it. The load already committed (without explicit transaction management), requiring rollback. Prevention (mandatory flag) is better than detection. Option D — S3 versioning preserves deleted objects but COPY doesn't reference specific versions by default. It reads the current (live) version. Even with versioning, the COPY would fail to find the current version of a deleted file (it becomes a delete marker).
  • IAM role with resource-level restrictions provides the cleanest access control: (1) the IAM role's policy uses resource-based conditions: "Resource": "arn:aws:s3:::production-data/*" for GetObject and "arn:aws:s3:::production-data" for ListBucket — limiting access to ONLY that bucket; (2) IAM_ROLE parameter in COPY is the recommended authentication method (over credentials/access keys); (3) Redshift COPY using IAM roles communicates with S3 over HTTPS by default — all data in transit is TLS-encrypted; (4) no additional encryption configuration is needed in the COPY syntax because TLS is the default transport for AWS API calls; (5) the role is attached to the cluster (or chained via ROLE), not embedded in SQL. Option B — embedding credentials in SQL statements (CREDENTIALS parameter) is deprecated for IAM roles. Temporary credentials expire, require rotation management, and are visible in query logs — a security risk. Option C — S3 VPC endpoints with resource policies provide network-level restriction but don't replace IAM authorization. COPY still needs an IAM role or credentials to authenticate. VPC endpoints alone don't satisfy the "only this bucket" requirement at the identity level. Option D — bucket policies based on IP addresses are fragile (Redshift IPs can change) and SSE-S3 is encryption at REST, not in transit. Encryption in transit is handled by the transport protocol (HTTPS/TLS), not storage-side encryption.
  • VACUUM SORT resolves the unsorted region problem from COPY appends: (1) COPY loads data into the UNSORTED region of a table — rows are physically stored at the end of each slice in arrival order; (2) the SORTKEY (order_date) defines logical sort order, but only the SORTED region benefits from zone map-based scan elimination; (3) as the unsorted region grows (6 months of daily appends), an increasing percentage of data cannot benefit from SORTKEY optimization; (4) the query planner switches to Seq Scan when the unsorted region is large because zone maps can't effectively filter unsorted blocks; (5) VACUUM SORT re-sorts the unsorted data and merges it into the sorted region, restoring zone map effectiveness and SORTKEY-based range restriction. Option B — ANALYZE updates table statistics (row counts, value distributions) used by the query planner for join strategies and cost estimation. However, stale statistics cause suboptimal JOIN orders, not loss of SORTKEY scan elimination. The issue here is physical data organization, not statistics. Option C — cluster sizing affects parallel processing capacity but doesn't fix the unsorted region problem. A larger cluster with unsorted data still performs unnecessary full scans. Option D — the question doesn't mention the SORTKEY type. Both compound and interleaved SORTKEYs are affected by unsorted regions from COPY appends. Changing SORTKEY type doesn't address the fundamental issue of unmaintained sort order.
  • Compression + Parquet conversion provides the most dramatic load time reduction after file splitting: (1) compression reduces data volume by 5-10x for typical CSV data (1 TB → 100-200 GB), proportionally reducing network transfer time; (2) Parquet format adds type information, eliminating expensive CSV parsing (string-to-type conversion for every field); (3) Parquet's columnar storage means COPY reads only required columns from each row group, further reducing I/O; (4) ZSTD compression offers the best compression ratio for Redshift COPY; LZO offers faster decompression; (5) combined effect: 5-10x less data transfer + faster parsing + columnar efficiency = achieving 30-minute target from 2-hour baseline. Option B — Concurrency Scaling provides ADDITIONAL transient compute for concurrent queries/loads. However, a single COPY command already utilizes all cluster slices. Running multiple COPYs to the same table creates lock contention and potential consistency issues; it doesn't make a single load faster. Option C — S3 prefixes for request rate partitioning was relevant before 2018 when S3 had per-prefix throttling. Current S3 supports 5,500 GET requests/second per prefix natively; 16-32 files at parallel won't approach this limit. Option D — Enhanced VPC Routing forces Redshift traffic through VPC (for security/compliance), but doesn't increase network bandwidth. In fact, it routes through VPC networking infrastructure which may add slight overhead. S3 within the same region already has high bandwidth without Enhanced VPC Routing.
  • MAXFILESIZE controls the size threshold at which UNLOAD splits output into new files: (1) UNLOAD writes output in parallel from each slice; each slice writes to one or more files; (2) MAXFILESIZE defines when a new file is started (default varies by format; uncompressed text default is 6.2 GB); (3) setting MAXFILESIZE larger means each file grows larger before splitting, producing fewer total files; (4) conversely, PARALLEL OFF forces all output through the leader node into a single sequential file — drastically slower for large tables but produces exactly 1 file (or files split only at MAXFILESIZE); (5) the optimal approach depends on trade-offs: fewer files improve downstream read efficiency but slower UNLOAD execution. For this scenario, MAXFILESIZE 1GB or 2GB reduces files from 200 to a more reasonable count while maintaining parallel UNLOAD speed. Option B — there is no FILECOUNT parameter in the UNLOAD command. You cannot directly specify the exact number of output files. Option C — PARALLEL is a boolean (ON/OFF), not a numeric parameter. PARALLEL ON (default) writes from all slices simultaneously; PARALLEL OFF writes sequentially from the leader. There's no PARALLEL 4 syntax. Option D — S3 doesn't have native file merging capability. S3 Object Lambda transforms objects on read, not at rest. Merging files would require downloading, concatenating, and re-uploading — adding significant time and cost for a problem UNLOAD's MAXFILESIZE solves natively.
  • Cross-account S3 access with IAM roles requires dual permission: (1) the resource policy (S3 bucket policy in Account B) must allow the principal (Account A role's ARN); (2) the identity policy (IAM policy attached to the Account A role) must allow the actions (s3:GetObject, s3:ListBucket) on the resource (Account B bucket ARN); (3) AWS evaluates BOTH policies — the effective permission is the INTERSECTION. If either denies or doesn't explicitly allow, the request is denied; (4) this is different from same-account access where either the identity policy OR resource policy can independently grant access. Cross-account ALWAYS requires both sides. The team verified the bucket policy (Account B side) but likely didn't add the cross-account bucket ARN to the Account A role's IAM policy. Option B — role chaining (assuming a role in Account B) is an alternative approach but not required when using bucket policies. Direct cross-account access via bucket policy + identity policy works without role assumption. Option C — ACL configuration affects object-level permissions but doesn't block bucket-policy-based access. "Bucket owner enforced" actually simplifies cross-account access by eliminating ACL complexity. Option D — using explicit credentials is deprecated, insecure (credentials in SQL logs), and unnecessary when IAM roles are properly configured. IAM_ROLE is the recommended approach.
  • JSONPaths files provide explicit mapping from JSON structure to flat table columns: (1) JSON 'auto' matches ONLY top-level JSON keys to table column names (case-insensitive); (2) nested objects (e.g., {"address": {"city": "Seattle"}}) are NOT automatically flattened — the 'address' key is a JSON object, not a scalar, so it can't map to a VARCHAR column; (3) a JSONPaths file specifies the exact path for each column: {"jsonpaths": ["$['name']", "$['address']['city']", "$['address']['zip']"]}; (4) each path entry corresponds to a target table column in order; (5) this enables loading any level of nesting into a flat table. JSONPaths files are referenced by S3 path in the COPY command. Option B — Redshift column names cannot contain dots. The 'auto' option does not create dot-notation names. It simply cannot map nested objects to non-SUPER columns without explicit path specification. Option C — SUPER columns are one approach for semi-structured data, but the requirement is a flat schema (no SUPER). JSONPaths achieves the flattening without changing the table structure. SUPER is appropriate when you WANT to preserve the nested structure for flexible querying. Option D — there is no "NESTING" parameter in the Redshift COPY command. Automatic nested flattening is not a built-in feature — explicit JSONPaths files are required for this mapping.
