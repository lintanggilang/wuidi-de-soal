Key Points

  • For 95% confidence and ±1% margin of error, the required sample size is approximately n = (1.96² × 0.5 × 0.5) / 0.01² ≈ 9,604 records minimum. However, for a population of 5 billion, a sample of ~1 million records provides extremely robust estimates while scanning only 0.02% of data—reducing Athena costs from $50 to approximately $0.01. Bernoulli sampling provides true random selection. Option B: The most recent partition may not represent historical data quality patterns (seasonality, source changes over time). Option C: 50% sampling saves only half the cost while providing no meaningful statistical improvement over a properly sized small sample. Option D: LIMIT 10000 returns the first rows encountered (not random), introducing selection bias—rows may be ordered by time or source, giving a non-representative sample.
  • Stratified sampling is optimal when the population has known subgroups (strata) with different characteristics. By sampling from each region independently, you guarantee representation of all regions including small ones that simple random sampling might miss. This is critical when quality varies significantly by region—underrepresenting high-error regions would underestimate overall quality issues. Option B: Simple random sampling may underrepresent small regions; if a region has only 0.5% of total data, it might have zero records in a small sample. Option C: Cluster sampling (selecting entire regions) introduces high variance because selected clusters may not represent excluded ones; with quality varying by region, this is risky. Option D: Systematic sampling on chronologically ordered data may miss entire regions if data arrives in geographic batches, and periodic patterns in data could align with the sampling interval.
  • Reservoir sampling is the ideal algorithm for streaming data quality monitoring: it maintains a statistically representative fixed-size sample regardless of stream volume, uses O(1) memory per record decision, and doesn't require knowing the total stream size in advance. A 10,000-record sample per 60-second window provides sufficient statistical power to detect quality degradation while processing overhead is minimal. Option B: Processing every record (100K/second) for quality checks adds significant cost and may introduce backpressure/latency on the stream. Option C: Firehose delivery to S3 adds latency (minimum 60-second buffer) before quality checks can run, and the Firehose → S3 → analysis path may exceed the 60-second detection requirement. Option D: Sampling only the first record per shard is not random; it introduces temporal bias and with typically few shards, provides an extremely small sample.
  • This is a fundamental limitation of sampling: rare events (0.01% = 1 in 10,000 records) require sample sizes large enough to capture them with statistical confidence. If DataBrew samples 20,000 records from 500 GB, it expects only ~2 occurrences of a 0.01% event—too few for reliable detection. Increasing sample size or profiling the full dataset for specific columns addresses this directly. Option B: DataBrew does support sampling for profiling jobs; it doesn't always process 100% of data. Option C: Switching to Spark adds operational complexity when DataBrew's sample size adjustment is sufficient. Option D: Multiple independent runs with small samples don't overcome the fundamental sample size limitation; each run independently misses the rare events.
  • For quality assessment "across all customers," stratified sampling with equal allocation ensures every customer (including the 9,995 smaller ones) has enough records in the sample for meaningful quality evaluation. A simple random sample would have very few records from small customers, making it impossible to assess their data quality. Equal allocation per stratum prevents the dominant customers from drowning out quality issues specific to smaller customers. Option B: A 1% random sample maintains the 80/20 skew—small customers might have 0-1 records in the sample, providing no quality signal for those customers. Option C: Sampling only top customers completely ignores quality issues that may be specific to smaller customers (different data entry processes, different systems). Option D: Systematic sampling ordered by customer_id would give proportionally more records to large customers and doesn't control representation.
  • Proper A/B testing requires: (1) processing the SAME records through both pipelines (paired comparison), (2) statistically powered sample size based on the desired confidence level and detectable difference, and (3) appropriate statistical tests to compare proportions. Power analysis for comparing two proportions with 99% confidence and 0.5% detectable difference requires approximately 150,000 records—far fewer than 100M but sufficient for statistically valid conclusions. Option B: Processing 100M records through both pipelines is wasteful when a sample provides the same statistical conclusion at a fraction of the cost. Option C: Using different records for each pipeline confounds data differences with pipeline differences—you can't tell if quality differences are due to the pipeline or the specific input data. Option D: 1,000 records is far too few for 99% confidence at 0.5% difference detection; the required sample size is ~150K.
  • When there's a known temporal event (system migration) that may have affected quality, the sampling strategy should enable direct comparison between pre and post periods. Stratified sampling by time period, with denser sampling around the migration, allows: (1) measuring baseline quality pre-migration, (2) detecting exactly when degradation began, and (3) comparing current quality against the historical baseline. This provides actionable insights about whether the migration caused quality issues. Option B: Simple random sampling dilutes the signal—if quality degraded 8 months ago, mixing good pre-migration data with potentially bad post-migration data obscures the change point. Option C: Only sampling post-migration prevents establishing a baseline—you can't prove quality degraded without comparing against pre-migration quality. Option D: The most recent month doesn't reveal whether issues are getting better or worse over time since the migration.
  • The confidence interval for a proportion is calculated using: CI = p ± Z × √(p(1-p)/n). With p=0.003, n=500,000, and Z=1.96 (95% confidence): margin = 1.96 × √(0.003 × 0.997 / 500,000) ≈ 1.96 × 0.000245 ≈ 0.00048 or ~0.05%. This narrow interval demonstrates that large samples provide very precise estimates even when the sample fraction is small. Option B: No sample gives an exact population parameter; there's always sampling error, though it's very small here. Option C: The sample fraction (sample/population ratio) is largely irrelevant for confidence intervals when the population is much larger than the sample; sample SIZE matters, not sample fraction. Option D: Confidence interval width is determined by sample size, not sample fraction; 500,000 records provides very high precision regardless of population size.
  • Using a Glue job parameter to control sampling provides a single codebase that works for both environments. The parameter-driven approach is clean, testable, and maintains code consistency between development and production. Spark's DataFrame.sample() is efficient and doesn't require reading all data first (for Parquet/columnar formats with pushdown). Option B: Two separate jobs require maintaining duplicate code, risking drift between development and production logic. Option C: Glue development endpoints (now deprecated in favor of interactive sessions) provide interactive access but don't automatically sample data for quality check validation. Option D: Using a single day's partition isn't truly sampling—it's a time-bounded subset that may not represent the full data characteristics (e.g., different customer mix on different days).
  • At 0.001% prevalence, a 1% sample of 2 billion (20 million records) would expect only ~200 unauthorized events—barely enough for a stable estimate. For security auditing where you need to identify ALL unauthorized access (not just estimate the rate), targeted filtering is superior to sampling. Athena can efficiently filter on IP ranges using predicate pushdown on Parquet/columnar data, effectively finding the needle in the haystack without scanning all bytes. Option B: 20M records would contain ~200 events of interest—while detectable, the confidence interval would be very wide (±30% relative error) for practical security decisions. Option C: Stratified sampling by IP range requires knowing which ranges are suspicious beforehand—but discovering unauthorized ranges IS the goal of the analysis. Option D: TABLESAMPLE doesn't guarantee detection of rare events; it provides statistical probability of inclusion, and even at 10%, some rare events may be missed.
