Skill 1.4.7: Storage volumes in Lambda

EFStmpephemeralLambda

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.4: Apply programming concepts), dengan fokus pada storage volumes in lambda. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS Lambda
Komputasi serverless event-driven; batas timeout 15 menit dan memori hingga 10 GB.
Amazon EFS
File system elastis yang dapat di-mount, termasuk ke Lambda untuk storage bersama.

Poin-Poin Kunci

  • EFS provides a persistent, shared filesystem that Lambda accesses via NFS mount. Unlike /tmp, EFS data persists across invocations and is shared across all concurrent executions. The model is stored once on EFS and accessed directly — no download step on cold starts. After initial cache warming, EFS provides consistent low-latency reads. EFS supports up to petabyte-scale storage, easily handling 3GB models.
  • Lambda ephemeral storage (/tmp) can be configured from 512MB to 10,240MB (10GB). For a 200MB file, increasing /tmp to 1-2GB provides sufficient space for input and output without the overhead of EFS (which requires VPC, ENI, and has per-GB-month storage costs plus data transfer costs). /tmp is included in Lambda pricing with a small additional cost only above 512MB.
  • EFS provides a shared filesystem accessible by multiple Lambda functions simultaneously. Both functions mount the same EFS file system and can read/write to the same directories. This enables direct data sharing without object copies — Function B reads the same file Function A wrote. EFS supports concurrent access and provides file-level locking if needed.
  • EFS requires Lambda to be in a VPC (EFS access points are VPC-only resources). VPC-attached Lambda functions experience additional cold start latency due to ENI creation — historically 10-30+ seconds. While AWS has improved this with Hyperplane (reducing to 1-2 seconds in most cases), insufficient IP addresses in subnets or security group rule complexity can still cause delays. The fix includes ensuring subnets have ample IP space and using Provisioned Concurrency to eliminate cold starts.
  • For transient workloads (download → process → upload), /tmp is ideal because data doesn't need to persist. Configuring /tmp to 3GB (within the 10GB limit) costs approximately $0.000000309 per GB-second above 512MB. For a 3-minute daily run using 2.5GB extra: ~$0.00014/day. EFS would cost $0.30/GB-month for storage PLUS data transfer costs, continuously. Since nothing needs to persist between daily runs, /tmp eliminates EFS's ongoing storage cost and VPC overhead.
  • EFS supports thousands of concurrent NFS connections from Lambda. All 50 invocations access the same filesystem simultaneously without duplicating data. Read-only access points enforce security. Elastic throughput mode automatically scales to match read demand from concurrent Lambdas without pre-provisioning. Weekly updates simply overwrite files on EFS. Total storage cost: ~$1.50/month (5GB × $0.30/GB).
  • EFS access points map Lambda's execution identity to a POSIX user (UID/GID). If the access point specifies UID 1000 but the /output directory is owned by UID 0 (root) with permissions 0755, UID 1000 cannot write. Fix: either configure the access point's CreationInfo to create directories with appropriate permissions (e.g., 0777), or ensure the root directory path's ownership matches the access point's UID/GID.
  • EFS provides a single source of truth accessible by all concurrent Lambda instances. When the refresh Lambda updates files on EFS, all readers immediately see the new data (NFS strong consistency for close-to-open operations). No cache invalidation protocol needed — it's a shared filesystem. All 100+ instances read from the same mount point.
  • EFS removes the /tmp size constraint entirely. The video file is stored on EFS and accessed with standard filesystem operations (seek, read) supporting the random access pattern required for video frame extraction. EFS scales to petabytes with no per-file size limits. Provisioned throughput ensures consistent I/O for large file operations.
  • For a 50MB file that changes monthly, a Lambda Layer is optimal: it's deployed with the function (no download latency on cold start), cached in the execution environment (/opt), requires no VPC or EFS infrastructure, and costs nothing beyond standard Lambda pricing. Layers support up to 250MB unzipped, easily accommodating 50MB. Monthly updates only require publishing a new layer version.

Miskonsepsi & Jebakan Umum

  • Lambda Layers have a 250MB unzipped limit, insufficient for a 3GB model.
  • While /tmp can be configured up to 10GB, the model must still be downloaded from S3 on cold starts (significant latency).
  • Downloading 3GB on every invocation adds 30+ seconds of latency, unacceptable for production.
  • S3 Select only supports limited query operations (SQL-like filtering), not complex transformations.
  • Splitting files adds complexity and requires an orchestration layer before Lambda.
  • EFS requires VPC configuration, adds cold start latency (ENI attachment), and costs more for simple temporary file storage.
  • DynamoDB item size limit is 400KB, and it's not designed for large binary data storage.
  • /tmp is ephemeral and local to a specific container instance. Different Lambda functions (or even different invocations of the same function) use different containers with isolated /tmp directories.
  • Step Functions payload limit is 256KB, far too small for 500MB.
  • Throughput issues would cause I/O errors during file operations, not cold start delays.
  • EFS uses lazy loading; only accessed files are read, not the entire filesystem.
  • EFS replication is transparent to clients and doesn't affect mount time.
  • EFS costs are continuous (storage charged 24/7) even though data is needed only 3 minutes/day.
  • S3 Select supports limited operations and cannot generate PDF reports.
  • Combining both adds unnecessary complexity and cost.
  • 50 concurrent downloads of 5GB each = 250GB of S3 transfer, costing significantly more and adding 30+ seconds of download time to each invocation.
  • Lambda Layers have a 250MB limit, cannot hold 5GB.
  • DynamoDB is not optimized for large binary datasets; 5GB in DynamoDB would be extremely expensive and complex to partition.
  • If security groups blocked NFS traffic, the function would fail to mount entirely (connection timeout), not produce a permission denied error.
  • Lambda fully supports both read AND write operations on EFS mounts.
  • EFS has no predefined storage capacity limit; it scales automatically to petabytes.
  • /tmp is isolated per container; there's no mechanism to "clear all containers" without redeployment, and new containers would still need to populate their cache.
  • SNS can trigger notification but each instance still needs to download 500MB independently, causing thundering herd and S3 bandwidth spikes.
  • Lambda environment variables have a 4KB total limit, far below 500MB.
  • While byte-range requests work for simple reads, video processing often requires seeking to multiple non-contiguous positions rapidly; S3 round-trip latency per seek makes this impractical for frame-by-frame analysis.
  • 10GB is the hard maximum for Lambda /tmp; it cannot be increased via service quotas.
  • Splitting videos breaks temporal continuity needed for multi-frame analysis and scene detection.
  • S3 download on cold start adds 2-5 seconds of latency and requires /tmp cleanup logic.
  • EFS adds VPC requirements, ENI cold start overhead, and ongoing storage/transfer costs — over-engineering for a 50MB static file.
  • DynamoDB adds per-query latency and read capacity costs; loading the entire table for in-memory lookups is faster than individual queries.
