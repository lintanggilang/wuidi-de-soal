Skill 2.4.1: Design schemas (Redshift, DynamoDB)

schemaRedshiftDynamoDBstar

Ringkasan

Skill ini termasuk dalam Domain 2: Data Store Management (Task 2.4: Design data models and schema evolution), dengan fokus pada design schemas (redshift, dynamodb). Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon Redshift
Data warehouse berskala petabyte; mendukung COPY/UNLOAD, materialized view, dan streaming ingestion.
Redshift Streaming Ingestion
Konsumsi langsung dari Kinesis/MSK ke materialized view Redshift, latensi detik, tanpa staging S3.
Amazon DynamoDB
Database NoSQL key-value latensi rendah; skala horizontal, mendukung TTL dan Streams.

Poin-Poin Kunci

  • KEY distribution pada kolom yang paling sering di-join (seperti product_id) memastikan bahwa rows dengan value yang sama berada di node yang sama, menghindari data redistribution saat join. Compound sort key yang dimulai dengan transaction_date memungkinkan zone maps untuk melakukan block-level pruning pada filter tanggal, sangat efektif untuk range queries.
  • Pattern 1 (posts by user sorted by time): PK=user_id, SK=timestamp memungkinkan query dengan ScanIndexForward. Pattern 2 (specific post): bisa menggunakan PK=user_id dan filter pada post_id (atau encode post_id dalam sort key dengan composite key). Pattern 3 (hashtag + engagement): GSI dengan PK=hashtag, SK=engagement_score.
  • Strategi optimal: dimension kecil (< beberapa juta rows) gunakan ALL distribution sehingga seluruh tabel direplikasi di setiap node, menghindari redistribution saat join. Dimension besar (5M+ rows) gunakan KEY distribution pada kolom join ke fact table, karena ALL distribution untuk tabel besar membuang storage dan memperlambat write.
  • Dalam single-table design, one-to-many relationship dimodelkan dengan menempatkan parent dan children items di partition key yang sama. PK=CUSTOMER#123, SK=CUSTOMER#123 untuk record customer, dan PK=CUSTOMER#123, SK=ORDER#456 untuk setiap order. Ini memungkinkan satu Query operation untuk mendapatkan customer beserta semua order-nya.
  • Partitioning harus mengikuti query patterns utama. Karena queries terutama filter by date range dan region, partition by region/year/month/day memungkinkan Athena dan Redshift Spectrum melakukan partition pruning yang efektif.
  • Redshift SUPER data type dirancang untuk semi-structured data (JSON, arrays, nested objects). SUPER menyimpan data dalam format binary yang efisien, mendukung schemaless ingestion (schema-on-read), dan bisa di-query menggunakan PartiQL atau dot notation. Ini ideal ketika schema sering berubah.
  • Compound sort key dengan impression_date sebagai leading column optimal ketika queries selalu filter by date range terlebih dahulu. Zone maps di Redshift menyimpan min/max values per block — leading sort column memungkinkan maximum block skipping. Date range filter mengeliminasi sebagian besar blocks, kemudian campaign_id filter diterapkan pada subset yang tersisa.
  • PK=player_id, SK=item_id mendukung semua access patterns secara optimal: (1) Query PK=player_id mendapatkan semua items, (2) GetItem PK=player_id SK=item_id mendapatkan item spesifik, (3) UpdateItem PK=player_id SK=item_id memperbarui quantity. Dengan 500 items per player, item collection masih di bawah 10GB partition limit.
  • Star schema dengan denormalized dimensions adalah best practice untuk Amazon Redshift. Redshift dioptimalkan untuk join patterns sederhana (fact-to-dimension) dan columnar storage membuat denormalization murah dari segi storage. Denormalized dimension mengurangi jumlah joins, meningkatkan query performance.
  • Apache Parquet dengan schema-on-write adalah best practice untuk data lake analytics. Parquet menyediakan columnar storage yang efficient, compression yang baik, dan predicate pushdown. Registrasi di Glue Data Catalog memungkinkan discovery oleh semua query engines (Athena, Spectrum, EMR). Partitioning by date memungkinkan partition pruning.

Miskonsepsi & Jebakan Umum

  • Akan menyebabkan data skew jika tanggal tidak merata.
  • Tidak mungkin untuk tabel 5 miliar rows — ALL hanya cocok untuk dimension tables kecil.
  • Interleaved sort key memiliki overhead maintenance yang tinggi untuk tabel besar.
  • Tidak mendukung pattern 1 efisien dari base table.
  • Menggunakan hashtag sebagai PK utama yang menyebabkan hot partition untuk hashtag populer.
  • Menggunakan post_id sebagai sort key yang tidak mendukung sorting by timestamp secara native.
  • Tidak optimal untuk dimension kecil yang lebih baik direplikasi penuh.
  • Akan memerlukan data redistribution saat setiap join.
  • Membuang storage untuk dimension 5M rows yang direplikasi di setiap node.
  • Memisahkan orders ke partition berbeda sehingga tidak bisa query customer + orders dalam satu operasi.
  • Tidak memanfaatkan item collection.
  • Melanggar best practice karena Set memiliki batas 400KB per item dan tidak scalable.
  • Memaksa full scan 100M records/hari yang sangat lambat untuk tabel besar.
  • Terlalu banyak partisi (365×24 = 8.760/tahun) dan tidak memanfaatkan region filter.
  • Menghasilkan partition explosion: 5×10×365×24 = 438.000 partisi/tahun yang terlalu banyak dan menyebabkan overhead metadata.
  • Untuk binary data, bukan structured JSON navigation.
  • Tidak flexible ketika fields berubah.
  • Bekerja tapi less efficient — tidak ada columnar optimization dan parsing ulang setiap query.
  • Menghindari masalah tapi menambah storage cost.
  • Memiliki overhead VACUUM yang tinggi untuk tabel 20B rows dan tidak seefisien compound ketika ada satu dominant filter pattern.
  • Menempatkan campaign_id pertama — kurang efisien karena range scan pada date lebih selective.
  • Tidak efisien untuk "get all items by player".
  • Tidak diperlukan — player_id sudah memberikan distribusi yang baik natural.
  • Memiliki batas 400KB per item dan setiap update memerlukan read-modify-write seluruh map.
  • Menambah joins yang mahal di Redshift — setiap join memerlukan data redistribution.
  • Sangat tidak cocok untuk analytics workload — terlalu banyak joins.
  • Menambah kompleksitas maintenance tanpa benefit signifikan — satu star schema melayani keduanya dengan baik.
  • Tidak mendukung complex types, tidak columnar, dan compression kurang baik.
  • Tidak bisa di-discover oleh Lake Formation dan tools lainnya.
  • Sangat tidak efisien untuk analytics — tidak columnar, tidak compressed optimal, dan schema inference bisa bermasalah.
