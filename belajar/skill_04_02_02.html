Key Services & Concepts

AWS Secrets Manager
Penyimpanan kredensial secure with rotasi automatic.
AWS Systems Manager Parameter Store
Stores configuration & secret (SecureString) with integration IAM.

Key Points

  • AWS Secrets Manager is satu-satunya service that provides BUILT-IN automatic rotation for RDS/Aurora credentials. Cara kerjanya: (1) Secret is stored in Secrets Manager with rotation enabled, (2) Rotation Lambda function (provided by AWS for RDS) automatically: creates new password, updates the database, updates the secret value, (3) Uses staging labels (AWSCURRENT, AWSPENDING) for zero-downtime rotation — old credentials still valid during transition, (4) Glue job calls GetSecretValue saat runtime — always mendapat credential terbaru.
  • Cost-optimized approach uses each service appropriate requirements: SSM Parameter Store Standard tier: FREE (up to 10,000 parameters), supports String/StringList types, sufficient for non-sensitive config values. Not ada per-API-call charges for standard parameters. Cocok for: bucket names, endpoint URLs, feature flags. AWS Secrets Manager: $0.40/secret/month + $0.05/10,000 API calls. Provides: encryption at rest (KMS), automatic rotation, versioning, cross-account access. Diperlukan for: sensitive credentials that requires rotation.
  • Common issue with credential rotation: Long-running jobs (Glue ETL can run hours) that retrieve credentials at startup and cache them. If rotation happens DURING job execution: (1) Job started with old password at T=0, (2) Rotation occurs at T=30min — database password changes, (3) Job's cached credential becomes invalid, (4) Next database connection attempt fails. Solutions: (1) Implement credential refresh logic — periodically call GetSecretValue, (2) Use connection pooling with credential refresh, (3) For Glue specifically — use Glue Connections which can be configured to retrieve secrets, (4) Schedule rotations during maintenance windows when no long-running jobs are active.
  • Cross-account secret access requires permissions in KEDUA sisi: Security Account (resource owner) — Secret resource policy: {"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::111111111111:role/AnalyticsRole"}, "Action": "secretsmanager:GetSecretValue", "Resource": "*"}. KMS key policy: HARUS grant kms:Decrypt to Analytics role because secret terenkripsi KMS. Without this, GetSecretValue will fails with AccessDenied although secret policy allows. Analytics Account (consumer): IAM policy on role: Allow secretsmanager:GetSecretValue on ARN secret "arn:aws:secretsmanager:region:999999999999:secret:redshift-creds-*". BOTH permissions (secret policy + KMS policy + IAM policy) is required.
  • Best migration approach leverages native integrations for minimize code changes: Lambda: AWS Parameters and Secrets Lambda Extension — retrieves secrets and makes them available as local HTTP endpoint or environment variables. Minimal code change: just reference env var instead of hardcoded value. Extension handles caching and refresh. Glue: Glue Connections can store connection details backed by Secrets Manager. Glue job references Connection name — framework handles credential retrieval. Step Functions: Native AWS SDK integration action (aws-sdk:secretsmanager:getSecretValue) — no Lambda needed, direct retrieval in state machine. Each service has purpose-built integration patterns that minimize changes.
  • Secrets Manager with full configuration memenuhi all requirements: (1) Customer-managed KMS key: Saat create secret, specify KmsKeyId with CMK ARN. Gives full control over key rotation, key policy, and audit. (2) Resource-based policy: {"Effect": "Allow", "Principal": {"AWS": ["arn:aws:iam::account:role/LambdaFunction1Role", "arn:aws:iam::account:role/LambdaFunction2Role"]}, "Action": "secretsmanager:GetSecretValue", "Resource": "*"}. Ini RESTRICTS access only to specified Lambda roles. (3) CloudTrail integration: Secrets Manager API calls (GetSecretValue, DescribeSecret, etc.) automatic logged in CloudTrail — each access attempt direcord with: who, when, source IP, success/failure.
  • Rotation strategies in Secrets Manager: Single User Strategy: Uses ONE database user. During rotation: (1) Change password in database, (2) Update secret. Brief window exists where password already changes in DB but applications still punya old cached value → connection failures. Alternating Users Strategy: Uses TWO database users (e.g., app_user and app_user_clone). Rotation cycle: (1) AWSCURRENT points to user_A (currently active), (2) Rotation creates/updates user_B with new password, (3) Tests user_B connectivity, (4) Swaps labels: user_B becomes AWSCURRENT, user_A becomes AWSPREVIOUS. At NO point are both users simultaneously invalid — eliminates connection failures. Applications using GetSecretValue always get working credentials because AWSCURRENT is always valid.
  • VPC Interface Endpoint for Secrets Manager enables EMR nodes accesses Secrets Manager API through AWS private network TANPA internet access. Configuration: (1) Create Interface Endpoint for service "com.amazonaws.{region}.secretsmanager", (2) Select subnets where EMR nodes berada, (3) Attach security group that allows inbound HTTPS (443) from EMR nodes' security group, (4) Enable Private DNS so that standard Secrets Manager API endpoint (secretsmanager.region.amazonaws.com) resolve to private endpoint IP. EMR code calls Secrets Manager SDK such as biasa — DNS resolution automatic mengarahkan to private endpoint.
  • Secrets Manager versioning uses staging labels for manage version lifecycle: AWSCURRENT: The version returned by default when GetSecretValue is called. This is the "active" version. AWSPREVIOUS: The version that was AWSCURRENT before the last rotation/update. AWSPENDING: Used during rotation process (temporary state). Rollback process: (1) Identify issue with current credential, (2) Call UpdateSecretVersionStage to move AWSCURRENT label from problematic version to AWSPREVIOUS version, (3) Immediately, all subsequent GetSecretValue calls return the rolled-back version. Important notes: Ini only rollback in Secrets Manager — if database password already changes, needs also rollback database password to match. For rotation-related rollbacks, both database and secret must be consistent.
  • Cost optimization strategy: SSM Parameter Store Standard tier: $0/month for storage (up to 10,000 parameters, 4KB each). Supports String, StringList, SecureString (encrypted with KMS). Perfect for: bucket names, endpoints, feature flags, non-rotating configuration. SecureString parameters still encrypted at rest with KMS. Secrets Manager: $0.40/secret/month = $8/month for 20 credentials. Worth the cost for: automatic rotation, cross-account sharing, staging labels, built-in RDS/Aurora rotation Lambdas. Savings: $208 → $8/month = $200/month saved ($2,400/year).

Common Misconceptions & Pitfalls

  • TIDAK has native rotation feature — must build itself. Advanced tier PS can trigger rotation but without built-in RDS rotation Lambda.
  • Requires manual intervention and credentials exposed in configuration.
  • Requires custom Lambda and not has built-in database password update mechanism.
  • Over-engineering for credential storage — no built-in rotation, additional DynamoDB charges.
  • Insecure — credentials in plaintext.
  • Works but unnecessarily expensive — $040/month × 3 secrets for values that not requires rotation.
  • If KMS key expired, rotation itself would have failed.
  • Secrets Manager uses staging labels (AWSCURRENT/AWSPREVIOUS) and old credential (AWSPREVIOUS) usually still valid briefly, but database already has new password setelah rotation.
  • If networking was wrong, rotation status would show failed.
  • Manual sync not scalable and credential can out of sync.
  • Secrets Manager cross-region replication exists but this cross-ACCOUNT not cross-region.
  • Credentials still static until next deployment, no auto-rotation.
  • AWS Config doesn't modify source code.
  • Expensive and risky full rewrite.
  • Possible but lacks purpose-built secret management features.
  • ACM is for SSL/TLS certificates, not API keys.
  • Supports SecureString but not supports resource-based policies for fine-grained access restriction.
  • Doesn't address the root cause.
  • Is valid alternative but changes the entire authentication mechanism, not only rotation strategy.
  • Bekerja but unnecessary exposure — traffic exits to internet lalu returns to AWS, and NAT Gateway expensive.
  • Reduces security posture significantly.
  • Credentials stored in plaintext and not mendapat benefit rotation/auditing.
  • Salah — SM keeps multiple versions.
  • Loses version history and audit trail.
  • Not needed, self-service available.
  • Has 64KB limit, makes granular access control impossible (all-or-nothing), and breaks rotation (can't rotate individual credentials).
  • Moves DB credentials to Parameter Store — loses rotation capability (critical for security compliance).
  • Credentials in plaintext, no encryption, no rotation, no audit.
