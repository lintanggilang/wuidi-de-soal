Domain 4: Security & Governance — Task 4.2: Apply authorization mechanisms

Skill 4.2.2: Store credentials securely

SecretsManagerParameterStore

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.2: Apply authorization mechanisms), dengan fokus pada store credentials securely. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS Secrets Manager
Penyimpanan kredensial aman dengan rotasi otomatis.
AWS Systems Manager Parameter Store
Menyimpan konfigurasi & secret (SecureString) dengan integrasi IAM.

Poin-Poin Kunci

  • AWS Secrets Manager adalah satu-satunya service yang menyediakan BUILT-IN automatic rotation untuk RDS/Aurora credentials. Cara kerjanya: (1) Secret disimpan di Secrets Manager dengan rotation enabled, (2) Rotation Lambda function (provided by AWS untuk RDS) secara otomatis: creates new password, updates the database, updates the secret value, (3) Menggunakan staging labels (AWSCURRENT, AWSPENDING) untuk zero-downtime rotation — old credentials tetap valid selama transition, (4) Glue job memanggil GetSecretValue saat runtime — selalu mendapat credential terbaru.
  • Cost-optimized approach menggunakan masing-masing service sesuai kebutuhan: SSM Parameter Store Standard tier: FREE (up to 10,000 parameters), supports String/StringList types, sufficient untuk non-sensitive config values. Tidak ada per-API-call charges untuk standard parameters. Cocok untuk: bucket names, endpoint URLs, feature flags. AWS Secrets Manager: $0.40/secret/month + $0.05/10,000 API calls. Menyediakan: encryption at rest (KMS), automatic rotation, versioning, cross-account access. Diperlukan untuk: sensitive credentials yang memerlukan rotation.
  • Common issue dengan credential rotation: Long-running jobs (Glue ETL can run hours) yang retrieve credentials at startup dan cache them. Jika rotation happens DURING job execution: (1) Job started with old password at T=0, (2) Rotation occurs at T=30min — database password changes, (3) Job's cached credential becomes invalid, (4) Next database connection attempt fails. Solutions: (1) Implement credential refresh logic — periodically call GetSecretValue, (2) Use connection pooling with credential refresh, (3) For Glue specifically — use Glue Connections which can be configured to retrieve secrets, (4) Schedule rotations during maintenance windows when no long-running jobs are active.
  • Cross-account secret access memerlukan permissions di KEDUA sisi: Security Account (resource owner) — Secret resource policy: {"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::111111111111:role/AnalyticsRole"}, "Action": "secretsmanager:GetSecretValue", "Resource": "*"}. KMS key policy: HARUS grant kms:Decrypt ke Analytics role karena secret terenkripsi KMS. Tanpa ini, GetSecretValue akan gagal dengan AccessDenied meskipun secret policy mengizinkan. Analytics Account (consumer): IAM policy pada role: Allow secretsmanager:GetSecretValue pada ARN secret "arn:aws:secretsmanager:region:999999999999:secret:redshift-creds-*". BOTH permissions (secret policy + KMS policy + IAM policy) diperlukan.
  • Best migration approach leverages native integrations untuk minimize code changes: Lambda: AWS Parameters and Secrets Lambda Extension — retrieves secrets dan makes them available as local HTTP endpoint or environment variables. Minimal code change: just reference env var instead of hardcoded value. Extension handles caching dan refresh. Glue: Glue Connections can store connection details backed by Secrets Manager. Glue job references Connection name — framework handles credential retrieval. Step Functions: Native AWS SDK integration action (aws-sdk:secretsmanager:getSecretValue) — no Lambda needed, direct retrieval in state machine. Each service has purpose-built integration patterns that minimize changes.
  • Secrets Manager dengan full configuration memenuhi semua requirements: (1) Customer-managed KMS key: Saat create secret, specify KmsKeyId dengan CMK ARN. Gives full control over key rotation, key policy, dan audit. (2) Resource-based policy: {"Effect": "Allow", "Principal": {"AWS": ["arn:aws:iam::account:role/LambdaFunction1Role", "arn:aws:iam::account:role/LambdaFunction2Role"]}, "Action": "secretsmanager:GetSecretValue", "Resource": "*"}. Ini RESTRICTS access hanya ke specified Lambda roles. (3) CloudTrail integration: Secrets Manager API calls (GetSecretValue, DescribeSecret, etc.) otomatis logged di CloudTrail — setiap access attempt direcord dengan: who, when, source IP, success/failure.
  • Rotation strategies di Secrets Manager: Single User Strategy: Uses ONE database user. During rotation: (1) Change password in database, (2) Update secret. Brief window exists dimana password sudah berubah di DB tapi applications masih punya old cached value → connection failures. Alternating Users Strategy: Uses TWO database users (e.g., app_user dan app_user_clone). Rotation cycle: (1) AWSCURRENT points to user_A (currently active), (2) Rotation creates/updates user_B with new password, (3) Tests user_B connectivity, (4) Swaps labels: user_B becomes AWSCURRENT, user_A becomes AWSPREVIOUS. At NO point are both users simultaneously invalid — eliminates connection failures. Applications using GetSecretValue always get working credentials because AWSCURRENT is always valid.
  • VPC Interface Endpoint untuk Secrets Manager memungkinkan EMR nodes mengakses Secrets Manager API melalui AWS private network TANPA internet access. Configuration: (1) Create Interface Endpoint for service "com.amazonaws.{region}.secretsmanager", (2) Select subnets dimana EMR nodes berada, (3) Attach security group yang allows inbound HTTPS (443) dari EMR nodes' security group, (4) Enable Private DNS agar standard Secrets Manager API endpoint (secretsmanager.region.amazonaws.com) resolve ke private endpoint IP. EMR code memanggil Secrets Manager SDK seperti biasa — DNS resolution otomatis mengarahkan ke private endpoint.
  • Secrets Manager versioning menggunakan staging labels untuk manage version lifecycle: AWSCURRENT: The version returned by default when GetSecretValue is called. This is the "active" version. AWSPREVIOUS: The version that was AWSCURRENT before the last rotation/update. AWSPENDING: Used during rotation process (temporary state). Rollback process: (1) Identify issue dengan current credential, (2) Call UpdateSecretVersionStage to move AWSCURRENT label from problematic version to AWSPREVIOUS version, (3) Immediately, all subsequent GetSecretValue calls return the rolled-back version. Important notes: Ini hanya rollback di Secrets Manager — jika database password sudah berubah, perlu juga rollback database password ke match. Untuk rotation-related rollbacks, both database and secret must be consistent.
  • Cost optimization strategy: SSM Parameter Store Standard tier: $0/month for storage (up to 10,000 parameters, 4KB each). Supports String, StringList, SecureString (encrypted with KMS). Perfect for: bucket names, endpoints, feature flags, non-rotating configuration. SecureString parameters still encrypted at rest with KMS. Secrets Manager: $0.40/secret/month = $8/month for 20 credentials. Worth the cost for: automatic rotation, cross-account sharing, staging labels, built-in RDS/Aurora rotation Lambdas. Savings: $208 → $8/month = $200/month saved ($2,400/year).

Miskonsepsi & Jebakan Umum

  • TIDAK memiliki native rotation feature — harus build sendiri. Advanced tier PS bisa trigger rotation tapi tanpa built-in RDS rotation Lambda.
  • Requires manual intervention dan credentials exposed in configuration.
  • Memerlukan custom Lambda dan tidak memiliki built-in database password update mechanism.
  • Over-engineering untuk credential storage — no built-in rotation, additional DynamoDB charges.
  • Insecure — credentials in plaintext.
  • Works tapi unnecessarily expensive — $040/month × 3 secrets untuk values yang tidak memerlukan rotation.
  • Jika KMS key expired, rotation itself would have failed.
  • Secrets Manager uses staging labels (AWSCURRENT/AWSPREVIOUS) dan old credential (AWSPREVIOUS) biasanya tetap valid briefly, tapi database already has new password setelah rotation.
  • Jika networking was wrong, rotation status would show failed.
  • Manual sync tidak scalable dan credential bisa out of sync.
  • Secrets Manager cross-region replication exists tapi ini cross-ACCOUNT bukan cross-region.
  • Credentials still static until next deployment, no auto-rotation.
  • AWS Config doesn't modify source code.
  • Expensive dan risky full rewrite.
  • Possible tapi lacks purpose-built secret management features.
  • ACM is for SSL/TLS certificates, not API keys.
  • Supports SecureString tapi tidak mendukung resource-based policies untuk fine-grained access restriction.
  • Doesn't address the root cause.
  • Is valid alternative tapi changes the entire authentication mechanism, tidak hanya rotation strategy.
  • Bekerja tapi unnecessary exposure — traffic keluar ke internet lalu kembali ke AWS, dan NAT Gateway mahal.
  • Reduces security posture significantly.
  • Credentials stored in plaintext dan tidak mendapat benefit rotation/auditing.
  • Salah — SM keeps multiple versions.
  • Loses version history dan audit trail.
  • Not needed, self-service available.
  • Has 64KB limit, makes granular access control impossible (all-or-nothing), dan breaks rotation (can't rotate individual credentials).
  • Moves DB credentials ke Parameter Store — loses rotation capability (critical for security compliance).
  • Credentials in plaintext, no encryption, no rotation, no audit.
