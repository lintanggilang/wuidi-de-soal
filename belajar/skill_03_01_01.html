Skill 3.1.1: Orchestrate data pipelines

Summary

Skill this including in Domain 3: Operations & Support (Task 3.1: Automate data processing), with fokus on orchestrate data pipelines. Materi berikut merangkum service AWS that relevan along with concept important that needs kamu kuasai for topik this.

Key Services & Concepts

Amazon MWAA
Managed Workflows for Apache Airflow; orkestrasi pipeline based on DAG.
AWS Step Functions
Orkestrasi flow kerja serverless (state machine) with retry, parallel, and error handling.

Key Points

  • Amazon MWAA is choice best because: (1) team already berpengalaman with Apache Airflow, (2) Airflow has sensors that unggul for waits external events, (3) supports complex dependency management with DAG, and (4) has rich operator ecosystem for Glue, Redshift, and service AWS others.
  • AWS Step Functions Standard Workflow is choice most cost-effective for pipeline that rarely runs (10-20/days) because pricing per state transition (not per hours such as MWAA). Standard workflow suitable because steps can until 5 minutes and requires exactly-once execution semantics.
  • Run a Job (.sync) integration pattern is way most simple and efficient for waits long-running jobs. By adds .sync suffix to resource ARN, Step Functions automatically polls Glue job status and melanjutkan to step berikutnya after job complete, fails, or timeout.
  • Step Functions Map state (Distributed mode for large-scale) designed correct for parallel processing of multiple items with logic that same but parameter different. MaxConcurrency parameter enables kontrol how many feeds is processed simultaneously, membantu manage resource limits downstream.
  • Airflow has built-in retry mechanism with parameter retries, retry_delay, and retry_exponential_backoff. Setting retries=5 with exponential backoff provides 5 attempts with increasing delay between retries, that ideal for intermittent API failures. This is way that proper and idiomatic in Airflow.
  • Pattern fan-in uses dummy/empty task as join point with trigger_rule='all_success' ensures that all 3 extraction tasks must succeeds before pipeline melanjutkan to Glue job. This is pattern standard Airflow for synchronization.
  • AWS Step Functions with cross-account IAM role assumption is approach most secure. Step Functions execution role in central account assumes roles in target accounts uses STS AssumeRole, that provides temporary credentials without stores long-lived secrets. Centralized state machine provides single-pane monitoring.
  • Step Functions Retry field with ErrorEquals enables retry selektif based on type error specific. Konfigurasi: Retry with ErrorEquals: ["Glue.ConcurrentRunsExceededException"], IntervalSeconds: 600, MaxAttempts: 3. Catch field then captures all error other ("States.ALL") and routes to notification step. This is built-in pattern that bersih and deklaratif.
  • Satu DAG with schedule harian and trigger external via EventBridge + MWAA REST API is pattern that clean. max_active_runs=1 ensures there is no concurrent execution. EventBridge rule on S3 PutObject event calls MWAA CLI/API for trigger DAG run in outside schedule normal. catchup=False prevents backfill runs.
  • Parallel state in Step Functions runs multiple branches in a concurrent. Because Glue (15 min) and Redshift load (5 min) both only depends on output EMR, mereka can runs simultaneously. Total time: EMR 30 min + max(Glue 15 min, Redshift 5 min) = 45 min → sebenarnya 35 min (30+15 with Redshift complete more awal in in parallel).

Common Misconceptions & Pitfalls

  • Terbatas on Glue services only.
  • Too simple for pipeline kompleks with dependencies.
  • Can performs this but less intuitif for complex dependencies and external event waiting dibandingkan Airflow sensors.
  • Limited 5 minutes total execution time, that too ketat if multiple steps each almost 5 minutes.
  • Has operational overhead high.
  • Has minimum cost ~$350/months for environment that running 24/7, very expensive for 10-20 executions/days.
  • Requires Glue job for send callback — Glue not natively support this without custom code.
  • Requires workflow separate and more complex.
  • Requires extra states and logic that does not need.
  • More kompleks for in-manage and monitor, as well as requires logic additional for aggregasi results.
  • For routing not parallel processing.
  • Will very slow — 200 feeds in a sequential not will meet 2-hour SLA.
  • Very fragile and not scalable.
  • Too aggressive — me-restart entire DAG only because one task fails.
  • Not utilizes Airflow's built-in retry/logging/monitoring.
  • Only for visual grouping, not automatic creates join-point dependency.
  • Digunakan for cross-DAG dependencies, not intra-DAG synchronization.
  • Already deprecated in Airflow modern and adds complexity.
  • Is for event routing not full workflow orchestration with sequencing.
  • Is anti-pattern security.
  • Less secure because uses long-lived credentials.
  • Requires logic additional that does not need.
  • Not solves problem error handling.
  • Adds operational overhead and kehilangan Step Functions' native error handling visibility.
  • Not prevents concurrent execution between second DAG.
  • Very wasteful and not event-driven.
  • Can works but adds extra Lambda layer that does not need.
  • Not creates jobs runs faster — only different pricing model.
  • For processing multiple items with logic same, not two task different.
  • Kehilangan centralized monitoring and error handling.
