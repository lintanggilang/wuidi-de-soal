Skill 2.2.5: Source/target connections

GlueconnectionsJDBCKafka

Ringkasan

Skill ini termasuk dalam Domain 2: Data Store Management (Task 2.2: Understand data cataloging systems), dengan fokus pada source/target connections. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon MSK
Apache Kafka terkelola; cocok untuk streaming throughput tinggi dengan ekosistem Kafka.
AWS Glue
ETL serverless berbasis Spark + Data Catalog; ideal untuk transformasi dan katalogisasi data.

Poin-Poin Kunci

  • A Glue JDBC connection for on-premises databases requires: (1) Connection type: JDBC with the full JDBC URL for Oracle; (2) VPC configuration: the VPC with VPN connectivity to on-premises, a subnet in the correct AZ, and a security group; (3) Security group: must allow outbound traffic to the Oracle port (1521) AND have a self-referencing inbound rule (Glue ENIs need to communicate with each other within the VPC); (4) Credentials: username and password stored in the connection properties (or referenced from Secrets Manager); (5) the crawler references this connection to obtain network path and credentials. Option B — Network-type connections provide only VPC networking (no JDBC URL or credentials); the crawler still needs a JDBC connection type that encapsulates the URL, credentials, AND network configuration together. You cannot split them. Option C — Direct Connect provides network connectivity but Glue crawlers still require a Glue connection object to know which VPC/subnet to place their ENIs in; without a connection, Glue has no way to route traffic into the VPC. Option D — RDS Proxy only works with Amazon RDS and Aurora databases; it cannot proxy connections to on-premises Oracle instances.
  • The most likely cause is that the RDS security group doesn't allow inbound traffic from the Glue connection's security group: (1) when Glue tests a connection, it creates ENIs in the specified subnet with the specified security group; (2) these ENIs attempt to connect to the RDS MySQL endpoint on port 3306; (3) the RDS instance's security group must have an inbound rule allowing port 3306 from the Glue connection's security group (or its CIDR); (4) the team confirmed "EC2 instances in the same subnet can connect" — those EC2 instances likely have a different security group that IS allowed in the RDS inbound rules; (5) Glue's ENIs use the Glue connection's security group, which hasn't been added to the RDS inbound rules. Option A — the self-referencing rule is important for Glue ETL jobs (which have multiple ENIs communicating), but the connection TEST is a simpler operation. A missing self-referencing rule causes issues during job execution more than test connection. The "timed out" error more specifically indicates the target (RDS) isn't reachable. Option B — RDS in a private subnet uses private IP; NAT Gateway is for outbound internet access, not for VPC-internal communication. Glue ENIs in the same VPC communicate via private IPs. Option C — missing ec2:CreateNetworkInterface would cause an explicit IAM error ("not authorized to perform ec2:CreateNetworkInterface"), not a timeout.
  • Glue natively supports MONGODB as a connection type: (1) the MONGODB connection type is a first-class Glue connection (not a generic JDBC wrapper); (2) it uses the MongoDB Wire Protocol directly, connecting to MongoDB's native port 27017; (3) it understands BSON document structures, enabling schema inference from MongoDB's flexible document model; (4) VPC/subnet/security group configuration is identical to JDBC connections — Glue creates ENIs in the specified subnet; (5) a Glue crawler using this connection can catalog MongoDB collections as tables, inferring column schemas from document fields. Supported MongoDB sources include self-managed MongoDB, MongoDB Atlas, and Amazon DocumentDB (MongoDB-compatible). Option B — while third-party MongoDB JDBC drivers exist, using them adds complexity (driver version management, JAR hosting) and doesn't leverage Glue's native BSON understanding. The native MONGODB connection type provides better schema inference for nested documents. Option C — Network-type connections only provide VPC access; they don't include connection URL or authentication details. The crawler cannot use a Network connection alone to connect to MongoDB — it needs the full connection specification. Option D — Marketplace connectors are for data sources that Glue doesn't natively support. Since MongoDB IS natively supported, a marketplace connector is unnecessary and adds cost.
  • Secrets Manager integration with Glue connections provides managed credential rotation: (1) Glue connections support referencing a Secrets Manager secret instead of static credentials; (2) Secrets Manager's built-in rotation uses Lambda functions to rotate credentials on a schedule (90 days in this case); (3) the rotation Lambda updates both the database password AND the secret value atomically; (4) Glue retrieves credentials from the secret at connection time — always getting the current valid password; (5) no Glue connection updates needed when rotation occurs. This is the AWS-recommended pattern for credential management with Glue. Option B — Parameter Store supports SecureString parameters but does NOT have built-in automatic rotation like Secrets Manager. Rotation would still require custom automation. Additionally, Glue connection properties don't natively support Parameter Store references in the same way they support Secrets Manager ARNs. Option C — custom Lambda rotation via EventBridge works but is a custom solution requiring maintenance. It has a race condition risk: if the Lambda updates some connections but fails partway through, some jobs use old credentials while others use new ones. Secrets Manager rotation is atomic. Option D — IAM database authentication is supported for RDS MySQL/PostgreSQL but NOT for all databases (not Oracle, SQL Server, or non-RDS databases). Also, Glue's IAM auth support for JDBC connections has limitations and isn't universally supported across all Glue connection types.
  • Glue natively supports KAFKA as a connection type for streaming source cataloging: (1) the KAFKA connection type understands the Kafka protocol and can connect to MSK or self-managed Kafka clusters; (2) it supports MSK authentication methods including IAM, SASL/SCRAM, and mTLS; (3) VPC configuration allows Glue to place ENIs in the same VPC as MSK for network connectivity; (4) a Glue crawler using this connection samples messages from Kafka topics to infer schemas; (5) inferred schemas (from JSON, Avro, or other formats) become tables in the Data Catalog that downstream Glue Streaming ETL jobs can reference. Option B — Kafka does NOT use JDBC protocol. It uses its own binary protocol over TCP. There is no standard "Kafka JDBC connector URL" — Glue has a dedicated KAFKA connection type specifically because JDBC doesn't apply to message brokers. Option C — MSK Connect deploys Kafka Connect connectors for data movement (source/sink), not for schema cataloging. While you could theoretically build a custom connector that registers schemas, this is not a standard pattern and adds complexity. Option D — Glue Schema Registry stores schemas for serialization/deserialization during streaming processing, but it's a separate system from the Glue Data Catalog. Schema Registry doesn't automatically create Data Catalog tables — they serve different purposes (serialization governance vs. metadata catalog).
  • Glue jobs operate within a single VPC networking context: (1) all ENIs for a Glue job are placed in the same VPC/subnet; (2) when a job has multiple connections, they must share the same VPC/subnet configuration; (3) the solution is to place the job's ENIs in one VPC and use network routing (VPC peering routes) to reach resources in the other VPC; (4) VPC-A's subnet route table must have a route for VPC-B's CIDR pointing to the peering connection; (5) both connections should reference VPC-A, subnet-A, and SG-A; the Redshift connection in VPC-B is reachable via the peering route. Security groups in VPC-B must allow inbound traffic from VPC-A's CIDR. Option B — Glue does NOT support multiple VPCs per job regardless of the networking mechanism (peering, Transit Gateway, etc.). The fundamental constraint is that job ENIs exist in one subnet. Transit Gateway provides routing but doesn't change Glue's single-VPC job execution model. Option C — more DPUs provide additional compute capacity but all ENIs are still placed in the same subnet; you cannot distribute ENIs across VPCs by adding DPUs. Option D — there is no concept of a "shared subnet" spanning VPCs. Each subnet belongs to exactly one VPC. A Network connection also specifies a single VPC/subnet combination.
  • Amazon AppFlow is the purpose-built service for integrating SaaS data sources with AWS: (1) AppFlow supports hundreds of SaaS connectors (Salesforce, ServiceNow, Slack, etc.) and can be configured to extract data on schedule or event; (2) it deposits data in S3 in structured formats (JSON, Parquet, CSV); (3) a Glue crawler on the AppFlow S3 output automatically discovers and catalogs the schema; (4) this creates a complete catalog entry usable by Athena, Redshift Spectrum, and Glue ETL; (5) it requires no custom code — configuration only. For a SaaS API that AppFlow supports, this is the simplest, most maintainable solution. Option A — custom connectors are powerful but require significant development effort (Java/Scala development, Spark DataSource API implementation, testing, packaging). This is appropriate when AppFlow doesn't support the specific SaaS application, but the question mentions a generic "SaaS application" — AppFlow likely supports it. Option C — Lambda + manual CreateTable works but requires maintaining custom code for API pagination, error handling, schema evolution detection, and catalog updates. It's more operational burden than AppFlow. Option D — Network-type connections provide VPC routing only and don't support HTTP/REST protocols. Glue crawlers cannot crawl REST APIs through Network connections — they're designed for TCP connectivity to databases.
  • The Glue connection test and ETL jobs may use different subnets within the specified VPC: (1) a Glue connection can be associated with a VPC and availability zone; (2) the test connection feature places an ENI in a specific subnet based on availability zone selection; (3) if multiple subnets are available and the test selects one with improper routing (missing route to the RDS subnet, NACL blocking traffic, or the RDS is in a different AZ without cross-AZ routing configured), the test fails; (4) ETL jobs may get placed in a different subnet that does have proper routing; (5) this commonly happens when the connection specifies an AZ different from where the RDS instance resides. The fix is ensuring all subnets in the connection's availability zone have security group rules and route table entries allowing access to the RDS endpoint. Option B — Glue does not apply additional default security groups to test ENIs beyond what's configured in the connection. The specified security group is the only one applied. Option C — both the test and ETL jobs use the same IAM role specified in the crawler or job configuration. There's no separate "testing IAM role." Option D — while timeouts differ, a "connection timeout" specifically indicates TCP-level connectivity failure (can't establish a socket), not slow response. SSL negotiation happens AFTER TCP connection is established and would result in a different error type.
  • Glue JDBC connections with PrivateLink work by placing ENIs in the VPC where the PrivateLink endpoint exists: (1) PrivateLink creates a VPC endpoint with a private DNS name (account.privatelink.snowflakecomputing.com) that resolves to private IPs within the VPC; (2) the Glue connection specifies this VPC/subnet so that Glue ENIs are placed where they can reach the PrivateLink endpoint; (3) Snowflake JDBC driver is uploaded to S3 and referenced as a custom driver since Glue doesn't bundle Snowflake drivers by default; (4) the JDBC URL uses the PrivateLink hostname which resolves to the VPC endpoint's private IPs; (5) all traffic stays within the VPC — no internet traversal. Option B — AppFlow supports Snowflake but is designed for data extraction/loading, not for schema cataloging. AppFlow deposits data in S3 but doesn't create Glue catalog entries that point back to Snowflake for federated queries. Option C — while Glue Marketplace connectors exist for Snowflake, they don't "automatically configure PrivateLink routing" — VPC networking configuration is always manual because it depends on the customer's specific VPC setup. Option D — Glue absolutely supports VPC endpoint connectivity through its connection VPC configuration; this is a core feature. Using public endpoints would bypass the security requirements that motivated PrivateLink deployment.
  • Using the RDS DNS endpoint (not IP) combined with proper multi-AZ subnet/security group configuration resolves failover issues: (1) RDS endpoints are DNS names that always resolve to the current primary — after failover, DNS is updated within ~30 seconds; (2) if the JDBC URL already uses the DNS name (which is likely), the actual issue is networking: the Glue connection's subnet or security group only allows connectivity to one AZ; (3) after failover, the primary moves to the standby AZ — if the Glue connection's subnet can only route to the original AZ, connections fail; (4) the fix is ensuring the connection's security group allows outbound to the RDS security group (which is AZ-agnostic) and that the subnet's route table covers both AZs' private address ranges (which VPC subnets in the same VPC do automatically for private traffic). Option B — Route 53 health checks can't modify Glue connection properties; also, using DNS endpoints eliminates the need for IP-based management. Option C — NLB in front of RDS is unnecessary complexity — RDS already provides DNS-based failover. NLB adds cost, latency, and another failure point. Option D — Read Replicas are for read scaling, not HA failover. They don't maintain "consistent IPs" — promotion also changes endpoints. Multi-AZ is the correct HA mechanism.
