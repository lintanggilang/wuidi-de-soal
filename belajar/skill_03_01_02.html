Domain 3: Operations & Support — Task 3.1: Automate data processing

Skill 3.1.2: Troubleshoot managed workflows

MWAAAirflowtroubleshoot

Ringkasan

Skill ini termasuk dalam Domain 3: Operations & Support (Task 3.1: Automate data processing), dengan fokus pada troubleshoot managed workflows. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon MWAA
Managed Workflows for Apache Airflow; orkestrasi pipeline berbasis DAG.

Poin-Poin Kunci

  • Ketika DAG tidak muncul di Airflow UI, penyebab paling umum adalah syntax error atau import error dalam file DAG. Airflow scheduler mem-parse semua DAG files secara periodik, dan jika ada error saat parsing, DAG tidak akan di-register. Error ini terlihat di scheduler logs di CloudWatch.
  • SIGTERM signals ketika worker CPU secara konsisten tinggi (>90%) menunjukkan resource exhaustion — workers kehabisan resources dan Airflow/system mengirim SIGTERM untuk membunuh task processes yang melebihi limits. Upgrade environment class (mw1.small → mw1.medium/large) meningkatkan CPU dan memory per worker.
  • MWAA menyimpan log instalasi requirements di CloudWatch Logs. Langkah pertama adalah memeriksa log tersebut untuk mengidentifikasi error spesifik — biasanya dependency conflicts, package incompatibilities, atau package yang tidak tersedia. Ini memberikan informasi untuk fix yang tepat.
  • Connection timeout (bukan authentication failure atau connection refused) antara resources di VPC yang berbeda subnet paling sering disebabkan oleh security group rules. MWAA workers berjalan di VPC menggunakan security group tertentu, dan RDS security group harus explicitly allow inbound traffic dari MWAA security group pada port database (3306/5432).
  • Airflow scheduler mem-parse setiap DAG file secara periodik (default setiap 30 detik). Kode di top-level (di luar task functions) dieksekusi setiap kali scheduler parse file. Jika top-level code membuat API calls ke S3/DynamoDB, ini menambah latency signifikan yang dimultiplikasi dengan jumlah DAG files (150 × API call latency). Solusinya adalah memindahkan semua API calls ke dalam task callables yang hanya dieksekusi saat task running.
  • MWAA webserver memerlukan network connectivity yang proper. HTTP 503 menunjukkan webserver tidak bisa melayani requests, yang sering disebabkan oleh networking issues — NAT Gateway unhealthy, VPC endpoint misconfiguration, atau network ACL blocking traffic. Fakta bahwa scheduler masih berjalan (DAGs running) menunjukkan masalah spesifik pada webserver networking, bukan general environment failure.
  • MWAA workers memiliki limited local storage. Solusi terbaik adalah mengubah approach — gunakan streaming reads (misalnya boto3 S3 streaming atau pandas chunked reading) untuk memproses file tanpa menyimpan seluruhnya di disk lokal. Jika perlu temp storage, gunakan /tmp dengan explicit cleanup setelah selesai.
  • MWAA auto-scaling memerlukan waktu untuk menambah workers (provisioning new containers). Jika ada burst 50 tasks tiba-tiba dengan hanya 2 min workers, scaling ke 10 workers membutuhkan waktu. Selama scaling period, tasks menunggu di queue. Solusinya adalah meningkatkan min_workers agar ada cukup workers ready untuk peak demand.
  • MWAA mengekstrak plugins.zip ke folder plugins/ Airflow. Jika directory structure di dalam zip salah (misalnya ada extra parent directory seperti plugins/my-plugin/ bukannya langsung file di root), module path tidak sesuai dan import gagal. Structure yang benar: zip root harus langsung berisi __init__.py dan module files yang bisa di-import.
  • Scheduler heartbeat failures dan frequent process kills/restarts adalah classic symptoms of scheduler resource exhaustion (OOM — Out of Memory). Ketika scheduler kehabisan memory (karena parsing terlalu banyak DAGs, DAGs yang sangat complex, atau banyak running task instances), process di-kill oleh OS dan di-restart oleh supervisor. Zombie tasks terjadi karena scheduler tidak bisa send heartbeats saat dead. Solusi: kurangi jumlah/complexity DAGs, atau upgrade environment class untuk lebih banyak scheduler memory.

Miskonsepsi & Jebakan Umum

  • Salah — MWAA tidak perlu restart, scheduler secara otomatis mendeteksi file baru di S3.
  • Salah — tidak ada hard limit 1 MB untuk DAG files.
  • Salah — S3 versioning diperlukan tapi ini akan menyebabkan error saat setup environment, bukan saat adding DAGs.
  • Tidak berlaku — MWAA selalu menggunakan CeleryExecutor dan tidak bisa diubah ke LocalExecutor.
  • Tidak menyelesaikan resource exhaustion.
  • Justru memperburuk masalah dengan menambah load pada workers yang sudah overloaded.
  • Salah — UPDATE_FAILED biasanya karena user's requirements/plugins, bukan AWS service issue.
  • Tidak membantu memahami masalah untuk fix di masa depan.
  • Sangat disruptive dan tidak diperlukan.
  • Jika sebelumnya berfungsi dan konfigurasi tidak berubah, ini bukan penyebab.
  • Akan menyebabkan "too many connections" error, bukan timeout.
  • RDS PostgreSQL connection menggunakan username/password melalui network, bukan IAM roles (kecuali IAM auth di-enable).
  • Bisa membantu sedikit tapi tidak menyelesaikan root cause.
  • Salah — 150 DAGs masih dalam batas wajar.
  • Tidak relevan dengan DAG parsing time.
  • Salah — scheduler dan webserver adalah komponen terpisah; scheduler overload tidak menyebabkan webserver 503.
  • Salah — jika DAGs bucket dihapus, scheduler juga akan berhenti.
  • Salah — worker failure tidak membuat webserver inaccessible.
  • MWAA tidak mendukung mounting EFS ke workers secara native.
  • Environment class upgrade memberikan sedikit lebih banyak storage tapi mungkin masih tidak cukup untuk 2 GB files + intermediate data.
  • Tidak membantu jika setiap worker masih harus process file 2 GB secara lokal.
  • MWAA manages Celery broker configuration, users tidak bisa set message delay.
  • Scheduler queuing dan task execution are separate; scheduler sudah queued tasks (mereka sudah di "queued" state).
  • Jika ini masalahnya, tasks akan stuck bukan karena kurang workers tapi karena limit per worker, tapi ini biasanya terlihat saat workers idle yang tidak sesuai scenario ini.
  • Jika path salah, environment update seharusnya gagal atau warning muncul, bukan silent failure.
  • Jika permission issue, environment update akan gagal karena MWAA perlu membaca pluginszip saat update.
  • Salah — MWAA fully mendukung custom plugins.
  • Tidak mempengaruhi scheduler operation.
  • MWAA manages credential rotation otomatis.
  • Akan menyebabkan connectivity errors, bukan OOM kills.
