Skill 3.1.2: Troubleshoot managed workflows

MWAAAirflowtroubleshoot

Summary

Skill this including in Domain 3: Operations & Support (Task 3.1: Automate data processing), with fokus on troubleshoot managed workflows. Materi berikut merangkum service AWS that relevan along with concept important that needs kamu kuasai for topik this.

Key Services & Concepts

Amazon MWAA
Managed Workflows for Apache Airflow; orkestrasi pipeline based on DAG.

Key Points

  • When DAG not muncul in Airflow UI, penyebab most umum is syntax error or import error in file DAG. Airflow scheduler mem-parse all DAG files in a periodik, and if there is error when parsing, DAG not will in-register. Error this terlihat in scheduler logs in CloudWatch.
  • SIGTERM signals when worker CPU in a consistent high (>90%) indicates resource exhaustion — workers kehabisan resources and Airflow/system sends SIGTERM for membunuh task processes that exceeds limits. Upgrade environment class (mw1.small → mw1.medium/large) increases CPU and memory per worker.
  • MWAA stores log instalasi requirements in CloudWatch Logs. Langkah first is memeriksa log said for identifies error specific — usually dependency conflicts, package incompatibilities, or package that not available. This provides informasi for fix that correct.
  • Connection timeout (not authentication failure or connection refused) between resources in VPC that different subnet most often disebabkan by security group rules. MWAA workers runs in VPC uses security group certain, and RDS security group must explicitly allow inbound traffic from MWAA security group on port database (3306/5432).
  • Airflow scheduler mem-parse each DAG file in a periodik (default each 30 seconds). Kode in top-level (in outside task functions) dieksekusi each kali scheduler parse file. If top-level code creates API calls to S3/DynamoDB, this adds latency significant that dimultiplikasi with number DAG files (150 × API call latency). The solution is moves all API calls to in task callables that only dieksekusi when task running.
  • MWAA webserver requires network connectivity that proper. HTTP 503 indicates webserver cannot serves requests, that often disebabkan by networking issues — NAT Gateway unhealthy, VPC endpoint misconfiguration, or network ACL blocking traffic. Fakta that scheduler still runs (DAGs running) indicates problem specific on webserver networking, not general environment failure.
  • MWAA workers has limited local storage. Solution best is changes approach — gunakan streaming reads (for example boto3 S3 streaming or pandas chunked reading) for processes file without stores entirely in disk local. If needs temp storage, gunakan /tmp with explicit cleanup after complete.
  • MWAA auto-scaling requires time for adds workers (provisioning new containers). If there is burst 50 tasks tiba-tiba with only 2 min workers, scaling to 10 workers requires time. During scaling period, tasks waits in queue. The solution is increases min_workers so that there is quite workers ready for peak demand.
  • MWAA mengekstrak plugins.zip to folder plugins/ Airflow. If directory structure in in zip incorrect (for example there is extra parent directory such as plugins/my-plugin/ bukannya directly file in root), module path not appropriate and import fails. Structure that correct: zip root must directly contains __init__.py and module files that can in-import.
  • Scheduler heartbeat failures and frequent process kills/restarts is classic symptoms of scheduler resource exhaustion (OOM — Out of Memory). When scheduler kehabisan memory (because parsing too many DAGs, DAGs that very complex, or many running task instances), process in-kill by OS and in-restart by supervisor. Zombie tasks occurs because scheduler cannot send heartbeats when dead. Solution: kurangi number/complexity DAGs, or upgrade environment class for more scheduler memory.
