Domain 1: Ingestion & Transformation — Task 1.2: Transform and process data

Skill 1.2.7: Troubleshoot transformation failures

troubleshootSparkOOMskew

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.2: Transform and process data), dengan fokus pada troubleshoot transformation failures. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

AWS Lake Formation
Tata kelola data lake: izin berbasis tabel/kolom/baris dan LF-Tags di atas Glue Catalog.
Apache Spark
Engine komputasi terdistribusi in-memory; inti Glue ETL dan EMR.

Poin-Poin Kunci

  • OOM during shuffle indicates each executor's memory is insufficient for the shuffle data it receives. G.2X provides 32 GB memory per executor (vs 16 GB for G.1X). Increasing shuffle.partitions distributes data more evenly — each partition is smaller, reducing per-executor memory pressure.
  • Ini adalah classic data skew pattern — beberapa tasks memproses data yang jauh lebih banyak. "Long tail" tasks memblokir stage completion. Salting technique menambahkan random suffix ke skewed key untuk mendistribusikan data lebih merata. Repartitioning sebelum operasi yang skewed juga membantu.
  • Schema incompatibility ("Cannot merge incompatible data types") biasanya terjadi ketika Spark membaca multiple Parquet files yang memiliki schema berbeda untuk kolom yang sama (misalnya file baru menulis integer sebagai string). Mengecek Data Catalog schema versions dan file terbaru mengidentifikasi perubahan. Crawler bisa mendeteksi dan update schema.
  • Sort-merge join menulis shuffle data ke local disk. Jika partisi terlalu besar dan executor memiliki limited local storage, disk penuh. Meningkatkan shuffle.partitions mengurangi ukuran setiap partisi. Alternatif: gunakan instances dengan lebih banyak local NVMe storage (i3, d2) atau configure spark.local.dir ke EBS volume yang lebih besar.
  • Gradual degradation dengan constant data volume strongly indicates small file accumulation. Setiap hari file baru ditambahkan tanpa compaction/cleanup. Setelah beberapa minggu, prefix memiliki ribuan file kecil. Spark membuat task per file, increasing scheduling overhead. Solusi: enable Glue groupFiles, atau tambahkan compaction job.
  • "Communications link failure" after extended time typically means idle connections were closed by the database. MySQL wait_timeout (default 28800s, but often reduced) closes idle connections. In parallel Glue processing, some JDBC connections become idle while others are active. After wait_timeout expires, idle connections are killed. Adding autoReconnect=true, tcpKeepAlive=true ke JDBC URL prevents this.
  • Broadcast join membutuhkan driver untuk mengumpulkan seluruh broadcast table dan mengirimkannya ke semua executors. Untuk 10 GB table, driver membutuhkan memory yang cukup (biasanya 2-3x table size untuk serialization overhead). Error "Could not execute broadcast in time" biasanya karena driver OOM atau timeout saat collecting data. Fix: increase driver memory, atau jangan broadcast table 10 GB — gunakan sort-merge join yang lebih scalable.
  • Spark writes one file per partition. Jika DataFrame memiliki 10,000 partitions (common setelah shuffle operations), output menghasilkan 10,000 files. coalesce(100) mengurangi partitions ke 100 tanpa shuffle (preferred jika mengurangi), atau repartition(100) jika perlu redistribute data evenly.
  • S3 throttles at prefix level (3,500 PUT/COPY/POST/DELETE dan 5,500 GET/HEAD per second per prefix). Multiple pipelines hitting the same prefix simultaneously exceeds these limits. Solution: distribute objects across multiple prefixes (e.g., add hash-based prefixes like /data/a1/, /data/b2/) to multiply the available request rate.
  • Dalam Spark SQL, NULL == NULL menghasilkan NULL (not TRUE), sehingga rows dengan NULL join keys biasanya tidak match. Namun, jika menggunakan Spark's internal join optimization atau certain join conditions, NULLs dapat menyebabkan unexpected behavior. Lebih umum, jika join column seharusnya unique tapi ada NULL duplicates, join bisa menghasilkan cross-product dari NULL rows. Best practice: filter WHERE join_column IS NOT NULL sebelum join, atau gunakan coalesce().

Miskonsepsi & Jebakan Umum

  • Menambah parallelism tapi tidak menambah memory per executor.
  • Mungkin bekerja tapi mengurangi throughput.
  • Tidak mengatasi join-related OOM.
  • Tasks yang lambat tetap di satu partition/worker.
  • Menyebabkan timeout error bukan schema error.
  • Tidak terjadi secara otomatis di Glue.
  • Tidak menyebabkan executor shuffle failure.
  • S3 tidak memiliki capacity limit per bucket.
  • Memberikan different error message.
  • Menyebabkan sudden degradation.
  • Would cause immediate failure.
  • Queries were succeeding initially.
  • Jika broadcast forced via hint, threshold tidak mencegah error.
  • S3 file size limit 5 TB, bukan 1 MB.
  • Worker type mempengaruhi memory bukan file size.
  • Parquet files bisa berukuran GB.
  • More DPUs means more concurrent S3 requests which worsens the problem.
  • All standard storage classes support same rate.
  • VPC gateway endpoints don't throttle at this level.
  • Tidak menjelaskan row explosion.
