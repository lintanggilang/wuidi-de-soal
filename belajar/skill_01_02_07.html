Key Points

  • OOM during shuffle indicates each executor's memory is insufficient for the shuffle data it receives. G.2X provides 32 GB memory per executor (vs 16 GB for G.1X). Increasing shuffle.partitions distributes data more evenly — each partition is smaller, reducing per-executor memory pressure.
  • This is classic data skew pattern — several tasks processes data that jauh more. "Long tail" tasks memblokir stage completion. Salting technique adds random suffix to skewed key for distributes data more evenly. Repartitioning before operation that skewed also membantu.
  • Schema incompatibility ("Cannot merge incompatible data types") usually occurs when Spark reads multiple Parquet files that has schema different for column that same (for example file new writes integer as string). Mengecek Data Catalog schema versions and file terbaru identifies changes. Crawler can detects and update schema.
  • Sort-merge join writes shuffle data to local disk. If partition too large and executor has limited local storage, disk full. Increases shuffle.partitions reduces size each partition. Alternatif: gunakan instances with more local NVMe storage (i3, d2) or configure spark.local.dir to EBS volume that larger.
  • Gradual degradation with constant data volume strongly indicates small file accumulation. Each days file new is added without compaction/cleanup. Setelah several weeks, prefix has ribuan file small. Spark creates task per file, increasing scheduling overhead. Solution: enable Glue groupFiles, or tambahkan compaction job.
  • "Communications link failure" after extended time typically means idle connections were closed by the database. MySQL wait_timeout (default 28800s, but often reduced) closes idle connections. In parallel Glue processing, some JDBC connections become idle while others are active. After wait_timeout expires, idle connections are killed. Adding autoReconnect=true, tcpKeepAlive=true to JDBC URL prevents this.
  • Broadcast join requires driver for collects entire broadcast table and mengirimkannya to all executors. For 10 GB table, driver requires memory that quite (usually 2-3x table size for serialization overhead). Error "Could not execute broadcast in time" usually because driver OOM or timeout when collecting data. Fix: increase driver memory, or jangan broadcast table 10 GB — gunakan sort-merge join that more scalable.
  • Spark writes one file per partition. If DataFrame has 10,000 partitions (common after shuffle operations), output produces 10,000 files. coalesce(100) reduces partitions to 100 without shuffle (preferred if reduces), or repartition(100) if needs redistribute data evenly.
  • S3 throttles at prefix level (3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD per second per prefix). Multiple pipelines hitting the same prefix simultaneously exceeds these limits. Solution: distribute objects across multiple prefixes (e.g., add hash-based prefixes like /data/a1/, /data/b2/) to multiply the available request rate.
  • In Spark SQL, NULL == NULL produces NULL (not TRUE), so that rows with NULL join keys usually not match. However, if uses Spark's internal join optimization or certain join conditions, NULLs can causes unexpected behavior. More umum, if join column should unique but there is NULL duplicates, join can produces cross-product from NULL rows. Best practice: filter WHERE join_column IS NOT NULL before join, or gunakan coalesce().

Common Misconceptions & Pitfalls

  • Adds parallelism but not adds memory per executor.
  • May works but reduces throughput.
  • Not resolves join-related OOM.
  • Tasks that slow still in one partition/worker.
  • Causes timeout error not schema error.
  • Not occurs automatically in Glue.
  • Not causes executor shuffle failure.
  • S3 not has capacity limit per bucket.
  • Provides different error message.
  • Causes sudden degradation.
  • Would cause immediate failure.
  • Queries were succeeding initially.
  • If broadcast forced via hint, threshold not prevents error.
  • S3 file size limit 5 TB, not 1 MB.
  • Worker type affects memory not file size.
  • Parquet files can berukuran GB.
  • More DPUs means more concurrent S3 requests which worsens the problem.
  • All standard storage classes support same rate.
  • VPC gateway endpoints don't throttle at this level.
  • Not menjelaskan row explosion.
