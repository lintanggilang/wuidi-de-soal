Key Points

  • ALTER TABLE APPEND is the ideal solution for minimizing lock contention during bulk loads in Redshift. The COPY command into the staging table doesn't affect the production fact table at all — analysts can query the fact table freely. When ALTER TABLE APPEND executes, it moves data blocks at the metadata level (pointer swap), requiring only a very brief exclusive lock measured in seconds rather than the minutes/hours a direct COPY into a large table might take.
  • A read replica with hot_standby_feedback provides the optimal solution: (1) reporting queries are physically separated from OLTP traffic, eliminating direct lock contention; (2) PostgreSQL's MVCC on the replica provides snapshot isolation — reads see a consistent point-in-time view; (3) hot_standby_feedback = on tells the primary not to vacuum rows that the replica's long-running queries still need, preventing the "conflict with recovery" cancellation errors; (4) the primary's OLTP performance is unaffected.
  • Splitting VACUUM into DELETE ONLY and SORT ONLY provides granular control: (1) VACUUM DELETE ONLY reclaims disk space from deleted rows and runs with minimal locking — concurrent reads are not blocked; (2) VACUUM SORT ONLY re-sorts unsorted rows and requires an exclusive lock, but scheduling it during maintenance windows minimizes user impact; (3) this approach separates the non-blocking operation (space reclamation) from the blocking operation (sorting), allowing the table to remain accessible for the majority of the time.
  • Canonical lock ordering is the definitive solution for preventing deadlocks: deadlocks occur when two transactions acquire locks in opposite orders, creating a circular dependency (A holds 101, waits for 102; B holds 102, waits for 101). By mandating all services lock accounts in ascending order, circular waits become impossible — if Service A holds lock on 101 and needs 102, Service B would also need 101 first before 102, so B waits for A to complete rather than creating a cycle.
  • The root cause is concurrent WRITE operations on the same table — WLM queue configuration cannot resolve table-level write locks because Redshift acquires exclusive table-level locks for write operations (INSERT/UPDATE/DELETE) regardless of which queue the query runs in. The solution is to eliminate concurrent writes to the same table: (1) each ETL stream loads into its own staging table (no contention — different tables); (2) after all streams complete, a sequential merge step combines staging data into the final table; (3) total elapsed time often decreases because parallel staging loads + sequential merge is faster than serialized concurrent writes with lock waits.
  • Redshift uses serializable isolation by default. Serialization violations (error 1023) are an expected outcome in high-concurrency environments — they indicate the system detected a potential anomaly where concurrent transactions' results might differ from any serial execution order. The standard handling pattern is: (1) catch the serialization error; (2) retry the entire transaction from the beginning; (3) use exponential backoff to reduce retry storms. Since the failed transaction is fully rolled back, retrying is safe and typically succeeds because the conflicting transaction has completed.
  • Transaction-level advisory locks (pg_advisory_xact_lock) are the definitive solution for preventing orphaned locks: (1) when a worker crashes, its database connection drops, the transaction is automatically rolled back, and all transaction-level advisory locks are released immediately; (2) no cleanup process or heartbeat mechanism is needed — the database handles lock lifecycle automatically; (3) this is PostgreSQL's built-in mechanism for exactly this use case. The key difference: session-level locks (pg_advisory_lock) persist until explicitly released with pg_advisory_unlock OR the session disconnects — if a connection pool reuses the session, the lock remains held indefinitely.
  • This is a critical Redshift behavior to understand: Redshift uses MVCC (Multi-Version Concurrency Control) where SELECT queries read from a consistent snapshot of committed data. Readers do NOT block writers and writers do NOT block readers. If dashboard SELECT queries appear "blocked," the actual cause is typically: (1) WLM queue slots fully consumed by ETL queries (dashboards queued waiting for a slot, not a lock); (2) cluster resource exhaustion (CPU/memory) from heavy ETL reducing resources available for dashboards; (3) DDL operations (ALTER TABLE, DROP) which DO acquire exclusive locks that block reads. The correct investigation is WLM queue configuration and resource allocation, not lock behavior.
  • The combination of batching + READ COMMITTED addresses both root causes: (1) READ COMMITTED isolation eliminates InnoDB gap locks — MySQL only locks the exact rows matching the UPDATE's WHERE clause, not the "gaps" between index values that could span into other tenants' ranges; (2) small batches ensure each transaction holds locks briefly (milliseconds), committing frequently and releasing locks for other tenants. This is the standard pattern for bulk operations in multi-tenant MySQL systems.
  • The rename-swap pattern provides atomic table replacement: (1) CTAS builds new_target while the existing target table remains fully available for queries; (2) within a single transaction: RENAME target → target_old, RENAME staging → target; (3) these renames are metadata operations (updating system catalog entries) that complete in milliseconds; (4) concurrent queries either see the pre-rename state or post-rename state — never a missing table; (5) after verifying success, DROP target_old to clean up. This is the standard zero-downtime table refresh pattern in Redshift.

Common Misconceptions & Pitfalls

  • LOCK TABLE with ACCESS SHARE is a read lock that would conflict with the COPY's write lock rather than resolving it; you cannot manually downgrade a write operation's lock requirements.
  • Splitting into smaller COPY commands means 10 separate lock acquisitions; each still blocks readers, and the total blocked time remains similar with gaps between loads still causing intermittent blocking.
  • Increasing WLM concurrency doesn't resolve the fundamental lock conflict; if an exclusive write lock is held, additional query slots will still queue waiting for the lock to release.
  • PostgreSQL treats READ UNCOMMITTED identically to READ COMMITTED (dirty reads are not supported in PostgreSQL); this parameter change has no practical effect on lock behavior.
  • Setting lock_timeout to 0 means queries wait forever for locks, which doesn't solve the problem — it makes it worse by creating potentially unbounded waits.
  • Shared_buffers controls memory for caching data pages, not concurrency or lock behavior; increasing it won't resolve lock contention.
  • Increasing timeout doesn't reduce blocking; dashboard queries still wait 45 minutes, appearing frozen to users.
  • Disabling VACUUM entirely leads to degraded query performance over time as the table accumulates unsorted regions and unreclaimable space ("ghost rows"); automatic optimization helps but doesn't fully replace explicit maintenance for high-churn tables.
  • VACUUM REINDEX rebuilds interleaved sort key indexes but still requires an exclusive lock and doesn't avoid the locking problem.
  • Reducing lock_wait_timeout makes deadlocked transactions fail faster but doesn't prevent deadlocks; under high trading volume, constant retries create a "thundering herd" problem and reduce throughput.
  • Innodb_deadlock_detect is enabled by default in MySQL; it detects and automatically rolls back one deadlocked transaction, but this is a reactive measure that wastes work — prevention through lock ordering is far superior to detection and recovery.
  • READ COMMITTED reduces some gap-locking but doesn't prevent the fundamental row-level circular wait pattern described; both isolation levels still acquire exclusive row locks on UPDATE.
  • Correctly identifies the problem but explicitly states it doesn't resolve it; separate queues don't prevent table-level write lock conflicts.
  • Higher concurrency and SQA help with many short queries competing for slots, not with table-level write locks blocking concurrent modifications.
  • Auto WLM optimizes resource allocation but cannot override Redshift's fundamental table-level write locking behavior.
  • LOCK TABLE with exclusive access would prevent violations but serializes ALL concurrent work, defeating parallelism; reconciliation jobs for non-overlapping account groups should run concurrently.
  • Changing to READ COMMITTED would eliminate serialization errors but also removes the consistency guarantees needed for financial reconciliation (phantom reads, non-repeatable reads become possible — unacceptable for balance adjustments).
  • Cluster size doesn't affect serialization conflict detection, which is inherent to the isolation level's logical constraints, not memory availability.
  • Pg_try_advisory_lock returns immediately without blocking but still creates session-level locks; an hourly cleanup adds latency (locks orphaned for up to 59 minutes) and complexity.
  • Heartbeat mechanisms add application complexity and race conditions; if the heartbeat check fails to detect a crashed worker, locks remain orphaned.
  • Max_locks_per_transaction controls the lock table size, not advisory lock behavior; this parameter doesn't address orphaned locks.
  • Manually acquiring SHARE MODE locks would actually CREATE blocking by conflicting with ETL's exclusive locks, making the situation worse.
  • Data sharing provides workload isolation but is an over-engineered solution if the actual problem is WLM queue configuration.
  • WLM priority and queue-hopping help with queue slot contention (which may be the real issue) but the question incorrectly premises that write locks block reads.
  • SKIP LOCKED is useful for queue-like processing where skipping rows is acceptable, but other tenants' regular queries (e.g., SELECT * WHERE tenant_id = 'B') need ALL their rows, not a subset with some skipped.
  • A composite index on (tenant_id, pk) might reduce gap lock ranges but doesn't eliminate them under REPEATABLE READ; gap locks still apply within the index structure for range scans.
  • Buffer_pool_size affects data caching, not lock behavior; lock structures use separate memory regardless of buffer pool configuration.
  • Retry logic masks the problem rather than solving it; users still experience intermittent errors and dashboard load time increases during the rebuild window.
  • Data sharing between schemas adds unnecessary complexity for what is a single-cluster table refresh operation.
  • A view approach works conceptually but introduces an extra layer; direct table renames are simpler and don't require restructuring how dashboards reference the table.
