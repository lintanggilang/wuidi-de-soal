Key Points

  • Broadcast join sends the small table (50 MB easily fits in memory) to all executors. The join happens locally on each executor without shuffling the 500 GB fact table across the network. This eliminates the most expensive operation (shuffle).
  • Sequential: 10,000 × 50ms = 500 seconds (8.3 minutes). With asyncio/aiohttp making 100 concurrent calls: 10,000/100 × 50ms = 5 seconds. Concurrency eliminates the I/O wait time bottleneck. This is the biggest optimization for I/O-bound workloads.
  • "Filter early, aggregate late" (predicate pushdown principle) — filtering first reduces the dataset from 1 TB to ~50 GB (5%). The subsequent groupBy only processes 50 GB instead of 1 TB, reducing shuffle volume by 95% and dramatically cutting runtime. This is one of the most impactful code optimizations.
  • orjson and ujson are C-extension libraries optimized for JSON parsing speed. orjson is typically 3-10x faster than stdlib json for both parsing and serialization. For 50K records where parsing dominates, this translates directly to 60% × (1 - 1/5) = 48% total time reduction.
  • Spark 3.0+ AQE with skew join optimization (spark.sql.adaptive.skewJoin.enabled=true) automatically detects and splits skewed partitions at runtime. It splits the large partition into smaller sub-partitions and replicates the matching data from the other side. This is the simplest solution requiring no code changes.
  • collect() brings entire dataset to driver memory — anti-pattern for large datasets. UDFs and mapPartitions execute custom logic on executors where data already resides, distributed across the cluster. This keeps 10 GB distributed across many executors (each handling a portion) instead of all on one driver.
  • Spark SQL optimizer automatically handles both: (1) Partition pruning — only reads S3 prefixes matching region='US', skipping all other region partitions. (2) Predicate pushdown to Parquet — uses Parquet's column statistics (min/max) to skip row groups where amount is entirely ≤ 1000. Both happen at read time, minimizing I/O.
  • BatchWriteItem sends up to 25 items per API call, reducing network round-trips from 100 to 4 (100/25). Each batch is processed in parallel by DynamoDB internally. This significantly reduces Lambda execution time.
  • Python UDFs serialize data row-by-row between JVM and Python interpreter — extremely slow. Built-in Spark functions execute natively in JVM (no serialization). Pandas UDFs (vectorized) process data in Arrow batches — much less serialization overhead than row-by-row UDFs. Can be 10-100x faster.
  • Redshift's columnar MPP architecture relies heavily on distribution and sort keys for performance. Proper DISTKEY on join columns eliminates network redistribution (data already co-located). SORTKEY enables zone-map pruning (skipping entire 1MB blocks that don't match predicates). These together can turn sequential scans into targeted reads.
