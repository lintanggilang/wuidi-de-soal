Key Points

  • Graph data structures are specifically designed for relationship-heavy data where traversal operations (shortest path, connected components, influence propagation) are the primary access pattern. Amazon Neptune is a purpose-built graph database that natively supports these operations with O(V+E) traversal time using BFS/DFS algorithms.
  • DAGs are the fundamental data structure for workflow orchestration (Airflow literally calls its workflows "DAGs"). The directed edges encode task dependencies, the acyclic property guarantees no infinite loops, and topological sort produces a valid execution order respecting all dependencies. Cycle detection (using DFS with coloring) validates the pipeline at definition time.
  • Bloom filters are purpose-built for probabilistic membership testing. They use multiple hash functions mapping elements to a bit array, achieving O(1) lookups in constant space (typically 10 bits per element for 1% false positive rate). For 500 billion records, a Bloom filter needs approximately 600 GB — large but feasible in distributed systems — versus storing all keys which would require many terabytes. The zero false negative guarantee means every duplicate WILL be caught; the small false positive rate only causes unnecessary re-checks.
  • The nested set model encodes tree structure as left/right boundary numbers assigned via DFS traversal. A node's subtree includes all nodes whose left value falls between the parent's left and right — this is a simple indexed range query, O(log n) with B-tree index. Ancestor queries reverse the logic. Both operations execute in a single SQL query without recursion. For 50,000 categories with heavy read operations, this provides optimal performance.
  • KEY distribution applies a consistent hash function to the specified column (customer_id), mapping each unique value to a specific compute node deterministically. This achieves both goals: (1) co-location — all rows for customer_id=123 always hash to the same node, enabling local JOINs without network shuffling; (2) even distribution — assuming customer_ids have sufficient cardinality, the hash function distributes them uniformly across nodes.
  • Hash tables provide O(1) average-case lookup by computing a hash of the key (device_id) to directly access the value without searching. ElastiCache Redis implements this as an in-memory key-value store, achieving sub-millisecond latency that easily meets the 5ms requirement at 100K events/second. The infrequent updates (daily) align well with a cache-aside pattern where the cache is refreshed once per day.
  • The hash join algorithm transforms the problem from O(n×m) = O(500 billion comparisons) to O(n+m) = O(1.5 million operations) — a dramatic reduction. Building the hash table on the smaller 500K-record reference set uses O(n) time and memory, then each of the 1M streaming records performs an O(1) hash probe. In Spark/Glue, this is implemented as a broadcast hash join where the reference table is broadcast to all executors.
  • The materialized path pattern pre-computes the tree position of each node as a string path. Querying "all cardiovascular conditions" becomes a simple prefix filter (WHERE path LIKE 'I/I00-I99/%'), which Athena/Glue can push down to partition pruning or Parquet column predicate filtering. This avoids runtime tree traversal while supporting any-level ancestor queries. Storage overhead is minimal (a short string per record).
  • Compound sort keys in Redshift physically order data on disk by the specified columns in sequence. With transaction_date first, zone maps (min/max metadata per 1MB block) allow Redshift to skip entire blocks that don't contain the target date range — dramatically reducing I/O for range queries. The secondary sort on account_id helps within-date-range filtering. Since date range queries are predominant, placing transaction_date first optimizes for the primary access pattern.
  • HyperLogLog is a probabilistic cardinality estimation algorithm that uses only O(log log n) space — approximately 16 KB for 2% standard error with 16,384 registers. It works by hashing each element and observing the longest run of leading zeros across all hashed values, which statistically correlates with cardinality. For 500M unique users, HLL provides ~2% accuracy in 16 KB versus the 8+ GB needed for exact counting. Redis (ElastiCache) has native HLL support via PFADD/PFCOUNT commands.

Common Misconceptions & Pitfalls

  • S3 + Glue is batch-oriented and cannot provide near real-time path queries; custom BFS on flat files lacks index support.
  • Redshift self-joins for graph traversal require multiple expensive joins proportional to path length, making real-time queries impractical at 50M nodes.
  • DynamoDB is a key-value store; recursive scans for path finding would be extremely inefficient with O(n) full table scans per hop and no native graph traversal support.
  • Linked lists only support linear sequential execution and cannot represent parallel tasks or complex dependency patterns with multiple predecessors.
  • Hash tables provide O(1) lookup but have no inherent structure for dependency relationships or ordering.
  • Binary trees limit each task to exactly two dependents, which doesn't model real-world pipelines where tasks may have many downstream consumers.
  • Storing 500 billion keys in a hash table would require tens of terabytes of RAM, which is impractical.
  • B-tree provides O(log n) not O(1), and for 500 billion records the tree depth creates significant I/O.
  • Sorted arrays require keeping all keys in memory and binary search is O(log n), not O(1).
  • Parsing JSON from S3 for every query introduces latency and lacks indexing capabilities for tree operations.
  • String LIKE queries ('Electronics%') cannot leverage indexes efficiently and break with name changes.
  • Adjacency lists require recursive traversal (CTE in SQL) for subtree queries, performing poorly for deep hierarchies and not supported natively in DynamoDB.
  • ALL distribution replicates the entire 10 TB table on every node (80 TB total storage), which is impractical for large fact tables.
  • Manual range-based partitioning is fragile, cannot guarantee even distribution, and doesn't adapt to cluster resizing.
  • EVEN distribution scatters rows randomly, so JOINs on customer_id require expensive inter-node data redistribution at query time.
  • S3 GetObject has 50-200ms first-byte latency, far exceeding the 5ms requirement.
  • Redshift is optimized for analytical queries on large datasets, not single-row point lookups; federated queries add significant overhead.
  • RDS with B-tree index provides O(log n) lookups with network + disk I/O latency, typically 2-10ms under load, and may not sustain 100K lookups/second without expensive scaling.
  • Sort-merge join at O(n log n + m log m) is better than nested loop but worse than hash join for this size ratio, and sorting adds significant overhead.
  • Adding DPUs provides linear speedup (10x more resources = ~10x faster) but doesn't change the O(n×m) algorithm, reducing 45 min to ~45 min unreliably.
  • Partitioning into smaller chunks doesn't reduce total comparison count; it's still O(n×m) in aggregate.
  • Storing the tree as JSON requires parsing and traversing a large document per query, which cannot leverage columnar storage or partition pruning.
  • Forcing users to enumerate all sub-codes (potentially hundreds) makes queries impractical and error-prone when codes are added.
  • Recursive parent-child lookups require multiple JOINs or CTEs at query time, which is expensive over billions of diagnosis records in a data lake.
  • Without a sort key, data is stored in insertion order, forcing full table scans regardless of filter predicates.
  • Redshift does not support traditional B-tree indexes; it uses columnar storage with zone maps and sort keys instead.
  • Interleaved sort keys give equal weight to all columns, which is beneficial only when both columns are filtered independently with equal frequency; for predominantly date-range queries, this reduces date filtering efficiency compared to compound.
  • DynamoDB would store 500M items daily at enormous cost, and count scans at 500M items take minutes.
  • Storing 500M user IDs (8 bytes each = 4 GB minimum) exceeds Lambda's memory limit (10 GB max) and is wasteful when approximate counting is acceptable.
  • Sorted arrays require O(n) space and O(log n) binary search for insertion, impractical at 500M elements.
