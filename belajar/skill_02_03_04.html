Domain 2: Data Store Management — Task 2.3: Manage the lifecycle of data

Skill 2.3.4: S3 versioning and DynamoDB TTL

versioningDynamoDBTTL

Ringkasan

Skill ini termasuk dalam Domain 2: Data Store Management (Task 2.3: Manage the lifecycle of data), dengan fokus pada s3 versioning and dynamodb ttl. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon S3
Object storage tahan lama; dasar data lake, mendukung event notification, versioning, dan lifecycle.
Amazon DynamoDB
Database NoSQL key-value latensi rendah; skala horizontal, mendukung TTL dan Streams.
DynamoDB TTL
Menghapus item otomatis setelah timestamp kedaluwarsa tanpa biaya tambahan.

Poin-Poin Kunci

  • Lifecycle rule untuk menghapus noncurrent versions setelah 30 hari memungkinkan pemulihan file yang tertimpa dalam waktu 30 hari sambil secara otomatis membersihkan versi lama untuk mengontrol biaya.
  • DynamoDB TTL membandingkan nilai atribut TTL (Unix epoch timestamp) dengan waktu saat ini. Item dihapus ketika current time > TTL value. Tidak ada "offset" yang bisa dikonfigurasi — atribut TTL harus berisi waktu ekspirasi absolut. Oleh karena itu, atribut terpisah "expirationTime" yang berisi lastActivity + 86400 (24 jam dalam detik) adalah implementasi yang benar.
  • MFA Delete mengharuskan autentikasi multi-faktor untuk menghapus versi objek secara permanen atau mengubah status versioning bucket. Ini mencegah penghapusan permanen tanpa MFA, bahkan oleh root account.
  • Untuk mengambil versi spesifik, gunakan ListObjectVersions API atau S3 console untuk melihat semua versi objek beserta version ID-nya, kemudian gunakan GetObject dengan parameter versionId untuk mengunduh versi yang diinginkan.
  • DynamoDB Streams menangkap TTL deletions sebagai event REMOVE dengan userIdentity.type = "Service" dan userIdentity.principalId = "dynamodb.amazonaws.com". Lambda consumer dapat memfilter event ini dan menulis data ke S3 untuk archival. Ini fully event-driven dan minimal overhead.
  • Ketika versioning di-suspend, objek baru yang diupload mendapat null version ID. Jika sudah ada objek dengan null version ID, objek tersebut ditimpa. Versi-versi sebelumnya yang memiliki version ID non-null tetap dipertahankan.
  • S3 Lifecycle rules mendukung NoncurrentVersionExpiration dengan parameter NewerNoncurrentVersions yang memungkinkan menyimpan sejumlah N versi noncurrent terbaru dan menghapus yang lebih lama. Ini adalah solusi native S3 yang paling efisien.
  • DynamoDB TTL tidak menjamin penghapusan instan — item biasanya dihapus dalam waktu 48 jam setelah expiration (umumnya dalam beberapa jam). Ini by design dan tidak bisa dipercepat. Solusi yang benar adalah menambahkan filter expression di query aplikasi untuk mengecualikan item yang sudah expired (TTL < current_time).
  • Untuk menghapus versi objek secara permanen di bucket dengan versioning enabled, Anda harus mengirim DeleteObject request dengan version ID spesifik. Tanpa version ID, S3 hanya membuat delete marker.
  • DynamoDB TTL deletions sepenuhnya gratis — tidak mengonsumsi write capacity units dan tidak dikenakan biaya. Ini menjadikan TTL cara yang paling cost-effective untuk menghapus data yang sudah expired secara otomatis.

Miskonsepsi & Jebakan Umum

  • Salah karena transition ke Glacier terjadi sebelum expiration, tapi lifecycle rule untuk noncurrent versions harus menggunakan NoncurrentVersionExpiration, bukan Expiration.
  • Tidak menghapus versi yang ada dan menghilangkan proteksi ke depan.
  • Tidak mungkin — versioning hanya bisa di-suspend, tidak di-disable, dan CRR membutuhkan versioning enabled.
  • Salah karena menggunakan lastActivity langsung berarti item langsung expired.
  • Tidak ada — DynamoDB tidak memiliki fitur TTL offset.
  • Menambah kompleksitas yang tidak perlu.
  • Tidak mencegah penghapusan manual. Pertanyaan spesifik menyebut "tanpa multi-factor authentication" yang langsung mengarah ke MFA Delete.
  • Bisa di-bypass oleh root account yang bisa mengubah policy.
  • Mencegah penghapusan selama retention period tapi tidak memerlukan MFA — ia memblokir semua penghapusan termasuk root.
  • Digunakan untuk restore dari Glacier, bukan untuk mengakses versi sebelumnya.
  • Untuk mengontrol SLA replikasi, bukan untuk restore.
  • Tidak real-time dan membutuhkan waktu untuk generate report.
  • Sangat mahal untuk tabel besar dan menghasilkan data duplikat.
  • Tidak efisien — GSI tidak bisa digunakan untuk query items berdasarkan waktu mendekati TTL secara efektif.
  • Memerlukan scan yang mahal dan berisiko race condition dengan TTL.
  • Salah — upload tetap berhasil.
  • Hampir benar tapi tidak menyebutkan bahwa null version ID sebelumnya ditimpa.
  • Salah — versi sebelumnya tidak dihapus otomatis. Ini penting dipahami: suspend versioning TIDAK menghapus versi yang sudah ada.
  • Untuk multipart upload yang tidak selesai, bukan versi.
  • Bisa dilakukan tapi membutuhkan pengelolaan manual dan tidak otomatis.
  • Mengelola storage class bukan jumlah versi.
  • Salah — TTL deletion menggunakan background proses yang terpisah dari WCU provisioned.
  • Tidak ada mekanisme untuk meningkatkan TTL throughput secara manual.
  • Tidak akan mempercepat proses.
  • Tanpa version ID hanya akan membuat delete markers, bukan penghapusan permanen.
  • Tidak bisa menargetkan objek spesifik berdasarkan key.
  • Salah — versioning tidak bisa di-disable, hanya di-suspend, dan itu tidak menghapus versi yang ada.
  • Salah — TTL menggunakan background proses terpisah yang tidak mempengaruhi WCU.
  • Salah — TTL deletions yang tercatat di DynamoDB Streams juga tidak menimbulkan biaya tambahan di luar biaya normal Streams (biaya read dari stream tetap berlaku jika ada consumer).
  • Tidak ada skema biaya seperti ini.
