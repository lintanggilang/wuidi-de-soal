Skill 4.5.2: PII identification (Macie)

MaciePIILakeFormation

Summary

Skill this including in Domain 4: Security & Governance (Task 4.5: Understand data privacy and governance), with fokus on pii identification (macie). Materi berikut merangkum service AWS that relevan along with concept important that needs kamu kuasai for topik this.

Key Services & Concepts

AWS Lake Formation
Tata kelola data lake: permission based on table/column/rows and LF-Tags in above Glue Catalog.
Amazon Macie
Deteksi & klasifikasi PII in S3 automatically uses ML.

Key Points

  • Kombinasi automated sensitive data discovery and scheduled classification jobs provides coverage most komprehensif. Automated sensitive data discovery performs sampling berkelanjutan against bucket for creates overview, while scheduled classification jobs ensures each object new in-scan in a sistematis each days. This provides both continuous monitoring and comprehensive deep scanning.
  • Macie custom data identifiers enables user mendefinisikan regex patterns for format data sensitif that unik for organisasi. Konfigurasi mencakup: regex pattern (MRN-\d{6}-[A-Z]{2}), keywords for reduces false positives (must muncul in proximity certain), and maximum match distance that determines seberapa dekat keyword must berada from match.
  • Macie terintegrasi native with Amazon EventBridge, sends findings as events. EventBridge rule can mem-filter based on severity (HIGH) and trigger Lambda function for automated remediation — for example adds deny policy on bucket for prefix certain, adds object tags (classification=pii), or moves to quarantine bucket. Parallel SNS notification memberitahu security team.
  • Suppression rules (findings filters with auto-archive) is way most correct for handles false positives from bucket certain. Rule can is configured for automatically archive findings from bucket specific said, so that not muncul in default findings view but still stored for audit. Macie still scanning bucket said (useful if real PII accidentally enters to test bucket).
  • Integrasi Macie-Lake Formation requires orchestration through EventBridge and Lambda because there is no native direct integration. Lambda function performs: (1) tagging S3 object for classification tracking, (2) mendaftarkan S3 location in Lake Formation if not yet registered, (3) uses Lake Formation API for GRANT permissions only to DPO role and REVOKE from that other. This memenuhi GDPR requirement for access restriction segera after PII teridentifikasi.
  • Macie classification jobs supports object criteria filtering including based on last modified date. By only scanning objects that changes since last successful run, volume scanning berkurang drastically. Sampling depth controls persentase eligible objects that in-scan per run. Kombinasi incremental approach + appropriate sampling ensures job complete in window without melewatkan data new.
  • Macie severity levels is determined in a internal based on number occurrences and type data — user cannot changes severity scoring logic. Solution that correct is creates EventBridge rule that filters based on type data identifier (classificationDetails.result.sensitiveData.detections.type = "CREDIT_CARD_NUMBER") without memperhatikan severity field. Rule this then trigger remediation workflow that appropriate policy internal (HIGH priority).
  • CCPA mendefinisikan personal information very luas. Macie managed data identifiers mencakup many standard PII (names, addresses, SSN, credit cards, emails, phone numbers) but not mencakup all kategori CCPA such as geolocation coordinates, device IDs, or browsing patterns. Solution best is kombinasi: managed identifiers for standard PII + custom data identifiers for format CCPA-specific that not in-cover. Custom identifiers can detects patterns such as koordinat GPS (regex for lat/long), MAC addresses, advertising IDs, dll.
  • Automated sensitive data discovery uses sampling, jadi sensitivity score is estimasi. Langkah proper is: (1) Run targeted classification job for gets complete picture (object-by-object detail), (2) Based on findings, implementation data masking/tokenization/encryption in ETL pipeline BEFORE data landing in staging — this ensures PII there is no in staging area. Approach this resolves root cause (PII in staging) not gejalanya.
  • Security Hub is central aggregation point for security findings including Macie. By enabling Security Hub integration: (1) Macie findings from all member accounts automatic flow to Security Hub, (2) Security Hub also receives findings from services other (GuardDuty, Inspector, dll) enables cross-service reporting, (3) Security Hub findings can in-export to S3 for querying with Athena and visualization with QuickSight. This provides trending, per-account breakdown, and aggregation that requested.

Common Misconceptions & Pitfalls

  • Melewatkan data that enters between scan and requires manual intervention.
  • Not way Macie works — Macie uses jobs, not per-object API calls.
  • Uses sampling and may melewatkan several object — not quite for compliance requirement that requires detection in all data.
  • Allow lists is used for MENGECUALIKAN known non-sensitive matches (false positives), not for detects data sensitif new.
  • Glue sensitive data detection there is but question specific about Macie and custom identifiers is feature built-in Macie.
  • AWS not receives request for adds managed identifiers for format proprietary perusahaan.
  • Macie not sends metrics to CloudWatch Alarms directly, and Auto Scaling + Glacier not remediation that correct.
  • Only notification without automation.
  • AWS Config rules not directly triggered by Macie findings, and deletes objects too agresif (may still is required but needs restricted access).
  • Requires Anda inserts each synthetic number — not scalable if ratusan test records.
  • Menghentikan scanning entirely — if real PII enters to test bucket, not will is detected.
  • Mempengaruhi ALL buckets, not only test bucket — credit card detection hilang in production buckets also.
  • Lake Formation not has capabilities reads Macie findings automatically.
  • Adds data movement overhead and can disrupting downstream pipelines that referencing original path.
  • Not there is built-in direct integration between Macie and Lake Formation.
  • Reduces identifiers reduces coverage and can causes compliance gaps; runtime reduction-nya also minimal because bottleneck usually in object reading not pattern matching.
  • Multiple parallel jobs not speeds up because Macie has account-level concurrency limits.
  • Increases sampling depth memperbanyak objects that in-scan so that memperlama runtime, not reduces.
  • Custom data identifiers not has "severity threshold setting" — severity still is calculated by Macie based on volume detections.
  • Macie not provides configuration for changes severity scoring per identifier type.
  • Security Hub cannot memodifikasi severity findings before EventBridge; findings flow to EventBridge directly from Macie.
  • Uses custom only berarti creates ulang detection that already there is in managed identifiers (duplikasi effort).
  • Managed identifiers not cover ALL kategori CCPA (especially behavioral data).
  • Macie can detects partly large with managed + custom; third-party not is required.
  • Memindahkan to region without Macie is security by obscurity that not solves PII exposure risk.
  • Deleting data disrupting ETL pipeline and may deletes data that still is required.
  • Exclusion list menyembunyikan problem, not solves.
  • Per-account configuration not is required if uses delegated administrator model; also adds management overhead.
  • Can works but only for Macie findings — not mengaggregasi with security tools other.
  • Macie not has built-in PDF reporting dashboard.
