Skill 1.4.10: Distributed computing

MapReduceSparkdistributed

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.4: Apply programming concepts), dengan fokus pada distributed computing. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon EMR
Cluster big data terkelola (Spark, Hive, Presto); mendukung Spot Instances untuk hemat biaya.
Apache Spark
Engine komputasi terdistribusi in-memory; inti Glue ETL dan EMR.

Poin-Poin Kunci

  • Data skew (one key receiving 90% of data) causes a single reducer to be overwhelmed while others sit idle. Salted keys distribute the hot key across multiple reducers: page_url becomes page_url_0 through page_url_N, spreading the load evenly. A combiner reduces data transferred during shuffle (less network I/O). The second-stage reduce merges partial counts. This transforms a 4-hour skewed job into a balanced ~1-hour job.
  • groupByKey shuffles ALL records for each key across the network, then aggregates at the reducer. reduceByKey/aggregateByKey performs partial aggregation on each executor FIRST (map-side combine), then shuffles only the partial results. For aggregations like sum/count/average, this reduces shuffle data by orders of magnitude. Example: 1 million records per customer_id shuffled (groupByKey) vs. one partial aggregate per customer_id per executor shuffled (reduceByKey).
  • Spark's lineage (DAG of transformations) is its primary fault tolerance mechanism. Unlike systems that replicate data (expensive for large datasets), Spark records HOW to recreate data from its source. When executor 5 fails, Spark knows that partition 5's data was created by: read S3 file X → filter → map → ... and reruns these transformations on another executor. Only lost partitions are recomputed, not the entire dataset. The driver coordinates task reassignment automatically.
  • Partitioning by date aligns with the query access pattern (WHERE timestamp = ...). Spark's partition pruning reads only the relevant directory, dramatically reducing I/O. For 5TB over one year, a daily query reads ~14GB instead of 5TB — a 365x improvement. Parquet's columnar format combined with partition pruning means Spark reads only the columns needed from the relevant date partitions. Hive-style partitioning (key=value directories) enables automatic pruning.
  • Bucketing pre-sorts and co-locates data with the same key in the same file (bucket). When both join sides are bucketed on the join key with equal bucket counts, Spark knows that all records for a given customer_id already reside in the same numbered bucket on both tables. It joins bucket 1 of orders with bucket 1 of customers locally — zero shuffle. This is a shuffle-free sort-merge join.
  • CAP theorem states that during a network partition, a distributed system must choose between consistency and availability. For real-time dashboards, availability matters most (users see dashboards, even with slightly stale data). DynamoDB with eventual consistency provides this — reads may be milliseconds behind but the system remains available during AZ failures. For financial reporting, consistency matters more — Redshift provides this for batch queries. This dual-approach optimizes each layer for its requirements.
  • Broadcast join sends the small table (50MB) to all executors. Each executor holds the entire dimension table in memory and performs a local hash-map lookup for each row of its fact table partition. No shuffle of the 2TB fact table occurs — only 50MB is broadcast (vs. shuffling 2TB). This is optimal when one side of the join fits in executor memory. The autoBroadcastJoinThreshold tells Spark to automatically choose broadcast join when one table is below the threshold.
  • Horizontal scaling leverages distributed computing's core principle: divide work across many nodes for parallel execution. 20 nodes processing simultaneously achieve near-linear speedup (20x faster). At similar hourly costs (20 small ≈ 1 large), the total job cost is dramatically lower because it runs 20x faster (30min vs 10hrs). Additionally, horizontal scaling provides fault tolerance (lose 1 of 20 nodes vs. losing the only node) and can use Spot instances for further savings.
  • Data locality is a fundamental distributed computing principle: computation should happen where data lives. Moving 500GB cross-region adds significant latency (40min vs seconds for same-region) and costs $0.02/GB ($10 per run). By colocating compute (EMR) with data (S3 in us-east-1), reads become same-region with near-zero added latency and no transfer cost. This is why Hadoop was designed with data-local scheduling — tasks run on the node storing their HDFS blocks.
  • Checkpointing breaks the lineage by saving intermediate results to reliable storage (HDFS/S3). After a checkpoint, Spark's fault recovery only replays from the checkpoint, not from the original source. For a 15-step pipeline with a checkpoint at step 7: a failure at step 14 recomputes 7 steps (8-14) instead of 14 steps (1-14) — cutting recovery time in half. Strategic checkpointing balances recovery cost vs. checkpoint overhead.

Miskonsepsi & Jebakan Umum

  • Increasing reducer count doesn't help when one key dominates; that key still goes to one reducer regardless of total count.
  • More map tasks don't address the reduce-phase bottleneck.
  • Pre-sorting doesn't change the fundamental data distribution problem in the reduce phase.
  • More memory delays the OOM but doesn't reduce the fundamental amount of data being shuffled.
  • More partitions distribute the same 500GB across more tasks but don't reduce total shuffle volume.
  • Caching stores the input data in memory but doesn't affect the shuffle operation behavior.
  • Spark doesn't replicate intermediate data like HDFS replicates blocks; it uses lineage instead (more memory-efficient).
  • Spark automatically handles executor failures; only driver failure requires restart (unless in cluster mode with supervision).
  • Checkpointing is optional and used for specific scenarios (long lineages, streaming); it's not the default mechanism.
  • Billions of tiny partitions create excessive S3 LIST API calls and file opening overhead (small file problem).
  • One file prevents any parallelism; Spark can't split a single Parquet file efficiently across 100 executors.
  • Random hash partitioning distributes data evenly but offers ZERO pruning benefit because queries can't determine which partitions contain relevant dates.
  • Broadcasting 200GB exceeds executor memory limits (default broadcast threshold is 10MB); it would crash executors.
  • More shuffle partitions distribute the work but still shuffle 700GB of data across the network.
  • Repartitioning triggers a full shuffle of both tables (700GB), which is exactly the problem being solved.
  • While AWS manages much complexity, architects must still choose consistency models (strong vs eventual reads).
  • CA is impossible in distributed systems; network partitions are inevitable in multi-AZ deployments, and single-AZ eliminates fault tolerance.
  • CP sacrifices availability; dashboards going down during AZ issues is unacceptable for real-time monitoring use cases.
  • Caching speeds up repeated reads but doesn't eliminate the shuffle; SortMergeJoin still requires data co-location via shuffle.
  • Repartitioning triggers a full shuffle of the 2TB fact table, which is the expensive operation we're trying to avoid.
  • 2TB per executor is impossible and unnecessary; broadcast join avoids moving the large table entirely.
  • Sequential batches still take 10 hours total with no parallelism benefit.
  • Vertical scaling has a ceiling (largest instance exists), provides no parallelism benefit for embarrassingly parallel workloads, and a single failure point means total restart.
  • Compression reduces I/O but doesn't address compute scaling needs; 10TB still requires proportional processing regardless of storage format.
  • More nodes don't reduce per-connection latency; cross-region bandwidth is limited by physical distance and AWS network architecture.
  • S3 Transfer Acceleration optimizes uploads to S3, not reads from S3; it doesn't apply to GET requests.
  • Compression helps but doesn't eliminate the fundamental latency of cross-region transfer (speed of light).
  • Combining transformations into one doesn't shorten the internal computation; the same work must be redone on failure.
  • More executors reduce failure probability but don't reduce recovery cost when failures do occur (they always will in large clusters).
  • Cache/persist stores data in memory but doesn't truncate lineage. If an executor with cached data fails, Spark still uses lineage to recompute (cache is just a hint, not a guarantee).
