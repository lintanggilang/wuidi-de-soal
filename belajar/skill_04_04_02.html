Domain 4: Security & Governance — Task 4.4: Prepare logs for audit

Skill 4.4.2: CloudWatch Logs for audit

CloudWatchLogsaudit

Ringkasan

Skill ini termasuk dalam Domain 4: Security & Governance (Task 4.4: Prepare logs for audit), dengan fokus pada cloudwatch logs for audit. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

CloudWatch Logs
Pengumpulan & penyimpanan log; CloudWatch Logs Insights untuk query log.
Amazon CloudWatch
Monitoring metrik, alarm, dan dashboard untuk sumber daya & aplikasi AWS.

Poin-Poin Kunci

  • Naming convention /aws/glue/{environment}/{job-name} memberikan organisasi hierarkis yang jelas. Retention 1827 hari (≈5 tahun) memenuhi compliance requirement secara tepat. CloudWatch Logs mendukung asosiasi customer-managed KMS key per log group menggunakan API associate-kms-key.
  • Subscription filter ke Firehose memberikan near real-time streaming ke S3 dengan prefiks terstruktur secara otomatis, minimal operational overhead, dan tidak memerlukan scheduled jobs. Firehose mendukung dynamic partitioning berdasarkan waktu.
  • CloudWatch cross-account observability memungkinkan monitoring account (sink) untuk melihat logs dari source accounts (links) tanpa menyalin data. Ketika dikelola via Organizations, konfigurasi diterapkan secara terpusat dan member accounts tidak bisa memodifikasi sharing configuration. Source accounts tetap memiliki akses baca ke logs mereka sendiri.
  • Subscription filters memungkinkan streaming real-time log events yang cocok dengan pola filter tertentu (seperti "DataCorruptionException") langsung ke Kinesis Data Streams. Ini memberikan full log event data ke downstream system.
  • Memisahkan logs berdasarkan pola akses ke dua log classes adalah pendekatan paling cost-effective. Infrequent Access class memiliki biaya ingestion lebih rendah (~50% lebih murah) tapi tidak mendukung semua fitur (misalnya subscription filters, Live Tail dibatasi). Logs yang sering di-query tetap di Standard class untuk fungsionalitas penuh.
  • Service Control Policies (SCPs) memberikan perlindungan terkuat karena diterapkan di level Organizations dan tidak bisa di-override oleh administrator di member accounts, termasuk yang memiliki AdministratorAccess policy. SCP bisa menggunakan kondisi pada resource ARN untuk menargetkan log groups spesifik.
  • CloudWatch Logs menggunakan envelope encryption. Service principal memerlukan kms:GenerateDataKey* untuk membuat data encryption key saat menulis logs, dan kms:Decrypt untuk membaca kembali (untuk fitur seperti filter patterns). IAM roles yang perlu membaca logs memerlukan kms:Decrypt untuk mendekripsi log data.
  • Log groups terpisah per tenant memungkinkan IAM policies yang membatasi akses berdasarkan log group ARN (arn:aws:logs:region:account:log-group:/app/tenant/{tenant_id}:*). Ini memberikan isolasi yang kuat dan auditable. Platform team bisa memiliki akses ke semua log groups.
  • AWS Lambda Advanced Logging Controls memungkinkan pengaturan log level di level fungsi (DEBUG, INFO, WARN, ERROR). Mengatur ke WARN akan mencegah DEBUG dan INFO logs dikirim ke CloudWatch Logs sama sekali, mengurangi ingestion costs langsung di source.
  • S3 Object Lock Compliance mode memberikan immutability yang dapat dibuktikan secara teknis — tidak ada user, termasuk root, yang bisa menghapus atau memodifikasi objek selama retention period. Dikombinasikan dengan CloudTrail evidence yang menunjukkan tidak ada PutLogEvents yang overwrote data, ini memberikan bukti terkuat.

Miskonsepsi & Jebakan Umum

  • Menyebut AWS-managed KMS yang tidak memenuhi syarat customer-managed key.
  • Menghapus log groups setelah export yang berisiko kehilangan data jika export gagal dan tidak memungkinkan query real-time.
  • Menggunakan satu log group yang sulit dikelola dan SSE-S3 bukan customer-managed KMS.
  • Tidak ada fitur automatic export bawaan di CloudWatch Logs — export harus dilakukan secara manual atau via API.
  • Tidak mendukung CloudWatch Logs sebagai source.
  • Berfungsi tapi memiliki keterbatasan: hanya satu export task per log group pada satu waktu, memerlukan maintenance Lambda, dan ada delay.
  • Tidak real-time dan tidak memberikan kemampuan query langsung dari CloudWatch console.
  • Memerlukan konfigurasi subscription filter di setiap source account yang bisa diubah admin lokal.
  • Memerlukan konfigurasi di source accounts dan tidak mencegah modifikasi oleh admin lokal.
  • Hanya menghasilkan numeric metrics dan alarm notifications — tidak meneruskan actual log event content ke Kinesis.
  • Bersifat batch dan memiliki delay, bukan real-time.
  • Mendeteksi deviasi dari baseline metrics, bukan pattern matching pada log content, dan tidak meneruskan log events.
  • Menambah kompleksitas dan menghilangkan kemampuan CloudWatch Logs Insights query.
  • Salah karena CloudWatch Logs sudah melakukan kompresi internal — pengguna tidak bisa mengirim data pre-compressed.
  • Menempatkan semua di Infrequent Access, yang membatasi kemampuan query untuk 10% logs yang sering diakses.
  • Bisa diubah oleh administrator dalam akun tersebut.
  • Berfungsi untuk masking sensitive data dalam logs, bukan untuk mencegah deletion log groups.
  • Bisa dimodifikasi oleh siapapun dengan permission logs:PutResourcePolicy.
  • Salah karena CloudWatch Logs memerlukan GenerateDataKey, bukan Encrypt langsung.
  • Terlalu permissive dan tidak membatasi decrypt access.
  • Memberikan Encrypt yang tidak diperlukan — CloudWatch Logs menggunakan GenerateDataKey untuk envelope encryption, bukan Encrypt.
  • Salah karena IAM permissions CloudWatch Logs tidak mendukung granularitas level log stream — permissions berlaku di level log group.
  • Menambah kompleksitas dan biaya (double ingestion) dan subscription filters memiliki limit per log group.
  • Tidak memberikan isolasi nyata — tenant dengan permission FilterLogEvents bisa melihat semua logs di log group.
  • Mengurangi storage costs tapi tidak ingestion costs — biaya terbesar biasanya ada di ingestion.
  • Tetap mengingestion semua logs — metric filters hanya memproses data yang sudah di-ingest.
  • Juga tidak mengurangi ingestion karena logs sudah masuk ke log group pertama sebelum difilter.
  • Mempertahankan versi tapi tidak mencegah deletion — delete markers bisa ditambahkan.
  • Bisa diubah kapan saja dan tidak memberikan bukti retroaktif.
  • Tidak mencegah manual deletion oleh administrator, hanya mencegah auto-deletion.
