Skill 4.4.2: CloudWatch Logs for audit

Summary

Skill this including in Domain 4: Security & Governance (Task 4.4: Prepare logs for audit), with fokus on cloudwatch logs for audit. Materi berikut merangkum service AWS that relevan along with concept important that needs kamu kuasai for topik this.

Key Services & Concepts

CloudWatch Logs
Pengumpulan & storage log; CloudWatch Logs Insights for query log.
Amazon CloudWatch
Monitoring metrik, alarm, and dashboard for source daya & application AWS.

Key Points

  • Naming convention /aws/glue/{environment}/{job-name} provides organisasi hierarkis that jelas. Retention 1827 days (≈5 years) memenuhi compliance requirement in a correct. CloudWatch Logs supports asosiasi customer-managed KMS key per log group uses API associate-kms-key.
  • Subscription filter to Firehose provides near real-time streaming to S3 with prefiks terstruktur automatically, minimal operational overhead, and not requires scheduled jobs. Firehose supports dynamic partitioning based on time.
  • CloudWatch cross-account observability enables monitoring account (sink) for melihat logs from source accounts (links) without menyalin data. When is managed via Organizations, configuration is applied in a terpusat and member accounts cannot memodifikasi sharing configuration. Source accounts still has access baca to logs mereka itself.
  • Subscription filters enables streaming real-time log events that suitable with pattern filter certain (such as "DataCorruptionException") directly to Kinesis Data Streams. This provides full log event data to downstream system.
  • Memisahkan logs based on pattern access to two log classes is approach most cost-effective. Infrequent Access class has cost ingestion lower (~50% cheaper) but not supports all feature (for example subscription filters, Live Tail is limited). Logs that often in-query still in Standard class for fungsionalitas full.
  • Service Control Policies (SCPs) provides perlindungan terkuat because is applied in level Organizations and cannot in-override by administrator in member accounts, including that has AdministratorAccess policy. SCP can uses condition on resource ARN for menargetkan log groups specific.
  • CloudWatch Logs uses envelope encryption. Service principal requires kms:GenerateDataKey* for creates data encryption key when writes logs, and kms:Decrypt for reads returns (for feature such as filter patterns). IAM roles that needs reads logs requires kms:Decrypt for mendekripsi log data.
  • Log groups separate per tenant enables IAM policies that limits access based on log group ARN (arn:aws:logs:region:account:log-group:/app/tenant/{tenant_id}:*). This provides isolasi that kuat and auditable. Platform team can has access to all log groups.
  • AWS Lambda Advanced Logging Controls enables configuration log level in level function (DEBUG, INFO, WARN, ERROR). Mengatur to WARN will prevents DEBUG and INFO logs is sent to CloudWatch Logs same at all, reduces ingestion costs directly in source.
  • S3 Object Lock Compliance mode provides immutability that can dibuktikan in a technical — there is no user, including root, that can deletes or memodifikasi object during retention period. Dikombinasikan with CloudTrail evidence that indicates there is no PutLogEvents that overwrote data, this provides bukti terkuat.

Common Misconceptions & Pitfalls

  • Menyebut AWS-managed KMS that not memenuhi syarat customer-managed key.
  • Deletes log groups after export that berisiko kehilangan data if export fails and not enables query real-time.
  • Uses one log group that difficult is managed and SSE-S3 not customer-managed KMS.
  • Not there is feature automatic export bawaan in CloudWatch Logs — export must is performed manually or via API.
  • Not supports CloudWatch Logs as source.
  • Berfungsi but has limitations: only one export task per log group on one time, requires maintenance Lambda, and there is delay.
  • Not real-time and not provides capabilities query directly from CloudWatch console.
  • Requires configuration subscription filter in each source account that can is changed admin local.
  • Requires configuration in source accounts and not prevents modifikasi by admin local.
  • Only produces numeric metrics and alarm notifications — not meneruskan actual log event content to Kinesis.
  • Bersifat batch and has delay, not real-time.
  • Mendeteksi deviasi from baseline metrics, not pattern matching on log content, and not meneruskan log events.
  • Adds complexity and eliminates capabilities CloudWatch Logs Insights query.
  • Incorrect because CloudWatch Logs already performs compression internal — user cannot sends data pre-compressed.
  • Places all in Infrequent Access, that limits capabilities query for 10% logs that often diakses.
  • Can is changed by administrator in akun said.
  • Berfungsi for masking sensitive data in logs, not for prevents deletion log groups.
  • Can dimodifikasi by siapapun with permission logs:PutResourcePolicy.
  • Incorrect because CloudWatch Logs requires GenerateDataKey, not Encrypt directly.
  • Too permissive and not limits decrypt access.
  • Provides Encrypt that not is required — CloudWatch Logs uses GenerateDataKey for envelope encryption, not Encrypt.
  • Incorrect because IAM permissions CloudWatch Logs not supports granularitas level log stream — permissions applies in level log group.
  • Adds complexity and cost (double ingestion) and subscription filters has limit per log group.
  • Not provides isolasi nyata — tenant with permission FilterLogEvents can melihat all logs in log group.
  • Reduces storage costs but not ingestion costs — cost terbesar usually there is in ingestion.
  • Tetap mengingestion all logs — metric filters only processes data that already in-ingest.
  • Also not reduces ingestion because logs already enters to log group first before difilter.
  • Mempertahankan versi but not prevents deletion — delete markers can is added.
  • Can is changed when only and not provides bukti retroaktif.
  • Not prevents manual deletion by administrator, only prevents auto-deletion.
