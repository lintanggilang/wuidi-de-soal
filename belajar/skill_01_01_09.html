Skill 1.1.9: Throttling and rate limits

throttlingratelimitsDynamoDBRDSKinesis

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.1: Perform data ingestion), dengan fokus pada throttling and rate limits. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon Kinesis Data Streams
Layanan streaming real-time terkelola; data dipartisi ke shard, urutan terjaga per shard via partition key.
Amazon DynamoDB
Database NoSQL key-value latensi rendah; skala horizontal, mendukung TTL dan Streams.
DynamoDB TTL
Menghapus item otomatis setelah timestamp kedaluwarsa tanpa biaya tambahan.
Amazon RDS
Relational database terkelola (PostgreSQL, MySQL, dll) untuk beban OLTP.

Poin-Poin Kunci

  • On-Demand capacity mode secara otomatis menyesuaikan kapasitas berdasarkan traffic aktual tanpa planning. Ini ideal untuk unpredictable workloads. Tidak ada throttling selama traffic tidak melebihi 2x previous peak.
  • Dengan 10 shards, total kapasitas adalah 10 MB/s write. Traffic 8 MB/s seharusnya cukup. Masalahnya adalah 60% records menggunakan partition key yang sama, sehingga satu shard menerima ~4.8 MB/s (melebihi 1 MB/s per shard limit). Solusinya adalah mendesain ulang partition key untuk distribusi merata.
  • Glue hashpartitions menentukan jumlah koneksi paralel ke database. Dengan menetapkan hashpartitions ke nilai di bawah max_connections (misalnya 50), Glue membatasi jumlah concurrent connections. Mengurangi workers juga mengurangi parallelism.
  • UnprocessedItems menunjukkan items yang gagal karena throttling. Best practice adalah retry hanya UnprocessedItems (bukan seluruh batch) dengan exponential backoff untuk memberikan waktu tabel recover. AWS SDK melakukan ini secara default.
  • KPL aggregation menggabungkan multiple user records menjadi satu Kinesis record, dramatically mengurangi jumlah API calls. Dengan 1,000 records/detik dan 5 shards (limit 1,000 records/shard/detik = 5,000 total), throttling mungkin terjadi karena hot partition. KPL juga memiliki built-in retry dan batching.
  • DynamoDB Export to S3 menggunakan PITR backup dan tidak mengonsumsi RCU tabel sama sekali. Ini memberikan zero impact pada production workload. Data diekspor ke S3 dalam format DynamoDB JSON atau ION dan bisa diquery dengan Athena.
  • API Gateway caching menyajikan responses dari cache tanpa memanggil Lambda atau DynamoDB. Dengan data yang hanya berubah setiap 5 menit, TTL 300 detik sangat efektif mengurangi backend calls hingga ~99% selama cache hit rate tinggi.
  • Step Functions Map state dengan MaxConcurrency=10 membatasi parallelism ke 10 iterations bersamaan. Dengan Wait state 1 detik di setiap iteration, ini menghasilkan ~10 requests/second yang sesuai rate limit. Ini scalable dan fault-tolerant.
  • Adaptive retry mode menggunakan token bucket algorithm untuk proaktif mengurangi request rate sebelum throttling terjadi, bukan hanya retry setelah failure. Ini mencegah thundering herd dan mengurangi total retry overhead. AWS SDK v2/v3 mendukung STANDARD, LEGACY, dan ADAPTIVE modes.
  • DynamoDB On-Demand memiliki initial throughput limit untuk tabel baru (dimulai dengan kapasitas terbatas dan scales berdasarkan traffic history). Jika full load dimulai langsung dengan throughput tinggi tanpa ramp-up, tabel belum punya history untuk scale. Solusinya adalah pre-warming (gradual increase) atau minta AWS Support untuk raise initial limits.

Miskonsepsi & Jebakan Umum

  • Memiliki delay 5-15 menit untuk merespons spike, sehingga masih bisa throttle selama ramp-up.
  • Mahal dan tetap bisa insufficient untuk spike tak terduga.
  • Hanya menangani retry tapi tidak menyelesaikan kapasitas.
  • Menambah shard tapi hot shard tetap menerima semua traffic yang sama.
  • Tidak relevan dengan throttling.
  • Valid tapi "without modifying the RDS instance" — RDS Proxy adalah komponen terpisah yang bisa ditambahkan.
  • Bisa menambah lebih banyak workers yang memperburuk masalah.
  • Tidak menyelesaikan connection limit.
  • BatchWriteItem sudah dibatasi 25 items per batch.
  • Membuang resources karena memproses ulang items yang sudah berhasil.
  • Mengurangi HTTP calls tapi masih 1 record = 1 Kinesis record.
  • Membantu tapi kurang sophisticated dibanding KPL.
  • Masih compete untuk RCU selama scan.
  • Tetap mengonsumsi RCU dari GSI yang bisa affect main table jika terjadi GSI backpressure.
  • Masih mengonsumsi RCU walaupun lebih terkontrol.
  • Mengurangi DynamoDB load tapi Lambda masih dipanggil setiap request (biaya compute).
  • Memiliki delay dan tetap costly untuk 50K rps sustained.
  • Timeout setelah 15 menit — 100K records × 01s = 2.7 jam.
  • Tidak bisa mengontrol exactly 10/second dari consumer side.
  • Tidak bisa mengontrol concurrency dengan presisi.
  • Kehilangan data dan menambah complexity.
  • Menambah biaya dan tidak menyelesaikan root cause.
  • Custom retry mungkin tidak lebih baik dari built-in adaptive mode.
  • Mempengaruhi DMS bukan DynamoDB throttling.
  • Salah — DMS kompatibel dengan On-Demand.
  • Salah — On-Demand mendukung batch writes.
