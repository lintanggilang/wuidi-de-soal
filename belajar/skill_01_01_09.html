Summary

Skill this including in Domain 1: Ingestion & Transformation (Task 1.1: Perform data ingestion), with fokus on throttling and rate limits. Materi berikut merangkum service AWS that relevan beserta concept important that needs kamu kuasai for topik this.

Key Services & Concepts

Amazon Kinesis Data Streams
Service streaming real-time managed; data is partitioned to shard, order maintained per shard via partition key.
Amazon DynamoDB
Database NoSQL key-value low latency; horizontal scaling, supports TTL and Streams.
DynamoDB TTL
Deletes item automatic setelah timestamp kedaluwarsa without cost additional.
Amazon RDS
Relational database managed (PostgreSQL, MySQL, dll) for beban OLTP.

Key Points

  • On-Demand capacity mode automatically adjusts capacity based on traffic aktual without planning. This is ideal for unpredictable workloads. Not ada throttling during traffic not melebihi 2x previous peak.
  • By 10 shards, total capacity is 10 MB/s write. Traffic 8 MB/s should quite. Masalahnya is 60% records uses partition key that same, so that satu shard receives ~4.8 MB/s (melebihi 1 MB/s per shard limit). Solusinya is mendesain ulang partition key for distribusi merata.
  • Glue hashpartitions determines number connection parallel to database. By sets hashpartitions to value in bawah max_connections (for example 50), Glue limits number concurrent connections. Reduces workers also reduces parallelism.
  • UnprocessedItems menunjukkan items that fails because throttling. Best practice is retry only UnprocessedItems (not entire batch) with exponential backoff for provides time table recover. AWS SDK performs this in a default.
  • KPL aggregation combines multiple user records menjadi satu Kinesis record, dramatically reduces number API calls. By 1,000 records/seconds and 5 shards (limit 1,000 records/shard/seconds = 5,000 total), throttling may occurs because hot partition. KPL also has built-in retry and batching.
  • DynamoDB Export to S3 uses PITR backup and not consumes RCU table same sekali. Ini provides zero impact on production workload. Data diekspor to S3 in format DynamoDB JSON or ION and can diquery with Athena.
  • API Gateway caching menyajikan responses from cache without calls Lambda or DynamoDB. By data that only changes each 5 minutes, TTL 300 seconds very effective reduces backend calls up to ~99% during cache hit rate high.
  • Step Functions Map state with MaxConcurrency=10 limits parallelism to 10 iterations simultaneously. By Wait state 1 seconds in each iteration, this produces ~10 requests/second that appropriate rate limit. Ini scalable and fault-tolerant.
  • Adaptive retry mode uses token bucket algorithm for proaktif reduces request rate before throttling occurs, not only retry setelah failure. Ini prevents thundering herd and reduces total retry overhead. AWS SDK v2/v3 supports STANDARD, LEGACY, and ADAPTIVE modes.
  • DynamoDB On-Demand has initial throughput limit for table new (dimulai with capacity limited and scales based on traffic history). If full load dimulai directly with high throughput without ramp-up, table not yet punya history for scale. Solusinya is pre-warming (gradual increase) or minta AWS Support for raise initial limits.

  • Adds shard but hot shard still receives all traffic that same.
  • Not relevan with throttling.
  • Valid but "without modifying the RDS instance" — RDS Proxy is komponen separate that can is added.
  • Can adds more workers that memperburuk problem.
  • Not solves connection limit.
  • BatchWriteItem already is limited 25 items per batch.
  • Membuang resources because processes ulang items that already succeeds.
  • Reduces HTTP calls but still 1 record = 1 Kinesis record.
  • Membantu but less sophisticated dibanding KPL.
  • Still compete for RCU during scan.
  • Tetap consumes RCU from GSI that can affect main table if occurs GSI backpressure.
  • Still consumes RCU even though more terkontrol.
  • Reduces DynamoDB load but Lambda still is called each request (cost compute).
  • Has delay and still costly for 50K rps sustained.
  • Timeout setelah 15 minutes — 100K records × 01s = 2.7 hours.
  • Not can mengontrol exactly 10/second from consumer side.
  • Not can mengontrol concurrency with presisi.
  • Kehilangan data and adds complexity.
  • Adds cost and not solves root cause.
  • Custom retry may not better from built-in adaptive mode.
