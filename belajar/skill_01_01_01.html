Domain 1: Ingestion & Transformation — Task 1.1: Perform data ingestion

Skill 1.1.1: Read data from streaming sources

KinesisMSKDynamoDBStreamsDMSGlueRedshiftstreaming

Ringkasan

Skill ini termasuk dalam Domain 1: Ingestion & Transformation (Task 1.1: Perform data ingestion), dengan fokus pada read data from streaming sources. Materi berikut merangkum layanan AWS yang relevan beserta konsep penting yang perlu kamu kuasai untuk topik ini.

Layanan & Konsep Utama

Amazon Kinesis Data Streams
Layanan streaming real-time terkelola; data dipartisi ke shard, urutan terjaga per shard via partition key.
Amazon MSK
Apache Kafka terkelola; cocok untuk streaming throughput tinggi dengan ekosistem Kafka.
MSK Connect
Menjalankan Kafka Connect connector secara fully managed (mis. S3 sink) tanpa mengelola infrastruktur.
DynamoDB Streams
Change data capture untuk perubahan item DynamoDB (insert/update/delete) secara real-time tanpa mengganggu tabel.
AWS DMS
Database Migration Service; migrasi full-load + CDC antar database, juga ke target seperti Kinesis/S3/Redshift.
AWS Glue
ETL serverless berbasis Spark + Data Catalog; ideal untuk transformasi dan katalogisasi data.
Amazon Redshift
Data warehouse berskala petabyte; mendukung COPY/UNLOAD, materialized view, dan streaming ingestion.
Redshift Streaming Ingestion
Konsumsi langsung dari Kinesis/MSK ke materialized view Redshift, latensi detik, tanpa staging S3.
Amazon DynamoDB
Database NoSQL key-value latensi rendah; skala horizontal, mendukung TTL dan Streams.

Poin-Poin Kunci

  • Amazon Kinesis Data Streams memastikan urutan per shard menggunakan partition key. Dengan menetapkan partition key ke trading symbol, semua event untuk simbol yang sama masuk ke shard yang sama, menjaga urutan. Kinesis juga dirancang untuk throughput tinggi dengan jutaan event per detik.
  • Amazon MSK Connect adalah solusi paling operasionally efisien untuk mengirim data dari MSK ke S3. MSK Connect adalah layanan fully managed yang menjalankan Kafka Connect connectors tanpa perlu mengelola infrastruktur. S3 sink connector sudah tersedia dan tinggal dikonfigurasi.
  • DynamoDB Streams menangkap perubahan data (inserts, updates, deletes) secara real-time tanpa mempengaruhi performa tabel produksi. Lambda sebagai consumer dapat memproses setiap perubahan dan memicu pipeline analytics ketika threshold tercapai.
  • AWS DMS mendukung CDC (Change Data Capture) dari Oracle sebagai source dan Kinesis Data Streams sebagai target endpoint. Ini adalah solusi paling terintegrasi dan managed untuk streaming change events ke Kinesis.
  • Setiap shard Kinesis mendukung hingga 1 MB/detik atau 1.000 records/detik untuk write. Berdasarkan throughput data: 5.000 records × 50 KB = 250.000 KB/detik = ~244 MB/detik. Berdasarkan volume: 244 MB / 1 MB per shard = 244 shards (dibulatkan ke 250). Berdasarkan jumlah records: 5.000 / 1.000 = 5 shards. Bottleneck ada pada throughput data (MB/s), sehingga minimal 250 shards diperlukan.
  • AWS Glue streaming ETL dapat mengonsumsi data dari MSK, melakukan lookup ke DynamoDB menggunakan DynamicFrame atau native Spark lookups, dan menulis ke Redshift. Ini adalah solusi paling scalable karena fully managed dan autoscaling.
  • Enhanced Fan-Out memberikan dedicated 2 MB/detik throughput per consumer per shard menggunakan HTTP/2 push (SubscribeToShard). Ini menghilangkan sharing throughput antar consumer dan memberikan latensi rata-rata ~70ms.
  • AWS Transfer Family menyediakan SFTP endpoint yang managed dan langsung menulis ke S3. S3 Event Notification memicu Lambda yang membaca CSV, mengubah ke format yang sesuai, dan menulis ke Kinesis Data Streams. Ini cocok karena source hanya bisa SFTP.
  • Kinesis Data Streams On-Demand mode secara otomatis menskalakan kapasitas berdasarkan throughput aktual tanpa perlu provisioning manual. Ini menghilangkan throttling tanpa perubahan kode producer.
  • Amazon Redshift Streaming Ingestion memungkinkan Redshift membaca langsung dari Amazon MSK (atau Kinesis) melalui materialized view, tanpa perlu staging di S3 atau ETL pipeline tambahan. Data tersedia dalam hitungan detik. Ini adalah solusi paling sederhana dengan minimal ETL complexity.

Miskonsepsi & Jebakan Umum

  • Memiliki batas throughput 3.000 pesan/detik per message group.
  • Bukan untuk ingestion berskala besar tapi untuk change data capture.
  • Dengan satu partisi tidak bisa scale.
  • Memiliki batas timeout 15 menit dan overhead cold start.
  • Bisa dilakukan tapi lebih mahal dan memiliki kompleksitas lebih untuk use case sederhana ini.
  • Memerlukan pengelolaan EC2 instances.
  • Memindai metadata schema bukan data aktual, dan tidak real-time.
  • Tidak bisa mendeteksi perubahan per-item secara granular.
  • Lebih cocok untuk migrasi atau replikasi berkelanjutan ke target lain, bukan untuk triggering logic.
  • Sangat kompleks dan tidak real-time.
  • Membutuhkan lisensi tambahan dan infrastruktur GoldenGate.
  • Tidak memiliki native CDC reader untuk Oracle redo logs secara streaming.
  • Memiliki batas concurrency dan timeout, serta Redshift Data API bersifat asynchronous yang menambah latensi.
  • Menggunakan Flink yang lebih kompleks, dan Redshift Streaming Ingestion hanya mendukung Kinesis/MSK langsung, bukan dari Flink.
  • Membutuhkan pengelolaan ECS dan JDBC connections ke Redshift.
  • Meningkatkan total throughput tapi consumer masih berbagi 2 MB/s per shard.
  • Hanya untuk scaling processing, bukan dedicated throughput.
  • Dibatasi 5 GetRecords calls/detik per shard shared antar semua consumer, dengan latensi lebih tinggi (~200-1000ms).
  • Tidak bisa membaca dari S3 secara streaming (hanya batch).
  • Tidak mendukung SFTP sebagai source endpoint.
  • Membutuhkan instalasi agent di on-premises dan tidak mendukung SFTP natively.
  • Hanya menangani retry tapi tidak menyelesaikan masalah kapasitas, dan membutuhkan perubahan kode.
  • Membutuhkan monitoring manual dan tetap bisa throttle jika traffic spike melebihi kapasitas baru.
  • Tidak berhubungan dengan throughput.
  • Membutuhkan konfigurasi connector dan management.
  • Menambahkan latensi karena buffering interval (minimum 60 detik) dan staging ke S3.
