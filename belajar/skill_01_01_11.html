Key Points

  • Best practice for replayability is stores raw data in immutable storage (S3) before processing. S3 berfungsi sebagai "source of truth" that can is used when saja for replay. Firehose mengarchive to S3 automatically.
  • S3 lifecycle policies optimizes cost based on umur data. Recent data in Standard (fast access), moderate in Glacier Instant Retrieval (millisecond access, lower cost), and old data in Deep Archive (cheapest). Date partitioning enables replay only days specific.
  • Uses natural unique key (for example order_id, transaction_id) sebagai partition key creates operasi idempotent. PutItem with key that same will overwrite record that already ada with data that identical — there is no duplikasi. Ini enables replay without cleanup.
  • Kafka stores messages in append-only immutable log. Messages not is deleted setelah consumed (different with traditional queues). Consumers melacak posisi (offset) mereka itself. Offset can in-reset to timestamp certain uses kafka-consumer-groups.sh --reset-offsets or API. Ini enables replay when saja in retention period.
  • Bronze layer in medallion pattern stores data mentah persis such as is received (raw, immutable). Append-only berarti data not pernah is changed or is deleted. Partisi based on time ingestion enables replay from periode time certain. Ini is prinsip main replayability — always simpan raw source data that not dimodifikasi.
  • Safe replayability requires tiga hal: (1) Deterministic logic — same input always produces same output, (2) Idempotent writes — avoids duplikasi saat replay (upsert by natural key), (3) Immutable source — data source not changes between replays. Kombinasi this guarantees output identical.
  • Firehose automatically delivers all Kinesis records to S3 with near-zero operational overhead. S3 sebagai replay source very cost-effective. Pipeline ETL didesain for can reads from Kinesis (real-time) or S3 (replay). S3 lifecycle policies deletes data setelah 30 days.
  • Staging table pattern (or DELETE+INSERT within transaction) is best practice for idempotent writes to Redshift. Langkahnya: (1) Load data to staging table, (2) Begin transaction, (3) DELETE existing records for time window from target, (4) INSERT from staging to target, (5) Commit. Replay will deletes data old and inserts that new.
  • If source data has window limited (7 days), pipeline kehilangan capabilities replay from source setelah window the said. For ensures replayability, raw responses HARUS is stored in S3 saat ingestion (capture at source). Ini is prinsip fundamental: if source can hilang, simpan salinan raw data.
  • Iceberg's branching (table branching) enables reprocessing in branch separate without affects main table that is read downstream consumers. Setelah validation, branch in-merge (fast-forward) to main. Time travel membantu identify correct snapshot. Ini is safe replay pattern.

Common Misconceptions & Pitfalls

  • For throughput not retention.
  • Only retain data 24 hours also.
  • Mahal and Kinesis still more costly dibanding S3.
  • Very expensive for 7 years × 500 GB/day (~1.2 PB).
  • Kinesis not supports 7-year retention (max 365 days).
  • Very expensive for cold storage.
  • Eliminates data that may still valid and not scalable approach.
  • Will menolak replay that justru diinginkan.
  • Creates each replay produces record new (duplikasi).
  • Perilaku default can "earliest" or "latest" depends config.
  • Mendeskripsikan traditional queue (SQS), not Kafka.
  • Not ada replay topic built-in.
  • Adalah feature data format not prinsip replay.
  • Adalah about code not data.
  • Only membantu ordering but not guarantees idempotency.
  • Membantu but not sufficient without idempotent writes.
  • Menghasilkan stale data if replay is required because bug fix.
  • Mahal for high-volume event storage.
  • Very expensive — extended retention dicharge per shard-hour.
  • On-demand mode for throughput not retention.
  • Not deletes logical duplicates.
  • Redshift not enforce uniqueness constraints.
  • Salah because API not punya data setelah 7 days.
  • AWS not stores third-party API responses.
  • Berisi processed data, not raw — cannot replay transformation.
  • Mempengaruhi downstream consumers during reprocessing.
  • Menyebabkan downtime and kehilangan history.
  • Deletes metadata not data correction.
