A data engineer is working on modeling data for a DynamoDB production database. To address certain access patterns for the application, the data engineer is in the process of creating secondary indexes.

Which of the following options should the data engineer consider for these requirements? (Select three)

Jawaban benar

Applications that need to perform many kinds of queries, using a variety of different attributes for their query criteria should use Global Secondary Indexes

A Global Secondary Index contains a selection of attributes from the base table which are organized by a primary key that is different from that of the table

If the writes are throttled on the Global Secondary Indexes, then the main table will be throttled, even though the Write Capacity Units on the main tables are fine

Karena

Opsi yang benar:

Aplikasi yang perlu melakukan banyak jenis query, menggunakan beragam attribute berbeda sebagai kriteria query, sebaiknya menggunakan Global Secondary Indexes - Beberapa aplikasi mungkin perlu melakukan banyak jenis query dengan beragam attribute sebagai kriteria query. Untuk mendukung kebutuhan ini, Anda dapat membuat satu atau beberapa global secondary index dan mengirimkan Query request terhadap index tersebut di Amazon DynamoDB.

Jika write di-throttle pada Global Secondary Indexes, maka main table juga akan di-throttle, meskipun Write Capacity Units pada main table sebenarnya masih mencukupi - Agar write ke sebuah table berhasil, pengaturan provisioned throughput untuk table dan seluruh global secondary index-nya harus memiliki write capacity yang cukup untuk menampung write tersebut. Jika tidak, write ke main table itu sendiri akan di-throttle.

Sebuah Global Secondary Index berisi sekumpulan attribute terpilih dari base table yang disusun berdasarkan primary key yang berbeda dari primary key table tersebut - Untuk mempercepat query pada attribute non-key, Anda dapat membuat global secondary index. Global secondary index berisi sekumpulan attribute terpilih dari base table, tetapi disusun berdasarkan primary key yang berbeda dari primary key table. Index key tidak harus memuat satu pun key attribute dari table. Index tersebut bahkan tidak harus memiliki key schema yang sama dengan table.

Opsi yang salah:

A Local Secondary Index maintains an alternate primary key for a given partition key value - Pernyataan ini tidak valid. Local secondary index mempertahankan alternate sort key untuk sebuah partition key value tertentu. Data pada local secondary index disusun berdasarkan partition key yang sama dengan base table tetapi dengan sort key yang berbeda.

Global secondary indexes support both data models - eventually consistent or strongly consistent reads - Pernyataan ini salah. Global secondary index hanya mendukung model data eventually consistent.

For greater query or scan flexibility, you can create up to twenty Local Secondary Indexes per table - Pernyataan ini tidak benar. Setiap table di DynamoDB dapat memiliki hingga 20 global secondary index (default quota) dan 5 local secondary index.

💡 Tips

Jika butuh query DynamoDB dengan banyak atribut berbeda maka pakai Global Secondary Index (GSI) karena GSI punya partition/sort key berbeda dari tabel; throttle di GSI bisa men-throttle tabel utama.Ingat index DynamoDB: GSI = key berbeda, bisa ditambah kapan saja, throughput terpisah; LSI = sort key beda, wajib saat create, pakai throughput tabel.

A company uses Amazon Redshift as its data warehouse solution. The company runs certain complex queries repeatedly over a large amount of data and hence uses Amazon Redshift materialized views. The company wants these materialized views to refresh automatically per a defined schedule.

Which of the following represents an optimal solution that can automate the process with the LEAST effort?

Jawaban benar

Create a schedule to refresh the materialized views with Amazon Redshift query editor v2

Karena

Opsi yang benar:

Buat jadwal untuk me-refresh materialized view dengan Amazon Redshift query editor v2

Dalam lingkungan data warehouse, aplikasi sering kali harus menjalankan query yang kompleks pada table berukuran besar. Contohnya adalah statement SELECT yang melakukan multi-table join dan agregasi pada table yang berisi miliaran baris. Memproses query seperti ini bisa sangat mahal, baik dari sisi system resource maupun waktu yang dibutuhkan untuk menghitung hasilnya.

Materialized view di Amazon Redshift menyediakan cara untuk mengatasi masalah ini. Sebuah materialized view berisi result set yang sudah dihitung sebelumnya, berdasarkan sebuah query SQL atas satu atau beberapa base table. Anda dapat mengirimkan statement SELECT untuk melakukan query terhadap materialized view, sama seperti ketika melakukan query pada table atau view lain di database. Amazon Redshift mengembalikan hasil yang sudah dihitung sebelumnya dari materialized view tanpa perlu mengakses base table sama sekali. Dari sudut pandang pengguna, hasil query dikembalikan jauh lebih cepat dibandingkan jika mengambil data yang sama dari base table.

Materialized views in Amazon Redshift: via - https://docs.aws.amazon.com/redshift/latest/dg/materialized-view-overview.html

Anda dapat membuat jadwal untuk menjalankan sebuah statement SQL guna me-refresh materialized view dengan Amazon Redshift query editor v2. Anda membuat jadwal agar statement SQL dijalankan pada interval waktu yang sesuai dengan kebutuhan bisnis Anda. Ketika tiba waktunya query terjadwal berjalan, query tersebut dimulai oleh Amazon EventBridge dan menggunakan Amazon Redshift Data API.

Untuk menjadwalkan query, AWS Identity and Access Management (IAM) user yang mendefinisikan jadwal serta IAM role yang terkait dengan jadwal tersebut harus dikonfigurasi dengan IAM permission untuk menggunakan Amazon EventBridge dan Amazon Redshift Data API.

Opsi yang salah:

You can set auto-refresh for materialized views using CREATE MATERIALIZED VIEW - Amazon Redshift dapat secara otomatis me-refresh materialized view dengan data terbaru dari base table-nya saat materialized view dibuat atau diubah dengan mengaktifkan opsi autorefresh. Amazon Redshift melakukan auto-refresh pada materialized view secepat mungkin setelah terjadi perubahan pada base table. Namun, kita ingin materialized view di-refresh sesuai jadwal, bukan setiap kali base table berubah. Karena itu, opsi ini tidak tepat untuk use case yang diberikan.

Configure an Amazon EventBridge to trigger an AWS Lambda function based on the defined schedule. The Lambda function will call the Amazon Redshift Data API to refresh the materialized views - Langkah-langkah ini dijalankan secara internal oleh Amazon Redshift query editor v2 ketika Anda menjadwalkan sebuah query. Secara operasional, lebih efisien memanfaatkan opsi Redshift query editor v2.

Materialized views cannot be refreshed automatically and need a manual refresh - Pernyataan ini salah dan hanya diberikan sebagai distraktor.

💡 Tips

Jika refresh materialized view Redshift terjadwal dengan effort minim maka buat schedule di Query Editor v2 karena penjadwalan bawaan tanpa infrastruktur tambahan.Ingat: MV Redshift bisa auto-refresh atau dijadwal via Query Editor v2 (serverless scheduler).

The database should be resilient with minimal operational overhead and require the least development effort. The application includes a device tracking system that stores the GPS data for all devices. Real-time IoT data, as well as metadata lookups, must be performed with high throughput and microsecond latency.

Which of the following options would you recommend as the MOST efficient solution for these requirements?

Jawaban benar

Use DynamoDB as the database with DynamoDB Accelerator (DAX)

Karena

Opsi yang benar:

Gunakan DynamoDB sebagai database dengan DynamoDB Accelerator (DAX)

Amazon DynamoDB adalah database key-value dan document yang memberikan performa single-digit millisecond pada skala berapa pun. DynamoDB merupakan database NoSQL yang fully managed, multi-region, multi-master, dan durable, dengan fitur security bawaan, backup and restore, serta in-memory caching untuk aplikasi berskala internet.

Amazon DynamoDB Accelerator (DAX) adalah in-memory cache untuk DynamoDB yang fully managed dan highly available, yang memberikan peningkatan performa hingga 10x – dari milidetik menjadi mikrodetik – bahkan pada jutaan request per detik. DAX menangani seluruh pekerjaan berat yang diperlukan untuk menambahkan akselerasi in-memory ke table DynamoDB Anda, tanpa mengharuskan developer mengelola cache invalidation, pengisian data, atau cluster management.

DAX Overview: via - https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DAX.concepts.html

Biasanya, response time DynamoDB dapat diukur dalam single-digit millisecond. Use case tertentu membutuhkan response time dalam mikrodetik. Untuk use case seperti ini, DynamoDB Accelerator (DAX) memberikan response time yang cepat untuk mengakses data yang eventually consistent. Selain itu, DAX mengurangi kompleksitas operasional dan aplikasi dengan menyediakan layanan managed yang API-compatible dengan DynamoDB. Oleh karena itu, hanya diperlukan perubahan fungsional minimal untuk menggunakannya pada aplikasi yang sudah ada. Karena itu, inilah opsi yang benar.

via - https://docs.amazonaws.cn/en_us/amazondynamodb/latest/developerguide/DAX.html

A company has an S3 bucket that contains files in two different folders - s3://my-bucket/images and s3://my-bucket/thumbnails. When an image is first uploaded and new, it is viewed several times. Post a detailed analysis, the data analytics team has noticed that after 45 days those image files are rarely requested, but the thumbnails still are. After 180 days, the company would like to archive the image files and the thumbnails. Overall, the company would like the solution to remain highly available to prevent disasters from happening against the entire AZ.

Which of the following represents the best-fit solutions for an efficient cost strategy for the given S3 bucket? (Select two)

Jawaban benar

Create a Lifecycle Policy to transition objects to S3 Standard IA using a prefix after 45 days

Create a Lifecycle Policy to transition all objects to Glacier Deep Archive after 180 days

Karena

Opsi yang benar:

Untuk mengelola S3 object Anda agar tersimpan secara hemat biaya sepanjang lifecycle-nya, konfigurasikan Amazon S3 Lifecycle-nya. Sebuah konfigurasi S3 Lifecycle adalah sekumpulan aturan yang mendefinisikan action yang diterapkan Amazon S3 pada sekelompok object. Ada dua jenis action:

Transition action — Mendefinisikan kapan object berpindah ke storage class lain. Misalnya, Anda dapat memilih untuk memindahkan object ke storage class S3 Standard-IA 30 hari setelah dibuat, atau mengarsipkan object ke storage class S3 Glacier Deep Archive satu tahun setelah dibuat.

Expiration action — Mendefinisikan kapan object kedaluwarsa. Amazon S3 akan menghapus object yang kedaluwarsa atas nama Anda.

Buat Lifecycle Policy untuk memindahkan object ke S3 Standard IA menggunakan prefix setelah 45 hari

S3 Standard-IA diperuntukkan bagi data yang lebih jarang diakses tetapi membutuhkan akses cepat saat diperlukan. S3 Standard-IA menawarkan durability tinggi, throughput tinggi, dan latency rendah seperti S3 Standard, dengan harga penyimpanan per GB yang rendah serta biaya retrieval per GB. Kombinasi biaya rendah dan performa tinggi ini menjadikan S3 Standard-IA ideal untuk penyimpanan jangka panjang, backup, dan sebagai data store untuk file disaster recovery. Biaya minimum durasi penyimpanan adalah 30 hari.

Seperti disebutkan pada use case, setelah 45 hari, file gambar jarang diminta, tetapi thumbnail-nya masih sering diminta. Jadi Anda perlu menggunakan prefix saat mengonfigurasi Lifecycle Policy agar hanya object di s3://my-bucket/images yang dipindahkan ke Standard IA, bukan semua object di bucket.

Buat Lifecycle Policy untuk memindahkan semua object ke Glacier Deep Archive setelah 180 hari

Amazon S3 Glacier Deep Archive adalah storage class cloud Amazon S3 yang aman, durable, dan sangat murah untuk pengarsipan data serta backup jangka panjang. Storage class ini dirancang untuk memberikan durability 99,999999999% dan menyediakan kemampuan security serta compliance yang komprehensif untuk membantu memenuhi persyaratan regulasi yang paling ketat sekalipun.

Opsi yang salah:

Create a Lifecycle Policy to transition all objects to S3 Standard IA after 45 days - Seperti dibahas di atas, Anda perlu menggunakan prefix saat mengonfigurasi Lifecycle Policy agar hanya object di s3://my-bucket/images yang dipindahkan ke Standard IA, bukan semua object di bucket.

Create a Lifecycle Policy to transition objects to Glacier Deep Archive using a prefix after 180 days - Setelah 180 hari, Anda dapat memindahkan semua object ke storage Glacier Deep Archive sesuai use case. Glacier Deep Archive tidak membutuhkan prefix untuk use case yang diberikan.

Create a Lifecycle Policy to transition objects to S3 One Zone IA using a prefix after 45 days - S3 Standard-IA diperuntukkan bagi data yang lebih jarang diakses tetapi membutuhkan akses cepat saat diperlukan. S3 Standard-IA menawarkan durability tinggi, throughput tinggi, dan latency rendah seperti S3 Standard, dengan harga penyimpanan per GB yang rendah serta biaya retrieval per GB. Kombinasi biaya rendah dan performa tinggi ini menjadikan S3 Standard-IA ideal untuk penyimpanan jangka panjang, backup, dan sebagai data store untuk file disaster recovery. Biaya minimum durasi penyimpanan adalah 30 hari.

S3 One Zone-IA diperuntukkan bagi data yang lebih jarang diakses tetapi membutuhkan akses cepat saat diperlukan. Berbeda dengan S3 Storage Class lain yang menyimpan data di minimal tiga Availability Zone (AZ), S3 One Zone-IA menyimpan data di satu AZ saja dan biayanya 20% lebih murah dari S3 Standard-IA. Biaya minimum durasi penyimpanan adalah 30 hari.

Terakhir, S3 One Zone IA tidak akan menawarkan availability yang dibutuhkan jika sebuah AZ mengalami gangguan.

💡 Tips

Jika image >45 hari jarang diakses (thumbnail tetap sering) & arsip >180 hari, tetap HA maka Lifecycle: Standard-IA (prefix image) 45 hari + Glacier Deep Archive 180 hari karena Standard-IA tetap multi-AZ (HA) dan prefix membatasi ke image.Ingat: One Zone-IA = 1 AZ (bukan HA); Standard-IA = multi-AZ.

A gaming company maintains a staging environment for its flagship application which uses a DynamoDB table to keep track of the gaming history of the players. This data needs to be kept for only a week and then it can be deleted. The IT manager has noticed that the table has several months of data in the table. The company wants to implement a cost-effective solution to keep only the latest week's data in the table.

Which of the following solutions requires the MINIMUM development effort and ongoing maintenance?

Jawaban benar

Add a new attribute in the table to track the expiration time and enable time to live (TTL) on the table

Karena

Opsi yang benar:

Tambahkan attribute baru pada table untuk melacak waktu kedaluwarsa dan aktifkan time to live (TTL) pada table

Anda dapat menggunakan DynamoDB Time to Live (TTL) untuk menentukan kapan sebuah item sudah tidak diperlukan lagi. TTL menggunakan timestamp per-item untuk menentukan item yang akan kedaluwarsa. Tak lama setelah tanggal dan waktu timestamp yang ditentukan, DynamoDB menghapus item tersebut dari table Anda tanpa mengonsumsi write throughput apa pun. Setelah Anda mengaktifkan TTL pada sebuah table, sebuah proses background scanner per-partition secara otomatis dan terus-menerus mengevaluasi status kedaluwarsa item pada table.

via - https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html

via - https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/howitworks-ttl.html

Opsi yang salah:

Add a new attribute in the table to track the expiration time and set up a Glue job to delete items that are more than a week old - Meskipun solusi ini layak, hal ini akan membutuhkan upaya pengembangan yang besar untuk membangun dan memelihara Glue job guna memangkas table DynamoDB. Ada pula biaya tambahan untuk menjalankan Glue job secara harian.

Add a created_at attribute in the table and then use a cron job on the EC2 instance to invoke a Python script daily. The script deletes items older than a week on the basis of this attribute - Melakukan provisioning EC2 instance dan mengembangkan script Python memerlukan upaya pengembangan, pemeliharaan, serta biaya tambahan yang signifikan. Jadi opsi ini tidak benar.

Add a created_at attribute in the table and then use a CloudWatch Events rule to invoke a Lambda function daily. The Lambda function deletes items older than a week on the basis of this attribute - Custom code perlu ditulis untuk Lambda function guna mengimplementasikan fungsionalitas memangkas table DynamoDB. Eksekusi Lambda function juga dikenai biaya terpisah. Jadi opsi ini tidak benar.

💡 Tips

Jika data DynamoDB cukup disimpan 1 minggu lalu hapus, maintenance minim maka pakai TTL karena TTL menghapus item kedaluwarsa otomatis gratis.Ingat: hapus data berdasar umur di DynamoDB → TTL (atribut epoch detik).

A CRM company has a software as a service (SaaS) application that feeds updates to other in-house and third-party applications. The SaaS application and the in-house applications are being migrated to use AWS services for this inter-application communication.

Which of the following would you suggest to asynchronously decouple the architecture?

Jawaban benar

Use Amazon EventBridge to decouple the system architecture

Karena

Opsi yang benar:

Gunakan Amazon EventBridge untuk melakukan decoupling pada arsitektur sistem

Baik Amazon EventBridge maupun Amazon SNS dapat digunakan untuk mengembangkan aplikasi event-driven, tetapi untuk use case ini, EventBridge adalah pilihan yang tepat.

Amazon EventBridge direkomendasikan ketika Anda ingin membangun aplikasi yang bereaksi terhadap event dari aplikasi SaaS dan/atau layanan AWS. Amazon EventBridge adalah satu-satunya layanan berbasis event yang terintegrasi langsung dengan partner SaaS pihak ketiga. Amazon EventBridge juga secara otomatis meng-ingest event dari lebih dari 90 layanan AWS tanpa mengharuskan developer membuat resource apa pun di akun mereka. Lebih lanjut, Amazon EventBridge menggunakan struktur berbasis JSON yang terdefinisi untuk event dan memungkinkan Anda membuat rule yang diterapkan pada seluruh body event untuk memilih event yang akan diteruskan ke sebuah target. Amazon EventBridge saat ini mendukung lebih dari 15 layanan AWS sebagai target, termasuk AWS Lambda, Amazon SQS, Amazon SNS, Amazon Kinesis Streams, dan Firehose, di antara lainnya. Saat peluncuran, Amazon EventBridge memiliki throughput terbatas (lihat Service Limits) yang dapat ditingkatkan atas permintaan, dengan latency umum sekitar setengah detik.

How Amazon EventBridge works: via - https://aws.amazon.com/eventbridge/

Opsi yang salah:

Use Amazon Simple Notification Service (Amazon SNS) to communicate between systems and decouple the architecture - Seperti dibahas di atas, Amazon SNS dapat digunakan untuk layanan berbasis event. Namun, use case yang diberikan membutuhkan integrasi dengan layanan SaaS pihak ketiga, sehingga Amazon EventBridge adalah pilihan yang tepat, karena Amazon SNS tidak mendukung integrasi layanan pihak ketiga.

Use Amazon Simple Queue Service (Amazon SQS) to decouple the architecture - Amazon SQS adalah layanan message queuing dari Amazon dan bekerja dengan baik untuk melakukan decoupling pada aplikasi. Namun layanan ini tidak terintegrasi langsung dengan layanan SaaS pihak ketiga.

Use Elastic Load Balancing (ELB) for effective decoupling of system architecture - Elastic Load Balancing (ELB) menawarkan decoupling aplikasi yang sinkron, yang tidak tepat untuk use case saat ini.

💡 Tips

Jika decouple antar-aplikasi (SaaS → banyak app) secara asinkron maka pakai Amazon EventBridge karena EventBridge event bus merutekan event ke banyak target dengan filter.Ingat decouple: EventBridge = routing event/integrasi SaaS; SNS = pub/sub fan-out; SQS = antrian point-to-point.
