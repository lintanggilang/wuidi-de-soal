A data engineering team is building a new data lake on AWS. They need to create a technical catalog that stores metadata for 500 tables across 10 databases. The catalog must support schema information, partition details, SerDe configurations, and be queryable by Athena, EMR Spark, Redshift Spectrum, and Glue ETL jobs. Which approach creates the MOST operationally efficient technical data catalog?
  • A. Deploy a self-managed Apache Hive metastore on an EC2 instance with a MySQL backend, configure all services to connect to it via thrift protocol
  • B. Create separate metadata stores for each service — Athena's internal catalog, EMR's Hive metastore, Redshift's own external schema definitions — and synchronize them with a custom Lambda function
  • C. Store all table metadata in a DynamoDB table and build custom API gateways for each service to read metadata from DynamoDB before executing queries with their column schemas and S3 locations
  • D. Use the AWS Glue Data Catalog as the centralized metastore. Create databases using the Glue API or console, define tables with their column schemas, SerDe properties, input/output formats, and S3 locations. The Glue Data Catalog is natively integrated with Athena, EMR (as Hive metastore replacement), Redshift Spectrum (via external schemas), and Glue ETL — all services reference the same catalog automatically without additional configuration per service
Jawaban Benar: D
The Glue Data Catalog is AWS's managed metastore service designed exactly for this use case: (1) serverless — no infrastructure to provision, patch, or scale; (2) native integration with the four major analytics services means creating a table once in the catalog makes it instantly available to all services; (3) supports all required metadata: column schemas with data types, partition keys and values, SerDe classes (OpenCSVSerDe, ParquetHiveSerDe, etc.), input/output formats, and S3 locations; (4) API-driven (CreateDatabase, CreateTable, GetPartitions) enables programmatic catalog management from ETL pipelines; (5) Hive-compatible interface means EMR Spark/Hive can use it as a drop-in Hive metastore replacement.

Opsi A: SALAH. Self-managed Hive metastore requires EC2 instances (availability, patching, scaling), MySQL backend (backup, HA), and manual integration with Athena/Spectrum (which natively use Glue Catalog); operational overhead is significantly higher.
Opsi B: SALAH. Separate metadata stores create synchronization challenges (drift, inconsistency), multiply management effort by 4×, and don't provide a single source of truth.
Opsi C: SALAH. Custom DynamoDB + API Gateway reimplements what Glue Catalog already provides, without native service integrations; every query requires a custom metadata fetch step — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: BENAR.

A data engineer needs to register a new partitioned Parquet table in the Glue Data Catalog. The data is stored in S3 at s3://data-lake/sales/year=2024/month=01/day=15/. The table has columns: order_id (bigint), customer_id (string), amount (decimal(10,2)), order_time (timestamp), and is partitioned by year, month, and day. Which Glue Data Catalog API call with the correct parameters creates this table definition?
  • A. Call CreateTable API specifying: DatabaseName, TableInput with Name, StorageDescriptor (Columns for non-partition columns with their data types, Location pointing to s3://data-lake/sales/, InputFormat as org.apache.hadoop.hive.ql.io.parquet.MapredParquetInputFormat, OutputFormat as org.apache.hadoop.hive.ql.io.parquet.MapredParquetOutputFormat, SerdeInfo with SerializationLibrary as org.apache.hadoop.hive.ql.io.parquet.serde.ParquetHiveSerDe), and PartitionKeys array defining year, month, day columns separately from the regular columns
  • B. Call CreateTable with partition columns included in the StorageDescriptor.Columns array alongside regular columns, and set PartitionKeys to an empty array
  • C. Call CreatePartition for each year/month/day combination, which automatically creates the parent table definition with Name
  • D. Call CreateTable with Location pointing to a specific partition path (s3://data-lake/sales/year=2024/month=01/day=15/) and let Glue infer the partition structure automatically
Jawaban Benar: A
The Glue CreateTable API requires proper separation of regular columns and partition keys: (1) StorageDescriptor.Columns lists only NON-partition columns (order_id, customer_id, amount, order_time) with their Hive-compatible data types; (2) PartitionKeys is a SEPARATE array listing the partition columns (year, month, day) — these must NOT appear in StorageDescriptor.Columns; (3) Location points to the TABLE ROOT (s3://data-lake/sales/), not individual partition paths — Glue appends partition key=value paths automatically; (4) InputFormat/OutputFormat/SerDe specify Parquet-specific classes that all integrated services recognize. After table creation, partitions are registered separately via BatchCreatePartition or discovered by a crawler.

Opsi A: BENAR.
Opsi B: SALAH. Including partition columns in StorageDescriptor.Columns with empty PartitionKeys creates a non-partitioned table; queries would not benefit from partition pruning and Glue wouldn't recognize the Hive-style directory structure.
Opsi C: SALAH. CreatePartition requires an existing table — you cannot create partitions without first creating the table definition; partitions are child records of a table — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: SALAH. Pointing Location to a specific partition path makes the table "see" only one partition's data; the table location must be the root path containing all partitions.
3
An organization migrating from an on-premises Hadoop cluster to AWS needs to move their existing Apache Hive metastore (containing 3,000 table definitions, 500,000 partitions, and custom SerDe configurations) to the AWS Glue Data Catalog. The Hive metastore uses a MySQL backend. Which migration approach preserves all metadata with MINIMUM data loss and operational disruption?
  • A. Run SHOW CREATE TABLE for each Hive table, convert the DDL to Athena-compatible DDL, and execute it in the Athena console to populate the Glue Catalog
  • B. Use the AWS Glue Catalog Migration utility (aws-glue-catalog-migration tool) which reads from the existing Hive metastore's MySQL backend and creates equivalent databases, tables, partitions, and SerDe configurations in the Glue Data Catalog. The tool handles Hive-to-Glue type mapping, partition batch creation (BatchCreatePartition for efficiency), and preserves custom SerDe class references and table properties
  • C. Export the Hive metastore MySQL database using mysqldump and import it into an RDS MySQL instance, then configure Glue to read from this RDS instance as its backend
  • D. Manually recreate each of the 3,000 tables in the Glue console, then run crawlers against the S3 data to rediscover partitions for efficiency)
Jawaban Benar: B
The Glue Catalog migration tool is purpose-built for Hive metastore migration: (1) it connects directly to the Hive metastore's database (MySQL/PostgreSQL), reads all metadata in bulk, and creates equivalent Glue Catalog entries; (2) handles 500,000 partitions efficiently using batch APIs (BatchCreatePartition processes 100 partitions per call vs. individual CreatePartition calls); (3) preserves SerDe configurations, table properties (TBLPROPERTIES), column statistics, and custom classifications; (4) maps Hive data types to Glue Catalog types with known compatibility; (5) provides a migration report showing successfully migrated vs. failed entries.

Opsi A: SALAH. Converting 3,000 Hive DDL statements to Athena DDL is partially viable but doesn't handle: (1) partition migration (500,000 partitions would require MSCK REPAIR TABLE or individual ALTER TABLE ADD PARTITION calls), (2) some Hive SerDe classes not supported in Athena DDL syntax, (3) custom table properties that DDL doesn't capture.
Opsi B: BENAR.
Opsi C: SALAH. Glue Data Catalog has its own managed backend storage; you cannot substitute an RDS instance as the Glue Catalog's storage layer — it's not architecturally supported.
Opsi D: SALAH. Manually recreating 3,000 tables is impractical and error-prone; crawlers might not recreate the exact schema definitions (column names, types, SerDe configurations) that were manually tuned in the original Hive metastore — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
4
A data platform team manages the Glue Data Catalog across three AWS accounts (development, staging, production). When a data engineer creates or modifies a table definition in development, the same change must be promoted to staging and then production through a review process. They need version control and promotion workflows for catalog metadata. Which approach provides the MOST robust catalog metadata lifecycle management?
  • A. Manually export table definitions from development using GetTable API, review the JSON output, and import to staging/production using CreateTable/UpdateTable APIs
  • B. Define all catalog resources (databases, tables, partitions) as AWS CloudFormation templates or Terraform configurations stored in a Git repository. Changes are made as pull requests, reviewed by the team, then deployed through CI/CD pipelines to each environment in sequence (dev → staging → prod). Each environment's Glue Catalog is managed entirely through Infrastructure-as-Code, ensuring identical definitions across environments and providing full version history through Git
  • C. Set up Glue Data Catalog replication between accounts using AWS Database Migration Service to synchronize metadata changes automatically and providing full version history through Git
  • D. Use the Glue Data Catalog's built-in table versioning feature to track changes across accounts and promote specific versions between environments
Jawaban Benar: B
Infrastructure-as-Code (IaC) for catalog management provides enterprise-grade lifecycle management: (1) Git history provides complete audit trail of who changed what, when, and why; (2) pull request reviews ensure catalog changes are validated before production deployment; (3) identical CloudFormation/Terraform templates guarantee consistent definitions across all environments — no configuration drift; (4) rollback capability: revert a Git commit to undo problematic catalog changes; (5) CI/CD pipelines can include validation steps (schema compatibility checks, naming convention enforcement) before deployment. This is the industry standard for managing infrastructure across environments.

Opsi A: SALAH. Manual export/import works for one-off changes but doesn't scale to frequent changes across 500+ tables; no review process, no rollback, no version history, high human error risk.
Opsi B: BENAR.
Opsi C: SALAH. DMS replicates data between databases, not Glue Catalog metadata; there is no DMS connector for Glue Data Catalog — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini. Automatic replication would also bypass review processes, potentially pushing untested changes to production.
Opsi D: SALAH. Glue Catalog versioning tracks table-level version history within a SINGLE account, not across accounts; it doesn't provide cross-account promotion workflows or peer review processes.

An EMR cluster running Apache Spark needs to use an external Apache Hive metastore (running on RDS MySQL) instead of the AWS Glue Data Catalog. This is required because the company uses Hive-specific features (Hive ACID tables, materialized views, storage handlers) that are not fully supported by the Glue Data Catalog. How should the EMR cluster be configured to use the external Hive metastore?
  • A. Install the Hive metastore thrift service on a separate EC2 instance and configure EMR to connect to it via the hive.metastore.uris property pointing to thrift://ec2-instance:9083
  • B. Configure EMR to use both the Glue Data Catalog and external Hive metastore simultaneously, routing queries to the appropriate metastore based on database name prefixes
  • C. Export the Hive metastore schema from RDS into the Glue Data Catalog using a migration tool and use Glue Catalog with Hive compatibility mode enabled and javax for authentication
  • D. Configure the EMR cluster with the hive-site classification at launch, setting javax.jdo.option.ConnectionURL to the RDS MySQL endpoint, javax.jdo.option.ConnectionDriverName to the MySQL JDBC driver, and javax.jdo.option.ConnectionUserName/Password for authentication. This directs Hive and Spark's catalog operations to the external MySQL-backed metastore instead of the default Glue Data Catalog
Jawaban Benar: D
Direct JDBC connection to the RDS MySQL backend is the standard configuration for EMR with external Hive metastore: (1) the hive-site classification in EMR configurations allows setting all Hive metastore connection properties at cluster launch; (2) javax.jdo.option.ConnectionURL points to the RDS MySQL endpoint (jdbc:mysql://rds-endpoint:3306/hive_metastore); (3) EMR's Hive and Spark use JDO (Java Data Objects) via DataNucleus to connect directly to the metastore's relational backend; (4) this supports ALL Hive metastore features including ACID tables, materialized views, and custom storage handlers that Glue Catalog may not support; (5) to disable Glue Catalog, ensure the EMR cluster is launched WITHOUT the "Use Glue Data Catalog" option.

Opsi A: SALAH. While thrift-based connection (hive.metastore.uris) works, it requires running a separate Hive Metastore Service (HMS) on EC2, adding infrastructure to manage; direct JDBC connection from EMR to RDS is simpler when only EMR needs metastore access.
Opsi B: SALAH. EMR does not natively support dual metastore routing; Hive/Spark connect to a single metastore at a time. While Spark can register multiple catalogs, the primary Hive metastore integration is single-endpoint.
Opsi C: SALAH. Migration to Glue defeats the requirement; the company specifically needs external Hive metastore features NOT supported by Glue — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: BENAR.
6
A data pipeline adds 10,000 new partition entries to a Glue Data Catalog table daily (hourly data, 400+ source systems). The pipeline currently calls CreatePartition individually for each new partition, and the process takes 45 minutes due to API throttling (Glue catalog API rate limits). How should the team optimize partition registration to minimize time and avoid throttling?
  • A. Replace individual CreatePartition calls with BatchCreatePartition API, which registers up to 100 partitions per call. This reduces the required API calls from 10,000 to 100, dramatically reducing execution time and eliminating throttling. Additionally, implement exponential backoff with jitter for any throttled requests, and consider using GetPartitions with expression filters before batch creation to avoid duplicate partition errors
  • B. Use MSCK REPAIR TABLE in Athena to discover and register all new partitions automatically
  • C. Request an AWS Service Quotas increase for Glue Data Catalog API rate limits to allow 10,000 requests per second with BatchCreatePartition API and eliminating throttling
  • D. Switch to partition projection in Athena to eliminate the need for registering partitions in the catalog entirely
Jawaban Benar: A
BatchCreatePartition is the optimal solution for high-volume partition registration: (1) batching 100 partitions per API call reduces API traffic by 100× (10,000 calls → 100 calls); (2) each batch is atomic — all 100 partitions in a batch either succeed or the response identifies which individual partitions failed; (3) exponential backoff with jitter handles any residual throttling gracefully; (4) pre-checking with GetPartitions avoids AlreadyExistsException errors in the batch; (5) total time drops from 45 minutes to under 1 minute. This is the standard pattern for ETL pipelines that generate many partitions.

Opsi A: BENAR.
Opsi B: SALAH. MSCK REPAIR TABLE lists ALL partition-formatted directories in S3 and compares against the catalog; for a table with 100,000+ existing partitions, this process scans the entire S3 prefix structure and takes longer than 45 minutes; it's also unreliable for very large partition counts.
Opsi C: SALAH. While quota increases help, they don't address the fundamental inefficiency of 10,000 individual API calls; batching is always preferred regardless of rate limits — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: SALAH. Partition projection eliminates the catalog partition entries but only works for Athena queries; other services (Glue ETL, EMR Spark, Redshift Spectrum) still need physical partition entries in the catalog. Also, projection doesn't work if partition values don't follow a predictable pattern.

A company's Glue Data Catalog has grown to 5,000 tables across 50 databases. They discover that many tables have incorrect or outdated metadata — wrong column data types (string instead of timestamp), missing partition definitions, and stale S3 locations pointing to deleted paths. This causes query failures and incorrect results. How should the team implement systematic catalog quality management?
  • A. Delete the entire catalog and re-run crawlers against all S3 locations to rebuild the catalog from scratch for the specified InputFormat
  • B. Use Amazon CloudWatch alarms to detect when Athena queries fail due to catalog metadata issues and notify the data team to fix individual issues
  • C. Implement a catalog validation pipeline that programmatically uses the Glue GetTable/GetPartitions APIs to check: (1) S3 locations exist and contain data (HEAD object calls); (2) column data types match actual Parquet/ORC schema (compare catalog types vs. file schema); (3) partition entries point to non-empty S3 prefixes; (4) SerDe configurations are valid for the specified InputFormat. Generate a quality report and use UpdateTable API to fix or deprecate invalid entries. Schedule this validation weekly via Step Functions
  • D. Add IAM policies preventing anyone from modifying catalog table definitions after initial creation to prevent metadata drift
Jawaban Benar: C
Programmatic catalog validation provides systematic quality assurance: (1) GetTable retrieves current metadata for comparison against actual data; (2) S3 existence checks (ListObjects on the table location) detect stale references to deleted data; (3) reading Parquet/ORC file schemas and comparing against catalog column definitions identifies type mismatches (the file says timestamp, catalog says string); (4) partition validation ensures all registered partitions have corresponding data; (5) UpdateTable programmatically fixes correctable issues (type corrections, location updates); (6) weekly scheduling via Step Functions catches drift before it causes widespread query failures. This is a proactive, scalable approach to catalog governance.

Opsi A: SALAH. Deleting and rebuilding the catalog loses manually-configured metadata (descriptions, custom properties, access policies, Lake Formation permissions) and causes service disruption; crawlers may also recreate incorrect types if data is ambiguous — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: SALAH. Reactive alerting (wait for failure, then fix) means problems impact users before they're detected; proactive validation catches issues before queries fail, providing a better user experience.
Opsi C: BENAR.
Opsi D: SALAH. Preventing modifications prevents legitimate schema evolution, new partition registration by ETL pipelines, and catalog maintenance; metadata must be updatable to remain accurate.

A data engineering team needs to manage the Glue Data Catalog for a multi-account data lake where Account A (producer) creates and maintains table definitions, and Accounts B, C, D (consumers) need to query these tables via Athena and Redshift Spectrum. Each consumer should see the producer's tables as if they were local catalog entries. How should cross-account catalog access be configured?
  • A. Configure a Glue Data Catalog resource policy in Account A granting cross-account access, then have consumers directly reference the producer's catalog ID in their Athena queries using catalog_id parameter
  • B. Set up AWS DMS to replicate the Glue Data Catalog metadata from Account A to Accounts B, C, and D periodically
  • C. In the producer account (A), use Lake Formation to grant table-level permissions (SELECT, DESCRIBE) to consumer account IDs. In each consumer account, create resource links pointing to the producer's shared tables. The resource links appear as local catalog entries in the consumer's databases — Athena and Spectrum query them using local schema references while data access is governed by the producer's Lake Formation permissions
  • D. Create IAM cross-account roles in Account A and have consumer Athena assume those roles to access the producer's catalog and S3 data configured for optimal performance and minimal operational overhead
Jawaban Benar: C
Lake Formation cross-account sharing with resource links is the recommended pattern: (1) Lake Formation GRANT specifies exactly which tables each consumer account can access — fine-grained control; (2) resource links in consumer accounts create local catalog references (CREATE TABLE resource_link ... TARGET TABLE ...) that point to the producer's tables; (3) consumers query using their local catalog namespace (SELECT * FROM my_db.shared_table) — no need to reference foreign catalog IDs; (4) the producer retains full control — can revoke access, add column-level restrictions, or modify permissions without consumer coordination; (5) CloudTrail audit in both accounts tracks access. This is AWS's recommended architecture for cross-account data lake access.

Opsi A: SALAH. Catalog resource policies with direct cross-account catalog ID references work but provide coarser access control (database/table level without column filtering) and require consumers to use the catalog_id syntax which complicates queries and doesn't work with all services.
Opsi B: SALAH. DMS cannot replicate Glue Data Catalog metadata; there's no DMS source/target connector for the catalog.
Opsi C: BENAR.
Opsi D: SALAH. Cross-account IAM roles work for S3 access but don't provide catalog-native discovery; consumers must know exact table structures and can't browse the producer's catalog through their own catalog interface — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A Glue Data Catalog table was incorrectly updated by an ETL job that changed column data types (e.g., changed "order_date" from "date" to "string"), causing downstream Athena queries to return incorrect results. The team discovers the issue 3 days later and needs to revert the table definition to its previous correct state. Which Glue Data Catalog feature enables reverting to a previous table definition?
  • A. Use AWS CloudTrail to find the UpdateTable API call from 3 days ago and reverse its parameter changes manually
  • B. Delete the incorrectly-defined table and re-run the original Glue crawler to recreate the table definition from the underlying data files
  • C. Restore the Glue Data Catalog from an AWS Backup recovery point created before the incorrect update with their timestamps
  • D. Use the Glue Data Catalog's built-in table versioning. Every UpdateTable call creates a new version while preserving the previous version. Call GetTableVersions to list all historical versions with their timestamps, identify the correct version (before the erroneous update), then call UpdateTable with the StorageDescriptor and column definitions from the correct historical version to restore the table to its previous state
Jawaban Benar: D
Glue Data Catalog automatically versions tables: (1) every CreateTable, UpdateTable, or crawler update creates a new version entry in the catalog; (2) GetTableVersions returns the complete history with version IDs, timestamps, and full table definitions (including StorageDescriptor, columns, SerDe, properties); (3) to revert: call GetTableVersion for the known-good version, extract its TableInput, and pass it to UpdateTable — the table definition is restored; (4) this is a metadata-only operation that takes effect immediately for all services referencing the table. The version history provides a clear audit trail of when changes occurred.

Opsi A: SALAH. CloudTrail shows the API parameters but requires manual extraction and reconstruction of the UpdateTable request; this is error-prone compared to using the built-in versioning which preserves complete table definitions ready for restoration.
Opsi B: SALAH. Re-running a crawler might recreate the table with the SAME incorrect types if the crawler's type inference is ambiguous (crawlers sometimes infer string for date columns in certain formats); also, deleting the table removes version history, Lake Formation permissions, and custom properties.
Opsi C: SALAH. AWS Backup does not support Glue Data Catalog as a backup resource; there's no backup/restore mechanism for the catalog through AWS Backup — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: BENAR.

A data platform team wants to programmatically manage their Glue Data Catalog using the Glue API. They need to: (1) list all tables in a specific database matching a name pattern, (2) retrieve partition information for date-based filtering, and (3) check table properties for custom metadata tags. Which combination of Glue API calls provides this capability MOST efficiently?
  • A. Use ListTables to get all table names, then call GetTable individually for each one to filter by name pattern in application code, then call GetPartitions without filters and filter the results client-side
  • B. Use Athena INFORMATION_SCHEMA queries (SELECT * FROM information_schema.tables WHERE table_name LIKE '%pattern%') to retrieve catalog metadata programmatically
  • C. Use GetTables with DatabaseName and Expression filter (regex pattern) to list matching tables. Use GetPartitions with Expression parameter (e.g., "year='2024' AND month='03'") to retrieve only matching partitions without listing all partitions. Access table properties through the Parameters field in the GetTable response's TableInput.StorageDescriptor and TableInput.Parameters maps
  • D. Use SearchTables API for text-based search across all databases, GetPartitionIndexes for filtered partition retrieval, and GetTags for custom metadata tags with DatabaseName and Expression filter (regex pattern) to list matching tables
Jawaban Benar: C
These Glue API calls are optimized for server-side filtering: (1) GetTables with Expression applies regex filtering server-side — only matching tables are returned, reducing response size and eliminating client-side filtering for large databases; (2) GetPartitions with Expression applies a SQL-like filter (supporting =, >, <, AND, OR on partition key values) server-side — for a table with 100,000 partitions, filtering "year='2024' AND month='03'" returns only ~31 partitions instead of paginating through all 100,000; (3) custom metadata is stored in the table's Parameters map (key-value pairs set during CreateTable/UpdateTable) — no separate API call needed since GetTable/GetTables responses include Parameters. This minimizes API calls and response sizes.

Opsi A: SALAH. Client-side filtering requires paginating through all tables/partitions, consuming more API calls (throttling risk) and more time; server-side filtering is always preferred.
Opsi B: SALAH. INFORMATION_SCHEMA in Athena provides basic table/column metadata but doesn't expose custom table properties (Parameters), has limited partition information, and requires running Athena queries (cost, latency) for what should be API metadata lookups.
Opsi C: BENAR.
Opsi D: SALAH. SearchTables provides text search across all databases but doesn't support regex; GetPartitionIndexes creates/manages partition indexes (for accelerating GetPartitions) but doesn't retrieve partition data; GetTags retrieves Lake Formation tags (LF-Tags), which are different from custom table properties in Parameters — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
