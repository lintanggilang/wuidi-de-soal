Skill 1.4.8: Use Infrastructure as Code (IaC) for Repeatable Resource Deployment

AWS CloudFormation and AWS CDK for consistent, repeatable data infrastructure deployment

1
A data engineering team updates a CloudFormation stack that manages their Redshift cluster. The update changes the ClusterType from single-node to multi-node and modifies the NodeType. During the update, CloudFormation shows the resource will be "replaced" rather than "modified in-place." What should the team understand about this behavior and how should they proceed safely?
  • A. Use a CloudFormation change set to preview the replacement behavior before execution. If Redshift requires replacement, ensure a snapshot exists, add a DeletionPolicy: Snapshot to the resource, and verify that dependent resources (security groups, IAM roles) will correctly reference the new cluster after replacement
  • B. Proceed with the update immediately since CloudFormation always handles replacements gracefully without data loss
  • C. Cancel the update and manually resize the cluster through the console instead
  • D. Delete the stack and recreate it with the new configuration to avoid replacement complexity
Jawaban Benar: A
Change sets preview exactly what CloudFormation will do — Add, Modify, Replace, or Delete each resource. For stateful resources like Redshift, "Replace" means the old cluster is deleted and a new one created. DeletionPolicy: Snapshot ensures a snapshot is taken before the old cluster is destroyed, enabling recovery. Verifying dependent resources prevents broken references after the new cluster gets a different endpoint. Opsi B — replacement of data stores CAN cause data loss if DeletionPolicy isn't configured properly. Opsi C — manual changes create drift between template and reality. Opsi D — deleting the entire stack destroys all resources unnecessarily and causes extended downtime.
2
A data platform uses CDK to define infrastructure. The CDK app contains a stack with an S3 bucket (data lake), Glue database, crawlers, and jobs. The engineer runs cdk synth followed by cdk deploy. During deployment, a Glue job fails to create because the IAM role referenced doesn't exist yet. What CDK concept resolves this dependency issue?
  • A. CDK automatically resolves dependencies when you pass construct references between resources (e.g., pass role object to the Glue job's role property). CDK generates the correct DependsOn in the synthesized CloudFormation template. If manual ordering is needed, use addDependency() method to explicitly declare dependencies
  • B. Deploy resources in separate stacks in the correct order manually
  • C. Add sleep() calls between resource definitions in the CDK code
  • D. Run cdk deploy multiple times until all resources eventually exist
Jawaban Benar: A
CDK uses construct references to automatically infer deployment order. When you write: glue_job = GlueJob(role=my_iam_role), CDK recognizes that the Glue job depends on the IAM role and generates the DependsOn clause in CloudFormation. This ensures resources are created in the correct order. For cases where implicit dependencies aren't detected, addDependency() explicitly states "create resource A before resource B." Opsi B — separating into stacks adds unnecessary complexity; within a single stack, CDK handles ordering. Opsi C — CDK code defines infrastructure declaratively; sleep() in CDK code would execute during synthesis, not deployment. Opsi D — repeated deployments are unreliable and don't solve the underlying dependency problem.

A company has two CloudFormation stacks: a "Data Lake" stack containing S3 buckets and Glue databases, and a "Pipeline" stack containing Glue jobs that need to reference the S3 bucket ARN and Glue database name from the Data Lake stack. The Pipeline stack is deployed after the Data Lake stack. What is the CORRECT way to share these values between stacks?
  • A. In the Data Lake stack, define Outputs with Export names for the S3 bucket ARN and Glue database name. In the Pipeline stack, use Fn::ImportValue with the export names to reference these cross-stack values. CloudFormation validates that exported values exist before the importing stack deploys
  • B. Hardcode the S3 bucket ARN and database name in the Pipeline stack template
  • C. Use SSM Parameter Store to manually copy values between stacks after each deployment
  • D. Pass values as Parameters every time the Pipeline stack is deployed
Jawaban Benar: A
CloudFormation cross-stack references (Outputs with Export + Fn::ImportValue) provide a managed way to share values between stacks. CloudFormation prevents the exporting stack from being deleted or modified in a way that would break importing stacks. This creates a dependency graph between stacks. The Pipeline stack automatically receives the correct S3 ARN and database name without hardcoding. Opsi B — hardcoded values break when resources are recreated with new ARNs/names. Opsi C — manual copying is error-prone and adds operational overhead. Opsi D — passing parameters manually requires the operator to know current values and is error-prone during frequent deployments.
4
A data engineer needs to create an AWS Glue Data Catalog database and register an initial set of tables as part of their CloudFormation deployment. However, CloudFormation doesn't natively support running Glue Crawler during stack creation (crawlers are long-running operations). The engineer needs tables registered immediately upon deployment. Which approach enables this within CloudFormation?
  • A. Use a CloudFormation Custom Resource backed by a Lambda function. The Lambda function is invoked during stack creation, runs the Glue Crawler or directly creates catalog tables via the Glue API (create_table), and reports success/failure back to CloudFormation via the response URL
  • B. Define the Glue Crawler as a standard CloudFormation resource and set a DependsOn to wait for it to complete its crawl
  • C. Run the crawler manually after the stack deploys and hope tables exist before downstream resources need them
  • D. Define all table schemas statically in the template using AWS::Glue::Table resources without ever running a crawler
Jawaban Benar: A
Custom Resources execute arbitrary logic during CloudFormation lifecycle events (Create, Update, Delete). A Lambda-backed custom resource can start a Glue Crawler, poll for completion, then create tables directly if needed. The cfn-response mechanism tells CloudFormation whether the operation succeeded, maintaining the stack's create/rollback semantics. This extends CloudFormation's capabilities beyond its native resource types. Opsi B — CloudFormation creates the crawler resource but doesn't RUN it; DependsOn only ensures the crawler is created, not that it has completed a crawl. Opsi C — manual intervention breaks automation and may cause race conditions with dependent resources. Opsi D — while valid for known schemas, this doesn't work when table schemas must be discovered from data at deployment time.
5
A team deploys their data pipeline infrastructure using CDK. After running cdk deploy, the deployment fails midway through creating 10 resources (5 were created successfully, 5 failed). The team needs to understand the rollback behavior. What happens to the successfully created resources when a CDK/CloudFormation deployment fails?
  • A. By default, CloudFormation performs automatic rollback — it deletes the 5 successfully created resources and returns the stack to its previous state (or DELETE_COMPLETE for new stacks). This ensures atomic deployments: either all resources are created or none are. The --no-rollback flag can be used during development to preserve created resources for debugging
  • B. CloudFormation keeps the 5 successfully created resources and marks the stack as partially complete
  • C. CloudFormation pauses and waits for manual intervention to decide what to do with existing resources
  • D. CDK automatically retries the failed resources three times before giving up
Jawaban Benar: A
CloudFormation's default behavior is all-or-nothing (atomic) deployment. If any resource fails to create, CloudFormation rolls back by deleting all resources created during that operation, returning to the previous known-good state. The stack enters ROLLBACK_COMPLETE or UPDATE_ROLLBACK_COMPLETE status. For new stacks, all resources are removed. The --no-rollback or DisableRollback option preserves resources for debugging but should only be used in development. Opsi B — partial deployment contradicts CloudFormation's atomic design principle. Opsi C — CloudFormation doesn't pause for manual decisions during creation; it's automatic. Opsi D — CDK doesn't add retry logic; it relies on CloudFormation's native behavior.
6
A data engineering team manages a large CloudFormation template (3000+ lines) that defines their entire data platform: VPC, S3 buckets, Glue jobs, EMR cluster, Redshift, and Lambda functions. The template is difficult to maintain and deployments take 45 minutes. Template changes have a large blast radius. Which architectural pattern BEST improves maintainability?
  • A. Decompose into nested stacks using AWS::CloudFormation::Stack resources: a networking stack (VPC), a storage stack (S3, Glue catalog), a compute stack (EMR, Redshift), and a pipeline stack (Glue jobs, Lambda). The parent stack orchestrates nested stacks, passing parameters between them for resource references
  • B. Keep the single template but add more comments for readability
  • C. Split into completely independent stacks with no shared resources or references
  • D. Convert the template to CDK but keep all resources in a single CDK stack
Jawaban Benar: A
Nested stacks decompose a monolithic template into focused, maintainable modules while maintaining a single deployment unit. Each nested stack handles one concern (networking, storage, compute). The parent stack passes outputs from one nested stack as parameters to another, maintaining resource references. Updates to one nested stack don't affect others unless their outputs change. This reduces blast radius while preserving cross-resource references. Opsi B — comments don't reduce deployment time or blast radius. Opsi C — completely independent stacks with no references make it impossible to share VPC, security groups, or IAM roles between resources that need them. Opsi D — CDK in a single stack still has the same blast radius and long deployment time; the monolith issue persists.
7
A company wants to deploy the same data pipeline infrastructure to both us-east-1 (primary) and eu-west-1 (DR). Some resources like S3 bucket names must be globally unique, and certain services (like Redshift Serverless) have different feature availability across regions. The team uses a single CloudFormation template. How should the template handle region-specific differences?
  • A. Use CloudFormation Conditions combined with AWS::Region pseudo-parameter to conditionally include or exclude resources per region. Use Mappings to define region-specific values (AMI IDs, instance types). For globally unique names, incorporate AWS::Region in resource names via Fn::Sub (e.g., ${AWS::AccountId}-${AWS::Region}-data-lake)
  • B. Create two separate templates with hardcoded region-specific values
  • C. Deploy the template without changes and manually fix region-specific failures afterward
  • D. Use only services available in all regions and avoid region-specific features
Jawaban Benar: A
Conditions (e.g., IsPrimary: !Equals [!Ref "AWS::Region", "us-east-1"]) enable/disable resources per region. Mappings provide lookup tables for region-specific values without parameters. Pseudo-parameters like AWS::Region and AWS::AccountId enable unique naming without hardcoding. This single template adapts to any region at deploy time. Fn::Sub makes string interpolation readable: "arn:aws:s3:::${AWS::AccountId}-${AWS::Region}-datalake". Opsi B — duplicate templates diverge and double maintenance effort. Opsi C — manual fixes break IaC principles and aren't repeatable. Opsi D — unnecessarily limiting functionality reduces the solution's capabilities.
8
A data engineer runs cdk deploy and the deployment succeeds. Two days later, another team member makes changes to the same CDK app and runs cdk deploy. The deploy fails because the synthesized CloudFormation template conflicts with manual changes someone made to the deployed resources via the console. How should the team prevent this situation?
  • A. Enable CloudFormation drift detection on the stack and run it before each deployment. Implement an AWS Config rule that detects changes not originating from CloudFormation. Use IAM policies that restrict console-level modifications to production resources (only allowing changes through the CI/CD pipeline with CloudFormation)
  • B. Always run cdk destroy and cdk deploy instead of updating the existing stack
  • C. Accept that drift will happen and manually fix conflicts as they arise
  • D. Add a README telling team members not to make console changes
Jawaban Benar: A
Multi-layered prevention works best: drift detection identifies existing drift before it causes deployment failures. AWS Config rules provide real-time alerting when manual changes occur. Restrictive IAM policies are the strongest control — if users can't modify resources via console, drift can't occur. Service Control Policies (SCPs) can enforce this at the organization level. Together, these ensure IaC remains the single source of truth. Opsi B — destroying and recreating causes data loss for stateful resources and extended downtime. Opsi C — accepting drift normalizes bad practices and makes deployments increasingly unreliable. Opsi D — documentation without enforcement doesn't prevent human error.

A team needs to deploy a complex data pipeline with an EMR cluster that takes 15 minutes to provision. CloudFormation's default creation timeout causes the stack to fail before EMR finishes provisioning. The team also needs CloudFormation to verify that the EMR cluster is healthy (not just created) before proceeding to deploy dependent Glue jobs. Which mechanism addresses both concerns?
  • A. Use CreationPolicy with a cfn-signal from a bootstrap action on the EMR master node. The bootstrap action signals CloudFormation after the cluster passes health checks. Set a Timeout in the CreationPolicy to accommodate the 15-minute startup. CloudFormation waits for the signal before marking the resource as complete and proceeding to dependent resources
  • B. Add a WaitCondition after the EMR resource with a fixed 20-minute timeout
  • C. Set a DependsOn attribute on the Glue jobs pointing to the EMR resource
  • D. Increase the stack-level timeout to 60 minutes and hope EMR finishes in time
Jawaban Benar: A
CreationPolicy with cfn-signal provides application-level readiness verification. The EMR bootstrap action runs after the cluster starts, performs health checks (e.g., verifying YARN is accepting jobs), then sends a success signal via cfn-signal. CloudFormation won't mark the EMR resource as CREATE_COMPLETE until the signal arrives or timeout occurs. This guarantees dependent resources (Glue jobs) are only created after EMR is truly ready, not just provisioned. Opsi B — WaitCondition with fixed timeout is a blunt instrument that always waits the full duration regardless of when EMR becomes ready. Opsi C — DependsOn only ensures CloudFormation creates EMR before Glue jobs, but "created" doesn't mean "healthy and ready." Opsi D — there is no stack-level timeout setting; CloudFormation waits indefinitely for resources by default.

A data engineer uses the CDK to deploy a Glue ETL pipeline. After initial deployment, the engineer modifies the Glue job script path in the CDK code. Running cdk diff shows the change will update the Glue job in-place. However, the engineer is concerned about the impact on currently running jobs. How does CloudFormation handle updates to running Glue jobs, and what precaution should be taken?
  • A. Run cdk diff to verify the change is an in-place update (not replacement). CloudFormation updates the Glue job configuration, but currently running executions continue with the old script until they complete. New executions use the updated script. As a precaution, implement the update during a maintenance window when no jobs are running, or use Glue job versioning with bookmarks to ensure data consistency
  • B. CloudFormation immediately terminates all running Glue jobs to apply the update
  • C. The update fails if any Glue job execution is currently running
  • D. CDK automatically creates a new Glue job with a different name and deletes the old one
Jawaban Benar: A
cdk diff (equivalent to a change set preview) shows exactly what will happen — update, replace, or delete. For Glue jobs, script path changes are in-place updates: CloudFormation modifies the job definition without affecting running executions. Running jobs continue with their original configuration. New runs pick up the updated script. Best practice is to deploy during maintenance windows to avoid version confusion, and use job bookmarks to track processing state across script changes. Opsi B — CloudFormation doesn't terminate running Glue job executions; it only updates the job definition. Opsi C — Glue job definition updates succeed regardless of running executions. Opsi D — script path changes don't trigger replacement; CDK/CloudFormation updates the existing job resource.
