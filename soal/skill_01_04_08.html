#CloudFormation#CDK
A team deploys their data pipeline infrastructure using CDK. After running cdk deploy, the deployment fails midway through creating 10 resources (5 were created successfully, 5 failed). The team needs to understand the rollback behavior. What happens to the successfully created resources when a CDK/CloudFormation deployment fails?
  • A. CloudFormation pauses and waits for manual intervention to decide what to do with existing resources, validating and cleansing each record before delivery and meeting the latency and throughput goals of the design and transforming records into the required target format and applying schema conversion and enrichment inline and handling the described workload reliably at scale
  • B. By default, CloudFormation performs automatic rollback — it deletes the 5 successfully created resources and returns the stack to its previous state (or DELETE_COMPLETE for new stacks). This ensures atomic deployments: either all resources are created or none are. The --no-rollback flag can be used during development to preserve created resources for debugging
  • C. CDK automatically retries the failed resources three times before giving up, validating and cleansing each record before delivery and meeting the latency and throughput goals of the design and handling the described workload reliably at scale and applying schema conversion and enrichment inline and transforming records into the required target format
  • D. CloudFormation keeps the 5 successfully created resources and marks the stack as partially complete for new stacks), applying schema conversion and enrichment inline and validating and cleansing each record before delivery and integrating natively with the rest of the pipeline and transforming records into the required target format and optimizing cost for the described workload
Jawaban Benar: B
CloudFormation's default behavior is all-or-nothing (atomic) deployment. If any resource fails to create, CloudFormation rolls back by deleting all resources created during that operation, returning to the previous known-good state. The stack enters ROLLBACK_COMPLETE or UPDATE_ROLLBACK_COMPLETE status. For new stacks, all resources are removed. The --no-rollback or DisableRollback option preserves resources for debugging but should only be used in development.

Opsi A: SALAH. CloudFormation doesn't pause for manual decisions during creation; it's automatic.
Opsi B: BENAR.
Opsi C: SALAH. CDK doesn't add retry logic; it relies on CloudFormation's native behavior.
Opsi D: SALAH. Partial deployment contradicts CloudFormation's atomic design principle — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A data engineering team manages a large CloudFormation template (3000+ lines) that defines their entire data platform: VPC, S3 buckets, Glue jobs, EMR cluster, Redshift, and Lambda functions. The template is difficult to maintain and deployments take 45 minutes. Template changes have a large blast radius. Which architectural pattern BEST improves maintainability?
  • A. Decompose into nested stacks using AWS::CloudFormation::Stack resources: a networking stack (VPC), a storage stack (S3, Glue catalog), a compute stack (EMR, Redshift), and a pipeline stack (Glue jobs, Lambda). The parent stack orchestrates nested stacks, passing parameters between them for resource references
  • B. Keep the single template but add more comments for readability, meeting the latency and throughput goals of the design and satisfying all of the stated requirements with minimal effort and validating and cleansing each record before delivery and applying schema conversion and enrichment inline
  • C. Split into completely independent stacks with no shared resources or references, meeting the latency and throughput goals of the design and transforming records into the required target format and validating and cleansing each record before delivery and applying schema conversion and enrichment inline
  • D. Convert the template to CDK but keep all resources in a single CDK stack and a pipeline stack (Glue jobs, Lambda) for resource references, applying schema conversion and enrichment inline and handling the described workload reliably at scale and minimizing end-to-end processing latency
Jawaban Benar: A
Nested stacks decompose a monolithic template into focused, maintainable modules while maintaining a single deployment unit. Each nested stack handles one concern (networking, storage, compute). The parent stack passes outputs from one nested stack as parameters to another, maintaining resource references. Updates to one nested stack don't affect others unless their outputs change. This reduces blast radius while preserving cross-resource references.

Opsi A: BENAR.
Opsi B: SALAH. Comments don't reduce deployment time or blast radius.
Opsi C: SALAH. Completely independent stacks with no references make it impossible to share VPC, security groups, or IAM roles between resources that need them.
Opsi D: SALAH. CDK in a single stack still has the same blast radius and long deployment time; the monolith issue persists — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A company wants to deploy the same data pipeline infrastructure to both us-east-1 (primary) and eu-west-1 (DR). Some resources like S3 bucket names must be globally unique, and certain services (like Redshift Serverless) have different feature availability across regions. The team uses a single CloudFormation template. How should the template handle region-specific differences?
  • A. Use CloudFormation Conditions combined with AWS::Region pseudo-parameter to conditionally include or exclude resources per region. Use Mappings to define region-specific values (AMI IDs, instance types). For globally unique names, incorporate AWS::Region in resource names via Fn::Sub (e.g., ${AWS::AccountId}-${AWS::Region}-data-lake)
  • B. Deploy the template without changes and manually fix region-specific failures afterward, removing the need to provision or patch any infrastructure and durably storing every event with built-in fault tolerance and validating and cleansing each record before delivery
  • C. Create two separate templates with hardcoded region-specific values, reducing day-to-day operational effort and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and providing exactly-once processing semantics
  • D. Use only services available in all regions and avoid region-specific features with AWS::Region pseudo-parameter for globally unique names, durably storing every event with built-in fault tolerance and applying schema conversion and enrichment inline and reducing day-to-day operational effort
Jawaban Benar: A
Conditions (e.g., IsPrimary: !Equals [!Ref "AWS::Region", "us-east-1"]) enable/disable resources per region. Mappings provide lookup tables for region-specific values without parameters. Pseudo-parameters like AWS::Region and AWS::AccountId enable unique naming without hardcoding. This single template adapts to any region at deploy time. Fn::Sub makes string interpolation readable: "arn:aws:s3:::${AWS::AccountId}-${AWS::Region}-datalake".

Opsi A: BENAR.
Opsi B: SALAH. Manual fixes break IaC principles and aren't repeatable.
Opsi C: SALAH. Duplicate templates diverge and double maintenance effort.
Opsi D: SALAH. Unnecessarily limiting functionality reduces the solution's capabilities — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
