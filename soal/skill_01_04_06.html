A data engineer is building a serverless data ingestion pipeline using AWS SAM. The pipeline consists of a Lambda function triggered by an S3 event that processes CSV files, transforms data, and writes results to DynamoDB. The engineer needs to define all resources in a single SAM template. Which SAM template structure correctly defines this architecture?
  • A. Use Transform: AWS::CloudFormation-2010-09-09 and define all resources using standard CloudFormation resource types without SAM transforms, reducing day-to-day operational effort and transforming records into the required target format and handling the described workload reliably at scale
  • B. Use Transform: AWS::Serverless-2016-10-31, define the Lambda function as AWS::Serverless::Function with an S3 event source (Events property with Type: S3 and Properties specifying bucket and event type s3:ObjectCreated:*), and define the DynamoDB table as AWS::Serverless::SimpleTable
  • C. Define the Lambda function without any Events property and create a separate AWS::S3::BucketNotification resource manually, running as a fully managed service with minimal operational overhead and reducing day-to-day operational effort and keeping steady-state operating costs low
  • D. Use AWS::Serverless::Api as the event source for the Lambda function since all SAM triggers must go through API Gateway with an S3 event source (Events property with Type: S3, reducing day-to-day operational effort
Correct Answer: B
SAM requires the Transform: AWS::Serverless-2016-10-31 header to enable SAM resource types. AWS::Serverless::Function with an S3 Events property automatically creates the S3 bucket notification, Lambda permission, and event mapping — reducing boilerplate significantly. AWS::Serverless::SimpleTable creates a DynamoDB table with minimal configuration.

Option A: INCORRECT. Using the CloudFormation transform instead of SAM transform means SAM resources won't be recognized.
Option B: CORRECT.
Option C: INCORRECT. Manually creating bucket notifications defeats the purpose of SAM's simplified event source definitions.
Option D: INCORRECT. SAM supports multiple event types (S3, SQS, Kinesis, Schedule, etc — although its description sounds convincing, in a fundamental still not appropriate for requirements this.), not just API Gateway.

A data engineer has developed a serverless ETL pipeline locally using SAM. The pipeline includes a Lambda function with Python dependencies (pandas, pyarrow) specified in a requirements.txt file. The engineer needs to package and deploy the application. Which sequence of SAM CLI commands correctly builds, packages, and deploys the application?
  • A. Run sam package first, then sam build, then sam deploy and installs dependencies into for deployment parameters on first run), handling the described workload reliably at scale
  • B. Run sam build (compiles code and installs dependencies into .aws-sam/build), then sam deploy --guided (packages artifacts to S3, creates/updates CloudFormation stack, and prompts for deployment parameters on first run)
  • C. Run sam init to create the deployment package, then sam publish to deploy to AWS, guaranteeing exactly-ordered delivery within each key group and keeping every related record in its produced order
  • D. Run sam deploy directly without building — SAM automatically handles dependencies at deployment time, integrating natively with the rest of the pipeline and validating and cleansing each record before delivery
Correct Answer: B
The correct SAM workflow is: sam build resolves dependencies (installs packages from requirements.txt), compiles code, and places everything in .aws-sam/build directory. sam deploy --guided (first time) or sam deploy (subsequent) uploads the built artifact to S3 and creates/updates the CloudFormation stack. The --guided flag prompts for stack name, region, and other parameters, saving them to samconfig.toml for future deployments.

Option A: INCORRECT. Sam package is an older workflow; sam deploy now handles packaging internally — although its description sounds convincing, in a fundamental still not appropriate for requirements this. The order is wrong.
Option B: CORRECT.
Option C: INCORRECT. Sam init scaffolds new projects; sam publish publishes to Serverless Application Repository, not deploy to your account.
Option D: INCORRECT. Sam deploy requires sam build first to resolve dependencies; it doesn't auto-build.

A data engineer is developing a Lambda function that processes Kinesis stream events for a real-time data pipeline. Before deploying to AWS, the engineer wants to test the function locally with sample Kinesis events to verify the transformation logic. Which SAM CLI approach enables effective local testing?
  • A. Use sam local start-api to create a local HTTP endpoint and send Kinesis events via curl with a JSON event file containing sample Kinesis records (sam local invoke MyFunction --event kinesis-event, applying schema conversion and enrichment inline
  • B. Deploy to AWS first and test using actual Kinesis stream data in production, streaming results downstream in near real time and meeting the latency and throughput goals of the design and delivering records with consistent sub-second latency
  • C. Use sam local generate-event kinesis get-records to create a sample event, but this only works with API Gateway events, transforming records into the required target format and satisfying all of the stated requirements with minimal effort
  • D. Use sam local invoke with a JSON event file containing sample Kinesis records (sam local invoke MyFunction --event kinesis-event.json), where the event file mirrors the actual Kinesis event structure including Records array with base64-encoded data
Correct Answer: D
sam local invoke executes the Lambda function locally in a Docker container that mimics the Lambda runtime environment. The --event flag passes a JSON file simulating the Kinesis event payload. You can generate sample events with sam local generate-event kinesis get-records and customize them. This provides fast local iteration without deploying to AWS.

Option A: INCORRECT. Sam local start-api is for testing API Gateway-triggered functions via HTTP, not Kinesis events — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Testing in production is risky and slow; local testing provides faster feedback.
Option C: INCORRECT. Sam local generate-event works for multiple services including Kinesis, not just API Gateway.
Option D: CORRECT.

A data engineering team builds a serverless data processing pipeline using SAM that includes a Step Functions state machine orchestrating three Lambda functions: extract, transform, and load. The state machine definition is complex (200+ lines of ASL). The team wants to keep the SAM template manageable. Which approach BEST organizes the Step Functions definition within a SAM project?
  • A. Embed the entire 200+ line ASL definition inline in the SAM template's Definition property, reducing day-to-day operational effort and integrating natively with the rest of the pipeline
  • B. Split the state machine into three separate state machines, one for each Lambda function with the DefinitionUri property pointing, reducing day-to-day operational effort and validating and cleansing each record before delivery
  • C. Create the Step Functions state machine manually in the console and reference its ARN in the SAM template, satisfying all of the stated requirements with minimal effort
  • D. Define the state machine using AWS::Serverless::StateMachine resource type with the DefinitionUri property pointing to a separate ASL JSON/YAML file (statemachine/etl-pipeline.asl.json), and use DefinitionSubstitutions to inject Lambda function ARNs dynamically
Correct Answer: D
AWS::Serverless::StateMachine with DefinitionUri separates the state machine definition from the SAM template, keeping both files focused and readable. DefinitionSubstitutions enables variable replacement — replacing placeholder strings in the ASL file with actual Lambda ARNs at deployment time (e.g., "${ExtractFunctionArn}" → actual ARN). This maintains IaC benefits while managing complexity.

Option A: INCORRECT. 200+ inline lines make the template unreadable and difficult to maintain or diff in version control.
Option B: INCORRECT. Splitting one workflow into three loses the orchestration logic that Step Functions provides — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Manual console creation loses IaC benefits (repeatability, version control).
Option D: CORRECT.

A data engineer's Lambda function requires the pandas library (50MB when compiled for Linux) for data transformation. When running sam build, the deployment package exceeds Lambda's 250MB unzipped limit because pandas plus its dependencies (numpy) are large. Which SAM packaging strategy BEST resolves this size limitation?
  • A. Increase Lambda's package size limit by requesting a service quota increase from AWS Support with fully managed infrastructure and automatic scaling, validating and cleansing each record before delivery and integrating natively with the rest of the pipeline and keeping steady-state operating costs low
  • B. Zip the code manually and upload directly to S3, bypassing SAM's build process entirely, applying schema conversion and enrichment inline and meeting the latency and throughput goals of the design and transforming records into the required target format and minimizing end-to-end processing latency
  • C. Use Lambda Layers by defining an AWS::Serverless::LayerVersion resource in the SAM template that packages pandas and numpy into a layer, then reference the layer in the function's Layers property — this separates dependencies from function code and allows sharing across functions
  • D. Remove pandas and rewrite all transformation logic using only Python standard library functions, integrating natively with the rest of the pipeline and handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort
Correct Answer: C
Lambda Layers separate dependencies from function code. The combined total (function code + all layers) can be up to 250MB unzipped, but layers are shared across functions and managed independently. AWS::Serverless::LayerVersion in SAM handles the layer packaging and versioning. Additionally, if still too large, container images support up to 10GB. Layers also enable reuse across multiple Lambda functions without duplicating dependencies.

Option A: INCORRECT. The 250MB limit is a hard limit that cannot be increased via quota requests for zip deployments — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Bypassing SAM loses build automation, dependency management, and cross-platform compilation.
Option C: CORRECT.
Option D: INCORRECT. Rewriting without pandas may not be feasible for complex data transformations.

A data pipeline deployed via SAM needs different configurations across environments: the development Lambda uses 256MB memory with a 30-second timeout processing data from a dev S3 bucket, while production uses 1024MB memory with a 300-second timeout processing from a production bucket. The team wants to manage this with a single SAM template. Which approach is MOST effective?
  • A. Maintain separate SAM template files for each environment (template-dev.yaml, template-prod.yaml), handling the described workload reliably at scale and integrating natively with the rest of the pipeline
  • B. Use SAM's Globals section for shared properties, Parameters section for environment-specific values, and deploy with parameter overrides: sam deploy --parameter-overrides Environment=prod MemorySize=1024 Timeout=300 DataBucket=prod-data-bucket
  • C. Hardcode production values in the template and manually change them for development deployments, integrating natively with the rest of the pipeline and providing exactly-once processing semantics
  • D. Use SAM Accelerate (sam sync) to push code changes without any template parameterization with parameter overrides: sam deploy --parameter-overrides Environment=prod MemorySize=1024 Timeout=300 DataBucket=prod-data-bucket for shared properties
Correct Answer: B
SAM Parameters with --parameter-overrides enable a single template to serve all environments. The Globals section sets defaults shared across all functions. Parameter overrides at deploy time inject environment-specific values. Combined with samconfig.toml (which stores deployment profiles per environment), this provides clean multi-environment management from one codebase.

Option A: INCORRECT. Separate templates diverge over time, requiring changes in multiple files for every modification.
Option B: CORRECT.
Option C: INCORRECT. Manual changes defeat IaC principles and risk deploying wrong values.
Option D: INCORRECT. Sam sync is for development iteration speed, not multi-environment configuration management — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data engineer deploys a serverless data API using SAM that includes an API Gateway REST API, a Lambda function for query execution, and a DynamoDB table for caching results. After deployment, the engineer discovers the Lambda function cannot write to DynamoDB and returns Access Denied errors. The SAM template uses the AWS::Serverless::Function Policies property. What is the MOST likely issue and fix?
  • A. The Lambda function needs to assume a different IAM role at runtime using STS AssumeRole with the TableName parameter referencing the table's logical ID — SAM policy templates automatically generate properly scoped IAM policies without requiring manual policy document authoring
  • B. DynamoDB requires a VPC endpoint for Lambda access, and the template is missing VPC configuration, satisfying all of the stated requirements with minimal effort and removing the need to provision or patch any infrastructure
  • C. The Policies property is missing the DynamoDB access policy. Add DynamoDBCrudPolicy with the TableName parameter referencing the table's logical ID — SAM policy templates automatically generate properly scoped IAM policies without requiring manual policy document authoring
  • D. API Gateway is blocking the Lambda-to-DynamoDB communication and needs a resource policy, integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort and reducing day-to-day operational effort
Correct Answer: C
SAM policy templates (like DynamoDBCrudPolicy, S3ReadPolicy, KinesisStreamReadPolicy) are shorthand that generates least-privilege IAM policies. If the Policies property doesn't include DynamoDB access, the Lambda execution role won't have DynamoDB permissions. Fix: add "- DynamoDBCrudPolicy: {TableName: !Ref MyTable}" to the Policies list. SAM resolves this to a proper IAM policy with read/write permissions scoped to that specific table.

Option A: INCORRECT. SAM automatically creates and assigns the execution role; no STS AssumeRole is needed — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Lambda accesses DynamoDB via public endpoints by default; VPC endpoints are only needed if Lambda is in a VPC with no internet access.
Option C: CORRECT.
Option D: INCORRECT. API Gateway doesn't mediate Lambda-to-DynamoDB calls; they're separate service interactions.

A data engineering team needs to build a data ingestion API that receives JSON payloads via HTTP POST requests, validates the data, and stores it in S3 for downstream processing. They want to deploy this using SAM with minimal configuration. Which SAM resource configuration creates this architecture with the LEAST amount of template code?
  • A. Define an AWS::Serverless::Function with an Api event type (Events: ApiEvent: Type: Api, Properties: Path: /ingest, Method: post) — SAM automatically creates an implicit API Gateway REST API with the specified route, requiring no separate AWS::Serverless::Api resource definition
  • B. Deploy API Gateway manually and use SAM only for the Lambda function, connecting them post-deployment with an Api event type (Events: ApiEvent: Type: Api, reducing day-to-day operational effort and validating and cleansing each record before delivery
  • C. Use AWS::Serverless::HttpApi with detailed route configuration, stage definition, and explicit Lambda integration, reducing day-to-day operational effort and meeting the latency and throughput goals of the design and applying schema conversion and enrichment inline and keeping steady-state operating costs low
  • D. Define separate resources: AWS::ApiGateway::RestApi, AWS::ApiGateway::Resource, AWS::ApiGateway::Method, AWS::Lambda::Permission, and AWS::ApiGateway::Deployment, removing the need to provision or patch any infrastructure and applying schema conversion and enrichment inline and running as a fully managed service with minimal operational overhead
Correct Answer: A
SAM's implicit API feature creates an API Gateway REST API automatically when a function has an Api event type. Just specifying Path and Method in the event properties generates all necessary resources: RestApi, Resource, Method, Lambda Permission, and Deployment. This reduces a typical 50+ lines of CloudFormation to 3-4 lines of SAM configuration.

Option A: CORRECT.
Option B: INCORRECT. Manual deployment loses IaC benefits and creates resources outside the template's management — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. While HttpApi works, the question asks for LEAST code; the implicit API from a function event is even more minimal.
Option D: INCORRECT. This is raw CloudFormation approach requiring extensive boilerplate that SAM eliminates.

A company has a SAM-deployed data pipeline that processes sensitive financial data. The security team requires that all Lambda environment variables containing configuration values (database endpoints, queue URLs) are encrypted at rest using a customer-managed KMS key rather than the default AWS-managed key. How should the engineer configure this in the SAM template?
  • A. In the AWS::Serverless::Function resource, set the KmsKeyArn property under the function definition to reference the customer-managed KMS key ARN, and define environment variables in the Environment.Variables property — Lambda automatically encrypts these at rest using the specified KMS key
  • B. Encrypt each environment variable value manually with the KMS CLI before putting them in the template, guaranteeing no data loss during component failures and satisfying strict compliance and audit requirements and reducing day-to-day operational effort and providing exactly-once processing semantics
  • C. Store all configuration in Secrets Manager and remove environment variables entirely from the template, reducing day-to-day operational effort and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort
  • D. Add a KMS key policy in the template but don't reference it from the Lambda function and define environment variables in the Environment, providing exactly-once processing semantics and integrating natively with the rest of the pipeline and reducing day-to-day operational effort
Correct Answer: A
Lambda's KmsKeyArn property specifies the CMK used to encrypt environment variables at rest. When set, Lambda uses this key instead of the default AWS-managed key. The function's execution role must have kms:Decrypt permission for the key. SAM handles the association between function and KMS key during deployment. This satisfies the security requirement with minimal code changes.

Option A: CORRECT.
Option B: INCORRECT. Manual pre-encryption is complex, doesn't integrate with Lambda's decryption at invocation, and values in the template are still visible.
Option C: INCORRECT. While valid for secrets, the requirement is about encrypting env vars with CMK, not eliminating them entirely; also adds latency for every invocation.
Option D: INCORRECT. A key policy without reference from the function doesn't enable encryption of that function's env vars — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data engineer maintains a SAM application with 5 Lambda functions that share common utility code (logging, error handling, data validation). Currently, this code is duplicated across all function directories. When a bug is found in the shared code, it must be fixed in 5 places. The engineer wants to refactor the project for better maintainability while keeping everything deployable via SAM. Which approach is MOST appropriate?
  • A. Combine all 5 functions into a single Lambda function with if/else logic to handle different event types, handling the described workload reliably at scale and meeting the latency and throughput goals of the design and integrating natively with the rest of the pipeline
  • B. Publish the shared code as a pip package to PyPI and list it in each function's requirements.txt, satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline and handling the described workload reliably at scale
  • C. Use symlinks in the file system to point each function directory to a shared folder with fully managed infrastructure and automatic scaling, satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design
  • D. Create a shared Lambda Layer containing the utility code, define it as AWS::Serverless::LayerVersion in the template, reference it in each function's Layers property, and use the Globals section to apply the layer to all functions automatically without repeating it per function
Correct Answer: D
Lambda Layers are specifically designed for sharing code across functions. AWS::Serverless::LayerVersion packages the shared utility code as a layer. Listing it in Globals.Function.Layers applies it to ALL functions in the template without per-function configuration. Bug fixes in the shared code only require updating the layer once. SAM builds and deploys the layer alongside the functions.

Option A: INCORRECT. Combining functions violates single-responsibility principle and increases blast radius of failures.
Option B: INCORRECT. Publishing to PyPI adds external dependency management complexity and requires public/private registry setup.
Option C: INCORRECT. Symlinks are not reliably handled by sam build and can cause deployment issues across different operating systems — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: CORRECT.
