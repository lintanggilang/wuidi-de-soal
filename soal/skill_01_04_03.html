A data engineering team needs to process 500 GB of daily transaction data stored in Amazon S3. The data must be cleaned, deduplicated, and aggregated before loading into Amazon Redshift. The team has strong Python expertise. Which approach provides the BEST balance of performance and development speed?
  • A. Use Python pandas library in an AWS Lambda function to read and process S3 files
  • B. Use PySpark in an AWS Glue job to process the data in a distributed manner across multiple workers
  • C. Write a custom Python script running on a single large EC2 instance using multiprocessing
  • D. Use Python pandas in an Amazon SageMaker notebook to process the data interactively
Jawaban Benar: B
PySpark in AWS Glue is ideal for 500 GB datasets because it provides distributed processing across multiple workers, handling data that far exceeds single-machine memory. The team can leverage their Python skills since PySpark uses Python syntax. Opsi A — Lambda has 10 GB memory limit and 15-minute timeout, unsuitable for 500 GB. Opsi C — single EC2 instance with multiprocessing doesn't scale horizontally and requires infrastructure management. Opsi D — SageMaker notebooks are for interactive exploration, not production batch processing of 500 GB.

A data engineer is building a pipeline that reads 50 MB of reference data from a DynamoDB table every hour, enriches incoming Kinesis stream records with the reference data, and writes results to S3. The enrichment logic involves simple key lookups. Which language and runtime combination is MOST cost-effective for this use case?
  • A. Python with boto3 in a Lambda function, caching the DynamoDB reference data in the function's memory between invocations
  • B. Scala on Amazon EMR with a long-running Spark Structured Streaming job
  • C. Java on Amazon ECS Fargate with a continuously running container
  • D. R script on an EC2 instance processing data in micro-batches
Jawaban Benar: A
Python with boto3 in Lambda is most cost-effective: Lambda charges only for execution time, boto3 natively integrates with DynamoDB and S3, and reference data (50 MB) fits within Lambda memory. Lambda can be triggered directly by Kinesis as an event source mapping, making simple key lookups efficient. Opsi B — EMR with Spark is over-provisioned for simple key lookups on small reference data; minimum cluster cost is high. Opsi C — Fargate continuously running incurs cost 24/7 regardless of traffic. Opsi D — R is not optimized for stream processing and EC2 requires always-on billing.

A company runs complex analytical queries on Amazon Redshift that involve window functions, CTEs, and multi-table joins. A data engineer needs to create a new transformation that calculates running totals, ranks customers by lifetime value within each region, and identifies gaps in sequential order IDs. Which approach is MOST appropriate?
  • A. Write the transformations directly in SQL using Redshift's native window functions (ROW_NUMBER, SUM OVER, LAG/LEAD) within a stored procedure or scheduled query
  • B. Extract data to Python, process using pandas groupby and rolling functions, then reload to Redshift
  • C. Use PySpark in AWS Glue to perform the window functions and write back to Redshift
  • D. Use R with dplyr to calculate rankings and running totals, then write results to Redshift via JDBC
Jawaban Benar: A
SQL window functions (ROW_NUMBER, SUM() OVER(), LAG/LEAD) are natively optimized in Redshift's MPP engine. Running totals, ranking, and gap detection are classic window function use cases. Processing stays within Redshift — no data movement, no external compute costs. Redshift's columnar storage and distribution keys optimize these operations. Opsi B — extracting 100s of GBs to Python adds latency, network cost, and pandas cannot handle Redshift-scale data. Opsi C — Glue adds unnecessary data movement; Redshift already has these capabilities. Opsi D — R via JDBC is slow for large datasets and adds external dependency.

A data engineering team is migrating a legacy on-premises Spark pipeline from Scala to AWS. The pipeline performs complex graph traversals and custom aggregations on 2 TB of relationship data. The team debates whether to rewrite in Python (PySpark) or keep Scala. The pipeline runs on Amazon EMR. Which recommendation is MOST appropriate?
  • A. Keep the pipeline in Scala because it runs directly on the JVM without serialization overhead, which is critical for iterative graph algorithms that require frequent data shuffling between the driver and executors
  • B. Rewrite in PySpark because Python is easier to maintain and performance is identical
  • C. Rewrite in Python pandas to simplify the code
  • D. Convert to SQL-only transformations in Amazon Athena
Jawaban Benar: A
Scala runs natively on the JVM alongside Spark, eliminating Python-JVM serialization overhead (via Py4J). For iterative graph algorithms with frequent shuffles and custom aggregations, Scala provides better performance because UDFs run in-process. On 2 TB with complex graph traversals, serialization overhead compounds significantly. Additionally, rewriting complex existing Scala introduces risk. Opsi B — PySpark has serialization overhead for UDFs and custom aggregators; performance is NOT identical for UDF-heavy workloads. Opsi C — pandas cannot process 2 TB. Opsi D — Athena SQL cannot express complex graph traversals.

A data engineer needs to write a bootstrap action for an Amazon EMR cluster that installs custom Python libraries, configures environment variables, downloads configuration files from S3, and sets file permissions. Which scripting language is MOST appropriate for this bootstrap action?
  • A. Bash shell script that uses aws s3 cp for file downloads, export for environment variables, chmod for permissions, and pip install for Python packages
  • B. Python script using boto3 and os modules
  • C. PowerShell script with AWS.Tools modules
  • D. Scala script compiled and uploaded as a JAR file
Jawaban Benar: A
EMR bootstrap actions run on Amazon Linux instances where Bash is the native shell. Bash directly handles system operations: aws CLI for S3 downloads, export for environment variables, chmod for permissions, and pip install for packages — all without additional runtime dependencies. Bootstrap actions execute before applications start, so Bash guarantees availability. Opsi B — Python may not be fully configured yet during bootstrap (that's what bootstrap installs). Opsi C — PowerShell is not natively available on Amazon Linux EMR nodes. Opsi D — Scala requires JVM setup which may not be complete during bootstrap phase.

A data engineer uses Python boto3 SDK to automate the creation of AWS Glue crawlers and jobs across 15 AWS accounts. The script must assume roles in each account, create crawlers with specific configurations, and handle API throttling gracefully. Which boto3 pattern is MOST appropriate?
  • A. Use boto3 STS assume_role() to get temporary credentials for each account, create account-specific Glue clients, and implement exponential backoff with jitter using botocore's built-in retry configuration
  • B. Store IAM access keys for all 15 accounts in the script and create separate boto3 sessions for each
  • C. Use a single IAM user with cross-account permissions and no retry logic
  • D. Use AWS CLI commands via subprocess calls in Python for each account
Jawaban Benar: A
STS assume_role() is the standard pattern for cross-account access — provides temporary credentials (security best practice). Botocore's retry configuration with exponential backoff and jitter handles API throttling automatically, essential when creating resources across 15 accounts. Pattern: sts.assume_role() → create session with temp credentials → create glue client → use Config(retries={'max_attempts': 10, 'mode': 'adaptive'}). Opsi B — storing long-term access keys is a security anti-pattern. Opsi C — no retry logic will fail under throttling with 15 accounts. Opsi D — subprocess CLI calls lose boto3's native retry handling and error typing.

A data analyst team runs SQL queries on Amazon Athena to generate weekly reports. They need to calculate the 7-day moving average of daily sales, the percentage contribution of each product to its category total, and the difference between current and previous month's revenue. Which SQL constructs should the data engineer recommend?
  • A. Window functions: AVG() OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) for moving average, SUM() OVER (PARTITION BY category) for percentage contribution, and LAG() OVER (ORDER BY month) for month-over-month difference
  • B. Self-joins with subqueries to calculate moving averages and GROUP BY with HAVING for category totals
  • C. Multiple CTEs with correlated subqueries for each calculation
  • D. Extract data to Python pandas and use rolling() and groupby() functions instead of SQL
Jawaban Benar: A
Window functions are purpose-built for these calculations: ROWS BETWEEN 6 PRECEDING AND CURRENT ROW creates exact 7-day windows, PARTITION BY category computes category-level aggregates alongside row-level detail, and LAG() accesses previous row values without self-joins. Athena (Presto/Trino) fully supports ANSI SQL window functions. Single pass over data = efficient. Opsi B — self-joins create cartesian products, extremely expensive on large datasets. Opsi C — correlated subqueries execute per-row, O(n²) performance. Opsi D — extracting to Python adds latency and doesn't scale for large Athena datasets.

A company deploys an AWS Lambda function that processes IoT sensor data every minute. The function must start quickly because data freshness is critical. The team evaluates runtime options. The processing logic involves JSON parsing, simple mathematical calculations, and writing to DynamoDB. Which Lambda runtime provides the FASTEST cold start for this use case?
  • A. Python 3.12 runtime, because Python has one of the fastest Lambda cold start times, and the required operations (JSON parsing, math, boto3 DynamoDB writes) are all available in the standard library and included SDK
  • B. Java 17 runtime with Spring Boot framework for enterprise-grade structure
  • C. .NET 6 runtime with full ASP.NET framework
  • D. Node.js 20 runtime with TypeScript compilation
Jawaban Benar: A
Python consistently has among the fastest Lambda cold starts (typically 100-200ms) because the interpreter is lightweight and boto3 is included in the Lambda runtime (no additional dependencies). For simple JSON parsing + math + DynamoDB writes, Python is more than performant enough. Opsi B — Java with Spring Boot has notoriously slow cold starts (3-10 seconds) due to JVM initialization and framework bootstrapping. Opsi C — .NET with full framework has significant cold start overhead. Opsi D — Node.js is also fast, but TypeScript requires compilation step which adds complexity; Node.js without TypeScript would be comparable to Python.

A data engineer processes datasets that range from 100 MB to 50 GB depending on the day. Small datasets (under 1 GB) arrive on weekdays, while large weekend batch files reach 50 GB. The pipeline runs on AWS Glue. The engineer wants to use a single codebase that automatically adapts to both scenarios. Which framework selection strategy is BEST?
  • A. Use PySpark (AWS Glue's native framework) for all datasets — Glue Auto Scaling automatically adjusts workers for small datasets (reducing to minimum workers) and scales up for large datasets, providing a single codebase that handles both scenarios
  • B. Use pandas for weekday processing and PySpark for weekend processing with conditional logic to switch
  • C. Use Dask as a middle ground between pandas and Spark
  • D. Always provision for the 50 GB case and accept over-provisioning on weekdays
Jawaban Benar: A
PySpark in Glue with Auto Scaling provides single codebase adaptability. Glue Auto Scaling dynamically adjusts the number of workers based on actual workload parallelism — fewer workers for 100 MB (minimum cost), more workers for 50 GB (maximum throughput). The same PySpark code runs identically regardless of data size. Opsi B — maintaining two code paths (pandas + PySpark) doubles testing effort and introduces bugs. Opsi C — Dask is not natively supported in AWS Glue. Opsi D — over-provisioning wastes cost on weekdays (paying for unused DPUs).

A data engineer deploys a Python-based ETL job to AWS Glue that uses several third-party libraries (great_expectations, cryptography, custom internal packages). The job fails at runtime with ModuleNotFoundError. How should the engineer package and deploy these dependencies following best practices?
  • A. Package the dependencies as a .whl (wheel) file or .zip archive and upload to S3, then reference the S3 path in the Glue job's --extra-py-files parameter. For compiled libraries (like cryptography), use a wheel built for the Glue runtime's Python version and Linux platform
  • B. Include a requirements.txt file alongside the Glue script in S3
  • C. Install libraries at runtime using subprocess pip install at the beginning of the script
  • D. Copy all library source files into the same S3 folder as the Glue script
Jawaban Benar: A
AWS Glue's --extra-py-files parameter is the official mechanism for additional Python dependencies. Wheel files (.whl) are preferred because they contain pre-compiled binaries for the target platform. For libraries with C extensions (cryptography), the wheel must match Glue's Python version and manylinux platform. Multiple .whl files can be comma-separated in the parameter. Opsi B — Glue doesn't automatically process requirements.txt (unlike some other services). Opsi C — subprocess pip at runtime is unreliable, slow, and may fail without internet access in VPC. Opsi D — loose source files won't be importable without proper package structure.
