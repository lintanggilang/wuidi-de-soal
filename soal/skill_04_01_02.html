A company has a data engineering team of 15 members who all need read access to production S3 data lake buckets, write access to development S3 buckets, and the ability to run AWS Glue jobs. Three senior engineers additionally need access to manage EMR clusters. Which IAM configuration follows AWS best practices for managing these permissions?
  • A. Create an IAM group "DataEngineers" with the common permissions attached as managed policies, and a second group "SeniorDataEngineers" with EMR management policies. Add engineers to appropriate groups.
  • B. Create a single IAM role "DataEngineerRole" with all permissions and have all engineers assume the role when needed with fully managed infrastructure and automatic scaling
  • C. Create individual IAM users with inline policies tailored to each engineer's specific needs, meeting the latency and throughput goals of the design and satisfying strict compliance and audit requirements
  • D. Create one IAM group with full administrator access and use AWS Organizations SCPs to restrict permissions at the account level, integrating natively with the rest of the pipeline
Correct Answer: A
AWS best practice is uses IAM Groups for manages permissions based on job function. Group "DataEngineers" contains common policies (S3 read prod, S3 write dev, Glue job run) that applies for all 15 engineer. Group "SeniorDataEngineers" adds EMR management policies. Senior engineers menjadi member in kedua groups and mewarisi all permissions.

Option A: CORRECT.
Option B: INCORRECT. Provides all orang permissions that same including EMR — melanggar least privilege — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Not scalable and difficult in-maintain.
Option D: INCORRECT. Terlalu permissive and SCP not dimaksudkan for granular user permissions.

A data engineer needs to create an IAM role that allows AWS Glue to access an S3 bucket in another AWS account (Account B). The Glue job runs in Account A. Which combination of configurations is required for cross-account access?
  • A. In Account A: Create IAM role with trust policy for s3.amazonaws.com. In Account B: Create an IAM user with access keys and store them in Secrets Manager for Glue to use, integrating natively with the rest of the pipeline
  • B. In Account A: Create a VPC endpoint for S3 pointing to Account B. In Account B: Allow access from Account A's VPC endpoint in the bucket policy, with trust policy for glue and a policy allowing s3:GetObject on Account B's bucket
  • C. In Account A: Create IAM role with AdministratorAccess. In Account B: Disable S3 Block Public Access on the bucket, handling the described workload reliably at scale and satisfying strict compliance and audit requirements and minimizing end-to-end processing latency
  • D. In Account A: Create IAM role with trust policy for glue.amazonaws.com and a policy allowing s3:GetObject on Account B's bucket. In Account B: Add a bucket policy allowing the Account A Glue role to access the bucket.
Correct Answer: D
Cross-account S3 access requires configuration in kedua akun: (1) Account A: IAM role for Glue with trust policy that allows glue.amazonaws.com sebagai principal, plus IAM policy with permission s3:GetObject on ARN bucket Account B. (2) Account B: Bucket policy that allows Account A's Glue role ARN for accesses bucket. Kedua sisi must explicitly allows.

Option A: INCORRECT. Melanggar best practice — gunakan roles, not long-term credentials.
Option B: INCORRECT. Not provides cross-account access — VPC endpoint only route traffic, not provides permission — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Very not secure.
Option D: CORRECT.

A data engineer needs to allow an Amazon Redshift cluster to access data in Amazon S3 and also to call AWS Lambda UDFs (User-Defined Functions). The engineer creates an IAM role for Redshift. Which trust policy configuration is correct for this IAM role?
  • A. Trust policy with Principal: {"AWS": "arn:aws:iam::ACCOUNT_ID:root"} allowing any service in the account to assume the role
  • B. Trust policy with Principal: {"Service": ["redshift.amazonaws.com", "lambda.amazonaws.com"]} and permission policy allowing s3:* and lambda:InvokeFunction
  • C. Trust policy with Principal: {"Service": "redshift.amazonaws.com"} and permission policy allowing s3:* and lambda:InvokeFunction
  • D. Trust policy with Principal: {"Service": "s3.amazonaws.com"} and separate trust for lambda.amazonaws.com
Correct Answer: C
Trust policy determines SIAPA that boleh assume role (Principal), whereas permission policy determines APA that boleh is performed setelah assuming role. Redshift that will assume role, jadi trust policy must has Principal: redshift.amazonaws.com. Permission policy then provides access to S3 and permission lambda:InvokeFunction.

Option A: INCORRECT. Terlalu permissive and not mengikuti service-specific trust.
Option B: INCORRECT. Salah because Lambda does not need assume role this — Redshift that calls Lambda uses role Redshift itself — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: CORRECT.
Option D: INCORRECT. Salah because S3 not assume role.

A data engineer needs to provide an EMR cluster with access to Amazon DynamoDB for a Hive-DynamoDB integration. The engineer creates an IAM role but the EMR cluster cannot access DynamoDB. The trust policy is configured for elasticmapreduce.amazonaws.com. What is the issue?
  • A. The trust policy should include both elasticmapreduce.amazonaws.com and dynamodb.amazonaws.com as principals, integrating natively with the rest of the pipeline and meeting the latency and throughput goals of the design
  • B. DynamoDB access requires a service-linked role that must be created separately, handling peak volume without any manual intervention and scaling elastically to millions of events per second
  • C. The EMR cluster must be launched in a VPC with a DynamoDB VPC endpoint before IAM permissions take effect and an EC2 instance profile role (for ec2
  • D. EMR requires two separate roles — a service role (for elasticmapreduce.amazonaws.com) and an EC2 instance profile role (for ec2.amazonaws.com). The DynamoDB permissions should be on the instance profile role.
Correct Answer: D
EMR uses dua IAM roles: (1) EMR Service Role — trusted by elasticmapreduce.amazonaws.com — for provisioning and managing cluster resources. (2) EC2 Instance Profile Role — trusted by ec2.amazonaws.com — is used by EC2 instances in cluster for accesses AWS services such as S3, DynamoDB, dll. Hive/Spark jobs running on EC2 instances uses instance profile role, jadi DynamoDB permissions must ada in role the said.

Option A: INCORRECT. Salah — DynamoDB not assume role.
Option B: INCORRECT. Salah — DynamoDB not requires service-linked role for access.
Option C: INCORRECT. Salah — VPC endpoint not is required for permission (although membantu routing).
Option D: CORRECT.

A company needs to access Amazon SageMaker, AWS Glue, and Amazon Athena from within a VPC without traversing the public internet. The data engineer evaluates endpoint options. Which statement correctly describes the differences between Gateway Endpoints and Interface Endpoints?
  • A. Gateway Endpoints require security groups for access control. Interface Endpoints use route table entries and VPC endpoint policies only, integrating natively with the rest of the pipeline and handling the described workload reliably at scale
  • B. Gateway Endpoints use ENIs and support all AWS services. Interface Endpoints use route tables and only support S3 and DynamoDB, satisfying all of the stated requirements with minimal effort and providing exactly-once processing semantics
  • C. Gateway Endpoints support S3 and DynamoDB only, are free, and use route table entries. Interface Endpoints support most AWS services, incur hourly and data processing charges, and use private IP addresses via ENIs.
  • D. Both endpoint types are functionally identical but Gateway Endpoints have higher throughput limits than Interface Endpoints. and DynamoDB only, are free, and use route table entries, meeting the latency and throughput goals of the design
Correct Answer: C
Gateway Endpoints only available for S3 and DynamoDB, gratis, and works through route table entries — traffic diarahkan through gateway without ENI. Interface Endpoints (powered by AWS PrivateLink) supports partly large AWS services (including SageMaker, Glue, Athena), uses ENI with private IP in subnet, and has cost per hours plus data processing. Interface Endpoints also requires security group on ENI for access control.

Option A: INCORRECT. Salah — Gateway Endpoints not requires security group, and Interface Endpoints that requires security group.
Option B: INCORRECT. Membalikkan definisi keduanya.
Option C: CORRECT.
Option D: INCORRECT. Salah — keduanya different in a fundamental in architecture — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data engineer attempts to configure role chaining where an AWS Glue job assumes Role A, which then assumes Role B to access resources in a different account. The role chaining fails with an AccessDenied error. All IAM policies and trust policies appear correct. What is the MOST likely limitation causing this failure?
  • A. Role chaining is limited to a maximum of 2 roles in a single chain, enforcing encryption and fine-grained access control
  • B. Role chaining has a maximum session duration of 1 hour regardless of the individual role's maximum session duration settings
  • C. AWS Glue does not support role chaining — it can only use the directly assigned IAM role configured for optimal performance and minimal operational overhead
  • D. The intermediate Role A must have sts:AssumeRole permission and its trust policy must allow the Glue service role as a principal, which is often missed
Correct Answer: B
Role chaining in AWS has limitasi important: session duration maximum is limited 1 hours (3600 seconds) terlepas from MaxSessionDuration that is configured on role individual. If Glue job runs more from 1 hours, temporary credentials from role chain will expire and menyebabkan AccessDenied. Ini is limitasi that often not diketahui.

Option A: INCORRECT. Salah — AWS allows chaining more from 2 roles.
Option B: CORRECT.
Option C: INCORRECT. Salah — Glue can performs role chaining through boto3 STS calls in job script — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Can jadi problem but soal menyebutkan "all policies appear correct" — limitasi 1 hours session duration is penyebab most umum that terlewat.

The partner needs to access specific prefixes in the bucket only during business hours (8 AM - 6 PM UTC). Which IAM configuration meets these requirements?
  • A. Create a Lambda function that generates pre-signed URLs only during business hours and share the function endpoint, protecting the data both in transit and at rest
  • B. Create role with trust policy allowing Account 222222222222 to assume role, with permission policy granting s3:GetObject on specific prefixes, and a Condition block using aws:CurrentTime for time restriction
  • C. Create an IAM user in Account 111111111111 for the partner with time-based MFA requirement, enforcing encryption and fine-grained access control and meeting the latency and throughput goals of the design
  • D. Use S3 Access Points with a bucket policy that restricts access to business hours only for time restriction, protecting the data both in transit and at rest
Correct Answer: B
Cross-account IAM role with: (1) Trust policy that allows Account 222222222222 sebagai Principal for AssumeRole. (2) Permission policy with s3:GetObject on resource ARN specific (arn:aws:s3:::bucket/prefix/*). (3) Condition uses "aws:CurrentTime" with StringGreaterThanEquals and StringLessThanEquals for limits time access. Ini memenuhi all requirement in a native IAM.

Option A: INCORRECT. Not scalable and difficult in-audit.
Option B: CORRECT.
Option C: INCORRECT. Melanggar best practice — always gunakan roles for cross-account access.
Option D: INCORRECT. Bagus for access management but not has native time-based condition — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data engineer is designing IAM policies for a new data platform. Multiple AWS services are used: Glue for ETL, Redshift for warehousing, and Athena for ad-hoc queries. The engineer wants to understand how IAM evaluates policies when a request is made. A user has an explicit Allow in their IAM group policy but an explicit Deny in an S3 bucket policy. What is the result when the user tries to access the S3 object?
  • A. Access is allowed because resource-based policies and identity-based policies are evaluated independently, and one Allow is sufficient
  • B. Access depends on which policy was created most recently configured for optimal performance and minimal operational overhead
  • C. Access is allowed because identity-based policies (IAM group) take precedence over resource-based policies (bucket policy)
  • D. Access is denied because an explicit Deny in any policy always overrides an Allow in any other policy
Correct Answer: D
IAM policy evaluation logic mengikuti rule: Explicit Deny always menang. Urutan evaluasi: (1) If ada explicit Deny in policy manapun → DENY. (2) If ada explicit Allow → ALLOW. (3) If there is no explicit Allow → implicit DENY. Because ada explicit Deny in bucket policy, access will ditolak although IAM group policy allows. Ini applies terlepas from type policy (identity-based, resource-based, SCP, permission boundary).

Option A: INCORRECT. Salah — this only applies for cross-account access where kedua sisi must Allow.
Option B: INCORRECT. Salah — time creation not affects evaluasi — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Salah — there is no hirarki prioritas between identity and resource-based policies for Deny.
Option D: CORRECT.

A data engineer discovers that the AWS Glue service-linked role (AWSServiceRoleForGlue) does not have sufficient permissions for a specific use case — the Glue crawler needs to access a KMS-encrypted S3 bucket with a customer-managed key. What should the engineer do?
  • A. Service-linked roles cannot be modified. Instead, add the Glue service-linked role's ARN to the KMS key policy as an authorized principal.
  • B. Delete the service-linked role and recreate it with additional KMS permissions in the trust policy, requiring no servers to manage or scale manually
  • C. Create a custom IAM role for the Glue crawler with both the required S3 and KMS permissions, and use that instead of the service-linked role
  • D. Modify the AWSServiceRoleForGlue by attaching an additional IAM policy with KMS decrypt permissions configured for optimal performance and minimal operational overhead
Correct Answer: A
Service-linked roles is pre-defined by AWS and cannot dimodifikasi — Anda cannot adds or changes permission policies-nya. For KMS customer-managed keys, solusinya is adds ARN service-linked role to KMS key policy sebagai authorized principal for kms:Decrypt and kms:GenerateDataKey. KMS key policy provides access from sisi resource.

Option A: CORRECT.
Option B: INCORRECT. Salah — service-linked roles cannot in-custom saat creation.
Option C: INCORRECT. Can works but not solution that correct if Anda already uses service-linked role and only needs access KMS — better update KMS key policy.
Option D: INCORRECT. Salah — service-linked roles cannot dimodifikasi — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A company deploys a data pipeline where Account A runs Glue jobs that write to an S3 bucket in Account B, and an EMR cluster in Account C reads from that bucket. The data engineer needs to set up IAM roles to enable this cross-account data flow. Which configuration correctly enables this three-account access pattern?
  • A. Grant Account A and Account C full administrator access to Account B using AWS Organizations trusted access, protecting the data both in transit and at rest and meeting the latency and throughput goals of the design
  • B. Account B bucket policy allows Account A Glue role to PutObject and Account C EMR role to GetObject. Account A has Glue role with s3:PutObject permission. Account C EMR instance profile has s3:GetObject permission.
  • C. Create a single cross-account role in Account B that both Account A and Account C assume to access the bucket, satisfying all of the stated requirements with minimal effort and satisfying strict compliance and audit requirements
  • D. Use S3 replication to copy data from Account A to Account C, avoiding cross-account access entirely with s3:PutObject permission and Account C EMR role to GetObject, handling the described workload reliably at scale
Correct Answer: B
For cross-account S3 access, is required permission in kedua sisi: (1) Identity-based policy in source account (IAM role permission) — Account A Glue role needs s3:PutObject, Account C EMR role needs s3:GetObject. (2) Resource-based policy in destination account (S3 bucket policy) — explicitly allow Account A's Glue role ARN for PutObject and Account C's EMR role ARN for GetObject. Ini mengikuti principle of least privilege.

Option A: INCORRECT. Very not secure and melanggar least privilege.
Option B: CORRECT.
Option C: INCORRECT. Kurang secure — kedua account mendapat permissions that same.
Option D: INCORRECT. Adds cost and complexity — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
