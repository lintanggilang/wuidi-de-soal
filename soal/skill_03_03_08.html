A security team needs to analyze 6 months of VPC Flow Logs stored in Amazon S3 (partitioned by date in Parquet format) to identify all denied traffic from specific CIDR ranges. The analysis will be run once for an incident investigation. The data totals approximately 2 TB. Which service is MOST cost-effective for this one-time analysis?
  • A. Amazon OpenSearch Service with a dedicated cluster sized for 2 TB of data, ingesting all 6 months of logs for interactive analysis.
  • B. CloudWatch Logs Insights by first importing the S3-stored logs back into CloudWatch Logs, then running queries, enforcing encryption and fine-grained access control
  • C. Amazon EMR with a transient Spark cluster to process all 2 TB of flow logs and produce a filtered result set, with native S3 integration and optimized data transfer
  • D. Amazon Athena with partition pruning on the date columns and predicate pushdown on the source CIDR field, querying the Parquet files directly in S3.
Jawaban Benar: D
Athena is ideal for one-time, ad-hoc analysis of S3-stored logs. It's serverless (no infrastructure to provision), charges only per data scanned ($5/TB), and with Parquet format + partition pruning, the actual data scanned will be far less than 2 TB. For a one-time investigation, this is the most cost-effective approach. Option B: OpenSearch requires provisioning and maintaining a cluster, with significant cost for a one-time analysis; ingesting 2 TB would take hours and the cluster would be idle afterward. Option C: EMR would work but requires cluster provisioning, configuration, and management; Athena provides the same capability without operational overhead. Option D: Re-ingesting S3 logs into CloudWatch Logs would incur $0.50/GB ingestion costs ($1,000 for 2 TB) and is impractical for historical data.

Opsi B: SALAH.
Opsi C: SALAH. Meskipun terdengar meyakinkan, tetap tidak tepat untuk skenario ini.

  • A. Use CloudTrail Lake to query the events directly using the CloudTrail Lake SQL syntax without needing to configure any external tables.

Option C: EMR requires cluster provisioning and Spark programming knowledge—significantly more setup time. Option D: OpenSearch requires data ingestion (time-consuming for 30 days of logs) and cluster management for a one-time query.

A company's data pipeline produces application logs in a custom multi-line format where each log entry spans 3-5 lines (timestamp on line 1, message on line 2, stack trace on lines 3-5). These logs are stored in CloudWatch Logs. When using CloudWatch Logs Insights, the team finds that queries return fragmented results because each line is treated as a separate event. How should they solve this?
  • A. Create a subscription filter that sends logs to a Lambda function which reassembles multi-line entries before writing them back to a new log group.
  • B. Configure the CloudWatch agent's multi_line_start_pattern setting to match the timestamp pattern, ensuring related lines are grouped into a single log event at ingestion time.
  • C. Modify the application to emit logs in single-line structured JSON format with the stack trace embedded as a JSON field, ensuring each CloudWatch log event is one complete entry.
  • D. Use the parse command in Logs Insights with a multi-line regex pattern to reconstruct full log entries from consecutive lines during query time.
Jawaban Benar: B
The CloudWatch agent supports multi_line_start_pattern configuration, which uses a regex pattern (matching the timestamp format) to identify the beginning of a new log event. All subsequent lines until the next match are grouped into a single CloudWatch log event. This solves the problem at ingestion time, making all downstream queries work correctly. Option A: Logs Insights' parse command works on individual log events; it cannot join separate events back together after they've been ingested as separate entries. Option B: While structured JSON logging is a best practice, it requires application code changes which may not be feasible for all components. Option D: This adds cost and complexity with Lambda processing and duplicate log storage.

Opsi A: SALAH.
Opsi B: BENAR.

Which service is BEST suited for this large-scale log processing?
  • A. Amazon Athena with CTAS (CREATE TABLE AS SELECT) queries to transform each log format into normalized Parquet tables, validating and cleansing each record before delivery and reducing day-to-day operational effort
  • B. CloudWatch Logs Insights for querying all log formats and exporting results to S3 in Parquet format, applying schema conversion and enrichment inline and scaling elastically to millions of events per second

#OpenSearch
A team uses Amazon OpenSearch Service for real-time log analytics of their data pipeline. The cluster has 3 data nodes with 1 TB EBS storage each. They've configured an index pattern where each day creates a new index. After 6 months, queries have become slow and the cluster shows high JVM memory pressure (>85%). What is the MOST effective solution?
  • A. Change the index pattern from daily to weekly to reduce the total number of indices in the cluster. and delete indices older than 90 days, making the data queryable within seconds of arrival and delivering records with consistent sub-second latency
  • B. Add more data nodes to the cluster to distribute the shard load and reduce per-node JVM memory pressure, satisfying all of the stated requirements with minimal effort and minimizing end-to-end processing latency and delivering records with consistent sub-second latency
  • C. Implement Index State Management (ISM) policies to automatically transition indices older than 7 days to warm storage (UltraWarm), and delete indices older than 90 days. Reduce the number of shards per index based on the daily data volume.
  • D. Increase the EBS volume size on each node to provide more storage capacity for the growing indices, minimizing end-to-end processing latency and handling the described workload reliably at scale and integrating natively with the rest of the pipeline
Jawaban Benar: C
High JVM memory pressure in OpenSearch is primarily caused by too many shards (each shard consumes heap memory for metadata). With daily indices over 6 months, the cluster has ~180 indices with potentially thousands of shards. ISM policies automate lifecycle management: moving old indices to UltraWarm (which doesn't consume data node JVM heap) and deleting very old data. Right-sizing shards reduces the total count. Option B: Adding nodes distributes shards but doesn't reduce the total shard count that causes JVM pressure; it's also more expensive. Option C: EBS size doesn't affect JVM memory pressure—the issue is shard metadata in heap, not disk space. Option D: Weekly indices reduce index count by 7x but don't address the fundamental lifecycle management problem; after enough weeks, the same issue recurs.

Opsi A: SALAH. Meskipun terdengar meyakinkan, tetap tidak tepat untuk skenario ini.

A data platform team wants to compare the costs of three log analysis approaches for their pipeline monitoring: CloudWatch Logs Insights, Athena on S3, and OpenSearch. Their daily log volume is 200 GB with queries running approximately 50 times per day. Logs must be retained for 30 days. Which statement about the cost comparison is CORRECT?
  • A. CloudWatch Logs Insights has the highest total cost because it charges $0.50/GB for ingestion plus $0.005/GB for queries scanned, making the ingestion cost ($100/day) the dominant factor regardless of query patterns.
  • B. OpenSearch is the cheapest because UltraWarm storage costs less than S3 Standard for the same data volume, optimizing cost for the described workload and keeping steady-state operating costs low
  • C. Athena is always the cheapest option because it only charges $5/TB scanned with no ingestion costs when data already resides in S3, keeping steady-state operating costs low and providing exactly-once processing semantics
  • D. All three services cost approximately the same at 200 GB/day because AWS normalizes pricing across analytics services. for ingestion plus $0, meeting the latency and throughput goals of the design
Jawaban Benar: A
CloudWatch Logs charges $0.50/GB for ingestion—the primary cost driver. At 200 GB/day, that's $100/day ($3,000/month) just for ingestion, before any query or storage costs. This makes it significantly more expensive than Athena (which queries S3 data at $5/TB scanned, with S3 storage at ~$0.023/GB) or OpenSearch (which has infrastructure costs but no per-GB ingestion fee of that magnitude). Option B: Athena's cost depends heavily on data format and query patterns; scanning 200 GB × 50 queries/day in unoptimized format can be expensive, but it's still typically cheaper than CloudWatch ingestion. The statement "always cheapest" is an oversimplification. Option C: UltraWarm storage is approximately $0.024/GB-month, comparable to S3, but OpenSearch requires hot node infrastructure costs. Option D: AWS services have very different pricing models.

Opsi A: BENAR.
