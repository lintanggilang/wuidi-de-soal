A healthcare company receives daily patient data files from 50 hospital partners via SFTP. Currently, partners upload files to an on-premises SFTP server, and a manual process copies them to S3 for ETL processing. The company wants to eliminate the on-premises server while maintaining the SFTP interface that partners already use (no partner-side changes allowed). Files must trigger an automated ETL pipeline upon arrival. Which AWS architecture MOST effectively replaces the on-premises SFTP workflow?
  • A. Deploy AWS Transfer Family with SFTP protocol, configured to store uploaded files directly in S3. Configure S3 Event Notifications on the destination bucket to trigger a Lambda function that initiates an AWS Glue ETL job. Partners continue using their existing SFTP clients with only a DNS change to point to the Transfer Family endpoint
  • B. Set up an EC2 instance running OpenSSH SFTP server with an S3-backed filesystem (s3fs-fuse), manually copying files to S3 after upload
  • C. Ask all 50 partners to modify their systems to use the AWS SDK and upload directly to S3 using pre-signed URLs
  • D. Use Amazon AppFlow to connect to each partner's SFTP server and pull files on a schedule
Jawaban Benar: A
AWS Transfer Family provides a fully managed SFTP service that stores files directly in S3, eliminating the on-premises server. Partners only need a DNS change (same SFTP protocol, same client software). The S3 Event Notification → Lambda → Glue pattern creates an event-driven pipeline that automatically processes files upon arrival without polling or manual intervention. Transfer Family handles authentication, encryption, and high availability. Opsi B — EC2 + s3fs-fuse requires server management, patching, scaling, and s3fs has known performance limitations; it doesn't provide automatic pipeline triggering. Opsi C — modifying 50 partners' upload processes violates the "no partner-side changes" requirement and introduces significant coordination overhead. Opsi D — AppFlow doesn't support SFTP as a source connector; it's designed for SaaS application integrations (Salesforce, SAP, etc.), not generic SFTP pulls.
2
A company needs to migrate 500 TB of historical data from an on-premises Hadoop cluster to Amazon S3 within a 2-week window. Their network connection is a 1 Gbps Direct Connect link (theoretical maximum transfer: ~10 TB/week). The data is stored as HDFS files and must maintain the same directory structure in S3. After the initial migration, 5 TB of new data is generated daily and must sync incrementally. Which migration strategy meets the timeline requirement?
  • A. Use AWS Snowball Edge devices (multiple units in parallel) for the initial 500 TB bulk transfer, which can physically ship ~80 TB per device in approximately 1 week including shipping time. Simultaneously configure AWS DataSync with HDFS agent to begin incremental daily sync of the 5 TB/day over Direct Connect once Snowball data arrives in S3
  • B. Use AWS DataSync over the 1 Gbps Direct Connect link for the full 500 TB transfer, running continuously for the 2-week window
  • C. Use AWS DMS to migrate the HDFS data to S3, leveraging its change data capture for incremental updates
  • D. Set up S3 Transfer Acceleration and use multiple parallel aws s3 cp commands over the internet
Jawaban Benar: A
This hybrid approach addresses the math: 500 TB over 1 Gbps = ~50 weeks (far exceeding 2-week deadline). Snow Family provides offline transfer — 7 Snowball Edge devices (80 TB each = 560 TB capacity) can be loaded in parallel on-premises in a few days and shipped to AWS in ~1 week. DataSync with HDFS agent then handles the ongoing 5 TB/day incremental sync over Direct Connect (easily achievable at 1 Gbps = ~10 TB/day capacity). This combination meets both the bulk deadline and ongoing sync requirement. Opsi B — 1 Gbps maxes out at ~10 TB/week; 500 TB would take ~50 weeks, far exceeding the 2-week window. Opsi C — DMS is designed for database migration (relational/NoSQL), not HDFS file migration; it doesn't support HDFS as a source. Opsi D — S3 Transfer Acceleration helps with internet transfers but is still bandwidth-limited; the internet connection would need 200+ Gbps to transfer 500 TB in 2 weeks.
3
A financial institution is migrating their Oracle data warehouse to Amazon Redshift. The Oracle database is 10 TB with 500+ tables, stored procedures, views, and materialized views. The migration must minimize downtime — the system processes $2 million in transactions per hour and cannot be offline for more than 4 hours. The team needs to handle schema conversion, full data load, and ongoing change synchronization until cutover. Which combination of AWS tools provides the MOST complete migration path?
  • A. Use AWS Schema Conversion Tool (SCT) to convert Oracle schema (tables, views, stored procedures) to Redshift-compatible DDL. Then use AWS DMS with full load + CDC (Change Data Capture) to perform initial data migration while capturing ongoing changes from Oracle redo logs, keeping Redshift synchronized until cutover. During the 4-hour cutover window, stop Oracle writes, let DMS drain remaining changes, verify data consistency, and switch application connections to Redshift
  • B. Export all Oracle data to CSV files, transfer to S3, and use Redshift COPY command to load the data, then manually recreate all schemas in Redshift
  • C. Use AWS DataSync to copy Oracle data files directly to S3 and mount them as external tables in Redshift Spectrum
  • D. Stop the Oracle database, take a full backup, restore it to RDS Oracle, then use Redshift federated queries to access the data
Jawaban Benar: A
SCT + DMS with CDC is the standard AWS migration methodology for database migrations with minimal downtime: (1) SCT handles schema complexity (converting Oracle PL/SQL to Redshift SQL, mapping data types, converting stored procedures); (2) DMS full load migrates the initial 10 TB while the source remains online; (3) CDC continuously replicates changes from Oracle redo logs to keep Redshift synchronized during migration (days/weeks); (4) final cutover within 4 hours only needs to drain last few minutes of changes. This approach minimizes downtime to the brief cutover window. Opsi B — CSV export requires taking Oracle offline for consistent export (exceeding 4-hour window for 10 TB), manual schema recreation for 500+ objects is error-prone, and provides no incremental sync. Opsi C — DataSync copies files, not database structures; Oracle data files are not directly readable by Redshift. Opsi D — stopping Oracle for backup and restore to RDS would require many hours of downtime (10 TB backup + restore), and federated queries aren't a migration — they create a dependency on Oracle.

A data engineering team needs to continuously replicate data from an on-premises PostgreSQL database (200 GB) to Amazon S3 for their data lake. The replication must capture inserts, updates, and deletes in near real-time (within 1 minute) and store data in S3 in Parquet format for efficient querying with Athena. The source database must not be impacted significantly (less than 5% performance overhead). Which approach BEST meets these requirements?
  • A. Use AWS DMS with a replication instance configured for ongoing CDC (Change Data Capture) from PostgreSQL using logical replication slots. Configure the DMS target endpoint as S3 with Parquet format output and appropriate partitioning settings (by date). DMS captures WAL changes with minimal source impact (~2-3% overhead from logical replication)
  • B. Schedule a nightly full database dump (pg_dump) to S3 and convert to Parquet using AWS Glue
  • C. Use AWS DataSync to copy PostgreSQL data directory files to S3 every minute
  • D. Create a PostgreSQL trigger on every table that calls an AWS Lambda function via pg_notify for each row change
Jawaban Benar: A
DMS with CDC leverages PostgreSQL's built-in logical replication (WAL-based) which adds minimal overhead (~2-3%) to the source database. DMS reads the WAL stream without adding triggers or modifying the source schema. The S3 target endpoint supports direct Parquet output with configurable partitioning (timestamp-based), eliminating the need for a separate format conversion step. CDC ensures near real-time replication (seconds to 1 minute latency). Opsi B — nightly pg_dump provides data that's up to 24 hours stale (not near real-time), and the dump process itself creates significant source load for a 200 GB database. Opsi C — DataSync copies files, not database logical changes; PostgreSQL data directory files are binary (not Parquet), and copying them every minute would be massive I/O overhead. Opsi D — triggers on every table and row add significant overhead (easily exceeding 5%) at high write volumes, and Lambda invocation per row change would be prohibitively expensive and create massive Lambda concurrency.

A media company has 50 TB of video processing results (metadata, thumbnails, analytics) stored in an on-premises NFS server. They need to migrate this data to Amazon S3 and then establish an ongoing sync to keep S3 updated as new video processing results are generated on-premises (approximately 500 GB/day of new data). The network connection is a 10 Gbps Direct Connect link. The migration must preserve file permissions and timestamps for audit compliance. Which tool is MOST appropriate for both the initial migration and ongoing synchronization?
  • A. AWS DataSync with an on-premises agent installed near the NFS server. DataSync performs the initial 50 TB transfer using parallel streams to maximize the 10 Gbps link, preserves file metadata (permissions, timestamps, ownership) as S3 object metadata, and schedules recurring sync tasks that transfer only changed files (incremental using checksums) for the daily 500 GB updates
  • B. AWS Transfer Family with SFTP protocol to upload files from the NFS server to S3
  • C. Use aws s3 sync CLI command running on an on-premises EC2 instance connected via Direct Connect
  • D. AWS Snow Family for the initial migration, then manually scripted rsync to an EC2 instance for ongoing sync
Jawaban Benar: A
DataSync is purpose-built for this exact scenario: (1) the agent maximizes network utilization with parallel streams, compression, and integrity verification — transferring 50 TB over 10 Gbps Direct Connect in approximately 12 hours; (2) built-in metadata preservation maps NFS permissions and timestamps to S3 object metadata for compliance; (3) incremental sync uses checksums to identify changed files, efficiently transferring only the 500 GB/day of new data; (4) scheduled tasks automate ongoing sync without custom scripting. Opsi B — Transfer Family is designed for partner file exchange (SFTP/FTP), not bulk data migration from NFS; it doesn't support NFS as a source or provide incremental sync capabilities. Opsi C — aws s3 sync works but uses single-stream transfer (not maximizing 10 Gbps), doesn't preserve NFS permissions as metadata, and requires managing the sync scheduling manually. Opsi D — Snow Family is unnecessary when 10 Gbps Direct Connect can transfer 50 TB in ~12 hours; manual rsync to EC2 adds complexity and doesn't preserve metadata for S3.

A company receives daily inventory files from 200 retail partners. Each partner has their own SFTP credentials and uploads files to a specific directory path. The files must be automatically routed to different S3 prefixes based on the partner who uploaded them, and a notification must be sent to the partner's dedicated SNS topic upon successful upload. File sizes range from 1 MB to 5 GB. Which AWS Transfer Family configuration BEST automates this multi-tenant workflow?
  • A. Configure AWS Transfer Family with custom identity provider (Lambda-backed) that authenticates each partner and returns their specific home directory mapping to a unique S3 prefix (s3://bucket/partners/{partner_id}/). Use managed workflows (post-upload steps) with a Lambda step that publishes to the partner-specific SNS topic based on the uploading user's identity
  • B. Create a single shared SFTP user for all 200 partners with a common home directory, then use S3 Event Notifications to trigger a Lambda function that identifies the partner from file naming conventions
  • C. Deploy 200 separate Transfer Family servers, one per partner, each with its own S3 bucket and SNS configuration
  • D. Use Amazon AppFlow with SFTP connectors to pull files from each partner's SFTP server on a schedule
Jawaban Benar: A
Transfer Family's custom identity provider + managed workflows provide the complete multi-tenant solution: (1) Lambda-backed authentication validates partner credentials and returns partner-specific home directory mapping (logical directory to S3 prefix), isolating partners from each other; (2) each partner sees only their directory (cannot access other partners' files); (3) managed workflows execute post-upload Lambda steps with access to the session context (username, uploaded file path), enabling partner-specific SNS notification routing; (4) single server handles all 200 partners efficiently. Opsi B — a single shared user has no isolation between partners (one partner could overwrite another's files), and file naming conventions are unreliable for identification. Opsi C — 200 separate servers would cost ~$43,800/month in endpoint fees alone ($0.30/hour × 200 × 730 hours), which is prohibitively expensive when a single server with multiple users suffices. Opsi D — AppFlow doesn't support generic SFTP as a connector; it's for SaaS integrations, and pulling from partner servers reverses the data flow direction.

A company is migrating their MongoDB database (5 TB, 100+ collections) from on-premises to Amazon DynamoDB. The MongoDB schema uses nested documents (up to 5 levels deep), arrays of embedded objects, and polymorphic collections (documents with different structures in the same collection). The team needs to flatten and transform the data model for DynamoDB's key-value structure during migration. Which approach handles the schema transformation MOST effectively?
  • A. Use AWS DMS with MongoDB as the source and DynamoDB as the target, configuring table mappings with transformation rules to flatten nested documents into top-level attributes. For complex transformations (array flattening, polymorphic handling), create an intermediate S3 target in DMS, then use AWS Glue ETL jobs with custom Python transforms to restructure the data before loading to DynamoDB
  • B. Export MongoDB collections to JSON files, upload to S3, and use Athena CREATE TABLE AS SELECT with JSON SerDe to flatten the structure before loading to DynamoDB
  • C. Use AWS DMS with direct MongoDB-to-DynamoDB migration without any transformation, relying on DynamoDB's ability to store nested documents as Map attributes
  • D. Rewrite the application to use Amazon DocumentDB (MongoDB compatible) instead of migrating to DynamoDB
Jawaban Benar: A
The two-stage approach (DMS → S3 → Glue → DynamoDB) provides maximum transformation flexibility: (1) DMS handles the efficient extraction from MongoDB with CDC support for ongoing replication during migration; (2) S3 intermediate stage decouples extraction from transformation; (3) Glue ETL with Python allows complex logic for flattening 5-level nested documents, unwinding arrays into separate DynamoDB items, and handling polymorphic documents with conditional attribute mapping; (4) DynamoDB batch writes from Glue load the transformed data efficiently. Opsi B — Athena JSON SerDe handles simple nesting but struggles with deeply nested polymorphic structures and cannot handle array flattening into separate records well. Opsi C — storing MongoDB documents as raw DynamoDB Maps preserves the nested structure but doesn't optimize for DynamoDB's access patterns (GSIs require top-level attributes; nested Maps can't be indexed). Opsi D — DocumentDB is a valid alternative but the question specifically asks about migrating to DynamoDB; this changes the target architecture entirely.

An enterprise has 200 TB of data across 3 on-premises data centers that needs to be migrated to AWS. Each data center has limited bandwidth (1 Gbps each) and the total migration must complete within 6 weeks. The data includes files (150 TB on NFS), a 30 TB Oracle database, and 20 TB of VMware virtual machine images. Which combination of migration tools creates the MOST efficient parallel migration strategy?
  • A. AWS Snowball Edge devices (multiple per data center) for the 150 TB of NFS files, running in parallel across all 3 data centers. AWS DMS for the 30 TB Oracle database with full load + CDC over Direct Connect. AWS Application Migration Service (MGN) for the 20 TB VMware images with continuous block-level replication
  • B. Use AWS DataSync for all 200 TB over the combined 3 Gbps bandwidth across all data centers
  • C. Order a single AWS Snowmobile (100 PB capacity) to visit each data center sequentially and load all data types
  • D. Use AWS DMS for all data types — files, database, and VM images — since DMS supports multiple source types
Jawaban Benar: A
Using purpose-built tools for each data type, running in parallel, maximizes efficiency: (1) Snowball Edge for 150 TB files bypasses bandwidth limitations (3 Gbps × 6 weeks = ~18 TB maximum over network, far short of 150 TB); multiple devices per data center enable parallel loading; (2) DMS is purpose-built for database migration with CDC, handling Oracle-to-AWS replication efficiently; (3) MGN replicates VMware images at the block level with continuous sync until cutover. All three streams can run simultaneously, meeting the 6-week deadline. Opsi B — 3 Gbps combined bandwidth can transfer only ~18 TB in 6 weeks; DataSync cannot move 200 TB within the timeline. Opsi C — Snowmobile is for extremely large migrations (50-100 PB); for 200 TB it's overkill, has long lead times, and visiting 3 data centers sequentially may not fit within 6 weeks. Opsi D — DMS is for database migration only; it doesn't support NFS file sources or VM image replication.

A company uses AWS Transfer Family to receive partner files. They need to implement a data quality validation workflow: when a file is uploaded, it must be scanned for malware, validated against an expected schema (CSV with specific columns and data types), moved to a "quarantine" location if validation fails, or moved to a "processed" location and trigger the ETL pipeline if validation passes. Which Transfer Family feature enables this automated validation workflow?
  • A. Configure Transfer Family managed workflows with sequential steps: Step 1 — Copy to a staging location; Step 2 — Custom Lambda step that performs malware scanning (using Amazon GuardDuty Malware Protection or ClamAV on Lambda) and schema validation; Step 3 — Conditional routing: on success, copy to "processed/" prefix and tag for ETL trigger; on exception, copy to "quarantine/" prefix and send SNS notification
  • B. Use S3 Event Notifications on the Transfer Family destination bucket to trigger a Step Functions state machine for the validation workflow
  • C. Deploy a separate EC2 instance that polls the S3 bucket every minute for new files and performs validation
  • D. Configure Transfer Family's built-in file validation feature to check CSV schema compliance
Jawaban Benar: A
Transfer Family managed workflows provide native post-upload processing: (1) workflows execute immediately after upload completes (no S3 event delay); (2) sequential steps ensure malware scan occurs before schema validation; (3) Lambda custom steps enable any validation logic (schema checks, data type validation, record counts); (4) conditional routing (on-success vs. on-exception) automatically moves files to appropriate locations; (5) built-in integration means no additional infrastructure between Transfer Family and the validation logic. Opsi B — S3 Event Notifications + Step Functions work but add architectural complexity, potential timing issues (event delay), and extra services to manage; managed workflows are the native, purpose-built solution within Transfer Family. Opsi C — polling introduces latency (up to 1 minute delay), wastes compute during idle periods, and requires managing EC2 infrastructure. Opsi D — Transfer Family does not have built-in CSV schema validation; it provides file transfer, not content validation.

A company is performing a heterogeneous database migration from SQL Server to Aurora PostgreSQL for their analytics reporting database. The database has 200 stored procedures with complex T-SQL logic, 50 SSIS packages for ETL, and custom CLR functions. The team needs to assess migration complexity and estimate effort before committing to the project. Which AWS tool provides the MOST comprehensive migration assessment?
  • A. AWS Schema Conversion Tool (SCT) assessment report, which analyzes all database objects (stored procedures, views, triggers, functions), identifies conversion complexity for each object (simple/medium/complex), highlights items requiring manual intervention (CLR functions, SSIS packages), provides equivalent PostgreSQL code suggestions where possible, and generates an overall migration effort estimate with action items
  • B. AWS DMS pre-migration assessment that validates source and target endpoint connectivity and configuration
  • C. Run AWS Trusted Advisor checks to assess the current SQL Server performance and identify optimization opportunities
  • D. Use Amazon RDS Performance Insights on the source SQL Server to determine if Aurora PostgreSQL can handle the workload
Jawaban Benar: A
SCT assessment reports are designed specifically for migration planning: (1) they analyze every database object and categorize conversion difficulty (green=automatic, yellow=needs review, red=requires manual rewrite); (2) for stored procedures, SCT attempts T-SQL to PL/pgSQL conversion and flags incompatible constructs; (3) CLR functions and SSIS packages are identified as requiring alternative solutions (Lambda, Glue); (4) the report provides percentage of automatic conversion achievable, helping estimate timeline and effort; (5) specific recommendations for each non-convertible item guide the team's manual work. Opsi B — DMS pre-migration assessment only checks technical connectivity and compatibility (data types, table structures), not stored procedure conversion complexity or ETL package migration. Opsi C — Trusted Advisor provides AWS account-level best practices (cost, security, performance), not database migration assessment. Opsi D — Performance Insights monitors query performance metrics but cannot assess schema conversion complexity or stored procedure compatibility.
