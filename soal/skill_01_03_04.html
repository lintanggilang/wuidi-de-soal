Amazon SNS, Amazon SQS for pipeline monitoring, failure alerts, and operational notifications

A data engineer needs to send email alerts to the on-call team when an AWS Glue ETL job fails. The alert should include the job name, error message, and timestamp. Which approach provides this with LEAST configuration effort?
  • A. Create an EventBridge rule matching Glue Job State Change events with state "FAILED", targeting an SNS topic that sends emails to the on-call team with input transformation to format the message
  • B. Create a CloudWatch alarm on Glue job metrics that triggers SNS
  • C. Add error notification code at the end of the Glue job script
  • D. Use a Lambda function that polls Glue job status every minute
Jawaban Benar: A
EventBridge captures Glue job state change events natively. Rule filters for FAILED state dan input transformation extracts jobName, message, timestamp into a readable email format. SNS topic delivers to email subscribers. All configuration, no code needed. Opsi B (CloudWatch alarm) doesn't capture error details like job name and error message in the alert. Opsi C (code in job) doesn't execute if job crashes unexpectedly. Opsi D (polling Lambda) adds unnecessary cost and latency.

A data pipeline sends alerts via SNS when processing completes. The engineering team receives too many notifications (100+ per day for normal operations) causing alert fatigue. Only failures and SLA breaches should generate alerts. How should the notification strategy be improved?
  • A. Implement tiered alerting: use SNS filter policies to route only CRITICAL alerts (failures, SLA breaches) to the pager/email topic, and INFO alerts to a separate low-priority topic or CloudWatch logs only
  • B. Unsubscribe the team from all SNS notifications
  • C. Set up email rules to filter out non-critical alerts
  • D. Reduce pipeline monitoring to check only once per day
Jawaban Benar: A
SNS filter policies allow subscribers to receive only messages matching certain criteria (e.g., severity=CRITICAL). Tiered approach: critical alerts → pager/email, informational → log archive or dashboard. This reduces noise while maintaining visibility. Opsi B (unsubscribe) loses all visibility. Opsi C (email rules) — still generates notifications, just hides them client-side. Opsi D (daily check) misses real-time failures requiring immediate action.

A data pipeline processes financial data with strict SLA: processing must complete by 6:00 AM daily. If not complete by 5:30 AM, an early warning alert should be sent. If not complete by 6:00 AM, a critical alert should be sent to the manager. Which implementation provides this two-tier alerting?
  • A. Use two EventBridge scheduled rules: one at 5:30 AM checks if processing is complete (via Lambda checking status) and sends warning via SNS, another at 6:00 AM sends critical alert if still incomplete
  • B. Set the pipeline timeout to 6:00 AM and alert on timeout
  • C. Use a CloudWatch alarm with two thresholds
  • D. Have the pipeline send a "completion" event and alert if not received
Jawaban Benar: A
Two scheduled checks implement the escalating alert pattern: 5:30 AM Lambda checks pipeline status → if incomplete, publishes WARNING to SNS topic 1 (team email). 6:00 AM check → if still incomplete, publishes CRITICAL to SNS topic 2 (manager pager + team). This provides early warning for proactive intervention before SLA breach. Opsi B (single timeout) only alerts after SLA already breached. Opsi C (CloudWatch) can't check "not completed by time X." Opsi D (missing event) — complex to implement reliably.

A data engineering team uses Amazon SQS as a buffer between pipeline stages. They need to be alerted when the queue depth exceeds 10,000 messages, indicating a processing backlog. Which monitoring and alerting configuration is correct?
  • A. Create a CloudWatch alarm on the ApproximateNumberOfMessagesVisible metric with threshold > 10,000, with the alarm action publishing to an SNS topic
  • B. Create a Lambda function polling the queue depth via GetQueueAttributes every minute
  • C. Configure SQS to send notifications when the queue is full
  • D. Use EventBridge to detect SQS queue depth changes
Jawaban Benar: A
SQS natively publishes ApproximateNumberOfMessagesVisible metric to CloudWatch. CloudWatch alarm monitors this metric and triggers when threshold is breached. Alarm action sends to SNS topic for team notification. This is the standard AWS pattern for queue depth monitoring — no custom code needed. Opsi B (Lambda polling) reinvents CloudWatch's built-in capability. Opsi C — SQS doesn't have built-in "queue full" notifications. Opsi D — EventBridge doesn't monitor SQS queue depth natively.

A Step Functions workflow has an on-failure SNS notification. When the workflow fails, the SNS notification is sent but only contains the execution ARN, not the actual error details. How can the notification include meaningful error information?
  • A. Use an EventBridge rule matching Step Functions execution status change to FAILED, with input transformation to extract the error and cause fields from the event detail, and target the SNS topic with the formatted message
  • B. Configure SNS to automatically fetch details from Step Functions
  • C. Add a Catch state in Step Functions that formats and sends the error to SNS directly
  • D. Increase the SNS message size limit to include full execution history
Jawaban Benar: C
Adding a Catch block (global or per-state) that catches errors and transitions to a "NotifyFailure" state allows formatting the error details (Error, Cause fields) and publishing to SNS with full context. The Catch state receives the error information which can be included in the SNS message. Opsi A (EventBridge) works too but Catch is more direct and captures error details within the workflow. Opsi B — SNS cannot fetch external data. Opsi D — message size not the issue; content is.

A company wants to integrate pipeline alerts with their Slack channel and PagerDuty for incident management. The alerts originate from an SNS topic. Which architecture enables multi-channel notification delivery?
  • A. SNS topic with multiple subscriptions: Lambda function for Slack (calling Slack webhook API) and HTTPS endpoint subscription for PagerDuty's Events API
  • B. Create separate EventBridge rules for each destination
  • C. Use AWS Chatbot for Slack integration and a separate SNS subscription for PagerDuty
  • D. Send all alerts to email and let team members forward to Slack/PagerDuty manually
Jawaban Benar: C
AWS Chatbot is the native AWS service for Slack integration — it subscribes to SNS topics and formats alerts nicely in Slack channels. For PagerDuty, HTTPS endpoint subscription or Lambda subscriber calls PagerDuty's API. This is the AWS-recommended approach. Opsi A (custom Lambda for Slack) works but AWS Chatbot is simpler. Opsi B (EventBridge) could work but adds complexity if SNS is already the alert source. Opsi D (manual) defeats automation purpose.
7
A data pipeline publishes processing metrics to SNS after each run. Downstream consumers (dashboard, alerting, auditing) subscribe to this topic. One consumer (the auditing system) must receive EVERY message without loss, even during outages. Which SNS subscription type guarantees this?
  • A. Subscribe an SQS queue to the SNS topic for the auditing system — SQS retains messages during consumer outages and provides at-least-once delivery guarantee
  • B. Use an email subscription for the auditing system
  • C. Use an HTTP endpoint subscription with retry enabled
  • D. Subscribe a Lambda function for the auditing system
Jawaban Benar: A
SQS subscription provides durability — messages persist in the queue (up to 14 days) even if the auditing consumer is down. When the consumer recovers, it processes queued messages. SNS → SQS is the standard pattern for guaranteed delivery to asynchronous consumers. Opsi B (email) — emails can be lost, no acknowledgment mechanism. Opsi C (HTTP endpoint) — if endpoint is down, SNS retries for limited time then gives up. Opsi D (Lambda) — if Lambda fails/throttles, message could be lost without DLQ configuration.
8
A data engineer needs to send different types of alerts from a single SNS topic: "pipeline-alerts". Some subscribers only want failure alerts, others want all alerts including success notifications. How can subscribers selectively receive messages?
  • A. Use SNS message attributes (e.g., "alertType": "FAILURE") and configure subscription filter policies on each subscriber to match only their desired alertType values
  • B. Create separate SNS topics for each alert type
  • C. Include filter instructions in the message body
  • D. Let subscribers discard unwanted messages after receiving them
Jawaban Benar: A
SNS subscription filter policies allow subscribers to receive only messages with matching attributes. Publisher sets MessageAttributes (alertType=FAILURE, SUCCESS, etc.). Subscriber A's filter: {"alertType": ["FAILURE"]}. Subscriber B's filter: {"alertType": ["FAILURE", "SUCCESS"]}. Messages not matching a subscriber's filter are not delivered to that subscriber. Opsi B (separate topics) increases publisher complexity. Opsi C (body instructions) SNS doesn't filter on body. Opsi D (discard after receipt) wastes resources.

A Kinesis Data Stream consumer (Lambda) is falling behind — the IteratorAge metric is increasing. The data engineer wants to be alerted when IteratorAge exceeds 5 minutes (300,000 ms), indicating the consumer is lagging. Which alerting configuration is CORRECT?
  • A. CloudWatch alarm on GetRecords.IteratorAgeMilliseconds metric (Maximum statistic) with threshold > 300000, alarm action targeting SNS topic
  • B. CloudWatch alarm on IncomingRecords metric exceeding a threshold
  • C. Lambda CloudWatch Logs metric filter for "IteratorAge" text
  • D. EventBridge rule matching Kinesis stream events
Jawaban Benar: A
GetRecords.IteratorAgeMilliseconds is the Kinesis metric showing how far behind the consumer is. Maximum statistic captures the worst-case lag. Alarm threshold 300,000 ms = 5 minutes. When breached, alarm publishes to SNS. This directly monitors consumer lag. Opsi B (IncomingRecords) shows ingestion rate, not consumer lag. Opsi C (log filter) requires the Lambda to explicitly log iterator age. Opsi D — Kinesis doesn't emit EventBridge events for consumer lag.

A data pipeline processes sensitive financial data. Compliance requires that alert notifications (sent via SNS) must NOT contain actual data values — only metadata like job name, status, and timestamp. A developer accidentally publishes customer account numbers in SNS messages. How can this be prevented architecturally?
  • A. Implement a Lambda function between the pipeline and SNS that sanitizes messages — removing or masking any PII/sensitive data before publishing to SNS, using a predefined allow-list of safe fields
  • B. Enable SNS encryption at rest
  • C. Use SNS message filtering to block messages containing numbers
  • D. Add an IAM policy preventing certain data from being published
Jawaban Benar: A
A sanitization Lambda acts as a gatekeeper between the pipeline and SNS. It validates that only allowed fields (job_name, status, timestamp) are present, strips or masks anything else. This enforces the compliance policy regardless of what the pipeline code sends. Allow-list approach is more secure than deny-list. Opsi B (encryption at rest) protects stored data, doesn't prevent sensitive data in message content. Opsi C (filtering) blocks entire messages, doesn't sanitize content. Opsi D (IAM) cannot inspect message content.
