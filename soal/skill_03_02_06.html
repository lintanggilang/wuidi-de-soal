A data engineer needs to calculate a 7-day rolling average of daily revenue in Amazon Redshift. The query should include the current day and the 6 preceding days. For days with fewer than 7 data points (first 6 days of the dataset), the average should still be calculated using available data. Which SQL window function clause correctly implements this?
  • A. AVG(revenue) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
  • B. SUM(revenue) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) / 7
  • C. AVG(revenue) OVER (ORDER BY date RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW)
  • D. AVG(revenue) OVER (ORDER BY date ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING)
Correct Answer: A
AVG() with ROWS BETWEEN 6 PRECEDING AND CURRENT ROW calculates rata-rata from maximum 7 rows (6 previously + current). AVG() automatically divides with number rows that there is in window, jadi for 6 days first will uses number data that available.

Option A: CORRECT.
Option B: INCORRECT. Always divides with 7 although less from 7 data points available, produces rata-rata that incorrect for days-days first.
Option C: INCORRECT. Uses RANGE that in Redshift has behavior different with ROWS for date types.
Option D: INCORRECT. Mengecualikan current row.

The report also needs subtotals per quarter. Which SQL clause in Amazon Redshift provides this multi-level aggregation in a single query?
  • A. GROUP BY ROLLUP(quarter, category)
  • B. GROUP BY CUBE(quarter, category) configured for optimal performance
  • C. GROUP BY GROUPING SETS((quarter, category), (quarter), ())

GROUPING SETS provides kontrol eksplisit above level agregasi that diinginkan. (quarter, category) provides detail per quarter per category, (quarter) provides subtotal per quarter, and () provides grand total. This persis memenuhi requirement.

Option A: INCORRECT. Will produces subtotals hierarchical from kanan: (quarter, category), (quarter), () that sebenarnya also correct in case this - however GROUPING SETS more eksplisit.
Option B: INCORRECT. Produces all possibility kombinasi including (category) alone that not requested — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: CORRECT.
Option D: INCORRECT. Requires multiple passes and UNION that less efficient.

  • A. Use conditional aggregation: SELECT product, SUM(CASE WHEN region='East' THEN sales_amount END) as East, SUM(CASE WHEN region='West' THEN sales_amount END) as West, ... GROUP BY product
  • B. Use UNPIVOT to reshape and then GROUP BY configured for optimal performance and minimal operational overhead, meeting the latency and throughput goals of the design
  • C. Use PIVOT clause: SELECT * FROM sales_table PIVOT (SUM(sales_amount) FOR region IN ('East', 'West', 'North', 'South')), handling the described workload reliably at scale
  • D. Use CROSSTAB function from the tablefunc extension, handling the described workload reliably at scale and integrating natively with the rest of the pipeline
Correct Answer: A
Conditional aggregation with CASE WHEN is technique pivot that most reliable and widely supported in Amazon Redshift. Each column output didefinisikan as aggregate with CASE that filters region certain.

Option A: CORRECT.
Option B: INCORRECT. Melakukan kebalikan from that requested — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Available in several database (SQL Server, Oracle) and Redshift new only adds dukungannya, however conditional aggregation still becomes approach most portable and well-understood.

The dataset has billions of events and exact COUNT(DISTINCT visitor_id) is too slow. The acceptable error margin is 2%. Which Redshift function provides the BEST performance-accuracy tradeoff?
  • A. Use a pre-computed materialized view with exact COUNT(DISTINCT)
  • B. APPROXIMATE COUNT(DISTINCT visitor_id) which uses HyperLogLog algorithm
  • C. COUNT(DISTINCT visitor_id) with a LIMIT clause to sample data

Option A: INCORRECT. Requires refresh time and storage, as well as still slow to compute initially.
Option B: CORRECT.
Option C: INCORRECT. Provides estimasi that not akurat and not representative.
Option D: INCORRECT. Not technique statistics that valid.

A data engineer is using PySpark on Amazon EMR to process IoT sensor data. Each record has a timestamp and a sensor_value. The engineer needs to compute a 1-hour rolling average grouped by sensor_id, handling late-arriving data with watermarks. Which PySpark approach correctly implements this?
  • A. df.groupBy("sensor_id").agg(avg("sensor_value")) with a filter on timestamp with partition-level ordering and dedicated throughput
  • B. df.groupBy(window(col("timestamp"), "1 hour"), col("sensor_id")).agg(avg("sensor_value"))
  • C. df.groupBy("sensor_id", "hour").pivot("hour").agg(avg("sensor_value"))
  • D. df.withColumn("rolling_avg", avg("sensor_value").over(Window.partitionBy("sensor_id").orderBy("timestamp").rangeBetween(-3600, 0)))
Correct Answer: D
Window function with rangeBetween(-3600, 0) on column timestamp (in seconds) calculates rolling average 1 hours for each row, looking back 3600 seconds from current row. partitionBy("sensor_id") ensures kalkulasi per sensor. This provides true rolling average not tumbling window.

Option A: INCORRECT. Only provides overall average, not rolling — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Uses tumbling window (fixed 1-hour windows) not rolling window.
Option C: INCORRECT. Changes shape data, not calculates rolling average.
Option D: CORRECT.

A data analyst is querying a time-series table in Amazon Athena. The table has columns: event_timestamp, user_id, and event_type. The analyst needs to aggregate events into 15-minute buckets showing the count of each event type per bucket. Which Athena SQL function is MOST appropriate for creating the time buckets?
  • A. EXTRACT(HOUR FROM event_timestamp) || ':' || LPAD(CAST(FLOOR(EXTRACT(MINUTE FROM event_timestamp)/15)*15 AS VARCHAR), 2, '0')
  • B. DATE_TRUNC('minute', event_timestamp) with additional modulo arithmetic for 15-minute alignment
  • C. date_trunc('hour', event_timestamp) + (minute(event_timestamp) / 15) * interval '15' minute
  • D. FROM_UNIXTIME(FLOOR(TO_UNIXTIME(event_timestamp) / 900) * 900) to create 15-minute aligned buckets
Correct Answer: D
Mengkonversi timestamp to unix time (seconds), divides with 900 (15 minutes × 60 seconds), floor for rounding down, lalu kali returns 900 and konversi to timestamp. This provides 15-minute aligned buckets that akurat. Digunakan with GROUP BY for aggregation.

Option A: INCORRECT. Produces string not timestamp, kehilangan temporal ordering.
Option B: INCORRECT. Only truncate to minutes, requires logic additional that rumit.
Option C: INCORRECT. In a konseptual correct but syntax integer division in Athena (Presto) requires CAST that creates less clean.
Option D: CORRECT.

A data engineer has a table with NULL values in the quantity column. When computing SUM(quantity) grouped by category, some categories have all NULL quantities. The business requirement is: categories with all-NULL quantities should show 0 in the report, not NULL. Which approach correctly handles this in Amazon Redshift?
  • A. SELECT category, NVL(SUM(quantity), 0) FROM table GROUP BY category
  • B. SELECT category, SUM(quantity) FROM table GROUP BY category
  • C. SELECT category, SUM(COALESCE(quantity, 0)) FROM table GROUP BY category
  • D. SELECT category, COALESCE(SUM(quantity), 0) FROM table GROUP BY category
Correct Answer: D
COALESCE(SUM(quantity), 0) handles case where SUM() returns NULL (when all values in group is NULL). SUM() in SQL mengabaikan NULLs, and if ALL values is NULL, hasilnya NULL. COALESCE mengkonversi NULL final becomes 0.

Option A: INCORRECT. Equivalent with COALESCE in Redshift and also correct - however COALESCE more standard SQL.
Option B: INCORRECT. Will menampilkan NULL for all-NULL categories.
Option C: INCORRECT. Changes each NULL becomes 0 before SUM - this produces 0 also but changes semantics because NULLs that should diabaikan malah is calculated as 0.
Option D: CORRECT.

The table has 50 different metric names. This operation needs to be performed in Amazon Athena. What is the challenge and recommended approach?

Tantangannya is 50 column creates query panjang but still efficient because single table scan. MAX is used because each sensor_id + metric_name combination only has one value.

A data engineer needs to compute year-over-year growth percentage for monthly revenue in Amazon Redshift. The table has columns: month_date and revenue. The result should show each month alongside its year-over-year growth rate. Which SQL approach is MOST efficient?
  • A. Create two CTEs (current year and previous year) and join them on month number configured for optimal performance and minimal operational overhead
  • B. Self-join the table on month number where the left table's year is one more than the right table's year
  • C. Use LAG(revenue, 12) OVER (ORDER BY month_date) to get the same month from previous year, then calculate percentage change
  • D. Use a correlated subquery that finds revenue for the same month in the previous year, keeping steady-state operating costs low
Correct Answer: C
LAG(revenue, 12) OVER (ORDER BY month_date) efficient because accesses row 12 posisi previously (12 months = 1 years) in single pass. Then (revenue - LAG(revenue,12)) / LAG(revenue,12) * 100 provides growth percentage. Window functions in Redshift very optimized.

Option A: INCORRECT. More verbose and less efficient dibanding single window function pass — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Requires full table scan two kali.
Option C: CORRECT.
Option D: INCORRECT. Very not efficient for large tables.

They need to compute: (1) total revenue per customer, (2) average order value per customer, (3) number of unique products purchased per customer, and (4) days since last purchase per customer. All aggregations should be computed in a single pass over the data. Which PySpark approach is MOST efficient?
  • A. Run four separate groupBy operations and join the results on customer_id
  • B. Use df.groupBy("customer_id").agg(sum("revenue"), avg("order_value"), countDistinct("product_id"), datediff(current_date(), max("purchase_date")))
  • C. Use a window function with PARTITION BY customer_id for each metric separately configured for optimal performance and minimal operational overhead
  • D. Convert to pandas DataFrame and use pandas groupby with multiple aggregation functions
Correct Answer: B
PySpark groupBy().agg() with multiple aggregate functions calculates all metrik in single shuffle operation. sum(), avg(), countDistinct(), and max() all dikomputasi in one pass after groupBy. datediff with max(purchase_date) provides days since last purchase. This most efficient because only one shuffle.

Option A: INCORRECT. Produces 4 shuffle operations and 3 joins additional.
Option B: CORRECT.
Option C: INCORRECT. Not mengagregasi rows, only adds column to each row — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Will fails on large datasets because memory constraints.
