Managing database-level access control in Amazon Redshift and other databases

1
A company's Redshift data warehouse has 50 analysts who need read-only access to the "sales" schema and 10 data engineers who need full access to all schemas. Currently, permissions are granted individually to each user. The DBA wants to simplify permission management. Which approach is MOST efficient?
  • A. Create a superuser account shared by all analysts and another shared by all engineers
  • B. Create a Redshift role "analysts_readonly" with SELECT on all tables in "sales" schema, and a role "engineers_full" with ALL on all schemas; then GRANT each role to the respective users. When new users join, simply GRANT the appropriate role
  • C. Use Redshift Spectrum to isolate analyst queries from engineer queries
  • D. Create separate Redshift clusters for analysts and engineers with SELECT on all tables in "sales" schema
Jawaban Benar: B
Redshift roles (introduced as native feature) memungkinkan centralized permission management: CREATE ROLE analysts_readonly; GRANT SELECT ON ALL TABLES IN SCHEMA sales TO ROLE analysts_readonly; GRANT ROLE analysts_readonly TO user1, user2, ..., user50; Benefit: (1) Permissions didefinisikan SEKALI di role, (2) New users hanya perlu GRANT role — no need to repeat permission statements, (3) Permission changes (e.g., add new table) hanya perlu update role — automatically applies to all members, (4) Audit simplified — check role membership vs 50 individual grants. Redshift role hierarchy juga memungkinkan roles inherit dari roles lain. Opsi A (shared superuser) — massive security risk, no audit trail per-user, violates least privilege. Opsi C (Spectrum) — query engine feature bukan access control mechanism. Opsi D (separate clusters) — expensive dan data duplication needed.
2
A healthcare company stores patient data in Redshift. Regulations require that customer service representatives can see patient names and appointment dates, but NOT diagnosis codes or treatment details. All data is in a single "patients" table with columns: patient_id, name, appointment_date, diagnosis_code, treatment_details, billing_amount. Which Redshift feature enforces this MOST effectively?
  • A. Create a view that excludes sensitive columns and grant access only to the view
  • B. Use column-level access control — GRANT SELECT (patient_id, name, appointment_date) ON patients TO ROLE customer_service; this ensures the role can only query permitted columns, and any attempt to SELECT diagnosis_code will return a permission error
  • C. Use dynamic data masking to show NULL for restricted columns
  • D. Separate the table into two tables and restrict access to the sensitive table configured for optimal performance and minimal operational overhead
Jawaban Benar: B
Column-level access control di Redshift memungkinkan GRANT/REVOKE pada specific columns: GRANT SELECT (patient_id, name, appointment_date) ON TABLE patients TO ROLE customer_service; Behavior: Jika user mencoba SELECT * FROM patients — query fails dengan "permission denied for column diagnosis_code". User HARUS explicitly list only permitted columns. Ini enforce security di database engine level — tidak bisa di-bypass melalui application layer. Opsi A (views) bekerja sebagai alternative approach — CREATE VIEW patient_safe AS SELECT patient_id, name, appointment_date FROM patients — tapi pengguna masih perlu dicegah akses ke base table langsung. Views + column-level grants bisa dikombinasikan untuk defense-in-depth. Opsi C (masking) shows NULL tapi user TAHU kolom exists — mungkin tidak compliant dengan regulations yang memerlukan "no access". Opsi D (table separation) requires application changes dan JOIN complexity.
3
A multi-tenant SaaS company uses Amazon Redshift to store data for 200 customers. Each customer's data is identified by a "tenant_id" column in every table. The company needs to ensure that when a customer's analyst runs queries, they can ONLY see their own tenant's data — without relying on application-level WHERE clause filtering. Which Redshift feature provides this server-enforced row-level security?
  • A. Create separate schemas for each tenant and grant access to only their schema
  • B. Implement Row-Level Security (RLS) policies in Redshift — CREATE RLS POLICY tenant_isolation USING (tenant_id = current_setting('app.tenant_id')); ATTACH RLS POLICY to tables and enable for the analyst role. The policy automatically filters rows based on the session variable
  • C. Use Redshift Spectrum with S3 bucket-per-tenant partitioning and enable for the analyst role for the analyst role
  • D. Add WHERE tenant_id = ? to all views accessed by customers
Jawaban Benar: B
Redshift Row-Level Security (RLS) policies transparently filter rows at query execution time: (1) CREATE RLS POLICY tenant_isolation WITH (tenant_id int) USING (tenant_id = current_setting('app.tenant_id')::int); (2) ATTACH RLS POLICY tenant_isolation ON sales TO ROLE tenant_analyst; (3) ALTER TABLE sales ROW LEVEL SECURITY ON; Saat tenant analyst menjalankan SELECT * FROM sales, Redshift automatically appends WHERE tenant_id = {their_tenant_id}. Advantages: Database-enforced (cannot bypass), transparent to queries (no application changes needed), works with any SQL client, auditable, cannot be accidentally removed by developers. Session variable (SET app.tenant_id) di-set saat connection establishment. Opsi A (separate schemas) works tapi 200 schemas = management nightmare, schema DDL changes harus di-replicate 200x. Opsi C (Spectrum per-tenant) expensive — 200 buckets. Opsi D (views with WHERE) can be bypassed jika user gains direct table access.
4
A data engineer needs to audit who has access to what in their Redshift cluster. The security team requests a report showing: all users, their group memberships, and effective permissions on the "finance" schema. Which system tables/views should the engineer query?
  • A. Query pg_catalog.pg_user for users, pg_catalog.pg_group for group memberships, and SVV_RELATION_PRIVILEGES for effective permissions on schema objects
  • B. Check CloudTrail logs for all Redshift GRANT statements executed in the past year
  • C. Query STL_QUERY system table for all SELECT statements on the finance schema configured for optimal performance and minimal operational overhead
  • D. Use AWS Config to evaluate Redshift database permissions
Jawaban Benar: A
Redshift provides system tables/views untuk permission auditing: pg_catalog.pg_user: Lists all database users (usename, usesysid, usesuper). pg_catalog.pg_group: Shows group names and member user IDs (groname, grolist). SVV_RELATION_PRIVILEGES: Shows effective permissions on tables/views — includes: identity_name (user/role), identity_type, relation_name, privilege_type. Additional useful views: SVV_ROLE_GRANTS: Shows role hierarchy dan membership, HAS_TABLE_PRIVILEGE(): Function to check specific user's access, pg_catalog.pg_namespace: Schema information. Example audit query: SELECT u.usename, g.groname, rp.relation_name, rp.privilege_type FROM pg_user u LEFT JOIN pg_group g ON u.usesysid = ANY(g.grolist) JOIN svv_relation_privileges rp ON rp.identity_name = u.usename WHERE rp.namespace_name = 'finance'; Opsi B (CloudTrail) shows API calls ke Redshift service tapi TIDAK in-database SQL permissions. Opsi C (STL_QUERY) shows query history bukan permissions. Opsi D (AWS Config) evaluates cluster-level configuration, bukan database-internal permissions.

A data engineer wants to implement IAM-based authentication for an Amazon RDS PostgreSQL database, eliminating the need for database passwords entirely. Application Lambda functions should authenticate to RDS using their IAM role. Which configuration steps are required?
  • A. Enable IAM database authentication on the RDS instance, create a database user mapped to the IAM role using GRANT rds_iam TO db_user, and configure the Lambda function to generate an authentication token using the RDS API (generate-db-auth-token) which is used as the password when connecting
  • B. Simply attach the AmazonRDSFullAccess policy to the Lambda role — RDS will automatically recognize it
  • C. Store IAM credentials in the RDS parameter group and enable auto-authentication configured for optimal performance and minimal operational overhead
  • D. Create an RDS Proxy and it will automatically handle IAM authentication without any database-level configuration
Jawaban Benar: A
RDS IAM Database Authentication memerlukan konfigurasi di multiple layers: Step 1 — RDS Instance: Modify DB instance → Enable IAM DB Authentication. Step 2 — Database level: CREATE USER lambda_app WITH LOGIN; GRANT rds_iam TO lambda_app; (rds_iam role indicates user authenticates via IAM). Step 3 — IAM Policy: Allow rds-db:connect pada resource "arn:aws:rds-db:region:account:dbuser:dbi-resource-id/lambda_app". Step 4 — Application code: token = rds_client.generate_db_auth_token(DBHostname, Port, DBUser); Connect menggunakan token sebagai password (valid 15 minutes). Benefits: No persistent passwords, token auto-expires, leverages IAM for centralized access control, integrates with CloudTrail. Opsi B — AmazonRDSFullAccess grants RDS API permissions (CreateDB, etc.), NOT database-level connectivity. Opsi C — not a valid configuration. Opsi D — RDS Proxy supports IAM auth tapi database-level GRANT rds_iam still needed.
6
A Redshift administrator creates the following permission structure: Group "analytics" has SELECT on schema "reporting". User "john" is a member of group "analytics". An explicit REVOKE SELECT on reporting.revenue_table FROM john is also applied. What happens when john tries to SELECT from reporting.revenue_table?
  • A. Access is allowed because group permissions override individual user revocations
  • B. Access is allowed because john inherits SELECT from the "analytics" group, and the individual REVOKE only removes directly-granted permissions, not group-inherited permissions — in Redshift, group grants and user grants are evaluated independently
  • C. Access is denied because REVOKE always overrides GRANT regardless of source
  • D. Access results in an error because conflicting permissions are not allowed configured for optimal performance and minimal operational overhead
Jawaban Benar: B
Redshift permission evaluation: Permissions dari groups dan individual users dievaluasi secara ADDITIVE (union). REVOKE pada user level hanya menghapus permissions yang directly granted ke user tersebut — TIDAK menghapus permissions yang inherited dari group membership. Dalam kasus ini: john's effective permissions = (permissions dari group "analytics") UNION (direct user permissions) - (direct user revocations). Karena SELECT didapat dari GROUP (bukan direct grant), REVOKE dari user tidak mempengaruhi. Untuk benar-benar block john dari revenue_table: (1) Remove john dari group "analytics", ATAU (2) REVOKE SELECT pada table dari GROUP "analytics" dan buat group baru tanpa table tersebut, ATAU (3) Gunakan RLS policy untuk deny access. Ini berbeda dari IAM dimana explicit Deny SELALU wins. Opsi A correct conclusion tapi wrong reasoning. Opsi C salah — Redshift bukan IAM (no explicit deny concept di database permissions). Opsi D — no error, just evaluated as described.
7
A data engineer needs to create a read-only role for business intelligence tools connecting to Redshift. The role should be able to SELECT from all CURRENT and FUTURE tables in the "analytics" schema. Which combination of GRANT statements ensures this?
  • A. GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO ROLE bi_readonly;
  • B. GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO ROLE bi_readonly; combined with ALTER DEFAULT PRIVILEGES IN SCHEMA analytics GRANT SELECT ON TABLES TO ROLE bi_readonly; — the first covers existing tables, the second ensures future tables automatically get the same grant
  • C. GRANT ALL ON SCHEMA analytics TO ROLE bi_readonly; with ALTER DEFAULT PRIVILEGES IN SCHEMA analytics GRANT SELECT ON TABLES
  • D. GRANT USAGE ON SCHEMA analytics TO ROLE bi_readonly; only
Jawaban Benar: B
Dua GRANT statements diperlukan untuk cover existing + future objects: (1) GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO ROLE bi_readonly — Memberikan SELECT pada semua tables yang SUDAH ADA saat statement dijalankan. (2) ALTER DEFAULT PRIVILEGES IN SCHEMA analytics GRANT SELECT ON TABLES TO ROLE bi_readonly — Mendefinisikan bahwa setiap table BARU yang dibuat di schema "analytics" akan otomatis mendapat GRANT SELECT ke bi_readonly role. Tanpa ALTER DEFAULT PRIVILEGES, setiap table baru memerlukan manual GRANT. Juga diperlukan: GRANT USAGE ON SCHEMA analytics TO ROLE bi_readonly (agar bisa "see" schema). Opsi A hanya cover existing tables — future tables won't be accessible. Opsi C (GRANT ALL) memberikan CREATE, DROP, dll — violates read-only requirement. Opsi D (USAGE only) mengizinkan melihat schema tapi tidak SELECT dari tables.
8
A company federates access to Amazon Redshift using IAM roles with SAML-based identity federation. Different teams assume different IAM roles. The DBA needs to map these federated IAM roles to appropriate Redshift database permissions. Which approach correctly maps IAM roles to Redshift database roles?
  • A. Create Redshift database users matching the IAM role names and manually assign permissions
  • B. Use Redshift's native IAM role integration — when federated users connect using GetClusterCredentials API with DbGroup parameter, they are automatically added to specified Redshift database groups; OR use role-based identity mapping where IAM roles are mapped to Redshift roles via the Redshift identity provider configuration
  • C. Federated users always get superuser access to Redshift with DbGroup parameter
  • D. Use S3 bucket policies to control Redshift access for federated users
Jawaban Benar: B
Redshift supports IAM-federated access melalui GetClusterCredentials API: Flow: (1) User authenticates via SAML/SSO → assumes IAM role, (2) Application calls redshift:GetClusterCredentials with parameters: DbUser (database username), DbGroups (Redshift groups to join), AutoCreate (auto-create user if not exists), (3) API returns temporary database credentials, (4) User connects to Redshift — automatically member of specified DbGroups. IAM Policy controls: IAM policy pada role determines WHICH DbUsers dan DbGroups the federated user can request (via conditions). Redshift database permissions: Groups in Redshift have pre-configured GRANT permissions. Mapping: IAM Role "analysts-role" → allowed DbGroups: ["analytics_readonly"] → Redshift group "analytics_readonly" has SELECT on analytics schema. Opsi A (manual users) doesn't scale for federation. Opsi C salah — federated users get permissions based on DbGroups, not superuser. Opsi D — S3 policies irrelevant for Redshift database access.
9
A data engineer discovers that a former contractor's database user in Redshift still has active permissions. The contractor's access was supposed to be revoked when they left 3 months ago. The DBA needs to: (1) immediately revoke all access, (2) audit what the user accessed in the past 3 months, and (3) prevent this from happening again. What is the correct remediation approach?
  • A. Only disable the user's password — their permissions will automatically expire
  • B. Execute ALTER USER contractor_user DISABLE; to immediately prevent login, then query STL_CONNECTION_LOG and STL_QUERY for the user's activity over the past 3 months, and implement a process using IAM-based temporary credentials (GetClusterCredentials) instead of persistent database passwords to ensure access automatically expires when IAM access is revoked
  • C. Delete the Redshift cluster and recreate it without the user
  • D. Wait for the password to expire naturally configured for optimal performance and minimal operational overhead
Jawaban Benar: B
Complete remediation approach: Immediate: ALTER USER contractor_user DISABLE; — prevents any new connections. Existing active sessions: SELECT pg_terminate_backend(pid) untuk kill active sessions. Also: REVOKE ALL ON ALL TABLES IN SCHEMA ... FROM contractor_user; untuk remove all permissions. Audit: STL_CONNECTION_LOG — shows all connections: login time, source IP, success/failure. STL_QUERY — shows all SQL executed by the user (full query text, timestamps, tables accessed). STL_QUERYTEXT — untuk queries yang terlalu panjang. SVL_STATEMENTTEXT — comprehensive statement log. Prevention: Migrate to IAM-based authentication via GetClusterCredentials. When contractor's IAM access is revoked (role assumption removed), they cannot generate DB credentials. Temporary credentials expire automatically (default 15 min - 3600 sec configurable). Opsi A — disabling password doesn't revoke permissions on existing sessions. Opsi C — extreme overreaction. Opsi D — passwords may not have expiry set.

A data warehouse team is implementing schema-level isolation in Redshift. They have schemas: "raw" (ETL landing), "staging" (transformations), and "presentation" (BI access). The requirements are: ETL role can write to raw and staging but NOT presentation; transformation role can read raw, write staging, and write presentation; BI role can ONLY read presentation. Which GRANT structure correctly implements this isolation?
  • A. Grant ALL on ALL schemas to all three roles for simplicity configured for optimal performance and minimal operational overhead
  • B. ETL role: GRANT USAGE, CREATE, INSERT, SELECT ON raw/staging schemas; Transformation role: GRANT SELECT ON raw, GRANT ALL ON staging/presentation; BI role: GRANT USAGE ON SCHEMA presentation + GRANT SELECT ON ALL TABLES IN SCHEMA presentation. Each role gets ONLY what's needed
  • C. Create separate Redshift clusters for each schema
  • D. Use only views in the presentation schema that reference staging tables, and grant SELECT on views only
Jawaban Benar: B
Schema-level isolation menggunakan precise GRANT statements: ETL Role: GRANT USAGE ON SCHEMA raw, staging TO ROLE etl_role; GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA raw TO ROLE etl_role; GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA staging TO ROLE etl_role; (NO grants on presentation schema — implicit deny). Transformation Role: GRANT USAGE ON SCHEMA raw, staging, presentation TO ROLE transform_role; GRANT SELECT ON ALL TABLES IN SCHEMA raw TO ROLE transform_role; GRANT ALL ON ALL TABLES IN SCHEMA staging, presentation TO ROLE transform_role; BI Role: GRANT USAGE ON SCHEMA presentation TO ROLE bi_role; GRANT SELECT ON ALL TABLES IN SCHEMA presentation TO ROLE bi_role; (Only USAGE + SELECT on presentation — cannot see raw/staging schemas). Key: USAGE permission on schema is required first — without it, user cannot even list objects. Opsi A violates least privilege. Opsi C expensive overengineering. Opsi D is good defense-in-depth addition but doesn't fully address schema isolation requirements.
