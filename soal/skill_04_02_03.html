A company's Redshift data warehouse has 50 analysts who need read-only access to the "sales" schema and 10 data engineers who need full access to all schemas. Currently, permissions are granted individually to each user. The DBA wants to simplify permission management. Which approach is MOST efficient?
  • A. Create a Redshift role "analysts_readonly" with SELECT on all tables in "sales" schema, and a role "engineers_full" with ALL on all schemas; then GRANT each role to the respective users. When new users join, simply GRANT the appropriate role
  • B. Create separate Redshift clusters for analysts and engineers with SELECT on all tables in "sales" schema, handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and transforming records into the required target format
  • C. Create a superuser account shared by all analysts and another shared by all engineers, transforming records into the required target format and satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline
  • D. Use Redshift Spectrum to isolate analyst queries from engineer queries, integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort and transforming records into the required target format and providing exactly-once processing semantics
Correct Answer: A
Redshift roles (introduced as native feature) enables centralized permission management: CREATE ROLE analysts_readonly; GRANT SELECT ON ALL TABLES IN SCHEMA sales TO ROLE analysts_readonly; GRANT ROLE analysts_readonly TO user1, user2, ..., user50; Benefit: (1) Permissions didefinisikan SEKALI in role, (2) New users only needs GRANT role — no need to repeat permission statements, (3) Permission changes (e.g., add new table) only needs update role — automatically applies to all members, (4) Audit simplified — check role membership vs 50 individual grants. Redshift role hierarchy also enables roles inherit from roles other.

Option A: CORRECT.
Option B: INCORRECT. Expensive and data duplication needed — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Massive security risk, no audit trail per-user, violates least privilege.
Option D: INCORRECT. Query engine feature not access control mechanism.

A healthcare company stores patient data in Redshift. Regulations require that customer service representatives can see patient names and appointment dates, but NOT diagnosis codes or treatment details. All data is in a single "patients" table with columns: patient_id, name, appointment_date, diagnosis_code, treatment_details, billing_amount. Which Redshift feature enforces this MOST effectively?
  • A. Separate the table into two tables and restrict access to the sensitive table configured for optimal performance and minimal operational overhead, handling the described workload reliably at scale and integrating natively with the rest of the pipeline
  • B. Use dynamic data masking to show NULL for restricted columns, handling the described workload reliably at scale and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort
  • C. Use column-level access control — GRANT SELECT (patient_id, name, appointment_date) ON patients TO ROLE customer_service; this ensures the role can only query permitted columns, and any attempt to SELECT diagnosis_code will return a permission error
  • D. Create a view that excludes sensitive columns and grant access only to the view, handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and reducing day-to-day operational effort
Correct Answer: C
Column-level access control in Redshift enables GRANT/REVOKE on specific columns: GRANT SELECT (patient_id, name, appointment_date) ON TABLE patients TO ROLE customer_service; Behavior: If user mencoba SELECT * FROM patients — query fails with "permission denied for column diagnosis_code". User MUST explicitly list only permitted columns. This enforce security in database engine level — cannot in-bypass through application layer.

Option A: INCORRECT. Requires application changes and JOIN complexity — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Shows NULL but user TAHU column exists — may not compliant with regulations that requires "no access".
Option C: CORRECT.
Option D: INCORRECT. Works as alternative approach — CREATE VIEW patient_safe AS SELECT patient_id, name, appointment_date FROM patients — but user still needs is prevented access to base table directly. Views + column-level grants can dikombinasikan for defense-in-depth.

A multi-tenant SaaS company uses Amazon Redshift to store data for 200 customers. Each customer's data is identified by a "tenant_id" column in every table. The company needs to ensure that when a customer's analyst runs queries, they can ONLY see their own tenant's data — without relying on application-level WHERE clause filtering. Which Redshift feature provides this server-enforced row-level security?
  • A. Use Redshift Spectrum with S3 bucket-per-tenant partitioning and enable for the analyst role, satisfying strict compliance and audit requirements and enforcing encryption and fine-grained access control and meeting the latency and throughput goals of the design
  • B. Implement Row-Level Security (RLS) policies in Redshift — CREATE RLS POLICY tenant_isolation USING (tenant_id = current_setting('app.tenant_id')); ATTACH RLS POLICY to tables and enable for the analyst role. The policy automatically filters rows based on the session variable
  • C. Create separate schemas for each tenant and grant access to only their schema, satisfying strict compliance and audit requirements and integrating natively with the rest of the pipeline and handling the described workload reliably at scale
  • D. Add WHERE tenant_id = ? to all views accessed by customers, integrating natively with the rest of the pipeline and protecting the data both in transit and at rest and satisfying strict compliance and audit requirements
Correct Answer: B
Redshift Row-Level Security (RLS) policies transparently filter rows at query execution time: (1) CREATE RLS POLICY tenant_isolation WITH (tenant_id int) USING (tenant_id = current_setting('app.tenant_id')::int); (2) ATTACH RLS POLICY tenant_isolation ON sales TO ROLE tenant_analyst; (3) ALTER TABLE sales ROW LEVEL SECURITY ON; When tenant analyst runs SELECT * FROM sales, Redshift automatically appends WHERE tenant_id = {their_tenant_id}. Advantages: Database-enforced (cannot bypass), transparent to queries (no application changes needed), works with any SQL client, auditable, cannot be accidentally removed by developers. Session variable (SET app.tenant_id) in-set when connection establishment.

Option A: INCORRECT. Expensive — 200 buckets — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: CORRECT.
Option C: INCORRECT. Works but 200 schemas = management nightmare, schema DDL changes must in-replicate 200x.
Option D: INCORRECT. Can be bypassed if user gains direct table access.

A data engineer needs to audit who has access to what in their Redshift cluster. The security team requests a report showing: all users, their group memberships, and effective permissions on the "finance" schema. Which system tables/views should the engineer query?
  • A. Use AWS Config to evaluate Redshift database permissions, applying schema conversion and enrichment inline
  • B. Query STL_QUERY system table for all SELECT statements on the finance schema configured for optimal performance and minimal operational overhead
  • C. Check CloudTrail logs for all Redshift GRANT statements executed in the past year
  • D. Query pg_catalog.pg_user for users, pg_catalog.pg_group for group memberships, and SVV_RELATION_PRIVILEGES for effective permissions on schema objects
Correct Answer: D
Redshift provides system tables/views for permission auditing: pg_catalog.pg_user: Lists all database users (usename, usesysid, usesuper). pg_catalog.pg_group: Shows group names and member user IDs (groname, grolist). SVV_RELATION_PRIVILEGES: Shows effective permissions on tables/views — includes: identity_name (user/role), identity_type, relation_name, privilege_type. Additional useful views: SVV_ROLE_GRANTS: Shows role hierarchy and membership, HAS_TABLE_PRIVILEGE(): Function to check specific user's access, pg_catalog.pg_namespace: Schema information. Example audit query: SELECT u.usename, g.groname, rp.relation_name, rp.privilege_type FROM pg_user u LEFT JOIN pg_group g ON u.usesysid = ANY(g.grolist) JOIN svv_relation_privileges rp ON rp.identity_name = u.usename WHERE rp.namespace_name = 'finance'.

Option A: INCORRECT. Evaluates cluster-level configuration, not database-internal permissions.
Option B: INCORRECT. Shows query history not permissions — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Shows API calls to Redshift service but TIDAK in-database SQL permissions.
Option D: CORRECT.

Store IAM credentials in the RDS parameter group and enable auto-authentication configured for optimal performance and minimal operational overhead, integrating natively with the rest of the pipeline and protecting the data both in transit and at rest and meeting the latency and throughput goals of the design
  • B. Simply attach the AmazonRDSFullAccess policy to the Lambda role — RDS will automatically recognize it, protecting the data both in transit and at rest and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design
  • C. Enable IAM database authentication on the RDS instance, create a database user mapped to the IAM role using GRANT rds_iam TO db_user, and configure the Lambda function to generate an authentication token using the RDS API (generate-db-auth-token) which is used as the password when connecting
  • D. Create an RDS Proxy and it will automatically handle IAM authentication without any database-level configuration, enforcing encryption and fine-grained access control and meeting the latency and throughput goals of the design and satisfying strict compliance and audit requirements and integrating natively with the rest of the pipeline
Correct Answer: C
RDS IAM Database Authentication requires configuration in multiple layers: Step 1 — RDS Instance: Modify DB instance → Enable IAM DB Authentication. Step 2 — Database level: CREATE USER lambda_app WITH LOGIN; GRANT rds_iam TO lambda_app; (rds_iam role indicates user authenticates via IAM). Step 3 — IAM Policy: Allow rds-db:connect on resource "arn:aws:rds-db:region:account:dbuser:dbi-resource-id/lambda_app". Step 4 — Application code: token = rds_client.generate_db_auth_token(DBHostname, Port, DBUser); Connect uses token as password (valid 15 minutes). Benefits: No persistent passwords, token auto-expires, leverages IAM for centralized access control, integrates with CloudTrail.

Option A: INCORRECT. Not a valid configuration — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. AmazonRDSFullAccess grants RDS API permissions (CreateDB, etc.), NOT database-level connectivity.
Option C: CORRECT.
Option D: INCORRECT. RDS Proxy supports IAM auth but database-level GRANT rds_iam still needed.

A Redshift administrator creates the following permission structure: Group "analytics" has SELECT on schema "reporting". User "john" is a member of group "analytics". An explicit REVOKE SELECT on reporting.revenue_table FROM john is also applied. What happens when john tries to SELECT from reporting.revenue_table?
  • A. Access is allowed because group permissions override individual user revocations, applying schema conversion and enrichment inline and transforming records into the required target format and satisfying all of the stated requirements with minimal effort
  • B. Access is denied because REVOKE always overrides GRANT regardless of source, integrating natively with the rest of the pipeline and handling the described workload reliably at scale and validating and cleansing each record before delivery
  • C. Access is allowed because john inherits SELECT from the "analytics" group, and the individual REVOKE only removes directly-granted permissions, not group-inherited permissions — in Redshift, group grants and user grants are evaluated independently
  • D. Access results in an error because conflicting permissions are not allowed configured for optimal performance and minimal operational overhead, applying schema conversion and enrichment inline and integrating natively with the rest of the pipeline
Correct Answer: C
Redshift permission evaluation: Permissions from groups and individual users dievaluasi in a ADDITIVE (union). REVOKE on user level only deletes permissions that directly granted to user said — TIDAK deletes permissions that inherited from group membership. In case this: john's effective permissions = (permissions from group "analytics") UNION (direct user permissions) - (direct user revocations). Because SELECT didapat from GROUP (not direct grant), REVOKE from user not affects. For correct-correct block john from revenue_table: (1) Remove john from group "analytics", ATAU (2) REVOKE SELECT on table from GROUP "analytics" and buat group new without table said, ATAU (3) Gunakan RLS policy for deny access. This different from IAM where explicit Deny SELALU wins.

Option A: INCORRECT. Correct conclusion but wrong reasoning.
Option B: INCORRECT. Incorrect — Redshift not IAM (no explicit deny concept in database permissions).
Option C: CORRECT.
Option D: INCORRECT. No error, just evaluated as described — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data engineer needs to create a read-only role for business intelligence tools connecting to Redshift. The role should be able to SELECT from all CURRENT and FUTURE tables in the "analytics" schema. Which combination of GRANT statements ensures this?
  • A. GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO ROLE bi_readonly; combined with ALTER DEFAULT PRIVILEGES IN SCHEMA analytics GRANT SELECT ON TABLES TO ROLE bi_readonly; — the first covers existing tables, the second ensures future tables automatically get the same grant
  • B. GRANT ALL ON SCHEMA analytics TO ROLE bi_readonly; with ALTER DEFAULT PRIVILEGES IN SCHEMA analytics GRANT SELECT ON TABLES, applying schema conversion and enrichment inline and validating and cleansing each record before delivery and satisfying all of the stated requirements with minimal effort
  • C. GRANT USAGE ON SCHEMA analytics TO ROLE bi_readonly; only, validating and cleansing each record before delivery and transforming records into the required target format and handling the described workload reliably at scale and integrating natively with the rest of the pipeline
  • D. GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO ROLE bi_readonly;, transforming records into the required target format and handling the described workload reliably at scale and meeting the latency and throughput goals of the design and validating and cleansing each record before delivery
Correct Answer: A
Dua GRANT statements is required for cover existing + future objects: (1) GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO ROLE bi_readonly — Provides SELECT on all tables that ALREADY EXIST when statement is run. (2) ALTER DEFAULT PRIVILEGES IN SCHEMA analytics GRANT SELECT ON TABLES TO ROLE bi_readonly — Mendefinisikan that each table NEW that is created in schema "analytics" will automatic mendapat GRANT SELECT to bi_readonly role. Without ALTER DEFAULT PRIVILEGES, each table new requires manual GRANT. Also is required: GRANT USAGE ON SCHEMA analytics TO ROLE bi_readonly (so that can "see" schema).

Option A: CORRECT.
Option B: INCORRECT. Provides CREATE, DROP, dll — violates read-only requirement — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Mengizinkan melihat schema but not SELECT from tables.
Option D: INCORRECT. Only cover existing tables — future tables won't be accessible.

A company federates access to Amazon Redshift using IAM roles with SAML-based identity federation. Different teams assume different IAM roles. The DBA needs to map these federated IAM roles to appropriate Redshift database permissions. Which approach correctly maps IAM roles to Redshift database roles?
  • A. Create Redshift database users matching the IAM role names and manually assign permissions, satisfying strict compliance and audit requirements and integrating natively with the rest of the pipeline and enforcing encryption and fine-grained access control and handling the described workload reliably at scale
  • B. Use Redshift's native IAM role integration — when federated users connect using GetClusterCredentials API with DbGroup parameter, they are automatically added to specified Redshift database groups; OR use role-based identity mapping where IAM roles are mapped to Redshift roles via the Redshift identity provider configuration
  • C. Federated users always get superuser access to Redshift with DbGroup parameter, protecting the data both in transit and at rest and meeting the latency and throughput goals of the design and handling the described workload reliably at scale and enforcing encryption and fine-grained access control
  • D. Use S3 bucket policies to control Redshift access for federated users, integrating natively with the rest of the pipeline and enforcing encryption and fine-grained access control and satisfying strict compliance and audit requirements and meeting the latency and throughput goals of the design
Correct Answer: B
Redshift supports IAM-federated access through GetClusterCredentials API: Flow: (1) User authenticates via SAML/SSO → assumes IAM role, (2) Application calls redshift:GetClusterCredentials with parameters: DbUser (database username), DbGroups (Redshift groups to join), AutoCreate (auto-create user if not exists), (3) API returns temporary database credentials, (4) User connects to Redshift — automatically member of specified DbGroups. IAM Policy controls: IAM policy on role determines WHICH DbUsers and DbGroups the federated user can request (via conditions). Redshift database permissions: Groups in Redshift have pre-configured GRANT permissions. Mapping: IAM Role "analysts-role" → allowed DbGroups: ["analytics_readonly"] → Redshift group "analytics_readonly" has SELECT on analytics schema.

Option A: INCORRECT. Doesn't scale for federation.
Option B: CORRECT.
Option C: INCORRECT. Incorrect — federated users get permissions based on DbGroups, not superuser — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. S3 policies irrelevant for Redshift database access.

  • A.   • B.   • C. Temporary credentials expire automatically (default 15 min - 3600 sec configurable).

A data warehouse team is implementing schema-level isolation in Redshift. They have schemas: "raw" (ETL landing), "staging" (transformations), and "presentation" (BI access). The requirements are: ETL role can write to raw and staging but NOT presentation; transformation role can read raw, write staging, and write presentation; BI role can ONLY read presentation. Which GRANT structure correctly implements this isolation?
  • A. Use only views in the presentation schema that reference staging tables, and grant SELECT on views only, satisfying all of the stated requirements with minimal effort and transforming records into the required target format and handling the described workload reliably at scale
  • B. Create separate Redshift clusters for each schema, validating and cleansing each record before delivery and applying schema conversion and enrichment inline and transforming records into the required target format and handling the described workload reliably at scale and absorbing sudden traffic spikes without throttling
  • C. Grant ALL on ALL schemas to all three roles for simplicity configured for optimal performance and minimal operational overhead, validating and cleansing each record before delivery and transforming records into the required target format and satisfying all of the stated requirements with minimal effort
  • D. ETL role: GRANT USAGE, CREATE, INSERT, SELECT ON raw/staging schemas; Transformation role: GRANT SELECT ON raw, GRANT ALL ON staging/presentation; BI role: GRANT USAGE ON SCHEMA presentation + GRANT SELECT ON ALL TABLES IN SCHEMA presentation. Each role gets ONLY what's needed
Correct Answer: D
Schema-level isolation uses precise GRANT statements: ETL Role: GRANT USAGE ON SCHEMA raw, staging TO ROLE etl_role; GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA raw TO ROLE etl_role; GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA staging TO ROLE etl_role; (NO grants on presentation schema — implicit deny). Transformation Role: GRANT USAGE ON SCHEMA raw, staging, presentation TO ROLE transform_role; GRANT SELECT ON ALL TABLES IN SCHEMA raw TO ROLE transform_role; GRANT ALL ON ALL TABLES IN SCHEMA staging, presentation TO ROLE transform_role; BI Role: GRANT USAGE ON SCHEMA presentation TO ROLE bi_role; GRANT SELECT ON ALL TABLES IN SCHEMA presentation TO ROLE bi_role; (Only USAGE + SELECT on presentation — cannot see raw/staging schemas). Key: USAGE permission on schema is required first — without it, user cannot even list objects.

Option A: INCORRECT. Is good defense-in-depth addition but doesn't fully address schema isolation requirements.
Option B: INCORRECT. Expensive overengineering.
Option C: INCORRECT. Violates least privilege — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: CORRECT.
