A company's security audit reveals that some applications access their S3 data lake using HTTP instead of HTTPS. This means data travels in plaintext between the application and S3. How should the data engineer ENFORCE HTTPS-only access to S3 buckets?
  • A. Configure S3 server-side encryption — this automatically enforces HTTPS
  • B. Add an S3 bucket policy with a Deny statement that blocks all requests where the condition aws:SecureTransport equals "false" — this denies any HTTP (non-TLS) request regardless of which principal makes it. Combined with the aws:SecureTransport condition, only HTTPS connections are permitted to access objects in the bucket
  • C. Disable the HTTP endpoint on S3 — S3 can be configured to only listen on port 443
  • D. Use VPC endpoints which automatically enforce HTTPS without any policy changes
Jawaban Benar: B
S3 bucket policy dengan aws:SecureTransport condition enforces TLS: Policy: {"Effect": "Deny", "Principal": "*", "Action": "s3:*", "Resource": ["arn:aws:s3:::my-bucket", "arn:aws:s3:::my-bucket/*"], "Condition": {"Bool": {"aws:SecureTransport": "false"}}}. How it works: aws:SecureTransport = "true" → request made over HTTPS (TLS). aws:SecureTransport = "false" → request made over HTTP (plaintext). Deny when "false" → ONLY HTTPS requests succeed. Scope: Applies to ALL principals (Principal: "*"). Applies to ALL S3 actions (s3:*). Both bucket-level (arn:aws:s3:::my-bucket) and object-level (arn:aws:s3:::my-bucket/*). Important nuances: AWS SDK default: Most SDKs use HTTPS by default (but can be overridden). AWS CLI: Uses HTTPS by default. Legacy applications: May have hardcoded HTTP endpoints — will break (by design). VPC Endpoints: Traffic to S3 via VPC endpoint is ALWAYS HTTPS (gateway endpoints). This policy additionally ensures public access is also HTTPS-only. Opsi A — SSE encrypts data at rest, doesn't affect transport protocol. Opsi C — S3 doesn't have configurable listener ports; both HTTP/HTTPS always available at service level. Opsi D — VPC endpoints use HTTPS but don't prevent HTTP access through public endpoint.

A data engineer connects a Glue ETL job to an Amazon RDS PostgreSQL database using a JDBC connection. The security team requires TLS encryption for all database connections. How should the engineer configure the Glue JDBC connection to enforce TLS?
  • A. TLS is always active on Glue JDBC connections by default — no configuration needed
  • B. Configure the Glue JDBC connection URL with SSL parameters: add "?ssl=true&sslmode=verify-full&sslrootcert=path-to-rds-ca-cert" to the JDBC URL. Additionally, configure the RDS instance to require SSL (rds.force_ssl=1 parameter). The Glue connection should reference the RDS CA certificate bundle for server certificate validation. In the Glue Connection properties, enable "Require SSL connection"
  • C. Place the RDS instance and Glue job in the same VPC — VPC-internal traffic is automatically encrypted
  • D. Use IAM database authentication which automatically encrypts the connection
Jawaban Benar: B
Enforcing TLS on Glue JDBC connections requires multi-layer configuration: Server side (RDS): Set parameter group: rds.force_ssl = 1 (PostgreSQL) or require_secure_transport = ON (MySQL). This REJECTS any non-SSL connection attempt. Download RDS CA certificate bundle (rds-combined-ca-bundle.pem). Client side (Glue Connection): JDBC URL: jdbc:postgresql://mydb.xyz.rds.amazonaws.com:5432/mydb?ssl=true&sslmode=verify-full. SSL modes: disable — no SSL (insecure). allow — try SSL, fallback to no-SSL. prefer — try SSL, fallback (DEFAULT for many drivers). require — SSL required but no server cert verification. verify-ca — SSL + verify server cert is signed by trusted CA. verify-full — SSL + verify cert + verify hostname (MOST secure). Glue Connection property: "Require SSL connection" = checked. Upload CA cert as Glue job resource (via S3 path). Why verify-full: Prevents man-in-the-middle attacks. Verifies you're connecting to the REAL RDS endpoint (not a DNS-spoofed server). Validates certificate chain to trusted Amazon CA. Opsi A — TLS is NOT default; many JDBC drivers default to sslmode=prefer (may fallback). Opsi C — VPC traffic is NOT automatically encrypted; eavesdropping possible within VPC. Opsi D — IAM auth uses TLS but must still be explicitly configured in the connection string.

A company connects their on-premises data center to AWS using AWS Direct Connect for large data transfers to S3. They discover that Direct Connect private virtual interfaces do NOT encrypt traffic by default. How should they add encryption to Direct Connect traffic?
  • A. Direct Connect traffic is always encrypted by AWS — no additional configuration needed
  • B. Layer a Site-to-Site VPN over the Direct Connect connection — create a VPN connection using the Direct Connect public virtual interface (or transit VIF with Transit Gateway), establishing an IPsec tunnel that encrypts all traffic traversing the Direct Connect link. This provides both the reliability/bandwidth of Direct Connect AND the encryption of VPN. Alternatively, use MACsec (802.1AE) encryption at the physical layer for dedicated connections that support it
  • C. Use S3 Transfer Acceleration which automatically encrypts Direct Connect traffic
  • D. Enable "encryption" toggle in the Direct Connect console settings
Jawaban Benar: B
Direct Connect encryption options: Option 1 — VPN over Direct Connect: Create VPN tunnels that ride over the Direct Connect link. Data path: On-prem → [IPsec encrypted] → Direct Connect → AWS VPN Gateway → VPC. Configuration: Use public VIF for VPN endpoint connectivity, OR use Transit Gateway with Direct Connect + VPN attachment. Encryption: IPsec (AES-256). Throughput: Up to 1.25 Gbps per VPN tunnel (multi-tunnel for more). Best for: Existing Direct Connect without MACsec support. Option 2 — MACsec (IEEE 802.1AE): Layer 2 encryption on the physical Direct Connect connection. Wire-speed encryption (10 Gbps, 100 Gbps — no throughput loss). Configuration: Direct Connect connection must support MACsec. Exchange MACsec keys (CKN/CAK) with AWS. Enable on connection. Best for: New dedicated connections, high-throughput requirements. Option 3 — Application-level TLS: S3 API calls use HTTPS regardless of transport. Glue, Athena, Redshift connections use TLS. Provides encryption even without VPN/MACsec. But: other protocols (NFS, custom TCP) remain unencrypted. Why encryption needed: Direct Connect is a PRIVATE connection but NOT encrypted. Traffic could theoretically be intercepted at co-location facility. Compliance standards (PCI-DSS, HIPAA) often require transit encryption. Opsi A — factually wrong; DX is unencrypted by default. Opsi C — Transfer Acceleration unrelated to DX. Opsi D — no simple toggle exists.

A data engineer configures Amazon MSK (Managed Streaming for Apache Kafka) for a streaming pipeline. The security team requires encryption in transit for all Kafka communications: producer-to-broker, broker-to-broker, and consumer-to-broker. How is TLS configured in MSK?
  • A. MSK encrypts all traffic by default — no additional configuration required by producers or consumers
  • B. Configure MSK cluster encryption settings: enable TLS encryption in the cluster configuration (set encryption in-transit to TLS or TLS_PLAINTEXT). For inter-broker communication, enable TLS in broker settings. Producers and consumers must be configured to use the TLS bootstrap endpoints (port 9094 for TLS vs 9092 for plaintext) and include SSL truststore configuration pointing to the Amazon certificate authority. MSK handles certificate provisioning via ACM
  • C. Use VPC security groups to encrypt traffic between producers, brokers, and consumers
  • D. Install custom SSL certificates on each Kafka broker EC2 instance manually
Jawaban Benar: B
MSK TLS configuration has multiple layers: Cluster-level configuration (at creation): Encryption in transit setting: TLS — ONLY encrypted connections accepted. TLS_PLAINTEXT — both TLS and plaintext accepted (migration mode). PLAINTEXT — no encryption (not recommended). Inter-broker encryption: separatement configurable. Between-broker replication can be encrypted independently. Client configuration (producers/consumers): Bootstrap servers: Use TLS endpoints (port 9094) not plaintext (9092). Producer config: security.protocol=SSL, ssl.truststore.location=/path/to/kafka.client.truststore.jks. Consumer config: Same SSL properties. Truststore contains Amazon root CA certificates. MSK-managed certificates: MSK automatically provisions TLS certificates for brokers via ACM. No manual certificate management on broker instances. Certificate rotation handled by AWS. Mutual TLS (mTLS) optional: Clients can authenticate with their own certificates. MSK supports ACM Private CA for client cert issuance. Provides both encryption AND authentication. Key ports: 9092 — plaintext. 9094 — TLS. 9096 — SASL/SCRAM with TLS. 9098 — IAM authentication with TLS. Opsi A — producers/consumers MUST be configured to use TLS endpoints. Opsi C — security groups control network access, NOT encryption. Opsi D — MSK is managed; no direct broker EC2 access for cert installation.

An EMR cluster processes sensitive healthcare data. The security team requires encryption for ALL data in transit within the cluster: inter-node communication (HDFS replication, MapReduce shuffle), communication between EMR and S3 (EMRFS), and application-level communication (Spark executors). How is comprehensive in-transit encryption configured for EMR?
  • A. Enable "encryption in transit" in a single checkbox in the EMR console — all components are encrypted automatically
  • B. Create an EMR Security Configuration that enables in-transit encryption and specifies a certificate provider: (1) For node-to-node: TLS certificates encrypt HDFS data transfer, MapReduce shuffle, and Spark shuffle between nodes, (2) For EMRFS (EMR to S3): TLS is used by default for S3 API calls (HTTPS), (3) For Spark: inter-executor communication encrypted with TLS. The certificate provider can be PEM certificates from an S3 path, ACM certificates, or a custom certificate provider Java class. Apply this Security Configuration when launching the cluster
  • C. EMR clusters in a VPC automatically encrypt all inter-node traffic — VPC provides encryption
  • D. Install and configure Apache Ranger on the cluster to handle all encryption
Jawaban Benar: B
EMR Security Configuration for comprehensive in-transit encryption: Configuration structure: {"EncryptionConfiguration": {"EnableInTransitEncryption": true, "InTransitEncryptionConfiguration": {"TLSCertificateConfiguration": {"CertificateProviderType": "PEM", "S3Object": "s3://my-bucket/certs/my-certs.zip"}}}}. What gets encrypted: (1) HDFS data transfer: DataNode-to-DataNode replication encrypted. Client-to-DataNode reads/writes encrypted. NameNode RPC communication encrypted. (2) MapReduce: Shuffle data between map and reduce tasks encrypted. (3) Spark: Executor-to-executor shuffle encrypted (spark.authenticate + spark.network.crypto.enabled). Driver-to-executor communication encrypted. (4) Tez: Shuffle encryption enabled. (5) EMRFS → S3: Already HTTPS by default (TLS 1.2+). Security Configuration ensures this can't be downgraded. Certificate options: PEM from S3: Upload zip with private key + certificate + CA chain. ACM: EMR requests certificates from ACM Private CA. Custom Java class: Programmatic certificate provision (e.g., HashiCorp Vault integration). Performance impact: ~5-15% overhead for encryption/decryption. CPU utilization increases for TLS handshakes and data encryption. Plan for larger instance types or more nodes. Opsi A — simplified but requires Security Configuration (not just a checkbox). Opsi C — VPC does NOT encrypt inter-instance traffic. Opsi D — Ranger is for authorization, not encryption.

A data engineer needs to enforce TLS 1.2 minimum on all connections to their Redshift cluster. Some legacy applications still attempt to connect using TLS 1.0. How should they configure Redshift to reject connections using older TLS versions?
  • A. Redshift only supports TLS 1.2+ by default — older versions are automatically rejected
  • B. Modify the Redshift cluster parameter group to enforce minimum TLS version: set the ssl_min_protocol_version parameter to "TLSv1.2". This rejects any connection attempt using TLS 1.0 or TLS 1.1. Additionally, require SSL by setting require_SSL to true in the parameter group, which blocks ALL unencrypted connections. Clients must then connect using JDBC/ODBC drivers that support TLS 1.2
  • C. Use a Network Load Balancer in front of Redshift to terminate TLS 1.0/1.1 connections
  • D. Configure security groups to block ports associated with older TLS versions
Jawaban Benar: B
Redshift TLS enforcement via parameter group: Configuration steps: (1) Modify parameter group: Parameter: require_SSL = true → ALL connections MUST use SSL/TLS (no plaintext). Parameter: ssl_min_protocol_version = "TLSv1.2" → reject TLS 1.0, TLS 1.1. (2) Apply parameter group to cluster (may require reboot for static parameters). (3) Client configuration: JDBC URL: jdbc:redshift://cluster.xxx.redshift.amazonaws.com:5439/mydb?ssl=true&sslMode=verify-full. ODBC: sslmode=verify-full, min_tls=1.2. (4) Legacy application remediation: Identify apps using TLS 1.0/1.1 (CloudWatch connection logs). Upgrade JDBC/ODBC drivers to versions supporting TLS 1.2. Update application SSL configuration. Additional Redshift SSL features: Supports ACM-issued certificates for custom domains. Certificate rotation managed by AWS. FIPS 140-2 compliant encryption modules available. Cipher suite configuration for specific algorithm requirements. Monitoring: CloudWatch metric: SSLConnections vs NonSSLConnections. System table: svl_connection_log shows SSL version per connection. Alert on any TLS 1.0/1.1 attempts after enforcement. Opsi A — Redshift historically supported TLS 1.0; must explicitly set minimum version. Opsi C — NLB in front of Redshift is not a standard architecture. Opsi D — security groups filter by port/IP, not TLS version.

A data pipeline uses Kinesis Data Streams to ingest sensitive financial transactions. The data moves from on-premises producers → Kinesis → Lambda consumers → DynamoDB. The security architect asks about encryption in transit at each hop. Which statement correctly describes the default and configurable encryption in transit for this pipeline?
  • A. All AWS services communicate in plaintext by default and require explicit TLS configuration at every hop
  • B. Kinesis Data Streams API endpoints use TLS by default (HTTPS) — producers using the AWS SDK or KPL communicate over TLS automatically. Lambda invocations from Kinesis use AWS's internal TLS-encrypted channels. Lambda to DynamoDB uses HTTPS (TLS) by default via the AWS SDK. The key responsibility is ensuring: (1) on-premises producers use HTTPS endpoints (not HTTP), (2) any custom SDK configurations haven't disabled SSL, (3) VPC endpoints if used are properly configured for private network paths
  • C. Only the Kinesis to Lambda hop is encrypted — all other hops require manual TLS configuration
  • D. Kinesis internally stores data without encryption between shards, creating a gap in transit protection
Jawaban Benar: B
AWS service-to-service encryption in transit analysis: Hop 1 — On-premises Producer → Kinesis: AWS SDK/KPL: HTTPS by default (TLS 1.2). Risk: Custom producers might use HTTP if misconfigured. Mitigation: Cannot force HTTPS at Kinesis level (no aws:SecureTransport equivalent for Kinesis). Must enforce at producer application configuration. Hop 2 — Kinesis → Lambda: AWS internal invocation: encrypted channel managed by AWS. Lambda event source mapping pulls from Kinesis over internal encrypted links. No user configuration needed or possible. Hop 3 — Lambda → DynamoDB: AWS SDK in Lambda: HTTPS by default. boto3/SDK calls always use TLS to DynamoDB endpoint. VPC endpoint (if configured): still HTTPS. Hop 4 — Within Kinesis (shard-to-shard): Kinesis manages data within the service boundary. Server-side encryption (at rest) protects stored stream data. Inter-AZ replication uses AWS-internal encrypted links. Key risks and mitigations: On-prem producers: Enforce HTTPS in application config. SDK customization: Developers might set verify=False or use_ssl=False — code review required. Older SDK versions: May negotiate TLS 1.0 — upgrade SDKs. VPC endpoints: Ensure DNS resolution points to VPC endpoint (not public endpoint). Opsi A — most AWS SDKs use TLS by default. Opsi C — all hops are encrypted by default with AWS SDK. Opsi D — Kinesis internal operations are protected by AWS infrastructure.

A data engineer needs to upload highly sensitive files to S3 where even the transit encryption provided by HTTPS is considered insufficient (defense-in-depth requirement). The data must be encrypted BEFORE it leaves the application and remain encrypted until the intended recipient decrypts it. Which approach provides this "before transit" encryption?
  • A. Configure S3 server-side encryption with a stronger cipher — SSE provides before-transit encryption
  • B. Implement client-side encryption (CSE) — encrypt the data locally using the AWS Encryption SDK or S3 Encryption Client BEFORE calling S3 PutObject. The data is encrypted in the application's memory using either a KMS-managed key (CSE-KMS) or a client-managed master key (CSE-C). The encrypted ciphertext is what travels over HTTPS to S3. S3 stores the already-encrypted object. Only the intended recipient with the correct key can decrypt, regardless of S3 permissions
  • C. Use a VPN connection to S3 which provides double encryption
  • D. Enable S3 Transfer Acceleration which adds an extra encryption layer
Jawaban Benar: B
Client-Side Encryption (CSE) = encrypt BEFORE data leaves your control: Two approaches: CSE-KMS (AWS KMS managed): Application calls KMS GenerateDataKey → gets plaintext + encrypted data key. Encrypts data locally with plaintext data key. Uploads: encrypted data + encrypted data key as S3 object metadata. S3 stores ciphertext (S3 never sees plaintext). Recipient: downloads encrypted object, calls KMS Decrypt on data key, decrypts locally. CSE-C (Client-managed key): Application uses its own master key (not in KMS). Generates data key locally, encrypts data. Uploads encrypted data + wrapped data key. Complete independence from AWS for key management. Defense-in-depth layers: Layer 1: Client-side encryption (data encrypted before leaving app). Layer 2: TLS (HTTPS) encrypts the already-encrypted data in transit. Layer 3: S3 SSE (can ALSO enable) encrypts the already-encrypted object at rest. Result: Triple encryption — even if one layer compromised, data remains protected. AWS Encryption SDK: Multi-language SDK (Java, Python, JavaScript, C). Handles envelope encryption, key caching, algorithm selection. Supports data key caching for performance. Message format includes authentication (prevents tampering). Opsi A — SSE happens at S3 (server-side) AFTER data arrives. Opsi C — VPN to S3 is not standard architecture. Opsi D — Transfer Acceleration is performance optimization, not security.

A company uses AWS Certificate Manager (ACM) to manage TLS certificates for their data pipeline endpoints. They have an Application Load Balancer in front of their data API, a custom domain for their Redshift endpoint, and internal services communicating over mTLS. Which ACM capabilities support each use case?
  • A. ACM provides a single certificate type that works for all use cases — public, private, and mutual TLS
  • B. ACM provides different capabilities for each scenario: (1) Public certificates (free) for ALB/CloudFront — ACM issues and auto-renews public TLS certificates for domains you own; attach to ALB for HTTPS termination. (2) ACM Private CA for internal mTLS — issue private certificates for internal services that need mutual authentication; each service gets a client certificate for bi-directional verification. (3) Imported certificates for Redshift custom domains — import third-party certificates for services that don't natively integrate with ACM. All with automated renewal (public) or managed lifecycle (private CA)
  • C. ACM only works with CloudFront and ALB — it cannot be used for database or internal service encryption
  • D. ACM requires manual certificate renewal every 90 days for all certificate types
Jawaban Benar: B
ACM capabilities untuk data pipeline TLS management: Use Case 1 — ALB (Public Certificate): ACM issues free public TLS cert for api.company.com. Auto-renews 60 days before expiration. Attach to ALB listener → HTTPS termination. No manual certificate management. Supports wildcard (*.company.com) and SAN certificates. Use Case 2 — Internal mTLS (Private CA): ACM Private Certificate Authority: Create private CA within your organization. Issue certificates for internal services (not publicly trusted). mTLS flow: Service A presents cert → Service B validates against private CA. Service B presents cert → Service A validates against private CA. Both sides verified → encrypted + authenticated channel. Use case: Glue → internal API, Lambda → internal microservices. Use Case 3 — Redshift Custom Domain: Redshift custom domain names support ACM certificates. Alternatively, import third-party certificates for services without native ACM integration. Lifecycle management: Public certs: auto-renewed by ACM (domain validation via DNS CNAME). Private certs: configurable expiration, programmatic issuance/revocation. Imported certs: manual renewal (ACM alerts 45 days before expiration). Cost: Public ACM certs: free. Private CA: $400/month per CA + per-certificate fee. Opsi A — different certificate types serve different purposes. Opsi C — ACM integrates with many services. Opsi D — public certs auto-renew, not manual.

A streaming data pipeline receives data from IoT devices over the internet to Amazon Kinesis. Some devices are in regions with poor network infrastructure where TLS handshake failures occur frequently due to latency. The security team refuses to allow plaintext connections. What architecture balances reliability with mandatory encryption in transit?
  • A. Allow HTTP fallback for devices that fail TLS handshake — availability over security
  • B. Deploy an architecture that optimizes TLS while maintaining encryption: (1) Use AWS IoT Core as an ingestion endpoint — it supports lightweight TLS (TLS 1.2 with optimal cipher suites for IoT), MQTT protocol (less overhead than HTTPS), and persistent connections (reducing repeated handshakes). (2) IoT Core rules route data to Kinesis. (3) For extremely constrained devices: use AWS IoT Greengrass as a local TLS-terminating gateway that aggregates messages and forwards to cloud over a single persistent TLS connection. This maintains end-to-end encryption while reducing per-device TLS overhead
  • C. Increase the Kinesis timeout settings to accommodate slow TLS handshakes
  • D. Use TLS 1.0 which has faster handshake than TLS 1.2/1.3
Jawaban Benar: B
IoT + streaming + mandatory TLS requires architectural optimization: Challenge: TLS handshake = 1-2 round trips. High-latency networks: handshake may timeout. Many devices = many concurrent handshakes. Direct to Kinesis: HTTPS PutRecord per message = new connection per request (unless HTTP keep-alive). Solution Architecture: [IoT Devices] → [TLS/MQTT] → [IoT Core] → [Rules Engine] → [Kinesis]. Benefits of IoT Core approach: MQTT protocol: Persistent connection — ONE TLS handshake, then thousands of messages over same connection. Much less overhead than per-request HTTPS. Optimized for low-bandwidth devices. TLS session resumption: IoT Core supports session tickets — subsequent connections skip full handshake. Reduces latency for reconnections. Greengrass edge gateway: Local devices connect to Greengrass (low latency, local network). Greengrass maintains SINGLE persistent TLS connection to cloud. Aggregates hundreds of device messages into batched uploads. Reduces cloud-facing TLS connections from N devices to 1. Connection management: IoT Core handles millions of persistent connections. Built-in retry logic and connection draining. QoS levels for delivery guarantees. Opsi A — violates security requirement. Opsi C — Kinesis doesn't have TLS timeout settings for producers. Opsi D — TLS 1.0 is deprecated, not faster in meaningful ways, and less secure.
