A data engineering team manages a large customer data lake on Amazon S3. They receive daily GDPR deletion requests requiring them to remove specific customer records from Parquet files. Currently, the process involves reading entire Parquet files, filtering out deleted records, and rewriting the files — taking 6 hours for a 20 TB dataset. They need row-level delete capability without full file rewrites. Which open table format feature BEST addresses this requirement?
  • A. Use S3 Object Lock with governance mode to mark specific records as deleted without modifying the underlying files configured for optimal performance and minimal operational overhead, applying schema conversion and enrichment inline and validating and cleansing each record before delivery and meeting the latency and throughput goals of the design and transforming records into the required target format
  • B. Implement a soft-delete pattern with a deleted_flag column and rewrite only the metadata files in the Parquet footer, meeting the latency and throughput goals of the design and transforming records into the required target format and applying schema conversion and enrichment inline and satisfying all of the stated requirements with minimal effort and reducing day-to-day operational effort
  • C. Use AWS Lake Formation row-level security to filter out deleted records at query time without modifying any files, applying schema conversion and enrichment inline and transforming records into the required target format and meeting the latency and throughput goals of the design and validating and cleansing each record before delivery and handling the described workload reliably at scale
  • D. Implement Apache Iceberg tables with position delete files. Iceberg supports row-level deletes by writing small delete files that reference the positions of deleted rows within data files — reads merge data files with delete files to exclude deleted rows without rewriting the original Parquet files. Periodic compaction merges delete files into data files during maintenance windows
Correct Answer: D
Apache Iceberg's row-level delete mechanism is purpose-built for this scenario: (1) position delete files record which row positions in which data files should be excluded — no data file rewrites needed for the delete operation itself; (2) equality delete files can specify deleted records by column values (e.g., customer_id = 'X'); (3) query engines (Athena, EMR, Glue) automatically apply delete files during reads, returning only non-deleted rows; (4) the 6-hour full rewrite is replaced by writing small delete files (seconds); (5) background compaction can physically remove deleted rows during off-peak hours. For GDPR compliance, this provides immediate logical deletion with deferred physical deletion.

Option A: INCORRECT. S3 Object Lock prevents file modification/deletion at the object level; it cannot mark individual records within Parquet files as deleted — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Soft-delete with a flag column still requires rewriting Parquet files to update the column value (Parquet is immutable); you cannot update a "footer" to change row data.
Option C: INCORRECT. Lake Formation row-level security controls query access permissions, not data deletion; GDPR requires actual data removal, not just access restriction.
Option D: CORRECT.

A company's data lake uses Apache Iceberg tables registered in the AWS Glue Data Catalog. The data science team needs to reproduce a machine learning model's training results from 30 days ago by querying the exact dataset that existed at that point in time. The underlying data has been updated daily since then with new records, updates, and deletes. Which Iceberg capability enables querying historical data states?
  • A. Configure AWS Backup to take daily snapshots of the Glue Data Catalog and restore the catalog state from 30 days ago, integrating natively with the rest of the pipeline and handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and minimizing end-to-end processing latency
  • B. Use Athena's CTAS to create daily backup tables and query the backup table from 30 days ago with a specific snapshot ID or timestamp — Iceberg maintains a history of table snapshots, handling the described workload reliably at scale and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort
  • C. Use Iceberg's time travel feature by querying with a specific snapshot ID or timestamp — Iceberg maintains a history of table snapshots, each representing the complete state of the table at a point in time. Query engines can read any historical snapshot, returning the exact dataset as it existed at that moment, including rows that were later updated or deleted
  • D. Enable S3 versioning on the data lake bucket and use version IDs to access historical file versions from 30 days ago, meeting the latency and throughput goals of the design and satisfying all of the stated requirements with minimal effort and handling the described workload reliably at scale and integrating natively with the rest of the pipeline and providing exactly-once processing semantics
Correct Answer: C
Iceberg's time travel is a core feature of the table format: (1) every commit (insert, update, delete) creates a new snapshot linked to the previous one; (2) each snapshot tracks the complete set of data files and delete files that constitute the table state at that moment; (3) querying a historical snapshot (e.g., SELECT * FROM table FOR SYSTEM_TIME AS OF TIMESTAMP '2024-01-15') reconstructs the exact table content from 30 days ago; (4) this works even if underlying data files have been compacted or reorganized since then, as long as snapshot metadata and referenced data files are retained. Athena, EMR, and Glue all support Iceberg time travel queries.

Option A: INCORRECT. AWS Backup doesn't support Glue Data Catalog, and even if it did, catalog metadata alone doesn't preserve historical data file references.
Option B: INCORRECT. Daily CTAS backups waste storage (duplicating the entire dataset daily) and create operational complexity managing 30+ backup tables — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: CORRECT.
Option D: INCORRECT. S3 versioning tracks object-level versions but doesn't understand table-level semantics (which files constituted the "table" 30 days ago, which delete files applied); reconstructing a consistent table state from raw S3 versions is impractical.

A retail company partitions their Iceberg sales table by region and date (year/month/day). After a business reorganization, they need to change the partition scheme from (region, year, month, day) to (country, year, month) to align with the new organizational structure. The table contains 50 TB of historical data. In a traditional Hive-style data lake, this would require rewriting all 50 TB of data. How does Iceberg handle this partition evolution?
  • A. Iceberg requires running ALTER TABLE ... SET PARTITION which triggers an automatic background rewrite of all existing data files into the new partition layout with partition-level ordering and dedicated throughput, satisfying all of the stated requirements with minimal effort and handling the described workload reliably at scale and meeting the latency and throughput goals of the design
  • B. Iceberg allows partition evolution only by adding new partition columns — removing or changing existing partition columns requires a full table rewrite using CTAS, handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and integrating natively with the rest of the pipeline
  • C. Iceberg creates virtual partitions by maintaining a mapping layer that translates queries against the new scheme into scans of the old physical layout, requiring no metadata or data changes, satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline and handling the described workload reliably at scale and providing exactly-once processing semantics
  • D. Iceberg supports partition evolution without rewriting existing data. The partition spec change is a metadata-only operation — existing data files retain their original physical partitioning while new data written after the change uses the new partition scheme. Iceberg's metadata tracks which partition spec applies to which data files, and the query engine uses both specs correctly during query planning
Correct Answer: D
Partition evolution is one of Iceberg's key advantages over Hive-style partitioning: (1) Iceberg decouples the logical partition spec from physical file layout — each data file records its own partition values in metadata; (2) changing the partition spec (ALTER TABLE ... SET PARTITION SPEC) is an instant metadata operation; (3) existing data files are NOT rewritten — they continue to live in their original directory structure; (4) new data files written after the change use the new partition spec; (5) the query planner reads both partition specs from metadata and applies appropriate filtering to files regardless of which spec was active when they were written. This means the 50 TB historical data remains untouched while new data partitions differently.

Option A: INCORRECT. Iceberg does NOT trigger automatic data rewrites on partition spec changes; this is the entire point of its partition evolution design — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Iceberg supports full partition evolution including removing, adding, and changing partition columns; CTAS is not required.
Option C: INCORRECT. It's not "virtual partitions" — Iceberg actually maintains explicit partition specs per manifest file; the query engine doesn't "translate" but rather directly understands each file's actual partition values from metadata.
Option D: CORRECT.

A streaming data pipeline writes events to an Apache Iceberg table on S3 every 5 minutes using AWS Glue Streaming. After several months, the table has accumulated 200,000 small data files (each 5-10 MB). Athena queries on this table have degraded from 10 seconds to 3 minutes due to the high file count causing excessive S3 LIST and GET operations. Which Iceberg maintenance operation MOST effectively resolves this performance degradation?
  • A. Increase the Athena DPU count to process more small files in parallel during each query scan, satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and running as a fully managed service with minimal operational overhead
  • B. Run Iceberg compaction (rewrite_data_files) to merge the many small files into fewer, larger optimally-sized files (128-512 MB each). This reduces the number of files from 200,000 to approximately 2,000-5,000 while maintaining the same data content, dramatically reducing S3 metadata operations and improving query scan parallelism
  • C. Enable S3 Transfer Acceleration to reduce latency for individual GET requests on the many small files, reducing day-to-day operational effort and handling the described workload reliably at scale and removing the need to provision or patch any infrastructure and integrating natively with the rest of the pipeline
  • D. Run expire_snapshots to remove old snapshot metadata that references historical file states and improving query scan parallelism, removing the need to provision or patch any infrastructure and reducing day-to-day operational effort and meeting the latency and throughput goals of the design and providing exactly-once processing semantics
Correct Answer: B
Small file compaction is the direct solution for the "small files problem" in data lakes: (1) rewrite_data_files merges small files into optimally-sized files (typically 128-512 MB for Parquet/ORC); (2) fewer files = fewer S3 LIST/GET operations per query = lower query latency; (3) larger files enable better columnar compression and more efficient read patterns; (4) Iceberg's compaction is atomic — queries see either the pre-compaction or post-compaction state, never partial results; (5) compaction can be targeted (specific partitions) or table-wide. In AWS, this can be run via Glue jobs, EMR Spark, or Athena maintenance queries.

Option A: INCORRECT. Athena doesn't use "DPUs" (that's Glue); more compute doesn't reduce the fundamental overhead of 200,000 S3 operations; the bottleneck is I/O operation count, not compute parallelism.
Option B: CORRECT.
Option C: INCORRECT. S3 Transfer Acceleration reduces network latency for cross-region transfers; within-region S3 access latency isn't improved, and the issue is operation count, not per-operation latency.
Option D: INCORRECT. Expire_snapshots cleans up metadata (manifest files, snapshot entries) and unreferenced data files, but the 200,000 current small files ARE referenced by the current snapshot — expiring old snapshots won't reduce them — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data engineering team needs to implement a Change Data Capture (CDC) pipeline that merges updates from an operational database into an Iceberg table in their data lake. The pipeline receives batches of 100,000 change records (inserts, updates, deletes) every 10 minutes. The target Iceberg table contains 500 million rows. They need an efficient upsert operation that handles all three change types atomically. Which Iceberg operation BEST supports this CDC merge pattern?
  • A. Use Iceberg's MERGE INTO statement which performs matched/not-matched logic in a single atomic operation — WHEN MATCHED AND change_type='delete' THEN DELETE, WHEN MATCHED AND change_type='update' THEN UPDATE, WHEN NOT MATCHED THEN INSERT. This handles all CDC change types in one pass with snapshot isolation guaranteeing consistent reads during the merge
  • B. Overwrite the entire partition containing changed records using INSERT OVERWRITE with the merged dataset for each affected partition, handling peak volume without any manual intervention and handling the described workload reliably at scale and removing the need to provision or patch any infrastructure and scaling elastically to millions of events per second
  • C. Append all CDC records as new rows with a version timestamp and use a view with ROW_NUMBER() to surface only the latest version at query time configured for optimal performance and minimal operational overhead, satisfying all of the stated requirements with minimal effort and scaling elastically to millions of events per second
  • D. Process each change type separately: first DELETE matching records, then INSERT all new/updated records — using three separate Iceberg operations within a transaction, meeting the latency and throughput goals of the design and requiring no servers to manage or scale manually and removing the need to provision or patch any infrastructure
Correct Answer: A
MERGE INTO is Iceberg's native upsert mechanism, purpose-built for CDC workloads: (1) single atomic operation handles inserts, updates, and deletes based on match conditions — either the entire merge succeeds or none of it does; (2) snapshot isolation ensures concurrent readers see a consistent table state (either pre-merge or post-merge); (3) the query engine efficiently identifies matching rows using metadata (min/max statistics, partition pruning) without scanning all 500 million rows; (4) MERGE INTO is supported by Athena v3, EMR Spark, and AWS Glue when working with Iceberg tables. This is significantly more efficient than processing change types separately.

Option A: CORRECT.
Option B: INCORRECT. INSERT OVERWRITE at partition level requires reading the entire partition to merge in changes; for a 500-million-row table with few affected partitions, this may rewrite massive amounts of unchanged data.
Option C: INCORRECT. Append-only with versioning avoids the merge complexity but continuously grows the table, degrades query performance (every query must deduplicate), and doesn't physically delete records (problematic for GDPR) — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Three separate operations create intermediate inconsistent states (after DELETE but before INSERT, the record is missing); without true multi-statement transactions (which Iceberg doesn't support across separate commits), this risks data inconsistency if a failure occurs mid-process.

  • A.   • B. Apache Hudi is the best choice because it provides built-in CDC ingestion support and incremental processing capabilities that Iceberg lacks, integrating natively with the rest of the pipeline and applying schema conversion and enrichment inline and validating and cleansing each record before delivery and handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort
  • C.   • D. Correct Answer: C
For AWS-native architectures, Iceberg has emerged as the preferred open table format: (1) AWS has invested heavily in Iceberg integration — Athena v3 uses Iceberg as its default managed table format; (2) Glue 4.0+ has native Iceberg support for reading, writing, and maintenance operations; (3) EMR supports Iceberg natively across Spark, Flink, and Trino; (4) Redshift Spectrum reads Iceberg tables directly; (5) the Glue Data Catalog serves as Iceberg's catalog (replacing HiveCatalog), eliminating the need for separate metadata stores. Iceberg's vendor-neutral Apache specification ensures no vendor lock-in.

Option B: INCORRECT. Hudi does excel at CDC but is more complex to configure and has narrower AWS service support (limited Athena support, no native Redshift Spectrum integration).
Option C: CORRECT.
Option D: INCORRECT. Delta Lake has excellent features but its full capability set (optimized writes, Z-ordering, liquid clustering) requires Databricks runtime; the open-source delta-rs version on EMR/Athena has limited features compared to Iceberg's consistent support.

A data lake team uses Apache Iceberg tables with hidden partitioning. Their events table contains a timestamp column (event_time) and they configure the partition spec as days(event_time). Users query with WHERE event_time BETWEEN '2024-03-01' AND '2024-03-15'. In a traditional Hive-partitioned table, users would need to include a separate partition column (event_date) in their WHERE clause. What advantage does Iceberg's hidden partitioning provide in this scenario?
  • A. Hidden partitioning automatically derives partition values from the source column using the specified transform (days()) — users write natural filter predicates on the actual timestamp column without knowing the partition scheme. Iceberg's query planning translates the timestamp filter into partition pruning internally, eliminating the common user error of forgetting to include partition columns in WHERE clauses that causes full table scans in Hive
  • B. Hidden partitioning stores partition metadata in a separate encrypted catalog that requires IAM permissions to access, integrating natively with the rest of the pipeline and meeting the latency and throughput goals of the design and handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and minimizing end-to-end processing latency
  • C. Hidden partitioning uses adaptive query execution to dynamically determine the optimal partition layout at query time based on the data distribution, handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and integrating natively with the rest of the pipeline and enforcing encryption and fine-grained access control
  • D. Hidden partitioning encrypts partition paths in S3 so users cannot browse the physical file structure directly with partition-level ordering and dedicated throughput, meeting the latency and throughput goals of the design and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort and handling the described workload reliably at scale and absorbing sudden traffic spikes without throttling
Correct Answer: A
Hidden partitioning is a fundamental Iceberg design principle that improves both usability and reliability: (1) partition values are derived from source columns using transforms (year, month, day, hour, bucket, truncate) — no separate partition columns needed in the schema; (2) users write queries against actual data columns (WHERE event_time > X), not synthetic partition columns (WHERE year = 2024 AND month = 3); (3) Iceberg's metadata stores min/max bounds per partition, enabling the query planner to prune partitions from any predicate on the source column; (4) this eliminates the "silent full scan" problem where Hive users forget to filter on the partition column and accidentally scan the entire table. The partition scheme is an internal optimization detail, not a user-facing concern.

Option A: CORRECT.
Option B: INCORRECT. Hidden partitioning is not a security feature; it's a query abstraction that separates physical layout from logical queries.
Option C: INCORRECT. Hidden partitioning uses a fixed partition spec (not dynamic); the transform is defined at table creation and applied consistently to all written data.
Option D: INCORRECT. "hidden" doesn't mean encrypted; it means the partitioning is abstracted from the user's query interface; physical S3 paths are still accessible — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data engineering team manages an Iceberg table that receives concurrent writes from two Glue jobs running simultaneously — one appending hourly sales data and another updating product prices. Both jobs occasionally fail with "CommitFailedException: Conflict detected" errors. The team needs to understand Iceberg's concurrency control model and configure appropriate conflict resolution. What causes these conflicts and how should they be resolved?
  • A. Iceberg uses optimistic concurrency control with snapshot isolation. Conflicts occur when two concurrent writers modify overlapping data (same partitions/files). The resolution is to enable automatic retry on CommitFailedException — the failed writer re-reads the current table state, validates its changes don't conflict with the committed write, and re-attempts the commit. For truly non-overlapping operations (appends to different partitions vs. updates to existing rows), Iceberg can validate there's no actual conflict and commit successfully on retry
  • B. The conflicts are caused by S3's eventual consistency model — both writers succeed on S3 but the Glue Data Catalog rejects the second commit, avoiding charges for idle provisioned capacity and handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline and optimizing cost for the described workload
  • C. The conflicts occur because Iceberg uses pessimistic locking and both jobs attempt to acquire the same table-level write lock simultaneously with snapshot isolation and re-attempts the commit, optimizing cost for the described workload and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort and handling the described workload reliably at scale and avoiding charges for idle provisioned capacity
  • D. The conflicts occur because Iceberg limits each table to a single writer at any given time; the solution is to queue writes sequentially, avoiding charges for idle provisioned capacity and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and optimizing cost for the described workload and keeping steady-state operating costs low
Correct Answer: A
Iceberg's optimistic concurrency control works as follows: (1) each writer reads the current metadata pointer (latest snapshot), performs its work, and attempts an atomic commit of a new snapshot pointing to the new/modified files; (2) the commit performs a compare-and-swap on the metadata pointer — if another writer committed between read and commit, the CAS fails with CommitFailedException; (3) on retry, the writer re-reads the now-updated metadata and validates whether its changes actually conflict with what was committed (conflict detection is based on the type of operation — appends rarely conflict with each other since they add non-overlapping files). For this scenario, the append job and update job likely don't truly conflict if they target different data files — proper retry logic resolves most cases automatically.

Option A: CORRECT.
Option B: INCORRECT. S3 provides strong read-after-write consistency (since 2020); eventual consistency is not the issue. The catalog's atomic compare-and-swap is the coordination mechanism.
Option C: INCORRECT. Iceberg does NOT use pessimistic (pre-acquired) locks; optimistic concurrency is a core design principle allowing high-throughput concurrent access — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Iceberg explicitly supports multiple concurrent writers; single-writer restriction would defeat the purpose of its concurrency model.

A company needs to add a new column (loyalty_tier VARCHAR) to their Iceberg customer table that contains 2 billion rows. In a traditional data warehouse, adding a column to a 2-billion-row table might require hours of table restructuring. The downstream analytics queries should immediately be able to query the new column (returning NULL for existing rows). How does Iceberg handle this schema evolution operation?
  • A. Iceberg requires creating a new table with the updated schema and using INSERT INTO ... SELECT to migrate all 2 billion rows to the new structure and data files, transforming records into the required target format and validating and cleansing each record before delivery and applying schema conversion and enrichment inline and minimizing end-to-end processing latency and handling the described workload reliably at scale
  • B. Iceberg schema evolution (adding columns) is a metadata-only operation that completes in milliseconds regardless of table size. The new column definition is added to the table's schema metadata. Existing data files are NOT rewritten — when queried, Iceberg returns NULL for the new column in rows from files that predate the schema change. New data files include the column. This is possible because Iceberg uses column IDs (not names or positions) to map between schemas and data files
  • C. Iceberg adds the column but requires running ALTER TABLE ... REORGANIZE to physically update existing data files before the new column is queryable, satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and minimizing end-to-end processing latency and transforming records into the required target format and validating and cleansing each record before delivery
  • D. Iceberg initiates an asynchronous background process to add the new column to all existing Parquet files, with queries returning partial results until the migration completes, applying schema conversion and enrichment inline and streaming results downstream in near real time and meeting the latency and throughput goals of the design and integrating natively with the rest of the pipeline and validating and cleansing each record before delivery
Correct Answer: B
Schema evolution without data rewriting is a fundamental Iceberg capability: (1) each column has a unique ID assigned at creation — this ID never changes even if the column is renamed; (2) data files store values by column ID, not by name or ordinal position; (3) adding a column creates a new ID in the schema metadata — existing files simply don't have data for that ID, so NULL is returned; (4) renaming a column updates the name-to-ID mapping in metadata only; (5) this makes schema changes instant regardless of table size. This contrasts with Hive where schema changes can break existing data files if column positions shift.

Option A: INCORRECT. CTAS migration is the old-world approach for Hive tables; Iceberg eliminates this requirement entirely through its ID-based column mapping — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: CORRECT.
Option C: INCORRECT. No REORGANIZE step is needed; the new column is immediately queryable after the metadata update completes (milliseconds).
Option D: INCORRECT. Iceberg never modifies existing data files as part of schema evolution; there's no background migration process.

A data lake team notices their Iceberg table's metadata has grown significantly — the table has 50,000 snapshots accumulated over 6 months of frequent writes (every 5 minutes). Query planning latency has increased from 200ms to 5 seconds because the query engine must traverse lengthy snapshot metadata chains. Which combination of Iceberg maintenance operations BEST reduces metadata overhead while preserving time travel capability for the last 7 days?
  • A. Delete old metadata JSON files directly from the S3 metadata directory to reduce the metadata chain length, minimizing end-to-end processing latency and meeting the latency and throughput goals of the design and reducing day-to-day operational effort and making the data queryable within seconds of arrival and delivering records with consistent sub-second latency
  • B. Run expire_snapshots with a retention threshold of 7 days to remove snapshots older than 7 days (preserving recent time travel), then run rewrite_manifests to consolidate the remaining manifest files into fewer, larger manifests — reducing both the snapshot chain length and manifest file count that the query planner must process
  • C. Increase the metadata.max-snapshots-to-keep property to allow more snapshots without performance degradation with a retention threshold of 7 days and manifest file count that the query planner must process, delivering records with consistent sub-second latency and satisfying all of the stated requirements with minimal effort and streaming results downstream in near real time
  • D. Run rewrite_data_files (compaction) which automatically cleans up old snapshots as a side effect of data file consolidation, requiring no servers to manage or scale manually and meeting the latency and throughput goals of the design and handling the described workload reliably at scale and integrating natively with the rest of the pipeline
Correct Answer: B
The two-step maintenance approach addresses both causes of metadata bloat: (1) expire_snapshots removes snapshot entries older than 7 days AND deletes data files that are no longer referenced by any remaining snapshot — this reduces the metadata chain from 50,000 snapshots to ~2,000 (7 days × 288 writes/day at 5-minute intervals); (2) rewrite_manifests consolidates fragmented manifest files (each containing file-level metadata for data files) into fewer, larger manifests — reducing the number of metadata files the query planner opens during query planning. Together, these reduce planning latency from 5 seconds back toward 200ms. Time travel within 7 days is preserved.

Option A: INCORRECT. Manually deleting metadata files from S3 corrupts the Iceberg table's metadata chain and can make the table unreadable; never directly manipulate Iceberg's metadata files outside of Iceberg's API.
Option B: CORRECT.
Option C: INCORRECT. Increasing max-snapshots-to-keep does the opposite of what's needed; allowing more snapshots increases metadata overhead rather than reducing it — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Rewrite_data_files (compaction) merges small data files but does NOT remove old snapshots; snapshot accumulation continues even after compaction, and compaction actually creates new snapshots.
