A data engineering team has 10 AWS Glue ETL jobs that process customer transaction data. The team currently deploys code changes by manually uploading scripts to S3 and updating job configurations via the console. Deployments take 2 hours, are error-prone, and have caused production incidents from misconfigured jobs. Which AWS CI/CD architecture BEST automates this deployment process?
  • A. Use AWS CodePipeline with three stages: Source (CodeCommit/GitHub triggers on merge to main), Build (CodeBuild runs unit tests on Glue scripts using pytest with local Spark, lints code, and packages artifacts), and Deploy (CodeBuild or CloudFormation deploys updated Glue job configurations and uploads scripts to S3)
  • B. Create a Lambda function triggered by S3 upload that automatically updates Glue job configurations
  • C. Use Step Functions to orchestrate manual approval and deployment steps
  • D. Write a cron job on an EC2 instance that periodically checks for code changes and deploys them with three stages: Source (CodeCommit/GitHub triggers on merge
Jawaban Benar: A
CodePipeline provides a fully managed CI/CD pipeline with distinct stages. Source stage automatically triggers on code commits (eliminating manual initiation). Build stage runs tests BEFORE deployment (catching bugs early). Deploy stage uses infrastructure-as-code for consistent, repeatable deployments. This reduces 2-hour manual processes to automated 10-minute deployments with built-in quality gates. Opsi B — Lambda triggered by S3 upload skips testing and has no approval mechanism; it's a fragile anti-pattern. Opsi C — Step Functions orchestrates workflow but isn't designed for CI/CD; it lacks source integration and build capabilities. Opsi D — cron-based polling is unreliable, introduces delay, and EC2 maintenance adds operational burden.

A data engineer implements CI/CD for an ETL pipeline that transforms sensitive healthcare data. The pipeline must pass data quality tests before production deployment. The team needs automated testing that validates both code correctness and data transformation accuracy without using actual patient data. Which testing strategy should the CodeBuild stage implement?
  • A. Implement a multi-layer testing approach: unit tests with mocked data (pytest + local Spark) to validate transformation logic, integration tests with synthetic data that mirrors production schema structure, and data quality assertion tests that validate output schema, null handling, data type conformity, and row count expectations
  • B. Copy a sample of production healthcare data to the test environment and run the ETL job against it
  • C. Skip testing in the CI pipeline and rely on manual QA review of output data in production
  • D. Run only syntax checks (pylint/flake8) without any functional testing of transformations with mocked data (pytest + local Spark)
Jawaban Benar: A
Multi-layer testing ensures comprehensive coverage: unit tests validate individual transformation functions quickly (seconds). Integration tests verify end-to-end flow with synthetic data that matches production schema without HIPAA violations. Data quality assertions catch schema drift, null handling issues, and data type mismatches that unit tests miss. Synthetic data eliminates regulatory risk while testing realistic scenarios. Opsi B — copying production healthcare data violates HIPAA and data privacy regulations; synthetic data must be used. Opsi C — manual QA in production is too late; bad data may already affect patients or downstream systems. Opsi D — syntax checks catch formatting issues but not logical errors in transformations (e.g., incorrect join conditions, wrong date parsing).

A data pipeline processes financial transactions and must maintain zero data loss during deployments. The current deployment process requires stopping the pipeline, deploying new code, and restarting — creating a 15-minute data processing gap. The team needs a deployment strategy that eliminates this gap. Which approach provides zero-downtime deployment for the data pipeline?
  • A. Implement blue/green deployment: deploy the new version (green) alongside the old version (blue) with both processing from the same Kinesis stream using separate consumer groups. Validate green output against blue output. Once confirmed, switch the downstream consumers to read from green's output and decommission blue
  • B. Deploy during a maintenance window at 3 AM when data volume is lowest with both processing from the same Kinesis stream using separate consumer groups and decommission blue
  • C. Speed up the deployment process to reduce the gap from 15 minutes to 5 minutes
  • D. Buffer incoming data in S3 during deployment and process the backlog after the new version starts
Jawaban Benar: A
Blue/green deployment runs both versions simultaneously, eliminating any processing gap. Both versions read from the same source (Kinesis stream with separate consumer groups ensures independent processing). Comparing outputs validates the new version produces correct results before cutover. If green produces errors, traffic stays on blue with no impact. This provides zero downtime AND safe rollback. For financial data, comparing transaction counts and checksums between blue and green validates accuracy. Opsi B — maintenance windows still create a gap and don't work for 24/7 financial processing. Opsi C — reducing the gap doesn't eliminate it; even 5 minutes of lost transactions is unacceptable. Opsi D — buffering delays processing and creates a burst when backlog is processed, potentially overwhelming downstream systems.

A company's data engineering team uses CodePipeline to deploy Glue jobs across dev, staging, and production accounts. A recent deployment to production introduced a bug that caused incorrect aggregations, affecting reporting for 4 hours before detection. The team needs a faster rollback mechanism. Which CI/CD enhancement provides the quickest recovery?
  • A. Maintain versioned Glue job scripts in S3 with versioning enabled. In CodePipeline, after each successful production deployment, tag the current working version. For rollback, trigger a pipeline action that points the Glue job to the previous S3 script version — restoring the last-known-good state in under 1 minute without a full redeployment cycle
  • B. Run the entire CI/CD pipeline again with the previous code commit to redeploy for rollback
  • C. Manually edit the Glue job script in the console to fix the bug immediately
  • D. Disable the Glue job trigger and wait for the engineering team to fix the code
Jawaban Benar: A
S3 versioning maintains every previous script version. Rollback is simply updating the Glue job's script location to point to the previous S3 version — a single API call taking seconds. Combined with CloudFormation's UpdateRollback or CodeDeploy's automatic rollback, recovery time drops from hours to under a minute. Tagging successful versions creates clear rollback targets. Opsi B — re-running the full pipeline (build + test + deploy) takes 10-30 minutes, prolonging the outage. Opsi C — manual console edits bypass version control and testing, potentially introducing new bugs while creating drift. Opsi D — disabling the job stops all data processing, making the outage worse, not better.

A data team has separate repositories for infrastructure (CDK/CloudFormation) and application code (Glue scripts, Lambda functions). When infrastructure changes and code changes must be deployed together (e.g., a new Glue job that also needs a new IAM role), deployments sometimes fail because code deploys before infrastructure is ready. Which pipeline architecture ensures correct deployment ordering?
  • A. Create a CodePipeline with sequential stages: first deploy infrastructure (CloudFormation/CDK stack with the new IAM role), then deploy application code (upload Glue scripts, deploy Lambda). Use pipeline artifacts to pass stack outputs (role ARN) to the application deployment stage. A source action monitors both repositories and triggers the pipeline when either changes
  • B. Maintain two completely independent pipelines and rely on developers to trigger them in the correct order
  • C. Combine all infrastructure and application code into a single repository to avoid ordering issues
  • D. Add retry logic in the application code to handle missing IAM roles gracefully with sequential stages: first deploy infrastructure (CloudFormation/CDK stack with the new IAM role) and triggers the pipeline when either changes
Jawaban Benar: A
Sequential pipeline stages guarantee ordering: infrastructure completes before application deployment begins. Pipeline artifacts enable passing values (new role ARN, new resource names) between stages without hardcoding. Multi-source triggers ensure the pipeline runs when either infrastructure or application code changes, always deploying in the correct order. Stage transitions only proceed after the previous stage succeeds. Opsi B — manual triggering is error-prone and doesn't scale; developers will forget the correct order under pressure. Opsi C — monorepos can work but don't inherently solve deployment ordering; a pipeline still needs sequential stages. Opsi D — retry logic for missing IAM roles is a band-aid that masks the fundamental ordering problem and introduces non-deterministic behavior.

A data engineering team wants to implement pipeline-as-code for their CI/CD process. They currently configure CodePipeline and CodeBuild through the AWS Console, but changes to the pipeline itself are untracked and difficult to reproduce. When they need to create similar pipelines for new projects, they start from scratch. Which approach BEST enables pipeline-as-code for data engineering deployments?
  • A. Define the CodePipeline and CodeBuild projects using CDK Pipelines (aws_cdk.pipelines module), which enables self-mutating pipelines that update themselves when the pipeline definition changes. Store buildspec.yml in the source repository alongside application code. The pipeline definition is version-controlled and reviewable via pull requests
  • B. Document the pipeline configuration steps in a wiki for other teams to follow
  • C. Export the existing pipeline as a CloudFormation template and store it without version control
  • D. Use the CodePipeline CLI to script pipeline creation without storing the script and CodeBuild projects using CDK Pipelines (aws_cdk
Jawaban Benar: A
CDK Pipelines enable "self-mutating" pipelines: the pipeline itself is defined in code, and if you change the pipeline definition (add a stage, modify a build step), the pipeline updates itself on the next run. buildspec.yml stored in the repo ensures build configuration is versioned alongside application code. Pull requests provide review before pipeline changes. New projects instantiate the same CDK pipeline construct with different parameters. Opsi B — wiki documentation can't create pipelines and becomes outdated quickly. Opsi C — exported templates without version control lack change history and review capability. Opsi D — scripts without storage aren't reproducible and lack change tracking.

A CodeBuild project runs tests for AWS Glue ETL jobs as part of the CI pipeline. The build environment needs PySpark, pandas, and AWS SDK dependencies. Each build currently takes 12 minutes, with 8 minutes spent installing dependencies. The team deploys 15 times per day and needs faster build times. Which optimization MOST reduces build duration?
  • A. Create a custom Docker image with all dependencies pre-installed (PySpark, pandas, boto3, pytest) and use it as the CodeBuild custom build environment. Dependencies are baked into the image and available immediately — eliminating the 8-minute installation phase and reducing builds to approximately 4 minutes
  • B. Use a larger CodeBuild compute type (BUILD_GENERAL1_2XLARGE) to speed up pip install
  • C. Cache the Python virtual environment in S3 between builds with all dependencies pre-installed (PySpark and use it as the CodeBuild custom build environment
  • D. Skip dependency installation by removing the install phase from buildspec.yml
Jawaban Benar: A
Custom Docker images with pre-installed dependencies eliminate installation time entirely. The image is built once (manually or via a separate pipeline), pushed to ECR, and referenced in the CodeBuild project. Every build starts with all dependencies available, making 15 daily deployments feasible with 4-minute builds. This saves the team 120 minutes/day (8 min × 15 builds) compared to installing each time. Opsi B — larger compute speeds up CPU-bound tasks but pip install is mostly network I/O (downloading packages), providing minimal improvement. Opsi C — S3 caching helps but still requires downloading and extracting the cache each build (2-3 minutes overhead); not as fast as pre-installed deps. Opsi D — skipping installation means tests can't run since PySpark/pandas won't be available.

A data engineering team implements CI/CD for their pipeline but lacks confidence in deployments because they have no automated way to verify the deployment succeeded beyond "no errors." After deploying a Glue job update, they want automated validation that the job processes data correctly in production. Which post-deployment verification approach is MOST appropriate?
  • A. Add a post-deployment stage in CodePipeline that triggers a canary test: run the Glue job against a small known dataset in production, validate output row counts, checksums, and schema against expected values. If validation fails, automatically trigger rollback to the previous version. Use CloudWatch custom metrics to track deployment success rate
  • B. Send a Slack notification after deployment and ask team members to manually check output data
  • C. Consider the deployment successful if CloudFormation stack update completes without errors and schema against expected values
  • D. Wait for downstream consumers to report data quality issues within 24 hours
Jawaban Benar: A
Post-deployment canary tests validate functional correctness in the actual production environment. Running against a known dataset with expected outcomes provides a definitive pass/fail signal. Automated rollback on failure minimizes the blast radius of bad deployments. CloudWatch metrics track deployment health over time, identifying patterns (e.g., deployments failing more on Fridays). This closes the gap between "deployed" and "working correctly." Opsi B — manual checks are slow, unreliable, and don't scale to 15 deployments/day. Opsi C — CloudFormation success means infrastructure deployed correctly, not that the application logic is correct. Opsi D — waiting 24 hours for consumer reports means bad data propagates through the entire system before detection.

A regulated financial institution requires that all data pipeline deployments have an auditable approval trail. Every production deployment must be approved by a team lead, and the approval record must be retained for 7 years. The team uses CodePipeline for CI/CD. Which mechanism satisfies the audit and approval requirements?
  • A. Add a Manual Approval action in CodePipeline between the staging and production deploy stages. Configure SNS to notify approvers. The approval action records who approved, when, and includes optional comments. CloudTrail logs all CodePipeline API calls including approval actions. Store CloudTrail logs in S3 with a lifecycle policy retaining them for 7 years with Glacier archival
  • B. Require team leads to send an email saying "approved" before the engineer deploys manually
  • C. Use IAM policies that require MFA for production deployments without any approval workflow
  • D. Add a Jira ticket approval step that blocks deployment until the ticket is marked "Done" with a lifecycle policy retaining them for 7 years with Glacier archival and production deploy stages
Jawaban Benar: A
CodePipeline Manual Approval actions provide integrated, auditable gates. The approval is recorded with the approver's IAM identity, timestamp, and comments — all stored in the pipeline execution history. CloudTrail provides additional audit logging of all API calls. S3 lifecycle policies with Glacier transition ensure 7-year retention at minimal cost. The entire flow is automated except the approval decision, creating an immutable audit trail. Opsi B — email approvals are not machine-verifiable, easily lost, and don't integrate with deployment automation. Opsi C — MFA verifies identity but doesn't capture explicit approval decisions or provide an audit trail of what was approved. Opsi D — Jira integration requires custom development and the approval record lives outside the AWS audit trail.

A data engineering team adopts GitOps for managing their data pipeline infrastructure. They want Git to be the single source of truth: any change to the Git repository automatically reconciles the actual AWS infrastructure to match the desired state in the repository. If someone manually changes infrastructure, the system should detect and correct the drift. Which architecture implements GitOps for data engineering on AWS?
  • A. Store all CloudFormation/CDK templates in Git. Configure CodePipeline to trigger on commits. Add a pre-deployment stage that runs CloudFormation drift detection — if drift is detected, the pipeline first reverts manual changes by redeploying the current Git state before applying new changes. Use AWS Config rules to continuously monitor for out-of-band changes and trigger remediation via Systems Manager Automation
  • B. Use Git webhooks to trigger Lambda functions that run AWS CLI commands for each resource change
  • C. Store infrastructure configurations in Git and manually run cdk deploy when changes are made and trigger remediation via Systems Manager Automation
  • D. Use pull requests for approval but still deploy by running scripts locally from developer laptops
Jawaban Benar: A
Full GitOps requires: Git as source of truth (all infra in repo), automatic deployment on commit (CodePipeline trigger), and drift remediation (detecting and correcting manual changes). The drift detection stage ensures infrastructure matches Git state before new changes. AWS Config continuously monitors for out-of-band modifications, and Systems Manager Automation automatically remediates drift without manual intervention. This creates a self-healing infrastructure system. Opsi B — Lambda functions running CLI commands lack state management, dependency resolution, and rollback capabilities. Opsi C — manual deployment breaks the "automatic reconciliation" principle of GitOps. Opsi D — local deployment from laptops isn't automated, auditable, or repeatable across team members.
