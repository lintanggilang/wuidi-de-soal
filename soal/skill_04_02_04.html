Lake Formation permissions for Amazon Redshift, Amazon EMR, Amazon Athena, and Amazon S3

1
A data lake team is migrating from S3 bucket policies to AWS Lake Formation for permission management. Currently, 30 different IAM policies grant access to various S3 paths for different teams. After enabling Lake Formation, some Athena queries that previously worked now return "Access Denied". What is the MOST likely cause?
  • A. When Lake Formation is enabled for a database/table, it becomes the authoritative permission layer — the IAMAllowedPrincipals group (which previously gave broad S3/Glue access) must be removed, and explicit Lake Formation GRANT permissions must be given to each principal that needs access. Existing IAM policies alone are no longer sufficient
  • B. Athena is not compatible with Lake Formation for a database/table
  • C. The S3 bucket was encrypted and Lake Formation cannot read encrypted data
  • D. Lake Formation requires all tables to be re-crawled before access is granted
Jawaban Benar: A
Transisi ke Lake Formation melibatkan perubahan permission model: Sebelum Lake Formation: Access dikontrol oleh IAM policies (glue:GetTable, s3:GetObject) + S3 bucket policies. Group "IAMAllowedPrincipals" di Lake Formation secara default memberikan "Super" permission ke semua databases — effectively bypassing Lake Formation permissions. Setelah migration (removing IAMAllowedPrincipals): Lake Formation becomes authoritative — principals HARUS memiliki BOTH: (1) IAM policy yang allows Lake Formation/Glue/S3 API calls, DAN (2) Lake Formation GRANT pada specific database/table/column. Tanpa Lake Formation GRANT, meskipun IAM policy allows glue:GetTable dan s3:GetObject, access DENIED. Migration steps: (1) Identify all principals needing access, (2) Create Lake Formation GRANTs untuk each, (3) THEN remove IAMAllowedPrincipals.

Opsi A: BENAR.
Opsi B: SALAH. Salah — Athena natively integrates with LF — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. Salah — LF handles KMS encrypted data.
Opsi D: SALAH. Re-crawl not required for permission changes.

A data engineer needs to implement row-level and cell-level security for a data lake table accessed via Athena and Redshift Spectrum. The "transactions" table contains a "region" column and a "ssn" column. The US team should only see US region rows and the SSN column should be masked for all non-admin users. Which Lake Formation feature provides this?
  • A. Implement client-side filtering in the application query layer
  • B. Create separate tables for each region and grant access accordingly with column-level exclusion or masking (exclude/mask SSN column)
  • C. Use S3 bucket policies to restrict access to specific S3 partitions
  • D. Use Lake Formation Data Filters — create a filter that combines row-level filtering (WHERE region = 'US') with column-level exclusion or masking (exclude/mask SSN column), then grant table access WITH the data filter applied to the US team's principal
Jawaban Benar: D
Lake Formation Data Filters (juga dikenal sebagai Data Cell Filtering) memungkinkan fine-grained access control: Row-Level Filter: Ekspresi yang mendefinisikan rows mana yang visible. Contoh: "region = 'US'" — hanya rows dengan region US yang returned ke querier. Column-Level Control: Specify included columns (whitelist) atau excluded columns (blacklist). Contoh: exclude "ssn" column. Cell-Level Security: Kombinasi row + column filtering. Specific cells (intersection of filtered rows and columns) yang accessible. Implementation: (1) CREATE DATA FILTER us_team_filter ON TABLE transactions WITH ROW FILTER EXPRESSION "region = 'US'" AND COLUMN EXCLUSION ["ssn"]; (2) GRANT SELECT ON TABLE transactions WITH DATA FILTER us_team_filter TO PRINCIPAL us_team_role; Saat US team queries: SELECT * FROM transactions → otomatis hanya melihat US rows, tanpa SSN column.

Opsi A: SALAH. Not enforced server-side, bypassable.
Opsi B: SALAH. Data duplication, ETL complexity — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. S3 bukan aware of column-level content.
Opsi D: BENAR.
3
A large organization has 500+ tables in their data lake catalog and 200+ IAM roles that need different levels of access. Managing individual GRANT statements for each role-table combination is becoming unscalable. Which Lake Formation feature dramatically simplifies permission management at scale?
  • A. Write a custom Lambda function to auto-generate GRANT statements nightly
  • B. Use LF-Tags (Tag-Based Access Control) — assign key-value tags to databases/tables/columns (e.g., "classification"="confidential", "domain"="finance"), then GRANT permissions based on tag expressions rather than specific resource ARNs. When new tables are created with matching tags, permissions are automatically applied
  • C. Create a single "data lake admin" role that has access to everything and share credentials
  • D. Use AWS Organizations SCPs to manage all data lake permissions with matching tags
Jawaban Benar: B
LF-Tags (Lake Formation Tag-Based Access Control) adalah ABAC pattern untuk data lakes: Step 1 — Define LF-Tag keys: "classification" (values: public, internal, confidential), "domain" (values: finance, marketing, engineering). Step 2 — Assign tags to resources: Table "revenue" → classification=confidential, domain=finance. Table "web_analytics" → classification=internal, domain=marketing. Step 3 — Grant permissions based on tags: GRANT SELECT TO analytics_role ON TAG (classification=internal OR classification=public) AND (domain=marketing); Result: analytics_role automatically gets access ke SEMUA current and future tables yang match tag expression. Scale benefit: 500 tables × 200 roles = 100,000 potential individual grants. Dengan LF-Tags: ~10-20 tag-based grant expressions cover semua scenarios. New tables automatically get permissions saat tagged.

Opsi A: SALAH. Custom code maintenance burden, eventual consistency issues.
Opsi B: BENAR.
Opsi C: SALAH. Massive security risk.
Opsi D: SALAH. SCPs are for API-level controls, not data-level — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A multi-account organization wants to share specific data lake tables from the central data account (Account A) with an analytics account (Account B) using Lake Formation. Account B's Athena users should be able to query the shared tables. What is the correct cross-account sharing configuration?
  • A. Use AWS Glue crawlers in Account B to re-crawl Account A's S3 data
  • B. Export data from Account A to Account B nightly using Glue ETL jobs configured for optimal performance and minimal operational overhead
  • C. In Account A: use Lake Formation to GRANT SELECT on specific tables to Account B's AWS account ID (or specific IAM roles/Organization). In Account B: accept the RAM share (if using RAM method) or create a resource link in the local Glue catalog pointing to the shared database; then grant Lake Formation permissions to local principals on the resource link
  • D. Create S3 cross-account bucket policies and share the Glue catalog ARNs directly
Jawaban Benar: C
Lake Formation cross-account sharing workflow: Account A (Data Owner): (1) Register S3 locations with Lake Formation, (2) GRANT SELECT on databases/tables ke Account B (AWS account ID, IAM role ARN, or Organization ID), (3) Optionally choose sharing method: Named Resource method or LF-Tag method. Account B (Data Consumer): (1) Accept the resource share (via AWS RAM if applicable), (2) Create Resource Link di local Glue catalog: This is a pointer to Account A's shared database/table. Resource link appears as local catalog entry. (3) GRANT Lake Formation permissions pada resource link ke local IAM principals (e.g., Athena users/roles). (4) Local users query through resource link — transparently queries Account A's data. Key: Data stays in Account A's S3 — no copying. Lake Formation handles cross-account S3 access transparently.

Opsi A: SALAH. Would require S3 cross-account access AND creates duplicate metadata.
Opsi B: SALAH. Data duplication, latency, cost — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: BENAR.
Opsi D: SALAH. Requires complex bucket policy management dan doesn't leverage LF governance.
5
A data engineer has both Lake Formation permissions AND S3 bucket policies configured for their data lake. An Athena user has Lake Formation GRANT (SELECT on table "orders") but the S3 bucket policy explicitly DENIES the user's role from accessing the underlying S3 path. What happens when the user queries the "orders" table via Athena?
  • A. The query succeeds but returns empty results with native S3 integration and optimized data transfer
  • B. Lake Formation disables all S3 bucket policies automatically when enabled
  • C. Access is denied — S3 bucket policies still apply as an additional layer. Lake Formation grants permission at the catalog/metadata level, but the actual data read from S3 still requires the S3 access to not be explicitly denied. However, when Lake Formation manages S3 access through its service role, the user's direct S3 permissions are not evaluated — the Lake Formation service role reads S3 on the user's behalf
  • D. Access is allowed because Lake Formation permissions override S3 bucket policies
Jawaban Benar: C
Lake Formation permission model has nuance regarding S3 access: When S3 location is REGISTERED with Lake Formation: LF service role (AWSServiceRoleForLakeFormation) reads S3 on behalf of users. The USER'S S3 permissions are NOT evaluated — LF service role's permissions are used. In this case, S3 bucket policy denying the USER's role wouldn't block access because the service role is the one actually reading S3. When S3 location is NOT registered (or using hybrid mode): User's credentials are used for S3 access — bucket policy WOULD apply. Critical distinction: Jika S3 bucket policy denies the LAKE FORMATION SERVICE ROLE, maka access blocked regardless. Best practice: Register all data lake S3 locations with Lake Formation sehingga permission management centralized. Remove broad IAMAllowedPrincipals access dan let LF service role handle S3 reads.

Opsi A: SALAH. Either full results or access denied, not empty — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: SALAH. Salah — bucket policies remain intact.
Opsi C: BENAR.
Opsi D: SALAH. Oversimplifies — LF doesn't "override" bucket policies, it uses different access path.

A data engineer is setting up Lake Formation for the first time. They need to register an S3 bucket (s3://company-data-lake/) as a data location. The bucket contains sensitive data encrypted with a customer-managed KMS key. What must be configured for Lake Formation to successfully manage permissions on this data?
  • A. Register the S3 location in Lake Formation, specifying the IAM role that Lake Formation uses to access the data. This role must have: s3:GetObject/PutObject/ListBucket on the S3 path AND kms:Decrypt/kms:GenerateDataKey on the customer-managed KMS key. The KMS key policy must also allow this role to use the key
  • B. Disable KMS encryption before registering with Lake Formation since they are incompatible
  • C. Use the root account credentials to register the S3 location
  • D. Only register the S3 path in Lake Formation — KMS permissions are handled automatically with fully managed infrastructure and automatic scaling
Jawaban Benar: A
Registering S3 locations dengan Lake Formation requires proper IAM role configuration: Registration: REGISTER RESOURCE s3://company-data-lake/ WITH IAM ROLE arn:aws:iam::account:role/LakeFormationDataAccessRole. The specified role needs: S3 Permissions: s3:GetObject, s3:PutObject, s3:DeleteObject on s3://company-data-lake/*, s3:ListBucket on the bucket. KMS Permissions (critical for encrypted data): kms:Decrypt — to read encrypted objects, kms:GenerateDataKey — to write encrypted objects, kms:DescribeKey — to verify key status. Additionally, KMS Key Policy must include: {"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::account:role/LakeFormationDataAccessRole"}, "Action": ["kms:Decrypt", "kms:GenerateDataKey", "kms:DescribeKey"], "Resource": "*"}. Without KMS permissions, Lake Formation reads will fail with AccessDenied even if S3 permissions are correct.

Opsi A: BENAR.
Opsi B: SALAH. Salah — Lake Formation fully supports KMS.
Opsi C: SALAH. Never use root account.
Opsi D: SALAH. Salah — KMS permissions require explicit configuration — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A company operates in "hybrid" permission mode for their Lake Formation catalog. Some databases use Lake Formation permissions (new databases), while legacy databases still use IAM-only permissions. A data engineer needs to understand how permissions are evaluated in each mode. Which statement correctly describes hybrid mode behavior?
  • A. In hybrid mode: databases opted-in to Lake Formation require BOTH Lake Formation grants AND IAM permissions; databases NOT opted-in (legacy) continue using IAM permissions only (with IAMAllowedPrincipals granting Super). This allows gradual migration without breaking existing access patterns
  • B. In hybrid mode, permissions are randomly applied from either Lake Formation or IAM depending on the query engine
  • C. Hybrid mode means Lake Formation is disabled and only IAM policies apply configured for optimal performance and minimal operational overhead
  • D. All databases use Lake Formation permissions regardless of the hybrid mode setting
Jawaban Benar: A
Hybrid Access Mode allows per-database/table opt-in to Lake Formation: Databases NOT opted-in (legacy mode): IAMAllowedPrincipals group retains "Super" permission. Any IAM principal with glue:GetTable, s3:GetObject permissions can access data. Lake Formation grants are ignored. This is the DEFAULT state untuk existing databases. Databases OPTED-IN to Lake Formation: IAMAllowedPrincipals is removed (or restricted). Access requires: (1) IAM policy allowing Glue/Athena/LF API calls (e.g., lakeformation:GetDataAccess, glue:GetTable), AND (2) Explicit Lake Formation GRANT to the principal. Migration strategy: Opt-in databases one at a time — add LF grants to all principals, then remove IAMAllowedPrincipals. If something breaks, can revert by re-adding IAMAllowedPrincipals.

Opsi A: BENAR.
Opsi B: SALAH. Nothing random, behavior is deterministic per-database.
Opsi C: SALAH. Salah — LF is active for opted-in DBs — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: SALAH. Salah — hybrid is per-database.

A data engineer grants Lake Formation permissions: GRANT SELECT ON TABLE "sales" TO ROLE "analyst_role" WITH GRANT OPTION. An analyst with this role then tries to grant SELECT on "sales" to another role "intern_role". What happens and what are the implications of WITH GRANT OPTION?
  • A. The grant fails because only Lake Formation Admins can grant permissions with GRANT OPTION delegates granting authority — the analyst becomes a data steward for this table and can further distribute access
  • B. The analyst can successfully grant SELECT on "sales" to "intern_role" because WITH GRANT OPTION delegates granting authority — the analyst becomes a data steward for this table and can further distribute access. However, they can only grant permissions they themselves possess and cannot grant higher-level permissions (like ALTER or DROP)
  • C. WITH GRANT OPTION means the permission will automatically expire after a set time
  • D. The analyst can grant ANY permission on any table because WITH GRANT OPTION provides administrative access
Jawaban Benar: B
WITH GRANT OPTION di Lake Formation mendelegasikan granting authority: Tanpa GRANT OPTION: Principal can use the permission (SELECT) but CANNOT share it with others. Dengan GRANT OPTION: Principal can both USE the permission AND GRANT it to other principals. Constraints: (1) Can only grant permissions they themselves hold — analyst has SELECT, so can only grant SELECT (not INSERT, ALTER, DROP, etc.). (2) Can grant to other roles/users but not beyond their own permission scope. (3) If the original grant is REVOKED, all downstream grants (cascading) can also be revoked. Use case: Data stewardship model — domain owners receive permissions WITH GRANT OPTION and manage access for their team without involving Lake Formation admin for every request. Decentralized governance.

Opsi A: SALAH. Salah — non-admins with GRANT OPTION can grant — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: BENAR.
Opsi C: SALAH. Salah — GRANT OPTION is about delegation bukan expiry.
Opsi D: SALAH. Salah — scope limited to what they themselves have.

An EMR cluster needs to query Lake Formation-governed tables. The cluster uses instance profiles for IAM authentication. The data engineer discovers that EMR jobs fail with permission errors even though the instance profile has Lake Formation grants. What additional configuration is required for EMR to work with Lake Formation?
  • A. EMR does not support Lake Formation integration with native S3 integration and optimized data transfer
  • B. Grant the EMR instance profile s3:* permissions on all data lake buckets
  • C. Run EMR jobs only during Lake Formation's scheduled permission evaluation window
  • D. Enable Lake Formation integration for the EMR cluster by specifying a "Runtime Role" or configuring the EMR security configuration to use Lake Formation session-level credentials; the EMR cluster must use credential vending through Lake Formation's GetDataAccess API rather than direct S3 access via the instance profile
Jawaban Benar: D
EMR + Lake Formation integration requires specific configuration: Standard EMR (without LF integration): EMR uses instance profile to access S3 directly. Lake Formation permissions are NOT enforced — only IAM + S3 policies apply. Anyone on the cluster with instance profile access can read ALL data. EMR with Lake Formation integration: (1) Configure EMR Security Configuration with Lake Formation enabled. (2) EMR uses "credential vending" — instead of using instance profile for S3, it calls Lake Formation's GetDataAccess API. (3) Lake Formation returns temporary, scoped credentials that only allow access to data the requesting principal is granted. (4) Per-user/per-job enforcement — different users on same cluster get different credentials. (5) Supports SAML-based user identity for fine-grained access. Requirements: EMR runtime roles support, Lake Formation grants to the runtime role or user identity, EMR cluster configured with proper security configuration.

Opsi A: SALAH. Salah — EMR does support LF integration — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: SALAH. Defeats purpose of LF (bypasses fine-grained control).
Opsi C: SALAH. No scheduled evaluation window concept in LF.
Opsi D: BENAR.

A data governance team wants to understand the precedence rules when Lake Formation permissions, IAM policies, and S3 bucket policies all exist. A principal has: Lake Formation GRANT SELECT on table "orders", IAM policy DENY on glue:GetTable for the "orders" table resource, and S3 bucket policy ALLOW for the underlying S3 path. What is the final access result when querying the "orders" table through Athena?
  • A. Access is allowed because Lake Formation GRANT and S3 Allow combine to override the IAM Deny
  • B. The request enters an infinite evaluation loop and times out
  • C. Access is allowed because Lake Formation permissions have higher priority than IAM policies with native S3 integration and optimized data transfer
  • D. Access is DENIED — IAM explicit Deny ALWAYS takes precedence over everything else. Even though Lake Formation grants SELECT and S3 allows the path, the IAM Deny on glue:GetTable prevents the query engine from reading table metadata, which blocks the entire query. Lake Formation permissions cannot override IAM explicit Deny
Jawaban Benar: D
Permission evaluation precedence (highest to lowest): (1) Explicit Deny (any layer) — ALWAYS wins. IAM explicit Deny overrides everything. (2) Service Control Policies (SCPs) — organization-level ceiling. (3) Permission Boundaries — identity-level ceiling. (4) IAM Allow + Lake Formation Grant — BOTH required for access. (5) S3/Resource policies — additional layer. In this scenario: Athena query process: Step 1: Athena calls Glue:GetTable to read table metadata → IAM evaluates → EXPLICIT DENY found → request FAILS immediately. Query never reaches Step 2 (actual data read from S3). Lake Formation permissions work ALONGSIDE IAM, not above it. For successful access, principal needs: (1) NO explicit IAM Deny on relevant actions, (2) IAM Allow for service APIs (glue:GetTable, lakeformation:GetDataAccess, athena:StartQueryExecution), (3) Lake Formation GRANT on the table.

Opsi A: SALAH. Salah — Deny always wins.
Opsi B: SALAH. No loop, evaluation is deterministic.
Opsi C: SALAH. Salah — LF does not override IAM — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: BENAR.
