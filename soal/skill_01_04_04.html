A data engineering team of 8 members works on a shared AWS Glue ETL codebase. They frequently experience merge conflicts and broken deployments when multiple engineers push changes simultaneously. The team needs a Git branching strategy that allows parallel development while protecting the production pipeline. Which approach is MOST appropriate?
  • A. Use a trunk-based development model with short-lived feature branches, requiring pull requests with at least one approval before merging to main, combined with automated CI tests that run Glue job unit tests on every PR
  • B. Have all engineers commit directly to the main branch with no reviews
  • C. Use long-lived feature branches (lasting weeks) that are merged monthly
  • D. Maintain separate repositories for each engineer's work and manually copy code to production
Jawaban Benar: A
Trunk-based development with short-lived feature branches minimizes merge conflicts because branches diverge briefly. Pull request reviews catch errors before production. Automated CI running unit tests on PRs ensures broken code never reaches main. This balances velocity with safety. Opsi B — direct commits with no reviews leads to broken production pipelines. Opsi C — long-lived branches accumulate massive merge conflicts and integration issues (the exact problem they're facing). Opsi D — separate repos make collaboration impossible and code synchronization a nightmare.

A data engineer writes an AWS Glue ETL job that reads CSV files from S3, applies data type conversions, filters invalid records, and writes Parquet to a target bucket. The engineer wants to write unit tests for the transformation logic WITHOUT requiring an actual Spark cluster or AWS resources. Which testing approach is MOST effective?
  • A. Use pytest with a local SparkSession (spark-testing-base or pyspark local mode), create small in-memory DataFrames as test inputs, apply the transformation functions, and assert expected outputs using DataFrame comparisons
  • B. Deploy the job to a Glue development endpoint and manually verify output files in S3
  • C. Write integration tests that run the full Glue job against production data
  • D. Test by reading the output Parquet files after a production run and checking data quality
Jawaban Benar: A
Local SparkSession with pytest allows testing transformation logic in isolation — no AWS resources needed, fast feedback loop (seconds vs minutes). Pattern: create DataFrame with known input → apply transform function → assert output matches expected DataFrame. This tests business logic independently of infrastructure. Opsi B — development endpoints are expensive, slow, and don't provide automated regression testing. Opsi C — integration tests against production are slow, expensive, and not unit tests. Opsi D — testing after production is too late — bugs already affect downstream consumers.

A data engineer needs to validate that an end-to-end data pipeline correctly ingests data from an RDS source, transforms it in Glue, and loads it into Redshift with correct schema and row counts. Unit tests pass but production still occasionally produces incorrect results. Which additional testing strategy addresses this gap?
  • A. Implement integration tests that run the full pipeline against a dedicated test environment with known seed data, then validate row counts, schema conformity, data types, and sample record values in the target Redshift cluster
  • B. Add more unit tests for individual transformation functions
  • C. Perform manual spot-checks on production data weekly
  • D. Run the same unit tests multiple times to increase confidence
Jawaban Benar: A
Integration tests validate the interaction between components (RDS → Glue → Redshift) which unit tests cannot cover. Issues like connection timeouts, schema drift in source, Redshift COPY command failures, and data type mismatches only surface during end-to-end execution. A dedicated test environment with seed data provides repeatable, automated validation. Opsi B — more unit tests don't catch integration-level issues (connectivity, permissions, schema mismatches). Opsi C — manual checks are unreliable and not scalable. Opsi D — running the same tests repeatedly doesn't increase coverage.

A production AWS Glue ETL job processes millions of records nightly. When failures occur, the team struggles to identify which specific records caused issues and at what stage the failure happened. The current logging only outputs "Job failed." How should the engineer implement logging best practices?
  • A. Implement structured logging (JSON format) with correlation IDs, log at key checkpoints (records read, records filtered, records written), capture failed record details in a dead-letter location, and use different log levels (INFO for progress, WARN for data quality issues, ERROR for failures)
  • B. Add print statements throughout the code to output record counts
  • C. Enable Glue continuous logging and rely solely on the default Glue metrics
  • D. Write all records to a debug S3 bucket for manual inspection after failures
Jawaban Benar: A
Structured logging (JSON) enables CloudWatch Logs Insights queries for fast troubleshooting. Correlation IDs link related log entries across distributed workers. Checkpoint logging (records_read=1M, records_filtered=50K, records_written=950K) quickly identifies where data loss occurs. Dead-letter capture preserves failed records for investigation. Log levels allow filtering noise. Opsi B — print statements are unstructured, unsearchable, and provide no context. Opsi C — Glue metrics show job-level info but not record-level failures. Opsi D — writing all records to debug bucket is expensive and doesn't identify the failure point.

A data engineering team operates 25 data pipelines in production. They need to detect pipeline failures, SLA breaches, and data quality degradation proactively rather than hearing about issues from downstream consumers. Which monitoring approach provides comprehensive pipeline health visibility?
  • A. Create CloudWatch custom metrics for each pipeline (records_processed, processing_duration, error_count), set CloudWatch Alarms with appropriate thresholds for SLA breach detection, configure SNS notifications to the on-call team, and build a CloudWatch Dashboard showing all pipeline health metrics
  • B. Check the Glue console manually each morning for failed jobs
  • C. Set up email notifications only for job failures via Glue job bookmarks
  • D. Rely on downstream consumers to report when they notice missing data
Jawaban Benar: A
Custom CloudWatch metrics provide quantitative pipeline health data. Alarms trigger proactively BEFORE SLA breaches (e.g., alarm if processing_duration exceeds 80% of SLA window). SNS notifications ensure immediate human response. Dashboards give at-a-glance health across all 25 pipelines. This covers failures (error_count), performance degradation (duration trending up), and data completeness (records_processed below expected). Opsi B — manual checking is reactive and doesn't scale. Opsi C — job failure notifications don't catch SLA breaches or quality issues. Opsi D — learning from consumers means SLAs are already broken.

A senior data engineer reviews a pull request for a Glue ETL job. The code works correctly but has several maintainability concerns: hardcoded S3 paths, no input validation, duplicated transformation logic across functions, and SQL queries embedded as multi-line strings without formatting. Which code review feedback is MOST important for long-term pipeline reliability?
  • A. Externalize configuration (S3 paths, database names) to Glue job parameters or AWS Systems Manager Parameter Store, add input validation with descriptive error messages, extract duplicated logic into reusable functions, and move SQL to separate files or use parameterized templates
  • B. The code works correctly, so approve the PR without changes
  • C. Only fix the hardcoded paths and approve the rest
  • D. Rewrite the entire job from scratch following a different design pattern
Jawaban Benar: A
All four concerns impact long-term reliability: Hardcoded paths break when environments change (dev→prod). No input validation causes cryptic failures on bad data. Duplicated logic means bugs must be fixed in multiple places. Unformatted SQL is error-prone to modify. Externalizing config enables environment promotion. Input validation provides clear failure messages. DRY functions reduce bug surface area. Separated SQL files enable syntax checking. Opsi B — working code with technical debt accumulates maintenance cost. Opsi C — partial fixes leave other risks. Opsi D — full rewrite is excessive when targeted improvements suffice.

A data pipeline processes financial transactions and must handle various error scenarios: source database unavailable, malformed records, network timeouts to target system, and disk space exhaustion on EMR. The current pipeline fails completely on any error, requiring full reruns. Which error handling pattern BEST improves resilience?
  • A. Implement a tiered error handling strategy: retry transient errors (network timeouts, throttling) with exponential backoff, route malformed records to a dead-letter queue for later investigation, use checkpointing to enable resumption from the last successful point, and alert on non-retryable errors (disk full, permission denied)
  • B. Wrap the entire pipeline in a single try-except block that catches all exceptions and retries from the beginning
  • C. Ignore errors and continue processing, logging them for later review
  • D. Add a 5-minute sleep between operations to avoid all errors
Jawaban Benar: A
Tiered error handling distinguishes between error types: Transient errors (network, throttling) are retryable — exponential backoff prevents thundering herd. Malformed records shouldn't stop the pipeline — dead-letter queue preserves them without blocking good records. Checkpointing prevents reprocessing already-completed work after recovery. Non-retryable errors (disk full) need immediate human intervention. This pattern maximizes data throughput while maintaining data integrity. Opsi B — retrying from beginning is wasteful and may hit the same non-transient error. Opsi C — ignoring errors silently loses data. Opsi D — arbitrary sleeps don't prevent errors and add latency.

A data engineering team needs to deploy AWS Glue jobs across development, staging, and production environments. Each environment has different S3 buckets, database endpoints, IAM roles, and Glue job configurations (number of workers, timeout values). Deployments are currently manual and error-prone. Which CI/CD approach is MOST appropriate?
  • A. Use AWS CodePipeline with CodeBuild stages: source from CodeCommit/GitHub triggers the pipeline, CodeBuild runs unit tests, then deploys via CloudFormation/CDK with environment-specific parameter files (dev.json, staging.json, prod.json) that contain S3 paths, IAM roles, and worker counts for each environment
  • B. Manually upload Glue scripts to S3 and update job configurations through the AWS Console for each environment
  • C. Use a single Glue job configuration across all environments with if/else statements in the code to switch behavior
  • D. Deploy only to production and use production as the test environment
Jawaban Benar: A
CodePipeline provides automated, repeatable deployments. Environment-specific parameter files separate configuration from code — same CloudFormation template deploys to dev/staging/prod with different parameters. CodeBuild runs tests before deployment (fail-fast). Pipeline stages can include manual approval gates before production. This eliminates human error and ensures consistency across environments. Opsi B — manual deployment is the problem being solved; error-prone and unauditable. Opsi C — environment logic in code is fragile and makes testing difficult. Opsi D — testing in production risks data corruption and outages.

A data engineering team manages configurations for 30 Glue jobs that connect to various databases across environments. Connection strings, API keys, and feature flags differ between dev, staging, and production. Engineers occasionally deploy with wrong configurations, causing pipeline failures. Which configuration management approach is MOST secure and maintainable?
  • A. Store sensitive values (connection strings, API keys) in AWS Secrets Manager with environment-specific secret names, store non-sensitive configuration (feature flags, batch sizes) in AWS Systems Manager Parameter Store with hierarchical paths (/app/prod/glue/batch-size), and have Glue jobs retrieve configurations at runtime based on an environment parameter
  • B. Store all configurations in a config.py file committed to the Git repository
  • C. Use environment variables hardcoded in each Glue job definition
  • D. Maintain a shared spreadsheet with all configuration values that engineers reference during deployment
Jawaban Benar: A
Secrets Manager handles sensitive credentials with automatic rotation capability and audit logging. Parameter Store with hierarchical paths (/app/{env}/glue/{param}) organizes non-sensitive config by environment and service. Runtime retrieval based on environment parameter ensures jobs automatically get correct config without code changes. IAM policies control which environment's secrets each role can access. Opsi B — credentials in Git repos are a critical security vulnerability and are hard to rotate. Opsi C — hardcoded env vars require job updates for config changes and don't support rotation. Opsi D — spreadsheets have no access control, versioning, or audit trail.

A new data engineer joins the team and must take over maintenance of a complex pipeline that processes healthcare data through 12 Glue jobs, 5 Step Functions workflows, and 8 Lambda functions. There is no documentation. The original engineer has left the company. What documentation should the team prioritize creating to ensure pipeline supportability?
  • A. Create a runbook containing: architecture diagram showing data flow between components, SLA requirements per pipeline stage, common failure scenarios with remediation steps, escalation procedures, monitoring dashboard locations, and a data dictionary describing input/output schemas at each stage
  • B. Write inline code comments explaining every line of code in all 25 components
  • C. Create a single README.md with a high-level description of the project
  • D. Record a video walkthrough of the AWS Console showing each resource
Jawaban Benar: A
A runbook is the most operationally valuable documentation for pipeline maintenance. Architecture diagrams show dependencies and data flow. SLA requirements define when issues are urgent. Common failure scenarios with remediation steps enable quick resolution without deep code knowledge. Escalation procedures prevent single points of failure. Data dictionaries help understand what each component does. Opsi B — line-by-line comments are excessive, become stale, and don't help with operational issues. Opsi C — a single README lacks the operational detail needed for incident response. Opsi D — video walkthroughs become outdated as UI changes and are not searchable during incidents.
