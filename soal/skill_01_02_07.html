Skill 1.2.7: Troubleshoot and Debug Common Transformation Failures and Performance Issues

Debugging OOM errors, data skew, shuffle failures, schema mismatches, and performance bottlenecks in ETL pipelines

1
An AWS Glue ETL job fails with "Container killed by YARN for exceeding memory limits" error. The job processes a 500 GB dataset with a join between two large tables. CloudWatch metrics show high memory usage during the shuffle phase. Which is the MOST effective fix?
  • A. Switch from G.1X to G.2X worker type for more memory per executor, and increase spark.sql.shuffle.partitions to distribute shuffle data across more partitions
  • B. Add more G.1X workers to the job
  • C. Reduce the batch size by processing fewer records per run
  • D. Enable Glue job bookmarks to process less data
Jawaban Benar: A
OOM during shuffle indicates each executor's memory is insufficient for the shuffle data it receives. G.2X provides 32 GB memory per executor (vs 16 GB for G.1X). Increasing shuffle.partitions distributes data more evenly — each partition is smaller, reducing per-executor memory pressure. Opsi B (more workers) menambah parallelism tapi tidak menambah memory per executor. Opsi C mungkin bekerja tapi mengurangi throughput. Opsi D (bookmarks) tidak mengatasi join-related OOM.
2
A Glue Spark ETL job completes successfully but takes 4 hours instead of the expected 1 hour. The Spark UI shows that 95% of tasks complete in 5 minutes but 5% of tasks take 50+ minutes. What is this symptom and the MOST likely solution?
  • A. Data skew — some partitions have significantly more data than others. Use salting technique on the join key or repartition the data before the slow operation
  • B. Insufficient DPUs — add more workers to process faster
  • C. Network bottleneck — switch to a larger VPC subnet
  • D. Disk I/O throttling — switch to SSD-backed instances
Jawaban Benar: A
Ini adalah classic data skew pattern — beberapa tasks memproses data yang jauh lebih banyak. "Long tail" tasks memblokir stage completion. Salting technique menambahkan random suffix ke skewed key untuk mendistribusikan data lebih merata. Repartitioning sebelum operasi yang skewed juga membantu. Opsi B (more workers) — tasks yang lambat tetap di satu partition/worker. Opsi C (network) — bukan pola network issue. Opsi D (disk) — bukan pola I/O bottleneck.
3
An AWS Glue ETL job reads Parquet files from S3 and fails with "org.apache.spark.sql.AnalysisException: Cannot merge incompatible data types." The job worked yesterday. What is the MOST likely cause and how should it be investigated?
  • A. New files were added with a different schema (e.g., a column changed from integer to string). Check the Glue Data Catalog for schema version changes and run the crawler to update the schema
  • B. The Parquet files are corrupted
  • C. The Spark version was upgraded overnight
  • D. Network timeout caused partial file reads
Jawaban Benar: A
Schema incompatibility ("Cannot merge incompatible data types") biasanya terjadi ketika Spark membaca multiple Parquet files yang memiliki schema berbeda untuk kolom yang sama (misalnya file baru menulis integer sebagai string). Mengecek Data Catalog schema versions dan file terbaru mengidentifikasi perubahan. Crawler bisa mendeteksi dan update schema. Opsi B (corrupted) memberikan error berbeda. Opsi C (Spark upgrade) tidak terjadi secara otomatis di Glue. Opsi D (network) menyebabkan timeout error bukan schema error.
4
An EMR Spark job processing 2 TB of data fails with "java.io.IOException: No space left on device" error during a sort-merge join. The cluster has adequate total storage across all nodes. What is the MOST likely cause?
  • A. Shuffle data for specific partitions exceeds the local disk space on individual executor nodes. Increase spark.sql.shuffle.partitions to create smaller partitions, or add more local storage per node
  • B. The S3 bucket is full
  • C. The HDFS namenode ran out of metadata storage
  • D. The EMR master node disk is full from log accumulation
Jawaban Benar: A
Sort-merge join menulis shuffle data ke local disk. Jika partisi terlalu besar dan executor memiliki limited local storage, disk penuh. Meningkatkan shuffle.partitions mengurangi ukuran setiap partisi. Alternatif: gunakan instances dengan lebih banyak local NVMe storage (i3, d2) atau configure spark.local.dir ke EBS volume yang lebih besar. Opsi B — S3 tidak memiliki capacity limit per bucket. Opsi C (namenode) memberikan different error message. Opsi D (master node) tidak menyebabkan executor shuffle failure.
5
A data engineer notices that an AWS Glue job processing S3 data has gradually slowed down over several weeks, from 20 minutes to 2 hours, without any code changes. The data volume has remained constant at 100 GB per day. What is the MOST likely cause?
  • A. Small file problem — many small files have accumulated in the S3 prefix, causing excessive task scheduling overhead. Each file creates a separate Spark task
  • B. AWS throttled the account
  • C. The Glue service has degraded performance in the region
  • D. The S3 bucket needs to be vacuumed
Jawaban Benar: A
Gradual degradation dengan constant data volume strongly indicates small file accumulation. Setiap hari file baru ditambahkan tanpa compaction/cleanup. Setelah beberapa minggu, prefix memiliki ribuan file kecil. Spark membuat task per file, increasing scheduling overhead. Solusi: enable Glue groupFiles, atau tambahkan compaction job. Opsi B (throttling) menyebabkan sudden degradation. Opsi C (regional issue) would affect all customers. Opsi D — S3 tidak membutuhkan VACUUM.
6
A Glue ETL job reads from a MySQL database via JDBC and fails after 2 hours with "Communications link failure" error. The job processes data correctly for the first hour. The RDS instance shows no errors in its logs. What should the engineer check FIRST?
  • A. Check if the JDBC connection's idle timeout or wait_timeout on MySQL is closing long-running idle connections. Add connection keep-alive parameters to the JDBC URL
  • B. Check if the Glue job timeout is 2 hours
  • C. Check if MySQL has a query execution time limit
  • D. Check if the VPC route table has changed
Jawaban Benar: A
"Communications link failure" after extended time typically means idle connections were closed by the database. MySQL wait_timeout (default 28800s, but often reduced) closes idle connections. In parallel Glue processing, some JDBC connections become idle while others are active. After wait_timeout expires, idle connections are killed. Adding autoReconnect=true, tcpKeepAlive=true ke JDBC URL prevents this. Opsi B (job timeout) gives different error. Opsi C (query timeout) — queries were succeeding initially. Opsi D (route table) would cause immediate failure.
7
A data engineer runs a Spark transformation on EMR that performs a broadcast join. The job fails with "SparkException: Could not execute broadcast in time" error. The broadcast table is 10 GB. What is the issue and the correct fix?
  • A. The broadcast table exceeds the default broadcast threshold (10 MB). Either increase spark.sql.autoBroadcastJoinThreshold to accommodate the table size, or switch to a sort-merge join for the 10 GB table
  • B. The network bandwidth is insufficient for broadcasting
  • C. The driver node has insufficient memory — increase driver memory to hold the 10 GB table for broadcast
  • D. Enable data compression before broadcasting
Jawaban Benar: C
Broadcast join membutuhkan driver untuk mengumpulkan seluruh broadcast table dan mengirimkannya ke semua executors. Untuk 10 GB table, driver membutuhkan memory yang cukup (biasanya 2-3x table size untuk serialization overhead). Error "Could not execute broadcast in time" biasanya karena driver OOM atau timeout saat collecting data. Fix: increase driver memory, atau jangan broadcast table 10 GB — gunakan sort-merge join yang lebih scalable. Opsi A (threshold) — jika broadcast forced via hint, threshold tidak mencegah error. Opsi B (bandwidth) unlikely. Opsi D (compression) minimal impact.
8
An AWS Glue job writes output to S3 in Parquet format. The job succeeds but produces 10,000 small files (each 1 MB) instead of the expected 100 files of 100 MB. The downstream Athena queries are slow due to excessive file count. What causes this and how should it be fixed?
  • A. The number of output files equals the number of Spark partitions. Use coalesce(100) or repartition(100) before writing to reduce the number of output partitions to 100
  • B. S3 has a file size limit causing splits
  • C. Parquet format cannot produce large files
  • D. The Glue worker type determines file size
Jawaban Benar: A
Spark writes one file per partition. Jika DataFrame memiliki 10,000 partitions (common setelah shuffle operations), output menghasilkan 10,000 files. coalesce(100) mengurangi partitions ke 100 tanpa shuffle (preferred jika mengurangi), atau repartition(100) jika perlu redistribute data evenly. Opsi B — S3 file size limit 5 TB, bukan 1 MB. Opsi C — Parquet files bisa berukuran GB. Opsi D — worker type mempengaruhi memory bukan file size.
9
A data engineer's Glue ETL job intermittently fails with "AmazonS3Exception: 503 Slow Down" when reading from a high-traffic S3 prefix. Multiple pipelines read from the same prefix simultaneously. What is the root cause and solution?
  • A. S3 request rate limit per prefix (3,500 PUT/5,500 GET per second) is being exceeded. Distribute data across multiple prefixes using hashed key patterns to spread requests
  • B. The S3 bucket storage class doesn't support high throughput
  • C. The Glue job needs more DPUs
  • D. The VPC endpoint for S3 is throttling
Jawaban Benar: A
S3 throttles at prefix level (3,500 PUT/COPY/POST/DELETE dan 5,500 GET/HEAD per second per prefix). Multiple pipelines hitting the same prefix simultaneously exceeds these limits. Solution: distribute objects across multiple prefixes (e.g., add hash-based prefixes like /data/a1/, /data/b2/) to multiply the available request rate. Opsi B — all standard storage classes support same rate. Opsi C — more DPUs means more concurrent S3 requests which worsens the problem. Opsi D — VPC gateway endpoints don't throttle at this level.
10
A Glue ETL job joins two tables and the result has more rows than expected (Cartesian product behavior). The join condition uses a column that should be unique but investigation reveals NULL values in both tables' join columns. What caused this and how should it be prevented?
  • A. NULL = NULL evaluates differently in Spark — NULLs in join columns can cause unexpected join behavior. Filter out NULL values from join columns before the join, or use coalesce() to replace NULLs with a default value
  • B. The join type is wrong — switch from INNER to LEFT join
  • C. Spark has a bug with joins on large datasets
  • D. The Parquet files have duplicate row groups
Jawaban Benar: A
Dalam Spark SQL, NULL == NULL menghasilkan NULL (not TRUE), sehingga rows dengan NULL join keys biasanya tidak match. Namun, jika menggunakan Spark's internal join optimization atau certain join conditions, NULLs dapat menyebabkan unexpected behavior. Lebih umum, jika join column seharusnya unique tapi ada NULL duplicates, join bisa menghasilkan cross-product dari NULL rows. Best practice: filter WHERE join_column IS NOT NULL sebelum join, atau gunakan coalesce(). Opsi B (join type) tidak menjelaskan row explosion. Opsi C bukan Spark bug. Opsi D unlikely.
