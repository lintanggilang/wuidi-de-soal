A Glue crawler runs weekly against an S3 data lake and discovers that a table's schema has changed — a new column "loyalty_points" (integer) appeared in recent Parquet files that wasn't in older files. The crawler's schema change policy is set to "Update table definition in the catalog." After the crawler runs, Athena queries on older partitions (which don't have the loyalty_points column) return NULL for that column, while newer partitions return actual values. A data analyst is concerned about this behavior. What explains this behavior and is it correct?
  • A. This is an error — Athena should fail with a schema mismatch error when querying partitions whose files don't match the catalog schema exactly and expected, handling the described workload reliably at scale and transforming records into the required target format and applying schema conversion and enrichment inline and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design
  • B. The crawler should have backfilled the loyalty_points column with default values in the older Parquet files to maintain consistency, satisfying all of the stated requirements with minimal effort and validating and cleansing each record before delivery and applying schema conversion and enrichment inline and handling the described workload reliably at scale and integrating natively with the rest of the pipeline
  • C. This behavior is correct and expected. The crawler updated the catalog schema to include the new column (additive schema evolution). When Athena queries older Parquet files that don't contain the loyalty_points column, it returns NULL for that column because Parquet is self-describing — Athena reads whatever columns exist in each file and fills missing columns with NULL. This is the standard behavior for schema evolution in data lakes: the catalog reflects the UNION of all columns, and each file contributes only the columns it contains
  • D. This behavior indicates a crawler misconfiguration — the crawler should have created a new table version rather than updating the existing table, preserving the old schema for old partitions, satisfying all of the stated requirements with minimal effort and validating and cleansing each record before delivery and applying schema conversion and enrichment inline and transforming records into the required target format and integrating natively with the rest of the pipeline
Jawaban Benar: C
This is the correct and designed behavior for schema evolution in columnar data lakes: (1) Parquet files are self-describing — each file's footer contains its own schema; (2) the catalog schema represents the "superset" schema (union of all columns across all files/partitions); (3) when Athena reads a specific Parquet file, it maps the file's columns to the catalog schema by column name; columns present in the catalog but absent from the file return NULL; (4) this enables forward-compatible schema evolution — new columns can be added to new data without rewriting historical data; (5) queries that don't reference loyalty_points work identically on old and new partitions; queries that reference it get actual values from new data and NULL from old data. This is analogous to Iceberg's schema evolution behavior.

Opsi A: SALAH. Strict schema enforcement would make data lakes impractical; schema flexibility is a core data lake advantage over rigid warehouse schemas — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: SALAH. Crawlers NEVER modify data files — they only read and update metadata; backfilling data would violate the principle that crawlers are read-only discovery tools.
Opsi C: BENAR.
Opsi D: SALAH. Creating a separate table for each schema version would break queries that need to span old and new data; the single-table approach with NULL filling is the standard data lake pattern.

Opsi A: SALAH.
