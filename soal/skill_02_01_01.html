Skill 2.1.1: Implement Appropriate Storage Services for Specific Cost and Performance Requirements

Amazon Redshift, Amazon EMR, AWS Lake Formation, Amazon RDS, Amazon DynamoDB, Amazon Kinesis Data Streams, Amazon MSK

1
A retail company runs nightly ETL jobs that aggregate daily sales transactions from 200 stores into summary reports. The raw transaction data is 500 GB daily, stored in S3 as Parquet files. Analysts run complex SQL queries involving multi-table JOINs across 3 years of historical data (approximately 50 TB total). Queries must return within 30 seconds, and the analytics workload runs 8 hours per day on weekdays only. The company wants to minimize costs while meeting performance requirements. Which storage service is MOST appropriate?
  • A. Amazon Redshift with RA3 nodes using reserved instances, leveraging Redshift Managed Storage (RMS) to automatically tier data between high-performance local SSD cache and cost-effective S3 storage based on access patterns
  • B. Amazon Athena querying data directly from S3 Parquet files using the Glue Data Catalog for schema management
  • C. Amazon Redshift Serverless, which automatically provisions capacity when queries are submitted and scales to zero during idle periods
  • D. Amazon EMR with Spark SQL running on spot instances, reading data from S3 and scales to zero during idle periods
Jawaban Benar: C
Redshift Serverless is ideal for this workload because it automatically scales to handle complex JOINs across 50 TB (meeting the 30-second requirement) and scales to zero during the 16 hours/day and weekends when the cluster is idle — eliminating cost for ~76% of the time. With predictable 8-hour weekday usage, the pay-per-use model significantly reduces costs compared to always-on provisioned clusters. Opsi A — RA3 reserved instances run 24/7 (168 hours/week) but the workload only needs 40 hours/week, wasting 76% of provisioned capacity costs. Opsi B — Athena is cost-effective for ad-hoc queries but complex multi-table JOINs across 50 TB consistently within 30 seconds is unreliable without dedicated compute resources and result caching. Opsi D — EMR with Spark SQL requires cluster management overhead and Spot instance interruptions may fail time-sensitive analytics queries.
2
An e-commerce platform needs to store user session data that includes shopping cart contents, browsing history, and personalization preferences. The access pattern is primarily single-item reads and writes by user_id with sub-10ms latency requirements. Traffic varies from 5,000 requests per second during off-peak to 50,000 requests per second during flash sales. The company wants to avoid over-provisioning and minimize costs during low-traffic periods. Which storage service and pricing model is MOST appropriate?
  • A. Amazon DynamoDB with On-Demand capacity mode, which automatically scales to handle traffic spikes without capacity planning and charges only for actual read/write requests performed
  • B. Amazon DynamoDB with Provisioned capacity set to 50,000 RCU/WCU to handle peak load, with auto-scaling configured
  • C. Amazon RDS PostgreSQL with a db.r5.4xlarge instance and read replicas to handle the peak load
  • D. Amazon ElastiCache Redis cluster with 10 nodes to serve all session data from memory and charges only for actual read/write requests performed for actual read/write requests performed
Jawaban Benar: A
DynamoDB On-Demand mode is purpose-built for unpredictable workloads with 10x traffic variance. It instantly accommodates traffic spikes (5K to 50K RPS) without pre-provisioning, and you pay only for actual requests — dramatically reducing costs during the extended off-peak periods. The single-item read/write by primary key (user_id) pattern is DynamoDB's optimal use case, providing consistent single-digit millisecond latency. Opsi B — Provisioned at 50K RCU/WCU costs for peak capacity even during 5K RPS periods; auto-scaling takes minutes to react and may not handle sudden flash sale spikes. Opsi C — RDS has connection limits, requires vertical scaling for peak capacity, and session data (key-value pattern) doesn't benefit from relational features. Opsi D — ElastiCache Redis provides excellent latency but requires provisioned nodes running 24/7 and manual cluster scaling; it also lacks DynamoDB's durability guarantees.
3
A media company ingests 2 TB of video metadata events per hour from 10 million connected devices. The data must be available for real-time dashboard updates within 5 seconds of event generation, while also being stored for batch analytics. The company wants to use a single ingestion layer that supports both real-time consumers and batch consumers simultaneously, with the ability to replay events from the past 7 days. Which streaming storage service BEST meets these requirements?
  • A. Amazon Kinesis Data Streams with enhanced fan-out consumers for real-time processing and a separate consumer that writes to S3 for batch analytics, configured with 7-day retention for event replay capability
  • B. Amazon MSK (Managed Streaming for Apache Kafka) with multiple consumer groups — one for real-time dashboards and another for S3 batch loading — using log compaction with 7-day retention
  • C. Amazon SQS FIFO queue with multiple receivers processing messages and writing to both the dashboard and S3 simultaneously
  • D. Direct writes to Amazon S3 with S3 Event Notifications triggering Lambda for real-time processing and Athena for batch queries with fully managed infrastructure and automatic scaling
Jawaban Benar: B
Amazon MSK is optimal for this scenario: (1) at 2 TB/hour throughput, Kafka's partitioned log architecture handles this volume efficiently; (2) consumer groups allow multiple independent consumers (real-time dashboard + batch S3 loader) to read the same stream at different rates without interference; (3) 7-day retention enables full event replay; (4) Kafka's publish-subscribe model inherently supports both real-time and batch consumption patterns. MSK also provides built-in integration with AWS services and supports exactly-once semantics. Opsi A — Kinesis Data Streams can handle this but has shard-level throughput limits (1 MB/s or 1000 records/s per shard); 2 TB/hour would require ~570 shards, making it more expensive and complex to manage than MSK at this scale. Opsi C — SQS is a queue (each message consumed once), not a stream; it doesn't support multiple consumers reading the same messages or replay. Opsi D — S3 writes don't provide sub-5-second latency for real-time dashboards due to eventual consistency and event notification delays.
4
A startup needs to build a data analytics platform with limited budget. They have 5 TB of structured data in S3 (Parquet format) and analysts run ad-hoc queries 10-15 times per day, scanning on average 200 GB per query. The queries are exploratory and don't require sub-second response times — 30-60 seconds per query is acceptable. The team wants the lowest possible cost with no infrastructure management. Which service is MOST cost-effective?
  • A. Amazon Athena, which charges $5 per TB of data scanned with no infrastructure to manage, no minimum fees, and no charges when queries aren't running — resulting in approximately $15-30 per day for their usage pattern
  • B. Amazon Redshift dc2.large 2-node cluster on On-Demand pricing for the dedicated compute power
  • C. Amazon EMR cluster with m5.xlarge instances running Presto for interactive queries
  • D. Amazon Redshift Serverless with base capacity of 32 RPU for their usage pattern
Jawaban Benar: A
Athena's pay-per-query model ($5/TB scanned) is ideal for infrequent, ad-hoc analytics. At 200 GB/query × 15 queries/day = 3 TB/day scanned = $15/day. With Parquet format (columnar), actual data scanned is often 10-30% of raw size due to column pruning, potentially reducing costs further. No infrastructure management, no idle costs, and acceptable query times for exploratory analysis. Opsi B — Redshift dc2.large 2-node On-Demand costs ~$480/month running 24/7, regardless of whether queries are running; far more expensive for 15 queries/day. Opsi C — EMR requires managing cluster lifecycle, and even with auto-termination, minimum cluster spin-up costs exceed Athena's per-query pricing for low-frequency usage. Opsi D — Redshift Serverless at 32 RPU base has minimum charges and is designed for more sustained workloads; costs significantly more than Athena for 15 queries/day.
5
A financial services company processes market data feeds and needs to store trade execution records. Requirements include: ACID transactions for trade operations, complex SQL queries for regulatory reporting, consistent read-after-write, storage of 500 GB of highly normalized relational data, and support for stored procedures that enforce business rules. Peak load is 5,000 transactions per second. Which storage service is MOST appropriate?
  • A. Amazon Aurora PostgreSQL with Multi-AZ deployment, providing ACID compliance, up to 128 TB storage, up to 15 read replicas, and support for complex SQL including stored procedures and triggers with sub-millisecond read latency from the buffer cache
  • B. Amazon DynamoDB with transactions enabled to provide ACID compliance for trade operations configured for optimal performance and minimal operational overhead
  • C. Amazon Redshift for its SQL support and ability to handle complex queries on large datasets
  • D. Amazon S3 with AWS Glue for ETL processing and Athena for SQL queries on trade records
Jawaban Benar: A
Aurora PostgreSQL addresses all requirements: (1) ACID transactions are native to relational databases; (2) complex SQL with JOINs, window functions, CTEs for regulatory reporting; (3) read-after-write consistency guaranteed; (4) 500 GB highly normalized data is a classic OLTP relational use case; (5) stored procedures enforced at the database level; (6) Aurora handles 5,000 TPS with auto-scaling read replicas. Multi-AZ provides durability for financial data. Opsi B — DynamoDB transactions support ACID but limited to 100 items per transaction; it doesn't support complex SQL JOINs or stored procedures needed for regulatory reporting. Opsi C — Redshift is OLAP (analytical), not OLTP; it's optimized for large sequential scans, not high-frequency transactional writes at 5,000 TPS. Opsi D — S3 + Athena is a data lake pattern without ACID transactions, stored procedures, or consistent read-after-write guarantees.
6
A data engineering team needs to process and analyze 100 TB of semi-structured log data from a one-time migration project. The analysis involves complex transformations including sessionization, custom UDFs in Python, graph analysis of user journeys, and machine learning feature engineering. The project has a 2-week deadline and will not repeat. The team wants maximum flexibility and lowest cost for this temporary workload. Which service is MOST appropriate?
  • A. Amazon EMR with Spark on a transient cluster using Spot Instances (up to 90% savings), leveraging Spark's support for custom Python UDFs, GraphX for graph analysis, and MLlib for feature engineering, with the cluster terminated after the 2-week project completes
  • B. Amazon Redshift with a permanent provisioned cluster sized for the 100 TB workload
  • C. AWS Glue ETL jobs for all transformation, analysis, and ML feature engineering tasks with Spark on a transient cluster using Spot Instances (up
  • D. Amazon Athena for querying the log data with SQL and performing all required transformations
Jawaban Benar: A
EMR provides maximum flexibility for this scenario: (1) Spark supports custom Python UDFs, graph analysis (GraphX), and ML feature engineering (MLlib) — all required capabilities; (2) transient clusters (terminate after use) eliminate idle costs; (3) Spot Instances reduce compute costs by up to 90% for fault-tolerant batch processing; (4) 100 TB processing is well-suited to Spark's distributed computing model; (5) the 2-week temporary nature makes a transient cluster ideal — no long-term commitment. Opsi B — Redshift is a permanent data warehouse; provisioning for 100 TB, using it for 2 weeks, then decommissioning is expensive and Redshift doesn't support custom Python UDFs or graph analysis natively. Opsi C — Glue ETL has a 48-hour maximum job timeout and limited support for custom graph analysis or ML feature engineering compared to native Spark on EMR. Opsi D — Athena is SQL-only; it cannot perform graph analysis, custom Python UDFs, or ML feature engineering.
7
A company is building a data lake and needs to manage fine-grained access control, data governance, and cross-account data sharing for their analytics teams. They have data in S3, Redshift, and RDS sources. Different teams should only see specific columns and rows based on their department. The solution must centralize permission management rather than configuring access at each individual service. Which service BEST provides this centralized governance capability?
  • A. AWS Lake Formation, which provides centralized governance with column-level and row-level security, tag-based access control (LF-Tags), cross-account data sharing via RAM or direct Lake Formation grants, and integration with Athena, Redshift Spectrum, and Glue for unified permission enforcement
  • B. IAM policies applied to each S3 bucket, Redshift cluster, and RDS instance individually to control team access
  • C. Amazon Redshift with its native GRANT/REVOKE SQL commands to manage user permissions at the column level for unified permission enforcement
  • D. AWS Organizations with Service Control Policies (SCPs) to restrict which teams can access which data services
Jawaban Benar: A
Lake Formation is designed specifically for centralized data lake governance: (1) column-level security controls which columns each team can see; (2) row-level security (data filters) restricts rows by department; (3) LF-Tags allow policy-based access (tag columns as "PII" and grant access to tagged resources); (4) cross-account sharing via RAM or direct grants; (5) single permission model enforced across Athena, Glue, Redshift Spectrum — eliminating per-service configuration. Opsi B — per-service IAM policies create a fragmented, hard-to-maintain permission landscape with no column/row-level granularity in S3. Opsi C — Redshift native permissions only apply within Redshift, not across S3/Glue/Athena, and don't provide centralized governance. Opsi D — SCPs control service-level access (which services accounts can use), not data-level access (which rows/columns users can see).
8
A company currently uses Amazon Redshift DC2 nodes for their data warehouse. Their data has grown from 2 TB to 20 TB over 18 months, and frequently accessed "hot" data represents only 3 TB while the remaining 17 TB is accessed rarely for historical analysis. The current DC2 cluster requires expensive resizing to accommodate growth. Which Redshift node type migration provides the MOST cost-effective solution for this data growth pattern?
  • A. Migrate to Redshift RA3 nodes with Managed Storage, which automatically tiers hot data on fast local SSD cache and warm/cold data on S3-backed managed storage, allowing compute and storage to scale independently — pay for compute nodes while storage costs pennies per GB on S3
  • B. Add more DC2 nodes to the cluster through elastic resize to accommodate the full 20 TB on local SSDs with Managed Storage
  • C. Keep the DC2 cluster at 3 TB and offload historical data to S3, using Redshift Spectrum for historical queries
  • D. Migrate all 20 TB to Amazon Athena and decommission the Redshift cluster entirely
Jawaban Benar: A
RA3 nodes decouple compute from storage. Hot data (3 TB) is automatically cached on high-performance local SSDs for fast access, while the full 20 TB is stored on S3-backed Managed Storage at S3 pricing ($0.024/GB/month). You size RA3 nodes for compute needs (query concurrency/complexity), not storage volume. As data grows further, storage costs increase minimally while compute stays constant. This addresses the DC2 limitation where adding storage requires adding expensive compute nodes. Opsi B — adding DC2 nodes couples compute scaling with storage, paying for expensive SSD+compute even for rarely-accessed historical data; cost-ineffective for 17 TB of cold data. Opsi C — this manual approach requires data lifecycle management and separate query logic for hot vs. cold data; RA3 automates this transparently. Opsi D — Athena cannot match Redshift's performance for complex multi-table JOINs on hot data that requires sub-second response times.
9
A gaming company needs to store player state data (inventory, progress, achievements) for a mobile game with 20 million daily active users. Access patterns include: (1) read player state on game launch (point read by player_id), (2) update player state after each action (frequent writes), (3) leaderboard queries ranking top 100 players by score globally. Write latency must be under 10ms and reads under 5ms. Which combination of storage services addresses ALL requirements MOST effectively?
  • A. Amazon DynamoDB for player state reads/writes (point operations by player_id with consistent single-digit ms latency) combined with DynamoDB Global Secondary Index on score for leaderboard queries, using DynamoDB Accelerator (DAX) for sub-millisecond read caching
  • B. Amazon DynamoDB for player state with Amazon ElastiCache Redis Sorted Sets for the leaderboard (ZRANGEBYSCORE provides O(log n) + O(m) ranking queries with sub-millisecond latency)
  • C. Amazon Aurora PostgreSQL for all operations, using B-tree indexes on player_id for point lookups and ORDER BY score LIMIT 100 for leaderboard queries
  • D. Amazon S3 for player state storage with CloudFront caching for reads, and a Lambda function maintaining a leaderboard file configured for optimal performance and minimal operational overhead
Jawaban Benar: B
This combination uses each service for its optimal use case: (1) DynamoDB excels at high-throughput point reads/writes by primary key (player_id) with single-digit ms latency at 20M DAU scale; (2) Redis Sorted Sets are purpose-built for leaderboards — ZRANGEBYSCORE returns top-N players in O(log n + m) time with sub-millisecond latency, automatically maintaining sort order on every score update. Opsi A — DynamoDB GSI on score requires scanning all items to find top 100 globally, which is inefficient; GSI doesn't support efficient "top N across all partitions" queries because results are distributed across partitions. Opsi C — Aurora can handle this but connection pooling at 20M DAU with frequent writes and 5ms read requirement is challenging; it also requires managing read replicas and won't match DynamoDB's effortless scaling. Opsi D — S3 has 50-200ms first-byte latency, far exceeding the 5ms read requirement.

A logistics company needs to choose between building a data lake on S3 with Athena/Glue versus a data warehouse on Redshift for their analytics. Their data includes: structured shipment records (200 GB/day), semi-structured IoT sensor data from trucks (500 GB/day in JSON), and unstructured driver notes (50 GB/day in text). Analysts need both exploratory queries on raw data AND curated dashboards with sub-second response times. Which architecture BEST addresses both needs cost-effectively?
  • A. A lakehouse architecture: store all raw data in S3 (data lake) with Glue Data Catalog for schema management, use Athena for exploratory queries on raw/semi-structured data, and load curated aggregations into Redshift for sub-second dashboard queries — combining the flexibility of a data lake with the performance of a data warehouse
  • B. Load all data (structured, semi-structured, and unstructured) directly into Amazon Redshift, converting everything to structured tables
  • C. Store everything in S3 and use only Athena for both exploratory and dashboard queries
  • D. Use Amazon RDS PostgreSQL for structured data and S3 for unstructured data, with no integration between them with native S3 integration and optimized data transfer
Jawaban Benar: A
The lakehouse architecture combines data lake flexibility (S3 stores any format at low cost — structured, semi-structured, unstructured) with data warehouse performance (Redshift for curated, optimized sub-second queries). This addresses both requirements: analysts explore raw JSON/text in the lake using Athena's schema-on-read, while dashboards query pre-aggregated data in Redshift with sub-second latency. Cost is optimized by storing the bulk (750 GB/day) cheaply in S3 while loading only curated summaries into expensive Redshift storage. Opsi B — loading JSON and text into Redshift requires expensive transformation, wastes Redshift storage on data that may only be queried occasionally, and Redshift isn't optimized for semi-structured exploration. Opsi C — Athena cannot provide sub-second dashboard response times for concurrent users without result caching limitations. Opsi D — RDS isn't designed for analytics at this scale, and having no integration prevents cross-source analysis.
