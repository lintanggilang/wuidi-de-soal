A data engineer builds a serverless ETL workflow using Step Functions and Lambda. The workflow processes files uploaded to S3. During peak hours, 1,000 files arrive simultaneously. The Lambda function hits the account's concurrent execution limit (1,000), causing throttling. How should the workflow handle this without increasing the account limit?
  • A. Use Step Functions Map state with MaxConcurrency set to a value below the Lambda limit (e.g., 100) to control how many files are processed simultaneously
  • B. Add Wait states between each Lambda invocation
  • C. Process all files sequentially in a single Lambda invocation
  • D. Use reserved concurrency on the Lambda function set to 1,000
Jawaban Benar: A
MaxConcurrency pada Map state membatasi berapa banyak iterations yang berjalan bersamaan. Dengan MaxConcurrency=100, hanya 100 Lambda invocations berjalan concurrent, jauh di bawah account limit. Files lain menunggu dalam queue dan diproses saat slots tersedia. Opsi B (Wait states) adds latency tanpa guaranteeing concurrency control. Opsi C (single Lambda) timeout 15 menit — 1,000 files mungkin tidak selesai. Opsi D (reserved 1,000) mengambil semua account concurrency dari functions lain.
2
A serverless data pipeline uses EventBridge → Lambda → S3. The Lambda function processes events but occasionally takes longer than 15 minutes for large datasets. The function hits the maximum timeout limit. Which serverless redesign resolves this?
  • A. Replace the single Lambda with a Step Functions workflow that breaks processing into smaller chunks, each handled by a separate Lambda invocation within the 15-minute limit
  • B. Increase Lambda timeout beyond 15 minutes
  • C. Use Lambda provisioned concurrency to run longer
  • D. Switch to an EC2 instance for processing
Jawaban Benar: A
Step Functions can orchestrate multiple Lambda calls, each within the 15-minute limit. Pattern: first Lambda reads data and creates chunk list → Map state processes each chunk in separate Lambda invocations → final Lambda aggregates results. This remains fully serverless while removing the timeout constraint. Opsi B — 15 minutes is Lambda's hard limit, cannot be increased. Opsi C — provisioned concurrency doesn't change timeout. Opsi D — EC2 is not serverless, adds operational overhead.
3
A company has a serverless workflow that runs every hour via EventBridge Scheduler → Step Functions → Glue ETL. The Glue job costs significantly increase month-over-month. Analysis shows the job processes the same amount of data each run but worker utilization is low. Which serverless optimization reduces costs?
  • A. Enable AWS Glue Auto Scaling to dynamically reduce workers when utilization is low, and review if the number of workers can be reduced in the job configuration
  • B. Switch from Glue to a self-managed Spark cluster
  • C. Run the workflow less frequently (daily instead of hourly)
  • D. Increase the Glue job timeout to allow slower processing with fewer DPUs
Jawaban Benar: A
Glue Auto Scaling memungkinkan job menyesuaikan jumlah workers berdasarkan actual utilization. Jika utilization rendah, Auto Scaling mengurangi workers = fewer DPU-hours billed. Juga review NumberOfWorkers setting — mungkin over-provisioned dari awal. Opsi B (self-managed) menambah operational overhead, melanggar serverless principle. Opsi C mengubah business requirement. Opsi D (longer timeout) tetap membayar DPU per jam minimum billing.
4
A serverless data pipeline needs to maintain state between processing steps. Step 1 produces a list of files to process, Step 2 processes each file, and Step 3 needs to know which files succeeded and which failed. In AWS Step Functions, how is this state management handled?
  • A. Step Functions automatically passes output from each state as input to the next state via the state machine's JSON data flow (InputPath, OutputPath, ResultPath)
  • B. Use DynamoDB to store state between steps
  • C. Use S3 to store intermediate state files
  • D. Use environment variables shared across Lambda functions
Jawaban Benar: A
Step Functions has built-in state management. Each state receives input JSON, produces output JSON, and passes it to the next state. InputPath selects which part of input to send to the task, ResultPath determines where task output is placed, OutputPath selects what passes to next state. Map state automatically collects results from all iterations. No external storage needed for workflow state. Opsi B/C (external storage) unnecessary complexity. Opsi D (env vars) cannot be shared between separate Lambda invocations.
5
A data engineer needs to implement a serverless workflow that processes data every 5 minutes. The workflow must: read new files from S3, transform them, and load to DynamoDB. The total processing time is under 1 minute. Which is the MOST cost-effective serverless implementation?
  • A. EventBridge Scheduler (rate 5 minutes) → Lambda function that reads S3, transforms, and writes to DynamoDB
  • B. EventBridge Scheduler → Step Functions → Lambda
  • C. S3 Event Notifications → Lambda (triggered on each file upload)
  • D. Glue ETL job scheduled every 5 minutes
Jawaban Benar: C
S3 Event Notifications → Lambda is most cost-effective karena Lambda hanya dipanggil saat ada file baru (event-driven), bukan setiap 5 menit (polling). Jika tidak ada files, tidak ada cost. Processing under 1 minute easily fits Lambda limits. Opsi A (scheduled every 5 min) memicu Lambda bahkan ketika tidak ada new files. Opsi B (Step Functions) menambah cost tanpa benefit untuk simple single-step flow. Opsi D (Glue) memiliki minimum billing dan startup overhead yang overkill untuk sub-minute processing.
6
A serverless data pipeline uses Lambda functions. After a deployment, a Lambda function's cold start adds 10 seconds of latency to time-sensitive data processing. The function runs approximately every 30 seconds. How can cold starts be eliminated while maintaining serverless architecture?
  • A. Configure Provisioned Concurrency on the Lambda function to keep a specified number of execution environments warm and ready
  • B. Use a CloudWatch Events rule to "ping" the function every 5 minutes
  • C. Increase Lambda memory allocation to reduce cold start time
  • D. Move the function to a container on ECS Fargate
Jawaban Benar: A
Provisioned Concurrency keeps specified number of Lambda execution environments initialized and ready. Invocations go to pre-warmed environments with no cold start. Since the function runs every 30 seconds, Provisioned Concurrency of 1 ensures always-warm state. Opsi B (pinging) is unreliable — Lambda can still create new environments. Opsi C (more memory) reduces cold start time but doesn't eliminate it. Opsi D (ECS) leaves serverless paradigm and adds management overhead.
7
A data engineer maintains a serverless workflow deployed with AWS SAM. The workflow includes multiple Lambda functions, Step Functions, and DynamoDB tables. A recent deployment introduced a bug. The engineer needs to quickly revert to the previous working version. What is the FASTEST rollback approach?
  • A. Use CloudFormation rollback — update the SAM stack to the previous template version or trigger automatic rollback via the CloudFormation console/CLI
  • B. Manually delete all resources and redeploy from the previous git commit
  • C. Update each Lambda function individually to the previous version
  • D. Create a new stack with the previous version alongside the current one
Jawaban Benar: A
SAM deploys via CloudFormation. CloudFormation supports stack rollback — reverting all resources to previous state atomically. This rolls back Lambda code, Step Functions definition, and DynamoDB config together. Fastest because it's one command and handles all resources. Opsi B (delete+redeploy) causes downtime and potential data loss. Opsi C (individual Lambda) doesn't revert Step Functions or other resources. Opsi D (new stack) creates resource conflicts and doesn't fix the broken one.
8
A serverless ETL pipeline uses Step Functions Express Workflow for high-frequency, short-duration processing. The workflow is invoked 100,000 times per day, each execution lasting 10 seconds. The team notices unexpected costs. What is the MOST likely billing consideration they missed?
  • A. Express Workflows are billed per number of state transitions AND duration (memory × time), not just per execution. High state count per execution multiplied by 100K daily executions results in significant transition charges
  • B. Standard Workflows would be cheaper at this scale
  • C. Step Functions charges for failed executions too
  • D. The Lambda invocations inside the workflow are double-billed
Jawaban Benar: A
Express Workflows pricing = (number of requests) + (duration × memory). Duration is calculated per state transition multiplied by execution memory (64MB increments). For 100K executions/day × multiple state transitions each, costs accumulate. If each execution has 10 states × 10 seconds, that's billed differently than expected. Understanding the pricing model (transitions × duration × memory) is critical. Opsi B — depends on the specific case, at high volume Express is often cheaper. Opsi C — true but not the "missed" consideration. Opsi D — Lambda not double-billed.
9
A serverless workflow uses EventBridge Pipes to connect Amazon SQS (source) → Lambda (enrichment) → Step Functions (target). The engineer needs to filter messages so only orders above $100 are processed. Where should this filtering be applied for MAXIMUM cost efficiency?
  • A. Configure filtering in the EventBridge Pipe's filter criteria — messages not matching the filter are discarded before reaching the enrichment Lambda or target, saving Lambda invocation and Step Functions execution costs
  • B. Add filtering logic inside the Lambda enrichment function
  • C. Add a Choice state in Step Functions to discard low-value orders
  • D. Configure SQS message filtering on the queue
Jawaban Benar: A
EventBridge Pipes filter criteria evaluates messages BEFORE enrichment and target. Messages that don't match are discarded at the pipe level — no Lambda invocation, no Step Functions execution. This is the earliest and cheapest filtering point. Opsi B (Lambda filter) — Lambda already invoked and billed before filtering. Opsi C (Step Functions Choice) — Step Functions execution already started and billed. Opsi D — SQS doesn't have built-in message body filtering (only for SNS subscriptions).

A data engineer is troubleshooting a serverless workflow. A Step Functions execution failed but the error details are unclear from the execution history. The Lambda function inside didn't log sufficient information. Which approach provides BEST observability for serverless workflows?
  • A. Enable Step Functions X-Ray tracing for distributed tracing, configure CloudWatch Logs for the state machine execution logs (ALL level), and add structured logging with correlation IDs in Lambda functions
  • B. Add print statements throughout the Lambda code
  • C. Check the Step Functions console execution history only
  • D. Enable VPC Flow Logs for the Lambda function
Jawaban Benar: A
Comprehensive observability: X-Ray provides end-to-end distributed traces showing timing and errors across all services. CloudWatch Logs at ALL level captures every state transition with input/output. Structured logging with correlation IDs (execution ID) links Lambda logs to specific Step Functions execution. This gives full picture. Opsi B (print statements) unstructured and hard to correlate. Opsi C (console only) limited detail. Opsi D (VPC Flow Logs) for network traffic, not application logic.
