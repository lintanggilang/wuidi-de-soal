Skill 2.3.3: Expire Data When It Reaches a Specific Age

S3 Lifecycle expiration policies for automatic data deletion based on object age

12345 678910
1
A European financial company must comply with GDPR Article 17 (Right to Erasure). Customer interaction logs stored in S3 must be automatically deleted exactly 2 years after creation. The bucket is NOT versioned. The company needs a verifiable, automated mechanism that guarantees deletion at the required age without manual intervention. Which S3 feature provides this compliance guarantee?
  • A. Create an S3 Lifecycle expiration rule with the action "Expire current versions of objects" set to 730 days. This rule automatically deletes objects 730 days after their creation date. S3 evaluates lifecycle rules daily and marks qualifying objects for deletion. For audit purposes, enable S3 Server Access Logging or CloudTrail Data Events to record deletion actions, providing a verifiable audit trail proving objects were deleted on schedule
  • B. Create a Lambda function triggered daily by EventBridge that lists all objects older than 730 days and deletes them using the S3 DeleteObject API
  • C. Use S3 Object Lock in Governance mode with a retention period of 730 days — after retention expires, objects are automatically deleted
  • D. Configure DynamoDB TTL on a metadata table that references S3 objects. When DynamoDB deletes the metadata record after 730 days, a DynamoDB Stream triggers a Lambda to delete the S3 object
Jawaban Benar: A
S3 Lifecycle expiration is the purpose-built, managed service for age-based object deletion: (1) it's a declarative policy — set once, enforced automatically by S3 infrastructure; (2) objects are deleted based on their creation timestamp (accurate to the day they were uploaded); (3) S3 evaluates lifecycle rules continuously and queues qualifying objects for deletion (typically within 24 hours of qualifying); (4) no custom code to maintain, no Lambda failures to handle, no scheduling to manage; (5) combined with CloudTrail Data Events (logging S3:DeleteObject API calls), provides auditable proof of deletion for GDPR compliance; (6) the rule persists even if team members leave — infrastructure-level guarantee. Option B — Lambda-based deletion introduces failure modes: Lambda timeout (15 min limit), pagination for millions of objects, rate limiting on S3 LIST/DELETE operations, Lambda service errors. If the Lambda fails, objects aren't deleted on time — a compliance violation. It's a custom implementation of what lifecycle rules provide natively. Option C — S3 Object Lock prevents DELETION, not triggers it. Governance/Compliance mode PROTECTS objects from being deleted during the retention period. After retention expires, objects simply become deletable — they are NOT automatically deleted. Object Lock is for PREVENTING premature deletion, not enforcing timely deletion. Option D — this Rube Goldberg architecture has multiple failure points (DynamoDB TTL delay can be up to 48 hours, Lambda failures, stream processing errors) and requires maintaining a separate metadata table synchronized with S3 objects. Lifecycle rules are simpler and more reliable.
2
A versioned S3 bucket stores daily data pipeline outputs. A lifecycle expiration rule is configured to "Expire current versions of objects after 90 days." After the rule has been active for 6 months, the team notices storage isn't decreasing as expected — the bucket size continues to grow. Investigation shows objects ARE being "expired" but the data remains. What explains this behavior in a versioned bucket?
  • A. In a versioned bucket, "expiring" a current version does NOT physically delete the data. Instead, S3 creates a delete marker as the new current version, and the previous current version becomes a noncurrent version (which is retained). The data is still stored as noncurrent versions, consuming storage. To actually remove data, the team must ALSO add a rule to "Permanently delete noncurrent versions" after N days (e.g., NoncurrentVersionExpiration after 1 day)
  • B. The lifecycle rule has a race condition — new objects are being created faster than the daily lifecycle evaluation can expire them
  • C. S3 lifecycle expiration in versioned buckets requires MFA Delete to be enabled before physical deletion occurs
  • D. The 90-day rule counts from the date the version became noncurrent, not from creation date, so objects haven't reached their expiration age yet
Jawaban Benar: A
Versioned buckets fundamentally change how lifecycle expiration works: (1) in an unversioned bucket, expiration = physical deletion; (2) in a VERSIONED bucket, "expiring" the current version creates a delete marker (a zero-byte placeholder indicating the object is "deleted"); (3) the previous current version becomes noncurrent — it's NOT deleted, just hidden from normal GET requests; (4) noncurrent versions continue consuming storage at the full per-GB rate; (5) to achieve actual storage reduction, you need TWO lifecycle rules: one to expire current versions (creates delete markers) and one to permanently delete noncurrent versions (NoncurrentVersionExpiration: Days: 1 or similar); (6) additionally, consider a rule to "Delete expired delete markers" to clean up the zero-byte markers. Without the NoncurrentVersionExpiration rule, ALL data is retained indefinitely as noncurrent versions — the bucket grows forever. Option B — lifecycle evaluation is not a race condition issue. S3 processes lifecycle rules asynchronously and handles high-volume buckets at scale. New objects wouldn't prevent old objects from being processed. Option C — MFA Delete adds a requirement for DELETE operations from the API (human-initiated) but doesn't affect lifecycle-managed deletions. Lifecycle rules bypass MFA Delete requirements. Option D — the "Expire current versions" rule uses the object's CREATION date (when it became the current version). NoncurrentVersionExpiration uses the date it became noncurrent. The question specifies an "Expire current versions" rule, which correctly triggers at 90 days from creation.
3
A data pipeline creates multipart uploads to S3 for large files (10+ GB). Occasionally, uploads fail midway (network errors, job crashes), leaving incomplete multipart uploads that consume storage but are invisible in normal S3 listing. Over time, these orphaned uploads accumulate significant storage costs. How can lifecycle policies address this hidden storage cost?
  • A. Create a lifecycle rule with the action "Abort incomplete multipart uploads" after a specified number of days (e.g., 7 days). This rule automatically aborts multipart uploads that haven't been completed within the specified timeframe, releasing the storage consumed by uploaded parts. Incomplete multipart upload parts are not visible in standard S3 object listings but DO consume storage and incur charges. This rule is a best practice for ANY bucket that uses multipart uploads
  • B. Enable S3 server access logging to detect incomplete uploads, then use a Lambda function to abort them
  • C. Configure the multipart upload timeout in the S3 bucket settings to automatically abort uploads after a deadline
  • D. Use S3 Inventory reports to identify incomplete multipart uploads, then run S3 Batch Operations to abort them periodically
Jawaban Benar: A
Lifecycle rules with "AbortIncompleteMultipartUpload" are the standard solution for orphaned upload cleanup: (1) S3 lifecycle natively supports this action — specify DaysAfterInitiation (e.g., 7); (2) after 7 days without completion, the multipart upload is aborted and all uploaded parts are deleted; (3) this reclaims storage that's otherwise invisible and growing indefinitely; (4) it's a set-and-forget rule that requires no custom code or monitoring; (5) AWS recommends this as a STANDARD lifecycle rule on every bucket regardless of use case — orphaned multipart uploads are a universal risk for any application using the multipart upload API (including SDK-level automatic multipart for large files). The cost savings can be significant for high-volume buckets. Option B — server access logging records API calls but doesn't directly track "incomplete" status. You'd need to correlate CreateMultipartUpload with CompleteMultipartUpload/AbortMultipartUpload — complex log analysis compared to a one-line lifecycle rule. Option C — there is no "multipart upload timeout" in S3 bucket settings. S3 doesn't have a built-in per-upload timeout configuration. Multipart uploads remain indefinitely until explicitly completed, aborted, or cleaned by a lifecycle rule. Option D — S3 Inventory doesn't include incomplete multipart uploads in its reports (Inventory lists completed objects only). You'd need to use the ListMultipartUploads API, adding custom code complexity. Lifecycle rules handle this without any custom infrastructure.
4
A healthcare organization has different data retention requirements based on data type: patient records must be retained for 7 years, appointment logs for 3 years, and temporary processing files for 30 days. All data resides in a single S3 bucket organized by prefix (patients/, appointments/, temp/). How should lifecycle expiration rules be configured to enforce these different retention periods?
  • A. Create three lifecycle rules, each with a prefix filter and different expiration periods: Rule 1: Prefix "patients/" → Expire after 2,555 days (7 years). Rule 2: Prefix "appointments/" → Expire after 1,095 days (3 years). Rule 3: Prefix "temp/" → Expire after 30 days. Each rule's filter scopes its action to objects matching the prefix, allowing different retention policies coexisting on the same bucket. Objects not matching any prefix filter are unaffected
  • B. Create three separate S3 buckets (one per data type) and apply a single lifecycle expiration rule per bucket with the appropriate retention period
  • C. Use a single lifecycle rule with the shortest expiration (30 days) and rely on S3 Object Lock to prevent deletion of patient records and appointment logs before their respective retention periods
  • D. Tag objects with "retention-years=7", "retention-years=3", or "retention-days=30" at upload time, then create lifecycle rules filtered by these tags for each expiration period
Jawaban Benar: A
Prefix-filtered lifecycle rules provide the cleanest implementation for prefix-organized data: (1) prefix filters directly match the bucket's organizational structure (patients/, appointments/, temp/); (2) each rule independently specifies its expiration timeline without affecting other prefixes; (3) no tagging overhead — objects are automatically covered by the rule matching their prefix at creation time; (4) rules are simple to audit ("show me the retention policy for patient data" → look at the patients/ prefix rule); (5) up to 1,000 lifecycle rules per bucket allows complex retention policies. This is the standard pattern when data is organized by prefix aligned with retention categories. Option B — separate buckets work functionally but add operational complexity: separate bucket policies, separate access configurations, separate monitoring, and cross-bucket queries become more complex. When data is already prefix-organized, multiple rules on one bucket is simpler. Option C — Object Lock prevents deletion (protects data), while lifecycle expiration enforces deletion (removes data). Using Object Lock to prevent a lifecycle rule from deleting objects is technically clever but architecturally confusing. The lifecycle rule would try to delete patient records after 30 days, and Object Lock would prevent it — resulting in failed deletion attempts logged as errors. This is not a clean design. Option D — tag-based rules work well and are valid, but they require tagging every object at upload time (additional PUT cost, requires application-level coordination). When data is already prefix-organized, prefix filters achieve the same result without per-object tagging overhead.
5
A company's S3 bucket has a lifecycle expiration rule deleting objects after 365 days. A legal hold is placed on certain objects related to an ongoing lawsuit — these objects must NOT be deleted regardless of age. The objects subject to legal hold are scattered across various prefixes and don't follow a predictable naming pattern. How can the company prevent lifecycle expiration from deleting legally-held objects?
  • A. Enable S3 Object Lock on the bucket (requires versioning). Place a Legal Hold on each object subject to the lawsuit using PutObjectLegalHold API. Objects with active Legal Hold are protected from deletion by ANY mechanism — including lifecycle expiration rules. The lifecycle rule continues to expire non-held objects normally, while held objects remain regardless of age. When the lawsuit concludes, remove the Legal Hold and the lifecycle rule will expire the objects normally
  • B. Add a tag "legal-hold=true" to affected objects, then modify the lifecycle rule to exclude objects with this tag using a tag filter
  • C. Move legally-held objects to a separate bucket without lifecycle rules, then move them back after the hold is lifted
  • D. Disable the lifecycle rule entirely while the legal hold is active, then re-enable it once the lawsuit concludes
Jawaban Benar: A
S3 Object Lock with Legal Hold provides irrevocable protection against deletion: (1) Legal Hold is a binary flag on individual objects — when enabled, the object CANNOT be deleted or overwritten by any user, any role, or any automated process (including lifecycle); (2) it requires no specific retention period — the hold persists until explicitly removed by a user with s3:PutObjectLegalHold permission; (3) lifecycle rules attempting to expire a legally-held object silently skip it (the object remains, no error is logged); (4) this is the purpose-built AWS feature for litigation hold scenarios; (5) when the legal matter resolves, removing the hold allows normal lifecycle processing to resume. Option B — tag-based exclusion works technically but has compliance risks: (1) lifecycle rules with tag filters require modifying the existing rule (adding a NOT condition or restructuring); (2) tags can be accidentally removed by anyone with s3:PutObjectTagging permission, inadvertently exposing objects to deletion; (3) there's no immutability guarantee — a misconfigured IAM policy could allow tag removal. For legal compliance, Object Lock provides stronger guarantees. Option C — moving objects between buckets risks data integrity issues, loses object metadata/creation timestamps (affecting other lifecycle rules if they return), and adds operational complexity. Object Lock is designed to avoid data movement. Option D — disabling the lifecycle rule stops ALL expiration for ALL objects in the bucket. Objects that SHOULD be deleted (non-legal-hold objects past 365 days) continue accumulating, increasing storage costs and potentially violating other data retention policies (like GDPR right to erasure).
6
A data engineering team implements a lifecycle rule to expire objects after 90 days. They notice that some objects are being deleted at 91 or 92 days instead of exactly 90 days. Business stakeholders are concerned about this 1-2 day delay. Is this behavior expected, and what are its implications for compliance requirements that specify "delete after exactly 90 days"?
  • A. This is expected behavior. S3 lifecycle rules are evaluated asynchronously and are not guaranteed to execute at exactly the specified day. AWS documentation states that lifecycle actions are "best effort" with typical completion within 1-2 days of qualifying. For compliance purposes: (1) objects are guaranteed to be deleted, but with up to 1-2 day latency; (2) for strict "not before" compliance (retain for minimum 90 days), this is acceptable; (3) for strict "not after" compliance (delete within exactly 90 days), build a buffer — set expiration to 88 days to account for processing delay; (4) document this technical limitation in compliance documentation
  • B. This indicates a misconfiguration — lifecycle rules should execute at exactly midnight UTC on the 90th day. The delay suggests the rule creation timestamp is offset from UTC
  • C. The 1-2 day delay is caused by S3 needing to calculate the exact creation timestamp for each object, which requires scanning object metadata
  • D. Versioned objects have additional processing time for creating delete markers, causing the observed delay. Unversioned buckets expire objects exactly on the specified day
Jawaban Benar: A
S3 lifecycle rule execution timing is inherently asynchronous with documented latency: (1) AWS processes lifecycle rules in batches across billions of objects globally; (2) the official documentation states lifecycle transitions and expirations may take "up to a few days" to complete after objects qualify; (3) for most objects, expiration occurs within 24-48 hours of the specified age; (4) this is NOT a bug or misconfiguration — it's an inherent characteristic of a distributed, asynchronous system processing at S3's scale. For compliance implications: "minimum retention" requirements (retain at least 90 days) are satisfied because deletion happens AFTER 90 days. "Maximum retention" requirements (delete within 90 days) require setting the expiration earlier (e.g., 88 days) to ensure deletion completes by day 90. Document this architectural characteristic for auditors. Option B — lifecycle rules don't execute at a specific clock time. They're evaluated continuously by background processes, not triggered at midnight UTC. There's no configuration to control execution timing. Option C — S3 stores creation timestamps as metadata with each object; no "scanning" is needed. The timestamp is immediately available for lifecycle evaluation. The delay is from batch processing queues, not metadata lookup. Option D — the delay applies to both versioned and unversioned buckets equally. It's a characteristic of lifecycle rule processing, not version management. Unversioned buckets also experience 1-2 day processing latency.
7
A versioned bucket accumulates delete markers over time as objects are deleted and recreated. The bucket now has 10 million expired delete markers (delete markers where the underlying object has no noncurrent versions remaining — they serve no purpose). These markers consume minimal storage but cause S3 LIST operations to be slow (LIST must enumerate delete markers). Which lifecycle action cleans up these useless delete markers?
  • A. Enable the "Delete expired object delete markers" lifecycle action (ExpiredObjectDeleteMarker: true). This rule identifies delete markers that are the ONLY remaining version of an object (no noncurrent versions exist underneath) and removes them. These "expired" delete markers serve no purpose — they mark an object as deleted, but since no versions exist to hide, the marker itself is meaningless. Removing them improves LIST performance and cleans up the bucket's version history
  • B. Create a lifecycle rule that expires all objects with zero bytes (since delete markers are zero-byte objects)
  • C. Run S3 Batch Operations with the "Delete" action filtering for objects of type "DeleteMarker"
  • D. Suspend bucket versioning — this automatically removes all delete markers and converts the bucket to unversioned mode
Jawaban Benar: A
"Delete expired object delete markers" is a specific lifecycle action for this exact cleanup scenario: (1) an "expired" delete marker is one where it's the sole remaining version of an object ID — no noncurrent versions exist below it; (2) these markers served their purpose (marking deletion) but all actual data versions have been removed (by NoncurrentVersionExpiration or manual deletion); (3) the marker now pointlessly occupies the version list, slowing LIST operations; (4) this lifecycle action specifically targets and removes ONLY these orphaned markers; (5) it's safe — it never removes delete markers that are still "covering" noncurrent versions (those are still meaningful). This is commonly paired with NoncurrentVersionExpiration: after noncurrent versions are deleted, the remaining delete markers are cleaned up by this rule. Option B — lifecycle expiration rules don't filter by object size. You cannot target zero-byte objects specifically. Also, delete markers are version metadata entries, not regular objects — they can't be targeted by standard expiration rules based on size. Option C — S3 Batch Operations works on objects listed in S3 Inventory or manifests. S3 Inventory can include delete markers, but building and executing a batch operation for 10 million markers is operationally complex compared to a declarative lifecycle rule. Option D — suspending versioning does NOT remove delete markers or any version history. It only prevents NEW versions from being created. All existing versions and delete markers remain. You cannot "convert" a versioned bucket to unversioned — version history is permanent once created.
8
A company combines lifecycle transition and expiration in a single rule: transition to Glacier Flexible Retrieval after 90 days, then expire (delete) after 365 days. An auditor asks: "When an object is expired at day 365, is it immediately unrecoverable, or can it be restored from Glacier within a grace period?" What is the correct answer for an unversioned bucket?
  • A. When lifecycle expiration deletes an object from Glacier Flexible Retrieval in an unversioned bucket, the deletion is IMMEDIATE and PERMANENT. There is no grace period, no recycle bin, and no recovery mechanism. The object is gone. Unlike versioned buckets (where deletion creates a recoverable delete marker), unversioned bucket deletion is irreversible. For audit compliance: if data must be recoverable after expiration, use versioning with NoncurrentVersionExpiration providing a grace period, or replicate to another bucket before expiration
  • B. Objects in Glacier have a 90-day minimum storage duration. If expired before 90 days in Glacier, there's a pro-rated charge but the object is still deleted. After 90 days in Glacier, deletion is immediate and free
  • C. Glacier provides a 30-day recovery window after deletion — the object can be restored using the vault recovery feature during this period
  • D. Lifecycle expiration of Glacier objects requires a restore operation first — the object is restored to Standard, then deleted. This adds a 3-5 hour delay between expiration trigger and actual deletion
Jawaban Benar: A
Lifecycle expiration in unversioned buckets is permanent and immediate (from the user's perspective): (1) S3 lifecycle deletes the object regardless of its storage class — Standard, IA, or Glacier; (2) for Glacier objects, the deletion removes the object from the storage system permanently — no restore is possible after deletion; (3) there is NO grace period, undo, or recovery mechanism for unversioned bucket deletions; (4) this applies to lifecycle expiration AND manual deletion — both are permanent; (5) for compliance requiring recoverability, versioning + NoncurrentVersionExpiration provides a configurable grace period (e.g., retain noncurrent versions for 30 days after deletion, giving 30 days to "recover" by restoring a previous version). Option B — the statement about minimum storage duration charges is true (Glacier charges for 90 days minimum), but it's about BILLING, not recoverability. The object is still deleted even if early deletion charges apply. The question asks about recoverability, not cost. Option C — S3 Glacier (as a storage class within S3) does NOT have a "vault recovery" feature with a deletion grace period. This might confuse S3 Glacier storage class with the legacy Glacier Vault service (which has vault lock policies) — but neither provides post-deletion recovery. Option D — lifecycle expiration does NOT require restoration first. S3 can delete Glacier objects directly without restoring them. The deletion API operates on the object's metadata and storage allocation without needing the data to be in a readable state.

A data pipeline writes files to S3 with different retention requirements based on data sensitivity. Files tagged with "sensitivity=high" must be retained for 7 years, "sensitivity=medium" for 3 years, and "sensitivity=low" for 1 year. A new regulation requires that all objects tagged "sensitivity=high" AND "department=research" must be retained for 10 years instead of 7. How should the lifecycle rules be structured?
  • A. Create four lifecycle rules using tag-based filters: Rule 1: Tag filter (sensitivity=high AND department=research) → Expire after 3,650 days (10 years). Rule 2: Tag filter (sensitivity=high) → Expire after 2,555 days (7 years). Rule 3: Tag filter (sensitivity=medium) → Expire after 1,095 days (3 years). Rule 4: Tag filter (sensitivity=low) → Expire after 365 days (1 year). S3 applies the MOST SPECIFIC matching rule — objects matching both "sensitivity=high" AND "department=research" match Rule 1 (more specific AND filter) rather than Rule 2 (single tag filter)
  • B. Only three rules are needed — modify the "sensitivity=high" rule to 10 years, which covers all high-sensitivity data including research
  • C. S3 lifecycle rules cannot combine multiple tag conditions in a single filter — create separate rules per tag and use rule priority ordering
  • D. When multiple lifecycle rules match the same object, S3 applies the rule with the LONGEST expiration period, so Rule 1 (10 years) automatically takes precedence over Rule 2 (7 years) for research objects
Jawaban Benar: A
S3 lifecycle rule filters support AND combinations of prefix and multiple tags, allowing granular policies: (1) a filter can include prefix AND/OR multiple tag conditions combined with AND logic; (2) an object matching multiple rules has all applicable rules evaluated — S3 uses the rule that results in the "most aggressive" action applying first, but for overlapping expiration rules, the behavior depends on specificity; (3) for objects with BOTH "sensitivity=high" AND "department=research," the AND filter in Rule 1 matches more specifically than the single-tag filter in Rule 2; (4) in practice, when two expiration rules both match, S3 applies the shorter expiration (favoring deletion). To ensure 10-year retention for research objects, structure rules so that the 7-year rule EXCLUDES research department objects (using filter that says sensitivity=high but NOT for research). However, S3 doesn't support NOT conditions, so the cleanest approach is to ensure Rule 1's objects aren't also matched by Rule 2 by removing the conflict. Option B — modifying all high-sensitivity to 10 years over-retains non-research high-sensitivity data by 3 years, increasing storage costs unnecessarily and potentially violating "right to erasure" requirements for non-research data. Option C — S3 lifecycle rules DO support multiple tags in an AND filter. The filter syntax supports: sensitivityhighdepartmentresearch. Option D — when multiple expiration rules match, S3's behavior is to apply the SHORTEST expiration (most aggressive action), not the longest. This would delete research objects at 7 years, not 10 — which is why careful rule structuring is critical.

A data lake stores raw ingestion data and processed output data in the same bucket under different prefixes (raw/ and processed/). The team wants to: (1) expire raw data after 30 days (it's reprocessable from source), (2) transition processed data to Glacier after 90 days, and (3) expire processed data after 365 days. However, they also want to ensure that if an object in "processed/" is currently being restored from Glacier (someone initiated a restore for ad-hoc analysis), it should NOT be expired during the restore. Does S3 lifecycle expiration respect ongoing restore operations?
  • A. S3 lifecycle expiration does NOT consider restore status. If an object qualifies for expiration (age ≥ 365 days), it will be deleted regardless of whether a restore is in progress or a restored copy exists. The lifecycle rule treats all objects uniformly based on age — there is no "skip if being restored" condition. To prevent this scenario: use Object Lock Legal Hold on objects being restored for analysis, OR adjust the expiration period to provide a buffer beyond typical restore+analysis duration, OR implement a tagging workflow (tag objects during analysis, exclude tagged objects from the lifecycle rule)
  • B. S3 automatically pauses lifecycle expiration for objects with active restore operations, resuming the countdown once the restore copy expires
  • C. Restored copies are separate temporary objects that aren't subject to lifecycle rules — the original Glacier object is still expired on schedule but the restored copy remains accessible
  • D. Lifecycle rules are evaluated before restore requests are processed, so a restore initiated on the same day as expiration will always fail
Jawaban Benar: A
Lifecycle expiration is age-based and doesn't consider object state (restore status, ongoing access, etc.): (1) lifecycle rules evaluate ONE criterion: object age (days since creation); (2) there's no awareness of restore operations, active downloads, or usage patterns; (3) if an object is 365 days old and the rule says expire at 365 days, it's queued for deletion regardless of anything else happening with that object; (4) a restored copy of a Glacier object is NOT a separate object — it's a temporary accessibility layer on the same object. When the object is deleted by lifecycle, the restore copy goes with it; (5) for protection during analysis, use Object Lock Legal Hold (prevents deletion) or a tag-based exclusion (tag objects being analyzed, lifecycle rule excludes that tag). Option B — S3 has no mechanism to "pause" lifecycle rules based on restore status. Lifecycle processing is stateless — it checks age, determines action, and executes. There's no "pause" concept. Option C — restored Glacier objects are NOT separate objects. The restore creates a temporary copy in the S3 Standard access tier associated with the SAME object version. If the object is deleted (by lifecycle or manually), the restore copy is also gone — it's the same underlying object. Option D — lifecycle evaluation and restore requests are independent asynchronous operations. They don't have a defined ordering relationship. Both can happen to the same object concurrently, but lifecycle will delete the object when it processes the expiration action.
