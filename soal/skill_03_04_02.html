#DQDL
A data engineer needs to define a DQDL ruleset for a customer table that validates: email addresses must be present in at least 98% of records, customer_status must only contain values "active", "inactive", or "suspended", and the created_date must not be in the future. Which DQDL ruleset is CORRECT?
  • A. Rules = [ Completeness "email" >= 0.98, ColumnValues "customer_status" in ["active", "inactive", "suspended"], ColumnValues "created_date" <= now() ]
  • B. Rules = [ NullCheck "email" < 0.02, Enum "customer_status" in ("active", "inactive", "suspended"), RangeCheck "created_date" <= today() ]
  • C. Rules = [ IsComplete "email" >= 98%, ColumnValues "customer_status" = ["active", "inactive", "suspended"], DateColumnValues "created_date" < current_date ]
  • D. Rules = [ Completeness "email" = 1.0, UniqueValues "customer_status" = 3, Freshness "created_date" <= 0 days ] configured for optimal performance and minimal operational overhead
Jawaban Benar: A
This DQDL ruleset uses the correct syntax: Completeness checks the percentage of non-null values (0.98 = 98%), ColumnValues with "in" validates against an allowed set of values, and ColumnValues with a comparison operator validates that dates don't exceed the current timestamp using now(). Option B: "IsComplete" is not a valid DQDL rule type (it's "Completeness"), percentage notation isn't used (decimals are), and "DateColumnValues" isn't a separate rule type. Option C: "NullCheck", "Enum", and "RangeCheck" are not valid DQDL rule type names. Option D: Completeness = 1.0 means 100% (not 98%), UniqueValues counts distinct values which doesn't enforce specific allowed values, and Freshness checks data age relative to now, not whether dates are in the future.

A data engineer needs to define a conditional DQDL rule where the "discount_percentage" field must be between 0 and 30 ONLY when the "customer_tier" is "standard", but can be between 0 and 50 when "customer_tier" is "premium". How can this conditional logic be expressed in DQDL?
  • A. Use the Composite rule type: CompositeRule "discount_validation" = (customer_tier = "standard" AND discount_percentage <= 30) OR (customer_tier = "premium" AND discount_percentage <= 50), handling the described workload reliably at scale
  • B. DQDL does not support conditional rules; implement this logic as custom Python validation in the Glue ETL script instead, handling the described workload reliably at scale
  • C. Use two separate rules with the "where" clause: ColumnValues "discount_percentage" between 0 and 30 where "customer_tier = 'standard'", ColumnValues "discount_percentage" between 0 and 50 where "customer_tier = 'premium'"
  • D. Create a single rule using IF-THEN-ELSE syntax: IF "customer_tier" = "standard" THEN ColumnValues "discount_percentage" <= 30 ELSE ColumnValues "discount_percentage" <= 50 with the "where" clause: ColumnValues "discount_percentage" between 0
Jawaban Benar: C
DQDL supports the "where" clause (also called row-level filtering) that applies a rule only to rows matching a condition. By creating two rules with different "where" conditions, you effectively implement conditional validation logic. Each rule evaluates only against the subset of rows matching its condition. Option B: IF-THEN-ELSE is not valid DQDL syntax; DQDL uses declarative rule definitions, not procedural logic. Option C: DQDL does support conditional evaluation through the "where" clause, making custom code unnecessary for this case. Option D: "CompositeRule" is not a valid DQDL rule type; DQDL rules are individual declarations that can be combined in a ruleset.

#DQDL
A data engineer needs to define a freshness rule for a dataset that should be updated at least every 4 hours. The dataset has a "last_modified_timestamp" column. Additionally, the dataset should have between 10,000 and 1,000,000 records per daily partition. Which DQDL rules correctly express these requirements?
  • A. Rules = [ DataFreshness "last_modified_timestamp" <= 4 hours, RowCount between 10000 and 1000000 ]
  • B. Rules = [ Freshness "last_modified_timestamp" <= 240 minutes, ColumnValues "row_count" between 10000 and 1000000 ]
  • C. Rules = [ ColumnValues "last_modified_timestamp" >= now() - interval 4 hours, RowCount >= 10000 AND RowCount <= 1000000 ]
  • D. Rules = [ DataFreshness "last_modified_timestamp" <= 4, DatasetRowCount between 10000 and 1000000 ]
Jawaban Benar: A
The correct DQDL syntax uses "DataFreshness" for checking that a timestamp column's most recent value is within a specified time window (using human-readable time units like "hours"), and "RowCount" with "between" for validating record count ranges. DQDL supports natural time units (hours, minutes, days) for freshness rules. Option B: "Freshness" is not the correct rule type name (it's "DataFreshness"), and using minutes instead of the supported "hours" unit may not parse correctly. Option C: This uses ColumnValues with a computed expression which isn't valid DQDL syntax; DataFreshness is the purpose-built rule for this. Option D: "DataFreshness" without a time unit (just "4") is ambiguous and invalid; "DatasetRowCount" is not the correct rule name (it's "RowCount").

The team wants to ensure that no unexpected new categories appear in future data loads. Which DataBrew/Glue Data Quality approach is MOST maintainable?
  • A. Create a DataBrew recipe step that filters out rows with unexpected categories, effectively enforcing the rule during transformation, satisfying all of the stated requirements with minimal effort and providing exactly-once processing semantics
  • B. Use Glue Data Quality's "ColumnValues in" rule with the 47 known categories listed explicitly, and schedule periodic reviews to update the allowed list when legitimate new categories are introduced.
  • C. Use the DistinctValuesCount rule to ensure exactly 47 distinct values exist, alerting if the count changes. configured for optimal performance and minimal operational overhead, integrating natively with the rest of the pipeline
  • D. Define a CustomSql rule in DQDL that joins against a reference table of valid categories maintained in a Glue Data Catalog table, validating that all product_category values exist in the reference.
Jawaban Benar: D
Using a CustomSql rule that validates against a reference table is the most maintainable approach for large value sets. The reference table can be updated independently (adding new legitimate categories) without modifying the DQDL ruleset itself. Option A: Listing 47 values explicitly in the DQDL rule works but requires ruleset modifications whenever a legitimate new category is added, creating a maintenance burden. Option B: DataBrew recipe filtering removes data silently without alerting—this is a transformation, not a quality rule. Option C: Counting distinct values (exactly 47) is too rigid; it would fail if a legitimate new category is added AND if an existing category disappears in a batch, conflating two different issues.

#DQDL
A data quality team needs to implement rules that check relationships between columns. Specifically, when "payment_method" is "credit_card", the "card_last_four" field must not be null and must be exactly 4 digits. When "payment_method" is "bank_transfer", the "bank_account_id" must not be null. How should these cross-column dependency rules be defined in DQDL?
  • A. Rules = [ IF payment_method = "credit_card" THEN IsNotNull("card_last_four") AND Matches("card_last_four", "[0-9]{4}"), IF payment_method = "bank_transfer" THEN IsNotNull("bank_account_id") ] configured for optimal performance and minimal operational overhead
  • B. Rules = [ Completeness "card_last_four" >= 0.5, ColumnValues "card_last_four" matches "[0-9]{4}", Completeness "bank_account_id" >= 0.5 ], handling the described workload reliably at scale and avoiding charges for idle provisioned capacity
  • C. Rules = [ Completeness "card_last_four" = 1.0 where "payment_method = 'credit_card'", ColumnValues "card_last_four" matches "[0-9]{4}" where "payment_method = 'credit_card'", Completeness "bank_account_id" = 1.0 where "payment_method = 'bank_transfer'" ]
  • D. Rules = [ CrossColumnCheck "payment_method" -> "card_last_four" when "credit_card" requires not_null and pattern "[0-9]{4}", CrossColumnCheck "payment_method" -> "bank_account_id" when "bank_transfer" requires not_null ], handling the described workload reliably at scale
Jawaban Benar: C
The "where" clause in DQDL enables cross-column dependency validation by scoping a rule's evaluation to a subset of rows. This correctly validates that card_last_four is complete AND matches the 4-digit pattern only for credit card payments, and bank_account_id is complete only for bank transfers. Option B: IF-THEN conditional syntax is not valid in DQDL; the language uses declarative rules with "where" clauses for conditional evaluation. Option C: "CrossColumnCheck" is not a valid DQDL rule type. Option D: Using overall completeness of 0.5 (50%) is a crude approximation that doesn't properly validate the conditional relationships and would pass even if the wrong records have nulls.

How should the engineer make the ruleset more resilient?
  • A. Split the 15 rules into multiple smaller rulesets (one per rule) so that a single evaluation failure doesn't prevent other rules from running, and run all rulesets independently, providing exactly-once processing semantics
  • B. Wrap each rule in a try-catch block within the DQDL ruleset to handle evaluation errors per-rule. configured for optimal performance and minimal operational overhead, satisfying all of the stated requirements with minimal effort
  • C. Add a schema validation rule (ColumnDataType) as the first rule in the ruleset to verify column types before other rules execute, and use the "Analyzers" section to handle type-related evaluation errors gracefully.
  • D. Configure the EvaluateDataQuality transform with the "failOnError = false" option so that rules that encounter evaluation errors are marked as failed rather than crashing the entire evaluation, providing exactly-once processing semantics
Jawaban Benar: C
Adding ColumnDataType validation as a prerequisite ensures type assumptions are verified before dependent rules execute. The Analyzers section in DQDL provides metadata about the data being evaluated, helping identify type mismatches early. This defensive approach prevents cascade failures from unexpected data types. Option B: DQDL does not support try-catch syntax; it's a declarative rule language, not a procedural programming language. Option C: Running 15 separate rulesets is operationally expensive (15 separate evaluations) and loses the ability to have a single quality score for the dataset. Option D: While controlling error behavior is useful, simply marking errors as failures without addressing the root cause (type mismatch) doesn't improve the quality of the evaluation results.
