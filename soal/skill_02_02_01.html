Skill 2.2.1: Use Data Catalogs to Consume Data from the Data's Source

Using data catalogs for data discovery, access, and consumption across the organization

1
A large enterprise has data spread across 15 AWS accounts — each business unit manages its own S3 data lake, RDS databases, and Redshift clusters. Data analysts need to discover available datasets across all business units without directly accessing each account's resources. The company wants a centralized discovery mechanism that shows what data exists, its schema, and how to access it. Which architecture provides the MOST effective cross-account data discovery using AWS Glue Data Catalog?
  • A. Designate a central governance account with AWS Lake Formation. Use Lake Formation's cross-account catalog sharing to grant the central account read access to each business unit's Glue Data Catalog. Analysts browse the central catalog to discover datasets across all 15 accounts, view schemas and table properties, and request access through Lake Formation permissions — all without needing IAM access to individual accounts' resources
  • B. Create AWS Glue crawlers in each account that export catalog metadata to a shared S3 bucket, then build a custom search application on top of the exported metadata files
  • C. Use AWS Resource Access Manager (RAM) to share individual S3 buckets and databases from all 15 accounts directly with every analyst
  • D. Deploy Amazon DataZone in each account separately and let analysts log into each account's DataZone portal individually to discover that account's data
Jawaban Benar: A
Lake Formation's cross-account catalog sharing provides centralized data discovery without data movement: (1) each business unit's Glue Data Catalog is shared with the central governance account via Lake Formation grants (database/table-level sharing); (2) analysts in the central account see a unified view of all shared databases and tables across all 15 accounts; (3) schema information, partition details, and table properties are visible without executing queries; (4) Lake Formation permissions control who can discover (see metadata) vs. who can access (query data), providing layered security; (5) no data duplication — analysts still query data in its source location, but discovery is centralized. Opsi B — building a custom search application on exported metadata creates operational overhead (crawlers, exports, custom code), introduces staleness (metadata becomes outdated between exports), and doesn't integrate with Lake Formation's permission model. Opsi C — RAM sharing of S3 buckets gives direct access to underlying data without metadata context (schema, descriptions, classifications); analysts see raw files, not discoverable datasets. Opsi D — requiring analysts to log into 15 separate DataZone portals defeats the purpose of centralized discovery; they'd need to know which account has which data to begin searching.

A data analytics team uses Amazon Athena to query data stored in S3. They receive a request to analyze customer purchase patterns, but they don't know which database or table contains purchase data. The company's Glue Data Catalog has 500+ tables across 20+ databases. How should the analyst MOST efficiently discover the relevant tables using the data catalog?
  • A. Use the AWS Glue Data Catalog's search functionality to search for tables by name, column names, or classification. Search for keywords like "purchase," "order," or "transaction" across table names, descriptions, and column names. The catalog returns matching tables with their schemas, locations, and any business metadata tags — allowing the analyst to identify the correct table without querying every database
  • B. Write an Athena query that scans INFORMATION_SCHEMA across all databases to find tables with columns containing "purchase" in their name
  • C. Contact each database owner individually to ask which table contains purchase data
  • D. Run SELECT * LIMIT 10 on every table in the catalog to inspect sample data and determine which contains purchase information
Jawaban Benar: A
The Glue Data Catalog functions as a searchable metadata repository: (1) the catalog search API and console allow text search across table names, column names, descriptions, and custom properties; (2) searching "purchase" surfaces tables with purchase-related columns even if the table name is non-obvious (e.g., a table named "fact_transactions" with a column "purchase_amount"); (3) business metadata tags (added by data stewards) like "domain:sales" or "contains:purchase-data" enhance discoverability; (4) the catalog shows full schema details, data location, partition structure, and last-updated timestamps without requiring query execution. This is the primary use case for a data catalog — enabling discovery without pre-existing knowledge of data organization. Opsi B — INFORMATION_SCHEMA in Athena is limited to the currently-selected database; cross-database schema search requires switching databases individually and doesn't search descriptions or tags. Opsi C — manual outreach to owners is inefficient at scale (20+ databases, potentially different owners) and defeats the purpose of a catalog. Opsi D — running queries against 500+ tables wastes compute cost, takes hours, and may access sensitive data the analyst shouldn't see; discovery should happen at the metadata level, not the data level.
3
A healthcare company stores patient data in an S3 data lake with tables registered in the Glue Data Catalog. Different teams need different access levels: clinical researchers can access de-identified data, billing can access financial fields only, and compliance can access all fields including PHI (Protected Health Information). They want to use the catalog as the access control point — teams discover and consume data through catalog permissions without needing S3 bucket policies. Which service enables this catalog-based column-level access control?
  • A. AWS Lake Formation with column-level permissions — define grants specifying which IAM principals can access which columns of which catalog tables. When Athena, Redshift Spectrum, or Glue ETL queries reference a table through the catalog, Lake Formation enforces column-level filtering automatically. Researchers see only de-identified columns, billing sees financial columns, and compliance sees all columns — all consuming the same physical data through different permission grants
  • B. Create separate physical copies of the data in S3 for each team with different column subsets, and register each copy as a separate table in the Glue Data Catalog
  • C. Use S3 Access Points with different access policies for each team, creating separate access paths to the same underlying data
  • D. Define IAM policies with S3 object-level ARN conditions that restrict which Parquet column data can be read
Jawaban Benar: A
Lake Formation provides fine-grained catalog-based access control: (1) column-level permissions let administrators grant SELECT on specific columns to specific principals — GRANT SELECT (patient_id, diagnosis_code) ON TABLE patient_records TO ROLE clinical_researchers; (2) when services query through the catalog, Lake Formation intercepts and filters columns the principal isn't authorized to see; (3) cell-level filtering (row-level) can further restrict access based on data values; (4) a single physical dataset serves all teams — no data duplication; (5) the catalog becomes the "data access API" where discovery and authorization are unified. This is the recommended architecture for regulated data in AWS. Opsi B — physical copies multiply storage costs (especially for PHI data), create data synchronization challenges, and increase the compliance surface area (more copies of sensitive data to track). Opsi C — S3 Access Points operate at the object (file) level, not the column level; you cannot restrict access to specific columns within a Parquet file using S3 policies. Opsi D — IAM policies cannot enforce column-level access within Parquet/ORC files; IAM operates on S3 objects (entire files), not on columnar data within files.
4
A data engineering team supports 50 data analysts who use Amazon Athena to query the data lake. Analysts frequently write incorrect table references (wrong database name, misspelled table names, outdated table versions) because they reference data from memory rather than checking the catalog. The team wants to make data consumption self-service by ensuring analysts always discover and reference current, valid catalog entries. Which approach MOST effectively promotes catalog-driven data consumption?
  • A. Implement Amazon DataZone as a data marketplace portal integrated with the Glue Data Catalog. Analysts browse published data products (curated catalog entries with descriptions, schemas, sample queries, and quality indicators), subscribe to datasets they need, and receive pre-configured Athena connections. DataZone surfaces catalog metadata in a business-friendly interface, ensuring analysts always work from current, approved data sources
  • B. Create a shared wiki page listing all available tables with their database names, schemas, and example queries that analysts can reference
  • C. Restrict Athena access to only allow queries against tables that the analyst has explicitly requested permission for via a ticketing system
  • D. Enable Athena query suggestions that auto-complete table names from the Glue Data Catalog while analysts type their queries
Jawaban Benar: A
Amazon DataZone transforms the technical catalog into a self-service data marketplace: (1) data producers publish curated "data products" with business descriptions, quality metrics, and usage documentation; (2) consumers browse and subscribe to data products through a user-friendly portal — no need to memorize database/table names; (3) subscriptions automatically provision the correct Athena access to the catalog tables; (4) schema changes, deprecations, and new datasets are visible immediately in the portal; (5) usage analytics show which datasets are most popular, helping analysts discover relevant data through community signals. This creates a "catalog-first" culture where discovery precedes consumption. Opsi B — wiki pages become outdated as tables are added/modified/deprecated; maintaining documentation separate from the actual catalog metadata creates drift and inaccuracies. Opsi C — a ticketing system adds friction without improving discovery; analysts still need to know what to request, and the process slows down self-service analytics. Opsi D — auto-complete helps with typing accuracy but doesn't solve discovery (analysts need to already know approximately what table to type); it also doesn't provide context about what each table contains.

A company uses Amazon Redshift Spectrum to query data in their S3 data lake. The data lake has 200 tables registered in the Glue Data Catalog. The Redshift team needs to configure Spectrum to read table definitions from the Glue Data Catalog so analysts can query S3 data using familiar Redshift SQL. How does Redshift Spectrum integrate with the Glue Data Catalog for data consumption?
  • A. Create an external schema in Redshift that references the Glue Data Catalog database. Redshift automatically reads table definitions, column schemas, partition information, and data locations from the catalog. Analysts query external tables using standard Redshift SQL — the catalog provides the metadata layer that maps SQL table references to physical S3 locations, eliminating the need to define external tables manually in Redshift
  • B. Export the Glue Data Catalog definitions to DDL scripts and execute them in Redshift to create matching external table definitions
  • C. Configure a JDBC connection from Redshift to the Glue Data Catalog service endpoint to read metadata at query time
  • D. Use AWS DMS to synchronize the Glue Data Catalog metadata into Redshift's internal pg_catalog system tables
Jawaban Benar: A
Redshift Spectrum's native Glue Data Catalog integration works through external schemas: (1) CREATE EXTERNAL SCHEMA spectrum_schema FROM DATA CATALOG DATABASE 'my_glue_db' IAM_ROLE 'arn:aws:iam::...' creates the link; (2) Redshift immediately sees all tables defined in that Glue database — no manual table creation needed; (3) as tables are added/modified in the Glue catalog (by crawlers, ETL jobs, or manual updates), Spectrum automatically picks up changes on next query; (4) partition information from the catalog is used for pruning (WHERE dt='2024-03-01' only scans that partition's S3 prefix); (5) analysts query with SELECT * FROM spectrum_schema.table_name using standard SQL. The catalog is the single source of truth for metadata. Opsi B — manually exporting and executing DDL creates a maintenance burden; any catalog change requires re-exporting and re-running DDL, creating metadata drift. Opsi C — there is no JDBC interface to the Glue Data Catalog; Spectrum uses AWS API calls (Glue GetTable/GetPartitions) internally, not JDBC connections. Opsi D — DMS replicates data between databases, not catalog metadata; pg_catalog is PostgreSQL's internal system catalog that tracks Redshift's own objects, not external data sources.

A data mesh organization has domain teams that own their data products. Each domain team publishes data to their own Glue Data Catalog database. Consumer teams need to discover and consume data products from multiple domains without knowing the internal structure of each domain's catalog. The organization wants catalog-based data consumption where consumers reference logical data product names, not physical database/table paths. Which pattern enables this abstraction?
  • A. Use Lake Formation tag-based access control (LF-TBAC) combined with resource links. Domain teams tag their data products with standardized business tags (domain, product-name, classification). Consumer teams receive access through tag-based grants. Resource links in the consumer's catalog point to producer tables, providing a local reference without copying metadata. Consumers discover products by tag and consume through their local resource links
  • B. Create a single Glue Data Catalog database where all domain teams register their tables with standardized naming conventions like domain_productname
  • C. Have each consumer team maintain a configuration file mapping logical data product names to physical Glue database.table paths
  • D. Use AWS Service Catalog to publish Glue Data Catalog table definitions as provisioned products that consumers deploy into their own accounts
Jawaban Benar: A
LF-TBAC with resource links implements the data mesh pattern on AWS: (1) Tag-Based Access Control allows producers to tag tables with business metadata (LF-Tags like "domain=sales", "product=customer-360", "sensitivity=pii") and grant access based on tag expressions rather than individual table ARNs; (2) resource links create local catalog entries in the consumer's database that point to the producer's shared table — consumers query their own schema (SELECT * FROM my_catalog.customer_360) while data remains in the producer's account; (3) new data products are automatically discoverable by consumers who have matching tag-based grants; (4) this separates logical (tag-based discovery) from physical (actual database/table locations). Opsi B — a single shared database violates data mesh ownership principles; all domains become dependent on a shared namespace, creating governance bottlenecks and naming conflicts. Opsi C — configuration files become stale, don't integrate with query engines natively, and require manual updates when producers reorganize their catalogs. Opsi D — AWS Service Catalog provisions infrastructure resources, not data catalog metadata; it's designed for CloudFormation templates, not data product discovery.

An EMR Spark cluster needs to read data from multiple sources: S3 data lake tables (Parquet), an Aurora PostgreSQL database, and a DynamoDB table. The team wants to use the Glue Data Catalog as the unified metadata source so that Spark jobs reference catalog table names instead of hardcoding connection strings, S3 paths, or DynamoDB table details in code. How should the EMR cluster be configured for catalog-based data consumption?
  • A. Configure EMR to use the Glue Data Catalog as its Hive metastore by setting hive.metastore.client.factory.class to the AWS Glue catalog implementation. Spark's catalog integration then resolves table references (spark.sql("SELECT * FROM glue_db.table_name")) against the Glue catalog — for S3 tables, it reads the location/schema from catalog metadata; for JDBC sources registered in the catalog, connection details are stored as table properties. All data access is catalog-mediated
  • B. Install the AWS Glue SDK on EMR and write custom code that calls the Glue GetTable API before each Spark read operation to retrieve connection details programmatically
  • C. Export all Glue Data Catalog metadata to a JSON file on S3 and have Spark read this file at job startup to configure data source connections
  • D. Use AWS Secrets Manager to store all data source connection details and reference Secrets Manager ARNs in Spark configurations instead of using the catalog
Jawaban Benar: A
EMR's native Glue Data Catalog integration replaces the traditional Hive metastore: (1) setting the metastore factory class to AWS Glue's implementation makes ALL Spark SQL table references resolve against the Glue catalog transparently; (2) Spark jobs use standard SQL table references without knowledge of underlying storage (spark.table("sales_db.transactions") works whether the data is on S3, registered via a crawler, or defined manually); (3) catalog table properties store format, location, SerDe, schema, and connection details; (4) this is configured once at the EMR cluster level — all Spark jobs on the cluster automatically use catalog-based resolution; (5) changes to catalog metadata (new partitions, schema updates) are picked up by subsequent Spark queries without code changes. Opsi B — programmatic Glue API calls work but require custom code in every Spark job, don't integrate with Spark SQL's native catalog resolution, and duplicate functionality that the native integration provides automatically. Opsi C — exporting to JSON creates a point-in-time snapshot that becomes stale; real-time catalog resolution ensures Spark always reads current metadata. Opsi D — Secrets Manager stores credentials securely but doesn't provide schema metadata, table locations, or partition information — it solves authentication but not catalog-based data discovery/access.

A company's data lake has evolved over 3 years, resulting in duplicate and overlapping datasets. Multiple teams independently ingested similar data (e.g., three different customer tables from different source systems). Analysts waste time querying wrong tables or getting inconsistent results because they don't know which table is the authoritative source. The company wants to use catalog metadata to designate authoritative data sources and guide consumers toward the correct tables. Which catalog enrichment strategy BEST addresses this problem?
  • A. Implement a catalog classification system using Glue Data Catalog table properties and Lake Formation tags to designate data quality tiers: "gold" (authoritative, curated), "silver" (transformed but not primary), "bronze" (raw ingestion). Add business metadata properties like owner, refresh-frequency, source-system, and data-quality-score. Deprecate non-authoritative tables by adding a "status: deprecated" property with migration guidance pointing to the gold-tier equivalent
  • B. Delete all duplicate and non-authoritative tables from the catalog, keeping only one version of each dataset
  • C. Create IAM policies that deny access to non-authoritative tables, forcing analysts to use only the designated gold tables
  • D. Rename all non-authoritative tables with a "DO_NOT_USE_" prefix so analysts can identify them by name
Jawaban Benar: A
Catalog enrichment with classification metadata provides discoverable data governance: (1) tiering (gold/silver/bronze) communicates data quality and authoritativeness at the catalog level — analysts searching for customer data see the gold-tier table first and understand it's the authoritative source; (2) business metadata (owner, refresh frequency, data quality score) helps analysts evaluate which dataset meets their needs; (3) "deprecated" status with migration guidance provides a transition path — existing queries referencing deprecated tables can be identified and migrated; (4) Lake Formation tags enable tag-based search (find all gold-tier tables in the sales domain); (5) this approach preserves historical tables for backward compatibility while clearly guiding new consumption. Opsi B — deleting tables breaks existing queries, dashboards, and ETL jobs that reference them; this causes immediate production issues without a transition period. Opsi C — IAM deny policies prevent access but don't explain WHY or WHERE to find the correct alternative; analysts get cryptic access-denied errors without guidance. Opsi D — renaming tables breaks existing references (same problem as deletion) and is a crude mechanism that doesn't convey quality level, ownership, or alternatives.

A financial institution needs to share specific catalog tables with an external partner organization that has its own AWS account. The partner needs to query shared data using their own Athena environment. The institution requires: (1) the partner sees only approved tables, (2) data remains in the institution's S3 bucket (no copying), (3) the institution can revoke access instantly, (4) all partner queries are auditable. Which mechanism enables secure catalog-based data sharing with external AWS accounts?
  • A. Use Lake Formation cross-account data sharing with named resources. Grant SELECT permission on specific catalog tables to the partner's AWS account ID. The partner creates a resource link in their own catalog pointing to the shared tables, then queries through their Athena — data stays in the institution's S3, Lake Formation enforces permissions, and CloudTrail logs all cross-account catalog access for audit
  • B. Create an S3 bucket policy granting the partner's account read access to the specific S3 prefixes containing the approved table data
  • C. Set up a VPN connection between both accounts and share a JDBC connection string for the partner to query the institution's Athena directly
  • D. Export approved table data to CSV files daily and upload them to a shared S3 bucket that both accounts can access
Jawaban Benar: A
Lake Formation cross-account sharing meets all four requirements: (1) named resource grants specify exact tables — the partner sees ONLY granted tables in their resource links, not the institution's full catalog; (2) data remains in the institution's S3 bucket — resource links point to the original location, no data copying occurs; (3) REVOKE permission immediately removes access — the partner's next query fails instantly without waiting for data deletion or bucket policy propagation; (4) CloudTrail records all cross-account Glue API calls (GetTable, GetPartitions) and Lake Formation access events provide query-level audit trails. The partner's experience: they see shared tables as local catalog entries and query normally through their own Athena. Opsi B — S3 bucket policies grant raw file access without table/column-level control; the partner could read ALL files in that prefix (potentially including other tables), and revoking requires identifying and removing specific policy statements (error-prone). Opsi C — VPN + direct Athena access would require sharing IAM credentials or creating cross-account roles for the partner to use the institution's Athena; this complicates security and doesn't use catalog-based discovery. Opsi D — daily CSV exports create data staleness, duplicate data (compliance risk for financial data), and require managing the export pipeline — this is data movement, not data sharing.

A data team manages a Glue Data Catalog with 2,000 tables. They notice that different query engines (Athena, Redshift Spectrum, EMR Spark, Glue ETL) sometimes interpret the same catalog table differently — Athena handles a certain date format correctly while EMR Spark throws parsing errors on the same table. The root cause is that catalog table definitions need engine-specific configurations. How should the team ensure consistent data consumption across all engines using the same catalog metadata?
  • A. Ensure catalog table definitions use standardized, engine-agnostic configurations: (1) use Hive-compatible SerDe formats that all engines understand (OpenCSVSerDe, ParquetHiveSerDe); (2) define explicit data types using catalog-standard type mappings; (3) set table properties like "skip.header.line.count" and date format properties that all engines honor; (4) use Parquet/ORC columnar formats which embed schemas in the files themselves, reducing dependence on catalog-level type definitions for parsing
  • B. Create separate catalog tables for each engine — athena_sales, emr_sales, spectrum_sales — each with engine-specific configurations
  • C. Standardize on a single query engine across the organization to eliminate cross-engine compatibility issues
  • D. Add a pre-processing Lambda function that transforms catalog metadata into engine-specific configurations before each query executes
Jawaban Benar: A
Standardized catalog definitions ensure consistent consumption across all engines: (1) Hive-compatible SerDe classes (like OpenCSVSerDe, LazySimpleSerDe, ParquetHiveSerDe) are understood by Athena, Spark, Spectrum, and Glue because they all implement the Hive metastore interface; (2) columnar formats (Parquet/ORC) include schema information within the data files, making them self-describing — engine differences in type handling are minimized because the file itself declares its types; (3) explicit table properties in the catalog (serialization.format, field.delim, timestamp.formats) provide consistent hints to all engines; (4) using standard Hive data types (string, bigint, timestamp) avoids ambiguity that causes cross-engine differences. Prevention is better than engine-specific workarounds. Opsi B — maintaining multiple table definitions per dataset creates N× catalog complexity, synchronization challenges, and defeats the purpose of a single catalog as source of truth. Opsi C — mandating a single engine is impractical — different workloads benefit from different engines (Athena for ad-hoc, EMR for heavy processing, Spectrum for Redshift-integrated queries). Opsi D — Lambda-based metadata transformation adds latency, complexity, and a failure point to every query; it patches symptoms rather than fixing root cause (non-standard catalog definitions).
