A data engineer manages a data lake on Amazon S3 with 10 TB of event data stored in JSON format. Athena queries on this data are slow and expensive, scanning the entire dataset for most queries. The most common query pattern filters by event_date and event_type. Which combination of optimizations will provide the GREATEST reduction in query cost and execution time?
  • A. Convert data to Apache Parquet format with Snappy compression and partition by event_date and event_type
  • B. Add an S3 Lifecycle policy to compress old JSON files and increase Athena DPU allocation
  • C. Create Athena views that pre-filter data by event_date and use LIMIT clauses in all queries
  • D. Enable S3 Intelligent-Tiering and use Athena query result caching with Snappy compression and partition by event_date and event_type
Correct Answer: A
Kombinasi konversi to Parquet (columnar format — only kolom that diquery in-scan), Snappy compression (reduces size data that in-scan), and partitioning by event_date and event_type (Athena only reads partition that relevan) provides reduction drastis on data scanned. Parquet itself can reduces scan 90%+ for query that only requires several kolom. Partitioning avoids full table scan.

Option A: CORRECT.
Option B: INCORRECT. Tetap requires parsing entire file because JSON row-based.
Option C: INCORRECT. Views not stores data and LIMIT runs setelah full scan.
Option D: INCORRECT. Not reduces scan size — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A company has multiple business units using Amazon Athena. The finance team frequently runs expensive queries that consume most of the query capacity, impacting other teams. Management wants to: limit finance team spending to $500/month on Athena, track usage per team, and prevent any single query from scanning more than 100 GB. Which Athena feature addresses ALL these requirements?
  • A. Use IAM policies to restrict the tables each team can query and set billing alarms with per-query data scan limits for tracking
  • B. Create separate AWS accounts for each team with AWS Budgets alerts, satisfying all of the stated requirements with minimal effort
  • C. Configure Athena workgroups — one per team — with per-query data scan limits and workgroup-level spending thresholds with CloudWatch metrics for tracking
  • D. Implement a Lambda-based query proxy that checks query cost estimates before execution, integrating natively with the rest of the pipeline
Correct Answer: C
Athena workgroups provides: (1) per-query data usage control — limits maximum data that boleh in-scan per query (100 GB limit), (2) workgroup-level data scan limits that can is configured per periode (equivalent spending control), (3) CloudWatch metrics per workgroup for tracking usage per team. Ini single feature that memenuhi all requirements.

Option A: INCORRECT. Mengontrol access table not spending — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Berlebihan and adds complexity.
Option C: CORRECT.
Option D: INCORRECT. Requires custom development and cannot akurat memperkirakan cost before execution.

A data engineer needs to use Athena to create transformed datasets for downstream analytics. The requirement is to read raw data from the "events_raw" table, apply aggregations and filters, and write the results as a new Parquet table partitioned by date in a different S3 location. Which Athena feature accomplishes this as a single SQL operation?
  • A. Use CREATE TABLE AS SELECT (CTAS) with format='PARQUET', partitioned_by, and external_location properties
  • B. Use INSERT INTO with a pre-existing external table pointing to the new S3 location and external_location properties
  • C. Create a VIEW on the aggregated query and export it using Athena's export to S3 feature
  • D. Run a SELECT query and configure the workgroup's query results location to the target S3 path
Correct Answer: A
CTAS (CREATE TABLE AS SELECT) in Athena enables transformation data and creation table new in satu operasi SQL. Properties that can is configured including: format (PARQUET, ORC, JSON, etc.), compression, partitioned_by columns, external_location for S3 path, and bucketing. This is ideal for ETL operations.

Option A: CORRECT.
Option B: INCORRECT. Can is used but requires table already is created sebelumnya — not single operation — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Athena views not stores data and there is no native "export" feature.
Option D: INCORRECT. Stores sebagai CSV query results, not partitioned Parquet table.

A data engineer has built an Athena-based reporting system where user-supplied parameters (date ranges, product IDs) are incorporated into SQL queries. The application constructs queries by string concatenation. A security review has flagged this as a SQL injection risk. Which Athena feature mitigates this vulnerability?
  • A. Implement input validation in the application layer using regex patterns with parameterized queries
  • B. Use Athena prepared statements with parameterized queries to safely bind user-supplied values
  • C. Use IAM policies to limit the SQL statements users can execute
  • D. Create Athena views that pre-filter data and restrict users to only query through views
Correct Answer: B
Athena prepared statements enables parameterized queries where user-supplied values in-bind sebagai parameter (uses ?) and not diinterpretasi sebagai SQL code. Ini is best practice security standard for prevents SQL injection.

Option A: INCORRECT. Adalah defense-in-depth that baik but rentan against bypass and not solves root cause — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: CORRECT.
Option C: INCORRECT. Mengontrol access to resources, not content from SQL queries.
Option D: INCORRECT. Membatasi access but not solves injection if views receives parameter.

A company has data distributed across multiple sources: a data lake in S3, operational data in Amazon RDS PostgreSQL, and reference data in Amazon DynamoDB. A data analyst needs to write a single Athena SQL query that joins data from all three sources. Which Athena capability enables this?
  • A. Export data from RDS and DynamoDB to S3 first, then query all data through standard Athena tables
  • B. Create Glue ETL jobs to replicate all data into a single Redshift cluster, then use Athena to query Redshift
  • C. Athena Federated Query using data source connectors for RDS and DynamoDB, allowing cross-source JOINs in a single query
  • D. Use Athena CTAS to materialize RDS and DynamoDB data into S3 tables before joining and DynamoDB, allowing cross-source JOINs in a single query
Correct Answer: C
Athena Federated Query enables eksekusi SQL queries against berbagai data sources uses Lambda-based data source connectors. Connectors available for RDS (PostgreSQL, MySQL), DynamoDB, Redshift, CloudWatch Logs, and others. Ini enables JOIN lintas source in satu query without moves data.

Option A: INCORRECT. Dan C (export/materialize) requires data movement and not provides real-time access to data terbaru.
Option B: INCORRECT. Berlebihan and expensive for satu requirements query.
Option C: CORRECT.
Option D: INCORRECT. Meskipun sounds convincing, still not correct for skenario this.

A data analytics team runs the same expensive aggregation query multiple times per hour across different dashboards. The underlying data only updates once every 6 hours. Each execution scans 500 GB and costs approximately $2.50. The team wants to reduce costs without modifying the dashboards. Which Athena feature directly addresses this?
  • A. Create a materialized view in Athena that pre-computes the aggregation with appropriate max-age setting, applying schema conversion and enrichment inline
  • B. Enable Athena query result reuse with appropriate max-age setting, so identical queries return cached results without re-scanning data
  • C. Schedule a Lambda function to run the query every 6 hours and store results in a separate S3 table
  • D. Increase the number of Athena DPUs to make queries run faster, satisfying all of the stated requirements with minimal effort
Correct Answer: B
Athena query result reuse enables identical queries (same SQL) mengembalikan result that already in-cache without re-scanning data. By max-age setting (for example 6 hours appropriate update frequency), queries berulang not dikenakan cost scan additional. Ini transparan bagi dashboards — does not need modifikasi.

Option A: INCORRECT. Salah because Athena not supports materialized views (that feature Redshift) — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: CORRECT.
Option C: INCORRECT. Requires modifikasi dashboard for reads from table different.
Option D: INCORRECT. Mempercepat execution but not reduces cost scan.

A data engineer manages a large Athena table with 5 years of historical data (50 TB total). Most queries only access the last 30 days of data. The table is partitioned by date. However, some queries still scan more data than expected because analysts forget to add partition filters. Which approach BEST prevents unnecessary full-table scans?
  • A. Split the table into "recent" and "archive" tables and only grant access to the recent table, meeting the latency and throughput goals of the design and minimizing end-to-end processing latency
  • B. Enable partition projection to make Athena automatically detect which partitions to scan with a WHERE clause limiting, handling the described workload reliably at scale and minimizing end-to-end processing latency
  • C. Move data older than 30 days to S3 Glacier and only keep recent data accessible, integrating natively with the rest of the pipeline and handling the described workload reliably at scale
  • D. Create an Athena view with a WHERE clause limiting to the last 30 days as the default access point, and configure workgroup per-query data scan limits as a safety net
Correct Answer: D
Athena views with built-in WHERE clause on partition column ensures that queries through view only scan 30 days data in a default. Workgroup per-query data scan limits provides safety net — if query melebihi threshold (for example 1 TB), query will dibatalkan. Kombinasi this prevents accidental full scans.

Option A: INCORRECT. Requires maintenance dua table and logic pemisahan.
Option B: INCORRECT. Membantu performance metadata lookup but not prevents user from scanning all partition — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Creates data historis not queryable if is required.
Option D: CORRECT.

A data lake contains millions of small files (average 1 MB each) generated by IoT devices. Athena queries on this data are extremely slow despite the total data volume being only 100 GB. The data is already in Parquet format and properly partitioned. What is the PRIMARY cause and the BEST solution?
  • A. The small file problem causes excessive S3 LIST and GET operations — use Athena CTAS or AWS Glue to compact files into larger sizes (128 MB - 512 MB optimal range)
  • B. The partitioning scheme has too many partitions — reduce the number of partitions by using monthly instead of daily, handling the described workload reliably at scale and applying schema conversion and enrichment inline
  • C. Athena needs more compute resources — switch to Athena provisioned capacity for consistent performance, scaling elastically to millions of events per second and satisfying all of the stated requirements with minimal effort
  • D. Parquet format is not efficient for small files — convert to ORC format which handles small files better with native S3 integration and optimized data transfer, scaling horizontally as ingestion throughput keeps growing
Correct Answer: A
Small file problem is problem umum in data lakes. Each file requires overhead: S3 LIST operations for menemukan file, GET requests for membuka file, and Parquet footer reading per file. By millions of file small, overhead this mendominasi query time. Solusinya is compaction — combines file small menjadi file berukuran 128-512 MB that optimal for Athena/Presto. CTAS or Glue job can performs compaction this.

Option A: CORRECT.
Option B: INCORRECT. Not solves problem file per partition that too many.
Option C: INCORRECT. Membantu throughput but overhead per-file still ada.
Option D: INCORRECT. Salah — ORC not handles small files better from Parquet — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

The raw tables have cryptic column names (col_a1, col_b2), contain technical columns not relevant to analysts, and require complex JOINs between multiple tables. Analysts should be able to query using business-friendly names without knowing the underlying table structure. Which Athena approach is MOST appropriate?
  • A. Create a Glue crawler to re-catalog the tables with new business-friendly column names, integrating natively with the rest of the pipeline
  • B. Use AWS Lake Formation to create virtual columns with business names on top of existing tables, handling the described workload reliably at scale
  • C. Build a CTAS that creates a denormalized copy of all tables with renamed columns for analysts, integrating natively with the rest of the pipeline

Athena views provides abstraction layer that ideal: column aliases provides business-friendly names, pre-built JOINs menyederhanakan access pattern, and column selection menyembunyikan technical fields. Views not stores data duplikat and always reflect data terbaru.

Option B: INCORRECT. Salah — Lake Formation not has feature "virtual columns" for renaming.

A data engineer is optimizing Athena query performance for a 2 TB partitioned Parquet table. Queries that filter on non-partition columns (e.g., WHERE customer_segment = 'enterprise') still scan all files within the matching partitions. The table has 50 columns but most queries only access 5-10 columns. Which optimization technique provides the BEST improvement for this query pattern?
  • A. Increase the Parquet file size to 1 GB to reduce the number of files to open, satisfying all of the stated requirements with minimal effort
  • B. Add customer_segment as an additional partition column to enable partition pruning, meeting the latency and throughput goals of the design and minimizing end-to-end processing latency
  • C. Convert the data to CSV format which supports faster full-file scanning with row group statistics, meeting the latency and throughput goals of the design
  • D. Ensure Parquet files are written with row group statistics and page-level column indexes enabled, allowing predicate pushdown to skip irrelevant row groups within files
Correct Answer: D
Parquet row group statistics (min/max values) and page-level column indexes enables predicate pushdown — Athena (Presto/Trino) can skip row groups where filter condition (customer_segment = 'enterprise') cannot dipenuhi based on statistics, without reads actual data. Ini significant reduces I/O for non-partition column filters.

Option A: INCORRECT. Reduces open operations but not membantu filtering within files without statistics.
Option B: INCORRECT. Can over-partition and increases small file problem if cardinality high.
Option C: INCORRECT. Kehilangan all keuntungan columnar format — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: CORRECT.
