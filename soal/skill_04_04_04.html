A data engineering team stores CloudTrail logs in S3 partitioned by year/month/day. They need to query these logs to investigate a security incident that occurred on a specific date. The CloudTrail log bucket contains 5 years of data totaling 50 TB. The team wants to minimize query costs. Which Athena configuration provides the MOST cost-effective querying?
  • A. Create an Athena table with Hive-style partitioning matching the S3 path structure and use WHERE clauses on partition columns
  • B. Create a CTAS (Create Table As Select) query to copy the relevant day's data to a new table in Parquet format, then query that table
  • C. Create an Athena table without partitions and use the built-in CloudTrail SerDe to filter by eventTime with date-type partition keys matching the S3 path pattern
  • D. Use Athena partition projection with date-type partition keys matching the S3 path pattern to avoid partition metadata management
Correct Answer: D
Partition projection eliminates requirements for runs MSCK REPAIR TABLE or adds partition manually, that very important for data that terus bertambah each days. By date-type projection matching path pattern (s3://bucket/AWSLogs/account/CloudTrail/region/yyyy/mm/dd/), Athena automatically calculates partition without metadata calls to Glue catalog. Query with WHERE date = '2024-03-15' only scan data days that (~27 GB vs 50 TB), very reduces cost.

Option A: INCORRECT. Berfungsi but requires maintenance partition manual.
Option B: INCORRECT. Requires scan full data first and adds cost storage.
Option C: INCORRECT. Without partition will scan entire 50 TB (very expensive) — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: CORRECT.

A DevOps engineer needs to quickly identify the top 10 Lambda functions generating the most errors in the past hour across all production Lambda log groups. The log groups follow the naming pattern /aws/lambda/prod-*. The engineer needs results within seconds. Which tool and approach is MOST appropriate?
  • A. Use Amazon Athena to query exported Lambda logs in S3 with a GROUP BY function name
  • B. Use CloudWatch Logs Insights to query multiple log groups simultaneously with a stats command grouping by function name
  • C. Use CloudWatch Metrics to view the Errors metric filtered by FunctionName dimension with a stats command grouping by function name
  • D. Use Amazon OpenSearch Service with a pre-built Kibana dashboard showing Lambda error rates, streaming results downstream in near real time
Correct Answer: B
CloudWatch Logs Insights can query up to 50 log groups in a simultaneously and provides result in hitungan seconds for data recent. Query: `filter @message like /ERROR/ | stats count(*) as errorCount by @logGroup | sort errorCount desc | limit 10` will provides top 10 functions with error terbanyak. Supports wildcard pattern for log group selection.

Option A: INCORRECT. Requires export to S3 first and not provides result real-time.
Option B: CORRECT.
Option C: INCORRECT. Menunjukkan error count per function but not provides ranking top-N in one query and requires navigasi manual — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Requires setup and ingestion pipeline that already runs — not solution "quick".

A company needs to build a real-time security dashboard that displays: login failures, API throttling events, and unauthorized access attempts with sub-second search latency. The dashboard must support full-text search across all log fields and provide alerting capabilities. Data volume is 2 TB per day. Which AWS service is BEST suited for this use case?
  • A. Amazon OpenSearch Service with OpenSearch Dashboards and alerting plugin
  • B. CloudWatch Logs Insights with CloudWatch Dashboards and CloudWatch Alarms
  • C. Amazon Redshift Serverless with materialized views refreshed every minute
  • D. Amazon Athena with scheduled queries feeding a QuickSight dashboard
Correct Answer: A
Amazon OpenSearch Service memenuhi all requirements: sub-second search latency through inverted indexing, full-text search across all fields, real-time dashboards via OpenSearch Dashboards (Kibana successor), and built-in alerting plugin for notifications. By 2 TB/day, OpenSearch can handles volume this with cluster that appropriately sized.

Option A: CORRECT.
Option B: INCORRECT. Has query latency several seconds and not supports full-text search with sub-second response on 2 TB daily data.
Option C: INCORRECT. Not dioptimasi for full-text search and materialized view refresh each minutes not real-time.
Option D: INCORRECT. Bersifat batch and not provides sub-second latency for interactive search.

A data engineer writes the following CloudWatch Logs Insights query to analyze API Gateway access logs but gets no results despite logs being present in the log group. What is the MOST likely issue?

fields @timestamp, @message | filter status >= 500 | stats count(*) by bin(5m)
  • A. The stats command cannot be used after a filter command — the order must be reversed, handling the described workload reliably at scale and integrating natively with the rest of the pipeline
  • B. The bin() function requires a time field parameter — it should be bin(@timestamp, 5m) configured for optimal performance and minimal operational overhead, satisfying all of the stated requirements with minimal effort
  • C. The field "status" needs to be parsed from the log message first using the parse command since API Gateway logs store it as part of a JSON or text string
  • D. CloudWatch Logs Insights does not support the >= comparison operator for string fields, handling the described workload reliably at scale and meeting the latency and throughput goals of the design
Correct Answer: C
API Gateway access logs, if in format custom or CLF, stores status code as part from messages log. CloudWatch Logs Insights requires `parse` command for mengekstrak fields from log messages that not in format JSON that automatic in-discover. Contoh: `parse @message "* * * *" as ip, method, path, status | filter status >= 500`. For JSON logs, fields automatic available but must direferensikan with prefix that correct.

Option A: INCORRECT. Incorrect — filter before stats is order that correct and valid.
Option B: INCORRECT. Incorrect — `bin(5m)` is syntax valid that uses @timestamp in a implisit — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: CORRECT.
Option D: INCORRECT. Incorrect — >= operator works after field in-parse with correct.

A company has the following log analysis requirements: (1) VPC Flow Logs — 500 GB/day, queried weekly for compliance reports, (2) Application logs — 50 GB/day, queried interactively multiple times daily, (3) CloudTrail logs — 10 GB/day, queried occasionally during investigations. Which combination of tools provides the MOST cost-effective solution while meeting latency requirements?
  • A. Use CloudWatch Logs Insights for all three log types since they all originate from AWS services with partitioned Parquet)
  • B. VPC Flow Logs → Athena (S3 with Parquet), Application logs → CloudWatch Logs Insights, CloudTrail → CloudTrail Lake
  • C. VPC Flow Logs → Athena (S3 with partitioned Parquet), Application logs → OpenSearch Service, CloudTrail → Athena with partition projection
  • D. Use Amazon OpenSearch Service for all three log types with index lifecycle management for cost optimization, minimizing end-to-end processing latency
Correct Answer: C
Solution optimal memilih tool based on volume, frekuensi query, and latency requirement: (1) VPC Flow Logs 500 GB/day that in-query weekly suitable for Athena + S3 Parquet — cost storage low and bayar per query, partition reduces scan. (2) Application logs 50 GB/day with interactive queries multiple times/day suitable for OpenSearch that provides sub-second latency and rich dashboards. (3) CloudTrail 10 GB/day that rarely in-query suitable for Athena — cost very low because rarely query.

Option A: INCORRECT. CloudWatch Logs Insights has cost ingestion high for 500 GB/day — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Can works but CloudWatch Logs Insights less ideal for 50 GB/day interactive analysis and CloudTrail Lake expensive for occasional queries.
Option C: CORRECT.
Option D: INCORRECT. Very expensive for 500 GB/day VPC logs that rarely queried.

A data engineer needs to create an Athena table for structured query of CloudTrail logs stored in S3. The logs are in JSON format with nested fields like userIdentity, requestParameters, and responseElements. Which table creation approach provides the BEST query performance and cost efficiency?
  • A. Use CTAS to convert all CloudTrail JSON to Parquet format with columnar storage, then query the Parquet table
  • B. Use CREATE TABLE with the CloudTrail SerDe, define struct types for nested fields, add partition projection for date-based partitions
  • C. Use CREATE TABLE with OpenX JSON SerDe (org.openx.data.jsonserde.JsonSerDe) and define all fields as STRING type for simplicity
  • D. Use CREATE TABLE with the CloudTrail SerDe (com.amazon.emr.hive.serde.CloudTrailSerde) and define the full nested schema including partition columns for date
Correct Answer: B
Uses CloudTrail SerDe that didesain khusus for format CloudTrail JSON, mendefinisikan struct types for nested fields (userIdentity STRUCT), and partition projection for date provides kombinasi best. Struct types enables dot notation queries (userIdentity.arn) and partition projection mengeliminasi overhead metadata management.

Option A: INCORRECT. Provides performance best per-query but requires process konversi ongoing and double storage costs.
Option B: CORRECT.
Option C: INCORRECT. Kehilangan capabilities query nested fields directly — must uses JSON functions that slower.
Option D: INCORRECT. Without partition projection requires manual partition management.

A company uses Amazon OpenSearch Service for log analytics. Their OpenSearch cluster stores 30 days of hot data (5 TB) for dashboards and alerting. After 30 days, data should still be searchable but with relaxed latency requirements (up to 10 seconds). After 90 days, data should be archived for compliance only. Which index lifecycle configuration is MOST cost-effective?
  • A. Hot tier (0-30 days) → Delete after 30 days and export to S3 for Athena queries
  • B. Hot tier (0-30 days) → Warm tier (30-90 days) → Delete after 90 days with snapshots to S3
  • C. Hot tier (0-30 days) → UltraWarm tier (30-90 days) → Cold storage (90+ days)
  • D. Single hot tier for all data with force merge of older indices to reduce shard count
Correct Answer: C
OpenSearch Service provides three tiers: Hot (instance store/EBS, fastest), UltraWarm (S3-backed, cost-effective for data that rarely diakses but still searchable), and Cold storage (most cheap, data must in-attach returns to warm before can in-search). Konfigurasi B memenuhi all requirements: hot for dashboards real-time (0-30d), UltraWarm for searchable with latency higher (30-90d), cold for compliance archival (90d+).

Option A: INCORRECT. Kehilangan capabilities search in OpenSearch after 30 days.
Option B: INCORRECT. Deletes data after 90 days padahal compliance still requires retention.
Option C: CORRECT.
Option D: INCORRECT. Very expensive because hot tier for all data.

Dashboard automatically menampilkan top contributors that changes in real-time.

A data engineer needs to create a CloudWatch Logs Insights query that calculates the p99 latency for each API endpoint from application logs. The logs are in JSON format with fields: endpoint, method, latency_ms, status_code, and timestamp. Which query correctly produces the p99 latency per endpoint sorted by highest latency first?
  • A. filter ispresent(latency_ms) | stats avg(latency_ms) as p99 by endpoint | sort p99 desc
  • B. fields endpoint, latency_ms | stats percentile(latency_ms, 99) as p99 by endpoint | sort p99 desc
  • C. fields endpoint, latency_ms | stats p99(latency_ms) as p99_latency by endpoint | sort p99_latency desc
  • D. fields endpoint, latency_ms | stats pct(latency_ms, 99) as p99 by endpoint | sort p99 desc
Correct Answer: B
In CloudWatch Logs Insights, function `percentile(field, percent)` calculates persentil that is determined. Syntax `stats percentile(latency_ms, 99) as p99 by endpoint` mengelompokkan based on endpoint and calculates p99 latency. `sort p99 desc` mengurutkan from tertinggi.

Option A: INCORRECT. Uses `avg()` that calculates rata-rata, not persentil to-99.
Option B: CORRECT.
Option C: INCORRECT. Uses `p99()` that not syntax function that valid — must uses percentile(field, 99).
Option D: INCORRECT. Uses `pct()` that not function valid in CloudWatch Logs Insights — function that correct is `percentile()`.
