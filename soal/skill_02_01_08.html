Skill 2.1.8: Describe Vector Index Types

HNSW, IVF — vector index types for similarity search and AI/ML workloads

1
A machine learning team is building a product recommendation engine that stores 10 million product embedding vectors (768 dimensions each) in Amazon Aurora PostgreSQL with the pgvector extension. The application requires sub-100ms query latency for finding the 10 most similar products, and the team can tolerate up to 5% recall loss (missing truly similar items) for speed. They expect infrequent bulk updates (weekly catalog refresh) but very high read throughput (1,000 queries/second). Which vector index type is MOST appropriate?
  • A. HNSW (Hierarchical Navigable Small World) index — HNSW builds a multi-layer graph structure where each node connects to its nearest neighbors. At query time, the search traverses from a top-layer entry point down through progressively denser layers, providing consistently low latency (sub-100ms) with high recall (95%+). HNSW excels for read-heavy workloads with infrequent updates due to its fast query speed but higher index build time
  • B. IVF (Inverted File) index with 1,000 clusters — IVF partitions vectors into clusters and searches only the nearest clusters at query time
  • C. Flat (brute-force) exact nearest neighbor search without any index to guarantee 100% recall
  • D. A B-tree index on a hash of the embedding vector for exact match lookups
Jawaban Benar: A
HNSW is the optimal choice for this workload profile: (1) consistently low query latency — HNSW provides O(log N) search complexity through its hierarchical graph structure, easily achieving sub-100ms for 10M vectors; (2) high recall — with properly tuned ef_search parameters, HNSW typically achieves 95-99% recall, well within the 5% tolerance; (3) read-heavy optimization — HNSW's pre-built graph structure makes queries extremely fast, and since catalog updates are weekly, the higher index build time is acceptable; (4) pgvector supports HNSW natively with CREATE INDEX ... USING hnsw. Opsi B — IVF is viable but provides less consistent latency than HNSW; IVF's recall depends heavily on the nprobe parameter (number of clusters searched), and achieving 95% recall at 1,000 QPS may require probing many clusters, increasing latency. IVF is better suited for scenarios where memory is constrained or rapid index builds are needed. Opsi C — brute-force search on 10 million 768-dimensional vectors would take 500ms-2s per query, far exceeding the 100ms requirement, and cannot sustain 1,000 QPS. Opsi D — B-tree indexes don't support similarity/distance operations; they can only do exact value matches, which is meaningless for embedding vector similarity search.
2
A data engineering team is deploying a real-time fraud detection system that stores 500 million transaction embedding vectors in Amazon OpenSearch Service. New vectors are ingested at 50,000 per second during peak hours, and the index must support similarity searches against incoming transactions within 200ms while continuously incorporating new vectors. Memory constraints limit the solution to 256 GB RAM. Which vector index type BEST handles this high-ingestion, memory-constrained workload?
  • A. IVF (Inverted File) index — IVF partitions the vector space into clusters using k-means centroids. New vectors are assigned to existing clusters quickly (only computing distance to centroids), making ingestion fast. The index structure is more memory-efficient than graph-based approaches because it stores cluster assignments rather than per-vector neighbor lists. IVF supports incremental additions without full reindexing
  • B. HNSW index with default parameters — HNSW provides the best query latency regardless of ingestion rate and memory constraints
  • C. Flat index with S3-backed storage to offload memory requirements to object storage
  • D. Product Quantization (PQ) index alone without any partitioning structure for maximum compression
Jawaban Benar: A
IVF is the preferred choice for high-ingestion, memory-constrained environments: (1) ingestion speed — inserting a vector into IVF requires computing distance to centroids only (not updating neighbor connections like HNSW), making insertions O(k) where k = number of clusters, not O(M × log N) like HNSW graph updates; (2) memory efficiency — IVF stores a centroid table + inverted lists (vector assignments), consuming significantly less memory per vector than HNSW's multi-layer neighbor adjacency lists (which store M connections per vector per layer); (3) for 500M vectors at 256 GB RAM, IVF with quantization (IVF-PQ) can compress vectors while IVF structure provides search partitioning; (4) OpenSearch k-NN supports IVF natively via the Faiss engine. Opsi B — HNSW provides excellent query latency but requires ~4× more memory per vector (storing neighbor lists) and has slower insertions (graph updates require connecting to M neighbors); at 500M vectors with 256 GB limit, HNSW likely exceeds memory. Opsi C — flat indexes don't use specialized data structures and require loading all vectors for search; S3-backed storage would make 200ms queries impossible due to I/O latency. Opsi D — PQ alone compresses vectors but doesn't provide a search structure; without IVF partitioning, the system must still compare against all 500M compressed vectors (too slow at 200ms target).

A data scientist working with Amazon Aurora PostgreSQL (pgvector) needs to build a semantic search application for legal documents. The corpus contains 5 million document embeddings at 1,536 dimensions (from a large language model). The application requires 99% recall — almost no relevant documents can be missed because missing a relevant legal precedent could have serious consequences. Query latency up to 500ms is acceptable. Which index configuration BEST achieves this high-recall requirement?
  • A. Use an HNSW index with high ef_construction (512) during build time and high ef_search (200) at query time. Higher ef_construction creates denser graph connections during index building, and higher ef_search explores more candidates during query traversal — both directly increase recall at the cost of build time and query latency respectively. At ef_search=200 for 5M vectors, HNSW typically achieves 99%+ recall within the 500ms latency budget
  • B. Use an IVF index with nlist=100 clusters and nprobe=1 to minimize latency while relying on cluster quality for recall
  • C. Use a flat (exact) brute-force index for guaranteed 100% recall regardless of dataset characteristics
  • D. Use HNSW with default parameters (ef_construction=64, ef_search=40) and post-filter results using a re-ranking model to catch missed documents
Jawaban Benar: A
HNSW with tuned parameters provides the optimal balance of high recall and acceptable latency: (1) ef_construction=512 builds a denser graph — each node maintains connections to more neighbors, creating more paths to find relevant results; (2) ef_search=200 means the query explores 200 candidates during traversal (vs. default 40), dramatically increasing the probability of finding all 99% of true nearest neighbors; (3) at 5 million vectors and 500ms budget, HNSW with these parameters typically achieves 99%+ recall while staying within latency bounds; (4) the trade-off is ~4× slower index build and ~3× slower queries compared to defaults — but both remain acceptable (build once for static corpus, 500ms query budget is generous). Opsi B — IVF with nprobe=1 searches only the single nearest cluster, providing ~50-70% recall at best; achieving 99% recall with IVF requires nprobe≈50-100 which may exceed the latency budget for 5M vectors at 1,536 dimensions. Opsi C — brute-force on 5M vectors at 1,536 dimensions requires computing 5M distance calculations of 1,536-dimensional vectors per query; this takes 2-5 seconds on typical Aurora instances, exceeding the 500ms budget. Opsi D — default HNSW parameters (ef_search=40) achieve approximately 90-95% recall; a re-ranking model can only re-rank the candidates already retrieved — it cannot find documents that HNSW missed entirely.

A company uses Amazon OpenSearch Service for a customer support chatbot that performs semantic similarity search against 50 million FAQ and knowledge base embeddings. They notice that their HNSW index consumes 180 GB of RAM just for the graph structure (separate from vector storage). The team needs to reduce memory footprint by at least 60% while maintaining acceptable query performance. Which technique MOST effectively reduces HNSW memory consumption?
  • A. Reduce the HNSW M parameter (maximum connections per node) from the default 16 to 8. The graph adjacency lists consume M × 4 bytes × number_of_vectors × number_of_layers — halving M approximately halves the graph memory. Additionally, combine with Product Quantization (PQ) to compress the stored vectors from full-precision floats to 8-bit quantized codes, reducing vector storage by 4×. Together, these achieve 60%+ memory reduction
  • B. Enable OpenSearch's disk-based vector search to move the entire HNSW graph to SSD storage instead of RAM
  • C. Increase ef_construction to build a higher-quality graph that requires fewer connections per node for the same recall
  • D. Switch from cosine similarity to dot product distance metric to reduce the computational memory required during search
Jawaban Benar: A
Reducing M and applying quantization are the two primary levers for HNSW memory reduction: (1) HNSW graph memory is proportional to M (connections per layer) — reducing M from 16 to 8 cuts graph adjacency list memory by ~50%; the trade-off is slightly lower recall, compensated by increasing ef_search at query time; (2) Product Quantization compresses each 768/1536-dimensional float32 vector from thousands of bytes to 64-128 bytes of quantized codes — a 75-90% reduction in vector storage; (3) combined effect on 180 GB: graph reduction (90 GB) + vector quantization (potentially 120 GB → 30 GB) achieves the 60% target. OpenSearch k-NN supports both M parameter tuning and PQ encoding via the Faiss engine. Opsi B — while OpenSearch supports disk-based approximate nearest neighbor search (for IVF-based indexes), HNSW is fundamentally designed as an in-memory structure; disk-based HNSW would have dramatically higher latency due to random graph traversal patterns causing many disk seeks. Opsi C — increasing ef_construction increases build time and memory (larger candidate lists during construction) without reducing the final graph size. Opsi D — the distance metric doesn't affect memory consumption; it's purely a computation choice that doesn't change storage requirements.

A data engineering team needs to implement a vector similarity search for an image recognition pipeline. The image embeddings are 2,048 dimensions (from a ResNet model), and they have 100 million vectors. They observe that query latency is 800ms even with an HNSW index, primarily because computing distance between high-dimensional vectors is expensive. Which preprocessing technique MOST effectively reduces query latency while preserving search quality?
  • A. Apply dimensionality reduction using PCA (Principal Component Analysis) to reduce embeddings from 2,048 to 256 dimensions before indexing. PCA identifies the principal components that capture the most variance in the embedding space, compressing vectors by 8× with typically 90-95% of the original similarity information preserved. Distance computation becomes 8× faster per vector comparison, dramatically reducing query latency
  • B. Split each 2,048-dimensional vector into 8 sub-vectors of 256 dimensions and create separate indexes for each sub-vector, then aggregate results
  • C. Increase the number of OpenSearch data nodes to distribute the 100M vectors across more shards for parallel search
  • D. Switch from HNSW to a flat brute-force index with SIMD-optimized distance computation for high-dimensional vectors
Jawaban Benar: A
Dimensionality reduction directly attacks the root cause — expensive high-dimensional distance computations: (1) distance computation is O(d) where d = dimensions; reducing from 2,048 to 256 makes each distance computation 8× faster; (2) PCA is the standard preprocessing step that identifies dimensions contributing most to variance — for learned embeddings like ResNet, the top 256 principal components typically capture 90-95% of the discriminative information; (3) index build time, memory consumption, and query latency all improve proportionally to the dimension reduction; (4) the reduced vectors are indexed normally with HNSW, benefiting from both faster distance computation AND smaller graph structure. Opsi B — splitting vectors into sub-vectors and maintaining separate indexes creates complex query coordination, result merging challenges, and doesn't reduce total computation (same total dimensions compared across sub-indexes). Opsi C — more shards distribute vectors but each shard still computes 2,048-dimensional distances; latency is bounded by the per-vector computation cost, not parallelism (at 100M vectors with HNSW, the graph traversal itself isn't the bottleneck — distance computation is). Opsi D — flat index on 100M vectors requires computing distance against ALL vectors (even with SIMD); this would be far slower than HNSW's graph-based approach that only computes distance against ~200-400 candidates.

A company is building a multi-modal search platform on AWS that combines text embeddings (from BERT, 768 dimensions) with image embeddings (from CLIP, 512 dimensions) for product search. They want to store and search 20 million product vectors in a managed AWS service. The platform requires: (1) vector similarity search, (2) metadata filtering (brand, category, price range), (3) hybrid search combining vector similarity with keyword matching. Which AWS service and index configuration BEST supports this multi-modal search use case?
  • A. Amazon OpenSearch Service with k-NN plugin — store vectors in k-NN vector fields (HNSW or IVF engine), combine with OpenSearch's native full-text search and filtering capabilities. Use a single index with both vector fields and metadata fields, enabling hybrid queries that combine k-NN similarity scores with BM25 text relevance scores and exact metadata filters in a single request. The k-NN score_mode allows blending vector and text scores
  • B. Amazon Aurora PostgreSQL with pgvector — store vectors with pgvector and use SQL WHERE clauses for metadata filtering and LIKE queries for text search
  • C. Amazon Neptune with graph-based vector similarity — store embeddings as graph node properties and use graph traversal for finding similar products
  • D. Amazon S3 with a custom Lambda function that performs brute-force similarity search and applies metadata filters in memory
Jawaban Benar: A
OpenSearch provides the complete feature set for multi-modal search: (1) k-NN plugin supports both HNSW and IVF indexes for vector similarity on text AND image embeddings; (2) native Lucene-based full-text search with BM25 scoring for keyword matching; (3) efficient metadata filtering using OpenSearch's inverted indexes (brand, category as keyword fields, price as numeric range); (4) hybrid queries combine all three signal types in a single request using script_score or neural search plugin; (5) the rescore API and normalization processors allow tuning the blend of vector similarity + text relevance + filter scores; (6) managed service handles scaling to 20M vectors. Opsi B — pgvector provides vector search and SQL filtering, but PostgreSQL's text search (ts_vector/ts_query) is significantly less capable than OpenSearch's BM25 for full-text relevance ranking, and hybrid scoring requires complex manual query construction; it also lacks the native score blending capabilities. Opsi C — Neptune is a graph database for relationship traversal; it doesn't support vector similarity search natively and isn't designed for embedding-based search workloads. Opsi D — Lambda with brute-force search on 20M vectors would take seconds per query and cannot sustain production query volumes; this is not a viable architecture for similarity search at scale.

A data engineer is configuring an IVF index in Amazon OpenSearch Service for a 200-million vector dataset. They need to choose the number of clusters (nlist) and the number of clusters to search at query time (nprobe). The dataset has embeddings from multiple distinct domains (electronics, clothing, food, books — roughly 50M vectors each). What considerations determine the optimal nlist and nprobe values for balancing recall and latency?
  • A. Set nlist = sqrt(N) as a baseline (approximately 14,142 clusters for 200M vectors), which provides roughly equal-sized clusters of ~14,000 vectors each. Set nprobe based on recall requirements: nprobe=1 gives ~50-60% recall with minimal latency; nprobe=10-20 achieves 90-95% recall; nprobe=50+ approaches 99% recall but with proportionally higher latency. The multi-domain nature suggests vectors cluster well, so moderate nprobe values should achieve high recall
  • B. Set nlist equal to the number of distinct domains (4 clusters) since vectors naturally group by domain, and set nprobe=4 to always search all clusters
  • C. Set nlist=1,000,000 (very fine granularity) to maximize precision per cluster and set nprobe=1 to search only the single closest cluster for minimum latency
  • D. Set nlist and nprobe to the same value to ensure every cluster is searched, guaranteeing 100% recall
Jawaban Benar: A
The sqrt(N) heuristic for nlist is a well-established starting point for IVF configuration: (1) nlist = sqrt(200M) ≈ 14,142 creates clusters of manageable size (~14,000 vectors); too few clusters means each cluster is too large (slow exhaustive search within cluster); too many means cluster centroids poorly represent their members (low recall); (2) nprobe directly controls the recall-latency trade-off: searching more clusters finds more true neighbors but takes proportionally longer; (3) with distinct domains (electronics, clothing, etc.), embeddings from the same domain cluster tightly together, meaning the correct cluster is usually found with moderate nprobe values; (4) practical tuning: start with nprobe=sqrt(nlist)≈120, then adjust based on measured recall. Opsi B — only 4 clusters for 200M vectors means each cluster contains 50M vectors; searching within a 50M-vector cluster is essentially brute-force and provides no speed benefit over a flat index. Opsi C — 1M clusters with 200M vectors gives only ~200 vectors per cluster; clusters are so small that cluster centroids become unreliable representatives, and nprobe=1 gives very low recall because similar vectors may span many tiny clusters. Opsi D — nprobe=nlist means searching ALL clusters = brute-force search = no speed benefit from having an index at all.

A data pipeline team needs to implement a vector similarity search solution for a RAG (Retrieval-Augmented Generation) application. The system stores 2 million document chunk embeddings (1,536 dimensions from OpenAI ada-002). Queries involve retrieving the top-20 most relevant chunks for a user question. The application has strict requirements: (1) must return results within 50ms, (2) must support filtered search (by document category, date range, access level), (3) data updates occur daily (batch). They choose Amazon Aurora PostgreSQL with pgvector. Which index strategy BEST meets all requirements?
  • A. Create an HNSW index on the embedding column with m=16 and ef_construction=200. For filtered queries, use partial HNSW indexes (CREATE INDEX ... WHERE category = 'X') for high-cardinality filters, or use post-filtering for low-selectivity filters. Set ef_search=100 at query time for high recall. With 2M vectors, HNSW provides sub-50ms latency while pgvector's SQL integration allows combining vector search with standard WHERE clause metadata filtering
  • B. Create an IVF index with lists=1000 and use pre-filtering (filter first, then vector search on filtered subset) for all queries
  • C. Use a flat (no index) approach with parallel sequential scan since 2M vectors at 1,536 dimensions is small enough for brute-force within 50ms on Aurora
  • D. Create separate HNSW indexes for each combination of category and access level to avoid any runtime filtering
Jawaban Benar: A
HNSW with pgvector is the optimal configuration for this RAG use case: (1) 2M vectors with HNSW provides consistent sub-50ms latency for top-20 retrieval — HNSW's graph traversal is highly efficient at this scale; (2) pgvector integrates with standard PostgreSQL WHERE clauses, enabling filtered vector search (e.g., ORDER BY embedding <=> query_vector WHERE category = 'legal' AND date > '2024-01-01'); (3) partial indexes (CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops) WHERE access_level = 'public') create separate HNSW graphs for high-value filter categories, providing filtered search without post-filtering recall loss; (4) daily batch updates are well-suited to HNSW which handles periodic bulk insertions efficiently. Opsi B — IVF with pre-filtering can be effective but pgvector's IVF implementation has limitations with filtered search; applying a WHERE filter before IVF search may eliminate entire clusters, reducing effective recall significantly for selective filters. Opsi C — brute-force on 2M vectors at 1,536 dimensions requires 2M × 1,536 × 4 bytes = 12 GB of distance computations per query; on Aurora's instance types, this takes 200-500ms, exceeding the 50ms requirement. Opsi D — creating indexes for every combination of category × access_level leads to index explosion (potentially hundreds of indexes), excessive storage consumption, and maintenance complexity during daily updates.

A data engineering team needs to compare HNSW and IVF vector indexes for a new embedding search workload. They run benchmarks on 50 million vectors at 256 dimensions and observe: HNSW achieves 97% recall at 5ms latency (p99), while IVF achieves 95% recall at 8ms latency. However, the HNSW index takes 4 hours to build and consumes 45 GB of RAM, while IVF builds in 30 minutes and uses 12 GB. The dataset receives 100,000 new vectors daily. Which architectural factor should MOST influence the final index type selection?
  • A. The daily ingestion of 100,000 new vectors is the decisive factor. HNSW requires expensive graph updates for each insertion (connecting new nodes to existing neighbors and potentially updating connections at multiple graph layers), while IVF only needs to assign new vectors to existing clusters (a single centroid distance computation). For frequently-updated datasets, IVF's lighter write path provides better operational sustainability despite slightly lower recall
  • B. The 2% recall difference (97% vs 95%) is the decisive factor — in production, this means missing 2% more relevant results which may be unacceptable
  • C. The RAM difference (45 GB vs 12 GB) is the decisive factor — it directly determines infrastructure cost and instance type selection
  • D. The build time difference (4 hours vs 30 minutes) is the decisive factor — it determines how quickly the index can be rebuilt after failures
Jawaban Benar: A
For operational data engineering, the write/update pattern is typically the most impactful architectural decision: (1) 100,000 daily insertions into HNSW requires 100,000 graph update operations — each insertion traverses the graph to find connection points and updates neighbor lists at potentially multiple layers; this can degrade index quality over time if not periodically rebuilt; (2) IVF insertion is trivially cheap — compute distance to cluster centroids, assign to nearest cluster, append to inverted list; (3) HNSW's query advantage (2% recall, 3ms latency) may not justify the operational complexity of maintaining a graph-based index under continuous writes; (4) IVF cluster centroids remain stable across insertions (periodic re-clustering needed only when data distribution shifts significantly). The choice is fundamentally about operational sustainability, not peak performance. Opsi B — 2% recall difference is relevant but can often be recovered by increasing ef_search for HNSW or nprobe for IVF without changing the fundamental architecture. Opsi C — RAM is important for cost but can be addressed with instance sizing; it's a linear cost factor, not an architectural constraint. Opsi D — build time matters for disaster recovery but indexes are typically rebuilt rarely; daily operations dominate architectural decisions.

A data engineering team builds an ETL pipeline that generates product embeddings using Amazon SageMaker, stores them in Amazon Aurora PostgreSQL (pgvector), and serves similarity queries to a downstream recommendation API. The pipeline must generate embeddings for 1 million new products weekly, upsert them into the vector store, and ensure the HNSW index remains performant. After 3 months, they notice query latency has increased from 10ms to 80ms. Investigation reveals the HNSW index has become fragmented due to frequent updates. What is the MOST effective maintenance strategy?
  • A. Schedule a weekly REINDEX CONCURRENTLY operation after the embedding upsert pipeline completes. REINDEX CONCURRENTLY rebuilds the HNSW index from scratch without blocking concurrent queries — it builds a new index in the background, then atomically swaps it with the old index. This restores optimal graph connectivity that degrades when nodes are deleted and re-inserted, returning latency to the original 10ms baseline
  • B. Increase the maintenance_work_mem parameter to allow PostgreSQL's autovacuum to rebuild the HNSW index more efficiently
  • C. Switch from HNSW to IVF index type which doesn't suffer from fragmentation during updates
  • D. Increase the ef_search parameter from the original value to compensate for index quality degradation without rebuilding
Jawaban Benar: A
REINDEX CONCURRENTLY is the correct maintenance pattern for HNSW indexes under update workloads: (1) HNSW graph quality degrades when nodes are updated (deleted + re-inserted) because the new node's connections may be suboptimal — it connects to current neighbors that may not be the globally best connections; (2) REINDEX rebuilds the entire graph from scratch, re-establishing optimal connectivity across all nodes; (3) CONCURRENTLY ensures the rebuild happens in the background without blocking the recommendation API's read queries; (4) weekly scheduling aligns with the embedding pipeline cadence — rebuild after new vectors are loaded. The pattern: upsert 1M vectors → REINDEX CONCURRENTLY → latency returns to 10ms baseline. Opsi B — autovacuum handles dead tuple cleanup (standard PostgreSQL maintenance) but does not rebuild or optimize HNSW graph connectivity; maintenance_work_mem doesn't affect index quality. Opsi C — switching to IVF is unnecessary; IVF does avoid graph fragmentation but has lower recall characteristics; the proper solution is maintaining HNSW quality through periodic rebuilds. Opsi D — increasing ef_search partially compensates (explores more candidates to find correct neighbors despite poor graph connectivity) but doesn't fix the root cause; latency will continue to degrade each week, requiring ever-higher ef_search values — an unsustainable approach.
