Skill 2.1.6: Manage Locks to Prevent Access to Data

Amazon Redshift, Amazon RDS — managing database locks, concurrency control, and preventing data access conflicts

1
A data engineering team runs a nightly ETL pipeline that performs a COPY command to load 500 million rows into a large fact table in Amazon Redshift. During the COPY operation, analysts report that their SELECT queries on the same table hang for 30+ minutes. The team needs to allow concurrent reads during bulk data loads. Which approach BEST resolves the lock contention while maintaining data consistency?
  • A. Use LOCK TABLE with ACCESS SHARE mode before running the COPY command to allow concurrent reads
  • B. Split the 500 million rows into 10 smaller COPY commands of 50 million each to reduce lock duration per operation
  • C. Load data into a staging table first, then use ALTER TABLE APPEND to move rows from the staging table to the target fact table — this operation acquires only a brief exclusive lock at the metadata level rather than holding a write lock throughout the entire load duration
  • D. Increase the WLM concurrency level for the queue handling analyst queries to allow more parallel query slots configured for optimal performance and minimal operational overhead
Jawaban Benar: C
ALTER TABLE APPEND is the ideal solution for minimizing lock contention during bulk loads in Redshift. The COPY command into the staging table doesn't affect the production fact table at all — analysts can query the fact table freely. When ALTER TABLE APPEND executes, it moves data blocks at the metadata level (pointer swap), requiring only a very brief exclusive lock measured in seconds rather than the minutes/hours a direct COPY into a large table might take.

Opsi A: SALAH. LOCK TABLE with ACCESS SHARE is a read lock that would conflict with the COPY's write lock rather than resolving it; you cannot manually downgrade a write operation's lock requirements.
Opsi B: SALAH. Splitting into smaller COPY commands means 10 separate lock acquisitions; each still blocks readers, and the total blocked time remains similar with gaps between loads still causing intermittent blocking.
Opsi C: BENAR.
Opsi D: SALAH. Increasing WLM concurrency doesn't resolve the fundamental lock conflict; if an exclusive write lock is held, additional query slots will still queue waiting for the lock to release — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

An Amazon RDS PostgreSQL database serves both an OLTP application (frequent single-row updates to an orders table) and a reporting process (long-running aggregate queries on the same table). The reporting queries occasionally fail with "ERROR: canceling statement due to conflict with recovery" or experience significant delays. The DBA identifies that reporting queries are being blocked by row-level locks from OLTP transactions. Which PostgreSQL feature MOST effectively allows reporting queries to run without being blocked by OLTP write locks?
  • A. Create a read replica for reporting workloads and set hot_standby_feedback = on to prevent query cancellations on the replica, allowing long-running read queries to execute against a consistent snapshot without interference from primary write locks
  • B. Change the transaction isolation level to READ UNCOMMITTED for reporting queries to bypass write locks
  • C. Set lock_timeout to 0 for reporting queries so they wait indefinitely for locks to release configured for optimal performance and minimal operational overhead
  • D. Increase shared_buffers on the primary instance to allow more concurrent transactions to hold locks simultaneously
Jawaban Benar: A
A read replica with hot_standby_feedback provides the optimal solution: (1) reporting queries are physically separated from OLTP traffic, eliminating direct lock contention; (2) PostgreSQL's MVCC on the replica provides snapshot isolation — reads see a consistent point-in-time view; (3) hot_standby_feedback = on tells the primary not to vacuum rows that the replica's long-running queries still need, preventing the "conflict with recovery" cancellation errors; (4) the primary's OLTP performance is unaffected.

Opsi A: BENAR.
Opsi B: SALAH. PostgreSQL treats READ UNCOMMITTED identically to READ COMMITTED (dirty reads are not supported in PostgreSQL); this parameter change has no practical effect on lock behavior.
Opsi C: SALAH. Setting lock_timeout to 0 means queries wait forever for locks, which doesn't solve the problem — it makes it worse by creating potentially unbounded waits — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: SALAH. Shared_buffers controls memory for caching data pages, not concurrency or lock behavior; increasing it won't resolve lock contention.

A data pipeline in Amazon Redshift performs a sequence of operations: DELETE rows older than 90 days, INSERT new daily data, then VACUUM to reclaim space. A monitoring dashboard queries the same table every 5 minutes. The team discovers that VACUUM FULL acquires an exclusive lock that blocks all concurrent access for 45 minutes on this 2 TB table. Which strategy minimizes VACUUM lock impact while still maintaining table performance?
  • A. Replace VACUUM FULL with VACUUM DELETE ONLY followed by VACUUM SORT ONLY during a maintenance window. VACUUM DELETE ONLY reclaims space with minimal blocking and can run concurrently with read queries. Schedule VACUUM SORT ONLY (which requires an exclusive lock) during the lowest-traffic maintenance window
  • B. Increase the WLM query timeout threshold to allow dashboard queries to wait until VACUUM completes with VACUUM DELETE ONLY followed by VACUUM SORT ONLY during a maintenance window and can run concurrently with read queries
  • C. Disable automatic VACUUM entirely and rely on Redshift's automatic table optimization to manage sort order and disk reclamation
  • D. Use VACUUM REINDEX instead of VACUUM FULL to avoid table-level locks during the sort operation
Jawaban Benar: A
Splitting VACUUM into DELETE ONLY and SORT ONLY provides granular control: (1) VACUUM DELETE ONLY reclaims disk space from deleted rows and runs with minimal locking — concurrent reads are not blocked; (2) VACUUM SORT ONLY re-sorts unsorted rows and requires an exclusive lock, but scheduling it during maintenance windows minimizes user impact; (3) this approach separates the non-blocking operation (space reclamation) from the blocking operation (sorting), allowing the table to remain accessible for the majority of the time.

Opsi A: BENAR.
Opsi B: SALAH. Increasing timeout doesn't reduce blocking; dashboard queries still wait 45 minutes, appearing frozen to users — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. Disabling VACUUM entirely leads to degraded query performance over time as the table accumulates unsorted regions and unreclaimable space ("ghost rows"); automatic optimization helps but doesn't fully replace explicit maintenance for high-churn tables.
Opsi D: SALAH. VACUUM REINDEX rebuilds interleaved sort key indexes but still requires an exclusive lock and doesn't avoid the locking problem.

A financial services company uses Amazon RDS MySQL with multiple microservices writing to a shared accounts table. During peak trading hours, they experience frequent deadlocks: Service A updates account balances in order (account 101, then 102) while Service B updates in reverse order (account 102, then 101). Both services use explicit BEGIN/COMMIT transactions. Which approach MOST effectively prevents these deadlocks?
  • A. Set innodb_lock_wait_timeout to 1 second so deadlocked transactions fail quickly and can be retried configured for optimal performance and minimal operational overhead
  • B. Enable MySQL's innodb_deadlock_detect and increase innodb_lock_wait_timeout to allow the system to resolve deadlocks automatically
  • C. Change all transactions to use READ COMMITTED isolation level instead of REPEATABLE READ to reduce lock duration
  • D. Enforce a canonical lock ordering across all services — mandate that all transactions acquire row locks in ascending account ID order regardless of which service initiates the transaction, preventing circular wait conditions that cause deadlocks
Jawaban Benar: D
Canonical lock ordering is the definitive solution for preventing deadlocks: deadlocks occur when two transactions acquire locks in opposite orders, creating a circular dependency (A holds 101, waits for 102; B holds 102, waits for 101). By mandating all services lock accounts in ascending order, circular waits become impossible — if Service A holds lock on 101 and needs 102, Service B would also need 101 first before 102, so B waits for A to complete rather than creating a cycle.

Opsi A: SALAH. Reducing lock_wait_timeout makes deadlocked transactions fail faster but doesn't prevent deadlocks; under high trading volume, constant retries create a "thundering herd" problem and reduce throughput — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: SALAH. Innodb_deadlock_detect is enabled by default in MySQL; it detects and automatically rolls back one deadlocked transaction, but this is a reactive measure that wastes work — prevention through lock ordering is far superior to detection and recovery.
Opsi C: SALAH. READ COMMITTED reduces some gap-locking but doesn't prevent the fundamental row-level circular wait pattern described; both isolation levels still acquire exclusive row locks on UPDATE.
Opsi D: BENAR.

An Amazon Redshift data warehouse handles concurrent ETL writes from three different source systems during a 2-hour overnight batch window. Each ETL stream targets different columns of the same denormalized table using UPDATE statements. The team observes that ETL Stream B frequently waits 20+ minutes for locks held by ETL Stream A, extending the batch window beyond its SLA. How should the team configure Redshift Workload Management (WLM) to optimize concurrency for this workload?
  • A. Create separate WLM queues for each ETL stream with concurrency level 1 per queue, and assign each ETL stream to its own queue using query groups. This isolates each stream's resources but does NOT resolve the table-level write lock contention since all streams target the same table
  • B. Redesign the ETL to load each source system into separate staging tables, then merge into the final denormalized table sequentially — eliminating concurrent write contention on the same table entirely
  • C. Set the WLM queue concurrency to 15 and enable short query acceleration (SQA) for all ETL streams configured for optimal performance and minimal operational overhead
  • D. Enable Auto WLM and let Redshift dynamically allocate memory and concurrency based on workload requirements
Jawaban Benar: B
The root cause is concurrent WRITE operations on the same table — WLM queue configuration cannot resolve table-level write locks because Redshift acquires exclusive table-level locks for write operations (INSERT/UPDATE/DELETE) regardless of which queue the query runs in. The solution is to eliminate concurrent writes to the same table: (1) each ETL stream loads into its own staging table (no contention — different tables); (2) after all streams complete, a sequential merge step combines staging data into the final table; (3) total elapsed time often decreases because parallel staging loads + sequential merge is faster than serialized concurrent writes with lock waits.

Opsi A: SALAH. Correctly identifies the problem but explicitly states it doesn't resolve it; separate queues don't prevent table-level write lock conflicts.
Opsi B: BENAR.
Opsi C: SALAH. Higher concurrency and SQA help with many short queries competing for slots, not with table-level write locks blocking concurrent modifications — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: SALAH. Auto WLM optimizes resource allocation but cannot override Redshift's fundamental table-level write locking behavior.

A data engineering team uses Amazon Redshift with serializable isolation level for a financial reconciliation process. The process reads account balances, performs calculations, and writes adjusted balances — all within a single transaction. During month-end close, multiple reconciliation jobs run concurrently on different account groups but occasionally fail with "ERROR: 1023 — Serializable isolation violation on table." What causes this error and how should the team address it?
  • A. The serializable violation occurs because Redshift detects that concurrent transactions accessed overlapping data ranges that could produce different results if executed in a different serial order. Implement application-level retry logic with exponential backoff — when a serialization failure occurs, the transaction is rolled back and can be safely retried since no partial changes persist
  • B. Add LOCK TABLE statements at the beginning of each reconciliation job to pre-acquire exclusive access to the accounts table
  • C. Change the isolation level to READ COMMITTED for all reconciliation jobs to eliminate serializable violations entirely with exponential backoff — when a serialization failure occurs and can be safely retried since no partial changes persist
  • D. Increase the Redshift cluster size to provide more memory for tracking serialization dependencies across concurrent transactions
Jawaban Benar: A
Redshift uses serializable isolation by default. Serialization violations (error 1023) are an expected outcome in high-concurrency environments — they indicate the system detected a potential anomaly where concurrent transactions' results might differ from any serial execution order. The standard handling pattern is: (1) catch the serialization error; (2) retry the entire transaction from the beginning; (3) use exponential backoff to reduce retry storms. Since the failed transaction is fully rolled back, retrying is safe and typically succeeds because the conflicting transaction has completed.

Opsi A: BENAR.
Opsi B: SALAH. LOCK TABLE with exclusive access would prevent violations but serializes ALL concurrent work, defeating parallelism; reconciliation jobs for non-overlapping account groups should run concurrently.
Opsi C: SALAH. Changing to READ COMMITTED would eliminate serialization errors but also removes the consistency guarantees needed for financial reconciliation (phantom reads, non-repeatable reads become possible — unacceptable for balance adjustments) — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: SALAH. Cluster size doesn't affect serialization conflict detection, which is inherent to the isolation level's logical constraints, not memory availability.

An Amazon RDS PostgreSQL instance supports a data pipeline that uses advisory locks to coordinate multiple worker processes. Each worker acquires an advisory lock (pg_advisory_lock) on a partition ID before processing that partition's data. A new deployment doubled the number of workers from 10 to 20, and now some workers experience hangs — they acquire advisory locks but never release them due to occasional worker crashes. What is the MOST robust approach to prevent orphaned advisory locks from blocking subsequent processing?
  • A. Use pg_try_advisory_lock with a timeout and implement a separate cleanup process that detects and releases abandoned locks hourly
  • B. Implement a heartbeat mechanism where each worker periodically confirms its advisory lock is still needed and releases it if processing is complete
  • C. Replace pg_advisory_lock (session-level) with pg_advisory_xact_lock (transaction-level advisory locks). Transaction-level advisory locks are automatically released when the transaction ends — whether by COMMIT, ROLLBACK, or unexpected session termination — eliminating the possibility of orphaned locks from crashed workers
  • D. Increase max_locks_per_transaction to accommodate 20 concurrent workers acquiring advisory locks with pg_advisory_xact_lock (transaction-level advisory locks)
Jawaban Benar: C
Transaction-level advisory locks (pg_advisory_xact_lock) are the definitive solution for preventing orphaned locks: (1) when a worker crashes, its database connection drops, the transaction is automatically rolled back, and all transaction-level advisory locks are released immediately; (2) no cleanup process or heartbeat mechanism is needed — the database handles lock lifecycle automatically; (3) this is PostgreSQL's built-in mechanism for exactly this use case. The key difference: session-level locks (pg_advisory_lock) persist until explicitly released with pg_advisory_unlock OR the session disconnects — if a connection pool reuses the session, the lock remains held indefinitely.

Opsi A: SALAH. Pg_try_advisory_lock returns immediately without blocking but still creates session-level locks; an hourly cleanup adds latency (locks orphaned for up to 59 minutes) and complexity.
Opsi B: SALAH. Heartbeat mechanisms add application complexity and race conditions; if the heartbeat check fails to detect a crashed worker, locks remain orphaned.
Opsi C: BENAR.
Opsi D: SALAH. Max_locks_per_transaction controls the lock table size, not advisory lock behavior; this parameter doesn't address orphaned locks — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A Redshift cluster processes both high-priority real-time dashboard queries and lower-priority batch ETL UPDATE operations. The ETL UPDATEs acquire write locks on dimension tables for 10-15 minutes each. Dashboard queries that need to read these dimension tables are queued behind the write locks, causing dashboard SLA violations. The team cannot change ETL timing. Which Redshift approach BEST ensures dashboard queries are not blocked by ETL write locks?
  • A. Implement table-level read locks using LOCK TABLE IN SHARE MODE before dashboard queries execute to prevent concurrent writes
  • B. Create a secondary Redshift cluster using data sharing specifically for dashboard queries, completely isolating read workloads from ETL write contention
  • C. Use Redshift's snapshot isolation behavior: in Redshift, SELECT queries read from a snapshot of committed data and are NOT blocked by concurrent write locks. If dashboards are experiencing delays, the actual issue is likely WLM queue configuration or resource contention, not write locks blocking reads
  • D. Configure WLM with a high-priority queue for dashboard queries with queue-hopping rules that preempt ETL queries when dashboards are waiting and are NOT blocked by concurrent write locks
Jawaban Benar: C
This is a critical Redshift behavior to understand: Redshift uses MVCC (Multi-Version Concurrency Control) where SELECT queries read from a consistent snapshot of committed data. Readers do NOT block writers and writers do NOT block readers. If dashboard SELECT queries appear "blocked," the actual cause is typically: (1) WLM queue slots fully consumed by ETL queries (dashboards queued waiting for a slot, not a lock); (2) cluster resource exhaustion (CPU/memory) from heavy ETL reducing resources available for dashboards; (3) DDL operations (ALTER TABLE, DROP) which DO acquire exclusive locks that block reads. The correct investigation is WLM queue configuration and resource allocation, not lock behavior.

Opsi A: SALAH. Manually acquiring SHARE MODE locks would actually CREATE blocking by conflicting with ETL's exclusive locks, making the situation worse.
Opsi B: SALAH. Data sharing provides workload isolation but is an over-engineered solution if the actual problem is WLM queue configuration.
Opsi C: BENAR.
Opsi D: SALAH. WLM priority and queue-hopping help with queue slot contention (which may be the real issue) but the question incorrectly premises that write locks block reads — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A multi-tenant SaaS platform uses Amazon RDS MySQL with tenant data in a shared table (tenant_id column). During a bulk data migration for Tenant A (updating 2 million rows), other tenants experience query timeouts because the migration's long-running transaction holds gap locks in the InnoDB index that span across tenant boundaries when using REPEATABLE READ isolation. Which approach BEST prevents cross-tenant lock interference during bulk operations?
  • A. Use SELECT ... FOR UPDATE SKIP LOCKED to allow other tenants' queries to skip rows locked by the migration
  • B. Execute the bulk migration in smaller batches (e.g., 1,000 rows per transaction with LIMIT) using READ COMMITTED isolation level. READ COMMITTED eliminates gap locks entirely in InnoDB — only the specific rows being updated are locked, preventing lock ranges from spanning into other tenants' data ranges
  • C. Add a unique index on (tenant_id, primary_key) to prevent gap locks from crossing tenant boundaries with LIMIT) using READ COMMITTED isolation level
  • D. Increase innodb_buffer_pool_size to allow MySQL to maintain more concurrent lock structures in memory
Jawaban Benar: B
The combination of batching + READ COMMITTED addresses both root causes: (1) READ COMMITTED isolation eliminates InnoDB gap locks — MySQL only locks the exact rows matching the UPDATE's WHERE clause, not the "gaps" between index values that could span into other tenants' ranges; (2) small batches ensure each transaction holds locks briefly (milliseconds), committing frequently and releasing locks for other tenants. This is the standard pattern for bulk operations in multi-tenant MySQL systems.

Opsi A: SALAH. SKIP LOCKED is useful for queue-like processing where skipping rows is acceptable, but other tenants' regular queries (e.g., SELECT * WHERE tenant_id = 'B') need ALL their rows, not a subset with some skipped.
Opsi B: BENAR.
Opsi C: SALAH. A composite index on (tenant_id, pk) might reduce gap lock ranges but doesn't eliminate them under REPEATABLE READ; gap locks still apply within the index structure for range scans — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: SALAH. Buffer_pool_size affects data caching, not lock behavior; lock structures use separate memory regardless of buffer pool configuration.

A data engineering team operates a Redshift cluster where a nightly ETL job performs DROP TABLE followed by CREATE TABLE AS SELECT (CTAS) to rebuild a large aggregation table. During the brief moment between DROP and CTAS completion, dashboard queries fail with "relation does not exist" errors. The team needs zero-downtime table rebuilds. Which technique provides atomic table replacement without any window where the table is unavailable?
  • A. Add error handling in dashboard queries to retry with exponential backoff when the table is temporarily unavailable
  • B. Implement a blue-green table strategy using Redshift data sharing between two schemas configured for optimal performance and minimal operational overhead
  • C. Use CREATE OR REPLACE VIEW to point a view at the new table without dropping the underlying table
  • D. Use a CREATE TABLE AS SELECT to build the new data in a differently-named staging table, then execute ALTER TABLE target RENAME TO target_old followed by ALTER TABLE staging RENAME TO target in immediate succession within the same transaction — the rename operations are metadata-only (near-instantaneous) and queries see either the old or new version, never a missing table
Jawaban Benar: D
The rename-swap pattern provides atomic table replacement: (1) CTAS builds new_target while the existing target table remains fully available for queries; (2) within a single transaction: RENAME target → target_old, RENAME staging → target; (3) these renames are metadata operations (updating system catalog entries) that complete in milliseconds; (4) concurrent queries either see the pre-rename state or post-rename state — never a missing table; (5) after verifying success, DROP target_old to clean up. This is the standard zero-downtime table refresh pattern in Redshift.

Opsi A: SALAH. Retry logic masks the problem rather than solving it; users still experience intermittent errors and dashboard load time increases during the rebuild window.
Opsi B: SALAH. Data sharing between schemas adds unnecessary complexity for what is a single-cluster table refresh operation — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. A view approach works conceptually but introduces an extra layer; direct table renames are simpler and don't require restructuring how dashboards reference the table.
Opsi D: BENAR.
