Skill 1.2.8: Create Data APIs to Make Data Available to Other Systems

Building REST/GraphQL APIs using API Gateway, Lambda, AppSync, and Redshift Data API to expose data products

1
A data engineering team has transformed customer analytics data stored in Amazon Redshift. Internal teams need programmatic access to this data via a REST API. The queries take 5-30 seconds to execute. Which architecture provides the MOST scalable API solution?
  • A. Amazon API Gateway → AWS Lambda → Amazon Redshift Data API (asynchronous), with a second endpoint to retrieve results by query ID
  • B. Amazon API Gateway → Lambda → Redshift via JDBC (synchronous)
  • C. Direct Redshift endpoint exposed to internal teams
  • D. Amazon API Gateway with direct service integration to Redshift
Jawaban Benar: A
Redshift Data API bersifat asynchronous — cocok untuk queries 5-30 detik yang exceeds API Gateway's 29-second timeout. Pattern: POST /query returns queryId immediately, GET /query/{queryId} returns results when ready. Lambda tidak perlu menunggu query selesai (menghindari timeout). Opsi B (JDBC synchronous) — Lambda timeout dan API Gateway timeout menjadi masalah untuk 30-second queries. Connection pooling juga sulit di Lambda. Opsi C (direct Redshift) — security concern dan no rate limiting. Opsi D — tidak ada direct integration API Gateway-Redshift.
2
A company needs to expose their data lake (stored in S3 as Parquet files) as a queryable API for partner companies. Partners should be able to send SQL-like query parameters and receive JSON results. Queries should be authenticated per partner. Which architecture is MOST appropriate?
  • A. API Gateway with API keys per partner → Lambda → Amazon Athena (start query, poll results) → Return JSON
  • B. Give partners direct access to the S3 bucket with IAM roles
  • C. Set up a Redshift Serverless cluster and give JDBC access to partners
  • D. Use AWS AppSync with a DynamoDB data source
Jawaban Benar: A
API Gateway provides authentication (API keys per partner), rate limiting, and usage plans. Lambda orchestrates Athena queries against the data lake (Parquet in S3) dan returns JSON results. Partners interact via REST API without knowing the underlying infrastructure. Opsi B (direct S3) — partners can't run SQL against Parquet directly, security concern. Opsi C (JDBC access) menambah ongoing Redshift costs dan exposes database directly. Opsi D (AppSync + DynamoDB) — data is in S3/Parquet not DynamoDB.
3
A data engineer needs to create a real-time data API that returns the latest IoT sensor readings. Data is ingested via Kinesis and stored in DynamoDB with device_id as the partition key and timestamp as the sort key. The API must return the latest reading for a specific device with single-digit millisecond latency. Which architecture is optimal?
  • A. API Gateway → Lambda → DynamoDB Query (device_id = X, ScanIndexForward = false, Limit = 1)
  • B. API Gateway → Lambda → Athena query on S3 data
  • C. API Gateway → Lambda → Redshift query
  • D. API Gateway → Step Functions → DynamoDB
Jawaban Benar: A
DynamoDB Query dengan partition key (device_id) dan ScanIndexForward=false (reverse sort) with Limit=1 returns the latest reading in single-digit milliseconds. DynamoDB adalah database optimal untuk point lookups dengan consistent low latency. API Gateway → Lambda → DynamoDB adalah pattern standar untuk real-time APIs. Opsi B (Athena) memiliki seconds of latency untuk query startup. Opsi C (Redshift) tidak designed untuk single-record lookups. Opsi D (Step Functions) menambah unnecessary latency.
4
A data team wants to expose their product catalog data through a GraphQL API. The data is stored across DynamoDB (product details), ElastiCache (pricing), and S3 (product images metadata). Multiple frontend teams need different views of the same data. Which AWS service is BEST suited for this multi-source GraphQL API?
  • A. AWS AppSync with multiple data source resolvers (DynamoDB resolver, Lambda resolver for ElastiCache, HTTP resolver for S3 metadata)
  • B. API Gateway with GraphQL proxy to a self-managed GraphQL server on ECS
  • C. Lambda function implementing a GraphQL schema and resolvers
  • D. Amazon API Gateway REST API with multiple endpoints
Jawaban Benar: A
AWS AppSync adalah managed GraphQL service yang natively supports multiple data source resolvers. DynamoDB direct resolver (no Lambda needed), Lambda resolver untuk ElastiCache, dan HTTP data source untuk S3. AppSync handles schema stitching dari multiple sources ke single GraphQL endpoint. Frontend teams query hanya fields yang mereka butuhkan. Opsi B (self-managed) menambah operational overhead. Opsi C (Lambda GraphQL) possible tapi tidak scalable dan membutuhkan semua custom code. Opsi D (REST) bukan GraphQL — each endpoint returns fixed structure.
5
A data API serves aggregated analytics (daily totals, weekly averages) from Redshift. The API receives 10,000 requests per minute but the underlying data only updates once per hour. Many requests ask for the same data. How should the API be optimized to reduce Redshift load?
  • A. Enable API Gateway response caching with a TTL of 3600 seconds (1 hour) matching the data refresh interval
  • B. Scale up the Redshift cluster to handle 10,000 queries per minute
  • C. Add a read replica for Redshift
  • D. Rate limit the API to 100 requests per minute
Jawaban Benar: A
API Gateway caching menyajikan cached responses tanpa memanggil backend. Dengan data yang hanya update per jam, TTL 1 jam memastikan cache selalu berisi data terkini. Ini mengurangi Redshift load hingga ~99% (hanya 1 query per unique request per hour). Opsi B (scale Redshift) mahal dan unnecessary jika data static. Opsi C — Redshift tidak memiliki read replicas (ada RA3 data sharing tapi beda konsep). Opsi D (rate limit) mengurangi service availability untuk users.
6
A data engineer needs to create an API that allows other teams to submit data transformation requests (e.g., "aggregate sales by region for Q1 2024") and receive results asynchronously. Results might take 5 minutes to compute. Which API design pattern is MOST appropriate?
  • A. Asynchronous request-reply pattern: POST /jobs returns jobId immediately, GET /jobs/{jobId} returns status/results. Use Step Functions to orchestrate the long-running computation
  • B. Synchronous API that holds the connection for 5 minutes until results are ready
  • C. WebSocket API that pushes results when ready
  • D. Batch API that processes all requests once per day
Jawaban Benar: A
Asynchronous request-reply pattern is ideal for long-running operations. Client receives immediate acknowledgment (jobId), then polls for status. API Gateway timeout is 29 seconds, so synchronous would fail. Step Functions orchestrates: receive request → run query → store results → mark complete. Opsi B (synchronous 5 min) impossible — API Gateway has 29s timeout. Opsi C (WebSocket) valid alternative tapi more complex for client implementation. Opsi D (daily batch) tidak on-demand.
7
A company exposes a data API that returns customer transaction history. The API must support pagination for large result sets (thousands of transactions per customer). The data is stored in DynamoDB. Which pagination strategy is CORRECT for this DynamoDB-backed API?
  • A. Use cursor-based pagination with DynamoDB's LastEvaluatedKey as the cursor token, passed as an opaque nextToken parameter in the API response
  • B. Use offset-based pagination (page=2&limit=50) with DynamoDB Scan
  • C. Return all results in a single API response regardless of size
  • D. Use random access pagination with DynamoDB BatchGetItem
Jawaban Benar: A
DynamoDB natively supports cursor-based pagination via LastEvaluatedKey. Ketika Query/Scan returns partial results, LastEvaluatedKey menunjukkan posisi terakhir. Ini di-encode sebagai opaque nextToken untuk client. Client mengirim nextToken pada request berikutnya. Ini efficient — DynamoDB langsung melompat ke posisi yang benar. Opsi B (offset) — DynamoDB tidak support OFFSET; Scan harus membaca semua records sampai offset yang mahal. Opsi C (all results) — response size limit dan slow. Opsi D (BatchGetItem) membutuhkan knowing all keys upfront.
8
A data API must be accessible by external partner companies over the internet. The company requires: (1) partner-specific rate limiting, (2) API key authentication, (3) usage metering for billing. Which API Gateway feature set satisfies ALL three requirements?
  • A. API Gateway Usage Plans with API Keys — provides per-partner rate limits, throttling, API key validation, and usage tracking for metering/billing
  • B. API Gateway Lambda authorizer with custom rate limiting logic
  • C. AWS WAF with rate-based rules attached to API Gateway
  • D. IAM authentication with resource-based policies
Jawaban Benar: A
Usage Plans provide all three: (1) Rate limit dan burst limit per plan (assignable per partner), (2) API keys for authentication dan partner identification, (3) Usage metering that tracks calls per API key for billing. This is the purpose-built feature for multi-tenant API monetization. Opsi B (Lambda authorizer) provides auth but not built-in rate limiting or metering. Opsi C (WAF) provides rate limiting but not per-partner metering. Opsi D (IAM) not suitable for external partners who don't have AWS accounts.
9
A data engineer builds an API that returns large datasets (up to 50 MB response) from Athena query results. API Gateway has a 10 MB payload limit. How should large responses be handled?
  • A. Generate a pre-signed S3 URL for the result file and return the URL in the API response. Client downloads directly from S3
  • B. Compress the response with gzip to fit within 10 MB
  • C. Split the response across multiple API calls automatically
  • D. Increase the API Gateway payload limit to 50 MB
Jawaban Benar: A
Pre-signed S3 URL pattern: Athena writes results to S3, API generates a time-limited pre-signed URL, client downloads directly from S3. S3 supports unlimited file sizes dan high bandwidth. Ini bypasses API Gateway payload limit entirely. Opsi B (compression) mungkin tidak cukup jika data 50 MB bahkan compressed. Opsi C (split) — API Gateway doesn't auto-split responses. Opsi D — 10 MB adalah hard limit yang tidak bisa diubah.
10
A data engineer creates an API using Amazon API Gateway and Lambda to query DynamoDB. During load testing, the API returns HTTP 429 (Too Many Requests) errors at 5,000 requests per second. The Lambda function and DynamoDB are not throttling. What is causing the 429 errors?
  • A. API Gateway has a default account-level throttle of 10,000 requests per second with a default per-route throttle that may be lower. Request a quota increase or configure stage-level throttling settings
  • B. Lambda concurrency limit is reached
  • C. DynamoDB read capacity is exceeded
  • D. The API Gateway cache is full
Jawaban Benar: A
API Gateway has account-level (10,000 rps default) dan stage/route-level throttling. If method-level throttle is set lower than 5,000, API Gateway returns 429 before reaching Lambda/DynamoDB. The question states Lambda dan DynamoDB are NOT throttling, confirming the bottleneck is at API Gateway level. Solusi: increase throttle limits di stage settings atau request account quota increase. Opsi B/C explicitly stated not throttling. Opsi D (cache full) doesn't cause 429.
