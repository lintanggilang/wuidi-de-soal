A data engineering team has transformed customer analytics data stored in Amazon Redshift. Internal teams need programmatic access to this data via a REST API. The queries take 5-30 seconds to execute. Which architecture provides the MOST scalable API solution?
  • A. Direct Redshift endpoint exposed to internal teams, validating and cleansing each record before delivery and satisfying all of the stated requirements with minimal effort
  • B. Amazon API Gateway → AWS Lambda → Amazon Redshift Data API (asynchronous), with a second endpoint to retrieve results by query ID
  • C. Amazon API Gateway → Lambda → Redshift via JDBC (synchronous) with a second endpoint, transforming records into the required target format
  • D. Amazon API Gateway with direct service integration to Redshift, handling the described workload reliably at scale and applying schema conversion and enrichment inline
Correct Answer: B
Redshift Data API bersifat asynchronous — suitable for queries 5-30 seconds that exceeds API Gateway's 29-second timeout. Pattern: POST /query returns queryId immediately, GET /query/{queryId} returns results when ready. Lambda does not need waits query complete (avoids timeout).

Option A: INCORRECT. Security concern and no rate limiting.
Option B: CORRECT.
Option C: INCORRECT. Lambda timeout and API Gateway timeout becomes problem for 30-second queries — although its description sounds convincing, in a fundamental still not appropriate for requirements this. Connection pooling also difficult in Lambda.
Option D: INCORRECT. Not there is direct integration API Gateway-Redshift.

A company needs to expose their data lake (stored in S3 as Parquet files) as a queryable API for partner companies. Partners should be able to send SQL-like query parameters and receive JSON results. Queries should be authenticated per partner. Which architecture is MOST appropriate?
  • A. Use AWS AppSync with a DynamoDB data source configured for optimal performance and minimal operational overhead
  • B. Give partners direct access to the S3 bucket with IAM roles, integrating natively with the rest of the pipeline
  • C. API Gateway with API keys per partner → Lambda → Amazon Athena (start query, poll results) → Return JSON
  • D. Set up a Redshift Serverless cluster and give JDBC access to partners, handling the described workload reliably at scale
Correct Answer: C
API Gateway provides authentication (API keys per partner), rate limiting, and usage plans. Lambda orchestrates Athena queries against the data lake (Parquet in S3) and returns JSON results. Partners interact via REST API without knowing the underlying infrastructure.

Option A: INCORRECT. Data is in S3/Parquet not DynamoDB — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Partners can't run SQL against Parquet directly, security concern.
Option C: CORRECT.
Option D: INCORRECT. Adds ongoing Redshift costs and exposes database directly.

A data engineer needs to create a real-time data API that returns the latest IoT sensor readings. Data is ingested via Kinesis and stored in DynamoDB with device_id as the partition key and timestamp as the sort key. The API must return the latest reading for a specific device with single-digit millisecond latency. Which architecture is optimal?
  • A. API Gateway → Lambda → DynamoDB Query (device_id = X, ScanIndexForward = false, Limit = 1)
  • B. API Gateway → Step Functions → DynamoDB, delivering records with consistent sub-second latency and minimizing end-to-end processing latency
  • C. API Gateway → Lambda → Redshift query configured for optimal performance and minimal operational overhead
  • D. API Gateway → Lambda → Athena query on S3 data, making the data queryable within seconds of arrival
Correct Answer: A
DynamoDB Query with partition key (device_id) and ScanIndexForward=false (reverse sort) with Limit=1 returns the latest reading in single-digit milliseconds. DynamoDB is database optimal for point lookups with consistent low latency. API Gateway → Lambda → DynamoDB is pattern standard for real-time APIs.

Option A: CORRECT.
Option B: INCORRECT. Adds unnecessary latency.
Option C: INCORRECT. Not designed for single-record lookups — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Has seconds of latency for query startup.

A data team wants to expose their product catalog data through a GraphQL API. The data is stored across DynamoDB (product details), ElastiCache (pricing), and S3 (product images metadata). Multiple frontend teams need different views of the same data. Which AWS service is BEST suited for this multi-source GraphQL API?
  • A. Amazon API Gateway REST API with multiple endpoints for ElastiCache, meeting the latency and throughput goals of the design
  • B. AWS AppSync with multiple data source resolvers (DynamoDB resolver, Lambda resolver for ElastiCache, HTTP resolver for S3 metadata)
  • C. Lambda function implementing a GraphQL schema and resolvers, meeting the latency and throughput goals of the design
  • D. API Gateway with GraphQL proxy to a self-managed GraphQL server on ECS, integrating natively with the rest of the pipeline
Correct Answer: B
AWS AppSync is managed GraphQL service that natively supports multiple data source resolvers. DynamoDB direct resolver (no Lambda needed), Lambda resolver for ElastiCache, and HTTP data source for S3. AppSync handles schema stitching from multiple sources to single GraphQL endpoint. Frontend teams query only fields that mereka butuhkan.

Option A: INCORRECT. Not GraphQL — each endpoint returns fixed structure — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: CORRECT.
Option C: INCORRECT. Possible but not scalable and requires all custom code.
Option D: INCORRECT. Adds operational overhead.

A data API serves aggregated analytics (daily totals, weekly averages) from Redshift. The API receives 10,000 requests per minute but the underlying data only updates once per hour. Many requests ask for the same data. How should the API be optimized to reduce Redshift load?
  • A. Add a read replica for Redshift with a TTL of 3600 seconds (1 hour) matching the data refresh interval
  • B. Rate limit the API to 100 requests per minute, integrating natively with the rest of the pipeline
  • C. Scale up the Redshift cluster to handle 10,000 queries per minute, handling the described workload reliably at scale
  • D. Enable API Gateway response caching with a TTL of 3600 seconds (1 hour) matching the data refresh interval
Correct Answer: D
API Gateway caching serves cached responses without calls backend. By data that only update per hours, TTL 1 hours ensures cache always contains data terkini. This reduces Redshift load up to ~99% (only 1 query per unique request per hour).

Option A: INCORRECT. Redshift not has read replicas (there is RA3 data sharing but beda concept) — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Reduces service availability for users.
Option C: INCORRECT. Expensive and unnecessary if data static.
Option D: CORRECT.

A data engineer needs to create an API that allows other teams to submit data transformation requests (e.g., "aggregate sales by region for Q1 2024") and receive results asynchronously. Results might take 5 minutes to compute. Which API design pattern is MOST appropriate?
  • A. Synchronous API that holds the connection for 5 minutes until results are ready, meeting the latency and throughput goals of the design
  • B. Asynchronous request-reply pattern: POST /jobs returns jobId immediately, GET /jobs/{jobId} returns status/results. Use Step Functions to orchestrate the long-running computation
  • C. Batch API that processes all requests once per day, applying schema conversion and enrichment inline and minimizing end-to-end processing latency
  • D. WebSocket API that pushes results when ready configured for optimal performance and minimal operational overhead, transforming records into the required target format
Correct Answer: B
Asynchronous request-reply pattern is ideal for long-running operations. Client receives immediate acknowledgment (jobId), then polls for status. API Gateway timeout is 29 seconds, so synchronous would fail. Step Functions orchestrates: receive request → run query → store results → mark complete.

Option A: INCORRECT. Impossible — API Gateway has 29s timeout.
Option B: CORRECT.
Option C: INCORRECT. Not on-demand.
Option D: INCORRECT. Valid alternative but more complex for client implementation — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A company exposes a data API that returns customer transaction history. The API must support pagination for large result sets (thousands of transactions per customer). The data is stored in DynamoDB. Which pagination strategy is CORRECT for this DynamoDB-backed API?
  • A. Use random access pagination with DynamoDB BatchGetItem configured for optimal performance and minimal operational overhead, handling the described workload reliably at scale
  • B. Use offset-based pagination (page=2&limit=50) with DynamoDB Scan, satisfying all of the stated requirements with minimal effort and reducing day-to-day operational effort
  • C. Use cursor-based pagination with DynamoDB's LastEvaluatedKey as the cursor token, passed as an opaque nextToken parameter in the API response
  • D. Return all results in a single API response regardless of size, integrating natively with the rest of the pipeline
Correct Answer: C
DynamoDB natively supports cursor-based pagination via LastEvaluatedKey. When Query/Scan returns partial results, LastEvaluatedKey indicates posisi last. This in-encode as opaque nextToken for client. Client sends nextToken on request berikutnya. This efficient — DynamoDB directly melompat to posisi that correct.

Option A: INCORRECT. Requires knowing all keys upfront — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. DynamoDB not support OFFSET; Scan must reads all records until offset that expensive.
Option C: CORRECT.
Option D: INCORRECT. Response size limit and slow.

A data API must be accessible by external partner companies over the internet. The company requires: (1) partner-specific rate limiting, (2) API key authentication, (3) usage metering for billing. Which API Gateway feature set satisfies ALL three requirements?
  • A. API Gateway Lambda authorizer with custom rate limiting logic, handling the described workload reliably at scale and optimizing cost for the described workload
  • B. IAM authentication with resource-based policies, satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline
  • C. API Gateway Usage Plans with API Keys — provides per-partner rate limits, throttling, API key validation, and usage tracking for metering/billing
  • D. AWS WAF with rate-based rules attached to API Gateway and usage tracking for metering/billing for metering/billing, handling the described workload reliably at scale
Correct Answer: C
Usage Plans provide all three: (1) Rate limit and burst limit per plan (assignable per partner), (2) API keys for authentication and partner identification, (3) Usage metering that tracks calls per API key for billing. This is the purpose-built feature for multi-tenant API monetization.

Option A: INCORRECT. Provides auth but not built-in rate limiting or metering.
Option B: INCORRECT. Not suitable for external partners who don't have AWS accounts.
Option C: CORRECT.
Option D: INCORRECT. Provides rate limiting but not per-partner metering — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data engineer builds an API that returns large datasets (up to 50 MB response) from Athena query results. API Gateway has a 10 MB payload limit. How should large responses be handled?
  • A. Generate a pre-signed S3 URL for the result file and return the URL in the API response. Client downloads directly from S3
  • B. Compress the response with gzip to fit within 10 MB, satisfying all of the stated requirements with minimal effort and providing exactly-once processing semantics
  • C. Increase the API Gateway payload limit to 50 MB and return the URL in the API response, handling the described workload reliably at scale
  • D. Split the response across multiple API calls automatically, handling the described workload reliably at scale and integrating natively with the rest of the pipeline
Correct Answer: A
Pre-signed S3 URL pattern: Athena writes results to S3, API generates a time-limited pre-signed URL, client downloads directly from S3. S3 supports unlimited file sizes and high bandwidth. This bypasses API Gateway payload limit entirely.

Option A: CORRECT.
Option B: INCORRECT. May not quite if data 50 MB even compressed.
Option C: INCORRECT. 10 MB is hard limit that cannot is changed — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. API Gateway doesn't auto-split responses.

A data engineer creates an API using Amazon API Gateway and Lambda to query DynamoDB. During load testing, the API returns HTTP 429 (Too Many Requests) errors at 5,000 requests per second. The Lambda function and DynamoDB are not throttling. What is causing the 429 errors?
  • A. Lambda concurrency limit is reached, satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and handling the described workload reliably at scale
  • B. The API Gateway cache is full, handling the described workload reliably at scale and meeting the latency and throughput goals of the design and integrating natively with the rest of the pipeline
  • C. DynamoDB read capacity is exceeded with a default per-route throttle that may be lower, meeting the latency and throughput goals of the design and integrating natively with the rest of the pipeline
  • D. API Gateway has a default account-level throttle of 10,000 requests per second with a default per-route throttle that may be lower. Request a quota increase or configure stage-level throttling settings
Correct Answer: D
API Gateway has account-level (10,000 rps default) and stage/route-level throttling. If method-level throttle is set lower than 5,000, API Gateway returns 429 before reaching Lambda/DynamoDB. The question states Lambda and DynamoDB are NOT throttling, confirming the bottleneck is at API Gateway level. Solution: increase throttle limits in stage settings or request account quota increase.

Option A: INCORRECT. /C explicitly stated not throttling.
Option B: INCORRECT. Doesn't cause 429.
Option C: INCORRECT. Although it sounds convincing, it is still not the correct answer for this scenario.
Option D: CORRECT.
