#Glue#Redshift#S3#CloudWatch#IAM#Spark
A data engineer notices that an AWS Glue ETL job that previously completed in 45 minutes is now taking over 3 hours. The job reads from S3, performs joins and aggregations, and writes to Amazon Redshift. CloudWatch metrics show that the Glue job's DPU utilization is consistently at 100%. The Spark UI reveals significant shuffle spill to disk. What is the MOST likely root cause and solution?
  • A. The S3 source files are too small, creating excessive task overhead. Consolidate files using Glue's groupFiles option, transforming records into the required target format
  • B. Data skew in the join key is causing uneven partition distribution. Repartition the data using a salted key before the join operation.
  • C. The Redshift COPY command is bottlenecked by WLM queue concurrency. Increase WLM slots for the loading queue, handling the described workload reliably at scale
  • D. The Glue job's IAM role has been throttled by AWS, reducing S3 read throughput, with partition-level ordering and dedicated throughput
Jawaban Benar: B
100% DPU utilization combined with shuffle spill to disk strongly indicates data skew during join/aggregation operations. When one partition key has disproportionately more records, a single executor handles most of the work while others sit idle, and the oversized partition spills to disk. Salting the join key distributes skewed data evenly across partitions. Option B: Small files cause high task scheduling overhead but would show low DPU utilization with many short tasks, not sustained 100% with disk spill. Option C: Redshift write issues wouldn't cause Glue-side shuffle spill. Option D: IAM role throttling is not a standard AWS behavior for S3 access.

Opsi A: SALAH.
Opsi B: BENAR.
Opsi C: SALAH.
Opsi D: SALAH. Meskipun terdengar meyakinkan, tetap tidak tepat untuk skenario ini.

#Redshift
A Redshift cluster is experiencing slow query performance for a critical dashboard query. The EXPLAIN plan shows a "DS_DIST_ALL" distribution for a large fact table join. The query joins a 500 million row fact table with a 10,000 row dimension table. Both tables use EVEN distribution style. What change would MOST improve this query's performance?
  • A. Change the fact table's distribution style to ALL to ensure all data is available on every node, scaling horizontally as ingestion throughput keeps growing
  • B. Add a sort key on the join column for both tables to speed up the join operation, absorbing sudden traffic spikes without throttling
  • C. Change the dimension table's distribution style to ALL so it's replicated to every node, eliminating the redistribution of the large fact table.
  • D. Increase the number of nodes in the Redshift cluster to distribute the workload. configured for optimal performance and minimal operational overhead
Jawaban Benar: C
When a small dimension table (10,000 rows) is joined with a large fact table, using ALL distribution on the dimension table replicates it to every node. This eliminates network redistribution of the 500M row fact table during the join, as each node can join its local fact data with the local copy of the dimension table. Option B: Distributing a 500M row table with ALL style would waste enormous storage and is impractical. Option C: Sort keys help with range-restricted scans and merge joins but don't eliminate redistribution overhead. Option D: Adding nodes helps with overall capacity but doesn't fix the fundamental redistribution inefficiency.

Opsi A: SALAH.
Opsi B: SALAH.
Opsi C: BENAR.

#EMR#Spark
An EMR cluster running a Spark job is experiencing long garbage collection pauses that significantly degrade performance. The YARN ResourceManager shows that executor memory is frequently at capacity. The job processes a 2 TB dataset with complex transformations. Which tuning approach MOST effectively addresses this issue?
  • A. Switch from DataFrame API to RDD API to have more control over memory management, with -XX:+UseG1GC for the executor JVM options and set spark
  • B. Increase spark.executor.memory and set spark.memory.fraction to 0.8 to allocate more heap space. Configure G1GC with -XX:+UseG1GC for the executor JVM options.
  • C. Increase spark.sql.shuffle.partitions to 2000 to reduce the data size per partition, validating and cleansing each record before delivery and minimizing end-to-end processing latency
  • D. Reduce the number of executors and increase cores per executor to minimize GC overhead across JVMs, applying schema conversion and enrichment inline
Jawaban Benar: B
Long GC pauses with memory at capacity indicate that executors need more heap space. Increasing spark.executor.memory provides more room, raising spark.memory.fraction allocates more heap to Spark operations (vs. user code), and G1GC is optimized for large heaps with predictable pause times. Option B: Fewer executors with more cores reduces parallelism and doesn't address the memory pressure issue. Option C: More shuffle partitions helps with shuffle-related memory pressure but doesn't address general executor memory issues during transformations. Option D: RDD API provides lower-level control but doesn't reduce memory consumption; it often uses more memory due to lack of Catalyst optimization.

Opsi A: SALAH. Meskipun terdengar meyakinkan, tetap tidak tepat untuk skenario ini.
Opsi B: BENAR.

#Kinesis#EC2#CloudWatch
A real-time data pipeline uses Kinesis Data Streams. The CloudWatch metric GetRecords.IteratorAgeMilliseconds has been steadily increasing over the past hour, indicating growing consumer lag. The stream has 10 shards, and the consumer application uses KCL with 5 EC2 instances. The IncomingBytes metric shows the stream is receiving 8 MB/s. What is the MOST likely cause of the increasing lag?
  • A. The read throughput limit is exceeded. With standard consumers sharing 2 MB/s per shard read capacity, the total read capacity is 20 MB/s which should be sufficient.
  • B. The Kinesis Data Stream retention period is too short, causing data expiration before consumers read it, with partition-level ordering and dedicated throughput, minimizing end-to-end processing latency
  • C. The stream's write capacity is exhausted. Each shard supports 1 MB/s write, so 10 shards handle 10 MB/s which is close to the 8 MB/s incoming rate.
  • D. The consumer processing logic is slower than the incoming data rate. The 5 KCL workers cannot process 8 MB/s of data fast enough across 10 shards.
Jawaban Benar: D
Steadily increasing IteratorAge means consumers are falling behind the data production rate. Since the stream has capacity (10 shards × 1 MB/s write = 10 MB/s > 8 MB/s incoming), and read capacity (10 shards × 2 MB/s = 20 MB/s) is sufficient, the bottleneck is in consumer processing speed. The 5 KCL workers processing 10 shards means each worker handles 2 shards; if processing logic (transformations, external API calls) takes too long per record, lag accumulates. Option A: Write capacity isn't exhausted (8 MB/s < 10 MB/s limit). Option C: Read capacity (20 MB/s) far exceeds the incoming rate. Option D: Retention period affects data availability but doesn't cause increasing iterator age; that's caused by slow consumption.

Opsi A: SALAH.
Opsi B: SALAH. Meskipun terdengar meyakinkan, tetap tidak tepat untuk skenario ini.
Opsi C: SALAH.
Opsi D: BENAR.

A DynamoDB table used in a data pipeline is experiencing intermittent ProvisionedThroughputExceededException errors during peak hours. The table uses provisioned capacity with 5,000 WCU. CloudWatch shows that consumed WCU averages 3,000 but has brief spikes to 8,000. The application uses batch writes with items distributed across many partition keys. Which solution addresses the throttling with MINIMAL cost increase?
  • A. Enable DynamoDB Auto Scaling with a target utilization of 70% and increase the maximum capacity to 10,000 WCU.
  • B. Increase provisioned WCU to 10,000 to handle peak spikes, with a target utilization of 70% and increase the maximum capacity to 10,000 WCU
  • C. Implement a write buffer using SQS to smooth out traffic spikes before writing to DynamoDB.
  • D. Switch to on-demand capacity mode to automatically handle traffic spikes without pre-provisioning, scaling elastically to millions of events per second
Jawaban Benar: A
DynamoDB Auto Scaling adjusts provisioned capacity based on actual consumption patterns. With a 70% target utilization and max 10,000 WCU, it scales up during peak spikes and scales down during low traffic, providing the minimal cost increase while handling bursts. Option A: On-demand mode charges per-request and at the described usage pattern (average 3,000 WCU) would be significantly more expensive than provisioned with auto scaling. Option C: Static 10,000 WCU means paying for peak capacity 24/7, which is wasteful during off-peak hours. Option D: SQS buffering adds architectural complexity and latency, and is over-engineered when auto scaling solves the problem natively.

Opsi A: BENAR.

#Glue#S3#Spark
A data engineer is troubleshooting a slow AWS Glue job. The job reads 500,000 small JSON files (average 50 KB each) from S3. The Spark UI shows that the job creates 500,000 tasks in the first stage, each processing a single file. The stage takes 2 hours despite low DPU utilization. What is the PRIMARY performance issue and how should it be resolved?
  • A. The DPU count is too low. Increase MaxCapacity to allocate more workers for parallel file reading, meeting the latency and throughput goals of the design
  • B. S3 request throttling is limiting file read performance. Add random prefixes to the file keys. configured for optimal performance and minimal operational overhead
  • C. The small file problem is causing excessive task scheduling overhead. Use Glue's groupFiles and groupSize parameters to combine multiple files into single tasks.
  • D. The JSON parsing is slow. Convert source files to Parquet format before running the Glue job, handling the described workload reliably at scale
Jawaban Benar: C
The small file problem (500,000 files × 50 KB = ~25 GB total) creates 500,000 Spark tasks with high scheduling overhead. Each task has fixed overhead (launch, S3 connection, result reporting) that dominates the actual processing time. Glue's groupFiles parameter combines multiple small files into single tasks, dramatically reducing task count and overhead. Option B: Converting to Parquet helps with read performance but doesn't address the task count issue; you'd still have 500,000 Parquet files. Option C: More DPUs won't help because the bottleneck is task scheduling overhead, not compute capacity (evidenced by low DPU utilization). Option D: S3 prefix throttling occurs at >5,500 GET/s per prefix; the issue here is Spark task overhead, not S3 throttling.

Opsi A: SALAH.
Opsi B: SALAH. Meskipun terdengar meyakinkan, tetap tidak tepat untuk skenario ini.
Opsi C: BENAR.
Opsi D: SALAH.

A Redshift cluster experiences severe performance degradation every Monday morning when multiple analytics queries compete with the daily ETL load process. The ETL load uses COPY commands that consume significant cluster resources. Queries that normally complete in seconds are taking minutes. Which Redshift feature BEST addresses this contention?
  • A. Configure Workload Management (WLM) with separate queues for ETL and analytics workloads. Assign higher memory allocation and concurrency limits to the analytics queue during business hours.
  • B. Enable concurrency scaling to automatically add temporary cluster capacity when queues are backed up, with separate queues for ETL and analytics workloads, applying schema conversion and enrichment inline
  • C. Increase the cluster size by adding more nodes to handle both workloads simultaneously, handling the described workload reliably at scale and transforming records into the required target format
  • D. Schedule the ETL load to run during off-peak hours (e.g., 3 AM) to avoid contention with analytics queries, validating and cleansing each record before delivery
Jawaban Benar: A
WLM (Workload Management) allows creating separate queues with dedicated memory and concurrency slots for different workload types. Assigning ETL to a limited-concurrency queue prevents it from consuming all cluster resources, while the analytics queue maintains guaranteed resources for user queries. Option B: Concurrency scaling adds capacity for read queries in the queue but doesn't help with COPY command resource contention on the main cluster. Option C: Adding nodes increases total capacity but doesn't prevent one workload from starving the other without WLM. Option D: Rescheduling avoids the immediate problem but doesn't solve the underlying resource contention issue and may not be feasible for all ETL schedules.

Opsi A: BENAR.

A data engineer notices that an Amazon Kinesis Data Analytics (Apache Flink) application has increasing backpressure metrics. The application reads from a Kinesis stream, performs windowed aggregations, and writes to S3. The operator metrics show that the sink operator has high busy time while the source and transformation operators have low utilization. What is the MOST likely bottleneck?
  • A. The Kinesis source is not reading fast enough, causing backpressure that propagates to the sink, satisfying all of the stated requirements with minimal effort and providing exactly-once processing semantics
  • B. The Flink application needs more Kinesis Processing Units (KPUs) for overall throughput, with parallel processing and horizontal scaling capabilities, transforming records into the required target format
  • C. The S3 sink is the bottleneck due to small file writes or high-latency put operations. Increasing the sink parallelism or buffering more data before flushing would help.
  • D. The windowed aggregation requires more memory allocation for state management, handling the described workload reliably at scale and integrating natively with the rest of the pipeline
Jawaban Benar: C
High busy time on the sink operator with low utilization on source and transformation operators clearly indicates the sink is the bottleneck. In Flink, backpressure propagates upstream from the slowest operator. S3 writes can be slow due to small file overhead or high latency per PUT. Solutions include increasing sink parallelism, batching more records before flush, or using a faster intermediate sink. Option B: Low source utilization contradicts this; if the source were slow, it wouldn't show backpressure. Option C: Memory issues in aggregation would show high busy time on the transformation operator, not the sink. Option D: More KPUs provide more parallelism overall but don't address the specific sink bottleneck identified by the metrics.

Opsi A: SALAH.

#DynamoDB
A data pipeline writes processed data to DynamoDB. During performance testing, the team observes that writes are being throttled despite the table having 10,000 provisioned WCU and average consumed capacity of only 4,000 WCU. The table has a composite primary key (customer_id as partition key, timestamp as sort key). Investigation reveals that 80% of writes are for 5 specific customer IDs. What explains this behavior?
  • A. DynamoDB batch writes are limited to 25 items, causing artificial throttling when more items are sent per batch, with partition-level ordering and dedicated throughput
  • B. The sort key (timestamp) is causing write conflicts when multiple records have the same timestamp for the same customer, handling the described workload reliably at scale
  • C. The table's provisioned capacity has not been fully allocated yet due to the recent capacity increase taking time to propagate, handling the described workload reliably at scale
  • D. Hot partition key problem. DynamoDB distributes WCU across physical partitions, and the 5 hot customer_ids are concentrated on fewer partitions that exceed their per-partition throughput limit.
Jawaban Benar: D
DynamoDB distributes provisioned capacity across partitions based on partition key values. When 80% of writes target only 5 customer_ids, those partitions receive disproportionate traffic that exceeds their individual partition limit (typically 1,000 WCU per partition), causing throttling even though total table capacity is underutilized. This is the classic hot partition anti-pattern. Option B: Sort key conflicts would cause conditional check failures, not throughput throttling. Option C: DynamoDB capacity changes take effect immediately (within minutes for increases). Option D: Batch write limits cause validation errors, not throttling exceptions.

Opsi A: SALAH. Meskipun terdengar meyakinkan, tetap tidak tepat untuk skenario ini.
Opsi B: SALAH.
Opsi C: SALAH.
Opsi D: BENAR.

  • B. Glue is always more expensive than EMR for the same workload because of the managed service premium, with no cluster management overhead, applying schema conversion and enrichment inline and meeting the latency and throughput goals of the design and keeping steady-state operating costs low

Option B: This is a blanket statement that ignores operational costs and use-case specifics. Option D: Glue doesn't use standard EC2 instances directly; its pricing model is different, and operational costs are a significant factor.
