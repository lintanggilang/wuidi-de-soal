Concepts of distributed data processing: MapReduce, Spark architecture, data partitioning, shuffles, and fault tolerance

A data engineering team runs an EMR cluster with Hadoop MapReduce to process 10TB of web server logs daily. The MapReduce job counts unique visitors per page. The Map phase emits (page_url, visitor_id) pairs, and the Reduce phase counts distinct visitor_ids per page_url. The job takes 4 hours and the Reduce phase accounts for 80% of the runtime due to data skew — one page receives 90% of all traffic. Which optimization MOST reduces the processing time?
  • A. Increase the number of Reduce tasks from the default to 500 configured for optimal performance and minimal operational overhead
  • B. Implement a combiner function that performs partial aggregation on each Mapper before the shuffle phase. Use a salted key approach: append a random suffix to the hot page_url key during Map (e.g., page_url_0, page_url_1), distribute the Reduce work across multiple reducers, then add a second Reduce stage to merge the partial results
  • C. Add more Map tasks by splitting input into smaller HDFS blocks
  • D. Sort the input data by page_url before running the MapReduce job
Jawaban Benar: B
Data skew (one key receiving 90% of data) causes a single reducer to be overwhelmed while others sit idle. Salted keys distribute the hot key across multiple reducers: page_url becomes page_url_0 through page_url_N, spreading the load evenly. A combiner reduces data transferred during shuffle (less network I/O). The second-stage reduce merges partial counts. This transforms a 4-hour skewed job into a balanced ~1-hour job.

Opsi A: SALAH. Increasing reducer count doesn't help when one key dominates; that key still goes to one reducer regardless of total count — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: BENAR.
Opsi C: SALAH. More map tasks don't address the reduce-phase bottleneck.
Opsi D: SALAH. Pre-sorting doesn't change the fundamental data distribution problem in the reduce phase.
2
A Spark application running on EMR processes a 2TB dataset. The Spark UI shows that a groupByKey operation generates 500GB of shuffle data, causing executor memory errors and disk spill. The operation groups customer_id values to compute aggregated purchase statistics. Which Spark operation MOST effectively reduces shuffle data volume?
  • A. Increase executor memory from 4GB to 16GB to handle the shuffle data
  • B. Increase spark.sql.shuffle.partitions to 2000 to distribute shuffle data across more partitions
  • C. Replace groupByKey with reduceByKey or aggregateByKey, which performs map-side (local) aggregation before the shuffle. Instead of shuffling all individual records to reducers, each executor first combines records locally, then shuffles only the aggregated results — dramatically reducing shuffle data from 500GB to a fraction of that size
  • D. Add .cache() before the groupByKey to store the dataset in memory with reduceByKey or aggregateByKey
Jawaban Benar: C
groupByKey shuffles ALL records for each key across the network, then aggregates at the reducer. reduceByKey/aggregateByKey performs partial aggregation on each executor FIRST (map-side combine), then shuffles only the partial results. For aggregations like sum/count/average, this reduces shuffle data by orders of magnitude. Example: 1 million records per customer_id shuffled (groupByKey) vs. one partial aggregate per customer_id per executor shuffled (reduceByKey).

Opsi A: SALAH. More memory delays the OOM but doesn't reduce the fundamental amount of data being shuffled.
Opsi B: SALAH. More partitions distribute the same 500GB across more tasks but don't reduce total shuffle volume.
Opsi C: BENAR.
Opsi D: SALAH. Caching stores the input data in memory but doesn't affect the shuffle operation behavior — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
3
A Spark application on EMR has a driver (master) node and 20 executor nodes. During execution, 2 executor nodes fail due to hardware issues. The application is processing a critical daily ETL batch that must complete successfully. How does Spark handle this failure, and what architectural feature enables recovery?
  • A. Spark replicates all data across three nodes (like HDFS), so when two nodes fail, the data is still available on the third copy
  • B. The entire Spark application fails and must be restarted from the beginning by the user with partition-level ordering and dedicated throughput
  • C. Spark writes checkpoints to disk after every transformation, and recovery reads from the last checkpoint
  • D. Spark uses its lineage-based fault tolerance: each RDD/DataFrame records the sequence of transformations (lineage) used to create it. When executors fail, Spark recomputes only the lost partitions by replaying the lineage on other available executors. The driver reassigns the failed tasks to healthy executors, and the overall job continues without restarting from the beginning
Jawaban Benar: D
Spark's lineage (DAG of transformations) is its primary fault tolerance mechanism. Unlike systems that replicate data (expensive for large datasets), Spark records HOW to recreate data from its source. When executor 5 fails, Spark knows that partition 5's data was created by: read S3 file X → filter → map → ... and reruns these transformations on another executor. Only lost partitions are recomputed, not the entire dataset. The driver coordinates task reassignment automatically.

Opsi A: SALAH. Spark doesn't replicate intermediate data like HDFS replicates blocks; it uses lineage instead (more memory-efficient).
Opsi B: SALAH. Spark automatically handles executor failures; only driver failure requires restart (unless in cluster mode with supervision) — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. Checkpointing is optional and used for specific scenarios (long lineages, streaming); it's not the default mechanism.
Opsi D: BENAR.
4
A data engineer processes a 5TB dataset on EMR Spark with 100 executors. The dataset is stored in S3 as Parquet files and contains a timestamp column used in most WHERE clauses. Currently, the data is not partitioned, and every query reads all 5TB. The engineer needs to optimize the data layout for query performance. Which partitioning strategy is MOST effective?
  • A. Create one partition per record (5 billion partitions) for maximum parallelism
  • B. Store all data in a single large Parquet file to minimize S3 API calls
  • C. Partition the data by date (year/month/day) derived from the timestamp column. When Spark reads with a filter on the timestamp, partition pruning eliminates reading irrelevant partitions entirely. For a query filtering one day of data, Spark reads ~14GB (1/365th) instead of 5TB. Store as Parquet with the partition scheme: s3://bucket/data/year=2024/month=01/day=15/
  • D. Partition by a random hash to ensure all partitions are equal size with a filter on the timestamp for a query filtering one day of data
Jawaban Benar: C
Partitioning by date aligns with the query access pattern (WHERE timestamp = ...). Spark's partition pruning reads only the relevant directory, dramatically reducing I/O. For 5TB over one year, a daily query reads ~14GB instead of 5TB — a 365x improvement. Parquet's columnar format combined with partition pruning means Spark reads only the columns needed from the relevant date partitions. Hive-style partitioning (key=value directories) enables automatic pruning.

Opsi A: SALAH. Billions of tiny partitions create excessive S3 LIST API calls and file opening overhead (small file problem).
Opsi B: SALAH. One file prevents any parallelism; Spark can't split a single Parquet file efficiently across 100 executors.
Opsi C: BENAR.
Opsi D: SALAH. Random hash partitioning distributes data evenly but offers ZERO pruning benefit because queries can't determine which partitions contain relevant dates — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
5
An EMR Spark job joins a 500GB orders table with a 200GB customers table on customer_id. The Spark UI shows a massive shuffle stage where 700GB of data is exchanged between executors. Both tables are already partitioned by customer_id in S3 with the same number of partitions. The engineer wants to leverage this pre-partitioned layout to eliminate the shuffle. Which Spark technique achieves this?
  • A. Broadcast the 200GB customers table to all executors using broadcast join
  • B. Increase the number of shuffle partitions to 4000 to spread the 700GB across more tasks
  • C. Repartition both DataFrames by customer_id immediately before the join with the same number of buckets
  • D. Use bucketing: write both tables as bucketed tables on customer_id with the same number of buckets. When Spark detects that both sides of a join are bucketed on the join key with matching bucket counts, it performs a sort-merge join WITHOUT shuffle — each executor joins its local bucket pair directly since matching customer_ids are co-located
Jawaban Benar: D
Bucketing pre-sorts and co-locates data with the same key in the same file (bucket). When both join sides are bucketed on the join key with equal bucket counts, Spark knows that all records for a given customer_id already reside in the same numbered bucket on both tables. It joins bucket 1 of orders with bucket 1 of customers locally — zero shuffle. This is a shuffle-free sort-merge join.

Opsi A: SALAH. Broadcasting 200GB exceeds executor memory limits (default broadcast threshold is 10MB); it would crash executors.
Opsi B: SALAH. More shuffle partitions distribute the work but still shuffle 700GB of data across the network.
Opsi C: SALAH. Repartitioning triggers a full shuffle of both tables (700GB), which is exactly the problem being solved — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: BENAR.
6
A data engineering team designs a distributed data processing system on AWS that must handle both real-time analytics queries (requiring immediate consistency) and batch processing (requiring high availability). According to the CAP theorem, they must make trade-offs. Their streaming pipeline uses Kinesis for ingestion and needs to serve real-time dashboards while remaining available during network partitions between Availability Zones. Which architectural trade-off is MOST appropriate?
  • A. Ignore CAP theorem since AWS managed services handle these trade-offs automatically
  • B. Choose AP (Availability + Partition tolerance) for the streaming layer: use DynamoDB with eventual consistency reads for the real-time dashboards, accepting that during network partitions, dashboards may show slightly stale data (seconds behind). For the batch analytics layer requiring accuracy, use Amazon Redshift with strong consistency for the source-of-truth reporting
  • C. Choose CA (Consistency + Availability) by deploying everything in a single AZ to avoid network partitions with eventual consistency reads for the real-time dashboards
  • D. Choose CP (Consistency + Partition tolerance) for all systems, accepting that dashboards may become unavailable during AZ issues
Jawaban Benar: B
CAP theorem states that during a network partition, a distributed system must choose between consistency and availability. For real-time dashboards, availability matters most (users see dashboards, even with slightly stale data). DynamoDB with eventual consistency provides this — reads may be milliseconds behind but the system remains available during AZ failures. For financial reporting, consistency matters more — Redshift provides this for batch queries. This dual-approach optimizes each layer for its requirements.

Opsi A: SALAH. While AWS manages much complexity, architects must still choose consistency models (strong vs eventual reads).
Opsi B: BENAR.
Opsi C: SALAH. CA is impossible in distributed systems; network partitions are inevitable in multi-AZ deployments, and single-AZ eliminates fault tolerance — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: SALAH. CP sacrifices availability; dashboards going down during AZ issues is unacceptable for real-time monitoring use cases.
7
A Spark job on EMR joins a large fact table (2TB, 10 billion rows) with a small dimension table (50MB, 100K rows). The Spark execution plan shows a SortMergeJoin that shuffles both tables. The engineer knows the dimension table is small enough to avoid shuffling the fact table. Which Spark mechanism eliminates the expensive shuffle of the large table?
  • A. Cache both tables in memory before the join to speed up the SortMergeJoin with the in-memory dimension table — eliminating the 2TB shuffle entirely and broadcasts it to every executor
  • B. Repartition both tables by the join key to ensure co-location before joining
  • C. Use a broadcast join by either hinting (broadcast(dim_df)) or setting spark.sql.autoBroadcastJoinThreshold to at least 50MB. Spark serializes the small dimension table and broadcasts it to every executor. Each executor joins its local fact table partitions with the in-memory dimension table — eliminating the 2TB shuffle entirely
  • D. Increase executor memory to handle the full 2TB dataset in memory per executor
Jawaban Benar: C
Broadcast join sends the small table (50MB) to all executors. Each executor holds the entire dimension table in memory and performs a local hash-map lookup for each row of its fact table partition. No shuffle of the 2TB fact table occurs — only 50MB is broadcast (vs. shuffling 2TB). This is optimal when one side of the join fits in executor memory. The autoBroadcastJoinThreshold tells Spark to automatically choose broadcast join when one table is below the threshold.

Opsi A: SALAH. Caching speeds up repeated reads but doesn't eliminate the shuffle; SortMergeJoin still requires data co-location via shuffle — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: SALAH. Repartitioning triggers a full shuffle of the 2TB fact table, which is the expensive operation we're trying to avoid.
Opsi C: BENAR.
Opsi D: SALAH. 2TB per executor is impossible and unnecessary; broadcast join avoids moving the large table entirely.

A company needs to scale their data processing capacity. They currently use a single large EMR instance (r5.24xlarge) that processes data sequentially. As data volume grows from 1TB to 10TB, processing time increases linearly from 1 hour to 10 hours. The team evaluates two scaling approaches. Which approach provides BETTER cost-efficiency for 10TB processing?
  • A. Horizontal scaling: replace the single large instance with a cluster of 20 smaller instances (r5.2xlarge). Distribute the 10TB across all nodes using Spark's parallel processing. Each node processes its partition simultaneously, achieving near-linear speedup. Total cost is similar (20 × r5.2xlarge ≈ 1 × r5.24xlarge) but processing completes in approximately 30 minutes instead of 10 hours
  • B. Process the data in 10 sequential 1TB batches on the existing instance with a cluster of 20 smaller instances (r5
  • C. Vertical scaling: upgrade to an even larger instance type (r5.metal with 96 vCPUs and 768GB RAM) to handle the 10TB dataset faster on a single machine
  • D. Compress the data to reduce volume rather than scaling compute
Jawaban Benar: A
Horizontal scaling leverages distributed computing's core principle: divide work across many nodes for parallel execution. 20 nodes processing simultaneously achieve near-linear speedup (20x faster). At similar hourly costs (20 small ≈ 1 large), the total job cost is dramatically lower because it runs 20x faster (30min vs 10hrs). Additionally, horizontal scaling provides fault tolerance (lose 1 of 20 nodes vs. losing the only node) and can use Spot instances for further savings.

Opsi A: BENAR.
Opsi B: SALAH. Sequential batches still take 10 hours total with no parallelism benefit — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. Vertical scaling has a ceiling (largest instance exists), provides no parallelism benefit for embarrassingly parallel workloads, and a single failure point means total restart.
Opsi D: SALAH. Compression reduces I/O but doesn't address compute scaling needs; 10TB still requires proportional processing regardless of storage format.

A Spark job reads data from S3 that is stored across three S3 buckets in us-east-1, but the EMR cluster runs in us-west-2. The job processes 500GB and the engineer notices that the Shuffle Read stage is fast but the initial data read from S3 takes 40 minutes. Network transfer costs are also high. Which distributed computing principle should guide the architecture fix?
  • A. Increase the EMR cluster size to add more network bandwidth for faster cross-region downloads
  • B. Use S3 Transfer Acceleration to speed up cross-region reads
  • C. Compress the S3 data to reduce the bytes transferred cross-region with native S3 integration and optimized data transfer
  • D. Apply data locality: move the EMR cluster to us-east-1 (same region as the S3 data) or replicate the S3 data to us-west-2. In distributed computing, moving computation to where data resides is always cheaper and faster than moving large datasets to where computation happens. Cross-region transfer adds latency and cost per GB
Jawaban Benar: D
Data locality is a fundamental distributed computing principle: computation should happen where data lives. Moving 500GB cross-region adds significant latency (40min vs seconds for same-region) and costs $0.02/GB ($10 per run). By colocating compute (EMR) with data (S3 in us-east-1), reads become same-region with near-zero added latency and no transfer cost. This is why Hadoop was designed with data-local scheduling — tasks run on the node storing their HDFS blocks.

Opsi A: SALAH. More nodes don't reduce per-connection latency; cross-region bandwidth is limited by physical distance and AWS network architecture.
Opsi B: SALAH. S3 Transfer Acceleration optimizes uploads to S3, not reads from S3; it doesn't apply to GET requests.
Opsi C: SALAH. Compression helps but doesn't eliminate the fundamental latency of cross-region transfer (speed of light) — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: BENAR.
10
A distributed Spark application on EMR processes 1TB of data with a long chain of transformations: 15 sequential map, filter, and join operations. The lineage DAG is extremely deep. An executor fails during the 14th transformation, and Spark must recompute from the beginning (transformation 1) because the lineage is too long for efficient re-execution. How should the engineer prevent this expensive recomputation?
  • A. Insert checkpoint() calls at strategic points in the transformation chain (e.g., after transformation 7). Checkpointing materializes the DataFrame to HDFS/S3 and truncates the lineage at that point. If a failure occurs after the checkpoint, Spark only needs to recompute from the checkpoint forward (transformations 8-14) rather than from the beginning (transformations 1-14)
  • B. Rewrite the 15 transformations as a single complex transformation to shorten the lineage and truncates the lineage at that point
  • C. Increase the number of executors to reduce the probability of any single executor failing
  • D. Use cache() or persist() to store intermediate results in executor memory
Jawaban Benar: A
Checkpointing breaks the lineage by saving intermediate results to reliable storage (HDFS/S3). After a checkpoint, Spark's fault recovery only replays from the checkpoint, not from the original source. For a 15-step pipeline with a checkpoint at step 7: a failure at step 14 recomputes 7 steps (8-14) instead of 14 steps (1-14) — cutting recovery time in half. Strategic checkpointing balances recovery cost vs. checkpoint overhead.

Opsi A: BENAR.
Opsi B: SALAH. Combining transformations into one doesn't shorten the internal computation; the same work must be redone on failure — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. More executors reduce failure probability but don't reduce recovery cost when failures do occur (they always will in large clusters).
Opsi D: SALAH. Cache/persist stores data in memory but doesn't truncate lineage. If an executor with cached data fails, Spark still uses lineage to recompute (cache is just a hint, not a guarantee).
