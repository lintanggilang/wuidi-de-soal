Skill 4.2.6: Construct Custom Policies That Meet the Principle of Least Privilege

Building minimal-permission IAM policies for data engineering workloads

A data engineer creates a Glue ETL job that reads from s3://raw-data/transactions/ and writes to s3://processed-data/transactions/. The initial IAM policy uses "s3:*" on "Resource": "*". The security team requests least-privilege refinement. Which policy BEST follows least privilege?
  • A. Replace with s3:GetObject on arn:aws:s3:::raw-data/* and s3:PutObject on arn:aws:s3:::processed-data/*
  • B. Separate read and write permissions with prefix-level specificity: Allow s3:GetObject on arn:aws:s3:::raw-data/transactions/*, Allow s3:PutObject and s3:DeleteObject on arn:aws:s3:::processed-data/transactions/*, Allow s3:ListBucket on both buckets with Condition restricting s3:prefix to "transactions/", and Allow glue:GetTable for the specific catalog database/table needed
  • C. Use s3:Get* and s3:Put* on both bucket ARNs without prefix restrictions
  • D. Keep s3:* but restrict to the two specific bucket ARNs only
Jawaban Benar: B
Least privilege untuk Glue ETL memerlukan granularitas di multiple levels: Action-level granularity: s3:GetObject (read only) — NOT s3:Get* (which includes s3:GetBucketPolicy, s3:GetEncryptionConfiguration). s3:PutObject (write) — only on output path. s3:DeleteObject — only if job overwrites/replaces output files. s3:ListBucket — needed for Spark to list partition paths, but restricted via Condition. Resource-level granularity: PREFIX restriction: arn:aws:s3:::raw-data/transactions/* — NOT arn:aws:s3:::raw-data/* (which exposes other data). ListBucket condition: {"StringLike": {"s3:prefix": ["transactions/*"]}} — prevents listing other prefixes. Supporting permissions: glue:GetTable, glue:GetDatabase — for catalog metadata reads needed by Spark. Why not others: Opsi A — bucket-level wildcard too broad (exposes all data in bucket). Opsi C — s3:Get* includes admin actions, no prefix restriction. Opsi D — s3:* includes s3:DeleteBucket, s3:PutBucketPolicy — extremely dangerous.

A security team wants to use IAM Access Analyzer to generate a least-privilege policy for an existing Glue job role that has been running in production for 90 days with overly permissive policies. What is the correct workflow to use Access Analyzer for policy refinement?
  • A. Access Analyzer automatically replaces existing policies with least-privilege versions without any manual intervention
  • B. Use IAM Access Analyzer's "Generate Policy" feature: specify the CloudTrail trail and time window (e.g., last 90 days), Access Analyzer analyzes all API calls made by the role during that period, then generates a policy containing ONLY the actions, resources, and conditions that were actually used — providing a starting point for a refined least-privilege policy that needs human review before deployment
  • C. Access Analyzer only works with S3 bucket policies, not IAM role policies
  • D. Run Access Analyzer against the policy document itself without needing CloudTrail data
Jawaban Benar: B
IAM Access Analyzer policy generation workflow: Step 1 — Prerequisites: CloudTrail trail enabled with management AND data events (for S3 object-level tracking). Trail must cover sufficient time period (ideally 90+ days for full coverage of periodic jobs). Step 2 — Generate Policy: Console: IAM → Roles → Select role → "Generate policy". Specify: CloudTrail trail ARN, time period (e.g., last 90 days), region(s). Step 3 — Analysis: Access Analyzer scans CloudTrail for all API calls made by that role. Identifies: exact actions used, specific resource ARNs accessed, conditions (source IPs, request parameters). Step 4 — Output: Generated policy with ONLY used actions/resources. Example: If role only called s3:GetObject on 3 specific prefixes in 90 days, generated policy reflects exactly that. Step 5 — Human review: Generated policy is a STARTING POINT. May need additions for: infrequent operations (quarterly reports), disaster recovery actions, future growth. Critical: Don't blindly apply — review for missing edge cases. Opsi A — never automatic replacement. Opsi C — works with IAM policies. Opsi D — needs actual usage data from CloudTrail.
3
A Redshift administrator needs to create an IAM policy for a reporting tool that connects to Redshift Serverless. The tool should ONLY be able to run SELECT queries on specific schemas and should NOT be able to modify cluster settings, create/delete tables, or access other AWS services. Which policy construct achieves this?
  • A. Grant redshift:* and rely on Redshift database-level permissions to restrict actions
  • B. Create a minimal IAM policy: Allow redshift-serverless:GetCredentials (to obtain temporary database credentials) and redshift-data:ExecuteStatement + redshift-data:GetStatementResult + redshift-data:DescribeStatement (for Data API access), scoped to the specific workgroup ARN. Combine with a Redshift database user/role that only has SELECT privilege on specific schemas — IAM handles AWS API access while Redshift handles SQL-level authorization
  • C. Use redshift:GetClusterCredentials with full database superuser access
  • D. Grant AdministratorAccess and configure Redshift internal permissions only
Jawaban Benar: B
Least privilege untuk Redshift access memerlukan two-layer approach: Layer 1 — IAM Policy (AWS API level): {"Effect": "Allow", "Action": ["redshift-serverless:GetCredentials"], "Resource": "arn:aws:redshift-serverless:region:account:workgroup/specific-workgroup"}, {"Effect": "Allow", "Action": ["redshift-data:ExecuteStatement", "redshift-data:GetStatementResult", "redshift-data:DescribeStatement"], "Resource": "*", "Condition": {"StringEquals": {"redshift-data:workgroup-name": "specific-workgroup"}}}. NOT included: redshift-serverless:CreateWorkgroup, redshift-serverless:DeleteWorkgroup, redshift-serverless:UpdateWorkgroup (no admin actions). Layer 2 — Redshift Database Permissions: CREATE USER reporting_tool PASSWORD DISABLE; GRANT USAGE ON SCHEMA reporting TO reporting_tool; GRANT SELECT ON ALL TABLES IN SCHEMA reporting TO reporting_tool; No INSERT, UPDATE, DELETE, CREATE, DROP privileges. Combined: Even if someone modifies IAM policy, database permissions still restrict actions. Even if database permissions are broadened, IAM policy limits which AWS APIs can be called. Opsi A — redshift:* allows cluster management. Opsi C — superuser access defeats least privilege. Opsi D — AdministratorAccess is the opposite of least privilege.

A data platform team needs to restrict Glue job roles so they can ONLY access Glue Data Catalog tables within their team's database (not other teams' databases). The databases follow the naming pattern: {team-name}_database. Which IAM policy condition BEST implements this resource-level restriction?
  • A. Use "Resource": "*" and add a comment in the policy documenting the intended restriction
  • B. Use specific resource ARNs with the team's database name pattern: "Resource": ["arn:aws:glue:region:account:database/analytics_database", "arn:aws:glue:region:account:table/analytics_database/*", "arn:aws:glue:region:account:catalog"] — restricting Glue GetDatabase, GetTable, GetPartitions actions to ONLY the team's specific database and its tables
  • C. Grant glue:* on all resources and use Lake Formation as the only access control layer
  • D. Create a VPC endpoint policy that restricts Glue API calls based on the database name
Jawaban Benar: B
Resource-level restrictions di IAM policies untuk Glue catalog: Policy structure: {"Effect": "Allow", "Action": ["glue:GetDatabase", "glue:GetDatabases"], "Resource": "arn:aws:glue:us-east-1:123456789012:database/analytics_database"}, {"Effect": "Allow", "Action": ["glue:GetTable", "glue:GetTables", "glue:GetPartitions", "glue:GetPartition", "glue:BatchGetPartition"], "Resource": ["arn:aws:glue:us-east-1:123456789012:table/analytics_database/*", "arn:aws:glue:us-east-1:123456789012:catalog"]}, Catalog resource: Required for glue:GetTable calls (Glue needs catalog-level access to resolve database/table hierarchy). Database resource: Specific database ARN — cannot access marketing_database, finance_database, etc. Table resource: Wildcard within specific database — analytics_database/* allows all tables IN that database only. Key: Even if Glue job code attempts client.get_table(DatabaseName='finance_database', Name='sensitive_table') → AccessDenied at IAM level. Opsi A — Resource:* provides no restriction. Opsi C — IAM should ALSO enforce restrictions (defense in depth). Opsi D — VPC endpoint policies have limited Glue catalog condition support.

An organization wants to ensure that no team can accidentally grant themselves broader S3 permissions than intended when creating IAM roles for their data pipelines. Teams have permission to create IAM roles for their Glue jobs. How can the security team enforce permission boundaries while still allowing teams self-service role creation?
  • A. Remove role creation permissions from all teams and have security create every role manually
  • B. Use IAM Permission Boundaries — create a boundary policy that defines the MAXIMUM permissions any team-created role can have (e.g., only S3 access to team-specific prefixes, only Glue actions, no IAM/STS admin actions). Require teams to attach this boundary when creating roles via a condition: iam:CreateRole only allowed if iam:PermissionsBoundary equals the team's boundary policy ARN
  • C. Use AWS Config rules to detect overly permissive roles after creation and send notifications
  • D. Trust teams to follow documentation guidelines for least-privilege policies
Jawaban Benar: B
Permission Boundaries enable delegated administration with guardrails: Concept: Permission Boundary = ceiling on what a role CAN be granted. Effective permissions = Intersection of (identity policy) AND (permission boundary). Even if role has "s3:*" on "Resource":"*" in its identity policy, boundary limits actual permissions. Implementation: (1) Security team creates boundary policy: "analytics-team-boundary" → Allows: s3:GetObject/PutObject on arn:aws:s3:::analytics-*, glue:* on analytics databases, logs:CreateLogGroup/PutLogEvents. Denies: iam:*, sts:AssumeRole to other accounts, s3 access outside analytics-* prefix. (2) Team's role creation policy: {"Effect": "Allow", "Action": "iam:CreateRole", "Resource": "*", "Condition": {"StringEquals": {"iam:PermissionsBoundary": "arn:aws:iam::account:policy/analytics-team-boundary"}}}. (3) Result: Teams can create roles freely BUT every role they create is capped by the boundary. Self-service WITH guardrails. Opsi A — doesn't scale, creates bottleneck. Opsi C — detective control only, damage already done. Opsi D — no enforcement mechanism.

A data engineer needs to write an IAM policy for a Lambda function that processes S3 events. The function reads objects from s3://intake-bucket/uploads/, calls Amazon Comprehend for PII detection, and writes results to a DynamoDB table "pii-scan-results". The function should ONLY operate during business hours (8 AM - 6 PM UTC). Which policy elements are needed?
  • A. Grant s3:*, comprehend:*, and dynamodb:* with no conditions
  • B. Create a policy with specific actions per service, resource restrictions, AND time-based conditions: s3:GetObject on intake-bucket/uploads/*, comprehend:DetectPiiEntities (no resource restriction as it's a stateless API), dynamodb:PutItem on the specific table ARN, plus a Condition block using aws:CurrentTime to restrict API calls to business hours
  • C. Use aws:SourceIp condition to restrict access to office network IPs
  • D. Grant full access and rely on Lambda's timeout settings to prevent execution outside business hours
Jawaban Benar: B
Multi-dimensional least privilege policy: Service-specific actions: S3: s3:GetObject ONLY (not PutObject, DeleteObject). Comprehend: comprehend:DetectPiiEntities ONLY (not comprehend:* which includes model training). DynamoDB: dynamodb:PutItem ONLY (not GetItem, Scan, DeleteItem). Resource restrictions: S3: "arn:aws:s3:::intake-bucket/uploads/*" — only uploads prefix. Comprehend: "*" — stateless APIs don't have specific resource ARNs. DynamoDB: "arn:aws:dynamodb:region:account:table/pii-scan-results" — specific table only. Time-based condition: {"Condition": {"DateGreaterThan": {"aws:CurrentTime": "2024-01-01T08:00:00Z"}, "DateLessThan": {"aws:CurrentTime": "2024-01-01T18:00:00Z"}}}. Note: aws:CurrentTime is evaluated per-request. Better approach for Lambda: use EventBridge schedule to only trigger during business hours, and add time condition as defense-in-depth. Opsi A — wildcard actions/resources violate least privilege. Opsi C — Lambda doesn't have a source IP (runs in AWS network). Opsi D — timeout ≠ access control, function could still be invoked.

An organization wants to prevent ANY data engineer from using unencrypted S3 PutObject operations across all accounts in their AWS Organization. They need this enforced as an organization-wide guardrail that individual account administrators cannot override. Which mechanism provides this enforcement?
  • A. Create an IAM policy in each account that denies unencrypted PutObject and attach it to all roles
  • B. Implement a Service Control Policy (SCP) at the Organization level that denies s3:PutObject when the condition s3:x-amz-server-side-encryption is absent or not equal to "aws:kms" — SCPs act as a permission ceiling for ALL principals in member accounts (including account administrators) and cannot be overridden by any IAM policy within the account
  • C. Use AWS Config rules to detect unencrypted objects and send alerts
  • D. Set S3 bucket default encryption and assume all uploads will be encrypted
Jawaban Benar: B
Service Control Policies (SCPs) provide organization-level guardrails: SCP Characteristics: Applied at Organization Root, OU, or Account level. CANNOT be overridden by ANY policy within member accounts. Even account root user is bound by SCPs. Acts as permission ceiling — narrows what's possible. SCP Example: {"Effect": "Deny", "Action": "s3:PutObject", "Resource": "*", "Condition": {"StringNotEquals": {"s3:x-amz-server-side-encryption": "aws:kms"}}}. Add second statement for missing header: {"Effect": "Deny", "Action": "s3:PutObject", "Resource": "*", "Condition": {"Null": {"s3:x-amz-server-side-encryption": "true"}}}. Result: ANY s3:PutObject call WITHOUT KMS encryption → DENIED. Applies to all accounts under the OU/Organization. Account admins CANNOT override (they can't modify SCPs). Why not others: Opsi A — account admins can remove/modify IAM policies. Opsi C — detective only, doesn't prevent. Opsi D — default encryption doesn't ENFORCE (clients can specify different encryption or none with explicit header).
8
A data engineer discovers that their Glue Crawler role has permissions for glue:CreateDatabase, glue:CreateTable, glue:UpdateTable, and glue:DeleteTable. The crawler only needs to CREATE new tables and UPDATE existing ones when schema changes are detected — it should never delete tables or create new databases. How should the policy be refined?
  • A. Keep all four permissions since the crawler might need them in the future
  • B. Remove glue:DeleteTable and glue:CreateDatabase from the policy, keeping only glue:CreateTable and glue:UpdateTable plus the required supporting actions (glue:GetTable, glue:GetDatabase, glue:BatchCreatePartition, glue:BatchUpdatePartition) — restricting to only the actions the crawler actually performs during normal operation
  • C. Replace with the AWS managed policy AWSGlueServiceRole which includes all necessary permissions
  • D. Add a Deny statement for DeleteTable but keep CreateDatabase for potential future use
Jawaban Benar: B
Principle of least privilege = grant ONLY what is needed NOW, not what might be needed later: Crawler actual requirements: glue:CreateTable — creates new tables when new data sources found. glue:UpdateTable — updates schema when source structure changes. glue:GetTable, glue:GetDatabase — reads existing metadata. glue:CreatePartition, glue:BatchCreatePartition — adds new partition metadata. glue:UpdatePartition, glue:BatchUpdatePartition — updates existing partitions. s3:GetObject, s3:ListBucket — reads actual data files. logs:CreateLogGroup, logs:PutLogEvents — writes CloudWatch logs. NOT needed: glue:DeleteTable — crawler doesn't delete tables (even when source removed, table metadata remains). glue:CreateDatabase — database should be pre-created by admin; crawler discovers tables WITHIN existing database. glue:DeleteDatabase — destructive, never needed for crawling. Refinement principle: Start with what's needed → add ONLY when use case demands. "Future use" = over-provisioning = security risk. Opsi A — "might need" ≠ "needs now". Opsi C — managed policies are often overly broad. Opsi D — explicit Deny + Allow CreateDatabase still over-provisions.
9
A data engineering team runs Glue jobs that process data from multiple S3 buckets. After enabling CloudTrail data events and waiting 30 days, they use IAM Access Analyzer to generate a policy. The generated policy is much narrower than expected — missing some S3 paths that are processed quarterly. How should they handle this gap?
  • A. Discard the generated policy entirely since it's incomplete and keep the original broad policy
  • B. Use the generated policy as a BASELINE, then manually supplement it with permissions for known quarterly operations: identify all periodic/seasonal access patterns from documentation and runbooks, add those specific S3 paths and actions to the policy, validate against the full operational calendar, and deploy with monitoring to catch any remaining gaps using CloudTrail + CloudWatch alarms for AccessDenied events
  • C. Wait 365 days for full annual coverage before generating a policy
  • D. Add s3:* on Resource:* to cover any missing paths
Jawaban Benar: B
Access Analyzer generated policies are a starting point, not a final product: Known limitation: Access Analyzer only sees what WAS done — not what SHOULD be done. 30-day window may miss: quarterly reports, annual compliance jobs, disaster recovery procedures, seasonal data processing. Recommended workflow: (1) Generate baseline policy from CloudTrail (best starting point). (2) Review operational documentation: quarterly ETL runs, year-end processing, periodic data migrations. (3) Add missing permissions for known-but-infrequent operations. (4) Deploy policy with monitoring: CloudWatch Alarm on CloudTrail "errorCode=AccessDenied" for the role. SNS notification when access denied occurs. Rapid response process to add missing permissions. (5) Iterate: After a full annual cycle, re-generate to capture everything. Avoid: Waiting 365 days (C) — too long with overly permissive policy in place. Adding wildcards (D) — defeats the purpose of least privilege. Discarding (A) — wastes valuable baseline data. Key: Least privilege is ITERATIVE, not one-time.

A company's data lake architecture includes cross-account data sharing. A Glue ETL job in Account A needs to read from an S3 bucket in Account B and write results to a Redshift cluster in Account A. The security team requires the MOST restrictive policy possible. Which policy combination correctly implements cross-account least privilege?
  • A. Grant the Glue role in Account A full S3 and Redshift access, then add a bucket policy in Account B allowing Account A's root principal
  • B. In Account A (Glue role policy): Allow s3:GetObject on arn:aws:s3:::account-b-bucket/shared-prefix/* and Allow redshift-data:ExecuteStatement on the specific Redshift cluster ARN. In Account B (S3 bucket policy): Allow s3:GetObject from Account A's specific Glue role ARN (not account root) with a condition restricting to the shared prefix only. Both policies required for cross-account access — neither alone is sufficient
  • C. Use a VPC peering connection and rely on network-level security for cross-account access
  • D. Create an IAM user with access keys in Account B and hardcode credentials in the Glue job
Jawaban Benar: B
Cross-account least privilege requires policies on BOTH sides: Account A — Glue Job Role (Identity Policy): {"Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::account-b-bucket/shared-prefix/*"} — specific prefix, not entire bucket. {"Effect": "Allow", "Action": ["redshift-data:ExecuteStatement", "redshift-data:GetStatementResult"], "Resource": "arn:aws:redshift:region:account-a:cluster:my-cluster"} — specific cluster. Account B — S3 Bucket Policy (Resource Policy): {"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::account-a:role/GlueJobRole"}, "Action": "s3:GetObject", "Resource": "arn:aws:s3:::account-b-bucket/shared-prefix/*", "Condition": {"StringEquals": {"aws:PrincipalOrgID": "o-orgid123"}}} — restricts to: specific role (not account root), specific prefix, within organization. Why both needed: Cross-account S3 access requires BOTH identity policy AND resource policy to Allow. If either Denies → access denied. This is different from same-account where identity policy alone suffices. Opsi A — account root principal too broad. Opsi C — VPC peering doesn't provide S3 authorization. Opsi D — hardcoded credentials = massive security risk.
