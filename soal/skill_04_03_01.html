A healthcare company stores patient records in Amazon Redshift. Business analysts need to run aggregate queries (average treatment costs by region) but must NOT see individual patient names, SSNs, or dates of birth. The data must remain in the same table for other authorized users (physicians). Which approach provides real-time masking without data duplication?
  • A. Create a separate copy of the table with PII columns removed for analysts
  • B. Implement Redshift Dynamic Data Masking (DDM) — create masking policies on the patient_name, ssn, and date_of_birth columns that return masked values (e.g., "XXXX" for SSN, NULL for name) when queried by analyst roles, while physician roles see the original unmasked values. Masking is applied at query time without modifying stored data
  • C. Use Redshift views with CASE statements to filter PII based on current_user
  • D. Remove PII columns from the table entirely since analysts don't need them
Jawaban Benar: B
Redshift Dynamic Data Masking (DDM) adalah solusi optimal untuk skenario ini: Implementation: (1) Create masking policy: CREATE MASKING POLICY ssn_mask WITH (ssn VARCHAR) USING ('XXX-XX-' || RIGHT(ssn, 4)); CREATE MASKING POLICY full_mask WITH (val VARCHAR) USING (NULL); (2) Attach to columns for specific roles: ATTACH MASKING POLICY ssn_mask ON patient_records(ssn) TO ROLE analyst_role; ATTACH MASKING POLICY full_mask ON patient_records(patient_name) TO ROLE analyst_role; (3) Priority: physician_role → no masking policy attached → sees original data. analyst_role → masking policies active → sees masked values. Advantages: No data duplication (unlike Opsi A). Applied at query time — stored data unchanged. Centralized policy management. Works with any query tool connecting to Redshift. Role-based — same table serves multiple audiences. Opsi A — data duplication, sync overhead, storage cost. Opsi C — views work but are harder to maintain at scale, don't support complex masking functions natively. Opsi D — physicians need PII for patient care, can't remove.

A retail company needs to anonymize customer data in their data lake before sharing with a third-party analytics vendor. The vendor needs to track customer behavior across sessions (requiring consistent customer identifiers) but must NOT be able to reverse-engineer real customer IDs. Which anonymization technique is MOST appropriate?
  • A. Simply remove the customer_id column from the shared dataset
  • B. Apply deterministic tokenization — replace real customer_ids with consistent pseudonymous tokens using a keyed HMAC hash (e.g., HMAC-SHA256 with a secret key). The same customer_id always produces the same token (enabling cross-session tracking for the vendor), but without the secret key, the vendor cannot reverse the tokens to recover original IDs
  • C. Replace all customer_ids with a single static value like "ANONYMOUS"
  • D. Use random UUIDs for each record, generating a new UUID per row
Jawaban Benar: B
Deterministic tokenization (pseudonymization) memenuhi kedua requirement: Consistency requirement: HMAC-SHA256(customer_id, secret_key) → selalu menghasilkan token yang SAMA untuk customer_id yang sama. Vendor dapat track: "token_abc visited page X on Monday, then purchased Y on Tuesday" — behavioral analysis intact. Irreversibility: HMAC is one-way — tanpa secret_key, vendor tidak dapat reverse token → customer_id. Brute-force infeasible untuk large ID spaces. Secret key hanya disimpan oleh data owner — never shared with vendor. Implementation in Glue ETL: from hashlib import hmac; token = hmac.new(secret_key, customer_id.encode(), 'sha256').hexdigest(). Mengapa bukan opsi lain: Opsi A (remove ID) — vendor cannot do cross-session analysis (lose analytical value). Opsi C (static value) — semua records become one "customer" — useless for behavior analysis. Opsi D (random UUID per row) — same customer gets different IDs each session — cannot track behavior. Key distinction: Tokenization = pseudonymization (consistent replacement, reversible by key holder). Anonymization = irreversible (no one can recover original data).

A European bank must comply with GDPR's "right to be forgotten" (Article 17). Customer data exists across multiple systems: S3 data lake (raw + processed), Redshift data warehouse, and DynamoDB operational store. When a customer requests deletion, all their PII must be rendered unrecoverable within 30 days. Which masking/anonymization strategy BEST supports this requirement?
  • A. Physically scan and delete all records containing the customer's data across all systems within 30 days
  • B. Implement crypto-shredding (cryptographic erasure) — encrypt each customer's PII with a unique per-customer encryption key stored in KMS. When a deletion request arrives, delete ONLY the customer's encryption key from KMS. All encrypted PII across all systems becomes permanently unreadable without needing to locate and delete individual records across distributed systems
  • C. Mark records as "deleted" with a flag and hide them from query results
  • D. Move all customer records to a "deleted" S3 bucket with a lifecycle policy
Jawaban Benar: B
Crypto-shredding adalah approach yang paling practical dan reliable untuk GDPR deletion: Architecture: (1) During data ingestion: Each customer gets unique KMS key (or per-customer data key encrypted by a customer-specific CMK). PII fields encrypted with customer's key: {name: ENC(key_123, "John Doe"), email: ENC(key_123, "john@example.com"), transactions: [unencrypted aggregate data]}. (2) Normal operation: Applications decrypt PII using customer's key for display/processing. Non-PII data remains accessible without the key. (3) Deletion request (GDPR Art. 17): Schedule KMS key deletion: aws kms schedule-key-deletion --key-id key_123 --pending-window-in-days 7. After pending window: key permanently deleted. ALL encrypted PII across S3, Redshift, DynamoDB → permanently unreadable. Aggregated/anonymized data derived from customer remains usable. Advantages over physical deletion: Don't need to find every copy across distributed systems (backups, caches, logs). Instant "logical deletion" — data becomes garbage without key. Works even for data in immutable storage (S3 Glacier, backups). Opsi A — extremely difficult across distributed systems, backup tapes, etc. Opsi C — soft delete ≠ actual deletion, violates GDPR. Opsi D — moving data isn't deleting it.

  • A. Write custom Lambda functions with regex patterns to scan each bucket on a schedule
  • B. Use Amazon Macie — enable it across all accounts, configure automated sensitive data discovery jobs that continuously scan S3 buckets using machine learning and pattern matching to detect PII types (SSN, credit cards, names, addresses, passport numbers) across both structured and unstructured formats, with findings reported to Security Hub for centralized visibility
  • C. Use AWS Glue Data Quality to check for PII patterns in crawled tables
  • D. Manually review S3 object metadata tags to identify PII-containing objects
Jawaban Benar: B
Amazon Macie adalah purpose-built service untuk PII discovery in S3: Capabilities: ML-powered classification: identifies PII even in unstructured text, PDFs, images. Managed data identifiers: 100+ built-in PII patterns (SSN, credit cards, bank accounts, names, addresses, passport numbers, driver's licenses). Custom data identifiers: regex + keyword patterns for organization-specific sensitive data. Format support: CSV, JSON, Parquet, Avro, PDF, text, MS Office documents. Continuous monitoring: Automated sensitive data discovery — scans new/modified objects. Event-driven: integrates with S3 event notifications. Scheduled jobs: daily/weekly comprehensive scans. Scale: manages 500+ buckets across multi-account (Organizations integration). Findings: Severity classification (High, Medium, Low). Integration with Security Hub for centralized dashboard. EventBridge integration for automated remediation (e.g., quarantine, encrypt, alert). Cost optimization: sampling-based discovery mode reduces scan costs. Opsi A — custom regex misses complex patterns, doesn't handle unstructured data well, maintenance burden. Opsi C — Glue Data Quality checks data correctness, not PII detection. Opsi D — doesn't scale, relies on manual tagging accuracy.

A company needs to mask credit card numbers in an ETL pipeline built with AWS Glue. The requirement is: full card numbers in the source (s3://raw/payments/) must be masked to show only last 4 digits (e.g., "****-****-****-1234") in the target (s3://processed/payments/). The masking must be applied during transformation, not at query time. Which Glue feature handles this?
  • A. Use Glue DataBrew with a masking recipe — create a project that applies the "mask" or "cryptographic hash" transform to the credit_card column, outputting only last 4 digits with asterisks. DataBrew provides visual, no-code data masking transforms that can be scheduled as part of the ETL pipeline
  • B. Configure S3 server-side encryption to automatically mask credit card numbers
  • C. Use Redshift Dynamic Data Masking on the S3 data directly
  • D. Apply masking at the Glue Crawler level before writing to the Data Catalog
Jawaban Benar: A
AWS Glue DataBrew provides visual data masking transforms untuk ETL pipelines: DataBrew Masking Features: Built-in transformations: MASK_CUSTOM — replace characters with specified mask (e.g., * for all but last 4). MASK_DATE — generalize dates (keep only year). MASK_RANGE — mask numerical ranges. HASH — cryptographic hash replacement. REDACT — complete removal. Credit card masking recipe: Step 1: Select credit_card_number column. Step 2: Apply MASK_CUSTOM transform: mask character = "*", keep last 4 positions. Result: "4532-1234-5678-9012" → "****-****-****-9012". Alternative approach in Glue PySpark: Use custom transformation in Glue ETL script: df = df.withColumn("credit_card", concat(lit("****-****-****-"), substring(col("credit_card"), -4, 4))). DataBrew advantage: Visual, no-code, auditable transformations. Recipe versioning for compliance documentation. Profile data before/after to verify masking completeness. Opsi B — S3 encryption encrypts entire objects, doesn't mask specific fields. Opsi C — Redshift DDM operates within Redshift, not on S3 files. Opsi D — Crawlers read metadata, don't transform data content.

A data science team needs access to production customer data for model training but must comply with HIPAA requirements. The data includes patient diagnoses, ages, and zip codes. Simply removing names and SSNs is not sufficient — the team must ensure individuals cannot be re-identified from combinations of quasi-identifiers. Which technique addresses this?
  • A. Remove only the direct identifiers (name, SSN, phone) and share the rest unchanged
  • B. Apply k-anonymity through generalization — generalize quasi-identifiers so each record is indistinguishable from at least k-1 other records: generalize age to ranges (e.g., 30-39), truncate zip codes to 3-digit prefix (e.g., 981**), group rare diagnoses into broader categories. This prevents re-identification through linkage attacks on combinations of quasi-identifiers
  • C. Encrypt the data with a shared team key — this counts as anonymization under HIPAA
  • D. Add random noise to every field in the dataset including the diagnosis column
Jawaban Benar: B
K-anonymity via generalization addresses re-identification risk: Problem: Direct identifiers removed, but quasi-identifiers (age, zip, diagnosis) combined can uniquely identify individuals. Example: "35-year-old male, zip 98115, diabetes Type-1" → might identify only one person in a small community. K-anonymity (k≥5 for HIPAA Safe Harbor): Generalization: Age 35 → "30-39". Zip 98115 → "981**". Rare diagnosis → broader category. Result: Every record matches at least k-1 other records — cannot pinpoint individual. HIPAA Safe Harbor method requires: Zip codes truncated to 3 digits (or 000 if population < 20,000). Ages above 89 grouped as "90+". Dates generalized to year only. 18 specified identifiers removed or generalized. Implementation in ETL: Glue PySpark: bin ages, truncate zips, apply generalization hierarchies. Verify k value: GROUP BY generalized quasi-identifiers, HAVING COUNT(*) >= k for all groups. Opsi A — insufficient, quasi-identifier linkage attacks still possible. Opsi C — encryption ≠ anonymization under HIPAA; encrypted data is still considered PHI. Opsi D — random noise destroys data utility for ML; diagnosis noise makes data useless.

A payment processing company must comply with PCI-DSS requirements for handling credit card data. They store transaction data in a data lake and need to ensure that Primary Account Numbers (PAN) are masked in all non-production environments while maintaining referential integrity for testing. Which masking approach satisfies PCI-DSS requirement 3.4?
  • A. Use format-preserving encryption (FPE) with AES-FF1 — the masked PAN maintains the same format (16 digits, passes Luhn check) but is a completely different number. FPE is deterministic (same PAN always produces same masked value) preserving referential integrity across tables, while being NIST-approved and satisfying PCI-DSS requirement 3.4 for rendering PAN unreadable
  • B. Simply store PANs as plaintext but restrict network access to the database
  • C. Replace all PANs with the static value "0000-0000-0000-0000" across environments
  • D. Truncate all PANs to first 6 and last 4 digits in all environments including production
Jawaban Benar: A
Format-Preserving Encryption (FPE) optimal untuk PCI-DSS compliant masking: PCI-DSS Requirement 3.4: PAN must be rendered unreadable. Acceptable methods: One-way hash, truncation, index tokens, OR strong cryptography with associated key management. FPE (AES-FF1/FF3-1) properties: Format preservation: 16-digit input → 16-digit output. Valid format: output passes Luhn check → applications don't break. Deterministic: PAN "4532-1234-5678-9012" always maps to same masked value → referential integrity maintained (foreign keys, joins between tables still work). NIST-approved: FF1 (NIST SP 800-38G) — accepted by PCI-DSS. Reversible (with key): production can decrypt if needed; non-production environments never have the key. Why for testing: FK relationships preserved: masked PAN in transactions table matches masked PAN in refunds table. Format valid: application code doesn't throw validation errors. Realistic data: testing resembles production behavior. Opsi B — plaintext PAN violates PCI-DSS Req 3.4. Opsi C — static value breaks referential integrity, unrealistic testing. Opsi D — truncation is valid for DISPLAY only; PCI-DSS allows first 6 + last 4 for display, but stored data still needs full protection in scope systems.

A streaming data pipeline using Amazon Kinesis Data Streams receives customer events containing email addresses. A downstream analytics consumer needs event data but should NOT receive raw email addresses — they need a consistent pseudonymous identifier for cohort analysis. The masking must happen in-stream without adding significant latency. Which architecture implements this?
  • A. Store all raw data first, then run a batch masking job nightly
  • B. Use a Kinesis Data Streams consumer (Lambda or KDA/Managed Flink) that reads raw events, applies HMAC-based tokenization to the email field using a secret stored in Secrets Manager, then publishes masked events to a separate "clean" Kinesis stream consumed by analytics. Raw stream is restricted to authorized PII-handlers only
  • C. Configure Kinesis server-side encryption to mask email fields automatically
  • D. Use a Kinesis Firehose transformation to delete the email field entirely
Jawaban Benar: B
In-stream tokenization architecture untuk real-time masking: Architecture: [Producer] → [Raw Kinesis Stream (restricted)] → [Lambda/Flink Consumer] → [Clean Kinesis Stream (analytics)] → [Analytics Consumers]. Lambda/Flink transformation: Read event: {"user_email": "john@example.com", "event": "page_view", "timestamp": "..."}. Apply HMAC: token = HMAC-SHA256(secret_key, "john@example.com") → "a1b2c3d4...". Output: {"user_token": "a1b2c3d4...", "event": "page_view", "timestamp": "..."}. Consistency: Same email always produces same token → cohort analysis works. Secret management: Key from AWS Secrets Manager, rotated periodically. Latency: Lambda adds ~10-50ms processing per batch. Flink provides sub-second end-to-end. Separation of concerns: Raw stream: only authorized services (compliance, fraud detection) access. Clean stream: safe for any analytics consumer. Opsi A — batch introduces hours of latency, raw PII accessible during delay. Opsi C — Kinesis encryption protects data at rest/transit, doesn't mask specific fields. Opsi D — deleting email removes ability to do cross-session cohort analysis.

A company operates in multiple regulatory jurisdictions (GDPR in EU, CCPA in California, LGPD in Brazil). Each regulation has different definitions of personal data and different masking requirements. How should the data engineering team design a masking framework that handles multi-jurisdictional compliance?
  • A. Apply the least restrictive regulation's requirements uniformly across all data
  • B. Implement a metadata-driven masking framework: tag each data field with its jurisdiction(s) and applicable regulations in the Glue Data Catalog, then apply masking rules based on the MOST restrictive applicable regulation for each field. Use a centralized policy engine (e.g., masking rule tables in DynamoDB) that maps {field_type + jurisdiction} to {masking_technique}, enabling different masking for different regulatory contexts
  • C. Create completely separate data lakes for each jurisdiction with no shared infrastructure
  • D. Apply GDPR requirements everywhere since it's the most well-known regulation
Jawaban Benar: B
Metadata-driven masking framework untuk multi-jurisdictional compliance: Design: (1) Classification Layer (Glue Data Catalog tags): Field: email → PII_type: "contact_info", jurisdictions: ["GDPR", "CCPA", "LGPD"]. Field: IP_address → PII_type: "online_identifier", jurisdictions: ["GDPR"] (GDPR considers IP as PII, some others don't). (2) Policy Engine (DynamoDB rules table): {pii_type: "contact_info", regulation: "GDPR", context: "analytics"} → mask_technique: "pseudonymization". {pii_type: "contact_info", regulation: "CCPA", context: "sale"} → mask_technique: "opt_out_deletion". (3) Masking Execution: ETL jobs query policy engine → apply appropriate masking per field per jurisdiction. Most restrictive rule wins when data subject to multiple regulations. (4) Audit Trail: Every masking operation logged with regulation reference. Demonstrable compliance for each regulation. Why this approach: Flexible — new regulations added by updating policy table, not code. Auditable — clear mapping from regulation → masking action. Accurate — different fields masked differently based on actual regulatory requirements. Opsi A — "least restrictive" guarantees violations of stricter regulations. Opsi C — massive duplication, operational overhead. Opsi D — GDPR isn't always the most restrictive (e.g., Brazilian LGPD has unique requirements).

A data engineering team applies SHA-256 hashing to email addresses for anonymization in their data lake. A security auditor flags this approach as insufficient for true anonymization. What is the auditor's concern, and what technique should supplement or replace simple hashing?
  • A. SHA-256 is a broken algorithm and should be replaced with MD5 for better security
  • B. Plain SHA-256 hashing of emails is vulnerable to dictionary/rainbow table attacks — an attacker can hash all common email patterns (firstname.lastname@domain.com) and match against the hashed values to recover original emails. The solution: use HMAC with a secret key (keyed hashing) or apply salted hashing, making rainbow table attacks infeasible since the attacker would need the secret key or per-record salt to reproduce hashes
  • C. SHA-256 produces output that is too long to store efficiently in databases
  • D. The auditor's concern is that SHA-256 is reversible and the original email can be mathematically derived from the hash
Jawaban Benar: B
Plain hashing BUKAN true anonymization untuk low-entropy data seperti email: Vulnerability: Email addresses have limited entropy — predictable patterns. Attacker approach: Generate list of probable emails (firstname.lastname combinations + common domains). Hash each: SHA256("john.smith@gmail.com") → "abc123...". Match against hashed dataset. Result: millions of emails recoverable in minutes. This is a "pre-image attack via enumeration" — technically SHA-256 is one-way, but the INPUT SPACE is small enough to enumerate. Solutions (in order of preference): (1) HMAC with secret key: HMAC-SHA256(secret_key, email) — without secret_key, rainbow tables useless. Key management critical — store in KMS/Secrets Manager. (2) Salted hash: SHA256(random_salt + email) — different salt per record. Prevents matching across records but salt must be stored. (3) Differential privacy: Add calibrated noise to aggregated statistics rather than pseudonymizing individual records. For true anonymization: Consider if you need consistency (HMAC/tokenization) or irreversibility (generalization, differential privacy). Opsi A — MD5 is LESS secure than SHA-256, factually wrong. Opsi C — 64-character hex output is standard database column size. Opsi D — SHA-256 is NOT mathematically reversible; the issue is enumeration attack on limited input space.
