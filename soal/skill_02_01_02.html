#DynamoDB
An IoT platform stores sensor readings in DynamoDB. The primary access pattern is querying all readings for a specific device within a time range (e.g., "all readings for device-123 between January 1 and January 31"). Secondary access patterns include querying by sensor_type across all devices. The table receives 50,000 writes per second with 2 million unique devices. Which DynamoDB key design BEST supports these access patterns while avoiding hot partitions?
  • A. Partition key: timestamp (truncated to hour), Sort key: device_id. This distributes writes across time-based partitions, absorbing sudden traffic spikes without throttling and handling peak volume without any manual intervention and scaling elastically to millions of events per second
  • B. Single partition key: device_id#timestamp as a composite string with no sort key, using Scan with filter expressions for time range queries, scaling horizontally as ingestion throughput keeps growing and scaling elastically to millions of events per second
  • C. Partition key: sensor_type, Sort key: device_id#timestamp. This optimizes for the secondary access pattern of querying by sensor type with KeyConditionExpression and sort key timestamp for the secondary access pattern, meeting the latency and throughput goals of the design
  • D. Partition key: device_id, Sort key: timestamp. This allows efficient range queries on timestamp within a single device partition using Query with KeyConditionExpression. Add a GSI with partition key sensor_type and sort key timestamp for the secondary access pattern
Jawaban Benar: D
This design optimally serves the primary access pattern: Query operation on partition key device_id with sort key condition (timestamp BETWEEN start AND end) retrieves all readings for a device in a time range in a single efficient operation — no scan required. With 2 million unique devices, writes distribute evenly across partitions (avoiding hot partitions). The GSI on sensor_type enables the secondary pattern without compromising the base table design.

Opsi A: SALAH. Timestamp as partition key creates a "hot partition" problem where all current writes go to the same hourly partition, causing throttling.
Opsi B: SALAH. Composite string as sole key prevents range queries; DynamoDB cannot do "BETWEEN" on partition keys, requiring expensive full table Scans.

#Redshift
A data warehouse on Amazon Redshift contains a 2 TB fact table (orders) that is frequently JOINed with a 50 MB dimension table (products). The cluster has 4 nodes. Most queries filter by order_date and JOIN on product_id. The team notices that JOIN operations cause significant network traffic between nodes. Which combination of distribution style and sort key configuration BEST optimizes query performance for this pattern?
  • A. Orders table: KEY distribution on product_id, compound sort key (order_date, product_id). Products table: ALL distribution. This co-locates the dimension table on every node, eliminating network shuffling for JOINs, while the sort key optimizes date range filtering
  • B. Orders table: ALL distribution. Products table: KEY distribution on product_id for JOINs, keeping every related record in its produced order and transforming records into the required target format and meeting the latency and throughput goals of the design
  • C. Both tables: KEY distribution on product_id. Orders table: sort key on order_date. This co-locates matching product_id rows from both tables on the same node, validating and cleansing each record before delivery and applying schema conversion and enrichment inline
  • D. Orders table: EVEN distribution. Products table: EVEN distribution. No sort keys defined, applying schema conversion and enrichment inline and transforming records into the required target format and handling the described workload reliably at scale
Jawaban Benar: A
ALL distribution replicates the small products table (50 MB) on every node, so JOIN operations between orders and products are always local — zero network traffic for the JOIN. The 50 MB dimension table has negligible storage overhead when replicated across 4 nodes (200 MB total). The compound sort key on the orders table with order_date first enables zone map-based block skipping for date range filters, dramatically reducing I/O.

Opsi A: BENAR.
Opsi B: SALAH. Distributing the 2 TB orders table with ALL would replicate it on every node (8 TB total storage), which is impractical and wastes storage — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. KEY distribution on both tables co-locates matching keys but the small products table would be sparse on each node (12.5 MB/node), and JOIN performance is identical to ALL distribution while adding complexity.
Opsi D: SALAH. EVEN distribution requires redistributing data at JOIN time (full network shuffle), which is the current performance problem.

#RDS
A SaaS application stores tenant data in Amazon RDS PostgreSQL. The application has grown to 500 tenants with uneven data distribution: 10 "enterprise" tenants generate 80% of queries (read-heavy reporting), while 490 "standard" tenants have balanced read/write patterns. The database is experiencing read contention during enterprise tenant reporting hours (9 AM - 5 PM). Which RDS configuration BEST addresses this access pattern imbalance?
  • A. Vertically scale the primary instance to a larger instance type (e.g., db.r5.8xlarge) to handle both read and write workloads, meeting the latency and throughput goals of the design and satisfying all of the stated requirements with minimal effort and minimizing end-to-end processing latency
  • B. Enable Multi-AZ deployment to distribute the read load across the primary and standby instances with custom endpoints, handling the described workload reliably at scale and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort
  • C. Create read replicas and configure the application to route enterprise tenant reporting queries to read replicas while directing all write operations and standard tenant queries to the primary instance, using an application-level routing layer or Amazon RDS Proxy with custom endpoints
  • D. Migrate all enterprise tenants to a separate RDS instance and all standard tenants to another instance, handling the described workload reliably at scale and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort
Jawaban Benar: C
Read replicas offload read-heavy reporting queries from the primary instance, eliminating contention. Routing enterprise reporting to replicas during business hours handles the 80% read load separately while the primary serves writes and standard tenant queries without contention. RDS supports up to 5 read replicas per instance, providing scalable read capacity. This targets the specific access pattern (read-heavy enterprise reporting) without over-engineering.

Opsi A: SALAH. Vertical scaling has limits (max instance size) and doesn't solve read contention — more CPU/RAM on a single instance still means shared I/O.
Opsi B: SALAH. Multi-AZ standby is for failover only; it does NOT serve read traffic (it's a synchronous replica that handles only failover scenarios) — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: BENAR.
Opsi D: SALAH. Splitting tenants into separate instances adds operational complexity, cross-instance queries, and doesn't leverage RDS's built-in read replica capability.

#Glue#Athena#S3
A data lake on S3 stores event data partitioned by date (s3://bucket/events/year=2024/month=01/day=15/). Analysts primarily query recent data (last 7 days) for operational dashboards, but occasionally run quarterly reports spanning 90 days. The data totals 50 TB with 500 GB added daily. Queries use Athena. The team notices that quarterly queries scan excessive data and cost $250+ per query. Which S3 access pattern optimization MOST reduces Athena query costs while maintaining performance for both access patterns?
  • A. Use S3 Select to push filter predicates to S3 and reduce the data read by Athena with columnar compression for partition discovery, handling the described workload reliably at scale and integrating natively with the rest of the pipeline and keeping steady-state operating costs low
  • B. Create a single large Parquet file per day instead of multiple small files to reduce Athena's listing overhead, requiring no servers to manage or scale manually and meeting the latency and throughput goals of the design and reducing day-to-day operational effort
  • C. Move data older than 7 days to S3 Glacier and restore it on-demand when quarterly reports are needed, requiring no servers to manage or scale manually and handling the described workload reliably at scale and running as a fully managed service with minimal operational overhead
  • D. Add a secondary partition on event_type within each date partition (s3://bucket/events/year=2024/month=01/day=15/event_type=click/), enabling Athena to prune irrelevant event types during quarterly scans. Additionally, convert data to Parquet with columnar compression and use partition projection in Athena to eliminate Glue Catalog calls for partition discovery
Jawaban Benar: D
This multi-pronged optimization addresses Athena's cost model ($5/TB scanned): (1) secondary partition on event_type allows quarterly queries that filter by specific events to skip entire partitions, potentially reducing scanned data by 80%+; (2) Parquet columnar format means Athena only reads required columns (vs. all columns in CSV/JSON); (3) compression reduces physical bytes scanned; (4) partition projection eliminates catalog lookup latency for the deeply nested partition structure. Together, a $250 quarterly query might drop to $30-50.

Opsi A: SALAH. S3 Select works with individual objects and doesn't integrate well with Athena's partition pruning or columnar format optimizations — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: SALAH. File size optimization helps with listing overhead but doesn't reduce data scanned (the main cost driver).
Opsi C: SALAH. Glacier has minimum 1-12 hour restore times, making quarterly reports impractical without advance planning; restore costs are also significant.
Opsi D: BENAR.

#DynamoDB
A DynamoDB table stores user profiles for a social application. The primary key is user_id (partition key only). The application needs to support three additional access patterns: (1) find all users in a specific city, (2) find all users who registered in the last 30 days, and (3) find users by email address for login lookups. Each pattern is queried at different frequencies — email lookup at 10,000 RPS, city lookup at 100 RPS, and registration date at 10 RPS. Which index strategy is MOST cost-effective and performant?
  • A. Create Local Secondary Indexes for all three attributes since they provide strongly consistent reads, integrating natively with the rest of the pipeline and avoiding charges for idle provisioned capacity and handling the described workload reliably at scale and keeping steady-state operating costs low and optimizing cost for the described workload
  • B. Create three Global Secondary Indexes: GSI1 (partition key: email) for login lookups with provisioned capacity matching 10K RPS, GSI2 (partition key: city, sort key: user_id) for city queries, and GSI3 (partition key: registration_month, sort key: registration_date) for recent registrations. Project only necessary attributes to minimize GSI storage costs
  • C. Create a single GSI with a generic partition key (GSI_PK) and sort key (GSI_SK) using the overloading pattern: store email, city, and registration_date as different GSI_PK values with a type prefix (e.g., "EMAIL#user@test.com", "CITY#Seattle"), optimizing cost for the described workload and avoiding charges for idle provisioned capacity
  • D. Use DynamoDB Scan operations with FilterExpressions on each attribute for all three access patterns with partition-level ordering and dedicated throughput, satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline and keeping steady-state operating costs low and providing exactly-once processing semantics
Jawaban Benar: B
Three separate GSIs, each optimized for its specific access pattern, provides the best performance and cost efficiency: (1) email GSI handles 10K RPS login lookups as O(1) point reads; (2) city GSI groups users by city for efficient listing; (3) registration_month GSI enables time-range queries. Projecting only needed attributes (KEYS_ONLY or INCLUDE specific attributes) minimizes GSI storage and write costs. Each GSI can have independent provisioned capacity matching its traffic pattern.

Opsi A: SALAH. LSIs require a composite primary key (partition + sort) on the base table and share throughput with the base table; they can't be created on a table that already exists with a simple key.
Opsi B: BENAR.
Opsi C: SALAH. GSI overloading with a single index means all three access patterns compete for the same partition key space and provisioned capacity; the 10K RPS email pattern would dominate capacity, and the different access pattern frequencies make independent scaling impossible.
Opsi D: SALAH. Scan operations read every item in the table and apply filters after reading, consuming full table RCUs regardless of result set size — prohibitively expensive at scale — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

#Redshift
A Redshift data warehouse serves a BI dashboard that runs the same 20 complex queries repeatedly throughout the day with different time-range parameters. Each query scans 500 GB and takes 45 seconds. The dashboard refreshes every 15 minutes, and 50 concurrent users access it during business hours. The team needs to reduce query response time to under 5 seconds for the dashboard while keeping the underlying data fresh. Which Redshift feature MOST effectively addresses this access pattern?
  • A. Create regular views for the 20 queries and have the BI tool query the views instead of the base tables with AUTO REFRESH enabled, integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort
  • B. Create materialized views for the 20 dashboard queries with AUTO REFRESH enabled, so Redshift pre-computes and caches results that are automatically refreshed when underlying data changes, serving dashboard queries from the materialized view in milliseconds instead of scanning 500 GB each time
  • C. Enable Redshift result caching, which automatically caches query results and serves identical queries from cache without re-execution, satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline and handling the described workload reliably at scale
  • D. Add more nodes to the Redshift cluster to increase parallel processing capacity and reduce query time through horizontal scaling, integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort and satisfying strict compliance and audit requirements
Jawaban Benar: B
Materialized views pre-compute and physically store query results, serving subsequent queries from the stored result set in milliseconds. AUTO REFRESH keeps the materialized view synchronized with base table changes, ensuring dashboard data freshness. Since the 20 queries are predictable and repeated, materialized views eliminate the 45-second full scan on every refresh. Redshift can also automatically rewrite incoming queries to use materialized views transparently.

Opsi A: SALAH. Regular views are just stored query text; they execute the full query every time they're accessed, providing no performance benefit over querying tables directly — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: BENAR.
Opsi C: SALAH. Result caching works for identical queries (same SQL text and parameters), but dashboard queries with different time-range parameters produce different SQL each time, bypassing the cache.
Opsi D: SALAH. Adding nodes provides linear speedup (45s → maybe 15-20s with double nodes) but cannot achieve the sub-5-second requirement without addressing the fundamental access pattern.

A multi-tenant analytics application stores data for 1,000 tenants in a shared Amazon Redshift cluster. Each tenant's queries should only access their own data. The largest 5 tenants generate 60% of total query volume. The team needs to prevent large-tenant queries from degrading performance for smaller tenants while maintaining data isolation. Which Redshift configuration addresses BOTH performance isolation and data access control?
  • A. Use Redshift Workload Management (WLM) with query queues: create a "large tenant" queue with limited concurrency and memory allocation (e.g., 40% of memory, max 5 concurrent queries) and a "standard tenant" queue with higher concurrency (60% memory, 15 concurrent queries). Combine with row-level security policies using Redshift RLS to restrict each tenant to their own data rows
  • B. Create separate Redshift clusters for each of the 1,000 tenants to ensure complete isolation, meeting the latency and throughput goals of the design and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort and handling the described workload reliably at scale and absorbing sudden traffic spikes without throttling
  • C. Use IAM policies to restrict Redshift access at the cluster level, with separate database users per tenant and memory allocation, integrating natively with the rest of the pipeline and handling the described workload reliably at scale and meeting the latency and throughput goals of the design and satisfying all of the stated requirements with minimal effort
  • D. Implement application-level filtering by adding WHERE tenant_id = :current_tenant to every query in the application code, handling the described workload reliably at scale and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and minimizing end-to-end processing latency
Jawaban Benar: A
WLM provides performance isolation by allocating resources to query queues — large tenants get dedicated resources that can't starve smaller tenants, even when running resource-intensive queries. Queue concurrency limits prevent large tenants from monopolizing all query slots. Row-Level Security (RLS) enforces data isolation at the database level — users see only their tenant's rows regardless of the SQL they execute, preventing accidental or malicious cross-tenant data access. Together, these address both requirements.

Opsi A: BENAR.
Opsi B: SALAH. 1,000 separate clusters is operationally impractical and prohibitively expensive (~$1M+/year at minimum cluster costs).
Opsi C: SALAH. IAM controls who can connect to the cluster but cannot restrict which rows within shared tables a user can see — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi D: SALAH. Application-level filtering is error-prone (one missed WHERE clause exposes all data) and provides no performance isolation between tenants.

A DynamoDB table stores order data with partition key order_id. The application needs to display a customer's order history sorted by order_date (most recent first) with pagination support. A customer may have thousands of orders. The query must be efficient, returning 20 orders per page with the ability to fetch the next page. Which DynamoDB design pattern BEST supports this paginated, sorted access pattern?
  • A. Use the base table with a Scan operation filtered by customer_id, sort results in application memory, and implement offset-based pagination, keeping every related record in its produced order and meeting the latency and throughput goals of the design
  • B. Store all orders for a customer in a single DynamoDB item as a list attribute, and use application logic to sort and paginate the list with partition key customer_id, handling the described workload reliably at scale and keeping steady-state operating costs low
  • C. Create a GSI with partition key customer_id and sort key order_date (stored as ISO-8601 string for lexicographic sorting). Query the GSI with ScanIndexForward=false (descending order), Limit=20 for page size, and use the returned LastEvaluatedKey as ExclusiveStartKey for subsequent page requests
  • D. Create a GSI with partition key customer_id and no sort key, then sort results alphabetically by order_id in the application, satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design
Jawaban Benar: C
This design leverages DynamoDB's native capabilities optimally: (1) GSI with customer_id as partition key groups all orders for a customer together; (2) order_date as sort key physically stores items in chronological order within the partition; (3) ScanIndexForward=false reverses the sort for "most recent first"; (4) Limit=20 returns exactly one page; (5) LastEvaluatedKey/ExclusiveStartKey provides server-side cursor-based pagination that's efficient regardless of dataset size. Each page request reads only 20 items — O(1) cost per page.

Opsi A: SALAH. Scan reads the entire table (all customers' orders), consuming massive RCUs and taking minutes; offset-based pagination requires re-reading all previous pages.
Opsi B: SALAH. DynamoDB items have a 400 KB limit; thousands of orders would exceed this, and list operations don't support efficient pagination — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: BENAR.
Opsi D: SALAH. Without a sort key, Query returns items in arbitrary order within the partition; application-side sorting requires fetching ALL items first, defeating pagination efficiency.

  • A. Increase the cluster size to have enough resources for both workloads to run simultaneously without contention, meeting the latency and throughput goals of the design and reducing day-to-day operational effort and integrating natively with the rest of the pipeline and requiring no servers to manage or scale manually and removing the need to provision or patch any infrastructure
  • B. Schedule analytical queries to run only during off-peak hours (nights and weekends) when API traffic is low with two separate queues: an "analytical" queue with low concurrency (3 slots), removing the need to provision or patch any infrastructure and handling the described workload reliably at scale and integrating natively with the rest of the pipeline and reducing day-to-day operational effort
  • C.   • D. WLM queue configuration with SQA directly solves the mixed-workload problem: (1) separate queues ensure analytical queries cannot consume resources allocated to API queries; (2) high concurrency for API queue means many short queries can execute simultaneously; (3) SQA detects short-running queries and routes them to a special fast lane, bypassing queued long queries; (4) query timeouts prevent runaway queries from holding resources indefinitely. Opsi A: SALAH. More resources reduce contention probability but don't guarantee isolation; a sufficiently complex analytical query can still monopolize shared resources.

Opsi D: BENAR.

A data team uses AWS Lake Formation to manage access to a data lake containing sensitive employee data. The HR department needs access to all employee fields including salary and SSN. The finance department needs salary data but not SSN. The marketing department needs only names and department for internal communications. All teams query the same underlying table in S3 via Athena. Which Lake Formation access control configuration MOST efficiently implements these differential access patterns?
  • A. Create three Athena named queries with appropriate column selections and train each team to only use their designated query and grant Marketing access only to name and department columns, validating and cleansing each record before delivery and satisfying all of the stated requirements with minimal effort
  • B. Use Lake Formation column-level permissions: grant HR full table access, grant Finance access to all columns except SSN, and grant Marketing access only to name and department columns. When users query via Athena, Lake Formation automatically enforces these column restrictions regardless of the SQL submitted
  • C. Create three separate copies of the data in S3: one with all columns for HR, one without SSN for Finance, and one with only name/department for Marketing, meeting the latency and throughput goals of the design and handling the described workload reliably at scale
  • D. Use IAM policies with S3 resource-level permissions to restrict access to specific Parquet column groups within S3 objects, satisfying all of the stated requirements with minimal effort and handling the described workload reliably at scale and satisfying strict compliance and audit requirements and providing exactly-once processing semantics
Jawaban Benar: B
Lake Formation column-level permissions are purpose-built for this scenario: permissions are granted on specific columns to specific principals, and enforcement happens transparently at query time — if Finance queries SELECT * FROM employees, Lake Formation automatically excludes SSN from results. This works across Athena, Redshift Spectrum, and Glue jobs without application changes. Single source of truth, centralized management, auditable access.

Opsi A: SALAH. Named queries are suggestions, not enforcement; users can write their own SQL selecting any columns, providing no actual security — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi B: BENAR.
Opsi C: SALAH. Data duplication creates sync issues (updates must propagate to all copies), triples storage costs, and doesn't prevent someone from accessing the wrong copy.
Opsi D: SALAH. IAM cannot provide column-level access control within Parquet files; S3 permissions are at the object (file) level, not column level.
