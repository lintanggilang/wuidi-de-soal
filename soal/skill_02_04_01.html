A data engineer is designing an Amazon Redshift schema for a sales analytics data warehouse. The primary query pattern involves filtering by date and joining the fact table with dimension tables. The fact table contains 5 billion rows with sales transactions spanning 3 years. Which distribution and sort key strategy provides OPTIMAL query performance?
  • A. KEY distribution on transaction_date with no sort key for maximum write performance configured for optimal performance and minimal operational overhead
  • B. ALL distribution on the fact table with a compound sort key on transaction_date, applying schema conversion and enrichment inline
  • C. KEY distribution on the most frequently joined column (product_id) with a compound sort key starting with transaction_date
  • D. EVEN distribution on the fact table with an interleaved sort key on date and product_id
Correct Answer: C
KEY distribution on kolom that most often in-join (such as product_id) ensures that rows with value that same berada in node that same, avoids data redistribution saat join. Compound sort key that dimulai with transaction_date enables zone maps for performs block-level pruning on filter tanggal, very effective for range queries.

Option A: INCORRECT. Will menyebabkan data skew if tanggal not merata — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Not may for table 5 miliar rows — ALL only suitable for dimension tables small.
Option C: CORRECT.
Option D: INCORRECT. Interleaved sort key has overhead maintenance that high for table large.

A social media company is designing a DynamoDB table to store user posts. Access patterns include: (1) Get all posts by a user sorted by timestamp, (2) Get a specific post by user and post ID, (3) Get all posts with a specific hashtag sorted by engagement score. Which key design supports ALL three access patterns?
  • A. Partition key: post_id only. GSI with partition key: user_id, sort key: timestamp with partition-level ordering
  • B. Partition key: hashtag, Sort key: engagement_score. GSI with partition key: user_id, sort key: timestamp
  • C. Partition key: user_id, Sort key: post_id. GSI with partition key: hashtag, sort key: timestamp
  • D. Partition key: user_id, Sort key: timestamp. GSI with partition key: hashtag, sort key: engagement_score
Correct Answer: D
Pattern 1 (posts by user sorted by time): PK=user_id, SK=timestamp enables query with ScanIndexForward. Pattern 2 (specific post): can uses PK=user_id and filter on post_id (or encode post_id in sort key with composite key). Pattern 3 (hashtag + engagement): GSI with PK=hashtag, SK=engagement_score.

Option A: INCORRECT. Not supports pattern 1 efficient from base table — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Uses hashtag sebagai PK main that menyebabkan hot partition for hashtag populer.
Option C: INCORRECT. Uses post_id sebagai sort key that not supports sorting by timestamp in a native.
Option D: CORRECT.

A data engineer is implementing a star schema in Amazon Redshift for a retail analytics platform. The dimension tables range from 1,000 rows (store dimension) to 5 million rows (customer dimension). The fact table has 10 billion rows. Which distribution strategy should be applied to the dimension tables?
  • A. KEY distribution for all dimension tables on their primary key, validating and cleansing each record before delivery and keeping steady-state operating costs low
  • B. EVEN distribution for all dimension tables configured for optimal performance and minimal operational overhead, scaling elastically to millions of events per second
  • C. ALL distribution for all dimension tables regardless of size, handling the described workload reliably at scale and applying schema conversion and enrichment inline
  • D. ALL distribution for small dimensions (store: 1,000 rows) and KEY distribution for large dimensions (customer: 5M rows) on their primary key
Correct Answer: D
Strategi optimal: dimension small (< several juta rows) gunakan ALL distribution so that entire table direplikasi in each node, avoids redistribution saat join. Dimension large (5M+ rows) gunakan KEY distribution on kolom join to fact table, because ALL distribution for table large membuang storage and memperlambat write.

Option A: INCORRECT. Not optimal for dimension small that better direplikasi full.
Option B: INCORRECT. Will requires data redistribution saat each join — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Membuang storage for dimension 5M rows that direplikasi in each node.
Option D: CORRECT.

A data engineer designs a DynamoDB single-table design for an e-commerce platform. The table stores Orders, Products, and Customers in one table using overloaded partition and sort keys (PK/SK). The engineer needs to model a one-to-many relationship where one customer has many orders. Which key pattern correctly implements this?
  • A. PK: ORDER#<order_id>, SK: CUSTOMER#<customer_id> for linking orders to customers, handling the described workload reliably at scale
  • B. PK: CUSTOMER#<id>, SK: METADATA for customer; separate PK: ORDER#<order_id>, SK: METADATA for each order with no partition key connection
  • C. PK: CUSTOMER#<id>, SK: CUSTOMER#<id> for customer record; PK: CUSTOMER#<id>, SK: ORDER#<order_id> for each order
  • D. Store a list of order IDs as a Set attribute within the customer item for customer record; PK: CUSTOMER#<id>
Correct Answer: C
In single-table design, one-to-many relationship dimodelkan with menempatkan parent and children items in partition key that same. PK=CUSTOMER#123, SK=CUSTOMER#123 for record customer, and PK=CUSTOMER#123, SK=ORDER#456 for each order. Ini enables satu Query operation for gets customer beserta all order-nya.

Option A: INCORRECT. Memisahkan orders to partition different so that cannot query customer + orders in satu operasi.
Option B: INCORRECT. Not memanfaatkan item collection.
Option C: CORRECT.
Option D: INCORRECT. Melanggar best practice because Set has limit 400KB per item and not scalable — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data lake architect needs to design a partitioning strategy for a Lake Formation table that stores IoT sensor data. The table receives 100 million records daily and common queries filter by device_type (5 types), region (10 regions), and date. Current query patterns primarily filter by date range and region. Which partitioning strategy BEST optimizes query performance?
  • A. No partitioning — rely on columnar format (Parquet) with predicate pushdown
  • B. Partition by region and year/month/day (multi-level partitioning)
  • C. Partition by year/month/day/hour for maximum granularity
  • D. Partition by device_type, region, and year/month/day/hour
Correct Answer: B
Partitioning must mengikuti query patterns main. Because queries especially filter by date range and region, partition by region/year/month/day enables Athena and Redshift Spectrum performs partition pruning that effective.

Option A: INCORRECT. Memaksa full scan 100M records/days that very slow for table large.
Option B: CORRECT.
Option C: INCORRECT. Terlalu many partition (365×24 = 8.760/years) and not memanfaatkan region filter.
Option D: INCORRECT. Menghasilkan partition explosion: 5×10×365×24 = 438.000 partition/years that too many and menyebabkan overhead metadata.

A data engineer receives JSON data with nested and variable structures from multiple API sources. They need to store and query this data in Amazon Redshift. The JSON schema changes frequently with new fields added by upstream teams. Which Redshift data type is MOST appropriate for this use case?
  • A. VARBYTE type for binary JSON storage with UDF for parsing and PartiQL queries for navigation
  • B. Multiple VARCHAR columns with one column per known JSON field
  • C. SUPER data type with schemaless storage and PartiQL queries for navigation
  • D. VARCHAR(MAX) to store raw JSON strings and parse with JSON_EXTRACT_PATH_TEXT at query time
Correct Answer: C
Redshift SUPER data type designed for semi-structured data (JSON, arrays, nested objects). SUPER stores data in format binary that efficient, supports schemaless ingestion (schema-on-read), and can in-query uses PartiQL or dot notation. This is ideal when schema often changes.

Option A: INCORRECT. For binary data, not structured JSON navigation — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Not flexible when fields changes.
Option C: CORRECT.
Option D: INCORRECT. Bekerja but less efficient — there is no columnar optimization and parsing ulang each query.

A data engineer is designing a Redshift schema for an advertising analytics platform. Queries frequently aggregate impression counts by campaign_id for specific date ranges. The table has 20 billion rows distributed across a 10-node cluster. Which sort key strategy minimizes I/O for these queries?
  • A. Compound sort key with impression_date as the leading column followed by campaign_id
  • B. No sort key — use materialized views for pre-aggregation instead with impression_date as
  • C. Interleaved sort key on (impression_date, campaign_id) for equal weight filtering
  • D. Compound sort key with campaign_id as the leading column followed by impression_date
Correct Answer: A
Compound sort key with impression_date sebagai leading column optimal when queries always filter by date range first. Zone maps in Redshift stores min/max values per block — leading sort column enables maximum block skipping. Date range filter mengeliminasi partly large blocks, then campaign_id filter is applied on subset that tersisa.

Option A: CORRECT.
Option B: INCORRECT. Menghindari problem but adds storage cost — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. Has overhead VACUUM that high for table 20B rows and not seefisien compound when ada satu dominant filter pattern.
Option D: INCORRECT. Menempatkan campaign_id pertama — less efficient because range scan on date more selective.

A gaming company uses DynamoDB to track player inventory. Each player can have up to 500 items. The most common operations are: (1) Get all items for a player, (2) Get a specific item for a player, (3) Update quantity of a specific item. The data engineer wants to avoid hot partitions. Which table design is MOST appropriate?
  • A. Partition key: item_id, Sort key: player_id. Create GSI with player_id as partition key
  • B. Partition key: player_id, Sort key: item_id. Store each inventory item as a separate DynamoDB item
  • C. Partition key: composite of player_id#shard_number with write sharding with partition-level ordering and dedicated throughput
  • D. Partition key: player_id only. Store entire inventory as a JSON Map attribute in a single item
Correct Answer: B
PK=player_id, SK=item_id supports all access patterns in a optimal: (1) Query PK=player_id gets all items, (2) GetItem PK=player_id SK=item_id gets item specific, (3) UpdateItem PK=player_id SK=item_id updates quantity. By 500 items per player, item collection still in bawah 10GB partition limit.

Option A: INCORRECT. Not efficient for "get all items by player".
Option B: CORRECT.
Option C: INCORRECT. Not is required — player_id already provides distribusi that baik natural — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Has limit 400KB per item and each update requires read-modify-write entire map.

A retail data warehouse team is debating between star schema and snowflake schema for their Redshift implementation. The warehouse serves both ad-hoc analyst queries and BI dashboard reports. The product dimension has sub-dimensions: category → subcategory → brand hierarchy. Which approach is RECOMMENDED for Amazon Redshift?
  • A. Snowflake schema to normalize product dimensions into separate tables for storage efficiency
  • B. Star schema with denormalized product dimension containing all hierarchy levels in one table
  • C. Third normal form (3NF) for all tables to maintain data integrity with denormalized product dimension
  • D. Separate schemas for analysts (snowflake) and dashboards (star) with ETL between them
Correct Answer: B
Star schema with denormalized dimensions is best practice for Amazon Redshift. Redshift dioptimalkan for join patterns simple (fact-to-dimension) and columnar storage creates denormalization cheap from segi storage. Denormalized dimension reduces number joins, increases query performance.

Option A: INCORRECT. Adds joins that expensive in Redshift — each join requires data redistribution.
Option B: CORRECT.
Option C: INCORRECT. Very not suitable for analytics workload — too many joins — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Adds complexity maintenance without benefit significant — satu star schema melayani keduanya with baik.

A data engineer is designing a data lake table in AWS Lake Formation for customer transaction data. The table will be queried by multiple teams using Athena, Redshift Spectrum, and EMR. The data arrives as JSON and needs to be stored optimally. Which combination of format and schema approach is MOST appropriate for the data lake?
  • A. Convert to Apache Parquet with schema-on-write, register in Glue Data Catalog, and partition by date
  • B. Store as CSV with explicit headers and create Athena views for schema abstraction
  • C. Convert to Apache ORC and store without Glue Data Catalog registration with schema-on-write and partition by date
  • D. Store as raw JSON with schema-on-read using Glue Crawlers to infer schema automatically
Correct Answer: A
Apache Parquet with schema-on-write is best practice for data lake analytics. Parquet provides columnar storage that efficient, compression that baik, and predicate pushdown. Registrasi in Glue Data Catalog enables discovery by all query engines (Athena, Spectrum, EMR). Partitioning by date enables partition pruning.

Option A: CORRECT.
Option B: INCORRECT. Not supports complex types, not columnar, and compression less baik.
Option C: INCORRECT. Not can in-discover by Lake Formation and tools others — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Very not efficient for analytics — not columnar, not compressed optimal, and schema inference can bermasalah.
