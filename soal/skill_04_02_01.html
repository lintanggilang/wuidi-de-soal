Skill 4.2.1: Create Custom IAM Policies When a Managed Policy Does Not Meet the Needs

Writing custom IAM policies with fine-grained permissions for data engineering resources

1
A data engineering team needs a custom IAM policy for their Glue ETL role. The role should: (1) Read from any S3 bucket with prefix "raw/", (2) Write only to the "processed/" prefix in a specific bucket "data-lake-prod", and (3) NOT be able to delete any S3 objects. Which policy statement set correctly implements these requirements?
  • A. A single Allow statement with s3:* on all resources, combined with a Deny on s3:DeleteObject
  • B. Statement 1: Allow s3:GetObject on "arn:aws:s3:::*/raw/*"; Statement 2: Allow s3:PutObject on "arn:aws:s3:::data-lake-prod/processed/*"; Statement 3: Deny s3:DeleteObject on "arn:aws:s3:::*"
  • C. Allow s3:GetObject and s3:PutObject on "arn:aws:s3:::data-lake-prod/*" only
  • D. Allow s3:GetObject on "arn:aws:s3:::*/raw/*" and s3:PutObject on "arn:aws:s3:::data-lake-prod/processed/*" without explicit deny
Jawaban Benar: B
Policy ini menerapkan least privilege dengan tepat: Statement 1 (Allow GetObject on */raw/*): Mengizinkan read dari ANY bucket tapi HANYA prefix "raw/" — memenuhi requirement #1. Statement 2 (Allow PutObject on specific bucket/prefix): Write hanya ke data-lake-prod/processed/* — memenuhi requirement #2. Statement 3 (Explicit Deny DeleteObject): Explicit Deny pada DeleteObject untuk semua S3 resources memastikan TIDAK ADA policy lain yang bisa override (explicit Deny always wins) — memenuhi requirement #3. Opsi A (s3:* + Deny) memberikan terlalu banyak permissions (s3:PutObject ke semua buckets). Opsi C terlalu restrictive (hanya satu bucket) dan memungkinkan write ke semua prefixes. Opsi D memenuhi requirements #1 dan #2 tapi tanpa explicit Deny, policy lain bisa memberikan DeleteObject permission.
2
A company wants to ensure that Glue jobs can only be created and run within the eu-west-1 region to comply with GDPR data residency requirements. The data engineer needs to add a condition to the IAM policy. Which condition key and structure correctly enforces this?
  • A. "Condition": {"StringEquals": {"aws:RequestedRegion": "eu-west-1"}} applied to a Deny statement when NOT eu-west-1
  • B. "Condition": {"StringEquals": {"aws:SourceRegion": "eu-west-1"}} on the Allow statement
  • C. "Condition": {"StringNotEquals": {"aws:RequestedRegion": "eu-west-1"}} applied to a Deny statement with Effect "Deny" on glue:* actions
  • D. "Condition": {"IpAddress": {"aws:SourceIp": "eu-west-1"}} on the Allow statement
Jawaban Benar: C
Untuk enforce regional restrictions, gunakan explicit Deny dengan condition StringNotEquals pada aws:RequestedRegion. Policy: {"Effect": "Deny", "Action": "glue:*", "Resource": "*", "Condition": {"StringNotEquals": {"aws:RequestedRegion": "eu-west-1"}}}. Ini artinya: DENY semua Glue actions jika region yang diminta BUKAN eu-west-1. Explicit Deny selalu override Allow policies manapun, sehingga bahkan jika ada Allow policy untuk Glue di region lain, Deny akan berlaku. aws:RequestedRegion adalah global condition key yang berisi region tempat API call ditujukan. Opsi A memiliki logic yang benar tapi deskripsinya membingungkan — ini sebenarnya sama dengan C jika diterapkan dengan benar. Opsi B — aws:SourceRegion bukan condition key yang valid untuk scenario ini. Opsi D — aws:SourceIp berisi IP address, bukan region name.
3
A data engineer's custom IAM policy is approaching the 6,144 character limit for managed policies. The policy needs to grant access to 50+ specific Glue databases and S3 paths. Which strategy allows the engineer to stay within the size limit while maintaining fine-grained access control?
  • A. Use wildcard (*) in resource ARNs to cover all databases and paths with a single statement
  • B. Use IAM policy variables (e.g., ${aws:PrincipalTag/team}) combined with consistent resource naming conventions to dynamically reference resources, reducing the number of explicit ARN entries needed
  • C. Convert all permissions to inline policies which have no size limit
  • D. Remove all condition blocks to save characters
Jawaban Benar: B
IAM policy variables memungkinkan dynamic resource resolution berdasarkan request context. Contoh: jika databases dinamai sesuai team tag (team-analytics-db, team-ml-db), Resource ARN bisa ditulis sebagai "arn:aws:glue:*:*:database/${aws:PrincipalTag/team}-*". Satu statement ini replace 50+ explicit ARN entries. Strategi lain untuk size management: (1) Group resources by common prefix patterns, (2) Use multiple managed policies (max 10 per role), (3) Combine conditions efficiently. Opsi A (wildcard) sacrifices fine-grained control — memberikan akses ke SEMUA databases. Opsi C salah — inline policies memiliki limit 2,048 characters (lebih kecil dari managed policy). Opsi D (remove conditions) removes security controls dan doesn't solve root cause jika resources dominate the policy size.

A data engineer wants to test a newly created custom IAM policy before attaching it to the production Glue role. The policy grants access to specific Redshift clusters and S3 paths. Which approach allows safe testing without affecting production workloads?
  • A. Attach the policy to the production role and monitor CloudTrail for errors
  • B. Use the IAM Policy Simulator to test the policy against specific actions and resources, then validate in a non-production environment before applying to the production role
  • C. Deploy the policy in a separate AWS region to test isolation
  • D. Add the policy with a start date condition set to tomorrow to give time to review
Jawaban Benar: B
IAM Policy Simulator (https://policysim.aws.amazon.com) memungkinkan testing policies tanpa deployment: (1) Input policy JSON, (2) Select specific actions (redshift:GetClusterCredentials, s3:GetObject, etc.), (3) Specify resource ARNs, (4) Simulator evaluates policy dan shows Allow/Deny/Implicit Deny result. Best practice workflow: Step 1 — Simulate policy dengan Policy Simulator untuk semua expected actions. Step 2 — Attach policy ke test role di non-prod environment. Step 3 — Run test workloads dan verify CloudTrail untuk access patterns. Step 4 — Setelah validated, attach ke production role. Opsi A langsung ke production — risky jika policy terlalu restrictive (break production) atau terlalu permissive (security gap). Opsi C — IAM policies are global, region separation tidak membantu testing. Opsi D — DateGreaterThan condition bisa bekerja tapi bukan proper testing approach.
5
A security team discovers that a data engineer accidentally created a policy with "Effect": "Allow", "Action": "s3:*", "Resource": "*" — granting full S3 access. They need to quickly restrict this without removing the policy (as other statements in it are needed). Which approach provides the FASTEST mitigation while maintaining other permissions?
  • A. Delete the entire policy and recreate it correctly
  • B. Add an explicit Deny statement to the same policy (or a permissions boundary) that blocks all S3 actions EXCEPT the specific actions and resources that are actually needed
  • C. Contact AWS Support to temporarily disable the policy
  • D. Remove the IAM role from the service entirely
Jawaban Benar: B
Fastest mitigation: Tambahkan explicit Deny statement yang membatasi overly-broad permissions. Approach: (1) Add Deny statement untuk dangerous actions (s3:DeleteBucket, s3:PutBucketPolicy, etc.) dan resources yang seharusnya tidak diakses, ATAU (2) Attach a Permissions Boundary yang defines maximum allowed permissions — boundary acts as ceiling regardless of identity policies. Permissions Boundary particularly useful karena: dapat di-apply tanpa modifying existing policy, immediately restricts effective permissions, doesn't break other needed statements. Contoh Deny: {"Effect": "Deny", "Action": ["s3:Delete*", "s3:PutBucket*"], "Resource": "*"} plus {"Effect": "Deny", "Action": "s3:*", "NotResource": ["arn:aws:s3:::allowed-bucket/*"]}. Opsi A (delete) disruptive jika policy has other needed statements. Opsi C (AWS Support) terlalu lambat untuk security incident. Opsi D (remove role) breaks ALL services attached to it.
6
A data engineer needs to create an IAM policy that allows a Lambda function to assume a role in another account (Account B: 333333333333) for cross-account data access to Redshift. The policy should only allow assumption during business hours (8 AM - 6 PM UTC, Monday-Friday). Which policy structure correctly implements this time-based cross-account access?
  • A. Allow sts:AssumeRole on the target role ARN with conditions: DateGreaterThanEquals {"aws:CurrentTime": "08:00:00Z"} AND DateLessThanEquals {"aws:CurrentTime": "18:00:00Z"} AND StringEquals {"aws:RequestedRegion": "us-east-1"}
  • B. Allow sts:AssumeRole on "arn:aws:iam::333333333333:role/CrossAccountRedshiftRole" with conditions: NumericGreaterThanEquals {"aws:MultiFactorAuthAge": "0"}
  • C. Allow sts:AssumeRole on "arn:aws:iam::333333333333:role/CrossAccountRedshiftRole" with conditions: DateGreaterThanEquals {"aws:CurrentTime": "2024-01-01T08:00:00Z"} AND DateLessThanEquals {"aws:CurrentTime": "2024-01-01T18:00:00Z"}
  • D. Allow sts:AssumeRole on "arn:aws:iam::333333333333:role/CrossAccountRedshiftRole" with conditions using aws:TokenIssueTime to restrict hours
Jawaban Benar: A
Untuk time-based access control, gunakan aws:CurrentTime condition key dengan DateGreaterThanEquals dan DateLessThanEquals operators. Format time-only (08:00:00Z) membuat condition berulang setiap hari (tanpa fixed date). Policy structure: {"Effect": "Allow", "Action": "sts:AssumeRole", "Resource": "arn:aws:iam::333333333333:role/CrossAccountRedshiftRole", "Condition": {"DateGreaterThanEquals": {"aws:CurrentTime": "08:00:00Z"}, "DateLessThanEquals": {"aws:CurrentTime": "18:00:00Z"}}}. Catatan: aws:CurrentTime dengan time-only format memungkinkan daily recurring windows. Untuk day-of-week restriction, memerlukan tambahan custom logic (Lambda authorizer) karena IAM tidak natively support day-of-week conditions. Opsi B (MFA age) mengecek MFA, bukan time. Opsi C menggunakan fixed date — hanya berlaku pada satu hari. Opsi D — aws:TokenIssueTime tracks kapan token dibuat, bukan current time.
7
A data platform team uses tag-based access control. They want to ensure that data engineers can only manage Glue jobs and crawlers that belong to their own team. Each engineer has a tag "team" on their IAM principal, and Glue resources are tagged with the same "team" tag. Which IAM policy condition implements this attribute-based access control (ABAC)?
  • A. Condition: {"StringEquals": {"aws:ResourceTag/team": "${aws:PrincipalTag/team}"}}
  • B. Condition: {"StringEquals": {"aws:RequestTag/team": "data-engineering"}}
  • C. Condition: {"StringEquals": {"glue:ResourceTag/team": "${aws:username}"}}
  • D. Condition: {"ForAllValues:StringEquals": {"aws:TagKeys": ["team"]}}
Jawaban Benar: A
ABAC (Attribute-Based Access Control) menggunakan tags untuk dynamic authorization. Condition key aws:ResourceTag/team mendapatkan value tag "team" pada resource yang diakses. Policy variable ${aws:PrincipalTag/team} mendapatkan value tag "team" dari calling principal (IAM user/role). Dengan StringEquals comparison: akses hanya diizinkan jika tag "team" pada resource SAMA dengan tag "team" pada principal. Jika engineer memiliki tag team=analytics, mereka hanya bisa manage Glue jobs yang juga tagged team=analytics. Benefit: tidak perlu update policy saat team members berubah — cukup manage tags. Opsi B hardcodes satu team value — tidak dynamic. Opsi C menggunakan ${aws:username} yang bukan team identifier. Opsi D (ForAllValues:TagKeys) hanya checks apakah tag key "team" ada, bukan value comparison.
8
A data engineer needs to write a custom policy for a Glue Crawler role. The crawler needs to: access a specific S3 source path, write metadata to the Glue Data Catalog (specific database only), and write logs to CloudWatch. The existing AWS managed policy AWSGlueServiceRole is too permissive. Which custom policy follows least privilege MOST accurately?
  • A. Use AWSGlueServiceRole managed policy and add a Deny statement for unnecessary permissions
  • B. Custom policy with: (1) s3:GetObject on specific source path ARN, (2) glue:CreateTable, glue:UpdateTable, glue:GetDatabase on specific database ARN, (3) logs:CreateLogGroup, logs:CreateLogStream, logs:PutLogEvents on the specific log group ARN
  • C. Custom policy with: s3:*, glue:*, logs:* on Resource "*"
  • D. Custom policy with only s3:GetObject — Glue will automatically have catalog and logging permissions
Jawaban Benar: B
Least privilege means granting ONLY the exact permissions needed, on the exact resources needed: S3: s3:GetObject (read only, no list/write) on "arn:aws:s3:::source-bucket/source-path/*" — crawler reads objects from specific path. Glue Catalog: glue:CreateTable, glue:UpdateTable, glue:BatchCreatePartition, glue:GetDatabase on "arn:aws:glue:region:account:database/specific-db" dan "arn:aws:glue:region:account:table/specific-db/*" — only the target database. CloudWatch Logs: logs:CreateLogGroup, logs:CreateLogStream, logs:PutLogEvents on "arn:aws:logs:region:account:log-group:/aws-glue/crawlers*" — specific log group. Opsi A (managed + Deny) is complex dan AWSGlueServiceRole grants access ke ALL databases/S3 paths. Opsi C (wildcard all) violates least privilege completely. Opsi D incorrect — Glue NEEDS explicit permissions for catalog and logging.

A company requires that all S3 objects uploaded by data pipelines must be encrypted with a specific KMS key (arn:aws:kms:us-east-1:111111111111:key/abcd-1234). The data engineer needs to write a policy that DENIES any PutObject request that doesn't use this specific encryption key. Which policy statement accomplishes this?
  • A. {"Effect": "Deny", "Action": "s3:PutObject", "Resource": "arn:aws:s3:::data-bucket/*", "Condition": {"StringNotEquals": {"s3:x-amz-server-side-encryption-aws-kms-key-id": "arn:aws:kms:us-east-1:111111111111:key/abcd-1234"}}}
  • B. {"Effect": "Allow", "Action": "s3:PutObject", "Resource": "arn:aws:s3:::data-bucket/*", "Condition": {"StringEquals": {"s3:x-amz-server-side-encryption": "aws:kms"}}}
  • C. {"Effect": "Deny", "Action": "s3:PutObject", "Resource": "arn:aws:s3:::data-bucket/*", "Condition": {"Bool": {"aws:SecureTransport": "false"}}}
  • D. {"Effect": "Deny", "Action": "s3:*", "Resource": "*", "Condition": {"Null": {"s3:x-amz-server-side-encryption": "true"}}}
Jawaban Benar: A
Policy ini menggunakan Deny + StringNotEquals untuk memaksa penggunaan SPECIFIC KMS key: Jika request PutObject tidak menggunakan KMS key ID yang ditentukan → DENY. Condition key s3:x-amz-server-side-encryption-aws-kms-key-id berisi ARN KMS key yang digunakan untuk server-side encryption. StringNotEquals ensures bahwa HANYA key spesifik tersebut yang diterima — bukan key lain, bukan encryption type lain. Opsi B (Allow with aws:kms) hanya memastikan KMS encryption digunakan tapi tidak memaksa KEY SPESIFIK — any KMS key would be allowed. Opsi C (SecureTransport) adalah tentang HTTPS vs HTTP transport, bukan encryption at rest. Opsi D (Null check) hanya memastikan SOME encryption header ada, tapi tidak memaksa specific key — terlalu broad (s3:* on all resources).

A data engineer has a complex IAM setup: the Glue role has an identity policy (Allow glue:StartJobRun), a permissions boundary (allows glue:* and s3:GetObject only), and the role is in an OU with an SCP that denies glue:DeleteJob. The engineer tries to run glue:StartJobRun and glue:DeleteJob. What is the effective result for EACH action?
  • A. Both actions are allowed because the identity policy has Allow
  • B. glue:StartJobRun is allowed (identity policy allows, permissions boundary allows, SCP does not deny); glue:DeleteJob is denied (SCP explicitly denies it, overriding any Allow)
  • C. Both actions are denied because the permissions boundary only allows s3:GetObject
  • D. glue:StartJobRun is denied by the permissions boundary; glue:DeleteJob is denied by the SCP
Jawaban Benar: B
IAM policy evaluation dengan multiple policy types: glue:StartJobRun evaluation: (1) Identity policy: Allow ✓, (2) Permissions boundary: allows glue:* ✓, (3) SCP: does not deny glue:StartJobRun ✓. Result: ALLOWED — all three layers permit it. glue:DeleteJob evaluation: (1) Identity policy: no explicit Allow for DeleteJob (implicit deny), tapi even if it were allowed: (2) SCP: explicit Deny on glue:DeleteJob ✗. Result: DENIED. SCP Deny overrides everything — even if identity policy AND permissions boundary both allowed it. Evaluation order: Explicit Deny (any layer) → SCP evaluation → Permissions Boundary → Identity policies → Resource policies. Key rule: untuk action to be allowed, it must be permitted by ALL applicable policy types (identity, boundary, SCP) with NO explicit deny from ANY layer. Opsi A ignores boundary/SCP. Opsi C salah — boundary allows glue:*. Opsi D salah — boundary allows glue:StartJobRun.
