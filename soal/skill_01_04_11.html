A social media analytics company needs to build a recommendation engine that identifies influencer networks. Their data consists of 50 million user profiles with "follows" relationships, and they need to find the shortest path of influence between any two users in near real-time. The data engineering team must choose the appropriate data structure and AWS service to store and query this relationship data. Which combination is MOST appropriate?
  • A. Use a graph data structure stored in Amazon Neptune, leveraging its native graph traversal capabilities with Gremlin or SPARQL queries to perform breadth-first search for shortest path calculations between users
  • B. Store the relationships in a DynamoDB table with a composite primary key (follower_id, followed_id) and use recursive scan operations to find paths between users
  • C. Load all relationships into an Amazon Redshift table with a self-join query to traverse connections between users
  • D. Store relationships as JSON documents in Amazon S3 and use AWS Glue PySpark jobs with custom BFS implementation to find paths
Jawaban Benar: A
Graph data structures are specifically designed for relationship-heavy data where traversal operations (shortest path, connected components, influence propagation) are the primary access pattern. Amazon Neptune is a purpose-built graph database that natively supports these operations with O(V+E) traversal time using BFS/DFS algorithms. Opsi B — DynamoDB is a key-value store; recursive scans for path finding would be extremely inefficient with O(n) full table scans per hop and no native graph traversal support. Opsi C — Redshift self-joins for graph traversal require multiple expensive joins proportional to path length, making real-time queries impractical at 50M nodes. Opsi D — S3 + Glue is batch-oriented and cannot provide near real-time path queries; custom BFS on flat files lacks index support.

A data engineering team is designing an ETL pipeline orchestration system using Apache Airflow on Amazon MWAA. The pipeline has 45 tasks with complex dependencies — some tasks must run in parallel, others sequentially, and no task should execute before all its prerequisites complete. The team needs to detect circular dependencies before pipeline execution to prevent infinite loops. Which data structure fundamentally enables this orchestration pattern?
  • A. A Directed Acyclic Graph (DAG) where each node represents a task and directed edges represent dependencies, allowing topological sort to determine execution order and cycle detection algorithms to validate the pipeline before execution
  • B. A doubly linked list where each task points to its predecessor and successor, allowing sequential execution in both directions
  • C. A binary tree where the root is the first task and children represent dependent tasks branching into two parallel streams
  • D. A hash table mapping task names to execution timestamps, with a scheduler that checks all entries every second to determine which tasks are ready
Jawaban Benar: A
DAGs are the fundamental data structure for workflow orchestration (Airflow literally calls its workflows "DAGs"). The directed edges encode task dependencies, the acyclic property guarantees no infinite loops, and topological sort produces a valid execution order respecting all dependencies. Cycle detection (using DFS with coloring) validates the pipeline at definition time. Opsi B — linked lists only support linear sequential execution and cannot represent parallel tasks or complex dependency patterns with multiple predecessors. Opsi C — binary trees limit each task to exactly two dependents, which doesn't model real-world pipelines where tasks may have many downstream consumers. Opsi D — hash tables provide O(1) lookup but have no inherent structure for dependency relationships or ordering.

A data lake processes 2 billion records daily. During the deduplication step, the ETL pipeline must check whether each incoming record already exists in the historical dataset of 500 billion records. The team needs a probabilistic approach that uses minimal memory and provides O(1) lookup time, accepting a small false positive rate (less than 1%) but zero false negatives. Which data structure is MOST appropriate for this use case?
  • A. A Bloom filter that uses multiple hash functions to map each record's key to a bit array, providing constant-time membership testing with guaranteed zero false negatives and configurable false positive rate based on array size and number of hash functions
  • B. A hash table storing all 500 billion record keys in memory for exact O(1) lookup with no false positives or false negatives
  • C. A B-tree index on the record key column in a relational database for O(log n) lookup time
  • D. A sorted array of all record keys using binary search for O(log n) membership testing
Jawaban Benar: A
Bloom filters are purpose-built for probabilistic membership testing. They use multiple hash functions mapping elements to a bit array, achieving O(1) lookups in constant space (typically 10 bits per element for 1% false positive rate). For 500 billion records, a Bloom filter needs approximately 600 GB — large but feasible in distributed systems — versus storing all keys which would require many terabytes. The zero false negative guarantee means every duplicate WILL be caught; the small false positive rate only causes unnecessary re-checks. Opsi B — storing 500 billion keys in a hash table would require tens of terabytes of RAM, which is impractical. Opsi C — B-tree provides O(log n) not O(1), and for 500 billion records the tree depth creates significant I/O. Opsi D — sorted arrays require keeping all keys in memory and binary search is O(log n), not O(1).

A company stores product catalog data in a hierarchical category structure (Electronics > Computers > Laptops > Gaming Laptops). The data engineering team needs to efficiently support queries like "find all products under Electronics" (subtree query) and "find the full category path from any product to the root" (ancestor query). The hierarchy has 6 levels deep with 50,000 categories. Which data structure and storage approach provides the BEST query performance for both access patterns?
  • A. A tree data structure implemented using nested set model (storing left and right boundary values for each node) in Amazon RDS, enabling subtree queries with a simple range condition (WHERE left BETWEEN parent.left AND parent.right) and ancestor queries with a reverse range condition
  • B. An adjacency list model storing only parent_id for each category in DynamoDB, requiring recursive queries to traverse up or down the hierarchy
  • C. A flat denormalized table in Redshift where each row contains the full path as a concatenated string, using LIKE queries for subtree and ancestor lookups
  • D. Store the hierarchy as a JSON document in S3 and use AWS Glue to parse the nested structure for each query
Jawaban Benar: A
The nested set model encodes tree structure as left/right boundary numbers assigned via DFS traversal. A node's subtree includes all nodes whose left value falls between the parent's left and right — this is a simple indexed range query, O(log n) with B-tree index. Ancestor queries reverse the logic. Both operations execute in a single SQL query without recursion. For 50,000 categories with heavy read operations, this provides optimal performance. Opsi B — adjacency lists require recursive traversal (CTE in SQL) for subtree queries, performing poorly for deep hierarchies and not supported natively in DynamoDB. Opsi C — string LIKE queries ('Electronics%') cannot leverage indexes efficiently and break with name changes. Opsi D — parsing JSON from S3 for every query introduces latency and lacks indexing capabilities for tree operations.

A data engineering team is implementing a hash-based partitioning strategy for distributing 10 TB of customer transaction data across an Amazon Redshift cluster with 8 nodes. They need even data distribution to prevent skew, while ensuring that all transactions for the same customer are co-located on the same node to optimize JOIN operations between the transactions and customer dimension tables. Which approach BEST achieves both goals?
  • A. Use Redshift KEY distribution style on customer_id, which applies a hash function to customer_id to deterministically assign each row to a specific node, ensuring all rows with the same customer_id land on the same slice while distributing different customer_ids evenly across nodes
  • B. Use Redshift EVEN distribution to spread rows uniformly across all nodes, then create a materialized view that groups data by customer_id for JOIN operations
  • C. Use Redshift ALL distribution to replicate the entire transaction table on every node, eliminating the need for data movement during JOINs
  • D. Manually partition the data into 8 S3 prefixes by customer_id ranges and load each prefix into a specific node using COPY with a manifest file
Jawaban Benar: A
KEY distribution applies a consistent hash function to the specified column (customer_id), mapping each unique value to a specific compute node deterministically. This achieves both goals: (1) co-location — all rows for customer_id=123 always hash to the same node, enabling local JOINs without network shuffling; (2) even distribution — assuming customer_ids have sufficient cardinality, the hash function distributes them uniformly across nodes. Opsi B — EVEN distribution scatters rows randomly, so JOINs on customer_id require expensive inter-node data redistribution at query time. Opsi C — ALL distribution replicates the entire 10 TB table on every node (80 TB total storage), which is impractical for large fact tables. Opsi D — manual range-based partitioning is fragile, cannot guarantee even distribution, and doesn't adapt to cluster resizing.

A data engineering team is building a real-time data pipeline that processes IoT sensor events. Each event must be looked up against a reference dataset of 10 million device configurations to enrich the event with device metadata. The pipeline processes 100,000 events per second, and each lookup must complete within 5 milliseconds. The reference data changes infrequently (daily updates). Which data structure and AWS service combination provides the MOST efficient lookup performance?
  • A. Use a hash table (hash map) implementation via Amazon ElastiCache for Redis, storing device_id as the key and configuration JSON as the value, providing O(1) average-case lookup time with sub-millisecond latency from in-memory storage
  • B. Store device configurations in Amazon RDS PostgreSQL with a B-tree index on device_id, querying the database for each event
  • C. Load the reference data into an Amazon Redshift table and use federated queries from the processing layer for each event lookup
  • D. Store configurations as individual JSON files in S3 with device_id as the filename and use S3 GetObject for each lookup
Jawaban Benar: A
Hash tables provide O(1) average-case lookup by computing a hash of the key (device_id) to directly access the value without searching. ElastiCache Redis implements this as an in-memory key-value store, achieving sub-millisecond latency that easily meets the 5ms requirement at 100K events/second. The infrequent updates (daily) align well with a cache-aside pattern where the cache is refreshed once per day. Opsi B — RDS with B-tree index provides O(log n) lookups with network + disk I/O latency, typically 2-10ms under load, and may not sustain 100K lookups/second without expensive scaling. Opsi C — Redshift is optimized for analytical queries on large datasets, not single-row point lookups; federated queries add significant overhead. Opsi D — S3 GetObject has 50-200ms first-byte latency, far exceeding the 5ms requirement.

A data team is optimizing their AWS Glue ETL job that performs a lookup join between a streaming dataset (1 million records/batch) and a reference table (500,000 records). The current implementation uses a nested loop join, resulting in job execution times of 45 minutes per batch. The team needs to reduce this to under 5 minutes. Which algorithmic improvement provides the MOST significant performance gain?
  • A. Replace the nested loop join with a hash join algorithm: build a hash table on the smaller reference dataset (O(n) time and space), then probe the hash table for each record in the streaming dataset (O(1) per lookup), reducing overall complexity from O(n×m) to O(n+m)
  • B. Sort both datasets by the join key and use a sort-merge join, which requires O(n log n + m log m) time for sorting plus O(n+m) for the merge phase
  • C. Increase the number of Glue DPUs from 10 to 100 while keeping the same nested loop join algorithm
  • D. Partition the streaming data into smaller chunks and run multiple sequential nested loop joins on each chunk
Jawaban Benar: A
The hash join algorithm transforms the problem from O(n×m) = O(500 billion comparisons) to O(n+m) = O(1.5 million operations) — a dramatic reduction. Building the hash table on the smaller 500K-record reference set uses O(n) time and memory, then each of the 1M streaming records performs an O(1) hash probe. In Spark/Glue, this is implemented as a broadcast hash join where the reference table is broadcast to all executors. Opsi B — sort-merge join at O(n log n + m log m) is better than nested loop but worse than hash join for this size ratio, and sorting adds significant overhead. Opsi C — adding DPUs provides linear speedup (10x more resources = ~10x faster) but doesn't change the O(n×m) algorithm, reducing 45 min to ~4.5 min unreliably. Opsi D — partitioning into smaller chunks doesn't reduce total comparison count; it's still O(n×m) in aggregate.

A healthcare company stores patient medical records with complex hierarchical relationships: each patient has multiple visits, each visit has multiple diagnoses, each diagnosis references a hierarchical medical coding system (ICD-10) with 70,000+ codes organized in a tree structure. The data team needs to support queries like "find all patients diagnosed with any cardiovascular condition" where cardiovascular includes hundreds of specific sub-codes at multiple levels. Which approach MOST efficiently handles this hierarchical query pattern in their data lake?
  • A. Implement a materialized path approach storing the full ancestor path for each ICD-10 code (e.g., "I/I00-I99/I20-I25/I21") in the diagnosis records, then use prefix matching on the path string to efficiently find all descendants of any category node
  • B. Store only the leaf-level ICD-10 code in each diagnosis record and perform recursive lookups through a separate parent-child hierarchy table at query time
  • C. Flatten the entire ICD-10 hierarchy into a single level by removing all parent categories and storing only leaf codes, requiring users to enumerate all specific codes in their queries
  • D. Store the full ICD-10 tree as a single JSON document and use Athena JSON functions to traverse the tree for each query
Jawaban Benar: A
The materialized path pattern pre-computes the tree position of each node as a string path. Querying "all cardiovascular conditions" becomes a simple prefix filter (WHERE path LIKE 'I/I00-I99/%'), which Athena/Glue can push down to partition pruning or Parquet column predicate filtering. This avoids runtime tree traversal while supporting any-level ancestor queries. Storage overhead is minimal (a short string per record). Opsi B — recursive parent-child lookups require multiple JOINs or CTEs at query time, which is expensive over billions of diagnosis records in a data lake. Opsi C — forcing users to enumerate all sub-codes (potentially hundreds) makes queries impractical and error-prone when codes are added. Opsi D — storing the tree as JSON requires parsing and traversing a large document per query, which cannot leverage columnar storage or partition pruning.

A data engineer is designing an Amazon Redshift table to store 5 years of financial transaction data (2 billion rows). Queries predominantly filter by transaction_date (range queries for reporting periods) and occasionally by account_id (point lookups for auditing). The engineer must choose the optimal indexing strategy to minimize disk I/O for both query patterns. Which Redshift configuration BEST optimizes for these access patterns?
  • A. Use a compound sort key with transaction_date as the first column and account_id as the second, allowing Redshift to skip disk blocks efficiently for date range queries (zone maps on sorted data) and providing secondary benefit for account_id filtering within a date range
  • B. Use an interleaved sort key on both transaction_date and account_id to give equal weight to both columns for filtering
  • C. Create a B-tree index on transaction_date and a separate B-tree index on account_id, similar to traditional RDBMS
  • D. Don't use any sort key and rely on Redshift's automatic optimization to determine the best data organization
Jawaban Benar: A
Compound sort keys in Redshift physically order data on disk by the specified columns in sequence. With transaction_date first, zone maps (min/max metadata per 1MB block) allow Redshift to skip entire blocks that don't contain the target date range — dramatically reducing I/O for range queries. The secondary sort on account_id helps within-date-range filtering. Since date range queries are predominant, placing transaction_date first optimizes for the primary access pattern. Opsi B — interleaved sort keys give equal weight to all columns, which is beneficial only when both columns are filtered independently with equal frequency; for predominantly date-range queries, this reduces date filtering efficiency compared to compound. Opsi C — Redshift does not support traditional B-tree indexes; it uses columnar storage with zone maps and sort keys instead. Opsi D — without a sort key, data is stored in insertion order, forcing full table scans regardless of filter predicates.

A streaming data pipeline processes clickstream events using Amazon Kinesis Data Streams. The pipeline uses a Lambda consumer that must maintain a count of unique users seen in the last 24 hours. With 500 million unique users daily and events arriving at 200,000 per second, the exact unique count isn't required — an estimate within 2% accuracy is acceptable. The solution must use minimal memory. Which algorithmic approach is MOST appropriate?
  • A. Use a HyperLogLog (HLL) data structure that maintains a fixed-size register array (approximately 16 KB for 2% accuracy) and applies hash-based probabilistic counting, providing cardinality estimation with O(1) time per insert and O(1) space regardless of the number of unique elements
  • B. Maintain a hash set (HashSet) of all unique user IDs in Lambda's memory, counting the set size at the end of the 24-hour window
  • C. Store each unique user_id in a DynamoDB table with a 24-hour TTL and perform a count scan at the end of the window
  • D. Use a sorted array of user IDs in ElastiCache, inserting in sorted order and counting the array length for the unique count
Jawaban Benar: A
HyperLogLog is a probabilistic cardinality estimation algorithm that uses only O(log log n) space — approximately 16 KB for 2% standard error with 16,384 registers. It works by hashing each element and observing the longest run of leading zeros across all hashed values, which statistically correlates with cardinality. For 500M unique users, HLL provides ~2% accuracy in 16 KB versus the 8+ GB needed for exact counting. Redis (ElastiCache) has native HLL support via PFADD/PFCOUNT commands. Opsi B — storing 500M user IDs (8 bytes each = 4 GB minimum) exceeds Lambda's memory limit (10 GB max) and is wasteful when approximate counting is acceptable. Opsi C — DynamoDB would store 500M items daily at enormous cost, and count scans at 500M items take minutes. Opsi D — sorted arrays require O(n) space and O(log n) binary search for insertion, impractical at 500M elements.
