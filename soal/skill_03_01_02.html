A data engineer deployed a new DAG to their Amazon MWAA environment by uploading the Python file to the S3 DAGs folder. After 10 minutes, the DAG still does not appear in the Airflow UI. The engineer verified the file is in the correct S3 path. What is the MOST likely cause?
  • A. The MWAA environment needs to be restarted after adding new DAGs, integrating natively with the rest of the pipeline
  • B. The DAG file has a Python syntax error or an import error that prevents the scheduler from parsing it
  • C. The DAG file exceeds the maximum file size limit of 1 MB configured for optimal performance and minimal operational overhead
  • D. The S3 bucket does not have versioning enabled, which is required for MWAA, integrating natively with the rest of the pipeline
Correct Answer: B
When DAG not muncul in Airflow UI, penyebab most umum is syntax error or import error in file DAG. Airflow scheduler mem-parse all DAG files in a periodik, and if there is error when parsing, DAG not will in-register. Error this terlihat in scheduler logs in CloudWatch.

Option A: INCORRECT. Incorrect — MWAA does not need restart, scheduler automatically detects file new in S3.
Option B: CORRECT.
Option C: INCORRECT. Incorrect — there is no hard limit 1 MB for DAG files — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Incorrect — S3 versioning is required but this will causes error when setup environment, not when adding DAGs.

An MWAA environment running Apache Airflow has tasks that intermittently fail with the error "Task received SIGTERM signal" even though the task logic executed correctly. The environment uses the mw1.small environment class with 5 workers. CloudWatch metrics show worker CPU usage frequently exceeds 90%. What is the MOST appropriate resolution?
  • A. Switch from CeleryExecutor to LocalExecutor to reduce overhead, meeting the latency and throughput goals of the design
  • B. Increase the task timeout setting in the DAG configuration configured for optimal performance and minimal operational overhead
  • C. Upgrade the MWAA environment class to mw1.medium or mw1.large to provide more resources per worker
  • D. Add more tasks per worker by increasing worker_concurrency in Airflow configuration overrides
Correct Answer: C
SIGTERM signals when worker CPU in a consistent high (>90%) indicates resource exhaustion — workers kehabisan resources and Airflow/system sends SIGTERM for membunuh task processes that exceeds limits. Upgrade environment class (mw1.small → mw1.medium/large) increases CPU and memory per worker.

Option A: INCORRECT. Not applies — MWAA always uses CeleryExecutor and cannot is changed to LocalExecutor.
Option B: INCORRECT. Not solves resource exhaustion — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: CORRECT.
Option D: INCORRECT. Justru memperburuk problem with adds load on workers that already overloaded.

A company's MWAA environment suddenly cannot access their Amazon RDS PostgreSQL database that is used as a data source in multiple DAGs. Tasks fail with connection timeout errors. The MWAA environment and RDS instance are in the same VPC but different subnets. The RDS instance is confirmed to be running and accessible from an EC2 instance in the same VPC. What should be checked FIRST?
  • A. The RDS instance's security group inbound rules to verify it allows traffic from the MWAA environment's security group
  • B. The MWAA Airflow connection configuration for correct hostname and port, integrating natively with the rest of the pipeline
  • C. The RDS instance's parameter group to check max_connections setting, satisfying all of the stated requirements with minimal effort
  • D. The MWAA execution role to verify it has permissions to access RDS configured for optimal performance and minimal operational overhead
Correct Answer: A
Connection timeout (not authentication failure or connection refused) between resources in VPC that different subnet most often disebabkan by security group rules. MWAA workers runs in VPC uses security group certain, and RDS security group must explicitly allow inbound traffic from MWAA security group on port database (3306/5432).

Option A: CORRECT.
Option B: INCORRECT. If previously berfungsi and configuration not changes, this not penyebab.
Option C: INCORRECT. Will causes "too many connections" error, not timeout.
Option D: INCORRECT. RDS PostgreSQL connection uses username/password through network, not IAM roles (except IAM auth in-enable) — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data engineer observes that their MWAA environment's DAG processing time has significantly increased. Previously, DAGs were parsed in under 30 seconds, but now parsing takes over 5 minutes. The DAGs folder contains 150 DAG files. Several DAGs use top-level code that queries AWS services (S3, DynamoDB) during import. What is the MOST likely cause and solution?
  • A. The scheduler needs more memory; upgrade to a larger environment class configured for optimal performance and minimal operational overhead
  • B. 150 DAG files exceeds the MWAA maximum; consolidate DAGs into fewer files, satisfying all of the stated requirements with minimal effort
  • C. Top-level code that makes API calls during DAG parsing is blocking the scheduler; move API calls inside task callables
  • D. The S3 bucket hosting DAGs has throttling; enable S3 Transfer Acceleration, handling the described workload reliably at scale
Correct Answer: C
Airflow scheduler mem-parse each DAG file in a periodik (default each 30 seconds). Kode in top-level (in outside task functions) dieksekusi each kali scheduler parse file. If top-level code creates API calls to S3/DynamoDB, this adds latency significant that dimultiplikasi with number DAG files (150 × API call latency). The solution is moves all API calls to in task callables that only dieksekusi when task running.

Option A: INCORRECT. Can membantu few but not solves root cause — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Incorrect — 150 DAGs still in limit wajar.
Option C: CORRECT.
Option D: INCORRECT. Not relevan with DAG parsing time.

  • A. The MWAA environment's network configuration — verify NAT Gateway or VPC endpoints are functioning for the webserver subnet
  • B. The scheduler is overloaded and needs more resources, causing the webserver to become unresponsive, enforcing encryption and fine-grained access control
  • C. The S3 DAGs bucket has been deleted, causing the webserver to fail, handling the described workload reliably at scale
  • D. All workers have failed and the webserver cannot display task status for the webserver subnet
Correct Answer: A
MWAA webserver requires network connectivity that proper. HTTP 503 indicates webserver cannot serves requests, that often disebabkan by networking issues — NAT Gateway unhealthy, VPC endpoint misconfiguration, or network ACL blocking traffic. Fakta that scheduler still runs (DAGs running) indicates problem specific on webserver networking, not general environment failure.

Option A: CORRECT.
Option B: INCORRECT. Incorrect — scheduler and webserver is component separate; scheduler overload not causes webserver 503.
Option C: INCORRECT. Incorrect — if DAGs bucket is deleted, scheduler also will stops.
Option D: INCORRECT. Incorrect — worker failure not creates webserver inaccessible — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

The task consistently fails with "OSError: [Errno 28] No space left on device" after running for about 20 minutes. The worker's local storage is filling up. What is the MOST appropriate solution?
  • A. Mount an EFS volume to the MWAA workers for additional storage, handling the described workload reliably at scale and delivering records with consistent sub-second latency
  • B. Process the file in chunks using streaming reads instead of downloading the entire file to local disk, or use /tmp with cleanup logic
  • C. Upgrade to the largest MWAA environment class for more local storage, meeting the latency and throughput goals of the design and reducing day-to-day operational effort
  • D. Increase the worker count to distribute the load across more workers with cleanup logic, handling the described workload reliably at scale
Correct Answer: B
MWAA workers has limited local storage. Solution best is changes approach — gunakan streaming reads (for example boto3 S3 streaming or pandas chunked reading) for processes file without stores entirely in disk local. If needs temp storage, gunakan /tmp with explicit cleanup after complete.

Option A: INCORRECT. MWAA not supports mounting EFS to workers in a native.
Option B: CORRECT.
Option C: INCORRECT. Environment class upgrade provides few more storage but may still not quite for 2 GB files + intermediate data.
Option D: INCORRECT. Not membantu if each worker still must process file 2 GB in a local — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data team notices that tasks in their MWAA DAG stay in "queued" state for extended periods (30+ minutes) before being picked up by workers. The environment has min_workers=2 and max_workers=10. During peak hours, there are 50 tasks waiting in the queue. What is the MOST likely cause?
  • A. The Celery broker (SQS) has a message delivery delay configured and current workers are at maximum capacity
  • B. The scheduler is processing DAGs too slowly to dispatch tasks to workers, absorbing sudden traffic spikes without throttling
  • C. The worker_concurrency setting is too low, limiting how many tasks each worker can execute simultaneously
  • D. The MWAA autoscaling is too slow to scale up workers, and current workers are at maximum capacity
Correct Answer: D
MWAA auto-scaling requires time for adds workers (provisioning new containers). If there is burst 50 tasks tiba-tiba with only 2 min workers, scaling to 10 workers requires time. During scaling period, tasks waits in queue. The solution is increases min_workers so that there is quite workers ready for peak demand.

Option A: INCORRECT. MWAA manages Celery broker configuration, users cannot set message delay — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Scheduler queuing and task execution are separate; scheduler already queued tasks (mereka already in "queued" state).
Option C: INCORRECT. If this the problem, tasks will stuck not because less workers but because limit per worker, but this usually terlihat when workers idle that not appropriate scenario this.
Option D: CORRECT.

A data engineering team's MWAA environment shows "Scheduler Heartbeat" failures in the CloudWatch metrics dashboard. DAGs are not being scheduled on time and some tasks are being marked as "zombie" tasks. The scheduler log group shows the scheduler process is being killed and restarted frequently. What is the root cause and resolution?
  • A. The scheduler is running out of memory due to too many DAGs or complex DAG structures; reduce DAG count or simplify DAGs and consider upgrading environment class
  • B. CloudWatch Logs subscription filters are blocking scheduler log delivery, meeting the latency and throughput goals of the design and integrating natively with the rest of the pipeline
  • C. The MWAA environment's IAM role has expired credentials and consider upgrading environment class, satisfying all of the stated requirements with minimal effort and applying schema conversion and enrichment inline
  • D. The VPC's DNS resolution is failing, causing scheduler connectivity issues, handling the described workload reliably at scale and meeting the latency and throughput goals of the design
Correct Answer: A
Scheduler heartbeat failures and frequent process kills/restarts is classic symptoms of scheduler resource exhaustion (OOM — Out of Memory). When scheduler kehabisan memory (because parsing too many DAGs, DAGs that very complex, or many running task instances), process in-kill by OS and in-restart by supervisor. Zombie tasks occurs because scheduler cannot send heartbeats when dead. Solution: kurangi number/complexity DAGs, or upgrade environment class for more scheduler memory.

Option A: CORRECT.
Option B: INCORRECT. Not affects scheduler operation.
Option C: INCORRECT. MWAA manages credential rotation automatic — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Will causes connectivity errors, not OOM kills.
