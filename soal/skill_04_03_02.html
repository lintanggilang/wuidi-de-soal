A data lake stores sensitive financial records in S3. The security team requires: (1) full control over key rotation schedule, (2) ability to immediately disable the key to block all access in an emergency, (3) audit trail of every encryption/decryption operation. Which S3 encryption configuration meets ALL these requirements?
  • A. SSE-S3 (S3-managed keys) — simplest configuration with automatic encryption with fully managed infrastructure and automatic scaling
  • B. SSE-KMS with a Customer Managed Key (CMK) — provides full key lifecycle control: custom rotation schedule (annual automatic or manual on-demand), ability to disable the key (immediately blocks all Encrypt/Decrypt operations), CloudTrail logging of every kms:Decrypt and kms:GenerateDataKey call showing who accessed what data and when
  • C. SSE-C (Customer-provided keys) — maximum control since you manage keys entirely outside AWS
  • D. No encryption at rest, rely on S3 bucket policies for security
Jawaban Benar: B
SSE-KMS with Customer Managed Key (CMK) memenuhi semua requirements: Requirement 1 — Key rotation control: Automatic rotation: Enable yearly rotation (key material rotated, key ID unchanged). Manual rotation: Create new key, re-encrypt data, update key alias. On-demand rotation for compliance. Requirement 2 — Emergency key disable: aws kms disable-key --key-id key-123. IMMEDIATE effect: all subsequent Encrypt/Decrypt calls FAIL. No one can read encrypted data — even with S3 access. Re-enable when emergency resolved. Requirement 3 — Audit trail: Every kms:Decrypt logged in CloudTrail: who (principal), what (key ARN), when (timestamp), from where (source IP). kms:GenerateDataKey logged for write operations. Integration with CloudWatch for alerting on anomalous patterns. Why NOT SSE-S3: No key disable capability. No per-request CloudTrail entries. No custom rotation control. AWS manages everything — limited visibility. Why NOT SSE-C: YOU must store/manage keys outside AWS. No CloudTrail logging of KMS operations (keys never touch KMS). Key loss = permanent data loss. Complex operational burden.

A data engineer is confused about how S3 encrypts a 5GB file using SSE-KMS. They ask: "Does S3 send the entire 5GB file to KMS for encryption?" Explain the encryption mechanism that S3 actually uses with KMS.
  • A. Yes, S3 sends all data to KMS for direct encryption using the CMK and its encrypted (ciphertext) copy
  • B. S3 uses envelope encryption: it calls KMS GenerateDataKey to get a unique plaintext data key AND its encrypted (ciphertext) copy. S3 encrypts the 5GB object locally using the plaintext data key (AES-256), then discards the plaintext key and stores the encrypted data key alongside the encrypted object. For decryption, S3 sends only the small encrypted data key to KMS for decryption, then uses the returned plaintext key to decrypt the object locally
  • C. S3 downloads the CMK from KMS and uses it directly to encrypt each file
  • D. KMS maintains a persistent connection to S3 and streams decryption in real-time
Jawaban Benar: B
Envelope encryption adalah fundamental concept di AWS KMS: Encryption flow (PutObject with SSE-KMS): (1) S3 calls kms:GenerateDataKey(KeyId=cmk-123). (2) KMS returns: {Plaintext: "random-256-bit-key", CiphertextBlob: "encrypted-version-of-key"}. (3) S3 uses Plaintext key to AES-256 encrypt the 5GB object LOCALLY (never leaves S3). (4) S3 DISCARDS the plaintext key from memory. (5) S3 stores: [Encrypted 5GB Object] + [CiphertextBlob metadata]. Decryption flow (GetObject): (1) S3 retrieves CiphertextBlob (encrypted data key) — tiny, ~200 bytes. (2) S3 calls kms:Decrypt(CiphertextBlob). (3) KMS returns Plaintext data key. (4) S3 decrypts object locally using plaintext key. (5) S3 discards plaintext key after use. Why envelope encryption: Performance: KMS has 5,500-30,000 requests/second limit. Sending 5GB through KMS would be impossibly slow. Data never leaves S3 in plaintext. Each object gets unique data key — compromising one key doesn't expose other objects. KMS only processes tiny data keys (~256 bits), not gigabytes. Opsi A salah — KMS has 4KB payload limit for direct encryption. Opsi C — CMK NEVER leaves KMS hardware (HSM). Opsi D — no persistent connection; stateless API calls.

A Glue ETL job processes 10 million small files per day from an encrypted S3 bucket (SSE-KMS). The job starts failing with "ThrottlingException" errors from KMS. The current KMS request quota is 5,500 requests per second. What is the MOST effective solution?
  • A. Disable S3 encryption to avoid KMS calls entirely with native S3 integration and optimized data transfer
  • B. Request a KMS quota increase AND implement S3 bucket keys — S3 Bucket Keys reduce KMS requests by generating a bucket-level data key that derives per-object keys locally, reducing KMS API calls by up to 99%. Instead of one kms:GenerateDataKey call per object, a single bucket-level key handles many objects within a time window
  • C. Switch to SSE-S3 encryption which has no API call limits
  • D. Reduce the number of files processed per day to stay under the quota
Jawaban Benar: B
S3 Bucket Keys dramatically reduces KMS API calls: Problem analysis: 10M files/day = ~115 files/second average. Peak could be 10-100x during batch processing = 1,000-10,000+ KMS calls/second. Each GetObject on SSE-KMS object = 1 kms:Decrypt call. Each PutObject = 1 kms:GenerateDataKey call. S3 Bucket Keys solution: Without Bucket Keys: [Object 1 → KMS call] [Object 2 → KMS call] [Object 3 → KMS call] ... (1 call per object). With Bucket Keys: [KMS generates bucket-level key] → S3 derives per-object keys LOCALLY from bucket key. KMS called once per time window → S3 handles millions of objects using derived keys. Result: 99% reduction in KMS API calls. Cost reduction: KMS charges $0.03 per 10,000 requests → significant savings at 10M files/day. Enable: aws s3api put-bucket-encryption --bucket my-bucket --server-side-encryption-configuration '{"Rules": [{"BucketKeyEnabled": true, ...}]}'. Additional: Request quota increase as buffer for peaks. Opsi A — removes security, violates compliance. Opsi C — SSE-S3 loses audit trail, key control, disable capability. Opsi D — limits business functionality to work around technical issue.

A data engineer needs to encrypt a Redshift cluster that was initially created without encryption. The cluster contains 50TB of data and handles production queries. What is the process to enable encryption on an existing unencrypted Redshift cluster?
  • A. Simply enable encryption in the cluster settings — Redshift encrypts data in-place instantly
  • B. Use Redshift's cluster encryption migration feature — modify the cluster to enable KMS encryption, which triggers an automatic background migration process. Redshift creates a new encrypted cluster, migrates data from the unencrypted cluster, then swaps endpoints. During migration, the cluster remains available for reads but may experience performance impact. This process can take hours depending on data volume
  • C. Export all data to S3, delete the cluster, recreate with encryption, and reimport for reads but may experience performance impact
  • D. Encryption cannot be added to an existing Redshift cluster under any circumstances
Jawaban Benar: B
Redshift cluster encryption migration process: Steps: (1) Modify cluster: aws redshift modify-cluster --cluster-identifier my-cluster --encrypted --kms-key-id key-arn. (2) Redshift initiates migration: Creates new encrypted storage. Copies data blocks with encryption applied. Maintains cluster availability during migration. (3) Timeline: 50TB cluster → several hours to complete. Performance degradation during migration (I/O intensive). (4) Completion: Cluster endpoint remains the same. All data now encrypted at rest with specified KMS key. Snapshots from this point forward are encrypted. Important considerations: Plan migration during low-usage window. Monitor cluster performance during migration. Automated snapshots may take longer during process. Once encrypted, cannot revert to unencrypted. Cross-region copies of encrypted snapshots require target region KMS key. KMS key selection: AWS managed key (aws/redshift): simple, no management. Customer managed key: full control, rotation, audit, cross-account sharing. Opsi A — not instant, requires data migration. Opsi C — unnecessary downtime, complex process. Opsi D — incorrect, migration IS supported.

A company's KMS key policy needs to allow a Glue ETL role to encrypt/decrypt data, a Redshift cluster role to decrypt data only, and an admin role to manage the key. The policy should follow least privilege. Which key policy structure is correct?
  • A. Grant kms:* to all three roles since they all need key access
  • B. Create separate statements with action-level granularity: (1) Glue role: Allow kms:GenerateDataKey + kms:Decrypt (read/write data), (2) Redshift role: Allow kms:Decrypt only (read-only data access), (3) Admin role: Allow kms:Create*, kms:Put*, kms:Enable*, kms:Disable*, kms:Schedule*, kms:Describe*, kms:List* (key management only, NOT data operations). Each principal gets ONLY the KMS actions their function requires
  • C. Use a single statement granting all three roles kms:Encrypt and kms:Decrypt with action-level granularity: (1) Glue role: Allow kms:GenerateDataKey + kms:Decrypt (read/write data)
  • D. Grant key access through IAM policies only, without any key policy statements
Jawaban Benar: B
KMS key policy least privilege = different actions for different roles: Glue ETL Role (data read/write): kms:GenerateDataKey — needed for S3 PutObject (SSE-KMS). kms:Decrypt — needed for S3 GetObject. kms:DescribeKey — needed to verify key availability. NOT needed: kms:Encrypt (S3 uses GenerateDataKey, not Encrypt directly). NOT needed: kms:CreateKey, kms:DisableKey, kms:ScheduleKeyDeletion. Redshift Role (data read-only): kms:Decrypt — needed to read encrypted data from S3/Redshift storage. kms:DescribeKey — verify key status. NOT needed: kms:GenerateDataKey (not writing new encrypted data via KMS). Admin Role (key management): kms:CreateKey, kms:PutKeyPolicy, kms:EnableKey, kms:DisableKey. kms:ScheduleKeyDeletion, kms:CancelKeyDeletion. kms:EnableKeyRotation, kms:GetKeyPolicy, kms:ListKeys. NOT needed: kms:Decrypt, kms:GenerateDataKey (admin manages keys, doesn't access data). Separation of duties: Data engineers can't disable keys. Admins can't decrypt data. Read-only consumers can't write encrypted data. Opsi A — kms:* gives everyone ability to delete keys, change policies. Opsi C — doesn't separate management from data operations. Opsi D — key policy required; IAM alone insufficient for KMS access (key policy is always evaluated).

A company uses DynamoDB to store session data for their data pipeline orchestration. They need encryption at rest but are evaluating cost implications. The table experiences 50,000 reads per second at peak. What are the DynamoDB encryption options and their cost/management tradeoffs?
  • A. DynamoDB does not support encryption at rest — only in-transit encryption is available with fully managed infrastructure and automatic scaling
  • B. DynamoDB offers three encryption options: (1) AWS owned key (DEFAULT, free) — AWS manages everything, no KMS costs, no CloudTrail entries for key usage; (2) AWS managed key (aws/dynamodb) — free KMS key, but generates CloudTrail entries for each table operation, can impact CloudTrail costs at 50K reads/sec; (3) Customer managed key (CMK) — full control, custom rotation, cross-account sharing, audit trail, but KMS API charges ($0.03/10K requests) which at 50K reads/sec would cost significantly more
  • C. All DynamoDB encryption options cost the same, the only difference is key management complexity
  • D. Customer managed keys in DynamoDB are always free because DynamoDB handles KMS calls internally
Jawaban Benar: B
DynamoDB encryption options have significant cost implications at scale: Option 1 — AWS Owned Key (DEFAULT): Cost: FREE (no KMS charges). Audit: No CloudTrail entries for encryption operations. Control: None — can't disable, rotate, or share. Best for: Non-regulated workloads, cost-sensitive applications. Option 2 — AWS Managed Key (aws/dynamodb): Cost: Key itself free, BUT each DynamoDB operation generates CloudTrail event. At 50K reads/sec = 4.3B events/day. CloudTrail costs for management events can be significant. Control: Limited — can view key policy, see usage, but can't rotate or share. Option 3 — Customer Managed Key (CMK): Cost: $1/month for key + $0.03 per 10,000 API requests. 50K reads/sec × 3600 × 24 = 4.32B requests/day. BUT: DynamoDB caches data keys, so NOT every read = KMS call. Actual KMS calls much lower than DynamoDB operations. Control: Full — custom rotation, disable/enable, cross-account, key policy. Audit: Full CloudTrail for key operations. Recommendation for 50K reads/sec: AWS owned key if audit not required (cheapest). CMK if compliance requires audit trail (DynamoDB's caching reduces actual KMS costs).

A company enables automatic annual key rotation on their KMS CMK used for S3 data lake encryption. After rotation occurs, they notice old objects are still readable. They expected rotation to re-encrypt everything. What is their misunderstanding about KMS key rotation?
  • A. Key rotation failed and they need to manually re-encrypt all objects configured for optimal performance and minimal operational overhead
  • B. KMS automatic key rotation creates NEW key material but retains ALL previous key material under the same Key ID (ARN). New encryption operations use the new material, but decryption of old data uses the original material automatically — KMS tracks which key material version encrypted each data key. Old objects remain readable WITHOUT re-encryption because KMS transparently selects the correct key material version during Decrypt calls
  • C. Key rotation in KMS only changes the key policy, not the actual cryptographic material
  • D. Old objects need to be manually re-encrypted within 24 hours of rotation or they become permanently unreadable
Jawaban Benar: B
KMS automatic rotation behavior: What happens during rotation: Key ID/ARN: UNCHANGED — still same arn:aws:kms:region:account:key/uuid. Key material: NEW cryptographic material generated. Old key material: RETAINED (never deleted during rotation). Metadata: KMS tracks which version encrypted each ciphertext. Behavior after rotation: Encrypt/GenerateDataKey: Uses NEW key material. Decrypt: Automatically identifies which key material version was used (from ciphertext metadata) → uses CORRECT version. Result: No disruption, no re-encryption needed. Key policy: Unchanged — same principals have same access. Why NO re-encryption needed: Each encrypted object's ciphertext contains metadata identifying the key material version. KMS Decrypt call reads this metadata → selects correct version transparently. All versions remain active under the same Key ID. When you SHOULD manually re-encrypt: Compliance requires data encrypted with material no older than X days. Want to decommission old key material (manual rotation with new key ID). Migrating between encryption types. Manual rotation (different key ID): Requires re-encryption of old data. Old key must be kept until all data re-encrypted. More complex but allows complete material decommission.

A data engineer needs to implement field-level encryption in a Glue ETL job. Specific columns (SSN, credit_card) must be encrypted before writing to S3, while other columns remain in plaintext for analytics. The encrypted fields need to be decryptable by a separate downstream service with appropriate permissions. Which approach implements this?
  • A. Use S3 SSE-KMS which automatically encrypts only sensitive columns
  • B. Implement client-side field-level encryption in the Glue job: call KMS GenerateDataKey to get a data key, use it to encrypt specific column values with AES-256 before writing the DataFrame to S3. Store the encrypted data key alongside the ciphertext in the column (or as metadata). The downstream service calls KMS Decrypt on the encrypted data key, then decrypts the field values locally — both services need kms:Decrypt permission on the same KMS key
  • C. Store sensitive columns in a separate encrypted S3 bucket and non-sensitive columns in an unencrypted bucket
  • D. Use Redshift column-level encryption for S3-stored data with AES-256 before writing the DataFrame
Jawaban Benar: B
Client-side field-level encryption provides granular column protection: Implementation in Glue PySpark: (1) Generate data key: response = kms.generate_data_key(KeyId='key-arn', KeySpec='AES_256'). plaintext_key = response['Plaintext']. encrypted_key = response['CiphertextBlob']. (2) Encrypt sensitive fields: from cryptography.fernet import Fernet (or AES-GCM). encrypted_ssn = encrypt(plaintext_key, row['ssn']). encrypted_cc = encrypt(plaintext_key, row['credit_card']). (3) Write to S3: DataFrame with: region (plaintext), amount (plaintext), ssn (encrypted blob), credit_card (encrypted blob), _encryption_key (encrypted data key). (4) Downstream decryption: Read encrypted_key → call kms:Decrypt → get plaintext key. Use plaintext key to decrypt field values locally. Why client-side: S3 SSE encrypts ENTIRE object — can't selectively encrypt columns. Analytics queries on region, amount still work without decryption. Only services with KMS access can read SSN, credit_card. Defense in depth: even if S3 access compromised, field-level encryption adds protection. Opsi A — SSE-KMS is object-level, not field-level. Opsi C — splits data, complicates joins, loses atomicity. Opsi D — Redshift encryption doesn't apply to S3 Parquet files.

A compliance team requires that a specific KMS key used for encrypting financial data can NEVER be deleted — even accidentally by an administrator. What KMS mechanism prevents key deletion?
  • A. Set the key rotation period to "never" which also prevents deletion with an SCP that denies kms:ScheduleKeyDeletion for this specific key ARN across the organization for ALL principals (including the root account)
  • B. Add a key policy statement that explicitly DENIES kms:ScheduleKeyDeletion for ALL principals (including the root account), combined with an SCP that denies kms:ScheduleKeyDeletion for this specific key ARN across the organization. The SCP ensures even account administrators cannot schedule deletion, and the key policy Deny statement provides the last line of defense
  • C. KMS keys cannot be deleted under any circumstances by design
  • D. Enable "deletion protection" flag on the KMS key similar to RDS deletion protection
Jawaban Benar: B
Preventing KMS key deletion requires multiple layers: Layer 1 — Key Policy Deny: {"Effect": "Deny", "Principal": {"AWS": "*"}, "Action": "kms:ScheduleKeyDeletion", "Resource": "*"}. This denies ALL principals from scheduling deletion. Note: Even root account is bound by explicit Deny in key policy. Layer 2 — SCP (Organization level): {"Effect": "Deny", "Action": "kms:ScheduleKeyDeletion", "Resource": "arn:aws:kms:region:account:key/specific-key-id"}. Prevents any principal in any account in the OU from scheduling deletion. Even account administrators cannot override SCPs. Layer 3 — Additional safeguards: aws kms disable-key-deletion (if available via custom configuration). CloudWatch Alarm on kms:ScheduleKeyDeletion API calls. AWS Config rule detecting keys with deletion scheduled. Important: KMS ScheduleKeyDeletion has mandatory 7-30 day waiting period — provides time to cancel even if somehow scheduled. CancelKeyDeletion can rescue a key during waiting period. Opsi A — rotation and deletion are independent settings. Opsi C — keys CAN be deleted (after waiting period). Opsi D — KMS doesn't have a "deletion protection" toggle like RDS (must be done via policy).

A data pipeline processes sensitive data across three services: Kinesis Data Streams → Glue ETL → S3. The security architect asks: "Is the data encrypted at every stage?" Which configuration ensures continuous encryption across all three services?
  • A. Encrypt only the final S3 output since that's where data persists long-term with KMS on the stream — data encrypted as soon as it enters Kinesis
  • B. Configure encryption at each service layer: (1) Kinesis: enable server-side encryption with KMS on the stream — data encrypted as soon as it enters Kinesis, (2) Glue: job processes data in memory (decrypted for processing) but temporary spill-to-disk uses encrypted storage; configure security configuration for job bookmark encryption and S3 encryption mode, (3) S3: SSE-KMS on output bucket — final output encrypted at rest. Additionally, ensure all inter-service communication uses TLS (encryption in transit) — Kinesis APIs, Glue connections, and S3 APIs all use HTTPS by default
  • C. Use a single KMS key across all services — this automatically ensures end-to-end encryption
  • D. VPC encryption handles all inter-service encryption automatically
Jawaban Benar: B
End-to-end encryption memerlukan explicit configuration di setiap stage: Stage 1 — Kinesis Data Streams: Server-side encryption: aws kinesis start-stream-encryption --stream-name my-stream --encryption-type KMS --key-id key-arn. Data encrypted immediately upon ingestion. Producer → Kinesis: TLS in transit (HTTPS endpoint). Consumer reads: KMS Decrypt called transparently. Stage 2 — Glue ETL: In-memory: data decrypted for processing (necessary for transformation). Security Configuration: Encrypts job bookmarks with KMS. Encrypts CloudWatch logs. S3 output encryption settings (SSE-KMS, key ARN). Temporary disk spill: Glue encrypts temp files on local disk. Glue ↔ S3/Kinesis: TLS in transit. Stage 3 — S3 Output: SSE-KMS on bucket: all objects encrypted at rest. Bucket policy enforcing encryption: Deny PutObject without encryption header. TLS enforced: Deny non-HTTPS requests. Continuous protection: At rest: encrypted in Kinesis, encrypted in S3, encrypted temp files in Glue. In transit: TLS between all services (default for AWS API calls). In processing: data necessarily decrypted in memory (encrypt output immediately). Opsi A — data unprotected in Kinesis and during processing. Opsi C — single key doesn't automatically configure encryption (each service needs explicit setup). Opsi D — VPC doesn't provide encryption (provides network isolation).
