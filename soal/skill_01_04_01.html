A Spark ETL job in AWS Glue performs a join between a 500 GB fact table and a 50 MB dimension table. The job takes 45 minutes. The Spark UI shows a large shuffle during the join. Which code optimization MOST reduces runtime?
  • A. Use broadcast join by broadcasting the small dimension table: df_fact.join(broadcast(df_dimension), "key") — eliminates the expensive shuffle of the large fact table
  • B. Increase spark.sql.shuffle.partitions from 200 to 2000
  • C. Cache both DataFrames before the join
  • D. Repartition the fact table by the join key before joining
Jawaban Benar: A
Broadcast join sends the small table (50 MB easily fits in memory) to all executors. The join happens locally on each executor without shuffling the 500 GB fact table across the network. This eliminates the most expensive operation (shuffle). Opsi B (more partitions) still requires shuffle, just into more smaller partitions. Opsi C (cache) helps for repeated use, not single-join performance. Opsi D (repartition) itself requires a full shuffle of 500 GB — adds cost before the join.
2
A Lambda function processes S3 files and makes API calls to enrich each record. The function handles 10,000 records per invocation. Currently it makes sequential HTTP calls (one at a time), taking 8 minutes. Each API call takes 50ms. How can the code be optimized to reduce runtime?
  • A. Use Python's asyncio with aiohttp to make concurrent HTTP calls, processing multiple API requests simultaneously instead of sequentially
  • B. Increase Lambda memory to get faster CPU
  • C. Use a connection pool with the requests library
  • D. Batch all records into a single API call
Jawaban Benar: A
Sequential: 10,000 × 50ms = 500 seconds (8.3 minutes). With asyncio/aiohttp making 100 concurrent calls: 10,000/100 × 50ms = 5 seconds. Concurrency eliminates the I/O wait time bottleneck. This is the biggest optimization for I/O-bound workloads. Opsi B (more memory/CPU) doesn't help I/O-bound tasks — CPU is idle while waiting for responses. Opsi C (connection pool) reduces connection overhead but calls are still sequential. Opsi D (single batch) depends on API supporting batch — many don't.
3
A Glue ETL job reads a 1 TB CSV dataset from S3. The job uses a filter early in the transformation (keeping only 5% of records). However, the filter is applied AFTER a costly groupBy operation. The Spark execution plan shows all 1 TB being grouped before filtering. How should the code be restructured?
  • A. Move the filter operation BEFORE the groupBy — "filter early, aggregate late" principle reduces the data volume from 1 TB to 50 GB before the expensive groupBy operation
  • B. Add more DPUs to process the groupBy faster
  • C. Cache the filtered results
  • D. Switch from groupBy to reduceByKey
Jawaban Benar: A
"Filter early, aggregate late" (predicate pushdown principle) — filtering first reduces the dataset from 1 TB to ~50 GB (5%). The subsequent groupBy only processes 50 GB instead of 1 TB, reducing shuffle volume by 95% and dramatically cutting runtime. This is one of the most impactful code optimizations. Opsi B (more DPUs) scales the problem rather than eliminating it. Opsi C (cache) helps for repeated reads, not for single-pass processing. Opsi D (reduceByKey) is RDD API, not applicable to DataFrames/DynamicFrames.
4
A Python Lambda function processes JSON events from Kinesis. Profiling shows that 60% of execution time is spent on JSON parsing using json.loads() for 50,000 records per batch. Which optimization MOST reduces the parsing overhead?
  • A. Replace json.loads() with orjson or ujson library which provides C-optimized JSON parsing, often 3-10x faster than the standard library
  • B. Parse JSON in a separate thread
  • C. Increase Lambda memory allocation
  • D. Use eval() instead of json.loads()
Jawaban Benar: A
orjson dan ujson are C-extension libraries optimized for JSON parsing speed. orjson is typically 3-10x faster than stdlib json for both parsing and serialization. For 50K records where parsing dominates, this translates directly to 60% × (1 - 1/5) = 48% total time reduction. Opsi B (threading) — Python GIL prevents true parallel CPU work; JSON parsing is CPU-bound. Opsi C (more memory) — parsing is CPU-bound, and Lambda memory increase provides proportional CPU but orjson is more efficient. Opsi D (eval()) — severe security vulnerability, never use on external data.
5
A Spark job joins two large tables (both 500 GB) on a column that has significant data skew — one key ("US") accounts for 40% of the data. The join stage takes 90 minutes with the "US" partition being the bottleneck. Which technique resolves this skew problem?
  • A. Apply key salting: append a random number (0-9) to the skewed key in the larger table, replicate the matching rows in the smaller table with all salt values, then join on the salted key
  • B. Filter out "US" records and process them separately in a simpler aggregation
  • C. Increase executor memory to handle the large partition
  • D. Use Spark AQE (Adaptive Query Execution) skew join optimization
Jawaban Benar: D
Spark 3.0+ AQE with skew join optimization (spark.sql.adaptive.skewJoin.enabled=true) automatically detects and splits skewed partitions at runtime. It splits the large partition into smaller sub-partitions and replicates the matching data from the other side. This is the simplest solution requiring no code changes. Opsi A (salting) works but requires manual code changes and is more complex. Opsi B (separate processing) changes logic and may miss join records. Opsi C (more memory) doesn't parallelize the single large task.
6
A Glue ETL job reads data from S3 and the code performs a collect() operation to bring all data to the driver for custom Python processing. The dataset is 10 GB. The job fails with driver OOM. Besides increasing driver memory, which code change avoids this pattern?
  • A. Replace collect() with distributed processing using Spark UDFs (User Defined Functions) or mapPartitions that processes data on executors without bringing it to the driver
  • B. Use toPandas() instead of collect()
  • C. Write to S3 first then read with pandas in a separate step
  • D. Add more executor nodes
Jawaban Benar: A
collect() brings entire dataset to driver memory — anti-pattern for large datasets. UDFs and mapPartitions execute custom logic on executors where data already resides, distributed across the cluster. This keeps 10 GB distributed across many executors (each handling a portion) instead of all on one driver. Opsi B (toPandas()) also brings all data to driver — same OOM risk. Opsi C (S3 + pandas) still single-node processing of 10 GB. Opsi D (more executors) doesn't help — problem is on driver, not executors.
7
A data engineer optimizes a Spark SQL query that reads a partitioned Parquet table in S3. The query filters on column 'region' which is the partition key, and column 'amount > 1000' which is stored within the Parquet files. Which optimization leverages both partition pruning AND predicate pushdown?
  • A. Write the query with both filters in the WHERE clause: WHERE region = 'US' AND amount > 1000 — Spark automatically applies partition pruning for 'region' and predicate pushdown for 'amount' to Parquet
  • B. Read all data first, then filter in Python code after collecting
  • C. Apply filters in separate sequential operations: first filter region, then filter amount
  • D. Create a secondary index on the 'amount' column in S3
Jawaban Benar: A
Spark SQL optimizer automatically handles both: (1) Partition pruning — only reads S3 prefixes matching region='US', skipping all other region partitions. (2) Predicate pushdown to Parquet — uses Parquet's column statistics (min/max) to skip row groups where amount is entirely ≤ 1000. Both happen at read time, minimizing I/O. Opsi B (collect then filter) reads everything — worst performance. Opsi C (sequential filters) — Spark optimizer combines them anyway, but explicit combined WHERE is clearer. Opsi D — S3/Parquet don't support secondary indexes.

A Lambda function is triggered by DynamoDB Streams. The function processes each record by making a write to another DynamoDB table. Currently it calls PutItem for each record individually. With batches of 100 records, this means 100 separate API calls. How should the code be optimized?
  • A. Use BatchWriteItem to write up to 25 items per API call, reducing the number of API calls from 100 to 4 and leveraging parallelism within each batch call
  • B. Use TransactWriteItems for all 100 records in one transaction
  • C. Increase Lambda timeout to accommodate sequential writes
  • D. Write to S3 instead of DynamoDB for better throughput
Jawaban Benar: A
BatchWriteItem sends up to 25 items per API call, reducing network round-trips from 100 to 4 (100/25). Each batch is processed in parallel by DynamoDB internally. This significantly reduces Lambda execution time. Opsi B (TransactWriteItems) limited to 100 items per transaction tapi much slower karena transaction overhead dan all-or-nothing semantics. Opsi C (longer timeout) doesn't optimize, just accommodates slow code. Opsi D changes architecture unnecessarily.
9
An AWS Glue PySpark job performs string operations on a column using a Python UDF (User Defined Function). The UDF processes 100 million rows but is extremely slow because of serialization overhead between JVM and Python. Which approach improves performance?
  • A. Replace the Python UDF with Spark built-in functions (pyspark.sql.functions) or Pandas UDFs (vectorized UDFs) that minimize JVM-Python serialization
  • B. Increase the number of Glue DPUs
  • C. Cache the DataFrame before applying the UDF
  • D. Process fewer rows per partition
Jawaban Benar: A
Python UDFs serialize data row-by-row between JVM and Python interpreter — extremely slow. Built-in Spark functions execute natively in JVM (no serialization). Pandas UDFs (vectorized) process data in Arrow batches — much less serialization overhead than row-by-row UDFs. Can be 10-100x faster. Opsi B (more DPUs) — each DPU still has the same serialization overhead per row. Opsi C (cache) helps repeated reads, not processing speed. Opsi D (fewer rows per partition) doesn't reduce total serialization cost.

A Redshift query that generates a daily report takes 20 minutes. The query performs multiple JOINs, a GROUP BY with 50 aggregate functions, and a HAVING clause. EXPLAIN shows sequential scans on large tables. Which Redshift-specific optimization is MOST likely to improve performance?
  • A. Review and optimize the table distribution keys (DISTKEY) to co-locate joined data on the same nodes, and ensure sort keys (SORTKEY) align with the WHERE/JOIN conditions to enable zone-map pruning
  • B. Add indexes to the join columns
  • C. Rewrite the query to use subqueries instead of JOINs
  • D. Run VACUUM and ANALYZE on all tables
Jawaban Benar: A
Redshift's columnar MPP architecture relies heavily on distribution and sort keys for performance. Proper DISTKEY on join columns eliminates network redistribution (data already co-located). SORTKEY enables zone-map pruning (skipping entire 1MB blocks that don't match predicates). These together can turn sequential scans into targeted reads. Opsi B — Redshift doesn't have traditional indexes. Opsi C (subqueries) — optimizer usually handles this, may not improve. Opsi D (VACUUM/ANALYZE) helps maintenance but DISTKEY/SORTKEY design is fundamental.
