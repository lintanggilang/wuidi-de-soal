#Glue#Spark
A Spark ETL job in AWS Glue performs a join between a 500 GB fact table and a 50 MB dimension table. The job takes 45 minutes. The Spark UI shows a large shuffle during the join. Which code optimization MOST reduces runtime?
  • A. Use broadcast join by broadcasting the small dimension table: df_fact.join(broadcast(df_dimension), "key") — eliminates the expensive shuffle of the large fact table
  • B. Cache both DataFrames before the join, integrating natively with the rest of the pipeline and handling the described workload reliably at scale
  • C. Repartition the fact table by the join key before joining, meeting the latency and throughput goals of the design
  • D. Increase spark.sql.shuffle.partitions from 200 to 2000 configured for optimal performance and minimal operational overhead, applying schema conversion and enrichment inline
Jawaban Benar: A
Broadcast join sends the small table (50 MB easily fits in memory) to all executors. The join happens locally on each executor without shuffling the 500 GB fact table across the network. This eliminates the most expensive operation (shuffle).

Opsi A: BENAR.
Opsi B: SALAH. Helps for repeated use, not single-join performance.
Opsi C: SALAH. Itself requires a full shuffle of 500 GB — adds cost before the join.
Opsi D: SALAH. Still requires shuffle, just into more smaller partitions — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

#Lambda#S3
A Lambda function processes S3 files and makes API calls to enrich each record. The function handles 10,000 records per invocation. Currently it makes sequential HTTP calls (one at a time), taking 8 minutes. Each API call takes 50ms. How can the code be optimized to reduce runtime?
  • A. Use a connection pool with the requests library, integrating natively with the rest of the pipeline
  • B. Batch all records into a single API call, integrating natively with the rest of the pipeline
  • C. Use Python's asyncio with aiohttp to make concurrent HTTP calls, processing multiple API requests simultaneously instead of sequentially
  • D. Increase Lambda memory to get faster CPU with aiohttp, transforming records into the required target format
Jawaban Benar: C
Sequential: 10,000 × 50ms = 500 seconds (8.3 minutes). With asyncio/aiohttp making 100 concurrent calls: 10,000/100 × 50ms = 5 seconds. Concurrency eliminates the I/O wait time bottleneck. This is the biggest optimization for I/O-bound workloads.

Opsi A: SALAH. Reduces connection overhead but calls are still sequential.
Opsi B: SALAH. Depends on API supporting batch — many don't.
Opsi C: BENAR.
Opsi D: SALAH. Doesn't help I/O-bound tasks — CPU is idle while waiting for responses — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

#Glue#S3#Spark
A Glue ETL job reads a 1 TB CSV dataset from S3. The job uses a filter early in the transformation (keeping only 5% of records). However, the filter is applied AFTER a costly groupBy operation. The Spark execution plan shows all 1 TB being grouped before filtering. How should the code be restructured?
  • A. Cache the filtered results, avoiding charges for idle provisioned capacity and keeping steady-state operating costs low and integrating natively with the rest of the pipeline and minimizing end-to-end processing latency
  • B. Switch from groupBy to reduceByKey configured for optimal performance and minimal operational overhead, integrating natively with the rest of the pipeline and validating and cleansing each record before delivery
  • C. Add more DPUs to process the groupBy faster, satisfying all of the stated requirements with minimal effort and keeping steady-state operating costs low and avoiding charges for idle provisioned capacity
  • D. Move the filter operation BEFORE the groupBy — "filter early, aggregate late" principle reduces the data volume from 1 TB to 50 GB before the expensive groupBy operation
Jawaban Benar: D
"Filter early, aggregate late" (predicate pushdown principle) — filtering first reduces the dataset from 1 TB to ~50 GB (5%). The subsequent groupBy only processes 50 GB instead of 1 TB, reducing shuffle volume by 95% and dramatically cutting runtime. This is one of the most impactful code optimizations.

Opsi A: SALAH. Helps for repeated reads, not for single-pass processing.
Opsi B: SALAH. Is RDD API, not applicable to DataFrames/DynamicFrames — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. Scales the problem rather than eliminating it.
Opsi D: BENAR.

#Spark
A Spark job joins two large tables (both 500 GB) on a column that has significant data skew — one key ("US") accounts for 40% of the data. The join stage takes 90 minutes with the "US" partition being the bottleneck. Which technique resolves this skew problem?
  • A. Apply key salting: append a random number (0-9) to the skewed key in the larger table, replicate the matching rows in the smaller table with all salt values, then join on the salted key
  • B. Use Spark AQE (Adaptive Query Execution) skew join optimization
  • C. Filter out "US" records and process them separately in a simpler aggregation
  • D. Increase executor memory to handle the large partition
Jawaban Benar: B
Spark 3.0+ AQE with skew join optimization (spark.sql.adaptive.skewJoin.enabled=true) automatically detects and splits skewed partitions at runtime. It splits the large partition into smaller sub-partitions and replicates the matching data from the other side. This is the simplest solution requiring no code changes.

Opsi A: SALAH. Works but requires manual code changes and is more complex.
Opsi B: BENAR.
Opsi C: SALAH. Changes logic and may miss join records.
Opsi D: SALAH. Doesn't parallelize the single large task.

A Glue ETL job reads data from S3 and the code performs a collect() operation to bring all data to the driver for custom Python processing. The dataset is 10 GB. The job fails with driver OOM. Besides increasing driver memory, which code change avoids this pattern?
  • A. Add more executor nodes, handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and minimizing end-to-end processing latency
  • B. Use toPandas() instead of collect() with distributed processing using Spark UDFs (User Defined Functions) or mapPartitions that processes data on executors without bringing it
  • C. Write to S3 first then read with pandas in a separate step, meeting the latency and throughput goals of the design and minimizing end-to-end processing latency
  • D. Replace collect() with distributed processing using Spark UDFs (User Defined Functions) or mapPartitions that processes data on executors without bringing it to the driver

collect() brings entire dataset to driver memory — anti-pattern for large datasets. UDFs and mapPartitions execute custom logic on executors where data already resides, distributed across the cluster. This keeps 10 GB distributed across many executors (each handling a portion) instead of all on one driver.

Opsi D: BENAR.

#S3#Spark
A data engineer optimizes a Spark SQL query that reads a partitioned Parquet table in S3. The query filters on column 'region' which is the partition key, and column 'amount > 1000' which is stored within the Parquet files. Which optimization leverages both partition pruning AND predicate pushdown?
  • A. Create a secondary index on the 'amount' column in S3, satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline and satisfying strict compliance and audit requirements
  • B. Apply filters in separate sequential operations: first filter region, then filter amount, handling the described workload reliably at scale and meeting the latency and throughput goals of the design and providing exactly-once processing semantics
  • C. Write the query with both filters in the WHERE clause: WHERE region = 'US' AND amount > 1000 — Spark automatically applies partition pruning for 'region' and predicate pushdown for 'amount' to Parquet
  • D. Read all data first, then filter in Python code after collecting with both filters in the WHERE clause: WHERE region = 'US', satisfying all of the stated requirements with minimal effort
Jawaban Benar: C
Spark SQL optimizer automatically handles both: (1) Partition pruning — only reads S3 prefixes matching region='US', skipping all other region partitions. (2) Predicate pushdown to Parquet — uses Parquet's column statistics (min/max) to skip row groups where amount is entirely ≤ 1000. Both happen at read time, minimizing I/O.

Opsi A: SALAH. S3/Parquet don't support secondary indexes.
Opsi B: SALAH. Spark optimizer combines them anyway, but explicit combined WHERE is clearer.
Opsi C: BENAR.
Opsi D: SALAH. Reads everything — worst performance — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A Lambda function is triggered by DynamoDB Streams. The function processes each record by making a write to another DynamoDB table. Currently it calls PutItem for each record individually. With batches of 100 records, this means 100 separate API calls. How should the code be optimized?
  • A. Use TransactWriteItems for all 100 records in one transaction, meeting the latency and throughput goals of the design and satisfying all of the stated requirements with minimal effort
  • B. Use BatchWriteItem to write up to 25 items per API call, reducing the number of API calls from 100 to 4 and leveraging parallelism within each batch call
  • C. Increase Lambda timeout to accommodate sequential writes, meeting the latency and throughput goals of the design and handling the described workload reliably at scale and keeping steady-state operating costs low
  • D. Write to S3 instead of DynamoDB for better throughput and leveraging parallelism within each batch call, meeting the latency and throughput goals of the design and reducing day-to-day operational effort
Jawaban Benar: B
BatchWriteItem sends up to 25 items per API call, reducing network round-trips from 100 to 4 (100/25). Each batch is processed in parallel by DynamoDB internally. This significantly reduces Lambda execution time.

Opsi A: SALAH. Limited to 100 items per transaction tapi much slower karena transaction overhead dan all-or-nothing semantics.
Opsi B: BENAR.
Opsi C: SALAH. Doesn't optimize, just accommodates slow code.

#Glue#Spark
An AWS Glue PySpark job performs string operations on a column using a Python UDF (User Defined Function). The UDF processes 100 million rows but is extremely slow because of serialization overhead between JVM and Python. Which approach improves performance?
  • A. Replace the Python UDF with Spark built-in functions (pyspark.sql.functions) or Pandas UDFs (vectorized UDFs) that minimize JVM-Python serialization
  • B. Increase the number of Glue DPUs, scaling elastically to millions of events per second and reducing day-to-day operational effort
  • C. Cache the DataFrame before applying the UDF, reducing day-to-day operational effort and requiring no servers to manage or scale manually
  • D. Process fewer rows per partition with Spark built-in functions, absorbing sudden traffic spikes without throttling and reducing day-to-day operational effort
Jawaban Benar: A
Python UDFs serialize data row-by-row between JVM and Python interpreter — extremely slow. Built-in Spark functions execute natively in JVM (no serialization). Pandas UDFs (vectorized) process data in Arrow batches — much less serialization overhead than row-by-row UDFs. Can be 10-100x faster.

Opsi A: BENAR.
Opsi B: SALAH. Each DPU still has the same serialization overhead per row.
Opsi C: SALAH. Helps repeated reads, not processing speed.
Opsi D: SALAH. Doesn't reduce total serialization cost — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

#Redshift
A Redshift query that generates a daily report takes 20 minutes. The query performs multiple JOINs, a GROUP BY with 50 aggregate functions, and a HAVING clause. EXPLAIN shows sequential scans on large tables. Which Redshift-specific optimization is MOST likely to improve performance?
  • A. Rewrite the query to use subqueries instead of JOINs, transforming records into the required target format and integrating natively with the rest of the pipeline and applying schema conversion and enrichment inline
  • B. Run VACUUM and ANALYZE on all tables with the WHERE/JOIN conditions, meeting the latency and throughput goals of the design and applying schema conversion and enrichment inline and minimizing end-to-end processing latency
  • C. Add indexes to the join columns, validating and cleansing each record before delivery and satisfying all of the stated requirements with minimal effort and handling the described workload reliably at scale
  • D. Review and optimize the table distribution keys (DISTKEY) to co-locate joined data on the same nodes, and ensure sort keys (SORTKEY) align with the WHERE/JOIN conditions to enable zone-map pruning
Jawaban Benar: D
Redshift's columnar MPP architecture relies heavily on distribution and sort keys for performance. Proper DISTKEY on join columns eliminates network redistribution (data already co-located). SORTKEY enables zone-map pruning (skipping entire 1MB blocks that don't match predicates). These together can turn sequential scans into targeted reads.

Opsi A: SALAH. Optimizer usually handles this, may not improve.
Opsi B: SALAH. Helps maintenance but DISTKEY/SORTKEY design is fundamental — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
Opsi C: SALAH. Redshift doesn't have traditional indexes.
Opsi D: BENAR.
