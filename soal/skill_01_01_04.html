A data engineer is consuming a financial data API that occasionally returns HTTP 429 (Too Many Requests) errors. The pipeline must be resilient and eventually process all data. Which implementation pattern is MOST appropriate?
  • A. Implement exponential backoff with jitter and a maximum retry count with dead letter queue for failed requests
  • B. Immediately retry failed requests with no delay, guaranteeing no data loss during component failures and providing exactly-once processing semantics
  • C. Skip the failed requests and log them for manual retry later with jitter, providing exactly-once processing semantics
  • D. Increase the concurrency of API calls to compensate for failed requests, guaranteeing no data loss during component failures
Correct Answer: A
Exponential backoff with jitter is best practice for handling rate limiting (429 errors). Jitter prevents thundering herd problem where all retry occurs simultaneously. Maximum retry count prevents infinite loops. Dead letter queue captures requests that fails after all retry for investigation.

Option A: CORRECT.
Option B: INCORRECT. Memperburuk rate limiting.
Option C: INCORRECT. Kehilangan data — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Justru causes more 429 errors.
