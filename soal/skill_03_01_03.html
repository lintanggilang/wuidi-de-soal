A data engineer is writing a Python script using boto3 to list all objects in an S3 bucket that contains over 2 million objects. The script uses s3_client.list_objects_v2() but only returns 1,000 objects. What is the correct approach to retrieve ALL objects from the bucket?
  • A. Set MaxKeys parameter to 2000000 in the list_objects_v2 call with native S3 integration and optimized data transfer
  • B. Use a paginator: paginator = s3_client.get_paginator('list_objects_v2') to automatically handle pagination across all pages
  • C. Use the S3 resource interface (s3.Bucket.objects.all()) which has no limit
  • D. Call list_objects_v2 in a loop, manually passing the NextContinuationToken from each response
Jawaban Benar: B
Boto3 paginators adalah cara yang paling clean dan recommended untuk menangani paginated API responses. Paginator secara otomatis handle continuation tokens, iterating melalui semua halaman tanpa manual loop. Ini juga mendukung PageSize configuration dan JMESPath filtering. Opsi A salah — MaxKeys dibatasi 1000 oleh S3 API, tidak bisa diset lebih tinggi — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini. Opsi C bisa bekerja untuk use case sederhana tapi resource interface memberikan kurang kontrol dan bisa memory-intensive untuk 2M objects. Opsi D secara teknis benar tapi manual token management lebih error-prone dan verbose dibandingkan paginator — paginator adalah best practice.

A data pipeline running on AWS Lambda uses boto3 to call the Glue StartJobRun API. During peak hours, the pipeline frequently receives "ThrottlingException" errors. The engineer needs to implement a resilient retry strategy without modifying every API call in the code. Which approach is MOST effective?
  • A. Wrap each boto3 API call in a try-except block with time.sleep(5) between retries
  • B. Configure boto3 client with a Config object using retries={'mode': 'adaptive', 'max_attempts': 10} for automatic adaptive retry with token bucket rate limiting
  • C. Increase the Lambda function's timeout to allow more time for API calls to succeed with a Config object using retries={'mode': 'adaptive'
  • D. Use the AWS SDK default retry configuration which handles all throttling scenarios
Jawaban Benar: B
Boto3 adaptive retry mode menggunakan token bucket algorithm yang secara dinamis menyesuaikan retry behavior berdasarkan throttling responses. Ini lebih sophisticated dari standard mode — ia memperlambat request rate ketika mendeteksi throttling, mencegah thundering herd. max_attempts: 10 memberikan cukup retry untuk intermittent throttling. Konfigurasi ini berlaku untuk semua API calls pada client tersebut. Opsi A (manual retry) tidak adaptive dan memerlukan modifikasi setiap call. Opsi C (timeout) tidak menyelesaikan throttling — hanya memberikan lebih banyak waktu untuk gagal — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini. Opsi D (default) menggunakan 'legacy' mode dengan hanya 5 attempts tanpa adaptive behavior.

A data engineer's Lambda function creates an EMR cluster and needs to wait until the cluster reaches the "WAITING" state before submitting steps. The function uses a polling loop with describe_cluster() calls every 30 seconds. This approach is unreliable because the Lambda function sometimes times out. What is the BEST boto3 pattern for waiting on resource state changes?
  • A. Use a boto3 waiter: emr_client.get_waiter('cluster_running').wait(ClusterId=cluster_id) with WaiterConfig for custom delay and max attempts
  • B. Increase the Lambda timeout to 15 minutes to ensure enough time for polling with WaiterConfig for custom delay and max attempts
  • C. Use EventBridge to detect EMR state changes and trigger a second Lambda function
  • D. Use the EMR resource interface which blocks until the cluster is ready
Jawaban Benar: A
Boto3 waiters adalah built-in polling mechanism yang menunggu resource mencapai state tertentu. Waiters memiliki configurable Delay (polling interval) dan MaxAttempts, dengan proper error handling untuk terminal failure states. Untuk EMR, 'cluster_running' waiter polls describe_cluster secara teratur. WaiterConfig memungkinkan tuning untuk fit within Lambda timeout. Opsi B (increase timeout) masih unreliable jika cluster takes longer than 15 min — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini. Opsi C (EventBridge) adalah arsitektur yang lebih baik untuk long waits tapi pertanyaan spesifik tentang boto3 pattern. Opsi D — EMR tidak memiliki "resource interface" yang blocking di boto3.

A data pipeline in Account A needs to read data from a DynamoDB table in Account B. The pipeline runs on an EC2 instance with an IAM role attached. The DynamoDB table in Account B has a resource policy allowing cross-account access. How should the data engineer configure boto3 to access the cross-account DynamoDB table?
  • A. Use sts_client.assume_role() to get temporary credentials for a role in Account B, then create a new boto3 DynamoDB client with those credentials
  • B. Configure the AWS_DEFAULT_REGION environment variable to point to Account B's region with those credentials for a role in Account B
  • C. Pass the Account B's account ID as a parameter to the DynamoDB client constructor
  • D. Create the DynamoDB client with endpoint_url pointing to Account B's DynamoDB endpoint
Jawaban Benar: A
Cross-account access ke AWS resources menggunakan STS AssumeRole pattern. Pipeline di Account A memanggil sts.assume_role() untuk mendapatkan temporary credentials (AccessKeyId, SecretAccessKey, SessionToken) yang memiliki permissions dari role di Account B. Credentials ini digunakan untuk membuat DynamoDB client baru yang beroperasi dalam context Account B. Opsi B (region) hanya mengatur region, tidak memberikan cross-account access — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini. Opsi C — tidak ada parameter account ID di client constructor. Opsi D — DynamoDB endpoint URL sama untuk semua accounts dalam region yang sama; endpoint tidak membedakan antar accounts.

A data engineer is developing a Glue ETL job that writes processed data to DynamoDB using boto3 batch_write_item(). The job processes 500,000 records. Some batch writes return UnprocessedItems in the response. The engineer notices data loss in the target table. What is the correct way to handle UnprocessedItems?
  • A. Ignore UnprocessedItems as DynamoDB will eventually process them with exponential backoff until all items are successfully written
  • B. Implement a retry loop that re-submits UnprocessedItems with exponential backoff until all items are successfully written
  • C. Increase the DynamoDB table's provisioned write capacity to prevent UnprocessedItems
  • D. Switch from batch_write_item to individual put_item calls for each record
Jawaban Benar: B
batch_write_item() dapat mengembalikan UnprocessedItems ketika throughput terlampaui. Items ini TIDAK secara otomatis di-retry oleh SDK — developer harus explicitly menangani mereka. Pattern yang benar: loop yang mengambil UnprocessedItems dari response, apply exponential backoff, dan re-submit sampai tidak ada UnprocessedItems tersisa. Opsi A salah — UnprocessedItems akan HILANG jika tidak di-handle (ini penyebab data loss) — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini. Opsi C (increase capacity) mengurangi kemungkinan UnprocessedItems tapi tidak menghilangkannya sepenuhnya — handling tetap diperlukan. Opsi D (individual put_item) sangat lambat untuk 500K records dan tetap bisa throttled.

A data engineer is writing a Lambda function using boto3 that processes S3 event notifications. The function needs to handle errors gracefully when the S3 object referenced in the event has been deleted by the time the function runs. Which boto3 exception handling pattern correctly catches this scenario?
  • A. Use a generic try-except Exception block to catch all possible errors
  • B. Catch botocore.exceptions.ClientError and check if error.response['Error']['Code'] == '404' or 'NoSuchKey'
  • C. Catch s3_client.exceptions.NoSuchKeyException using the client's built-in exception classes
  • D. Check if the object exists using head_object() before attempting to download it and check if error
Jawaban Benar: B
Boto3 S3 operations raise botocore.exceptions.ClientError untuk service-level errors. Untuk menangani "object tidak ada", Anda catch ClientError dan periksa error code di response dictionary. Untuk S3 get_object, code akan '404' atau 'NoSuchKey'. Pattern ini memberikan granular error handling. Opsi A (generic Exception) terlalu broad — tidak bisa membedakan antara missing object vs permission error vs network error. Opsi C — S3 client tidak expose exceptions sebagai attributes pada client object (berbeda dengan beberapa service seperti DynamoDB). Opsi D (head_object check) memiliki race condition — object bisa dihapus antara check dan download (TOCTOU) — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A data engineer's Python application running on ECS uses boto3 to interact with multiple AWS services (S3, Glue, Redshift Data API). The application currently uses hardcoded AWS access keys in the code. The security team requires moving to a more secure credential management approach. Which solution follows AWS best practices for credential management with the SDK?
  • A. Store access keys in environment variables on the ECS task definition
  • B. Store access keys in AWS Secrets Manager and retrieve them at application startup
  • C. Assign an IAM task role to the ECS task definition and let boto3 use the automatic credential provider chain
  • D. Encrypt the access keys and store them in the application's configuration file and let boto3 use the automatic credential provider chain
Jawaban Benar: C
IAM task roles pada ECS adalah best practice karena: (1) tidak ada credentials yang perlu di-manage — boto3 secara otomatis mendapatkan temporary credentials dari credential provider chain melalui container metadata endpoint, (2) credentials rotate otomatis, (3) tidak ada risk credential exposure. Boto3 akan otomatis menemukan dan menggunakan task role credentials tanpa konfigurasi tambahan. Opsi A (env vars) masih menggunakan long-lived credentials. Opsi B (Secrets Manager) memerlukan logic tambahan dan masih menggunakan long-lived keys. Opsi D (encrypted config) tetap memerlukan decryption key dan access keys management — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A data engineer needs to delete 10,000 objects from an S3 bucket as part of a data cleanup pipeline using boto3. Calling delete_object() for each object individually takes over 30 minutes. What is the MOST efficient approach to perform bulk deletions?
  • A. Use s3_client.delete_objects() which accepts up to 1,000 keys per call, processing objects in batches
  • B. Use Python multiprocessing to call delete_object() in parallel across multiple processes
  • C. Configure an S3 Lifecycle rule to delete the objects and wait for it to take effect
  • D. Use the S3 resource interface Bucket.objects.delete() which handles bulk deletion automatically
Jawaban Benar: A
S3 delete_objects() API (multi-object delete) menerima hingga 1,000 keys per single API call, secara drastis mengurangi jumlah HTTP requests dari 10,000 menjadi 10 calls. Ini adalah cara paling efisien untuk bulk deletion. Pattern: batch keys menjadi groups of 1000, call delete_objects() untuk setiap batch. Opsi B (multiprocessing) meningkatkan complexity dan masih memerlukan 10,000 API calls (hanya parallel). Opsi C (Lifecycle) tidak immediate — bisa memerlukan sampai 24+ jam untuk S3 memproses lifecycle rules. Opsi D bisa bekerja tapi resource interface secara internal tetap membatasi delete calls, dan less control dibanding explicit batching.

A data engineer is developing a Glue Python Shell job that starts a Redshift query using the Redshift Data API (redshift_data.execute_statement()). The query takes 5 minutes to complete. The execute_statement() call returns immediately with a query ID. How should the engineer wait for and retrieve the query results?
  • A. Call describe_statement() in a polling loop until the Status field returns 'FINISHED', then call get_statement_result() to retrieve the results
  • B. Call get_statement_result() immediately after execute_statement() — it will block until results are ready
  • C. Use a boto3 waiter for Redshift Data API to wait for statement completion
  • D. Set a synchronous=True parameter in execute_statement() to make it blocking configured for optimal performance and minimal operational overhead
Jawaban Benar: A
Redshift Data API adalah asynchronous — execute_statement() returns immediately dengan Id (query ID). Untuk mendapatkan results, Anda harus poll describe_statement() sampai Status menjadi 'FINISHED' (atau 'FAILED'/'ABORTED'), kemudian call get_statement_result() untuk mengambil data. Pattern: while loop dengan sleep interval checking status. Opsi B salah — get_statement_result() akan throw error jika statement belum selesai, tidak blocking. Opsi C — boto3 tidak memiliki built-in waiter untuk Redshift Data API statement completion. Opsi D — tidak ada parameter 'synchronous' di execute_statement() API — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.

A data engineering team has a Python application that makes boto3 calls to AWS Glue APIs. In production, the application occasionally experiences "EndpointConnectionError" and "ConnectTimeoutError" exceptions during network instability. The team wants to differentiate between retryable transient errors and non-retryable client errors in their error handling logic. Which exception hierarchy correctly categorizes these errors in botocore?
  • A. Catch botocore.exceptions.ConnectionError (parent of EndpointConnectionError and ConnectTimeoutError) for retryable network errors, and botocore.exceptions.ClientError for non-retryable API errors
  • B. All boto3 exceptions are retryable; implement retry for every exception type
  • C. Catch Exception base class and check the exception message string for "timeout" or "connection" keywords
  • D. Use ClientError for all errors and check the HTTP status code — 5xx is retryable, 4xx is not configured for optimal performance and minimal operational overhead
Jawaban Benar: A
Botocore memiliki exception hierarchy yang jelas: botocore.exceptions.ConnectionError (dan subclasses EndpointConnectionError, ConnectTimeoutError, ReadTimeoutError) adalah transient network errors yang aman untuk di-retry. botocore.exceptions.ClientError adalah service-level errors yang memerlukan pemeriksaan error code — beberapa retryable (throttling, 500) dan beberapa tidak (validation errors, access denied). Membedakan kedua tipe ini penting untuk retry strategy yang benar. Opsi B salah — retry pada non-retryable errors (misalnya AccessDenied) adalah sia-sia. Opsi C (string matching) fragile dan tidak reliable. Opsi D — network errors bukan ClientError dan tidak memiliki HTTP status code — meskipun deskripsinya terdengar meyakinkan, secara fundamental tetap tidak sesuai untuk kebutuhan ini.
