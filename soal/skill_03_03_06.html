A production AWS Glue ETL job that has been running successfully for 6 months suddenly fails with the error: "AnalysisException: cannot resolve 'customer_status' given input columns." The source data is an S3-based data lake with JSON files produced by an upstream microservice. What is the MOST likely cause and how should the data engineer investigate?
  • A. The upstream microservice deployed a schema change that removed or renamed the 'customer_status' field. Investigate by comparing recent source file schemas with the Glue Data Catalog table definition and checking the upstream service's deployment history.
  • B. The Glue job's DPU allocation is insufficient, causing memory errors that manifest as schema resolution failures.
  • C. The S3 bucket policy was modified, preventing the Glue job from reading certain files that contain the customer_status field.
  • D. The Glue Data Catalog table was accidentally deleted and recreated without the customer_status column.
Jawaban Benar: A
An AnalysisException for column resolution strongly indicates a schema drift issue — the upstream data no longer contains the expected column. This is the most common cause of sudden column-not-found errors in production pipelines: an upstream team deploys changes without coordinating with downstream consumers. Investigation should compare actual file schemas (using Glue crawler or manual inspection) with the expected schema. Option B: DPU exhaustion causes OutOfMemoryError or task failures, not schema resolution errors. Option C: Permission issues would cause AccessDenied errors, not column resolution errors. Option D: While possible, this would also affect the Glue crawler and would be evident in the catalog's modification history.
2
An EMR cluster running a daily Spark batch job fails during the bootstrap action phase with the error: "Bootstrap action returned a non-zero return code." The bootstrap script installs Python packages from PyPI. The same cluster configuration worked yesterday. What is the MOST likely cause and resolution?
  • A. A Python package dependency has a new version with breaking changes or an incompatible sub-dependency. Pin package versions in the bootstrap script's requirements file and host packages in a private S3-based PyPI mirror.
  • B. The EMR cluster's IAM role lost permissions to access the bootstrap script stored in S3.
  • C. The EMR AMI was automatically updated overnight, changing the base Python version.
  • D. The cluster's VPC security group was modified, blocking outbound internet access needed for pip install.
Jawaban Benar: A
Bootstrap scripts that install packages from PyPI without pinned versions are vulnerable to upstream package releases that introduce breaking changes or incompatible dependency versions. Since it worked yesterday, a new package release is the most likely cause. Pinning versions (package==x.y.z) and hosting in a private repository eliminates external dependency risks. Option B: IAM permission changes would produce a different error about accessing the bootstrap script, not a non-zero return code from script execution. Option C: EMR AMIs don't auto-update on running clusters; you specify the release label at launch. Option D: Network issues would produce timeout errors in the bootstrap logs, not a non-zero return code from package installation specifically.
3
A data engineer manages a Glue crawler that runs daily to update the Data Catalog. Recently, the crawler has been failing with: "Service Exception: Crawler already running." The crawler is scheduled at 6 AM but the previous day's run is sometimes still active. What is the BEST solution to prevent this issue while ensuring the catalog stays up to date?
  • A. Increase the crawler's timeout setting and configure the crawler to run on a longer schedule (e.g., every 2 hours instead of daily) to ensure completion before the next run.
  • B. Use a Step Functions workflow that checks the crawler state before starting it. If running, wait with an exponential backoff loop until the previous run completes, then start the new run.
  • C. Configure two crawlers pointing to the same source: one scheduled for 6 AM and a backup scheduled for 9 AM in case the first fails.
  • D. Disable the schedule and trigger the crawler from the Glue job's post-processing step only after data is written.
Jawaban Benar: B
A Step Functions workflow provides robust orchestration: it can check the crawler state (GetCrawler API), wait if running, and retry with backoff. This ensures the new crawl starts only when the previous one completes, preventing the "already running" error while guaranteeing catalog updates. Option A: Running more frequently doesn't solve the overlap problem and may increase costs. Option C: Two crawlers on the same source would have the same overlap problem and could cause catalog update conflicts. Option D: While event-driven triggering is good practice, it doesn't address the concurrent run issue if data writes overlap with ongoing crawls.
4
An EMR cluster running a long-running Spark Streaming job has been experiencing increasing task failures over the past week. YARN logs show that task attempts are failing with "Container killed by YARN for exceeding memory limits." The Spark UI shows that executor memory usage grows steadily over time. What is the MOST likely issue and resolution?
  • A. A memory leak in the application code is causing unbounded state growth. Review the streaming application for proper state cleanup, implement state TTL for stateful operations, and add periodic checkpointing with state pruning.
  • B. The executor memory configuration is too low for the workload. Increase spark.executor.memory to accommodate the growing data volume.
  • C. The YARN configuration yarn.nodemanager.resource.memory-mb is set too low, limiting container sizes.
  • D. The EMR cluster is running out of disk space for shuffle files, causing memory to be used as a fallback.
Jawaban Benar: A
Steadily growing memory usage in a streaming application is the hallmark of a memory leak or unbounded state accumulation. In Spark Streaming/Structured Streaming, stateful operations (aggregations, joins with watermarks) can accumulate state indefinitely if TTL or watermarks aren't properly configured. The solution is to implement state cleanup mechanisms. Option B: Simply increasing memory postpones the problem; if there's a leak, it will eventually exceed any allocation. Option C: Increasing YARN limits also postpones the issue without addressing the root cause. Option D: Disk space issues would manifest as "No space left on device" errors, not memory limit violations.
5
A data engineer maintains a Glue ETL job that processes data from 50 S3 partitions daily. The job uses Glue bookmarks to track processed data. After a source data reprocessing event (historical partitions were updated with corrected data), the Glue job is not picking up the corrected files because bookmarks mark those partitions as already processed. How should the engineer handle this situation?
  • A. Reset the Glue job bookmark for the specific job run to force reprocessing of all data, then let bookmarks resume tracking from the new state.
  • B. Disable bookmarks permanently and implement custom logic to track processed files using a DynamoDB table.
  • C. Delete the source S3 data and re-upload it with new filenames so bookmarks treat it as new data.
  • D. Create a new Glue job with a different name to process the corrected partitions, since bookmarks are per-job.
Jawaban Benar: A
Glue job bookmarks can be reset using the ResetJobBookmark API or from the console. This clears the bookmark state, causing the next run to reprocess all data as if running for the first time. After the full reprocessing run completes, the bookmark is re-established at the new state and subsequent runs resume incremental processing. Option B: Disabling bookmarks permanently is excessive for a one-time reprocessing need and adds ongoing maintenance overhead. Option C: Renaming files is operationally risky and doesn't address the fundamental issue. Option D: Creating a duplicate job adds unnecessary complexity; bookmark reset solves this directly.
6
An EMR cluster experiences a step failure with the error: "Step failed with bad application state: KILLED." The YARN ResourceManager UI shows the application was killed due to exceeding the maximum number of application attempts. The Spark application logs show multiple executor failures on specific nodes. What should the data engineer investigate FIRST?
  • A. Check the YARN node health on the failing nodes. Investigate node-level issues such as disk space exhaustion, unhealthy disks, or memory pressure that would cause executor failures on specific nodes rather than random distribution.
  • B. Increase the spark.yarn.maxAppAttempts configuration to allow more retries before the application is killed.
  • C. Check if the Spark application's JAR file is corrupted on S3 by comparing checksums.
  • D. Increase the EMR cluster size to provide more resources for the failing executors.
Jawaban Benar: A
When executor failures are concentrated on specific nodes (rather than random), it strongly suggests node-level issues: disk space exhaustion (/mnt or /tmp full), unhealthy local disks (HDFS or YARN marks disks as bad), or hardware issues. YARN marks nodes as unhealthy when local disk usage exceeds thresholds. Investigating node health is the correct first step before tuning configurations. Option B: Increasing max attempts masks the root cause and delays the eventual failure. Option C: Corrupted JARs would cause class loading errors uniformly across all nodes, not node-specific failures. Option D: Adding capacity doesn't fix underlying node health issues.
7
A production Glue ETL job that writes to Amazon Redshift via JDBC starts failing with the error: "Connection reset by peer" after running for 45 minutes. The job successfully processes data but fails during the write phase. The Redshift cluster appears healthy and accessible from the console. What is the MOST likely cause?
  • A. A network device (NAT Gateway, Network Load Balancer, or firewall) between Glue and Redshift is terminating idle TCP connections due to timeout. Configure the Glue JDBC connection with keepalive parameters and reduce the connection idle timeout.
  • B. The Redshift cluster's WLM queue has a statement timeout that kills long-running queries after 45 minutes.
  • C. The Glue job's execution role has been rotated and the new credentials expire after 45 minutes.
  • D. The Redshift cluster is running out of disk space during the COPY operation, causing connection termination.
Jawaban Benar: A
"Connection reset by peer" after a specific duration (45 minutes) is a classic symptom of network timeout issues. NAT Gateways have a 350-second idle timeout, and if the JDBC connection has idle periods during large batch writes, the connection is silently dropped. Adding TCP keepalive parameters (tcpKeepAlive=true) in the JDBC URL prevents this. Option B: WLM statement timeouts would produce a Redshift-specific error message ("statement timeout"), not a TCP connection reset. Option C: Glue job role credentials are managed internally and refresh transparently; they don't cause connection resets. Option D: Disk space issues would produce a Redshift error about disk full, not a TCP connection reset.

A data engineer needs to implement automatic retry logic for a Glue ETL job that occasionally fails due to transient S3 throttling errors (503 SlowDown). The job runs as part of a scheduled Glue workflow. What is the MOST appropriate retry strategy?
  • A. Configure the Glue job's MaxRetries parameter to 2 within the Glue workflow trigger configuration. This provides built-in retry with Glue handling the re-execution automatically.
  • B. Implement try-catch blocks in the Glue script's Python code to catch S3 throttling errors and retry individual S3 API calls with exponential backoff.
  • C. Configure S3 Event Notifications to detect 503 errors and trigger a Lambda function to restart the Glue job.
  • D. Use Amazon EventBridge to detect Glue job FAILED state changes and trigger job restart via Lambda with a 5-minute delay.
Jawaban Benar: A
Glue jobs support a MaxRetries parameter (0-10) that automatically retries the entire job upon failure. Within a Glue workflow, this is configured in the trigger settings. This is the simplest and most appropriate approach for transient failures because Glue handles the retry lifecycle, including waiting between attempts. Option B: While application-level retries are good for individual API calls, S3 throttling that fails the entire job suggests widespread throttling that requires job-level retry rather than call-level retry. Option C: S3 Event Notifications don't capture 503 error responses. Option D: EventBridge-based restart works but adds unnecessary complexity when Glue's built-in retry mechanism handles this natively.
9
An EMR cluster running a Hive-based ETL pipeline shows degrading performance over the past month. Investigation reveals that the metastore (RDS MySQL) query response times have increased from 50ms to 2 seconds. The metastore database has grown to contain 500,000 partitions across 200 tables. What maintenance action is MOST likely to resolve the performance degradation?
  • A. Clean up stale partitions and run ANALYZE TABLE to update partition statistics. Consider partitioning the metastore's PARTITIONS table or upgrading the RDS instance class.
  • B. Restart the EMR cluster to refresh the Hive metastore cache and clear connection pools.
  • C. Increase the Hive metastore connection pool size to handle more concurrent queries.
  • D. Switch from MySQL to Amazon Aurora for the Hive metastore to get better performance automatically.
Jawaban Benar: A
A Hive metastore with 500,000 partitions experiencing growing query latency is a classic database maintenance issue. Stale partitions from deleted/archived data still occupy metastore space, and outdated statistics cause suboptimal query plans. Cleaning up unnecessary partitions, updating statistics, and potentially scaling the RDS instance directly addresses the root cause. Option B: Restarting the cluster refreshes caches temporarily but doesn't fix the underlying metastore database growth. Option C: Connection pool size isn't the issue; the individual queries themselves are slow due to table scan operations on large partition tables. Option D: Migrating to Aurora may help but doesn't address the data volume issue; the same partition bloat would eventually cause problems on Aurora too.
10
A data engineering team manages 30 AWS Glue jobs that share common library dependencies packaged as a .whl file stored in S3. After updating the shared library to fix a bug, some jobs start failing with import errors while others work correctly. All jobs reference the same S3 path for the library. What is the MOST likely explanation?
  • A. Some Glue jobs are using cached versions of the library from previous runs. Glue workers may cache Python packages between job runs on warm pools. Updating the library filename with a version suffix (e.g., library-v2.0.whl) forces all jobs to download the new version.
  • B. The S3 upload of the new .whl file hasn't propagated to all S3 availability zones yet due to eventual consistency.
  • C. Some Glue jobs are running Glue version 2.0 while others run 3.0, causing Python compatibility differences with the new library.
  • D. The IAM roles for the failing jobs have lost read access to the S3 path where the library is stored.
Jawaban Benar: A
AWS Glue uses warm pools to speed up job startup. Workers in warm pools may have previously downloaded libraries cached locally. When the same S3 path is used for an updated library, some workers use the cached old version while others (cold-started) download the new one. The solution is to change the filename/path with versioning so all workers are forced to download the new file. Option B: S3 provides strong read-after-write consistency since December 2020; eventual consistency is no longer an issue for overwrites. Option C: While Glue version differences exist, import errors from a shared library update suggest a caching/version problem rather than Python version incompatibility. Option D: Permission issues would affect all runs of those jobs consistently, not intermittently.
