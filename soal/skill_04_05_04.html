A data engineering team suspects that someone changed the encryption settings on their production S3 bucket two weeks ago, which caused an ETL pipeline failure. They need to determine: WHO made the change, WHEN it happened, and WHAT the previous encryption configuration was. Which combination of AWS services provides all three pieces of information?
  • A. AWS Trusted Advisor provides the change history with user attribution for S3 security changes, satisfying all of the stated requirements with minimal effort
  • B. AWS Config configuration timeline shows the previous and current encryption settings with timestamps; CloudTrail shows who made the PutBucketEncryption API call
  • C. AWS Config alone provides who, when, and what — it records the IAM identity, timestamp, and configuration diff with timestamps; CloudTrail shows who made the PutBucketEncryption API call
  • D. CloudTrail alone provides all information since it logs the API call with user identity, timestamp, and request parameters
Correct Answer: B
AWS Config and CloudTrail provides informasi komplementer: Config stores configuration timeline (state history) — indicates configuration BEFORE and AFTER changes along with timestamp, enables Anda melihat persis what encryption setting old. CloudTrail merekam API calls including identity of caller (WHO — IAM user/role ARN, source IP). Kombinasi both provides complete audit trail.

Option A: INCORRECT. Trusted Advisor provides recommendations, not change history.
Option B: CORRECT.
Option C: INCORRECT. Config TIDAK merekam identitas who that creates changes; Config only merekam state changes — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. CloudTrail merekam API request parameters but not always stores PREVIOUS state; also request parameters not always indicates full previous configuration.

A company operates 15 AWS accounts in their organization and needs a centralized view of all resource configurations across all accounts and regions. The security team wants to query configuration data using SQL-like syntax to identify non-compliant resources. Which AWS Config feature enables this centralized multi-account, multi-region view?
  • A. Use AWS Organizations APIs to collect configuration details from all member accounts configured for optimal performance and minimal operational overhead, integrating natively with the rest of the pipeline
  • B. Deploy AWS Config rules in each account and aggregate findings to Security Hub, satisfying all of the stated requirements with minimal effort and satisfying strict compliance and audit requirements
  • C. Export Config snapshots from all accounts to a central S3 bucket and query with Athena, enforcing encryption and fine-grained access control and meeting the latency and throughput goals of the design
  • D. Create an AWS Config Aggregator in a central account that collects configuration data from all source accounts, then use AWS Config advanced queries to run SQL queries across aggregated data
Correct Answer: D
AWS Config Aggregator collects configuration and compliance data from multiple accounts and regions to one central view. Dikombinasi with Config advanced queries (that uses SQL-like syntax), security team can runs queries such as "SELECT resourceId, configuration WHERE resourceType = 'AWS::S3::Bucket' AND configuration.serverSideEncryptionConfiguration IS NULL" across all 15 accounts. Aggregator can in-setup through AWS Organizations (automatic enrollment) or individual account authorization.

Option A: INCORRECT. Organizations API not provides resource configuration details — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. Security Hub aggregasi for security findings, not full configuration data.
Option C: INCORRECT. Can works but requires additional infrastructure (Athena, Glue catalog) and data not real-time.
Option D: CORRECT.

A data platform team uses Amazon Redshift, AWS Glue, and Amazon S3 for their data pipeline. They want AWS Config to record configuration changes for these specific data services only, not all AWS resources in the account. This is to reduce Config costs and noise. How should they configure AWS Config recording?
  • A. Enable Config recording with tag-based filtering — only resources tagged with "data-pipeline=true" will be recorded
  • B. Configure AWS Config to record specific resource types only: AWS::Redshift::Cluster, AWS::Glue::Job, AWS::Glue::Crawler, AWS::Glue::Database, AWS::S3::Bucket
  • C. Enable Config with "Record all resources" and create a filter to display only data service resources
  • D. Use AWS Config's service-linked recording that automatically detects and records only data-related services with native S3 integration and optimized data transfer
Correct Answer: B
AWS Config supports selective recording — Anda can memilih resource types that want direkam daripada merekam all resources. By memilih specific types (Redshift clusters, Glue jobs/crawlers/databases, S3 buckets), only changes on resource types said that direkam. This reduces number configuration items that is stored and cost.

Option A: INCORRECT. Config not supports tag-based recording selection; tag-based filtering only available for Config rules evaluation scope, not recording.
Option B: CORRECT.
Option C: INCORRECT. "Record all resources" merekam ALL resource types in account that adds cost; filtering only in display level, recording still occurs.
Option D: INCORRECT. Not there is feature "service-linked recording" that auto-detect data services in Config — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A compliance team needs to ensure all S3 buckets in their data lake have: (1) server-side encryption enabled, (2) versioning enabled, (3) public access blocked, and (4) access logging enabled. They want to deploy all four checks as a package and ensure any new account added to the organization automatically gets these rules. Which Config feature achieves this?
  • A. Deploy an AWS Config Conformance Pack containing all four rules, deployed through AWS Organizations for automatic enforcement on new accounts
  • B. Use AWS Security Hub standards that include S3 security checks for automatic enforcement on new accounts, enforcing encryption and fine-grained access control
  • C. Create four individual Config rules and deploy them using CloudFormation StackSets across the organization, integrating natively with the rest of the pipeline
  • D. Create a single custom Config rule using Lambda that checks all four conditions simultaneously, handling the described workload reliably at scale
Correct Answer: A
Config Conformance Packs is collection of Config rules and remediation actions that can be deployed as a single entity. When deployed through AWS Organizations, conformance packs automatic is applied to all member accounts including accounts new that bergabung. Conformance pack can contains managed rules (s3-bucket-server-side-encryption-enabled, s3-bucket-versioning-enabled, s3-bucket-public-read-prohibited, s3-bucket-logging-enabled) in one template YAML.

Option A: CORRECT.
Option B: INCORRECT. Security Hub has S3 checks but this separate from Config rules and not provides Config-specific compliance reporting — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. CloudFormation StackSets can deploy rules but requires manual update when adds rules; also less terintegrasi with Config's compliance view.
Option D: INCORRECT. Single custom rule less maintainable and not mengikuti best practice separation of concerns.

An AWS Config rule detects that an S3 bucket has public read access enabled, which violates company policy. The security team wants automatic remediation — when the rule evaluates as NON_COMPLIANT, the public access should be automatically blocked. Which Config remediation configuration achieves this?
  • A. Create an EventBridge rule triggered by Config compliance change events and invoke a Lambda function to block public access
  • B. Use AWS Config auto-remediation with a custom Lambda function that calls S3 PutPublicAccessBlock API, handling the described workload reliably at scale
  • C. Configure the Config rule with automatic remediation using the SSM Automation document AWS-DisableS3BucketPublicReadWrite, with automatic remediation retries set to 5
  • D. Configure the Config rule with manual remediation and wait for security team approval with native S3 integration and optimized data transfer
Correct Answer: C
AWS Config remediation actions uses AWS Systems Manager Automation documents. AWS provides pre-built SSM Automation documents for common remediations including AWS-DisableS3BucketPublicReadWrite. By configures automatic remediation on Config rule, each kali rule evaluates as NON_COMPLIANT, SSM Automation document automatic dieksekusi. Retry mechanism ensures remediation dicoba several kali if fails.

Option A: INCORRECT. EventBridge + Lambda can works but this bypass Config's built-in remediation feature; less integrated and not utilizes retry/tracking built-in.
Option B: INCORRECT. Config auto-remediation uses SSM documents not direct Lambda invocation; for custom remediation, Anda creates custom SSM document that could call Lambda, but pre-built document already available.
Option C: CORRECT.
Option D: INCORRECT. Manual remediation not memenuhi requirement "automatic — although its description sounds convincing, in a fundamental still not appropriate for requirements this.".

A data engineer needs to write a custom AWS Config rule that evaluates whether Glue jobs use a specific security configuration (encryption and CloudWatch logging enabled). The managed Config rules do not cover Glue job configurations. Which approach correctly implements this custom rule?
  • A. Create a Lambda function that receives the configuration item from Config, checks if the Glue job has the required SecurityConfiguration property and CloudWatch logging, then returns COMPLIANT or NON_COMPLIANT using the Config PutEvaluations API
  • B. Write an AWS Config custom policy rule using Guard policy language to check Glue job properties declaratively configured for optimal performance and minimal operational overhead, handling the described workload reliably at scale
  • C. Create a CloudWatch Events rule that monitors Glue job creations and updates, triggering a Lambda that reports compliance to Config, removing the need to provision or patch any infrastructure and satisfying strict compliance and audit requirements
  • D. Use AWS Config advanced queries to periodically search for non-compliant Glue jobs and flag them manually, handling the described workload reliably at scale and protecting the data both in transit and at rest
Correct Answer: A
Custom Config rules uses Lambda functions that in-trigger by Config when configuration changes is detected or in a periodic. Lambda function receives event contains configuration item (resource details), evaluates compliance (whether SecurityConfiguration there is and mereferensikan config that correct, whether logging enabled), lalu calls PutEvaluations API with result COMPLIANT or NON_COMPLIANT.

Option A: CORRECT.
Option B: INCORRECT. Config custom policy rules (Guard/Proactive rules) available but not all resource types is supported by Guard; for Glue jobs, Lambda-based rule more reliable — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: INCORRECT. CloudWatch Events not mekanisme delivery for custom Config rules; Config must trigger Lambda directly.
Option D: INCORRECT. Advanced queries only menampilkan current state, not continuous compliance evaluation with tracking history.

A security audit requires the team to understand exactly what changed in an Amazon Redshift cluster's configuration over the past 30 days. They need to see a day-by-day timeline of all configuration modifications including parameter group changes, VPC security group modifications, and encryption status changes. Which AWS Config feature provides this detailed historical view?
  • A. Check the Redshift cluster's maintenance history in the Redshift console with diff comparisons for the specific Redshift cluster, satisfying strict compliance and audit requirements
  • B. Query CloudTrail event history with filter for Redshift API calls in the last 30 days, handling the described workload reliably at scale
  • C. Use the AWS Config console's Resource Timeline view for the specific Redshift cluster, which shows all configuration changes in chronological order with diff comparisons
  • D. Use AWS Config configuration snapshots delivered to S3 and compare daily snapshots, satisfying all of the stated requirements with minimal effort and reducing day-to-day operational effort
Correct Answer: C
AWS Config Resource Timeline (also disebut Configuration Timeline) is feature that menampilkan complete history of configuration changes for specific resource. For Redshift cluster, timeline indicates: each changes configuration (parameter group, VPC security groups, encryption, node type, dll), timestamp changes, and capabilities for compare configurations between two titik time (diff view). This is way most directly and detail for melihat what that changes.

Option A: INCORRECT. Redshift maintenance history only mencakup maintenance events (patches, upgrades), not user-initiated configuration changes — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. CloudTrail indicates API calls (SIAPA performs APA) but not menampilkan full configuration state before/after; also parameter group detail may not lengkap in event.
Option C: CORRECT.
Option D: INCORRECT. Configuration snapshots to S3 can in-compare but manual and not se-user-friendly timeline view.

A company wants to detect when any Amazon RDS instance in their data pipeline accounts is created without encryption enabled. When detected, they want to receive an SNS notification within minutes. They also need this detection to work for RDS instances across 20 accounts. Which approach provides near real-time detection across all accounts?
  • A. Deploy Config rule rds-storage-encrypted via Organization conformance pack, configure EventBridge rule in each account to forward compliance change events to a central event bus, which triggers SNS
  • B. Create the managed Config rule rds-storage-encrypted in each account with a Config Aggregator in central account, and configure SNS notification from the aggregator when NON_COMPLIANT
  • C. Use CloudTrail organizational trail to detect CreateDBInstance API calls and filter for unencrypted configurations via CloudWatch Logs Insights configured for optimal performance and minimal operational overhead
  • D. Deploy a periodic Lambda function that calls DescribeDBInstances across all accounts every 5 minutes and checks encryption status, streaming results downstream in near real time
Correct Answer: A
Organization conformance pack deploys Config rules to all member accounts automatically. EventBridge rules in each account forward compliance change events to central event bus when Config rule evaluates NON_COMPLIANT. Central EventBridge rule then triggers SNS notification. This provides near real-time notification (Config evaluates when resource creation detected, EventBridge forwards immediately).

Option A: CORRECT.
Option B: INCORRECT. Config Aggregator collects compliance data but not has native built-in notification mechanism that directly trigger SNS from compliance changes; aggregation can delay.
Option C: INCORRECT. CloudTrail can detects API calls but parsing CreateDBInstance parameters for encryption requires complex filtering and may miss encrypt-after-create scenarios — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Polling each 5 minutes not near real-time and creates significant API overhead across 20 accounts.

A data engineer is comparing AWS Config and AWS CloudTrail for their audit requirements. They need to answer: "What was the security group configuration of my Redshift cluster at 3:00 PM last Tuesday?" Which service answers this question and why?
  • A. Both services together — CloudTrail for the API call history and Config for the relationship mapping between Redshift and security groups, enforcing encryption and fine-grained access control and minimizing end-to-end processing latency
  • B. AWS Config — because it records point-in-time configuration snapshots (configuration items) that capture the complete resource configuration state, allowing you to look up the exact configuration at any past timestamp
  • C. VPC Flow Logs — because they record network-level security group usage at specific timestamps, handling the described workload reliably at scale and protecting the data both in transit and at rest
  • D. CloudTrail — because it logs all security group modification API calls with timestamps and full request/response parameters configured for optimal performance and minimal operational overhead, handling the described workload reliably at scale
Correct Answer: B
Pertanyaan this about STATE on titik time certain, not EVENTS. AWS Config merekam configuration items — snapshot lengkap from configuration resource on each changes. By Config, Anda can melihat "on timestamp X, resource Y has configuration Z." This including security groups that attached to Redshift cluster on time certain. CloudTrail merekam EVENTS (API calls) — for menjawab question state, Anda must replay all events from awal that complex and error-prone.

Option A: INCORRECT. Although kombinasi useful, Config alone quite for question about state.
Option B: CORRECT.
Option C: INCORRECT. VPC Flow Logs logs network traffic, not security group configuration.
Option D: INCORRECT. CloudTrail logs modification events but not stores resulting state directly; Anda must merekonstruksi state from sequence of events — although its description sounds convincing, in a fundamental still not appropriate for requirements this.

A data platform team wants to use AWS Config to detect when their data pipeline resources drift from the approved baseline configuration. Specifically, they need to detect: (1) Glue jobs that have been modified to remove encryption, (2) S3 buckets where lifecycle policies have been deleted, and (3) Redshift clusters where audit logging has been disabled. They want one unified compliance view. What is the MOST efficient approach?
  • A. Use AWS Config advanced queries running on a schedule via EventBridge to check all three conditions and publish results to a custom dashboard, handling the described workload reliably at scale
  • B. Create a single custom Config rule with a Lambda function that evaluates all three resource types based on the configuration item's resourceType field, handling the described workload reliably at scale
  • C. Create three separate custom Lambda-based Config rules, one for each resource type, and view compliance in the Config dashboard with fully managed infrastructure and automatic scaling
  • D. Use a combination of managed rules where available (s3-bucket-level-public-access-prohibited for S3, redshift-audit-logging-enabled for Redshift) and one custom rule for Glue, grouped in a conformance pack for unified view
Correct Answer: D
Best practice is uses managed rules when available (AWS maintains and updates them) and custom rules only when is required. AWS already provides managed rules for Redshift audit logging (redshift-audit-logging-enabled) and berbagai S3 checks. For S3 lifecycle, can is used custom rule or managed rule that appropriate. For Glue job encryption, custom rule is required because there is no managed rule. All rules dikelompokkan in conformance pack for unified compliance view and single deployment unit.

Option A: INCORRECT. Advanced queries not compliance evaluation mechanism; mereka snapshot current state without tracking history or compliance status.
Option B: INCORRECT. Single Lambda handling multiple resource types violates single responsibility principle and difficult in-maintain.
Option C: INCORRECT. Tiga custom rules adds maintenance burden for checks that already there is as managed rules — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: CORRECT.
