Skill 1.2.6: Transform Data Between Formats

Converting between CSV, JSON, Parquet, ORC, Avro and other data formats with appropriate compression

1
A data engineer receives daily data extracts in CSV format from a vendor. The data must be stored in the data lake for analytical queries using Amazon Athena, which primarily filters on specific columns. Which target format and compression combination provides the BEST query performance and cost efficiency in Athena?
  • A. Apache Parquet with Snappy compression
  • B. CSV with gzip compression
  • C. JSON with LZ4 compression
  • D. Apache Avro with deflate compression
Jawaban Benar: A
Parquet adalah columnar format — Athena hanya membaca kolom yang diquery (column pruning), secara drastis mengurangi data yang di-scan dan biaya. Snappy compression memberikan good compression ratio dengan decompression speed yang sangat cepat. Kombinasi ini optimal untuk analytical queries. Opsi B (CSV gzip) — row format berarti semua kolom dibaca meskipun hanya query 2 kolom. Opsi C (JSON LZ4) — JSON sangat verbose dan row-oriented. Opsi D (Avro deflate) — Avro row-oriented, lebih cocok untuk serialization bukan analytics.

A streaming pipeline delivers data to Amazon S3 via Amazon Data Firehose. The data arrives as JSON and needs to be converted to Parquet format for efficient querying. Which Firehose feature handles this conversion without additional services?
  • A. Enable Firehose format conversion with output format set to Parquet, referencing a schema from the AWS Glue Data Catalog
  • B. Use a Lambda transformation function to convert JSON to Parquet within Firehose
  • C. Configure S3 to automatically convert JSON to Parquet on write
  • D. Use Firehose data partitioning to output as Parquet with output format set
Jawaban Benar: A
Amazon Data Firehose memiliki built-in format conversion yang mengkonversi JSON/CSV input ke Apache Parquet atau Apache ORC. Fitur ini menggunakan schema dari Glue Data Catalog untuk mapping fields. Tidak perlu Lambda atau service tambahan. Opsi B — Lambda transformation bisa modify content tapi Firehose native format conversion lebih efisien untuk format change. Opsi C — S3 tidak melakukan format conversion. Opsi D — partitioning berbeda dari format conversion.

A data engineer has a Parquet file in S3 that uses INT96 timestamp format. The downstream system (Amazon Redshift Spectrum) requires timestamps in INT64 (microseconds) format. The Glue ETL job reads the file correctly but Redshift Spectrum shows incorrect timestamps. How should this be resolved?
  • A. Re-write the Parquet file using Glue ETL with Spark config spark.sql.parquet.outputTimestampType set to TIMESTAMP_MICROS (INT64)
  • B. Cast the timestamp column in the Redshift Spectrum query
  • C. Update the Glue Data Catalog table to change the timestamp format
  • D. Use a Redshift UDF to interpret INT96 timestamps with Spark config spark
Jawaban Benar: A
INT96 timestamp adalah legacy Parquet format yang tidak semua systems support correctly. Mengkonversi ke TIMESTAMP_MICROS (INT64) menggunakan spark.sql.parquet.outputTimestampType memastikan compatibility dengan Redshift Spectrum dan services lainnya. Ini fix masalah di source. Opsi B (cast di query) tidak bisa correctly interpret INT96 di Spectrum. Opsi C (catalog metadata) tidak mengubah physical file format. Opsi D (UDF) workaround yang fragile.
4
A data engineer needs to convert a 500 GB CSV dataset to Parquet using AWS Glue. The target Parquet files should be between 128 MB and 256 MB each for optimal query performance. How should the output file size be controlled?
  • A. Use the Glue DynamicFrame's repartition() or coalesce() before writing, calculating the number of partitions based on target file size
  • B. Set maxRecordsPerFile in the write options to control records per file
  • C. The file size is automatically optimized by Glue
  • D. Set the S3 multipart upload size to 256 MB with partition-level ordering and dedicated throughput
Jawaban Benar: A
File count = number of Spark partitions. Dengan repartition(N), Anda bisa mengontrol berapa banyak output files. Jika 500 GB CSV menjadi ~100 GB Parquet (compression), dan target 128-256 MB per file, maka N = 100GB/200MB ≈ 500 partitions. coalesce() juga bisa mengurangi partisi tanpa shuffle. Opsi B (maxRecordsPerFile) adalah Spark option yang valid tapi kurang presisi untuk size control. Opsi C — Glue tidak otomatis optimize file sizes ke target tertentu. Opsi D (S3 multipart) tidak mengontrol logical file size.

A company receives data from IoT devices in Apache Avro format with embedded schemas. A downstream analytics team needs the data in Parquet format in S3. The Avro schema evolves frequently (new fields are added). Which approach handles schema evolution during format conversion?
  • A. Use AWS Glue ETL with schema evolution enabled — Glue reads Avro schemas automatically and can merge schemas when writing to Parquet
  • B. Manually update the target Parquet schema definition each time the Avro schema changes
  • C. Reject files with new fields until the pipeline is updated and can merge schemas when writing to Parquet
  • D. Convert to JSON first as an intermediate format
Jawaban Benar: A
Glue membaca Avro files dengan embedded schemas otomatis. Dengan schema evolution handling (misalnya mergeSchema option saat write Parquet), new fields ditambahkan ke output schema tanpa breaking existing data. Existing records mendapat NULL untuk new fields. Opsi B (manual update) tidak scalable saat schema berubah sering. Opsi C (reject) menyebabkan data loss. Opsi D (intermediate JSON) menambah unnecessary step dan kehilangan type information.
6
A data engineer needs to choose between Snappy and GZIP compression for Parquet files in a data lake. The data is primarily read by Amazon Athena and Amazon Redshift Spectrum. Queries are latency-sensitive dashboards. Which compression is MORE appropriate and why?
  • A. Snappy — because it provides faster decompression speed which reduces query latency, despite slightly larger file sizes compared to GZIP
  • B. GZIP — because it produces smaller files which reduce Athena scan costs
  • C. No compression — for fastest read performance
  • D. LZO — because it is splittable unlike Snappy configured for optimal performance and minimal operational overhead
Jawaban Benar: A
Untuk latency-sensitive queries (dashboards), decompression speed lebih penting dari compression ratio. Snappy decompresses ~2-3x faster dari GZIP. Dalam Parquet, compression diterapkan per column chunk sehingga splittability bukan issue. Trade-off: file ~30% larger tapi query 2-3x faster decompression. Opsi B (GZIP) smaller files tapi slower decompression menambah query latency. Opsi C (no compression) file terlalu besar — more I/O time dari S3. Opsi D (LZO) — di Parquet semua compression splittable per row group.

A data engineer needs to convert nested JSON data (with arrays and nested objects) to a flat Parquet structure for analytical queries. The JSON has 5 levels of nesting. Which AWS Glue transform handles this flattening?
  • A. Use the Relationalize transform in Glue DynamicFrames to flatten nested structures into separate flat tables with foreign key relationships
  • B. Use standard Spark explode() and select() functions manually for each nested level
  • C. Glue automatically flattens nested JSON when writing to Parquet
  • D. Use AWS Glue DataBrew to flatten before the ETL job with foreign key relationships
Jawaban Benar: A
Glue DynamicFrame Relationalize transform secara otomatis flatten nested structures (arrays dan structs) menjadi separate flat DynamicFrames linked by auto-generated keys. Ini menangani multiple levels of nesting secara rekursif. Sangat powerful untuk complex nested JSON. Opsi B (manual explode) bekerja tapi membutuhkan code per nested level — tedious untuk 5 levels. Opsi C — Glue tidak auto-flatten, Parquet mendukung nested types. Opsi D (DataBrew) valid tapi Relationalize lebih direct di ETL pipeline.
8
A company uses Amazon Redshift and needs to export large query results to S3 in Parquet format for sharing with external partners. Which Redshift feature performs this export most efficiently?
  • A. Use the UNLOAD command with FORMAT PARQUET option to export query results directly to S3 in Parquet format
  • B. Use UNLOAD to export as CSV, then run a Glue job to convert to Parquet
  • C. Use a Python script with psycopg2 to fetch results and write Parquet using PyArrow
  • D. Create an external table in Redshift Spectrum and write to it with FORMAT PARQUET option
Jawaban Benar: A
Redshift UNLOAD command mendukung FORMAT AS PARQUET secara native. Data ditulis langsung ke S3 dalam Parquet format dengan columnar storage dan compression. Ini paling efisien karena Redshift melakukan conversion internally tanpa data transfer overhead. Opsi B (CSV + Glue) menambah step dan biaya Glue job. Opsi C (Python script) sangat lambat untuk large datasets dan bottleneck di single connection. Opsi D — Redshift Spectrum external tables are read-only, tidak bisa INSERT INTO.

A data lake stores historical data in ORC format (legacy from a previous Hive-based system). The company is migrating to an architecture that primarily uses Athena and Redshift Spectrum. The team wants to standardize on Parquet. What should they consider about ORC vs Parquet for this migration?
  • A. Both Athena and Redshift Spectrum support ORC natively, so conversion to Parquet is optional; however, Parquet has broader ecosystem support and is the AWS recommended format for new workloads
  • B. ORC must be converted to Parquet immediately because Athena cannot read ORC
  • C. Parquet and ORC are identical formats with different names for new workloads
  • D. ORC is always superior to Parquet for analytical queries
Jawaban Benar: A
Athena dan Redshift Spectrum keduanya mendukung ORC secara native. Migration ke Parquet tidak wajib untuk fungsionalitas. Namun, Parquet memiliki broader ecosystem support (Spark, pandas, Arrow, ML frameworks), lebih baik untuk nested data, dan umumnya direkomendasikan AWS untuk new workloads. Opsi B salah — Athena reads ORC. Opsi C salah — mereka berbeda (ORC dari Hive ecosystem, Parquet dari Hadoop/Spark). Opsi D over-generalization — keduanya memiliki trade-offs.

A data engineer needs to convert CSV files that contain columns with mixed data types (some rows have integers, others have strings in the same column) to Parquet. Parquet requires strongly-typed columns. What issue arises and how should it be resolved?
  • A. Use AWS Glue's ResolveChoice transform to handle ambiguous types by casting to a common type (e.g., cast to string) or creating separate columns for each detected type
  • B. Parquet will automatically handle mixed types using variant type
  • C. Remove rows with incorrect types before conversion for each detected type
  • D. Use CSV format permanently since it handles mixed types
Jawaban Benar: A
Glue DynamicFrames mendeteksi mixed types dan membuat ChoiceType. ResolveChoice transform menyediakan strategies: cast (convert semua ke satu type), make_cols (buat kolom terpisah per type), make_struct (nested structure), atau project (keep specific type). Ini menyelesaikan type ambiguity sebelum write ke Parquet. Opsi B — Parquet standard tidak memiliki variant type (beberapa extensions ada tapi non-standard). Opsi C menyebabkan data loss. Opsi D mengorbankan query performance.
