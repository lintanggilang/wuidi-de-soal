A retail company stores clickstream data in S3 partitioned by year/month/day/hour (s3://clickstream/year=2024/month=06/day=15/hour=08/). New hourly partitions are created automatically by a Kinesis Firehose delivery stream. Analysts using Athena report that queries for the most recent hours return zero results, even though data files exist in S3. The Glue Data Catalog table was initially created by a crawler that runs weekly. What is the FASTEST way to make newly created partitions queryable in Athena without waiting for the next crawler run?
  • A. Delete the existing Glue table and re-run the crawler to rebuild the entire table definition with all current partitions with real-time processing and low-latency data delivery, handling the described workload reliably at scale and meeting the latency and throughput goals of the design and providing exactly-once processing semantics
  • B. Manually run the Glue crawler on-demand via the AWS Console to trigger an immediate crawl of the clickstream prefix, integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design
  • C. Run MSCK REPAIR TABLE clickstream_table in Athena. This command scans the S3 location for Hive-style partition directories that exist in S3 but are not registered in the Glue Data Catalog, then adds them as new partitions. It discovers all missing year/month/day/hour combinations in a single operation
  • D. Use ALTER TABLE ADD PARTITION for each specific new hourly partition, specifying the exact partition values and S3 location, meeting the latency and throughput goals of the design and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort
Correct Answer: C
MSCK REPAIR TABLE is the fastest single-command solution for synchronizing Hive-style partitions: (1) it scans the table's S3 location for subdirectories matching the key=value partition pattern; (2) it compares discovered partitions against the catalog and adds missing ones; (3) it requires no configuration — just execute the SQL statement in Athena; (4) for Hive-style naming (year=XXXX/month=XX/...), it automatically extracts partition values from directory names. This is ideal when multiple partitions accumulate between crawler runs. Option B — running the crawler on-demand works but takes significantly longer (minutes to start, then crawl time) compared to MSCK REPAIR (seconds to minutes for the SQL command). Option C — ALTER TABLE ADD PARTITION is precise but requires knowing exact partition values and S3 paths for each new partition; for 24 hourly partitions added daily, this is impractical without automation. Option D — deleting and recreating the table is destructive and unnecessary; it risks losing table properties, permissions, and configuration that were set post-creation.

Option C — changing partition granularity requires rewriting all existing data and may not meet query requirements (device-level filtering). Option D — event-driven registration solves sync latency but not query planning latency; 500K partitions in the catalog still cause slow GetPartitions API calls during query planning.

The team corrected this by moving files to the correct S3 paths and deleting the incorrect partition folders. However, the Glue Data Catalog still shows the old (now-empty) partition entries. Athena queries on the old partition date return zero rows but don't fail. How should the team remove these orphaned partition entries from the catalog?
  • A. Use the Glue API BatchDeletePartition to remove the specific orphaned partition entries from the catalog. Provide the table name, database name, and the list of partition values (trade_date='2024-03-14') to delete. This removes the catalog metadata without affecting any S3 data. Alternatively, run ALTER TABLE DROP PARTITION (trade_date='2024-03-14') in Athena to achieve the same result
  • B. Run MSCK REPAIR TABLE to re-synchronize — it will automatically detect and remove partitions whose S3 paths no longer exist with native S3 integration and optimized data transfer, satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline and meeting the latency and throughput goals of the design
  • C. Run the Glue crawler with schema update policy set to "Update all" — the crawler will remove partitions pointing to empty S3 locations, handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and keeping steady-state operating costs low
  • D. Delete the entire Glue table and re-create it using a new crawler run that will only discover partitions with actual data, handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and minimizing end-to-end processing latency
Correct Answer: A
BatchDeletePartition (API) or ALTER TABLE DROP PARTITION (SQL) directly removes specific orphaned catalog entries: (1) these are the only methods that explicitly DELETE partition metadata from the catalog; (2) they're surgical — only the specified partitions are removed; (3) no S3 data is affected (only metadata); (4) ALTER TABLE DROP PARTITION in Athena is the SQL equivalent accessible without code. Option B — MSCK REPAIR TABLE only ADDS missing partitions; it does NOT remove partitions whose S3 paths are empty or deleted. This is a critical distinction: MSCK REPAIR is additive-only. The orphaned entries remain after MSCK REPAIR runs. Option C — Glue crawlers with "Update all" policy update schema and add new partitions, but the default crawler behavior does NOT remove partitions for deleted S3 paths. The crawler's "Delete objects from the catalog that are no longer in the data store" deletion policy must be explicitly enabled — and even then, it requires careful configuration to avoid accidentally removing valid partitions during transient S3 issues. Option D — deleting and recreating the table is unnecessarily destructive, losing table properties, permissions, column comments, and requiring downstream query updates if table properties change.

  • B.   • D. Configure S3 Event Notifications to trigger a Lambda function on ObjectCreated events. The Lambda function extracts partition values from the S3 key path, then calls the Glue API CreatePartition (or BatchCreatePartition for efficiency) to register the new partition in the catalog. Correct Answer: D
S3 event-driven Lambda with CreatePartition API provides the lowest latency for partition registration: (1) S3 Event Notifications fire within seconds of object creation; (2) Lambda extracts partition values from the S3 key (parsing year=, month=, day=, hour=, minute= from the path); (3) CreatePartition API call registers the partition instantly; (4) using BatchCreatePartition and deduplication logic (check if partition already exists before creating) handles multiple files per partition; (5) total latency from file landing to queryability is typically under 10 seconds. Option B — MSCK REPAIR every minute is wasteful: each execution performs a full S3 LIST of all directories (expensive at scale), consumes Athena query execution resources, and has a minimum overhead of 5-15 seconds per run even when no new partitions exist. Option C — partition projection is excellent but requires predictable, regular partition paths. It works here technically, but if any partition has no data (a 5-minute window with no events), queries targeting that partition would attempt to read non-existent S3 paths, resulting in potential errors or empty results that are harder to distinguish from "no data received." For streaming with consistent arrival, it's viable but doesn't provide the explicit registration guarantee. Option D — Glue crawlers have a minimum startup latency of 30-60 seconds and cannot achieve sub-minute registration; they're designed for batch discovery, not real-time.

When the team runs MSCK REPAIR TABLE, it returns "zero partitions added" because the directories don't follow key=value naming convention. The table definition in the Glue Catalog correctly defines year, month, and day as partition columns. How should the team register these non-Hive-style partitions?
  • A. Use a Glue crawler configured with a custom classifier that understands the numeric directory structure as partition values with native S3 integration and optimized data transfer
  • B. Use ALTER TABLE ADD PARTITION with explicit LOCATION for each partition: ALTER TABLE sales ADD PARTITION (year='2024', month='06', day='15') LOCATION 's3://sales/2024/06/15/'. This maps arbitrary S3 paths to partition values regardless of directory naming convention. For bulk registration, use the Glue BatchCreatePartition API with StorageDescriptor specifying each partition's S3 location
  • C. Configure partition projection with a custom S3 path template: storage.location.template = 's3://sales/${year}/${month}/${day}/' to map partition values to the non-Hive paths
  • D. Rename all S3 directories to follow Hive-style naming (year=2024/month=06/day=15/) so MSCK REPAIR can detect them, handling the described workload reliably at scale
Correct Answer: C
Partition projection with a custom storage.location.template is the optimal long-term solution for non-Hive-style paths: (1) the template s3://sales/${year}/${month}/${day}/ tells Athena exactly how to construct S3 paths from partition values; (2) no partition entries need to be stored in the catalog — Athena computes paths mathematically; (3) new partitions (new days) are automatically queryable without ANY registration step; (4) it handles the non-standard directory naming perfectly because the template is fully customizable; (5) no ongoing maintenance — no crawlers, no MSCK REPAIR, no Lambda functions needed. Option B — renaming S3 directories means rewriting all S3 keys (S3 doesn't support rename — it's copy + delete), which for large datasets is extremely time-consuming and expensive; it also breaks any existing references to these paths. Option D — Glue crawlers can handle numeric paths (they recognize pattern-based partitions), but this requires crawler scheduling and maintenance; partition projection eliminates the need for any external sync mechanism.

A data engineering team configures partition projection on an Athena table with the following properties: projection.enabled=true, projection.date.type=date, projection.date.range=2020-01-01,NOW, projection.date.format=yyyy-MM-dd. When analysts query SELECT * FROM events WHERE date = '2025-01-15', Athena returns zero rows even though data exists at s3://events/date=2025-01-15/. The same query works correctly when partition projection is disabled and the partition is registered in the catalog. What is the MOST likely cause?
  • A. The projection.date.range uses "NOW" which resolves to the current UTC date; if the query runs before midnight UTC, dates in tomorrow's timezone may not be included
  • B. The storage.location.template table property is missing or incorrect. Without this property, Athena doesn't know how to construct the S3 path for projected partitions. The team must add: storage.location.template = 's3://events/date=${date}/' as a table property so Athena can map the projected date value to the correct S3 location
  • C. Partition projection requires projection.date.interval and projection.date.interval.unit properties to define how dates are generated; without them, Athena cannot enumerate valid dates
  • D. The date column must be defined as a string type in the table schema for partition projection to work; if defined as date type, the format comparison fails
Correct Answer: C
For date-type partition projection, the interval and interval.unit properties are REQUIRED: (1) projection.date.interval defines the step between consecutive partition values (e.g., 1); (2) projection.date.interval.unit defines the time unit (DAYS, HOURS, MINUTES, etc.); (3) without these, Athena cannot generate the series of valid date values within the specified range; (4) the correct configuration requires: projection.date.interval=1 and projection.date.interval.unit=DAYS for daily partitions. Without these properties, Athena cannot determine which date values are valid within the 2020-01-01 to NOW range, so it cannot construct paths to read. Option A — storage.location.template is optional when the table's base Location combined with Hive-style partition naming (date=${date}/) matches the actual S3 structure. If the table Location is 's3://events/' and paths follow Hive-style naming, Athena constructs paths correctly without an explicit template. Option B — "NOW" resolves correctly and 2025-01-15 is within the range 2020-01-01 to NOW (assuming current date is after 2025-01-15); timezone issues might cause 1-day edge cases but wouldn't cause a failure for a date well within range. Option D — partition columns in Athena for partition projection work as string type by default; the projection.date.format handles string-to-date conversion internally regardless of the declared column type.

The Glue Data Catalog table-level schema includes customer_segment, but the individual partition schemas in the catalog still reflect their original schemas. When Athena queries old partitions, it returns NULL for customer_segment. A team member suggests running a crawler to "fix" this. Will re-crawling resolve the partition-level schema drift?

  • B. Re-crawling will NOT fix partition-level schema drift in this case. The crawler updates the TABLE-level schema (which already includes customer_segment), but individual partition schemas in the Glue Catalog reflect the actual data in each partition's files. This is working as designed — Athena returns NULL for missing columns, which is the correct schema evolution behavior for Parquet
  • C. What must be done to include the new region in partition projection?
  • A. Update the table property projection.region.values to include the new region: 'us-east-1,us-west-2,eu-west-1,ap-southeast-1'. With enum-type projection, Athena only recognizes values explicitly listed in the projection configuration. Use ALTER TABLE SET TBLPROPERTIES in Athena to update this property — the change takes effect immediately for subsequent queries
  • B.   • C. Correct Answer: A
Enum-type partition projection requires explicit enumeration of all valid values: (1) the projection.region.values property defines the complete set of valid region values; (2) Athena ONLY generates paths for values listed in this property; (3) "ap-southeast-1" is not in the current list, so Athena never constructs paths for it, hence zero results; (4) updating via ALTER TABLE SET TBLPROPERTIES ('projection.region.values'='us-east-1,us-west-2,eu-west-1,ap-southeast-1') immediately includes the new region; (5) this is a metadata-only change — no data movement or crawler run needed. This is the trade-off of enum-type projection: you get fast, deterministic partition resolution but must manually maintain the values list. Option B — when partition projection is enabled, Athena ignores catalog-based partitions entirely; MSCK REPAIR TABLE has no effect on projected tables because the catalog partitions aren't consulted. Option C — partition projection never scans S3 to discover values; it uses only the defined configuration. Disabling/re-enabling doesn't add auto-discovery. Option D — "injected" type requires the query to always include the partition column in the WHERE clause with specific values, and those values are passed directly to the path template. It doesn't auto-discover values from S3 either, and it removes the ability to query across all regions without explicitly listing them in WHERE.
