A data engineer creates a Lambda function that needs to read from a Kinesis Data Stream, write processed records to DynamoDB, and send notifications to SNS. When configuring the Lambda execution role, which set of permissions follows the principle of least privilege?
  • A. Create a custom policy with kinesis:*, dynamodb:*, and sns:* on resource "*" and sns:Publish on the specific topic ARN, removing the need to provision or patch any infrastructure
  • B. Create a custom policy allowing kinesis:GetRecords, kinesis:GetShardIterator, kinesis:DescribeStream, kinesis:ListShards on the specific stream ARN; dynamodb:PutItem, dynamodb:BatchWriteItem on the specific table ARN; and sns:Publish on the specific topic ARN
  • C. Attach the PowerUserAccess managed policy which covers all services except IAM, meeting the latency and throughput goals of the design and satisfying all of the stated requirements with minimal effort
  • D. Attach the AWS managed policy AmazonKinesisFullAccess, AmazonDynamoDBFullAccess, and AmazonSNSFullAccess, removing the need to provision or patch any infrastructure and running as a fully managed service with minimal operational overhead
Correct Answer: B
Least privilege berarti provides only permissions that correct-correct is required on resource that specific. Custom policy with: (1) Kinesis read permissions (GetRecords, GetShardIterator, DescribeStream, ListShards) — only actions for consume data. (2) DynamoDB write permissions (PutItem, BatchWriteItem) — only actions for writes. (3) SNS publish permission — only action for sends notifikasi. All limited on ARN specific.

Option A: INCORRECT. Terlalu broad — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: CORRECT.
Option C: INCORRECT. Provides almost all permissions.
Option D: INCORRECT. Provides permissions berlebihan (including Delete, Create).

A data engineer uses AWS CloudFormation to deploy a data pipeline stack that includes a Glue job, an S3 bucket, and a Lambda function. The CloudFormation stack creation fails with "AccessDenied" when trying to create the Glue job. The engineer's IAM user has full CloudFormation permissions. What is the MOST likely cause and solution?
  • A. The engineer's IAM user needs direct glue:CreateJob permission in addition to CloudFormation permissions, integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort
  • B. The Glue job definition in the template has a syntax error causing CloudFormation to report it as an access issue, satisfying all of the stated requirements with minimal effort
  • C. CloudFormation stacks can only be created from the AWS Management Console, not from the CLI with permissions and Lambda function, satisfying all of the stated requirements with minimal effort
  • D. CloudFormation needs a service role with permissions to create the Glue job, S3 bucket, and Lambda function. The engineer should create and assign a CloudFormation service role with appropriate permissions.
Correct Answer: D
CloudFormation service role is a best practice that separates "who can create stacks" from "what resources stacks can create." Without service role, CloudFormation uses permissions from calling user — if user not has glue:CreateJob, stack creation fails. Solusinya: buat IAM role that dipercaya by cloudformation.amazonaws.com with permissions for all resources that will is created, lalu assign role the said to stack.

Option A: INCORRECT. Can works but not best practice — provides user permission directly to all services less secure.
Option B: INCORRECT. Salah — syntax error produces error different.
Option C: INCORRECT. Salah — CloudFormation can is called from CLI, SDK, and Console — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: CORRECT.

A data engineer needs to allow a third-party SaaS application to write data to an S3 bucket in their AWS account. The SaaS provider gives their AWS Account ID and an External ID. Which IAM role configuration securely enables this access?
  • A. Create a role with trust policy allowing the SaaS provider's account as Principal, include an sts:ExternalId condition matching the provided External ID, and attach a policy allowing s3:PutObject on the target bucket
  • B. Create a role with trust policy allowing "*" as Principal and use the External ID in the permission policy's Condition block, protecting the data both in transit and at rest
  • C. Create an IAM user with access keys and share the credentials with the SaaS provider and attach a policy allowing s3:PutObject on the target bucket, integrating natively with the rest of the pipeline
  • D. Make the S3 bucket public and restrict access using bucket policy conditions based on the source IP of the SaaS provider, satisfying all of the stated requirements with minimal effort
Correct Answer: A
For third-party cross-account access, best practice is: (1) Trust policy with Principal: {"AWS": "arn:aws:iam::SAAS_ACCOUNT_ID:root"}. (2) Condition: {"StringEquals": {"sts:ExternalId": "provided-external-id"}}. External ID melindungi from "confused deputy" attacks — without External ID that correct, even if seseorang mengetahui role ARN, mereka cannot assume role. (3) Permission policy only provides s3:PutObject on bucket specific.

Option A: CORRECT.
Option B: INCORRECT. Enables who saja mencoba assume role.
Option C: INCORRECT. Long-term credentials not secure for third-party — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Very not secure.

A data engineer needs to configure an API Gateway REST API that triggers a Lambda function for a data ingestion endpoint. The API should accept requests only from authenticated IAM users and roles. Which authorization mechanism should be configured on the API Gateway method?
  • A. Set the authorization type to AWS_IAM on the API method. Callers must sign requests with SigV4 credentials of an IAM entity that has execute-api:Invoke permission on the API resource.
  • B. Create a Lambda authorizer that validates IAM access keys in the request headers, protecting the data both in transit and at rest and enforcing encryption and fine-grained access control
  • C. Create a Cognito User Pool and configure it as the authorizer for the API method with SigV4 credentials of an IAM entity that has execute-api:Invoke permission on the API resource
  • D. Set the authorization type to NONE and use a WAF rule to filter requests by IAM source, meeting the latency and throughput goals of the design and providing exactly-once processing semantics
Correct Answer: A
AWS_IAM authorization on API Gateway requires all request in-sign uses Signature Version 4 (SigV4) with credentials IAM entity (user or role). API Gateway memverifikasi signature and memeriksa whether caller has execute-api:Invoke permission on API resource ARN. Ini is mekanisme native and most secure for IAM-based authentication.

Option A: CORRECT.
Option B: INCORRECT. Adds complexity that does not need if IAM auth already quite.
Option C: INCORRECT. Dimaksudkan for end-user authentication, not IAM-based service-to-service — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Not secure — WAF cannot validates IAM identity.

A data engineer working from the AWS CLI needs to access resources in three different AWS accounts (Development, Staging, Production) for data pipeline management. Each account has a specific IAM role for the data engineering team. Which CLI configuration approach follows AWS best practices?
  • A. Create IAM users with access keys in each account and configure three named profiles with static credentials, handling the described workload reliably at scale
  • B. Store access keys for all accounts in environment variables and switch between them using shell scripts with role_arn, satisfying strict compliance and audit requirements
  • C. Configure named profiles in ~/.aws/config with role_arn and source_profile settings, allowing the CLI to automatically assume roles in each account using temporary credentials
  • D. Use a single set of administrator credentials that has cross-account access to all three accounts, integrating natively with the rest of the pipeline
Correct Answer: C
AWS CLI named profiles with role_arn and source_profile is best practice for multi-account access. Konfigurasi: [profile dev] role_arn = arn:aws:iam::DEV_ACCOUNT:role/DataEngineerRole, source_profile = default. CLI automatically calls sts:AssumeRole and uses temporary credentials (expire setelah 1 hours). Ini secure because uses temporary credentials, audit-friendly (AssumeRole events tercatat in CloudTrail), and not stores long-term credentials per account.

Option A: INCORRECT. Uses long-term credentials.
Option B: INCORRECT. Rawan error and security risk — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: CORRECT.
Option D: INCORRECT. Melanggar least privilege.

A data engineer creates a Glue job that needs to write to an S3 bucket and also needs to start another Glue job as part of a pipeline. The engineer creates a role named "GlueETLRole" and attaches it to the Glue job. However, when the engineer tries to assign this role to the Glue job, they receive an error: "User is not authorized to perform iam:PassRole." What is required to resolve this?
  • A. The engineer needs full IAM administrator access to assign any role to any service, applying schema conversion and enrichment inline and enforcing encryption and fine-grained access control
  • B. The GlueETLRole needs an iam:PassRole permission in its own policy to allow itself to be passed, transforming records into the required target format
  • C. The GlueETLRole trust policy must include the engineer's IAM user ARN as a trusted principal with the resource set and a condition restricting it to the glue
  • D. The engineer's IAM user/role needs an iam:PassRole permission with the resource set to the GlueETLRole ARN and a condition restricting it to the glue.amazonaws.com service
Correct Answer: D
iam:PassRole is permission that mengontrol who that boleh meng-assign (pass) IAM role to AWS service. Ini is security control that prevents privilege escalation — without batasan this, user can creates service with admin role and mendapat permissions more from that mereka miliki. Engineer requires policy: {"Effect": "Allow", "Action": "iam:PassRole", "Resource": "arn:aws:iam::ACCOUNT:role/GlueETLRole", "Condition": {"StringEquals": {"iam:PassedToService": "glue.amazonaws.com"}}}.

Option A: INCORRECT. Salah — full admin berlebihan.
Option B: INCORRECT. Salah — role does not need permission for in-pass.
Option C: INCORRECT. Salah — trust policy mengontrol who that boleh assume role, not who that boleh pass role — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: CORRECT.

A data engineer deploys an EMR cluster for a data processing pipeline. The cluster needs: (1) Access to S3 for input/output data, (2) Access to Glue Data Catalog as metastore, (3) Ability to publish CloudWatch metrics. Which IAM configuration correctly provides these permissions to the EMR cluster's EC2 instances?
  • A. Create an IAM user with the required permissions and pass the access keys to EMR through cluster configuration, satisfying strict compliance and audit requirements
  • B. Attach the permissions directly to the EMR service role (EMR_DefaultRole) with the required permissions and specify the instance profile when launching the EMR cluster
  • C. Create an IAM role with the required permissions, create an instance profile containing that role, and specify the instance profile when launching the EMR cluster
  • D. Create an IAM group with the required permissions and add the EMR cluster to the group, enforcing encryption and fine-grained access control and minimizing end-to-end processing latency
Correct Answer: C
EMR EC2 instances gets permissions through instance profile. Instance profile contains IAM role that mendefinisikan permissions for application that runs in cluster (Spark, Hive, etc.). Role this requires: s3:GetObject/PutObject for data access, glue:GetDatabase/GetTable for Catalog access, and cloudwatch:PutMetricData for metrics. In a default, AWS creates EMR_EC2_DefaultRole for this, but custom instance profile better for least privilege.

Option A: INCORRECT. Kurang secure, credentials can bocor.
Option B: INCORRECT. EMR service role for cluster management, not for EC2 instances — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: CORRECT.
Option D: INCORRECT. IAM groups only for IAM users, not services.

A data engineer creates an AWS Glue job that needs to assume a cross-account role to read data from Account B's S3 bucket. The Glue job uses a service role (GlueServiceRole) in Account A. The engineer writes code in the Glue job to call sts:AssumeRole for the cross-account role. However, the AssumeRole call fails. The cross-account role's trust policy allows Account A. What permission is MOST likely missing?
  • A. Account A needs to be part of the same AWS Organization as Account B with the cross-account role ARN as the resource
  • B. The cross-account role in Account B needs to trust the GlueServiceRole ARN specifically, not just Account
  • C. The Glue job needs a VPC endpoint to reach the STS service endpoint
  • D. The GlueServiceRole in Account A needs sts:AssumeRole permission with the cross-account role ARN as the resource
Correct Answer: D
For succeeds calls sts:AssumeRole, calling principal (in this case GlueServiceRole) requires permission sts:AssumeRole on target role ARN in IAM policy-nya. Ini often terlewat — engineer adds trust policy in Account B but lupa adds permission in Account A. Diperlukan: {"Effect": "Allow", "Action": "sts:AssumeRole", "Resource": "arn:aws:iam::ACCOUNT_B:role/CrossAccountRole"} on GlueServiceRole.

Option A: INCORRECT. AWS Organizations not is required for cross-account role assumption.
Option B: INCORRECT. If trust policy already allows Account A root, all principals in Account A that has sts:AssumeRole permission can assume.
Option C: INCORRECT. STS has regional endpoints that accessible in a default.
Option D: CORRECT.

A data engineer designs a serverless data pipeline where API Gateway receives data, triggers a Lambda function, which then writes to DynamoDB. The Lambda function also needs to invoke another Lambda function for data enrichment. Which trust policy should be on the Lambda execution role?
  • A. {"Version": "2012-10-17", "Statement": [{"Effect": "Allow", "Principal": {"Service": "lambda.amazonaws.com"}, "Action": "sts:AssumeRole"}]}
  • B. {"Version": "2012-10-17", "Statement": [{"Effect": "Allow", "Principal": {"AWS": "*"}, "Action": "sts:AssumeRole"}]}
  • C. {"Version": "2012-10-17", "Statement": [{"Effect": "Allow", "Principal": {"Service": ["lambda.amazonaws.com", "apigateway.amazonaws.com"]}, "Action": "sts:AssumeRole"}]}
  • D. {"Version": "2012-10-17", "Statement": [{"Effect": "Allow", "Principal": {"Service": "dynamodb.amazonaws.com"}, "Action": "sts:AssumeRole"}]}
Correct Answer: A
Lambda execution role only needs trust policy for lambda.amazonaws.com. Trust policy determines SIAPA that boleh assume role — in this case, Lambda service that will assume role saat runs function. API Gateway does not need ada in trust policy because API Gateway has role separate (API Gateway execution role) or uses Lambda proxy integration that quite with Lambda resource-based policy. DynamoDB and Lambda invocation is handled by permission policy, not trust policy.

Option A: CORRECT.
Option B: INCORRECT. Very not secure.
Option C: INCORRECT. Salah — API Gateway does not need assume Lambda's role.
Option D: INCORRECT. Salah — DynamoDB not assume role.

A data engineer uses AWS CloudFormation with a service role to deploy infrastructure. The CloudFormation template creates a Lambda function and assigns it an execution role. During stack creation, the error "User: arn:aws:iam::123456789012:role/CFNServiceRole is not authorized to perform: iam:PassRole on resource: arn:aws:iam::123456789012:role/LambdaExecRole" occurs. What should the engineer add to the CloudFormation service role?
  • A. Add sts:AssumeRole permission for the LambdaExecRole ARN with a condition that restricts iam:PassedToService
  • B. Add iam:PassRole permission for the LambdaExecRole ARN with a condition that restricts iam:PassedToService to lambda.amazonaws.com
  • C. Add iam:CreateRole and iam:AttachRolePolicy permissions to allow CloudFormation to create the role
  • D. Add administrator access to the CloudFormation service role to avoid permission issues
Correct Answer: B
CloudFormation service role requires iam:PassRole permission when template meng-assign role to service (for example assigning LambdaExecRole to Lambda function). Permission that is required: {"Effect": "Allow", "Action": "iam:PassRole", "Resource": "arn:aws:iam::123456789012:role/LambdaExecRole", "Condition": {"StringEquals": {"iam:PassedToService": "lambda.amazonaws.com"}}}. Condition ensures role only can in-pass to Lambda service.

Option A: INCORRECT. CloudFormation does not need assume LambdaExecRole — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: CORRECT.
Option C: INCORRECT. Error not about creates role, but meng-assign role to Lambda.
Option D: INCORRECT. Melanggar least privilege and merupakan security risk.
