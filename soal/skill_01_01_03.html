A data engineer is configuring an AWS Glue ETL job to process 2 TB of raw CSV data from Amazon S3. The job keeps failing due to out-of-memory errors. The data has significant skew with some partitions being 100x larger than others. Which configuration changes will MOST effectively resolve this issue?
  • A. Enable Glue Auto Scaling, set --conf spark.sql.shuffle.partitions to a higher value, and use groupFiles option
  • B. Switch to Glue version 4.0 and enable serverless execution, validating and cleansing each record before delivery
  • C. Enable Glue job bookmarks and increase the number of DPUs and use groupFiles option
  • D. Use a Glue Python Shell job instead of Spark ETL, handling the described workload reliably at scale
Correct Answer: A
Auto Scaling enables Glue adjusts worker in a dynamic. Increases spark.sql.shuffle.partitions distributes data skew to more partition. groupFiles combines files small becomes group that more efficient so that reduces memory overhead.

Option A: CORRECT.
Option B: INCORRECT. Not directly resolves OOM.
Option C: INCORRECT. Only adds resources but not resolves data skew — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option D: INCORRECT. Not suitable for 2 TB data because single-node processing.
