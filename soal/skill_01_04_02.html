Skill 1.4.2: Configure Lambda Functions to Meet Concurrency and Performance Needs

Lambda memory, timeout, concurrency settings, provisioned concurrency, and performance tuning for data workloads

1
A Lambda function processes batches of records from a Kinesis stream. During peak hours, the function's duration increases from 5 seconds to 14 seconds (close to the 15-second timeout configured). CloudWatch metrics show memory utilization at 95% of allocated 512 MB. What configuration change MOST likely resolves both issues?
  • A. Increase memory allocation to 1024 MB or higher — Lambda proportionally allocates more CPU and network bandwidth with memory, reducing duration. Increase timeout as a safety margin
  • B. Decrease batch size in the event source mapping
  • C. Enable provisioned concurrency
  • D. Change the runtime from Python to Java for faster processing
Jawaban Benar: A
Lambda CPU allocation is proportional to memory. At 512 MB, Lambda gets ~1/3 vCPU. At 1769 MB, it gets 1 full vCPU. Increasing memory reduces duration (more CPU + more memory headroom) and reduces memory pressure (95% → ~50%). This often makes functions faster AND cheaper because shorter duration offsets per-ms cost increase. Opsi B (smaller batch) reduces throughput. Opsi C (provisioned concurrency) eliminates cold starts but doesn't fix resource constraints. Opsi D (Java) has longer cold starts and unclear performance benefit.
2
A data pipeline has a Lambda function that consumes from an SQS queue. The queue receives 50,000 messages per minute during peak. Each message takes 200ms to process. What is the minimum reserved concurrency needed to process all messages without queue buildup?
  • A. Approximately 167 concurrent executions (50,000 messages/minute ÷ 60 seconds × 0.2 seconds per message = 167)
  • B. 50,000 concurrent executions (one per message)
  • C. 10 concurrent executions with batch size of 10
  • D. 1,000 concurrent executions for safety margin
Jawaban Benar: A
Concurrency = (messages per second) × (processing time per message). 50,000/60 = 833 messages/second. If each takes 0.2s, needed concurrency = 833 × 0.2 = ~167. With batch size = 10 and batch processing: 833/10 = 83 invocations/second × 0.2s = ~17 concurrent (even less). The formula depends on whether processing is per-message or per-batch. For single message processing: ~167. Opsi B (50K) massively over-provisioned. Opsi C (10) insufficient. Opsi D (1000) over-provisioned but the math shows ~167 is minimum.
3
A data engineer has a Lambda function that writes to an RDS PostgreSQL database. Under high concurrency (500 simultaneous invocations), the database reaches its max_connections limit (100). How should the Lambda function be configured to prevent connection exhaustion?
  • A. Set reserved concurrency on the Lambda function to a value at or below the database's max_connections (e.g., 80), and use Amazon RDS Proxy for connection pooling
  • B. Increase Lambda timeout so connections are held longer
  • C. Increase RDS max_connections to 500
  • D. Remove the VPC configuration from the Lambda function
Jawaban Benar: A
Two complementary strategies: (1) Reserved concurrency limits Lambda to 80 concurrent executions, ensuring max 80 connections. (2) RDS Proxy pools and multiplexes connections — even if 80 Lambdas run, Proxy manages connection reuse efficiently. Together they prevent connection exhaustion. Opsi B (longer timeout) makes problem worse — connections held longer. Opsi C (500 connections) may impact RDS performance and memory. Opsi D (remove VPC) — Lambda still needs VPC to reach RDS in private subnet.
4
A Lambda function is configured as a Kinesis stream consumer with 10 shards. The function uses the default parallelization factor of 1. Processing each batch takes 10 seconds. What is the maximum throughput (batches processed per second) for this configuration?
  • A. 1 batch per shard per 10 seconds = 10 shards × (1/10 batch per second) = 1 batch per second total (sequential per shard)
  • B. 10 batches per second (one per shard concurrently)
  • C. 100 batches per second
  • D. Unlimited — Lambda auto-scales
Jawaban Benar: A
With ParallelizationFactor=1, each shard has exactly 1 concurrent Lambda invocation. Since each takes 10 seconds, each shard processes 1 batch every 10 seconds = 0.1 batches/sec/shard. With 10 shards processing concurrently: 10 × 0.1 = 1 batch/second total. To increase throughput: (1) increase ParallelizationFactor (up to 10), or (2) reduce processing time, or (3) add shards. Opsi B would be correct if each batch took 1 second. Opsi C/D incorrect — Kinesis-Lambda doesn't auto-scale beyond configured parallelism per shard.
5
A Lambda function in a data pipeline has 3-second cold starts due to loading a large ML model (200 MB) at initialization. The function is invoked every 5 minutes. Most invocations experience cold starts because the execution environment is recycled. Which configuration ELIMINATES cold starts?
  • A. Configure Provisioned Concurrency with a value of 1 to keep at least one warm execution environment always ready
  • B. Move the model loading from handler initialization to inside the handler function
  • C. Increase memory to 10 GB for faster model loading
  • D. Use a CloudWatch Events rule to ping the function every 4 minutes to keep it warm
Jawaban Benar: A
Provisioned Concurrency guarantees pre-initialized execution environments. Model is loaded during provisioning (not at invocation time). Every invocation hits a warm environment with zero cold start. Cost: you pay for provisioned environment 24/7 regardless of usage. Opsi B (model in handler) makes EVERY invocation load the model — worse than cold start. Opsi C (more memory) speeds up cold start but doesn't eliminate it. Opsi D (pinging) unreliable — Lambda may still recycle, and doesn't guarantee preventing cold starts.
6
A data engineer needs to process large files (up to 5 GB) in Lambda. The function needs to read the entire file, transform it, and write the output. Lambda has a deployment package limit and ephemeral storage limit. Which Lambda configuration supports this?
  • A. Configure Lambda ephemeral storage (/tmp) to 10 GB (maximum), stream the file from S3 to /tmp, process it, and stream output back to S3
  • B. Use Lambda's 512 MB default /tmp storage
  • C. Include the file in the Lambda deployment package
  • D. Mount an EFS volume and store the file there
Jawaban Benar: A
Lambda supports configurable ephemeral storage from 512 MB to 10,240 MB (10 GB). For a 5 GB file, allocating 10 GB /tmp provides sufficient space. Download from S3 to /tmp, process, upload result to S3. Ensure memory is sufficient for processing (up to 10 GB). Opsi B (512 MB default) insufficient for 5 GB file. Opsi C (deployment package) max 250 MB unzipped — can't include 5 GB file. Opsi D (EFS) works but adds VPC requirement and latency — /tmp is simpler for this use case.
7
A data pipeline has 5 Lambda functions, each with different concurrency patterns. Function A handles real-time data (needs guaranteed availability), Functions B-E handle batch processing. During peak, batch functions consume all available account concurrency (1000), throttling the real-time function. How should concurrency be managed?
  • A. Set reserved concurrency on Function A (e.g., 200) to guarantee its availability, and set reserved concurrency on batch functions to limit their maximum (e.g., 200 each for B-E)
  • B. Request account concurrency increase to 5000
  • C. Remove batch functions and use Glue instead
  • D. Set provisioned concurrency on Function A only
Jawaban Benar: A
Reserved concurrency serves two purposes: (1) For Function A — guarantees 200 execution slots always available, even if other functions consume the remaining 800. (2) For batch functions — caps each at 200, preventing any single function from consuming all account concurrency. Total: 200 (A) + 200×4 (B-E) = 1000 = full account allocation, properly divided. Opsi B (increase limit) doesn't prevent batch from starving real-time. Opsi D (provisioned concurrency) prevents cold starts but doesn't guarantee concurrent execution slots.
8
A Lambda function processes data from DynamoDB Streams. The function needs to initialize a database connection pool and load configuration from Parameter Store during cold start. This initialization takes 2 seconds. Which coding pattern minimizes the impact of initialization across invocations?
  • A. Place initialization code (connection pool, config loading) OUTSIDE the handler function at module level — this code runs only during cold start and is reused across subsequent warm invocations
  • B. Place all initialization inside the handler function to ensure fresh state every time
  • C. Use environment variables for all configuration to avoid Parameter Store calls
  • D. Create a new connection for each record processed
Jawaban Benar: A
Lambda execution model: code outside the handler (module/global scope) executes once during cold start (INIT phase). The execution environment persists between invocations. Connection pools and config loaded at INIT are reused in subsequent warm invocations — 2-second initialization only happens once per environment lifecycle. Opsi B (inside handler) pays 2-second init EVERY invocation — terrible performance. Opsi C (env vars) still need to be read; connection pool still needed. Opsi D (new connection per record) highest latency possible.
9
A data engineer's Lambda function receives events from SQS with a batch size of 10. The function processes each message independently. If message 7 out of 10 fails, what happens with the default configuration, and how should it be configured for partial batch failure handling?
  • A. Default: entire batch of 10 returns to the queue (all messages retry including successful ones). Fix: enable ReportBatchItemFailures in the event source mapping and return batchItemFailures with the messageId of only message 7
  • B. Default: only message 7 is retried. No configuration change needed
  • C. Default: all 10 messages are discarded. Configure DLQ for failed messages
  • D. Default: Lambda automatically splits the batch and retries only the failed half
Jawaban Benar: A
Without ReportBatchItemFailures, any exception from the Lambda handler causes the ENTIRE batch to return to the queue — 9 successful messages are reprocessed unnecessarily. With FunctionResponseTypes: ["ReportBatchItemFailures"], the function returns a response specifying which messageIds failed. Only those messages return to the queue. Processed messages are deleted. This prevents duplicate processing. Opsi B — not the default behavior. Opsi C — messages aren't discarded by default. Opsi D — batch splitting is for Kinesis (BisectBatchOnError), not SQS.
10
A data processing Lambda function runs in a VPC to access an RDS database. The function experiences 8-10 second cold starts due to VPC ENI attachment. The function is invoked irregularly (once every 10-30 minutes). What is the BEST solution to reduce cold start time?
  • A. Lambda uses Hyperplane ENIs (since 2019) which should not cause 8-10 second cold starts. Investigate if the delay is from loading large dependencies — optimize the deployment package size and use Lambda Layers for shared libraries
  • B. Remove the VPC configuration and use RDS Proxy's public endpoint
  • C. Configure provisioned concurrency to maintain warm environments
  • D. Increase the Lambda function's memory allocation
Jawaban Benar: C
Since 2019, Lambda VPC networking uses Hyperplane ENIs with negligible cold start impact (~1 second vs. previous 10+ seconds). If cold starts are still 8-10 seconds, the cause is likely large deployment packages, heavy initialization code, or both. However, for irregular invocations (10-30 min gaps) where cold starts ARE the problem, Provisioned Concurrency is the definitive solution — it eliminates cold starts entirely. Opsi A correctly identifies that VPC shouldn't cause 8-10s delay, but doesn't solve the cold start problem for the user. Opsi B changes architecture. Opsi D helps but doesn't eliminate cold starts.
