A company is building a product recommendation system that uses vector embeddings generated by Amazon Bedrock. They have 10 million product embeddings (1536 dimensions each) and need to find the 50 most similar products to a given query vector with sub-100ms latency. The dataset is updated daily with 50,000 new products. The team is evaluating which vector index type to use with Amazon Aurora PostgreSQL (pgvector extension). Which index configuration BEST balances query speed and recall accuracy?
  • A. HNSW (Hierarchical Navigable Small World) index with ef_construction=128 and m=16, providing approximate nearest neighbor search with 95%+ recall at sub-50ms latency by building a multi-layer proximity graph that enables logarithmic-time traversal through the vector space
  • B. IVF (Inverted File Index) with nlist=1000 and nprobe=50, partitioning vectors into 1000 Voronoi cells and searching only the 50 closest cells during query time
  • C. Exact brute-force search (sequential scan) without any index, computing cosine similarity against all 10 million vectors for guaranteed 100% recall
  • D. A B-tree index on a hash of the vector values for equality lookups on exact vector matches
Jawaban Benar: A
HNSW is the optimal choice for this scenario: (1) it provides the best recall-latency tradeoff among approximate nearest neighbor algorithms at 10M scale; (2) the multi-layer graph structure enables O(log n) query time with 95%+ recall at sub-50ms; (3) HNSW handles incremental inserts well (daily 50K additions are added to the graph without full rebuild); (4) ef_construction=128 builds high-quality graphs, and m=16 connections per node balances memory and search quality. Opsi B — IVF requires periodic retraining when data distribution shifts (daily additions may degrade cell boundaries), and at nprobe=50/nlist=1000 it searches 5% of data which may give lower recall than HNSW for the same latency. Opsi C — brute-force scan of 10M × 1536-dimension vectors takes seconds, far exceeding the 100ms requirement. Opsi D — B-tree indexes work for scalar value ordering, not high-dimensional similarity search; hashing vectors destroys distance relationships.

An online gaming platform needs a session state store that supports: 100,000 read/write operations per second, sub-millisecond latency for both reads and writes, complex data structures (sorted sets for leaderboards, lists for chat history, hashes for player state), and automatic failover with zero data loss. The data is ephemeral (24-hour TTL) but must not be lost during infrastructure failures within that window. Which AWS service is MOST appropriate?
  • A. Amazon MemoryDB for Redis, which provides Redis-compatible data structure support (sorted sets, lists, hashes) with Multi-AZ durability using a distributed transaction log that ensures zero data loss on failover, while maintaining sub-millisecond read latency and single-digit millisecond write latency
  • B. Amazon ElastiCache for Redis with Multi-AZ replication enabled for automatic failover
  • C. Amazon DynamoDB with DAX caching layer for sub-millisecond reads
  • D. Amazon Aurora PostgreSQL with connection pooling using RDS Proxy for low-latency access
Jawaban Benar: A
MemoryDB is purpose-built for this scenario: (1) full Redis data structure support (sorted sets for leaderboards, lists for chat, hashes for player state); (2) sub-millisecond read latency from in-memory storage; (3) Multi-AZ durability with a distributed transaction log that persists every write before acknowledging — guaranteeing zero data loss on failover (unlike ElastiCache which may lose recent writes during failover); (4) 100K+ ops/sec throughput. Opsi B — ElastiCache Redis provides the same data structures and latency but uses asynchronous replication; during failover, the last few seconds of writes to the primary may be lost (the replica may not have received them yet). This violates the "zero data loss" requirement. Opsi C — DynamoDB+DAX provides sub-ms reads but doesn't natively support Redis data structures (sorted sets, lists); application must implement leaderboards differently. Opsi D — Aurora's disk-based architecture cannot achieve sub-millisecond latency consistently at 100K ops/sec.

A fraud detection system needs to identify suspicious financial transactions in real-time by checking if a transaction's characteristics are similar to known fraud patterns. The system stores 500,000 known fraud pattern vectors (256 dimensions) and must search for the nearest 10 patterns for each incoming transaction within 10ms to make a block/allow decision. The fraud pattern database is updated weekly. The team must choose between HNSW and IVF index types on Aurora PostgreSQL with pgvector. Which index type and why?
  • A. HNSW index because it provides consistent low-latency queries (sub-10ms for 500K vectors) regardless of data distribution changes, doesn't require retraining after weekly updates, and maintains high recall even with incremental insertions — critical for a fraud detection system where missing a similar pattern (false negative) has severe financial consequences
  • B. IVF index because it uses less memory than HNSW and provides faster index build times, making weekly rebuilds feasible
  • C. IVF index with nprobe equal to nlist (searching all cells) to guarantee 100% recall for the fraud detection use case
  • D. Neither — use exact brute-force search since 500K vectors is small enough for sequential scan within 10ms
Jawaban Benar: A
HNSW is superior for this fraud detection scenario: (1) at 500K vectors with 256 dimensions, HNSW easily achieves sub-5ms query time; (2) HNSW handles incremental insertions without retraining — new fraud patterns added weekly are immediately searchable; (3) HNSW provides higher recall (fewer missed similar patterns) than IVF at equivalent latency, critical when false negatives mean undetected fraud; (4) query latency is consistent regardless of query vector position in the space. Opsi B — while IVF uses less memory and builds faster, it requires retraining (rebuilding cell centroids) when data distribution changes; stale centroids after weekly updates degrade recall — unacceptable for fraud detection. Opsi C — IVF with nprobe=nlist is equivalent to brute-force search, defeating the purpose of an index. Opsi D — brute-force scan of 500K × 256-dim vectors takes approximately 50-100ms on Aurora, exceeding the 10ms requirement when accounting for concurrent queries and database overhead.

A knowledge management platform stores 5 million documents. Users ask natural language questions, and the system must retrieve the most relevant documents using semantic search (not keyword matching). The platform uses Amazon Bedrock to generate embeddings and needs a database that supports: vector similarity search, metadata filtering (by department, date, access level), full-text keyword search as a fallback, and ACID transactions for document updates. Which database service BEST addresses all these requirements in a single solution?
  • A. Amazon Aurora PostgreSQL with pgvector extension, which provides vector similarity search (HNSW/IVF indexes), traditional SQL for metadata filtering (WHERE department='Engineering' AND date > '2024-01-01'), full-text search via tsvector/tsquery, and native ACID transaction support — all in a single database engine
  • B. Amazon OpenSearch Service with k-NN plugin for vector search, combined with its native full-text search capabilities and metadata filtering
  • C. Amazon Neptune for storing document relationships as a knowledge graph with vector similarity as a graph traversal operation
  • D. Amazon DynamoDB for document storage with a separate Pinecone-compatible vector database for similarity search
Jawaban Benar: A
Aurora PostgreSQL with pgvector uniquely satisfies ALL four requirements in a single engine: (1) pgvector provides vector similarity search with HNSW indexes for semantic retrieval; (2) PostgreSQL's rich SQL supports complex metadata filtering with standard WHERE clauses and joins; (3) built-in full-text search (tsvector/tsquery with GIN indexes) provides keyword fallback; (4) PostgreSQL's native ACID transactions ensure document update consistency. This eliminates multi-service complexity and data synchronization challenges. Opsi B — OpenSearch provides vector + full-text search but lacks ACID transactions (eventual consistency) and has limited metadata query capabilities compared to SQL. Opsi C — Neptune is for graph traversal (relationship queries), not semantic similarity search or document management; it doesn't natively support vector indexes. Opsi D — using two separate services (DynamoDB + external vector DB) requires synchronization, doubles operational complexity, and DynamoDB doesn't provide full-text search.

A supply chain company needs to model and query complex relationships between suppliers, manufacturers, distributors, and retailers. Key queries include: "find all suppliers within 3 hops of a given retailer," "identify the shortest supply route between two entities," and "detect circular dependencies in the supply chain." The graph has 2 million nodes and 50 million edges with properties on both. Which AWS service is specifically designed for this use case?
  • A. Amazon Neptune, a purpose-built graph database supporting both property graph (Gremlin/openCypher) and RDF (SPARQL) models, optimized for traversal queries like multi-hop path finding, shortest path algorithms, and cycle detection across millions of nodes and edges with ACID transaction support
  • B. Amazon DynamoDB with an adjacency list pattern where each item stores a node and its direct connections as a list attribute
  • C. Amazon Redshift with recursive CTEs (Common Table Expressions) to traverse the supply chain relationships stored in a relational table
  • D. Amazon Aurora PostgreSQL with a self-referencing table and application-level graph traversal logic
Jawaban Benar: A
Neptune is purpose-built for graph workloads: (1) native graph storage engine optimizes for traversal operations (pointer-based adjacency vs. JOIN-based in relational); (2) Gremlin traversal language expresses "3 hops from retailer" naturally (g.V(retailer).repeat(out()).times(3)); (3) built-in shortest path algorithms execute in O(V+E) time; (4) cycle detection is native to graph query languages; (5) 50M edges with properties are Neptune's bread and butter. Opsi B — DynamoDB adjacency list requires multiple sequential reads for multi-hop traversal (one read per hop), with no native shortest path or cycle detection capabilities. Opsi C — Redshift recursive CTEs are possible but extremely inefficient for graph traversal at 50M edges — each recursion level requires a full JOIN operation, and Redshift is optimized for analytical scans, not iterative traversal. Opsi D — Aurora can simulate graph queries but self-JOINs for multi-hop paths become exponentially expensive; at 50M edges and 3+ hops, query performance degrades significantly.

A real-time bidding (RTB) platform for digital advertising must make bid decisions within 100ms of receiving an ad request. The decision requires looking up user segment data (key: user_id, value: JSON with demographics and interests) from a dataset of 200 million users. The system handles 500,000 requests per second with extreme latency sensitivity — p99 latency must be under 5ms for the cache layer. Which caching architecture is MOST appropriate?
  • A. Amazon ElastiCache for Redis cluster mode with multiple shards distributing the 200M keys across nodes, using consistent hashing for key distribution. Configure read replicas per shard for read scaling, and use connection pooling to minimize connection overhead at 500K RPS
  • B. Amazon DynamoDB with DAX (DynamoDB Accelerator) as the caching layer in front of DynamoDB
  • C. Application-level in-memory cache (local HashMap) in each bidding service instance, refreshed periodically from S3
  • D. Amazon ElastiCache for Memcached with multiple nodes for simple key-value caching
Jawaban Benar: A
Redis Cluster Mode is optimal for this use case: (1) sharding distributes 200M keys across multiple nodes (each node handles a subset of requests), enabling 500K+ RPS aggregate throughput; (2) consistent hashing ensures predictable key-to-node mapping; (3) read replicas per shard multiply read capacity for this read-heavy workload; (4) Redis provides sub-millisecond latency for single-key lookups, easily meeting p99 < 5ms; (5) cluster auto-scaling accommodates traffic spikes. Opsi B — DAX provides sub-ms reads but is tightly coupled to DynamoDB's data model and pricing; at 500K RPS, DAX cluster costs are higher than Redis for pure cache workloads, and DAX has limited data structure support. Opsi C — 200M users × ~1KB per record = 200+ GB exceeds per-instance memory; additionally, local caches create consistency issues across instances. Opsi D — Memcached provides simple caching but lacks data persistence, replication for HA, and cluster mode's automatic resharding; a node failure loses its entire cache segment.

An e-commerce search platform needs to support: full-text product search with relevance ranking, faceted navigation (filter by brand, price range, color), autocomplete suggestions, and "fuzzy" matching for misspellings. The catalog has 50 million products with structured attributes (price, brand) and unstructured text (descriptions, reviews). Which AWS service is purpose-built for this search use case?
  • A. Amazon OpenSearch Service, which provides inverted indexes for full-text search with BM25 relevance scoring, aggregation framework for faceted navigation, completion suggesters for autocomplete, and fuzzy query support for misspelling tolerance — all optimized for search workloads at scale
  • B. Amazon Aurora PostgreSQL with GIN indexes on tsvector columns for full-text search and B-tree indexes for faceted filtering
  • C. Amazon DynamoDB with a GSI for each searchable attribute and application-level text matching
  • D. Amazon Redshift with LIKE queries on product description columns and GROUP BY for facet counts
Jawaban Benar: A
OpenSearch is a dedicated search engine with all required capabilities built-in: (1) inverted indexes with BM25/TF-IDF scoring provide relevance-ranked full-text search; (2) aggregation framework computes facet counts (brand: Apple(500), Samsung(300)) in the same query; (3) completion suggesters provide type-ahead autocomplete from partial input; (4) fuzzy queries use Levenshtein distance for misspelling tolerance; (5) horizontal scaling handles 50M documents with sub-second search latency. Opsi B — PostgreSQL full-text search works for smaller datasets but lacks native autocomplete suggesters, fuzzy matching is limited, and faceted aggregations on 50M rows are slower than OpenSearch's optimized aggregation engine. Opsi C — DynamoDB doesn't support full-text search, relevance ranking, fuzzy matching, or faceted navigation; these would all require application-level implementation. Opsi D — Redshift LIKE queries don't provide relevance scoring, are slow for text search at scale, and Redshift is designed for analytical queries, not real-time search.

A machine learning team has trained a product recommendation model that generates 768-dimensional embedding vectors. They need to serve recommendations with: (1) vector similarity search across 100 million product embeddings, (2) real-time filtering by product availability (boolean) and price range during the search, (3) updates to product availability status within 1 second of change, and (4) 99.9% availability. The team wants a fully managed solution. Which approach BEST meets all requirements?
  • A. Amazon OpenSearch Service with k-NN plugin using HNSW algorithm, storing embeddings as knn_vector fields alongside product metadata. Use filtered k-NN queries that apply metadata filters (availability=true AND price BETWEEN 10 AND 50) during the vector search, with near real-time index refreshes for availability updates
  • B. Aurora PostgreSQL with pgvector, using HNSW index on the embedding column and WHERE clauses for metadata filtering
  • C. Amazon SageMaker with a custom endpoint hosting a FAISS index loaded from S3, with separate DynamoDB calls for metadata filtering
  • D. Amazon Neptune with vector similarity as a custom Lambda function integrated into graph queries
Jawaban Benar: A
OpenSearch with k-NN plugin is optimal: (1) HNSW algorithm handles 100M vectors efficiently with sub-100ms latency; (2) OpenSearch's filtered k-NN applies metadata predicates during the search (not post-search), ensuring results respect availability and price constraints; (3) near real-time index refresh (1-second default) makes availability changes searchable immediately; (4) OpenSearch Service is fully managed with Multi-AZ deployment for 99.9% availability. Opsi B — Aurora pgvector can work but 100M vectors may exceed practical limits for a single PostgreSQL instance; filtered vector queries with WHERE clauses scan all matching vectors before applying the ANN index, which is less efficient than OpenSearch's integrated filtered search. Opsi C — custom FAISS endpoints require managing infrastructure, scaling, and the separate DynamoDB call adds latency and complexity; also not a fully managed end-to-end solution. Opsi D — Neptune doesn't have native vector similarity search capabilities at this scale.

A data engineering team needs to accelerate read performance for a DynamoDB table that serves a product catalog API. The table has 5 million items and handles 50,000 read requests per second. 90% of reads are for the same 100,000 "popular" items (hot keys). The remaining 10% access the long-tail of less popular items. Current DynamoDB costs are high due to provisioned RCUs for peak traffic. Which caching strategy MOST reduces cost while maintaining performance?
  • A. Deploy DynamoDB Accelerator (DAX) as an in-memory cache in front of DynamoDB. DAX provides microsecond read latency for cached items (the hot 100K items), transparently handles cache misses by reading from DynamoDB (long-tail items), and reduces DynamoDB RCU consumption by serving repeated reads from cache — enabling RCU reduction by up to 90%
  • B. Increase DynamoDB provisioned RCUs to handle 50K reads/second without throttling
  • C. Switch to DynamoDB On-Demand mode to pay per-request and avoid over-provisioning
  • D. Implement application-level caching using ElastiCache Redis with TTL-based cache invalidation
Jawaban Benar: A
DAX is purpose-built for this pattern: (1) write-through/read-through cache that's transparent to the application (same DynamoDB API, just point to DAX endpoint); (2) the hot 100K items are cached in memory, serving 90% of reads at microsecond latency without consuming DynamoDB RCUs; (3) cache misses (10% long-tail) fall through to DynamoDB normally; (4) net effect: 90% reduction in DynamoDB RCU consumption (only long-tail reads consume RCUs). DAX cost is typically far less than the RCU savings. Opsi B — provisioning for peak (50K RCU) is the current expensive approach; doesn't reduce costs. Opsi C — On-Demand at 50K reads/second would cost more than provisioned with caching since every request is charged at on-demand rates ($1.25 per million reads). Opsi D — ElastiCache Redis works but requires application code changes (different API), cache invalidation logic, and lacks DAX's transparent DynamoDB integration and automatic item-level cache management.

A logistics company needs to optimize delivery routes by finding the shortest paths between multiple delivery stops, considering real-time traffic data that updates edge weights (travel times) every 5 minutes. The road network graph has 10 million intersections (nodes) and 30 million road segments (edges) with dynamic weight properties. Route calculations must complete within 2 seconds. Which database architecture supports both the graph traversal and dynamic weight updates efficiently?
  • A. Amazon Neptune for storing the road network graph with Gremlin traversal queries for path finding, combined with a property update mechanism that modifies edge weights (travel_time) every 5 minutes from real-time traffic feeds, using Neptune's ACID transactions to ensure consistent reads during weight updates
  • B. Amazon DynamoDB storing each road segment as an item with origin/destination as keys, with application-level Dijkstra's algorithm making individual GetItem calls for each step
  • C. Amazon Redshift with a roads table and recursive CTEs to find shortest paths using SQL
  • D. Amazon S3 storing the graph as an adjacency matrix CSV file, loaded into Lambda memory for route calculations
Jawaban Benar: A
Neptune excels at this use case: (1) native graph storage with index-free adjacency enables O(1) neighbor lookups during path traversal; (2) Gremlin's shortestPath() step or weighted traversals implement Dijkstra/A* algorithms natively; (3) edge property updates (travel_time) are simple property mutations that take effect immediately; (4) ACID transactions prevent route calculations from reading partially-updated weights during a traffic update batch; (5) 10M nodes/30M edges is well within Neptune's capacity. Opsi B — making individual DynamoDB GetItem calls per graph hop introduces 2-5ms network latency per step; a route with 50+ hops would take 100-250ms just for I/O, with no native shortest path algorithm. Opsi C — Redshift recursive CTEs over 30M edges would be extremely slow for shortest path calculations; Redshift is not designed for iterative graph algorithms. Opsi D — 10M nodes adjacency matrix would be 10M×10M entries (petabytes); even adjacency list format at 30M edges exceeds Lambda's 10 GB memory limit.
