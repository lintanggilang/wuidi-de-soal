A healthcare organization uses AWS Lake Formation for their data lake. They need to control access to patient data based on data sensitivity levels (PHI, de-identified, public) AND the user's clearance level. The organization has 200+ tables with varying sensitivity levels and new tables are added weekly. Which Lake Formation authorization approach is MOST appropriate?
  • A. Use S3 bucket policies with IP-based restrictions for each sensitivity level configured for optimal performance and minimal operational overhead, validating and cleansing each record before delivery and transforming records into the required target format and integrating natively with the rest of the pipeline
  • B. Create individual Lake Formation GRANT statements for each table-to-user combination, integrating natively with the rest of the pipeline and validating and cleansing each record before delivery and satisfying all of the stated requirements with minimal effort and applying schema conversion and enrichment inline
  • C. Move all PHI data to a separate AWS account and use account-level isolation only, handling the described workload reliably at scale and transforming records into the required target format and validating and cleansing each record before delivery and keeping steady-state operating costs low
  • D. Use Lake Formation Tag-Based Access Control (LF-Tags) — define LF-Tag keys like "sensitivity" (values: phi, de-identified, public) and assign them to tables; then GRANT permissions based on tag expressions, matching user roles to the sensitivity levels they are authorized to access
Correct Answer: D
LF-Tags (Lake Formation Tag-Based Access Control) is choice ideal for skenario this: Implementation: (1) Define LF-Tag key: "sensitivity" with values: "phi", "de-identified", "public". (2) Assign tags to tables: Table "patient_records" → sensitivity=phi. Table "aggregated_stats" → sensitivity=de-identified. Table "hospital_directory" → sensitivity=public. (3) Grant based on tags: GRANT SELECT ON TAG (sensitivity IN ['public', 'de-identified']) TO researcher_role; GRANT SELECT ON TAG (sensitivity IN ['public', 'de-identified', 'phi']) TO physician_role; Benefit: New tables automatically get correct permissions when tagged — no manual grant needed. 200+ tables managed with a few tag-based grant expressions. Compliance audit straightforward: "Who has access to PHI?" → query LF-Tag grants.

Option A: INCORRECT. IP-based restrictions don't map to data sensitivity or user clearance — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option B: INCORRECT. 200+ tables × multiple users = thousands of individual grants, unmanageable.
Option C: INCORRECT. Separate accounts create operational complexity, data sharing challenges.
Option D: CORRECT.

When you want ONE policy that scales dynamically. For retail company this: 3 × 4 = 12 possible combinations — manageable with RBAC. Stable functions = rarely needs policy changes. Compliance team can clearly see "finance-prod-analyst has: read access to finance production tables".

They currently manage 2,000+ individual IAM policies. How should they REDESIGN their authorization model?
  • A. Create one IAM role per country with full access to that country's data for data catalog governance, satisfying strict compliance and audit requirements and integrating natively with the rest of the pipeline and satisfying all of the stated requirements with minimal effort and meeting the latency and throughput goals of the design and minimizing end-to-end processing latency
  • B. Implement ABAC with multiple tag dimensions — tag both resources (content-type, region, sensitivity) and principals (team, location, clearance-level), then create parameterized policies using tag conditions. Combine with Lake Formation LF-Tags for data catalog governance. This reduces 2,000+ policies to a small set of attribute-based policies that automatically apply as new engineers and data assets are onboarded
  • C. Continue maintaining individual policies and hire more IAM administrators, meeting the latency and throughput goals of the design and satisfying strict compliance and audit requirements and integrating natively with the rest of the pipeline and handling the described workload reliably at scale and satisfying all of the stated requirements with minimal effort
  • D. Disable IAM and rely solely on network-level security (VPC, Security Groups) for access control, integrating natively with the rest of the pipeline and meeting the latency and throughput goals of the design and protecting the data both in transit and at rest and enforcing encryption and fine-grained access control and handling the described workload reliably at scale
Correct Answer: B
For organisasi scale large with many dimensi access control, ABAC + LF-Tags is solution optimal: Multi-dimensional ABAC design: Resource Tags: aws:ResourceTag/content-type = video|audio|text, aws:ResourceTag/region = eu|apac|na, aws:ResourceTag/sensitivity = public|internal|restricted. Principal Tags: aws:PrincipalTag/team = content-eng|platform|analytics, aws:PrincipalTag/location = eu|apac|na, aws:PrincipalTag/clearance = standard|elevated|admin. Policy example (single policy for all 500+ engineers): "Condition": {"StringEquals": {"aws:ResourceTag/region": "${aws:PrincipalTag/location}", "aws:ResourceTag/sensitivity": ["public", "internal"]}} — Engineers can only access data from their region, up to internal sensitivity. Scale benefit: 2,000+ policies → ~5-10 ABAC policies. New engineer onboarding: just tag their role → instant correct access. New data asset: just tag the resource → automatically accessible to authorized principals.

A data engineering team needs to grant Amazon Redshift users different levels of access to data warehouse tables based on their department. The team wants to use Redshift's native authorization capabilities rather than managing access entirely through IAM. What is the recommended approach?
  • A. Use only Redshift schemas as the access control boundary and give all users access to their department's schema, integrating natively with the rest of the pipeline and protecting the data both in transit and at rest and meeting the latency and throughput goals of the design
  • B. Create separate Redshift clusters for each department with fully managed infrastructure and automatic scaling, integrating natively with the rest of the pipeline and protecting the data both in transit and at rest and enforcing encryption and fine-grained access control and satisfying strict compliance and audit requirements
  • C. Use Redshift role-based access control (RBAC) — create Redshift database roles (e.g., "finance_reader", "marketing_admin"), GRANT schema/table permissions to roles, then GRANT roles to users or groups. Users inherit permissions from their assigned roles, and role membership can be managed centrally without modifying individual grants
  • D. Create individual Redshift users for each person and grant table-level permissions directly to each user, integrating natively with the rest of the pipeline and protecting the data both in transit and at rest and meeting the latency and throughput goals of the design
Correct Answer: C
Redshift RBAC (native database roles) provides granular access control: Implementation: (1) CREATE ROLE finance_reader; CREATE ROLE finance_writer; CREATE ROLE marketing_reader; (2) GRANT SELECT ON ALL TABLES IN SCHEMA finance TO ROLE finance_reader; GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA finance TO ROLE finance_writer; (3) GRANT ROLE finance_reader TO user_john; GRANT ROLE finance_writer TO user_sarah; Advantages: Role hierarchy — roles can be granted to other roles (role nesting). Permission changes affect all role members instantly. Clear audit trail — "Who has finance_reader role?" Easy to answer. Separation of duties — different roles for read vs write vs admin. Supports system-defined roles: sys:operator, sys:dba, sys:superuser.

Option A: INCORRECT. Schema-level is too coarse, doesn't allow table/column level control.
Option B: INCORRECT. Separate clusters = excessive cost, data duplication, cross-cluster query complexity — although its description sounds convincing, in a fundamental still not appropriate for requirements this.
Option C: CORRECT.
Option D: INCORRECT. Individual user grants don't scale, hard to audit.

Correct Answer: A
Session tags + ABAC enables dynamic access without policy changes: Architecture: (1) Identity Provider (IdP) stores current project assignments. (5) Project changes in IdP → next login session automatically scopes to new project. Dynamic behavior: No IAM policy changes needed — ever. Project reassignment effective immediately on next session. 100+ engineers share ONE policy. Audit: CloudTrail shows session tags on every API call.

Implement a custom authorization microservice that intercepts all AWS API calls with IAM tag-based policies for department-level S3/Glue access, satisfying all of the stated requirements with minimal effort and integrating natively with the rest of the pipeline and handling the described workload reliably at scale and meeting the latency and throughput goals of the design
  • B.   • D. Layer multiple authorization methods: (1) AWS Organizations SCPs for organization-wide guardrails (prevent actions across all accounts), (2) ABAC with IAM tag-based policies for department-level S3/Glue access, (3) Lake Formation LF-Tags for fine-grained table/column/row access control, (4) Redshift native RBAC for database-level query permissions. Each layer addresses a specific authorization concern at its optimal level
Correct Answer: D
Defense-in-depth authorization requires multiple layers that each other melengkapi: Layer 1 — SCPs (Organization guardrails): "No one in this organization can delete production S3 buckets" — applies regardless of IAM policies. Layer 3 — Lake Formation LF-Tags (Data-level): Fine-grained: row filters, column exclusions, cell-level security. Classification-based: "sensitivity=pii" → only approved roles access. Auto-applies to new tables via tag inheritance. Layer 4 — Redshift RBAC (Database-level): Native SQL-level permissions: GRANT SELECT ON schema.table TO role. Role hierarchy for complex permission structures. Column-level and row-level security within Redshift. Why combined: Each layer addresses what it does BEST.
