Skill 4.2.5: Apply Authorization Methods That Address Business Needs

Role-based, tag-based, and attribute-based access control for data pipelines

1
A financial services company has 50 data engineering teams across 8 departments. Each department has a dedicated S3 prefix (s3://data-lake/dept-name/) and a set of Glue databases. New teams are frequently created, and the security team spends significant time creating individual IAM policies for each new team. Which authorization approach BEST addresses this scalability challenge?
  • A. Create a single IAM policy with wildcard (*) access to all S3 paths and share it across teams
  • B. Implement Attribute-Based Access Control (ABAC) using AWS tags — tag IAM roles with "department" and "team" attributes, then create a single IAM policy with conditions that reference aws:PrincipalTag keys to dynamically scope S3 and Glue access based on the principal's tags
  • C. Create 50 separate IAM policies, one for each team, with hardcoded resource ARNs
  • D. Use AWS Organizations to create separate accounts for each team
Jawaban Benar: B
ABAC (Attribute-Based Access Control) menggunakan tags adalah solusi paling scalable untuk organisasi besar: Cara kerja: (1) Tag IAM roles: aws:PrincipalTag/department = "finance", aws:PrincipalTag/team = "risk-analytics". (2) Buat SATU IAM policy template yang menggunakan conditions: {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::data-lake/${aws:PrincipalTag/department}/*", "Condition": {...}}. (3) Saat new team dibuat: cukup tag role mereka — TIDAK perlu policy baru. Keuntungan ABAC: Satu policy melayani semua 50 teams. New teams otomatis mendapat access yang tepat via tags. Tidak ada policy sprawl. Audit lebih mudah karena policy logic terpusat. Opsi A — violates least privilege, massive security risk. Opsi C — policy sprawl, tidak scalable (butuh update manual setiap ada team baru). Opsi D — over-engineering, account proliferation complexity.
2
A healthcare organization uses AWS Lake Formation for their data lake. They need to control access to patient data based on data sensitivity levels (PHI, de-identified, public) AND the user's clearance level. The organization has 200+ tables with varying sensitivity levels and new tables are added weekly. Which Lake Formation authorization approach is MOST appropriate?
  • A. Create individual Lake Formation GRANT statements for each table-to-user combination
  • B. Use Lake Formation Tag-Based Access Control (LF-Tags) — define LF-Tag keys like "sensitivity" (values: phi, de-identified, public) and assign them to tables; then GRANT permissions based on tag expressions, matching user roles to the sensitivity levels they are authorized to access
  • C. Move all PHI data to a separate AWS account and use account-level isolation only
  • D. Use S3 bucket policies with IP-based restrictions for each sensitivity level
Jawaban Benar: B
LF-Tags (Lake Formation Tag-Based Access Control) adalah pilihan ideal untuk skenario ini: Implementation: (1) Define LF-Tag key: "sensitivity" dengan values: "phi", "de-identified", "public". (2) Assign tags ke tables: Table "patient_records" → sensitivity=phi. Table "aggregated_stats" → sensitivity=de-identified. Table "hospital_directory" → sensitivity=public. (3) Grant based on tags: GRANT SELECT ON TAG (sensitivity IN ['public', 'de-identified']) TO researcher_role; GRANT SELECT ON TAG (sensitivity IN ['public', 'de-identified', 'phi']) TO physician_role; Benefit: New tables automatically get correct permissions when tagged — no manual grant needed. 200+ tables managed with a few tag-based grant expressions. Compliance audit straightforward: "Who has access to PHI?" → query LF-Tag grants. Opsi A — 200+ tables × multiple users = thousands of individual grants, unmanageable. Opsi C — separate accounts create operational complexity, data sharing challenges. Opsi D — IP-based restrictions don't map to data sensitivity or user clearance.
3
A retail company has three environments (dev, staging, prod) and four business units (marketing, finance, supply-chain, HR). They are choosing between RBAC and ABAC for their data pipeline access control. The company has stable, well-defined job functions with predictable access patterns. Which approach is MORE suitable and why?
  • A. ABAC because it always provides better security than RBAC regardless of the scenario
  • B. RBAC (Role-Based Access Control) using IAM groups/roles — because with stable, well-defined job functions, creating specific roles (e.g., "finance-prod-analyst", "marketing-dev-engineer") provides clear permission boundaries, simpler auditing, and easier comprehension for compliance teams. RBAC is preferred when the number of distinct access patterns is manageable and changes are infrequent
  • C. Use both ABAC and RBAC on every resource simultaneously to maximize security
  • D. Neither — use only S3 bucket policies without any IAM-based access control
Jawaban Benar: B
Pemilihan antara RBAC vs ABAC bergantung pada organisasi: RBAC lebih cocok ketika: Job functions stabil dan well-defined. Number of distinct roles manageable (3 envs × 4 BUs = ~12-24 roles). Compliance teams prefer explicit role-to-permission mappings. Changes to access patterns infrequent. Easier to answer "What can role X do?" — langsung lihat policy attached ke role. ABAC lebih cocok ketika: Organisasi rapidly growing (new teams, new projects frequently). Hundreds of permutation possibilities. Need "automatic" permission assignment based on attributes. When you want ONE policy that scales dynamically. Untuk retail company ini: 3 × 4 = 12 possible combinations — manageable with RBAC. Stable functions = jarang perlu policy changes. Compliance team bisa clearly see "finance-prod-analyst has: read access to finance production tables". Opsi A salah — ABAC tidak selalu better, depends on use case. Opsi C — combining both unnecessarily adds complexity. Opsi D — S3 bucket policies alone insufficient for fine-grained access control.
4
A global media company is migrating to AWS. They have 500+ data engineers across 30 countries, accessing data that is classified by content type (video, audio, text), region (EU, APAC, NA), and business sensitivity (public, internal, restricted). They currently manage 2,000+ individual IAM policies. How should they REDESIGN their authorization model?
  • A. Continue maintaining individual policies and hire more IAM administrators
  • B. Implement ABAC with multiple tag dimensions — tag both resources (content-type, region, sensitivity) and principals (team, location, clearance-level), then create parameterized policies using tag conditions. Combine with Lake Formation LF-Tags for data catalog governance. This reduces 2,000+ policies to a small set of attribute-based policies that automatically apply as new engineers and data assets are onboarded
  • C. Create one IAM role per country with full access to that country's data
  • D. Disable IAM and rely solely on network-level security (VPC, Security Groups) for access control
Jawaban Benar: B
Untuk organisasi berskala besar dengan banyak dimensi access control, ABAC + LF-Tags adalah solusi optimal: Multi-dimensional ABAC design: Resource Tags: aws:ResourceTag/content-type = video|audio|text, aws:ResourceTag/region = eu|apac|na, aws:ResourceTag/sensitivity = public|internal|restricted. Principal Tags: aws:PrincipalTag/team = content-eng|platform|analytics, aws:PrincipalTag/location = eu|apac|na, aws:PrincipalTag/clearance = standard|elevated|admin. Policy example (single policy for all 500+ engineers): "Condition": {"StringEquals": {"aws:ResourceTag/region": "${aws:PrincipalTag/location}", "aws:ResourceTag/sensitivity": ["public", "internal"]}} — Engineers can only access data from their region, up to internal sensitivity. Scale benefit: 2,000+ policies → ~5-10 ABAC policies. New engineer onboarding: just tag their role → instant correct access. New data asset: just tag the resource → automatically accessible to authorized principals. Opsi A — unsustainable at scale. Opsi C — country-level is too broad, violates least privilege. Opsi D — network security cannot provide data-level authorization.
5
A data engineering team needs to grant Amazon Redshift users different levels of access to data warehouse tables based on their department. The team wants to use Redshift's native authorization capabilities rather than managing access entirely through IAM. What is the recommended approach?
  • A. Create individual Redshift users for each person and grant table-level permissions directly to each user
  • B. Use Redshift role-based access control (RBAC) — create Redshift database roles (e.g., "finance_reader", "marketing_admin"), GRANT schema/table permissions to roles, then GRANT roles to users or groups. Users inherit permissions from their assigned roles, and role membership can be managed centrally without modifying individual grants
  • C. Use only Redshift schemas as the access control boundary and give all users access to their department's schema
  • D. Create separate Redshift clusters for each department
Jawaban Benar: B
Redshift RBAC (native database roles) menyediakan granular access control: Implementation: (1) CREATE ROLE finance_reader; CREATE ROLE finance_writer; CREATE ROLE marketing_reader; (2) GRANT SELECT ON ALL TABLES IN SCHEMA finance TO ROLE finance_reader; GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA finance TO ROLE finance_writer; (3) GRANT ROLE finance_reader TO user_john; GRANT ROLE finance_writer TO user_sarah; Advantages: Role hierarchy — roles can be granted to other roles (role nesting). Permission changes affect all role members instantly. Clear audit trail — "Who has finance_reader role?" Easy to answer. Separation of duties — different roles for read vs write vs admin. Supports system-defined roles: sys:operator, sys:dba, sys:superuser. Opsi A — individual user grants don't scale, hard to audit. Opsi C — schema-level is too coarse, doesn't allow table/column level control. Opsi D — separate clusters = excessive cost, data duplication, cross-cluster query complexity.
6
A company wants to implement dynamic access control where a data engineer's access to specific S3 prefixes changes based on the project they are currently assigned to, without requiring IAM policy updates. Projects change monthly, and there are 100+ engineers. Which approach enables this dynamic authorization?
  • A. Update each engineer's IAM policy monthly through a manual change request process
  • B. Use ABAC with session tags — when engineers assume their IAM role via SSO/federation, pass session tags (e.g., "project=alpha") from the identity provider. IAM policies use aws:PrincipalTag/project condition to scope S3 access to s3://data-lake/${aws:PrincipalTag/project}/. When project assignment changes in the IdP, access automatically changes at next session without any IAM policy modification
  • C. Create a Lambda function that rewrites IAM policies nightly based on a project assignment database
  • D. Give all engineers access to all project prefixes and rely on naming conventions for separation
Jawaban Benar: B
Session tags + ABAC memungkinkan dynamic access tanpa policy changes: Architecture: (1) Identity Provider (IdP) stores current project assignments. (2) When engineer authenticates via SSO → IdP passes session tags: aws:PrincipalTag/project = "alpha". (3) IAM role trust policy allows transitive session tags. (4) Single IAM policy: {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::data-lake/${aws:PrincipalTag/project}/*"}. (5) Project changes in IdP → next login session automatically scopes to new project. Dynamic behavior: No IAM policy changes needed — ever. Project reassignment effective immediately on next session. 100+ engineers share ONE policy. Audit: CloudTrail shows session tags on every API call. Opsi A — manual process, slow, error-prone, doesn't scale. Opsi C — Lambda rewriting policies creates race conditions, eventual consistency issues, IAM policy size limits. Opsi D — no access control, violates least privilege.
7
A large enterprise needs to combine multiple authorization methods. Their requirements: (1) Organization-wide guardrails preventing certain actions, (2) Department-level resource access using attributes, (3) Fine-grained data lake table/column access, (4) Redshift-specific query permissions. Which combination of authorization methods addresses ALL these layers?
  • A. Use only IAM policies for everything — they can handle all authorization scenarios
  • B. Layer multiple authorization methods: (1) AWS Organizations SCPs for organization-wide guardrails (prevent actions across all accounts), (2) ABAC with IAM tag-based policies for department-level S3/Glue access, (3) Lake Formation LF-Tags for fine-grained table/column/row access control, (4) Redshift native RBAC for database-level query permissions. Each layer addresses a specific authorization concern at its optimal level
  • C. Use only Lake Formation for all authorization since it covers all AWS services
  • D. Implement a custom authorization microservice that intercepts all AWS API calls
Jawaban Benar: B
Defense-in-depth authorization memerlukan multiple layers yang saling melengkapi: Layer 1 — SCPs (Organization guardrails): "No one in this organization can delete production S3 buckets" — applies regardless of IAM policies. Prevents shadow admin scenarios. Sets hard ceiling on what ANY principal can do. Layer 2 — ABAC (Department-level): Tag-based IAM policies dynamically scope access: ${aws:PrincipalTag/department} matches resource tags. Handles 100s of departments with minimal policies. Layer 3 — Lake Formation LF-Tags (Data-level): Fine-grained: row filters, column exclusions, cell-level security. Classification-based: "sensitivity=pii" → only approved roles access. Auto-applies to new tables via tag inheritance. Layer 4 — Redshift RBAC (Database-level): Native SQL-level permissions: GRANT SELECT ON schema.table TO role. Role hierarchy for complex permission structures. Column-level and row-level security within Redshift. Why combined: Each layer addresses what it does BEST. Opsi A — IAM alone can't do row/column level, Redshift internal permissions, etc. Opsi C — Lake Formation doesn't cover Redshift internal permissions or org-level guardrails. Opsi D — custom interceptor adds latency, single point of failure, maintenance burden.

A data platform team is designing authorization for a multi-tenant data pipeline. Each tenant's data is stored in S3 with the prefix s3://pipeline-data/{tenant-id}/. Pipeline Glue jobs process data for multiple tenants but should only access the specific tenant's data during each job run. How should they implement tenant-scoped authorization for Glue jobs?
  • A. Create a separate Glue job and IAM role for each tenant
  • B. Use a single Glue job with a single IAM role that has s3:* access to all tenant prefixes
  • C. Pass tenant-id as a job parameter and use IAM policy conditions with variable substitution — the Glue job's IAM role policy uses a condition that restricts S3 access to the prefix matching the job's tag or a session policy that scopes down permissions to only the current tenant's data for that execution
  • D. Encrypt each tenant's data with a different KMS key and only grant decrypt permissions at runtime
Jawaban Benar: C
Tenant isolation dalam shared pipeline requires runtime-scoped authorization: Approach: (1) Glue job receives tenant-id as parameter (e.g., job argument --tenant-id=acme). (2) Glue job assumes a scoped-down role using session policy or the job's execution role uses resource tags. (3) Session policy restricts S3 access: {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::pipeline-data/acme/*"}. Alternative with ABAC: Tag the Glue job with tenant-id tag. Policy condition: "Condition": {"StringEquals": {"aws:ResourceTag/tenant-id": "${aws:PrincipalTag/tenant-id}"}}. Benefit: Single job definition, single base role, but per-execution tenant isolation. Even if job code has bug, IAM prevents cross-tenant data access. Opsi A — 1000 tenants = 1000 jobs + 1000 roles = unmanageable. Opsi B — violates tenant isolation, one tenant's job run could access all data. Opsi D — KMS-only approach doesn't prevent listing/metadata access and is complex to manage.

A data governance team notices that their ABAC implementation using IAM tags is not working for certain resources. Engineers tagged with "department=finance" cannot access Glue databases that are also tagged with "department=finance". The IAM policy uses aws:ResourceTag/department condition. What is the MOST likely issue?
  • A. ABAC does not work with AWS Glue resources
  • B. The Glue API actions being used do not support resource-level tag-based conditions — not all AWS services and actions support aws:ResourceTag conditions in IAM policies. Some Glue actions (like glue:GetDatabase) may not pass resource tags in the authorization context, requiring alternative approaches like resource-based naming conventions or Lake Formation for tag-based access
  • C. Tags on IAM roles are not visible to the IAM policy evaluation engine
  • D. ABAC only works with S3, not with any other AWS services
Jawaban Benar: B
Tidak semua AWS service actions support aws:ResourceTag conditions: Key concept: ABAC with aws:ResourceTag requires: (1) The service supports tagging the resource, (2) The specific API ACTION passes tag information in the authorization context, (3) The condition key is supported for that action. Issue dengan Glue: Beberapa Glue actions mendukung resource-level permissions dan tag conditions (e.g., glue:GetTable pada specific table ARN), TETAPI beberapa actions tidak fully support tag-based authorization. Solusi: Check AWS documentation "Actions, resources, and condition keys for AWS Glue" — verify which actions support resourceTag. Workarounds: (1) Use naming conventions (department prefix in database name) + wildcard ARN patterns. (2) Use Lake Formation LF-Tags instead — specifically designed for Glue catalog resource ABAC. (3) Combine IAM resource-level permissions with supplementary Lake Formation grants. Opsi A partially wrong — Glue DOES support some ABAC, but not uniformly. Opsi C wrong — aws:PrincipalTag IS visible to policy engine. Opsi D wrong — ABAC works with many services (EC2, RDS, S3, etc.).
10
A rapidly growing startup currently has 20 data engineers but expects to reach 200 within a year. They are deciding on an authorization strategy for their data lake. Currently they use simple RBAC with 5 IAM roles. The CTO asks: "At what point should we transition from RBAC to ABAC, and how?" What is the BEST recommendation?
  • A. Switch to ABAC immediately — RBAC is never suitable for any organization
  • B. Keep RBAC forever — it can handle any scale with enough roles
  • C. Plan a gradual transition: keep RBAC for stable, well-defined roles (e.g., "admin", "read-only") but introduce ABAC for the rapidly growing dimensions — use tags for project membership, team assignment, and environment access. The trigger to add ABAC is when the number of IAM policies exceeds manageable limits (typically 50-100+), when new team onboarding requires policy creation, or when access patterns become too dynamic for static role definitions
  • D. Abandon IAM-based controls entirely and use only network-level security
Jawaban Benar: C
Best practice adalah hybrid approach yang evolves dengan organisasi: Phase 1 (Current, 20 engineers): RBAC with 5 roles adequate. Simple, auditable, team understands it. Roles: admin, data-engineer, analyst, read-only, service-role. Phase 2 (Transition, 50-100 engineers): ABAC signals: New team → requires new policy (toil). Same role used by people needing different access scopes. IAM policy count growing linearly with team growth. Introduce ABAC for dynamic dimensions: project, team, environment. Keep RBAC for base capabilities. Phase 3 (Scale, 200+ engineers): Full ABAC for resource scoping (tags drive access boundaries). RBAC for capability levels (what CAN you do — read/write/admin). Lake Formation LF-Tags for data catalog governance. Migration strategy: (1) Start tagging all resources now (even while using RBAC). (2) Tag IAM roles with metadata. (3) Add ABAC conditions incrementally to existing policies. (4) New access patterns use ABAC; legacy RBAC remains until refactored. Opsi A — premature optimization for 20 engineers. Opsi B — pure RBAC at 200+ people creates role explosion. Opsi D — network security is NOT authorization.
