A data engineering team manages a data lake on AWS consisting of 15 AWS Glue crawlers, 20 Glue ETL jobs, an S3 data lake with multiple buckets, and associated IAM roles. Currently, all resources were created manually through the console. When the team needs to replicate the environment for a disaster recovery region, they estimate it will take 3 weeks of manual work. Which IaC approach MOST effectively addresses this challenge?
  • A. Use AWS CloudFormation templates with parameterized values for region-specific settings (bucket names, VPC IDs), organize resources into nested stacks by logical grouping (networking, storage, compute, ETL), and use CloudFormation StackSets to deploy across multiple regions simultaneously
  • B. Document all console steps in a wiki and have engineers follow the guide manually in the DR region
  • C. Export the existing resources using AWS Config rules and import them into the DR region
  • D. Create shell scripts that call AWS CLI commands to create each resource sequentially
Jawaban Benar: A
CloudFormation with parameterized templates enables repeatable, consistent deployments across regions. Nested stacks organize complex infrastructure logically. StackSets provide multi-region deployment from a single template. Parameters handle region-specific differences (bucket names, VPC IDs) without code changes. This reduces DR replication from weeks to minutes. Opsi B — manual documentation is error-prone and doesn't scale. Opsi C — AWS Config records configuration state but cannot deploy resources. Opsi D — shell scripts lack state management, rollback capability, and dependency resolution that CloudFormation provides.

A company uses AWS CDK (Python) to define their data pipeline infrastructure. A developer writes a CDK construct that creates an AWS Glue job, its IAM role, an S3 bucket for scripts, and a CloudWatch alarm for job failures. The team wants to reuse this construct across 12 different data pipelines with different configurations. Which CDK pattern BEST supports this requirement?
  • A. Create a custom L3 construct class that accepts configuration parameters (job name, script path, worker count, timeout, alarm threshold) and encapsulates the Glue job, IAM role, S3 bucket, and CloudWatch alarm as a single reusable unit that other stacks can instantiate multiple times
  • B. Copy and paste the CDK code 12 times, changing the configuration values in each copy
  • C. Create 12 separate CDK apps, each with its own stack definition
  • D. Use CloudFormation directly instead of CDK since CDK doesn't support reusability
Jawaban Benar: A
CDK L3 constructs (patterns) encapsulate multiple AWS resources into a single, configurable, reusable abstraction. The construct class defines the "blueprint" — IAM role, Glue job, S3 bucket, and alarm — while accepting parameters for customization. Each pipeline instantiates the construct with different config. Changes to the construct automatically apply to all 12 pipelines. This follows DRY principles and reduces maintenance burden. Opsi B — code duplication causes maintenance nightmares and inconsistency. Opsi C — separate apps prevent sharing common patterns and increase overhead. Opsi D — CDK was specifically designed for reusability; this statement is incorrect.

A data engineering team deploys their data lake infrastructure using CloudFormation. After a deployment, they notice that someone manually modified the Glue crawler schedule and added an S3 lifecycle policy through the console. These manual changes are not reflected in the template. What is the MOST appropriate way to detect and manage this situation?
  • A. Use CloudFormation drift detection to identify resources whose actual configuration differs from the template definition, review the drift results, and either update the template to incorporate desired changes or re-deploy the template to revert undesired manual modifications
  • B. Delete the entire stack and redeploy from the template to ensure consistency
  • C. Manually update the template to match whatever is currently deployed without verification
  • D. Ignore the differences since the pipeline is working correctly
Jawaban Benar: A
CloudFormation drift detection compares actual resource configurations against the template definition and reports differences. This allows the team to make informed decisions: if manual changes were intentional improvements, update the template to codify them. If they were unauthorized, redeploy the template to revert them. This maintains IaC as the source of truth. Opsi B — deleting the stack causes downtime and potential data loss. Opsi C — blindly updating templates without understanding changes may codify mistakes. Opsi D — ignoring drift causes template-reality divergence, making future deployments unpredictable and potentially destructive.

A company needs to deploy identical data pipeline infrastructure across development, staging, and production accounts. Each environment has different VPC configurations, instance sizes for EMR clusters, and number of Glue DPUs. The team wants a single IaC codebase that works across all environments. Which approach is MOST maintainable?
  • A. Use CloudFormation parameters with environment-specific parameter files (dev-params.json, staging-params.json, prod-params.json), combined with Conditions to include or exclude resources based on environment (e.g., only deploy monitoring alarms in production), and Mappings for fixed environment-specific values like instance types
  • B. Maintain three completely separate CloudFormation templates, one per environment
  • C. Use a single template with hardcoded production values and manually override them for other environments
  • D. Deploy only to production and use IAM roles to simulate different environments
Jawaban Benar: A
Parameter files externalize environment-specific values while maintaining a single template. Conditions enable environment-specific behavior (e.g., enhanced monitoring only in prod). Mappings provide lookup tables for fixed values per environment. This pattern keeps code DRY while supporting different configurations. Pipeline tools (CodePipeline, CDK Pipelines) select the appropriate parameter file per stage. Opsi B — separate templates diverge over time and triple the maintenance effort. Opsi C — hardcoded values with manual overrides are error-prone and defeat IaC purpose. Opsi D — single-account deployment violates AWS best practices for workload isolation.

A data engineer is writing a CloudFormation template to deploy an AWS Glue ETL job that reads from an RDS PostgreSQL database. The Glue job needs a JDBC connection that requires the database password. The engineer must ensure the password is not stored in plain text in the template or version control. Which approach is MOST secure?
  • A. Store the database password in AWS Secrets Manager, reference it in CloudFormation using dynamic references ({{resolve:secretsmanager:secret-name:SecretString:password}}), and configure the Glue connection to retrieve the credential at runtime from Secrets Manager
  • B. Pass the password as a CloudFormation parameter with NoEcho set to true and store it directly in the Glue connection properties
  • C. Encrypt the password with Base64 encoding and embed it in the template
  • D. Store the password in an S3 bucket with restricted access and have the Glue job read it at startup
Jawaban Benar: A
Secrets Manager dynamic references resolve at deployment time without exposing the secret in the template, parameters, or CloudFormation state. Secrets Manager also provides automatic rotation, audit logging via CloudTrail, and fine-grained IAM access control. The secret never appears in plain text in CloudFormation outputs or events. Opsi B — NoEcho hides the parameter in the console but the value still exists in the stack's properties and can be retrieved via API. Opsi C — Base64 is encoding, not encryption; it's trivially reversible. Opsi D — S3 with restricted access lacks rotation, auditing, and the password is still stored as a file.
6
A data platform team uses AWS CDK to manage their Amazon Redshift cluster, associated VPC, and dependent Glue jobs. They need to separate the infrastructure into logical units because the Redshift cluster rarely changes but Glue jobs are updated weekly. Deploying everything together risks unintended changes to the cluster. Which CDK architecture BEST addresses this concern?
  • A. Split into separate CDK stacks: a Foundation stack (VPC, Redshift cluster) and a Pipeline stack (Glue jobs, crawlers). Use cross-stack references via CfnOutput and Fn.importValue to share the Redshift endpoint and VPC subnet IDs from Foundation to Pipeline stack, allowing independent deployment lifecycles
  • B. Keep everything in one stack but add comments to mark sections that shouldn't be changed
  • C. Create a single stack with all resources and use CloudFormation resource-level policies to prevent modifications to Redshift
  • D. Deploy Redshift manually through the console and only manage Glue jobs with CDK
Jawaban Benar: A
Separate stacks with different deployment lifecycles is a CDK best practice. The Foundation stack (VPC, Redshift) deploys infrequently and requires change approval. The Pipeline stack (Glue jobs) deploys weekly without risking Redshift changes. Cross-stack references (CfnOutput/importValue) share necessary values between stacks while maintaining independence. Each stack has its own change set review. Opsi B — comments don't prevent accidental changes; all resources deploy together. Opsi C — stack policies prevent modifications but resources still share a deployment lifecycle and blast radius. Opsi D — manual resources outside IaC create configuration drift and lose repeatability benefits.
7
A team manages their data lake infrastructure with CloudFormation. During a stack update to modify a Glue job's worker count, CloudFormation unexpectedly attempts to replace the S3 bucket used as the data lake, which would delete all existing data. The engineer needs to understand why and prevent data loss. What is the MOST likely cause and appropriate preventive measure?
  • A. The S3 bucket's logical name or a property that requires replacement (like BucketName) was changed. Prevent this by using CloudFormation change sets to preview all changes before execution, applying DeletionPolicy: Retain on critical resources, and enabling stack termination protection
  • B. CloudFormation randomly replaces resources during updates as part of its optimization strategy
  • C. The Glue job modification triggered a cascade replacement of all resources in the stack
  • D. Roll back the update immediately and never modify the stack again
Jawaban Benar: A
CloudFormation replaces resources when properties that require replacement are modified (e.g., changing an S3 BucketName creates a new bucket and deletes the old one). Change sets preview all additions, modifications, and replacements BEFORE execution — the engineer would have seen the replacement and aborted. DeletionPolicy: Retain ensures CloudFormation never deletes the resource even if removed from the template. Stack termination protection prevents accidental full-stack deletion. Opsi B — CloudFormation never randomly replaces resources; all changes are deterministic based on template differences. Opsi C — resource replacement is per-resource, not cascading unless there are explicit dependencies. Opsi D — avoiding all updates defeats the purpose of IaC.

A startup needs to rapidly prototype a data pipeline that includes a Kinesis Data Stream, a Lambda consumer, a DynamoDB table for state tracking, and an S3 bucket for processed data. The sole data engineer is proficient in Python but has limited CloudFormation YAML/JSON experience. They need to deploy the infrastructure within hours, not days. Which IaC tool is MOST appropriate?
  • A. AWS CDK with Python, using L2 constructs that provide sensible defaults and reduce boilerplate — for example, a single line creates a Kinesis stream with default settings, and grant methods simplify IAM permissions (stream.grant_read(lambda_function))
  • B. Write raw CloudFormation YAML templates from scratch, manually defining every property including IAM policies
  • C. Use Terraform with HCL since it's the industry standard regardless of team expertise
  • D. Create all resources through the AWS Console and export them to CloudFormation later
Jawaban Benar: A
AWS CDK with Python leverages existing programming skills — no new language to learn. L2 constructs provide intelligent defaults (encryption enabled, logging configured) and type-safe interfaces with IDE autocomplete. Grant methods (stream.grant_read()) generate least-privilege IAM policies automatically, eliminating complex policy authoring. CDK synthesizes to CloudFormation for deployment, giving full CloudFormation benefits with developer-friendly authoring. Opsi B — raw CloudFormation requires learning YAML/JSON syntax and manually writing verbose IAM policies, taking days. Opsi C — Terraform requires learning HCL, a new language, adding time. Opsi D — console creation provides no repeatability and is the problem IaC solves.

A data engineering team uses CloudFormation to manage an EMR cluster for their data processing workloads. They need the EMR cluster to be automatically provisioned with specific bootstrap actions, step configurations, and security groups that reference other stack resources. The team also needs the ability to update the cluster's instance count without recreating the entire cluster. Which template design approach BEST meets these requirements?
  • A. Define the EMR cluster with Ref and Fn::GetAtt to reference security groups and subnets from the same template, use the Configurations property for application settings, define BootstrapActions inline, and set the InstanceCount as a parameter so updates only modify the instance group without cluster replacement
  • B. Create the EMR cluster outside CloudFormation and reference it using a hardcoded cluster ID in the template
  • C. Define all EMR configurations in a separate JSON file on S3 and reference it via a custom resource Lambda
  • D. Use a single monolithic parameter for all EMR settings as a comma-separated string
Jawaban Benar: A
Using Ref and Fn::GetAtt creates dynamic references to other stack resources (security groups, subnets), ensuring consistency. Inline BootstrapActions and Configurations keep the entire cluster definition self-contained in the template. Parameterizing InstanceCount allows scale-up/down via parameter updates without triggering cluster replacement (since InstanceCount changes are in-place updates for EMR instance groups). Opsi B — external resources create drift and lose dependency tracking. Opsi C — over-engineering with custom resources adds complexity and failure points. Opsi D — comma-separated strings are fragile, unvalidated, and impossible to maintain.

A financial services company must maintain strict change control for their production data pipeline infrastructure. Any infrastructure change must be reviewed, approved, and auditable. The team uses CloudFormation and needs to ensure that production deployments cannot bypass the approval process while still allowing rapid iteration in development. Which governance approach MOST effectively balances speed and control?
  • A. Implement a CI/CD pipeline where development deploys execute automatically after tests pass, but production deploys require a manual approval action in CodePipeline. Use CloudFormation change sets that generate a detailed diff for reviewers, and enable CloudTrail logging for all CloudFormation API calls to maintain an audit trail
  • B. Require manual approval for all deployments including development to maintain consistency
  • C. Allow automatic deployment to all environments and rely on rollback if issues are detected
  • D. Restrict CloudFormation access to a single administrator who performs all deployments manually
Jawaban Benar: A
This approach provides defense in depth: automated dev deploys enable rapid iteration without bottlenecks. Manual approval gates in CodePipeline enforce review for production. Change sets show exactly what will change (add/modify/replace/delete) so reviewers make informed decisions. CloudTrail provides audit trail showing who approved what and when — critical for financial services compliance. Opsi B — requiring approval for dev deploys slows iteration without adding production safety. Opsi C — automatic production deployment violates change control requirements; rollback doesn't prevent initial impact. Opsi D — a single admin creates a bottleneck, single point of failure, and doesn't provide peer review.
