A social media startup uses AWS Cloud to manage its IT infrastructure. The data engineering team at the startup wants to perform weekly database rollovers for a MySQL database server using a serverless cron job that typically takes about 5 minutes to execute the database rollover script written in Python. The database rollover will archive the past week’s data from the production database to keep the database small while still keeping its data accessible.

Which of the following would you recommend as the MOST cost-efficient and reliable solution?

Jawaban benar

Schedule a weekly Amazon EventBridge event cron expression to invoke an AWS Lambda function that runs the database rollover job

Karena

Opsi yang benar:

Schedule a weekly Amazon EventBridge event cron expression to invoke an AWS Lambda function that runs the database rollover job

AWS Lambda memungkinkan Anda menjalankan kode tanpa menyediakan atau mengelola server. Anda hanya membayar untuk waktu komputasi yang digunakan. AWS Lambda mendukung ekspresi rate dan cron standar untuk frekuensi hingga satu kali per menit.

Ekspresi penjadwalan menggunakan rate atau cron:

Opsi yang salah:

Create a time-based schedule option within an AWS Glue job to invoke itself every week and run the database rollover script - AWS Glue adalah layanan extract, transform, and load (ETL) yang terkelola sepenuhnya yang memudahkan pelanggan menyiapkan dan memuat data mereka untuk analitik. AWS Glue job ditujukan untuk pemrosesan data ETL secara batch dan tidak cocok untuk menjalankan database rollover script. Meskipun AWS Glue juga serverless, AWS Lambda merupakan opsi yang lebih hemat biaya dibandingkan AWS Glue.

Provision an Amazon EC2 spot instance to run the database rollover script to be run via an OS-based weekly cron expression - Spot Instance adalah Amazon EC2 instance yang tidak terpakai yang tersedia dengan harga lebih murah daripada On-Demand. Karena Spot Instance memungkinkan Anda meminta Amazon EC2 instance yang tidak terpakai dengan diskon besar, Anda dapat menurunkan biaya Amazon EC2 secara signifikan (hingga 90% lebih murah dari harga On-Demand). Karena Spot Instance berjalan kapan pun kapasitas tersedia, tidak ada jaminan bahwa pekerjaan mingguan akan dijalankan pada jendela waktu yang ditentukan. Selain itu, use case yang diberikan membutuhkan solusi serverless, sehingga opsi ini salah.

Provision an Amazon EC2 on-demand instance to run the database rollover script to be run via an OS-based weekly cron expression - Amazon EC2 on-demand instance memang dapat digunakan untuk menjalankan database rollover script yang dijalankan melalui OS-based weekly cron expression. Namun, use case yang diberikan membutuhkan solusi serverless, sehingga opsi ini salah.

A retail company maintains a central Amazon Redshift data warehouse that receives daily sales, inventory, and customer activity data from Amazon RDS for SQL Server and Amazon Aurora PostgreSQL databases. Several reporting teams run the same complex transformation queries each morning to calculate margin trends, regional demand forecasts, and customer segment metrics. A data engineer observes that these queries take several hours to complete and must reduce execution time as much as possible.

Which solution will meet this requirement?

Jawaban benar

Create Amazon Redshift materialized views for the frequently queried transformation patterns and refresh the views after the daily data loads finish

Karena

Opsi yang benar:

Create Amazon Redshift materialized views for the frequently queried transformation patterns and refresh the views after the daily data loads finish

Amazon Redshift materialized views dirancang untuk meningkatkan performa pada beban kerja analitik yang berulang dan dapat diprediksi. Sebuah materialized view menyimpan hasil yang telah dihitung sebelumnya dari sebuah query SQL, sehingga query berikutnya dapat menggunakan kembali hasil yang tersimpan alih-alih menghitung ulang setiap join, agregasi, dan transformasi dari tabel dasar.

Pendekatan ini cocok untuk skenario tersebut karena tim pelaporan menjalankan pola transformasi kompleks yang sama setiap pagi setelah pemuatan data harian. Data engineer dapat membuat materialized views untuk pola tersebut dan me-refresh view setelah pemuatan selesai, sehingga laporan dapat membaca hasil yang telah dihitung sebelumnya.

Solusi ini mengurangi waktu eksekusi query sebanyak mungkin di antara pilihan yang ada karena secara langsung menghindari eksekusi berulang dari logika transformasi yang mahal. Meningkatkan concurrency, mengekspor data, atau memindahkan query ke external tables tidak menghilangkan beban komputasi berat dari query berulang dengan cara yang sama.

via - https://docs.aws.amazon.com/redshift/latest/dg/materialized-view-overview.html

via - https://docs.aws.amazon.com/redshift/latest/dg/materialized-view-overview.html

Opsi yang salah:

Increase the concurrency scaling quota for the Amazon Redshift cluster so more reporting queries can run at the same time - Concurrency scaling dapat membantu Amazon Redshift mendukung lebih banyak query bersamaan ketika cluster mengalami tekanan antrean. Ini dapat meningkatkan throughput ketika banyak pengguna mengirimkan query pada waktu yang sama.

Namun, masalahnya adalah masing-masing query transformasi kompleks membutuhkan waktu berjam-jam untuk selesai. Meningkatkan kuota concurrency scaling tidak menghitung hasil terlebih dahulu atau mengurangi secara substansial pekerjaan yang dibutuhkan oleh setiap query yang mahal.

Create additional Amazon Redshift read-only clusters, copy the transformed tables to each cluster after the daily load, and route each reporting team to a separate cluster endpoint - Read-only cluster yang terpisah dapat mengurangi perebutan beban kerja antar tim. Ini dapat membantu ketika banyak tim bersaing untuk sumber daya Redshift cluster yang sama.

Namun, menyalin tabel yang sudah ditransformasi ke beberapa cluster menambah perpindahan data, sinkronisasi, biaya, dan beban operasional. Pendekatan ini juga tidak mengatasi akar masalah seefisien menyimpan hasil kompleks yang sering digunakan dalam materialized views.

Create Redshift Spectrum external tables over the Redshift warehouse tables and rewrite the complex transformation queries to reference the external tables - Redshift Spectrum dapat menjalankan query pada external tables atas data yang berada di Amazon S3. Ini berguna ketika pengguna Redshift perlu melakukan query pada file data lake tanpa memuat semua data ke dalam tabel Redshift lokal.

Namun, opsi ini secara keliru menggunakan Spectrum external tables sebagai lapisan performa di atas Redshift warehouse tables. Spectrum tidak dimaksudkan untuk membuat external tables berdasarkan tabel Redshift, dan tidak akan menghitung terlebih dahulu transformasi yang kompleks.

A digital media company has hired you to improve the data backup solution for applications running on the AWS Cloud. Currently, all of the applications running on AWS use at least two Availability Zones (AZs). The updated backup policy at the company mandates that all nightly backups for its data are durably stored in at least two geographically distinct Regions for Production and Disaster Recovery (DR) and the backup processes for both Regions must be fully automated. The new backup solution must ensure that the backup is available to be restored immediately for the Production Region and should be restored within 24 hours in the DR Region.

Which of the following represents the MOST cost-effective solution that will address the given use-case?

Jawaban benar

Create a backup process to persist all the data to an S3 bucket A using the S3 standard storage class in the Production Region. Set up cross-Region replication of this S3 bucket A to an S3 bucket B using S3 standard storage class in the DR Region and set up a lifecycle policy in the DR Region to immediately move this data to Amazon Glacier Deep Archive

Karena

Opsi yang benar:

Create a backup process to persist all the data to an S3 bucket A using the S3 standard storage class in the Production Region. Set up cross-Region replication of this S3 bucket A to an S3 bucket B using S3 standard storage class in the DR Region and set up a lifecycle policy in the DR Region to immediately move this data to Amazon Glacier Deep Archive

S3 Replication memungkinkan penyalinan objek secara otomatis dan asinkron antar Amazon S3 bucket. Ada dua jenis Replication:

Cross-Region Replication (CRR) digunakan untuk menyalin objek antar Amazon S3 bucket di AWS Region yang berbeda.

Same-Region replication (SRR) digunakan untuk menyalin objek antar Amazon S3 bucket di AWS Region yang sama.

via - https://docs.aws.amazon.com/AmazonS3/latest/dev/replication.html

Untuk use case yang diberikan, Anda dapat menyiapkan cross-Region replication dari S3 bucket A menggunakan S3 standard storage class di production Region ke S3 bucket B menggunakan S3 standard storage class di DR Region dan selanjutnya membuat lifecycle policy untuk mentransisikan data di bucket B dari standard storage class ke Amazon Glacier Deep Archive.

Perhatikan transisi yang diizinkan untuk S3 Lifecycle Policy: via - https://docs.aws.amazon.com/AmazonS3/latest/dev/lifecycle-transition-general-considerations.html

Secara default, Amazon S3 menyimpan replika objek menggunakan storage class yang sama dengan objek sumber. Anda juga dapat menentukan storage class yang berbeda untuk replika. Ini memungkinkan Anda menggunakan sesuatu seperti S3 Standard-IA untuk replica bucket, namun, S3 standard IA memiliki biaya minimum durasi penyimpanan 30 hari sehingga membuatnya lebih mahal dibandingkan menggunakan S3 Standard storage class untuk skenario yang diberikan karena data akan segera dipindahkan ke Glacier Deep Archive melalui Lifecycle policy.

via - https://aws.amazon.com/s3/storage-classes/

Opsi yang salah:

Create a backup process to persist all the data to an S3 bucket A using the S3 standard storage class in the Production Region. Set up cross-Region replication of this S3 bucket A to an S3 bucket B using S3 standard-IA storage class in the DR Region and set up a lifecycle policy in the DR Region to immediately move this data to Amazon Glacier Deep Archive - Seperti yang disebutkan dalam penjelasan di atas, S3 standard IA memiliki biaya minimum durasi penyimpanan 30 hari sehingga membuatnya lebih mahal dibandingkan menggunakan S3 Standard storage class untuk skenario yang diberikan, sehingga opsi ini salah.

Create a backup process to persist all the data to Amazon Glacier Deep Archive in the Production Region. Set up cross-Region replication of this data to Amazon Glacier Deep Archive in the DR Region to ensure minimum possible costs in both Regions - Salah satu persyaratan utama skenario yang diberikan adalah memastikan bahwa backup tersedia untuk dipulihkan segera untuk Production Region. Namun, Glacier Deep Archive memiliki first-byte latency hingga beberapa jam saat memulihkan data, sehingga opsi ini tidak tepat untuk use case yang diberikan.

Create a backup process to persist all the data to a large Amazon EBS volume attached to the backup server in the Production Region. Run nightly cron jobs to snapshot these volumes and then copy these snapshots to the DR Region - Salah satu persyaratan utama skenario yang diberikan adalah memastikan bahwa backup bersifat durable, tetapi data dalam EBS volume hanya direplikasi dalam Availability Zone-nya sehingga tidak sangat durable. Namun, EBS snapshots disimpan di Amazon S3 yang bersifat durable. Masalah dengan opsi ini adalah menambah biaya tambahan EBS volume dan juga tidak mengoptimalkan biaya penyimpanan di DR Region karena tidak memanfaatkan Glacier Deep Archive untuk penyimpanan data backup.

💡 Tips

Jika backup ke 2 region, Produksi restore instan & DR ≤24 jam, hemat maka S3 Standard (Produksi) + CRR ke region DR + Lifecycle ke Glacier Deep Archive karena CRR salin otomatis & Deep Archive termurah untuk DR 24 jam.Ingat: replikasi lintas region = CRR; restore 24 jam boleh → Glacier Deep Archive.

A healthcare analytics company maintains an Amazon S3 based data lake that contains datasets for clinical operations, finance, research, and compliance teams. The data lake receives several million patient interaction records each day. A data engineer must design an access control solution that allows each department to access only the datasets and columns that the department is authorized to use. The solution must enforce least privilege and minimize ongoing permission management effort.

Which solution will meet these requirements with the LEAST operational effort?

Jawaban benar

Set up AWS Lake Formation, assign LF-Tags to AWS Glue Data Catalog resources, and enable Lake Formation tag-based access control for department-specific permissions

Karena

Opsi yang benar:

Set up AWS Lake Formation, assign LF-Tags to AWS Glue Data Catalog resources, and enable Lake Formation tag-based access control for department-specific permissions

AWS Lake Formation menyediakan tata kelola terpusat untuk data lake yang menggunakan Amazon S3 dan AWS Glue Data Catalog. Lake Formation permissions dapat mengontrol akses ke database, table, column, dan data S3 yang mendasarinya untuk layanan analitik yang didukung.

Lake Formation tag-based access control, atau LF-TBAC, memungkinkan perusahaan menetapkan LF-Tags ke Data Catalog resources dan memberikan izin berdasarkan ekspresi tag. Sebagai contoh, perusahaan dapat memberi tag pada dataset berdasarkan departemen, tingkat sensitivitas, region, atau domain data, lalu memberikan setiap departemen akses hanya ke resource yang cocok dengan nilai tag yang disetujui.

Solusi ini memiliki beban operasional paling kecil untuk data lake berskala besar dengan banyak departemen karena menghindari pemeliharaan sejumlah besar IAM policy spesifik per resource. Ketika dataset baru tiba, data steward dapat mengklasifikasikan resource dengan LF-Tags, dan izin berbasis tag yang sudah ada dapat terus menegakkan least privilege dalam skala besar.

via - https://aws.amazon.com/blogs/big-data/build-a-modern-data-architecture-and-data-mesh-pattern-at-scale-using-aws-lake-formation-tag-based-access-control/

via - https://aws.amazon.com/blogs/big-data/build-a-modern-data-architecture-and-data-mesh-pattern-at-scale-using-aws-lake-formation-tag-based-access-control/

Opsi yang salah:

Deploy an Amazon RDS for PostgreSQL database with the aws_s3 extension, use AWS Step Functions to invoke Lambda functions that synchronize department-specific S3 data into tables, and grant database permissions by department - Amazon RDS for PostgreSQL dengan ekstensi aws_s3 dapat mengimpor atau mengekspor data antara PostgreSQL dan Amazon S3. Ini dapat mendukung alur kerja yang berpusat pada database yang perlu memindahkan file ke dalam atau keluar dari PostgreSQL.

Namun, opsi ini membuat salinan database terpisah dari konten data lake dan membutuhkan logika sinkronisasi khusus. Ini tidak menyediakan tata kelola lake terpusat lintas S3 dataset, metadata Glue Data Catalog, izin table, dan akses level kolom.

Use S3 Access Points for each department, configure one access point policy per department, and require data engineers to update the access point policies whenever datasets, columns, or department permissions change - S3 Access Points dapat menyederhanakan pengelolaan akses untuk dataset bersama dengan membuat access point bernama yang memiliki policy berbeda. Ini dapat berguna ketika beberapa aplikasi atau tim membutuhkan jalur akses berbeda ke bucket yang sama.

Namun, opsi ini tetap mengharuskan data engineer mengelola access point policy ketika dataset dan izin departemen berubah. Ini juga tidak menyediakan izin Data Catalog yang sama rincinya, kontrol level kolom, dan model tata kelola berbasis tag yang disediakan Lake Formation LF-TBAC.

Use Amazon Redshift and Amazon Redshift Spectrum as the only query layer for the data lake, and configure one Redshift IAM role with access to the S3 datasets - Amazon Redshift Spectrum dapat melakukan query pada data yang disimpan di Amazon S3, dan Redshift dapat mengambil peran IAM role untuk mengakses data eksternal. Pendekatan ini dapat menyediakan titik masuk SQL yang terkontrol untuk beberapa beban kerja analitik.

Namun, satu Redshift IAM role dengan akses S3 yang luas tidak menegakkan least privilege spesifik per departemen di seluruh data lake. Ini juga menjadikan Redshift sebagai lapisan akses utama alih-alih menggunakan Lake Formation untuk mengatur akses secara terpusat di seluruh layanan analitik yang didukung.

An e-commerce company performs analytics on the company's data using the Amazon Redshift cluster. The Redshift cluster has two important tables: the orders table and the product table which have millions of rows each. A few small tables with supporting data are also present. The team is looking for the right distribution patterns for the tables, to optimize query speed.

Which of the following are the key points to consider while planning for the best distribution style for your data? (Select two)

Jawaban benar

If a dimension table cannot be collocated with the fact table or other important joining tables, use ALL distribution style for such tables

Data should be distributed in such a way that the rows that participate in joins are already collocated on the nodes with their joining rows in other tables

Karena

Opsi yang benar:

Data should be distributed in such a way that the rows that participate in joins are already collocated on the nodes with their joining rows in other tables

Tujuan utama distribusi data adalah meminimalkan perpindahan data saat query berjalan. Oleh karena itu, jika baris yang berpartisipasi dalam join atau agregasi sudah ditempatkan bersama (collocated) pada node dengan baris pasangan join-nya di tabel lain, optimizer tidak perlu mendistribusikan ulang sebanyak itu data saat query berjalan.

If a dimension table cannot be collocated with the fact table or other important joining tables, use ALL distribution style for such tables

Ketika Anda menjalankan query, query optimizer mendistribusikan ulang baris ke compute node sesuai kebutuhan untuk melakukan join dan agregasi apa pun. Tujuan dalam memilih table distribution style adalah meminimalkan dampak langkah redistribusi dengan menempatkan data di lokasi yang dibutuhkan sebelum query dijalankan.

Salah satu pendekatan terbaik adalah mengubah beberapa dimension table agar menggunakan ALL distribution. Jika sebuah dimension table tidak dapat ditempatkan bersama dengan fact table atau tabel join penting lainnya, Anda dapat meningkatkan performa query secara signifikan dengan mendistribusikan seluruh tabel ke semua node. Menggunakan ALL distribution melipatgandakan kebutuhan ruang penyimpanan dan meningkatkan waktu pemuatan serta operasi pemeliharaan, jadi Anda harus menimbang semua faktor sebelum memilih ALL distribution.

Memilih distribution style terbaik: via - https://docs.aws.amazon.com/redshift/latest/dg/c_best-practices-best-dist-key.html

Opsi yang salah:

Choose a column with low cardinality in the filtered result set - Ini salah. Kolom dengan high cardinality yang seharusnya dipertimbangkan dalam filtered result set. Jika Anda mendistribusikan tabel sales pada kolom date, misalnya, Anda mungkin akan mendapatkan distribusi data yang cukup merata, kecuali sebagian besar penjualan Anda bersifat musiman. Namun, jika Anda biasanya menggunakan range-restricted predicate untuk memfilter periode tanggal yang sempit, sebagian besar baris yang terfilter berada pada sejumlah slice yang terbatas dan beban kerja query menjadi skewed.

A fact table with multiple distribution keys is useful when multiple dimension tables have to be joined to it - Fact table Anda hanya dapat memiliki satu distribution key. Tabel apa pun yang di-join pada key lain tidak ditempatkan bersama dengan fact table. Pilih satu dimensi untuk ditempatkan bersama berdasarkan seberapa sering dilakukan join dan ukuran baris join-nya.

Small Dimension tables should be marked to use KEY distribution style, which will cause them to be replicated to each physical node in the cluster - Dalam KEY distribution style, baris didistribusikan sesuai nilai pada satu kolom. Leader node menempatkan nilai yang cocok pada node slice yang sama. Jika Anda mendistribusikan sepasang tabel pada joining key-nya, leader node menempatkan baris pada slice sesuai nilai pada joining column. Dengan cara ini, nilai yang cocok dari kolom bersama secara fisik disimpan bersama.

Salinan seluruh tabel didistribusikan ke setiap node dalam ALL distribution style.

💡 Tips

Jika pilih distribution style Redshift (fact besar + dimensi kecil) maka join collocated via KEY, dimensi kecil pakai ALL karena KEY menaruh baris join di node sama & ALL mereplikasi tabel kecil ke semua node.Ingat: KEY = tabel besar yang di-join; ALL = dimensi kecil; EVEN = tanpa pola join.

A financial services company is implementing a data mesh architecture on AWS. The market analytics, credit risk, and regulatory reporting domains each own their own datasets and must share only approved views with other domains. The company has more than 1,200 tables across 60 databases in the AWS Glue Data Catalog. All domains use Amazon Athena for ad hoc analysis and Amazon Redshift for complex reporting. The regulatory reporting team must audit all data access, and personally identifiable information must be hidden from teams that do not have approval to view it. The company needs a scalable solution that supports cross-domain analysis across both query engines.

Which solution will meet these requirements?

Jawaban benar

Use AWS Glue Data Catalog views for shared domain views, manage access with Lake Formation, audit access with CloudTrail, and use security definer views to mask PII

Karena

Opsi yang benar:

Use AWS Glue Data Catalog views for shared domain views, manage access with Lake Formation, audit access with CloudTrail, and use security definer views to mask PII

AWS Glue Data Catalog views menyediakan cara yang scalable untuk mendefinisikan view bersama atas data yang terdaftar di AWS Glue Data Catalog. Perusahaan dapat membuat view yang disetujui untuk setiap domain dan hanya mengekspos kolom dan baris yang boleh di-query oleh tim lain.

Data Catalog views mendukung objek view umum yang dapat di-query pengguna dari layanan seperti Amazon Athena dan Amazon Redshift. Ini penting karena perusahaan membutuhkan analisis ad hoc di Athena dan pelaporan kompleks di Redshift tanpa membuat definisi view yang terpisah dan tidak konsisten untuk setiap engine.

Lake Formation dapat mengelola akses ke view dan data terkelola yang mendasarinya, sementara CloudTrail dapat mendukung audit akses data. Semantik security definer view membantu melindungi tabel yang mendasarinya dan memungkinkan perusahaan menyamarkan atau menghilangkan field PII pada view bersama sambil tetap mengaktifkan analitik lintas domain.

via - https://aws.amazon.com/blogs/big-data/automate-creating-aws-glue-data-catalog-views-with-aws-sdk-for-data-mesh-use-case/

Opsi yang salah:

Create standard Athena views for each domain, use those Athena views from Amazon Redshift for cross-domain reporting, enable CloudTrail auditing, and use Lake Formation table permissions - Athena views dapat mendukung analisis sesuai permintaan di Athena, dan Lake Formation dapat membantu mengatur akses ke data yang telah dikatalogkan. CloudTrail juga dapat mendukung audit untuk alur kerja tata kelola dan kepatuhan.

Namun, standard Athena views bukanlah lapisan view bersama yang paling scalable untuk Athena dan Amazon Redshift sekaligus. Persyaratan membutuhkan pendekatan lintas engine yang umum untuk banyak database dan table, yang memang dirancang untuk disediakan oleh AWS Glue Data Catalog views.

Create separate S3 prefixes for each domain, use IAM policies to control access to each prefix, and require Athena and Redshift users to query only their assigned prefixes - IAM policies dan S3 prefix dapat membatasi akses ke data pada lapisan penyimpanan. Pendekatan ini dapat bekerja untuk tata letak data lake sederhana di mana batas akses selaras rapi dengan jalur objek.

Namun, akses level prefix terlalu kasar untuk berbagi view spesifik, menyamarkan PII, dan mendukung analitik lintas domain yang terperinci pada banyak table dan database. Ini juga tidak menyediakan lapisan view yang konsisten untuk Athena dan Redshift.

Create Amazon Redshift materialized views for each domain, publish Redshift datashares to the other teams, and use Redshift permissions for all cross-domain analysis - Amazon Redshift materialized views dan datashares dapat mendukung pelaporan dan berbagi data terkontrol dalam arsitektur yang berpusat pada Redshift. Ini dapat berguna ketika pola akses analitik utama ada di dalam Redshift.

Namun, opsi ini tidak menyediakan lapisan tata kelola bersama untuk Athena dan Redshift sekaligus. Ini juga menjadikan Redshift sebagai pusat model akses data mesh, sedangkan persyaratan mencakup pengguna Athena dan AWS Glue Data Catalog resources di banyak domain.

💡 Tips

Jika data mesh berbagi view antar domain + audit + mask PII, lintas Athena & Redshift maka Glue Data Catalog views + Lake Formation + CloudTrail + security-definer views karena kombinasi ini berbagi aman, mengaudit, & menyembunyikan PII.Ingat: berbagi view lintas engine → Glue Data Catalog views; audit → CloudTrail.

Dengan mem-partisi data Anda, Anda dapat membatasi jumlah data yang dipindai oleh setiap query, sehingga meningkatkan performa dan mengurangi biaya. Anda dapat mem-partisi data berdasarkan key apa pun. Praktik umum adalah mem-partisi data berdasarkan waktu, yang sering menghasilkan skema partisi bertingkat. Sebagai contoh, pelanggan yang datanya masuk setiap jam mungkin memutuskan untuk mem-partisi berdasarkan year, month, date, dan hour. Pelanggan lain, yang datanya berasal dari banyak sumber berbeda tetapi hanya dimuat sekali per hari, mungkin mem-partisi berdasarkan identifier sumber data dan date.
