An application needs the output of SELECT query from Amazon Athena to be stored in an Amazon S3 bucket in Apache Parquet format. The data engineer has been advised against creating any additional tables in Athena.

How can this be achieved with the LEAST possible effort?

Jawaban benar

Use the UNLOAD statement in Athena

Karena

Correct option:

Use the UNLOAD statement in Athena

Amazon Athena automatically stores query results and metadata information for each query that runs in a query result location that you can specify in Amazon S3.

Writes query results from a SELECT statement to the specified data format. Supported formats for UNLOAD include Apache Parquet, ORC, Apache Avro, and JSON. CSV is the only output format supported by the Athena SELECT command, but you can use the UNLOAD command, which supports a variety of output formats, to enclose your SELECT query and rewrite its output to one of the formats that UNLOAD supports.

The UNLOAD statement is useful when you want to output the results of a SELECT query in a non-CSV format but do not require the associated table. For example, a downstream application might require the results of a SELECT query to be in JSON format, and Parquet or ORC might provide a performance advantage over CSV if you intend to use the results of the SELECT query for additional analysis.

Incorrect options:

Use the CREATE TABLE AS SELECT (CTAS) query in Athena - A CREATE TABLE AS SELECT (CTAS) query creates a new table in Athena from the results of a SELECT statement from another query.

Use the SELECT command in Athena - CSV is the only output format supported by the Athena SELECT command, so this option is incorrect.

Use the CREATE TABLE AS SELECT (CTAS) and INSERT INTO statements in Athena - You can use Create Table as Select (CTAS) and INSERT INTO statements in Athena to extract, transform, and load (ETL) data into Amazon S3 for data processing. A new table will still be created in Athena.

A media analytics company runs Apache Spark jobs on an Amazon EMR cluster to process streaming playback events from connected devices. The Spark jobs transform the data and write the curated output to an Amazon S3 bucket. Analysts use Amazon Athena to query the curated data for viewing trends, device usage, and content engagement patterns. The company needs to choose data formats and metadata management approaches that provide the shortest Athena query times.

Which solutions will meet these requirements? (Select two)

Jawaban benar

Write the transformed data in ORC format and use AWS Glue Data Catalog to track schema metadata for Athena queries

Write the transformed data in Apache Parquet format and use AWS Glue Data Catalog to track schema metadata for Athena queries

Karena

Correct options:

Write the transformed data in ORC format and use AWS Glue Data Catalog to track schema metadata for Athena queries

ORC is a columnar storage format that is optimized for analytical queries. When Athena queries only selected columns, ORC allows the query engine to read less data than row-oriented formats such as JSON or CSV.

Using AWS Glue Data Catalog gives Athena the table and schema metadata that it needs to query the ORC files in Amazon S3. The cataloged schema helps analysts query the curated streaming output without manually defining metadata for each query.

This solution helps produce shorter query times because it combines a columnar format with a managed metadata catalog. The EMR Spark jobs can write ORC output, and Athena can use the Glue catalog table to query that data efficiently.

Write the transformed data in Apache Parquet format and use AWS Glue Data Catalog to track schema metadata for Athena queries

Apache Parquet is also a columnar storage format that is widely used for analytics on Amazon S3. Parquet can reduce the amount of data Athena scans when queries access only a subset of columns.

AWS Glue Data Catalog is the correct metadata layer for Athena. The company can catalog the Parquet data, track table definitions, and allow Athena to use the catalog when running SQL queries.

This combination meets the requirement for the shortest query times because Parquet is optimized for columnar reads, compression, and predicate pushdown. It is a strong fit for transformed streaming data that analysts query through Athena.

via - https://docs.aws.amazon.com/athena/latest/ug/columnar-storage.html

Incorrect options:

Write the transformed data in Avro format and use AWS Glue Data Catalog to track schema metadata for Athena queries - Avro is a row-oriented format that supports schema evolution and is useful for data serialization. It can be appropriate for streaming pipelines and message-oriented workloads that need compact encoded records.

This option falls short for Athena analytical query performance because Avro does not provide the same columnar read benefits as ORC or Parquet. When analysts query only selected columns, Athena can scan less data with columnar formats.

Write the transformed data in ORC format and store schema definitions in separate JSON files in Amazon S3 - ORC is a valid columnar file format for Athena and can improve query performance compared with row-based formats. The EMR Spark jobs could write curated output in ORC format.

This option does not meet the metadata management requirement because separate schema files in Amazon S3 are not the normal catalog that Athena uses for table metadata. Using AWS Glue Data Catalog provides the managed schema layer required for Athena queries.

Write the transformed data in Apache Parquet format and use an external DynamoDB table to track schema changes for Athena queries - Apache Parquet is an excellent format for Athena analytics because it is columnar and efficient for selected-column queries. The data format portion of this option is valid.

The metadata approach is the problem. Athena does not use an external DynamoDB table as the standard schema catalog for S3 datasets. AWS Glue Data Catalog is the managed catalog that Athena uses for table definitions and schema metadata.

Jika Athena query tercepat atas output EMR/Spark maka tulis Parquet/ORC + lacak metadata di Glue Data Catalog karena format kolumnar + katalog = scan minimal & skema terkelola.Ingat: format query tercepat Athena = kolumnar (Parquet/ORC) + Glue Catalog.

A financial services company encrypts its Amazon Redshift provisioned cluster by using AWS Key Management Service. The company is implementing a disaster recovery strategy that requires automated snapshot copies to a different AWS Region.

A data engineer must configure cross-Region snapshot copy by using the AWS CLI. The copied snapshots must remain encrypted with a KMS key that is valid in the destination Region.

Which combination of steps will meet these requirements? (Select two)

Jawaban benar

Enable snapshot copying in the source Region and specify the snapshot copy grant name that exists in the destination Region

Create a KMS key in the destination Region and create a Redshift snapshot copy grant that uses that destination KMS key

Karena

Correct options:

Create a KMS key in the destination Region and create a Redshift snapshot copy grant that uses that destination KMS key

Amazon Redshift requires a snapshot copy grant when copying snapshots of an AWS KMS-encrypted cluster to another Region. The grant permits Amazon Redshift to use a KMS key to encrypt the copied snapshots.

The KMS key must be valid in the destination Region because AWS KMS keys are Regional resources. Creating the KMS key and the snapshot copy grant in the destination Region allows Redshift to encrypt the copied snapshots correctly.

This step is necessary for disaster recovery because the company wants the cross-Region snapshot copies to remain encrypted. Without the destination Region KMS key and snapshot copy grant, Redshift cannot use the correct encryption configuration for the copied snapshots.

Enable snapshot copying in the source Region and specify the snapshot copy grant name that exists in the destination Region

After the destination Region snapshot copy grant exists, the data engineer must enable snapshot copying for the Redshift cluster from the source Region. The enable operation identifies the destination Region for copied snapshots.

For an encrypted Redshift cluster, the enable-snapshot-copy configuration must reference the snapshot copy grant that was created for the destination Region. This tells Redshift which grant to use when encrypting copied snapshots in the target Region.

This step completes the cross-Region copy setup. The destination Region grant handles encryption permissions, and the source Region snapshot copy setting starts the automated copy behavior for disaster recovery.

via - https://aws.amazon.com/blogs/big-data/migrate-your-amazon-redshift-cluster-to-another-aws-region/

Incorrect options:

Create a KMS key in the source Region and create a Redshift snapshot copy grant that uses the source Region key - Creating a KMS key in the source Region can support encryption of the source Redshift cluster. The source cluster might already use a KMS key for encryption at rest.

The limitation is that copied snapshots in another Region must use a KMS key that is valid in the destination Region. A snapshot copy grant tied only to a source Region key does not satisfy the destination Region encryption requirement.

Create an S3 bucket in the destination Region, export the encrypted Redshift snapshot to the bucket, and configure S3 replication - Amazon S3 replication can copy S3 objects across Regions. Exporting data to S3 can be useful for some analytics, archival, or lake-based recovery patterns.

This option falls short because Redshift cross-Region snapshot copy does not require exporting encrypted snapshots to S3. The managed Redshift snapshot copy feature uses a snapshot copy grant and destination Region KMS key.

Enable snapshot copying in the destination Region and specify the snapshot copy grant name that exists in the source Region - Enabling snapshot copy involves configuring the Redshift cluster to copy snapshots to another Region. The snapshot copy grant name is part of the encrypted snapshot copy configuration.

This option reverses the required direction. The engineer enables snapshot copying from the source Region and references the grant created for the destination Region, not the other way around.

Karena

Correct option:

Create an AWS Glue DataBrew project to profile the telemetry data, define completeness rules for event_timestamp, and configure numeric range validation for vibration values

AWS Glue DataBrew is the best fit for this requirement because it provides a visual, low-code way to profile datasets and define data quality rules. The data engineer can create a DataBrew project for the telemetry dataset and inspect the profile results to understand missing values, value distributions, and numeric characteristics.

DataBrew rulesets can define validation checks for specific columns. In this scenario, the engineer can define a completeness rule for event_timestamp and a numeric range rule that checks whether vibration values remain between 0 and 85 mm/s.

This solution meets the requirement with minimal coding because DataBrew provides built-in profiling and rule-based validation capabilities. The company does not need to write a custom scanner, build a separate transformation framework, or use machine learning anomaly detection for fixed business rules.

Incorrect options:

Use AWS Glue Data Quality rules with ML-based anomaly detection to learn unusual vibration behavior and detect records that do not include event timestamps - AWS Glue Data Quality can define rule-based checks, and anomaly detection can help identify unusual data behavior. This can be useful when the data team needs to monitor changing data patterns over time.

However, the requirement is to validate fixed conditions: missing timestamps and vibration values outside a known range. The original solution pattern expects AWS Glue DataBrew because it provides visual profiling and configurable rules for these checks with minimal coding.

Use Amazon CloudWatch anomaly detection on custom vibration metrics and configure AWS Glue crawlers to identify records that have missing timestamp values - CloudWatch anomaly detection can help identify unusual trends in published metrics. It can be useful for operational monitoring when the application emits metrics continuously.

However, this option does not validate each source record against a fixed numeric range. AWS Glue crawlers discover schema metadata, but they do not identify individual records that are missing timestamp values.

Create an AWS Glue DynamicFrame with a custom validation operator and use Amazon SageMaker Data Wrangler transforms to validate timestamps and vibration ranges - AWS Glue DynamicFrames can support custom transformations during ETL processing. However, this option introduces unnecessary custom logic and an additional ML preparation tool. The requested checks are straightforward data quality validations that DataBrew can configure through profiling and rules.

A logistics company needs a fully automated solution to check for new records in several operational data stores and process any records that the solution finds. The solution must run every hour and must work with Amazon RDS, Amazon DynamoDB, and Amazon OpenSearch Service. Each processing run will handle up to 8 MB of data at a time. The company wants to minimize cost and operational overhead while using reliable error handling.

Which solution will meet these requirements?

Jawaban benar

Use Amazon EventBridge Scheduler to invoke a Lambda function every hour to check each data store, send processing messages to Amazon SQS when the function finds new data, and use a second Lambda function to process the messages with retries and a dead-letter queue

Karena

Correct option:

Use Amazon EventBridge Scheduler to invoke a Lambda function every hour to check each data store, send processing messages to Amazon SQS when the function finds new data, and use a second Lambda function to process the messages with retries and a dead-letter queue

Amazon EventBridge Scheduler can invoke an AWS Lambda function on an hourly schedule. The first Lambda function can connect to Amazon RDS, Amazon DynamoDB, and Amazon OpenSearch Service to check for new data and create processing messages when it finds records that need work.

Amazon SQS decouples the discovery step from the processing step. The message can contain metadata, identifiers, or pointers to the records rather than the entire dataset. A second Lambda function can read messages from the SQS queue, retrieve the relevant data from the source service, and process up to the required 8 MB working set.

This solution has low operational overhead because it uses managed serverless services. It also has robust error handling because Lambda integrations with SQS support retries, visibility timeout behavior, and dead-letter queues for messages that fail processing repeatedly.

via - https://docs.aws.amazon.com/lambda/latest/dg/with-eventbridge-scheduler.html

Incorrect options:

Use Amazon Managed Workflows for Apache Airflow to create a DAG that runs every hour, checks each data store for new records, processes the records, and handles errors in Python operators - Amazon MWAA can schedule workflows and implement dependency management through Apache Airflow DAGs. It can also run Python operators that check multiple data stores and process results.

However, Amazon MWAA introduces an Airflow environment, DAG operations, worker configuration, monitoring, and platform-level administration. For an hourly process that handles only a small amount of data, Lambda with EventBridge Scheduler and SQS is more cost-effective and operationally simpler.

Spark also allows developers to implement custom error handling in the application code.

However, EMR is unnecessarily heavy for a workload that runs hourly and processes only up to 8 MB of data at a time. The company would pay for and manage a big data processing environment when a serverless Lambda-based design is sufficient.

Use AWS Glue workflows to run a crawler every hour against Amazon RDS, Amazon DynamoDB, and Amazon OpenSearch Service, then start AWS Glue ETL jobs to process all records that the crawlers discover - AWS Glue crawlers help discover schemas and update the AWS Glue Data Catalog. AWS Glue workflows can orchestrate Glue jobs, crawlers, and triggers.

However, crawlers are not the correct mechanism to check Amazon OpenSearch Service for new operational records every hour, and they do not provide a lightweight record-processing workflow for small data volumes. This design adds catalog and ETL overhead that the requirement does not need.

A media streaming company stores subscriber activity files in an Amazon S3 bucket. The company runs an analysis pipeline whenever a subscriber cancels a premium plan. The pipeline uses Lambda functions that respond to S3 events, clean the activity data, and start an AWS Glue workflow for downstream processing.

The Lambda functions are configured with 128 MB of memory, 512 MB of ephemeral storage, and a timeout of 20 seconds. The functions complete successfully, but monitoring shows that CPU usage is frequently close to 100 percent, which slows the pipeline. The company wants to improve function performance and reduce total pipeline runtime.

Which solution will meet these requirements?

Jawaban benar

Increase the memory allocation of the Lambda functions to 512 MB so the functions receive more proportional CPU capacity

Karena

Correct option:

Increase the memory allocation of the Lambda functions to 512 MB so the functions receive more proportional CPU capacity

AWS Lambda allocates CPU power in proportion to the amount of memory configured for a function. When a function is CPU-bound and CPU usage is frequently near 100 percent, increasing memory gives the function more compute capacity.

In this scenario, the Lambda functions are already completing successfully. The problem is slow performance caused by CPU saturation, not failures, lack of timeout, or missing network access. Increasing memory from 128 MB to 512 MB can reduce execution duration because the functions receive more CPU resources.

This solution directly addresses the bottleneck and can reduce the total runtime of the pipeline. The company should test the new memory setting and monitor duration, cost, and performance, but memory tuning is the correct Lambda configuration change for CPU-bound workloads.

Incorrect options:

Create a second set of Lambda functions with the same 128 MB memory setting and distribute S3 events across both function groups by using separate event notification prefixes - Splitting events across multiple function groups can increase concurrency or separate processing paths when the workload is limited by event distribution. This can be useful for some high-throughput event designs.

However, each individual function would still run with only 128 MB of memory and the same limited proportional CPU capacity. The per-invocation CPU bottleneck remains, so this option does not directly improve the slow data-cleaning logic.

Configure the Lambda functions to run in the company's VPC so the functions can use private networking for S3 and AWS Glue access - Configuring Lambda functions to run in a VPC can be necessary when functions must access private resources such as databases or internal services. It can also support private connectivity patterns through VPC endpoints.

However, VPC configuration does not increase CPU allocation for the functions. The bottleneck is CPU saturation during processing, so moving the functions into a VPC does not solve the performance problem.

Increase the Maximum Retry Attempts setting for the Lambda functions so failed invocations have more opportunities to complete successfully - Increasing Maximum Retry Attempts can help when asynchronous invocations fail intermittently. Retries can give failed events another chance to process successfully.

However, the functions are not failing. They complete successfully but slowly. Adding retries does not improve CPU capacity and can add more duplicate work if errors occur later.

💡 Tips

Jika Lambda CPU ~100% memperlambat pipeline maka naikkan memori (mis. 512 MB) karena di Lambda, CPU proporsional dengan memori yang dialokasikan.Ingat: Lambda — naikkan memori = naikkan CPU & jaringan (vCPU penuh ~1769 MB).

Karena

Correct option:

Use AWS Glue ETL jobs with an Evaluate Data Quality transform, IsComplete rules for required columns, and ReferentialIntegrity rules for related datasets

AWS Glue Data Quality can run inside AWS Glue ETL jobs by using the Evaluate Data Quality transform. This allows the pipeline to evaluate records before writing the curated output to storage.

The IsComplete rule checks whether a required column is complete, which means the column does not contain null values. This directly addresses the requirement to detect missing values in important columns before downstream reports consume the data.

The ReferentialIntegrity rule validates relationships between a primary dataset and a reference dataset. Combining IsComplete and ReferentialIntegrity rules in the AWS Glue ETL job provides managed, rule-based validation with less operational overhead than maintaining custom SQL checks or Python validation code.

This can help with exploratory data preparation.

The limitation is that this option does not provide the most direct managed validation step inside an AWS Glue ETL pipeline before storage. The requirement calls for repeatable null checks and referential integrity checks in the pipeline, which AWS Glue Data Quality supports directly.

Use AWS Glue ETL jobs with SQL transforms to check required columns for null values and run separate SQL queries for referential integrity - SQL transforms in AWS Glue can detect null values and compare datasets. A data engineer could write SQL logic to check required fields and validate relationships.

This option falls short because it requires custom SQL validation logic and ongoing maintenance for each rule and dataset relationship. AWS Glue Data Quality provides purpose-built DQDL rules for these checks with less operational overhead.

Use Lake Formation permissions to restrict access to incomplete records and apply LF-Tags to separate valid records from invalid records - Lake Formation can manage permissions for data lake resources and can use LF-Tags for scalable access control. This is useful for governance and authorization.

Which solution will meet this requirement?

Enable Auto Scaling for the AWS Glue ETL jobs so AWS Glue can add and remove workers dynamically as stream processing demand changes

Karena

Correct option:

Enable Auto Scaling for the AWS Glue ETL jobs so AWS Glue can add and remove workers dynamically as stream processing demand changes

AWS Glue Auto Scaling allows AWS Glue to automatically add and remove workers during a job run based on the parallelism and resource needs of the workload. This is useful for streaming ETL jobs that experience changing traffic patterns during the day.

The high glue.driver.BlockManager.disk.diskSpaceUsed_MB metric indicates that Spark is using significant disk space for cached blocks, shuffle outputs, broadcasts, or spilling. During peak periods, this can cause slower processing and delay the outlier notifications that the job sends to Amazon SNS.

This solution has the least operational effort because the data engineer does not need to manually test and maintain a fixed DPU setting for every traffic pattern. AWS Glue can scale workers up when the streaming workload requires more resources and scale workers down when demand decreases.
